Эта страница помогает выбрать место для нового кода, не нарушить границы системы и подготовить изменение к выпуску. Она предназначена и для тех, кто только присоединился к проекту. Наша основа: монорепозиторий → сервис → модуль.

Начните с первого знакомства, выбора компонента и порядка выполнения задачи. Затем откройте правила, которые относятся к вашему изменению. Перед выпуском в рабочую среду пройдите список проверок. Подробные технические требования нужны по мере работы.

Правила действуют для новых компонентов и существенных изменений. Существующие части улучшаем постепенно, когда работаем с ними. Эта страница задаёт требования; она не утверждает, что вся система уже им соответствует.

Первое знакомство с проектом

  1. Посмотрите общую карту. Она объясняет, какие части платформы есть и как они связаны: .

  2. Найдите место вашей задачи. Откройте README нужного приложения, сервиса или курса. Там ищем актуальные команды запуска и проверок.

  3. Уточните ответственность. Что меняем, кто использует эту часть и кто отвечает за неё. Если ответственного нет в документации, выясните его в команде до изменения общей границы.

  4. Выберите самый небольшой подходящий компонент. Для новой функции часто достаточно модуля. Отдельный сервис нужен, когда есть понятная причина независимо выпускать, защищать или масштабировать его.

Главные правила

  • У каждой части одна понятная ответственность. По названию и README должно быть ясно, зачем она существует.

  • Сервисы работают через договорённые интерфейсы. Не импортируем чужую реализацию и не обращаемся напрямую к чужим таблицам.

  • Модули скрывают свои внутренности. Используем публичные операции модуля, а не его приватные функции и модели хранения.

  • Добавление реплик должно быть безопасным. Запущенные копии не теряют сессии, не дублируют работу и не спорят за локальный файл.

  • Нагрузка ограничена. У запросов есть сроки ожидания, у фоновых задач — предел очереди, у процессов — бюджет ресурсов.

  • Сбой одной части имеет понятные последствия. Мы заранее определяем, что продолжит работать, что временно недоступно и как восстановиться.

  • Изменение сохраняет совместимость. Обновление одного сервиса не должно неожиданно ломать его потребителей.

  • Скорость и надёжность проверяем. Для обещания «стало быстрее» нужны измерения; для выпуска — результаты подходящих проверок.

В подробных правилах «Обязательно» означает условие приёмки. «Обычно» — принятое решение, от которого можно отступить с объяснением в PR. «Допустимо» — разрешённый вариант при указанных условиях. PR, или pull request, — предложение изменения кода для проверки командой. Номера вроде DATA-01 сохранены, чтобы на требования было удобно ссылаться.

Как выбрать компонент

Сервис отвечает за отдельную область продукта, владеет её данными и имеет свои интерфейсы. Модуль — связная часть кода внутри сервиса. Worker — процесс, который выполняет работу в фоне. Один сервис может содержать несколько модулей, HTTP API и несколько видов workers.

Пример с отчётом условный: он показывает способ выбора, а не наличие готовой функции. Отдельный worker не становится новым сервисом автоматически.

В Kubernetes workload — описание запуска определённой роли: API, worker или задачи. Pod — один запущенный экземпляр с одним или несколькими контейнерами. Реплики — несколько экземпляров такой роли. API и workers одного сервиса могут масштабироваться отдельно. Модуль внутри общего процесса отдельно по репликам не масштабируется: для этого его исполнение нужно выделить в отдельный workload или сервис.

Как выполнить задачу

  1. До кода: опишите ожидаемое поведение, место изменения, затронутых потребителей и данные. Для нового компонента заполните паспорт ниже; для небольшого модуля достаточно применимых пунктов в PR.

  2. При изменении архитектурной границы: сделайте короткую запись решения — ADR. Она нужна для нового сервиса, смены владельца данных, несовместимого интерфейса, новой инфраструктурной зависимости или существенного исключения из правил. Укажите проблему, варианты, выбор, последствия и проверку.

  3. Во время разработки: сохраняйте границы кода и данных. Добавляйте проверки изменённого поведения, совместимости, повторов и отказов там, где они имеют значение.

  4. Перед проверкой командой: в PR напишите, что изменилось, почему, как проверено и какие ограничения остались. Не заменяйте конкретные результаты словом «готово».

  5. Перед рабочей средой: пройдите применимые пункты раздела «Что проверить перед выпуском». Выпуск выполняйте по актуальной инструкции сервиса и runbook — инструкции эксплуатации и восстановления.

Подробные требования

Ниже — справочник для разработки и проверки. Выбирайте относящиеся к задаче разделы; обязательные требования применяются с учётом их условий.

Как разделять код

ARCH-01 · Обязательно: различаем сервис и модуль. Сервис может оставаться одним приложением с несколькими модулями. Его API и workers могут использовать общий образ, но имеют отдельные настройки ресурсов и числа реплик.

ARCH-02 · Обязательно: у части есть владелец и понятный вход. Опишите её ответственность и публичные операции. Циклов импортов между модулями быть не должно. Синхронные вызовы сервисов по кругу обычно устраняем. Обмен событиями по кругу допустим, если есть ответственный, защита от повторного эффекта и ограничение повторов.

ARCH-03 · Обязательно: объясняем появление нового сервиса. Сравните его с модулем или worker: что выиграем и сколько добавим сетевых вызовов, миграций и обслуживания. Если обычное изменение постоянно требует одновременно выпускать соседние сервисы, пересмотрите границу.

ARCH-04 · Обычно: выбираем простое достаточное решение. Новый брокер сообщений, service mesh — дополнительный слой управления межсервисной сетью, новая технология БД или распределённая транзакция требуют обоснования.

MOD-01 · Обязательно: используем публичные операции модуля. Не вызывайте его приватные helpers и не меняйте его состояние через внутренние модели хранения. Внутри одного сервиса допустимы общая БД и общая транзакция; ответственность за изменение данных остаётся явной.

MOD-02 · Обязательно: отделяем правила от технических подключений. Бизнес-логика не должна зависеть от HTTP, Kubernetes или конкретной БД. Подключение этих технологий выполняют адаптеры; приложение собирает их вместе. Новые слои нужны для реальной задачи, а не ради сложного дерева папок.

MOD-03 · Обязательно: не импортируем реализацию соседнего сервиса. Его Python/JS-код и модели ORM — объекты для работы с таблицами — не становятся общей библиотекой. Не делаем запуск всего репозитория условием сборки одного сервиса. Между сервисами используем объявленный протокол.

MOD-04 · Обычно: общие библиотеки содержат небольшой технический код. Общие бизнес-правила принадлежат своему владельцу. Проверяйте изменение библиотеки на затронутых потребителях; уже выпущенные сервисы продолжают использовать зафиксированные версии до обновления.

Пример: модуль практики обращается к публичной операции обучения для изменения прогресса. Доступ к внутренней функции или таблице другого владельца не заменяет эту операцию.

Как работать с данными

DATA-01 · Обязательно: у данных один сервис-владелец. Другие сервисы запрашивают их через API, получают события или создают согласованную копию для чтения. Нельзя читать и менять чужие таблицы, связывать их межсервисными JOIN или внешними ключами.

DATA-02 · Обязательно: разделяем доступ и миграции. У сервисов отдельные учётные данные и история миграций. Рабочий процесс получает только необходимые права на данные; изменение схемы БД выполняется отдельной ролью.

DATA-03 · Допустимо: несколько сервисов на одном PostgreSQL instance. У каждого должны быть отдельные базы и роли. Instance — один работающий сервер PostgreSQL: его CPU, диск и отказ остаются общими. При более строгих требованиях к нагрузке, безопасности или восстановлению разделяем и физические ресурсы.

DATA-04 · Обязательно: важное состояние переживает замену Pod. Сессии и координация не должны зависеть от памяти одной реплики, локального файла или постоянного направления пользователя в тот же Pod. Временные файлы и локальный кэш допустимы при безопасной потере и ограниченном объёме. Для общего изменяемого состояния определите правила одновременного доступа.

DATA-05 · Обязательно: умеем восстановить данные. Укажите, сколько их можно потерять и за какое время восстановить — RPO и RTO. Определите сроки хранения и удаление. Проверьте восстановление из резервной копии в изолированной среде.

Пример: будущая Analytics получает разрешённые события Core и хранит свои расчёты. Общий PostgreSQL instance не даёт ей права читать таблицы Core напрямую.

Как связывать сервисы и фоновые задачи

API-01 · Обязательно: описываем договорённость между сторонами. Контракт задаёт входные данные, ответы, ошибки, права и ограничения. Для HTTP используем OpenAPI; для событий и других протоколов — подходящую проверяемую схему. Проектируйте контракт вместе с потребителем до реализации.

API-02 · Обязательно: сохраняем работу потребителей. Предпочитайте совместимые дополнения. Проверяйте строгих клиентов и списки допустимых значений. Несовместимый интерфейс вводите с переходным периодом, наблюдением использования и планом отключения старого.

API-03 · Обязательно: ограничиваем ожидание и повторы. У внешнего вызова есть timeout — максимальное время ожидания, внутри общего срока операции. Повторы ограничены по числу и времени; учитывают уже имеющиеся повторы библиотек. При повторе используем растущую задержку со случайной добавкой — backoff с jitter. Повторяем только операции, для которых повтор безопасен, и только при подходящих ошибках. Не повторяем одну ошибку независимо на каждом слое.

API-04 · Обязательно: повтор не создаёт лишний результат. Timeout не доказывает, что операция не выполнилась. Определите, как узнать результат и безопасно повторить действие. При необходимости используйте ключ операции, срок его хранения и атомарную запись результата. Один ключ с другими параметрами отклоняется. Это свойство называют идемпотентностью; оно не гарантирует однократную обработку во всех внешних системах.

MSG-01 · Обычно: выбираем способ связи по сценарию. Синхронный запрос нужен, когда ответ требуется сразу. Фоновая обработка подходит, когда пользователь может подождать. В обоих случаях опишите последствия недоступности зависимости.

MSG-02 · Обязательно для критичных событий: не теряем принятую работу. Изменение данных и намерение отправить событие сохраняются надёжно. Один вариант — outbox: запись события в той же транзакции БД. Независимые записи «сначала БД, потом брокер» без защиты от частичного сбоя не подходят. Получатель выдерживает дубликаты; определены версия, нужный порядок, предел очереди, повторы, место для ошибочных сообщений и повторная обработка сохранённых событий. Подтверждение приёма или обработки — ACK — имеет описанный смысл и связано с надёжным сохранением соответствующего состояния.

MSG-03 · Обязательно: работа имеет понятный жизненный цикл. Опишите потерю worker, повторный запуск и возврат незавершённой задачи. Если прежний исполнитель ещё может изменить состояние после передачи работы другому, обязательна защита от такого изменения. Временное право обработки — lease — один из способов координации; его истечение тоже должно учитываться. Не запускайте одну плановую задачу в каждой API-реплике. Принятая сервером фоновая работа переживает отключение клиента; для остальных операций явно определите отмену и её последствия.

Как готовить компонент к Kubernetes

В этой части речь о каждой запускаемой роли отдельно: API, worker или задаче. Deployment обычно поддерживает постоянно работающие копии, Job запускает конечную работу, StatefulSet применяется там, где важны устойчивые идентификаторы и состояние. Выбор зависит от поведения компонента.

K8S-01 · Обязательно: контейнер запускается воспроизводимо. Он проверяет настройки и не требует ручных действий после старта. Конфигурация окружения и секреты передаются отдельно от образа. Нельзя привязывать приложение к конкретному IP Pod или серверу.

K8S-02 · Обязательно: задаём бюджет ресурсов. Укажите requests для CPU и памяти — ресурсы, которые учитывает Kubernetes при размещении, и memory limit — верхний предел памяти контейнера. Ограничьте временный диск. CPU limit выбирайте с учётом измеренного ограничения CPU — throttling; отсутствие limit требует объяснённого бюджета и защиты соседних компонентов.

K8S-03 · Обязательно: различаем готовность и зависание. Readiness сообщает, можно ли направлять HTTP-трафик в Pod. Startup probe даёт время долгому старту. Liveness нужна, если перезапуск помогает исправить зависание. Отказ БД не должен вызывать перезапуск исправного процесса. Readiness учитывает критичные зависимости. Проверки должны быть дешёвыми; необязательная функция не выключает весь сервис.

K8S-04 · Обязательно: безопасно останавливаемся. Обработайте сигнал остановки, перестаньте принимать новую работу и завершите текущую либо верните её для повтора. Время завершения — grace period — должно покрывать эти действия. Принудительное завершение тоже не должно повреждать состояние.

K8S-05 · Обязательно: описываем способ роста. У каждой роли есть понятный предел нагрузки и способ изменения числа реплик. Если масштабирование автоматическое, настройте HPA или подходящий контроллер: метрику, минимум, максимум и защиту от частых колебаний. Для HPA по проценту CPU нужны CPU requests; для workers полезной метрикой может быть размер очереди или возраст ожидающей задачи.

K8S-06 · Обязательно: проверяем доступность целиком. Число реплик, размещение по разным зонам отказа и порядок обновления выбираются под цели качества. Учтите общие БД, очередь, хранилище и входящий трафик. PDB ограничивает допустимые добровольные выселения Pod через механизм Eviction; он не предотвращает отказ сервера и не управляет rolling update приложения.

Документация для настройки Kubernetes

Используйте документацию версии целевого кластера. Нужные темы: ресурсы, probes, жизненный цикл Pod, HPA, PDB. Экспериментальные возможности не делаем обязательной основой.

Как ограничивать доступ и влияние сбоев

ISO-01 · Обязательно: разрешаем только нужные связи. Окружения и сервисы разделены по правам и сетевому доступу. Исходная политика запрещает входящие и исходящие связи; затем явно разрешаются необходимые, включая DNS и наблюдаемость. Проверяйте и разрешённые, и запрещённые соединения на сетевом плагине кластера — CNI.

ISO-02 · Обязательно: процесс получает минимальные права. Обычные приложения не запускаются с root или privileged. Доступ к среде хоста, его файлам и токену Kubernetes выдаётся только при необходимости. Базовая цель для Linux — Restricted Pod Security: запрет повышения привилегий, минимум capabilities и профиль seccomp. Файловая система образа обычно read-only; writable-каталоги перечислены явно.

ISO-03 · Обязательно: защищаем секреты. Пароли и токены не попадают в Git, образ, логи и браузер. Доступ получают только нужные процессы. Есть порядок замены и отзыва. В рабочей среде проверяется шифрование хранилища секретов; base64 шифрованием не является.

ISO-04 · Обязательно: не принимаем бесконечную работу. Ограничьте одновременные запросы, очереди, размеры данных и вывода, batch size — объём одной порции работы, соединения и повторы. Тяжёлая операция не должна без ограничений занимать ресурсы входа и прогресса. При перегрузке возвращаем понятный отказ или заранее описанный сокращённый результат. Проверку прав не обходим.

ISO-05 · Обязательно: недоверенный код исполняется отдельно. Ученический код запускается в проверенной sandbox без секретов и данных Core. Обычный subprocess, контейнер или namespace сам по себе не доказывает такую изоляцию. До публичного использования отдельно проверяем защитную границу, лимиты и очистку после сбоев.

Namespace — область группировки объектов Kubernetes, прав и квот. Он не отделяет физически CPU, ядро ОС или диск. Если нужны более сильные границы, выбираем их по рискам и целям доступности. Официальные пояснения: изоляция в общем кластере, NetworkPolicy, Pod Security, Secrets.

Как проверять скорость и понимать состояние системы

PERF-01 · Обязательно: определяем, что измеряем. До оптимизации запишите сценарий, нагрузку, объём данных, целевую задержку, число операций и допустимые ошибки. Измеряйте также CPU, память, соединения, I/O БД и очередь там, где они важны. p95 и p99 показывают задержку, в которую укладываются 95% и 99% операций; одного среднего значения недостаточно.

PERF-02 · Обязательно: считаем общую нагрузку всех копий. Сложите пиковые соединения всех API и workers, включая дополнительные Pod во время обновления и ещё не остановившиеся старые Pod. Для каждого процесса учтите все pools и overflow — разрешённые дополнительные соединения сверх основного пула. Добавьте задачи обслуживания, миграции и резерв. Сумма должна укладываться в выделенный бюджет БД. При внешнем pooler — посреднике, управляющем соединениями, — отдельно считаем клиентские и серверные соединения.

Условный пример расчёта соединений

Допустим, в пике одновременно работают 3 целевых, 1 дополнительный при обновлении и 1 завершающийся Pod. В каждом 2 процесса, у каждого один pool на 10 соединений и ещё 2 overflow. Получаем (3 + 1 + 1) × 2 × (10 + 2) = 120 соединений. Ещё 20 на остальные работы и 20 резерва — нужен бюджет 160. При выделенном бюджете 150 такой вариант не проходит. Это учебные числа, не настройки knowi.

PERF-03 · Обычно: сначала ищем причину медленной работы. Проверьте запросы, индексы, лишние обращения к БД, I/O, блокировки и повторную работу. Затем выбирайте кэш, параллелизм или новые компоненты. Выдача API ограничена и разбита на страницы там, где нужно. У кэша есть владелец, предел размера, срок жизни или правило обновления и поведение при потере.

OBS-01 · Обязательно: по системе можно найти причину проблемы. Для важных операций нужны структурированные логи, идентификатор связи запросов и метрики ошибок, задержки, занятости ресурсов и очереди. Секреты исключены; user_id и request_id не используются как неограниченные метки метрик. Оповещение описывает влияние на пользователя и действие ответственного.

OBS-02 · Обязательно: у рабочей системы есть цели качества. SLI — измеряемый показатель, например доля успешных действий. SLO — цель для него за выбранный период. Выберите несколько важных пользовательских сценариев и ответственного. Задайте начальные цели до приёмки, затем уточняйте по измерениям. Несколько Pod сами по себе не доказывают доступность и пропорциональный рост скорости.

Как выпускать изменения

REL-01 · Обязательно: сервис можно собрать и выпустить самостоятельно. Его зависимости, тесты, Dockerfile, README и описание развёртывания находятся рядом либо явно связаны ссылками. Версии зависимостей зафиксированы. Тестовые среды изолированы. Поддерживаемые контракты позволяют обновлять сервис без принудительного обновления соседей.

REL-02 · Обязательно: выпускаем именно проверенный образ. Между окружениями продвигается образ с неизменяемым digest — точным отпечатком содержимого. Известны исходный commit и конфигурация. CI — автоматические проверки — проверяет границы, контракты, тесты, образ и manifests. У проверки безопасности есть критерии блокировки и порядок исключений. Локальная проверка не называется проверкой рабочей среды.

REL-03 · Обязательно: миграции выполняются управляемо. Не запускайте изменение схемы БД при старте каждой API-реплики. Обычно сначала добавляем совместимую структуру, переводим код, заполняем старые данные и только после вывода старых потребителей удаляем прежнее. Заполнение данных ограничено по нагрузке, наблюдаемо и безопасно продолжается после прерывания.

REL-04 · Обязательно: заранее знаем, как восстановиться. Для несовместимого перехода определите остановку старых writers — процессов записи, окно обслуживания при необходимости, backup, проверку основных сценариев и восстановление. Старый образ не откатывает данные. Возврат старой копии БД может потерять записи после её создания. Постепенный выпуск с одновременной работой старой и новой версий допустим, только если они совместимы.

Что проверить перед выпуском

Перед рабочей средой обязательны применимые проверки ниже. В PR или отчёте оставьте результаты, окружение и ограничения. Для прототипа можно выполнить часть проверок, если он явно обозначен и изолирован; это не делает его готовым к production.

ОбластьЧто должно быть подтверждено
КодНет запрещённых импортов и циклов кода; публичные операции проверены. Новые границы проверяются автоматически в CI; допустимые сценарии взаимных вызовов описаны.
КонтрактСхемы, ошибки, права и совместимость с поддерживаемыми потребителями проверены.
ДанныеНужные роли имеют доступ, чужие — нет. Миграция и восстановление отрепетированы, где применимы.
РепликиДля горизонтального роста проверены 1 → 2 → несколько реплик: общие сессии, корректное состояние и отсутствие лишней повторной работы.
НагрузкаЗаписаны условия, ресурсы, задержки, успешность и число операций. Известно ограничивающее звено; проверены рост, всплеск и восстановление после перегрузки.
СбоиПроверены потеря Pod, timeout зависимости, обычная и принудительная остановка. Последствия для других сценариев соответствуют описанию.
Фоновая работаПроверены сбои до и после сохранения/ACK, дубликат, просроченный исполнитель, заполнение очереди и повторная обработка без повреждения состояния.
ЗащитаНа целевом типе кластера проверены разрешённые и запрещённые связи, права, секреты и ограничения контейнера. Для ученического кода — отдельная проверка sandbox.
ВыпускИзвестны digest, commit и конфигурация; проверки CI пройдены. Есть диагностика и runbook, проверены выпуск и восстановление. Реально запущенная версия соответствует ожидаемой.

Чтение исходников, unit-тесты, проверка контрактов, запуск на стенде, нагрузочный эксперимент и проверка рабочего сервера подтверждают разные свойства. Указывайте, что именно проверили. Количество тестов не заменяет нужные сценарии.

Если правило не подходит

GOV-01 · Обязательно: объясняем исключение. Укажите номер правила, причину, область действия, владельца, компенсирующую проверку и срок или условие пересмотра. Существенное исключение оформите ADR и согласуйте с ответственным за архитектуру или эксплуатацию. Для рекомендации «Обычно» достаточно объяснения в PR. Оставшееся исключение видно в отчёте, а не скрыто за общим «всё прошло».

Наша текущая основа сохраняется: Core — одно модульное приложение, Web — общая оболочка, курсы — пакеты. Уведомления имеют отдельный процесс из Core. Runner pool остаётся лабораторным компонентом, Analytics — планом. Автоматические проверки и готовые шаблоны требуют отдельного внедрения; наличие этой страницы не означает, что все они уже настроены.
