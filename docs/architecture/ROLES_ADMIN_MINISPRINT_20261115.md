## 1. Цель и принятые решения

До реализации Analytics подготовить в Core и web три бизнес-роли: пользователь, ведущий курса, администратор платформы. Разделить курсовую админ-панель и `/admin-platform`, привязать занятия/слоты/календарь к курсу и ведущему, сохранить общую подписку и действующие данные. В миниспринте панели используют проверенные показатели Core; новый Analytics backend не является зависимостью этих работ.

Уточнения владельца заменяют первоначальную формулировку про текущий месяц:

* Ведущий видит людей, у которых были, есть или будут записи на его курс. Месяц — фильтр календаря/квоты, не граница разрешённого списка людей.
* Есть отдельный поиск людей, чтобы выдавать занятия человеку, которого ещё нет в списке курса.
* Занятия и их баланс привязаны к конкретному курсу. Здесь «занятие» — личная встреча/запись и право её забронировать; это не учебный lesson или отметка прогресса.
* Подписка исключительно общая для платформы. Отдельные подписки по курсам не вводятся. Ведущий вправе выдать общую подписку; её действие на остальные курсы — явная часть разрешённой операции.
* Первоначальный ведущий `backend` — существующий аккаунт `kiryukhin_nik@bk.ru`; его проверенный ID записывается в манифест перед применением. Это требование к конфигурации, не утверждение, что права в production уже выданы. `backend_copy` автоматически не получает того же ведущего.

## 2. Факты текущей системы

* `User.is_admin`, `Principal.from_user` и frontend `UserProfile.is_admin` различают только обычного пользователя и администратора. Признак нельзя просто использовать для ведущего: это откроет глобальные старые admin endpoints.
* Подписка уже общая: `users.subscription_until/subscription_plan`; принятый договор MC1.3/CORP-482 это подтверждает. Оплаченное время не дробится и не продлевается при миграции.
* `BookingSlot` не имеет course/owner и уникален глобально по дате/времени. `BookingQuota` — месячная глобальная квота user/year/month. Квота расходуется по месяцу слота. Advisory locks/overlap checks также глобальны.
* Текущая отмена очищает `student_id`, удаление слота удаляет строку. Полной истории booking lifecycle нет; notification outbox её не заменяет. Уже утраченные отменённые записи нельзя восстановить достоверно.
* Админский список выбирает всех пользователей; `year/month` меняют квоту, а не аудиторию по записям. Текущие агрегаты/профиль частично используют глобальные данные или default `backend`.
* В web админ-панель — Dockview panel внутри курса, доступная по одному `is_admin`. Страница `/admin-platform` отсутствует; запросам `/admin/*` клиент не добавляет course scope. Старый dashboard показывает показатели платформы, даже когда открыт внутри курса.
* Существуют refresh auth state и фильтрация восстановления Dockview. Их нужно развить под capabilities/scope; скрытая кнопка не заменяет серверную авторизацию.

Owning sources: `services/core-api/pymentor_core/modules/identity/principal.py`; `adapters/sql/models.py:184–218`; `adapters/sql/bookings.py`; `adapters/sql/administration.py`; `tests/fixtures/contracts/multicourse/MC1.3/access-contract.json`; `apps/web/src/app/App.tsx`; `apps/web/src/app/workspace/`; `apps/web/src/features/admin/`; `apps/web/src/shared/api/contracts/`. Доказательства — чтение исходников; live БД и сайт в этой подготовке не проверялись.

Пользователь остаётся ролью по умолчанию; регистрация/форма профиля не позволяют назначить staff. Подписка, число занятий, роль и отметка прогресса — независимые сущности. Ведущий видит агрегаты своего курса и индивидуальный прогресс людей из roster только по этому курсу: completed lesson/task IDs и даты, итоговые счётчики, без решений/приватных тестов и прогресса других курсов. Поиск человека вне roster не открывает его учебный профиль. Выдача занятий не отмечает учебные задания выполненными.

Для начала задаётся один активный ответственный ведущий на курс и один активный курс на ведущего. Техническая роль вычисляется сервером: admin при действующем platform admin grant; leader при активном назначении курса; иначе user. В этом объёме admin не имеет активного назначения ведущим. Будущие co-host/multi-course назначения требуют отдельного расширения правил, не неявного объединения прав.

## 4. Backend: право на ресурс и модель данных

### 4.1. Identity и курс

Источник полномочий администратора — `is_admin`. Источник полномочий ведущего — один `leader_user_id` в манифесте курса и активное назначение `course_leadership`, привязанное к поколению аккаунта. У аккаунта одна роль из `admin`, `leader` и `user`. Неизвестный аккаунт, конфликт назначения, повторное использование числового ID и неподтверждённый аккаунт блокируют привязку. Активные назначения уникальны по курсу и пользователю.

Для переноса старых администраторов сначала настроить по одному курсу на каждый старый аккаунт в `leader_user_id`. Локальный инструмент `python -m tools.maintenance.course_leader_config --migrate-legacy-admins --dry-run --database-url <target>` проверяет весь набор. При `--apply` он снимает старые права и применяет назначения в одной транзакции. Конфликт или неполное сопоставление отменяет перенос целиком. Маркер завершения защищает новые роли от повторного переноса. Этот инструмент принимает только выделенный локальный PostgreSQL-профиль по своим проверкам.

После переноса новые администраторы добавляются явно через `python -m tools.maintenance.make_admin <email> --dry-run --database-url <target>` и применение через `--apply`. Назначение блокируется для активного ведущего. Кнопки и публичного API назначения администратора нет. Ноль новых администраторов после переноса допустим.

`/user/me` возвращает совместимый `is_admin` только для администратора платформы, `role`, `capabilities`, назначенный course_id и revision прав. Ведущий не получает `is_admin=true`. `require_admin` остаётся platform guard; новый course guard проверяет текущее назначение, действие и конкретный ресурс. Подмена course/user/slot IDs, body/header/localStorage не расширяет scope. Core проверяет актуальные права на каждом запросе; версии в cookie/UI не считаются доказательством.

Конфигурация ведущих фиксируется неизменяемым снимком на время жизни runtime. Редактирование файла само по себе не отзывает права работающего процесса; hot reload этой настройки не поддерживается. Применение новой конфигурации требует остановки и дренирования всех writers, guarded dry-run/apply, затем запуска нового runtime со свежим снимком. DB-проекция и смена platform-admin роли выполняются транзакционно. Нельзя снять последнего platform admin. Lifecycle binding не позволяет старому конфигу вернуть права удалённой/заменённой учётке. Конфликтующий конфиг останавливает применение с конкретной причиной; скрытая смена владельца действующих записей запрещена. Изменение полномочий в БД и staff-команды используют согласованный lock/version протокол. UI получает auth revision/403 и очищает открытые staff данные.

### 4.2. Занятия и roster

Квота становится `(course_id, student_id, year, month)`, с тем же месячным правилом расходования по дате слота. Новый курс не получает копию старого баланса. Бронь в backend не расходует квоту backend_copy. Общая подписка не создаёт квоту занятий и квота не создаёт подписку.

Slot имеет `course_id` и `calendar_owner_id` ведущего. Booking lifecycle хранится отдельно или эквивалентно неизменяемой историей: booking_id, course, slot, student, owner-at-booking, status, starts/ends, created/cancelled/completed timestamps. Slot availability не является историей ученика. Запретить hard-delete занятого/исторически связанного слота; отмена/архивация сохраняют связь и её статус. Пользовательское удаление данных выполняется отдельным согласованным privacy процессом.

Roster — distinct пользователей с подтверждённой текущей или исторической booking связью с курсом; отменённая запись сохраняет факт «была запись» с видимым cancelled status. Включаются будущие записи, люди без активной подписки и без остатка занятий. Само получение квоты/найденный search result не считается booking: это отдельное состояние «занятия выданы, ещё не записан», доступное для завершения операции, без ложного расширения roster. Фильтр дат/месяца может сужать UI, но по умолчанию список охватывает всю доступную историю. Исторический охват до миграции ограничен реально сохранившимися данными и помечается явно.

Search-to-grant не предоставляет ведущему выгрузку всех пользователей: точный email или запрос имени от 3 символов, server-side limit 10, pagination/quotas, минимальный DTO (стабильный идентификатор, имя, маскированный email; точный email для проверки совпадения). Empty/wildcard запрос запрещён; по чужому user_id нельзя получить общий admin profile. Сервер снова проверяет target и scope при выдаче. Для выдачи общей подписки можно показать только её необходимый текущий срок; чужие курсы/расписания/платформенная активность не раскрываются.

### 4.3. Команды выдачи

Ведущий может добавлять месячную квоту только своего курса, продлевать общую подписку найденного/выбранного человека; число дней и занятий валидируются сервером. Квоту/даты другого курса он не меняет. Ведущий не может обнулить/сократить уже выданную общую подписку; администратор имеет отдельный явный reset/revoke сценарий.

Выдача подписки использует текущую семантику срока: продление от max(now, current_until), не обрезает оплаченное время. Две разные команды изменения одной подписки сериализуются блокировкой target user/subscription; квоты — блокировкой строки course/user/year/month либо атомарным upsert/update. Оба начисления сохраняются, stale read-modify-write запрещён; общий порядок identity/assignment/quota/calendar locks закрепляется в R1. Команды имеют idempotency key и transactionally persisted результат/аудит: actor, actual role/course authority, target lifecycle ID, scope (`platform` для подписки, course для занятий), delta/before-after, причина, timestamp, command_id. Повтор двойного клика/timeout не удваивает выдачу. Одинаковый key с другим payload — conflict. Проверка отзыва actor/target deletion выполняется до commit под конфликтующими блокировками; один network retry не даёт права повторить действие.

### 4.4. Календарь и конкурентность

Ведущий видит своё расписание на курсе; часовой пояс/границы месяца сохраняют нынешнюю семантику UTC+03:00 до отдельного изменения. На курсе один ведущий; выбора нескольких владельцев нет. Admin смотрит и редактирует календарь выбранного курса, новый slot принадлежит его единственному настроенному ведущему. У студента список слотов и запись явно указывают course_id и ведущего.

Блокировки/unique/overlap меняются согласованно: один ведущий не ведёт два занятия одновременно; один ученик не бронирует пересекающиеся занятия в разных курсах; разные ведущие могут работать одновременно. Lock key учитывает calendar owner/date; student collision проверяется с отдельной стабильной блокировкой ученика. Порядок locks единый, quota check + claim slot + lifecycle + outbox атомарны. Существующее правило отмены учеником за 36 часов сохраняется; отмена и админская корректировка не создают отрицательный остаток и не возвращают квоту дважды.

Исторический owner записи сохраняется. Перенос слотов между ведущими не является функцией этого релиза; конфликт новой конфигурации с действующими записями требует отдельного плана сохранной миграции. Уведомления используют сохранённый course/owner snapshot. Реальные Telegram/SMTP отправки не нужны для локальной приёмки — используется sink.

### 4.5. API и метрики

Новые boundaries: `/api/admin/courses/{course_id}/...` для панели курса; `/api/admin-platform/...` для глобального администрирования. Конкретные OpenAPI paths закрепляет R1. Старые `/api/admin/*` не становятся доступны ведущему и не выбирают default backend при пропущенном scope; пока нужны старым admin clients — остаются только platform-admin совместимостью.

Course queries фильтруют SQL до pagination/aggregation; profile/progress/lesson counts учитывают product course_id и roster личных занятий. Query body/response возвращает scope и период. Курсовой panel показывает аудиторию/записи/выданные и использованные занятия/учебный прогресс по доступным данным. Глобальные activity days без course attribution не выдаются за посещения конкретного курса: блок возвращает not available до Analytics, не ноль. Для общего дашборда показатель «сегодня» использует существующий журнал платформы с явными ограничениями покрытия; новые таблицы посещений в Core не вводятся.

Analytics затем получает общую таблицу фактов времени: пользователь/lifecycle, курс, занятие, сессия, временной интервал и активная длительность. Посещения, уникальные люди и время по курсу/занятию получаются фильтрами и агрегацией этих фактов; таблиц на каждый курс и дублирующих независимых источников статистики нет. Сбор такого Tracker и сервис Analytics не входят в текущий миниспринт.

Общие подписки не суммируются по курсам: один подписчик в двух курсах — один платформенный подписчик; платформенные пользователи считаются distinct, курсовые события суммируются только по определению метрики. На курсовой панели срок общей подписки ученика отображается как общий, а количество «подписок курса» не изобретается. Глобальные отчёты работают без назначенного курса у администратора.

## 5. Frontend и пользовательские потоки

### Панель курса

Сохранить текущий визуальный каркас и понятные секции со скриншота: «Обзор», «Ученики», «Слоты записи», «Календарь». Контекст курса/ведущего виден в заголовке. Для ведущего кнопка администрирования доступна по назначению; её стартовый экран — обзор своего курса. Обычное открытие курса не принудительно выбрасывает пользователя из урока в admin. Для платформенного admin тот же panel открывается с выбранным course scope.

«Ученики» показывает roster, поиск внутри него и отдельное действие «Найти человека и выдать». Месяц в выдаче квоты подписан явно; поисковый результат не подгружает весь глобальный profile. Кнопки «Выдать занятия» всегда показывают курс, месяц и количество. «Продлить общую подписку» показывает область действия платформы и итоговую дату. Delete user/reset subscription/role management отсутствуют у ведущего и запрещены API.

Календарь/слоты используют course/owner в API и состоянии; student booking UI учитывает курс и отдельный баланс. Role/capability guard заменяет нынешние Boolean gates во всех точках открытия и восстановления Dockview.

### `/admin-platform`

Самостоятельный top-level route, доступный только admin. Секции: обзор платформы, курсы с переходом в курсовую панель, все пользователи и журнал операций. Видны общие метрики и фильтр курса. Назначения ведущих и переносы в UI отсутствуют. В карточке человека — одна общая подписка и отдельные балансы занятий по курсам; выдача требует выбора курса для занятий. Прежний визуальный язык панели сохраняется.

У admin нет «моего курса» или «моего календаря», а открытие платформенной панели не выбирает backend автоматически. Переход к расписанию — через явно выбранный курс с его единственным ведущим. Личные учебные записи admin как обычного ученика сохраняются.

### Изоляция состояния

Auth/profile contracts содержат роль и capabilities, не только is_admin. Админские API явно получают course scope, без глобального авто-default. Client state/cache keys: user + role/auth revision + scope + course + owner + filters. При смене курса/роли/logout очищаются чувствительные данные и pending запросы; поздний ответ старого scope не перерисовывает новый экран. Layout migration отбрасывает недоступные панели. Покрыть direct URL/refresh/back/forward и mobile состояния loading/empty/error/403.

## 6. Миграция и начальное назначение

1. Перед DDL инвентаризировать фактический schema head и данные: users/admins, subscriptions, quotas, slots/bookings, lifecycle и уведомления. Не предполагать, что production уже соответствует локальному c504. Снять baseline counts/IDs/timestamps/балансов и восстановимую копию.
2. Additive migration добавляет assignments/scope/history/audit и индексы; backfill существующих slots/quotas в `backend` допускается только после подтверждения их исходной принадлежности. Неопределённые строки идут в отчёт для администратора, не в случайный курс; слепое копирование в backend_copy запрещено.

   До cutover все строки, влияющие на действующий баланс или будущую бронь, должны иметь подтверждённый mapping либо проверенный безопасный совместимый путь обслуживания. Иначе блокируется затронутый cutover, сохраняются исходные значения и доступ через прежнюю совместимую сборку; новые обязательные scope-фильтры не должны скрыть оплаченные занятия/будущую запись. Неопределённая старая неактивная история остаётся отмеченной ограниченным coverage.
3. Существующие platform admins сохраняются; обычные users остаются users. Для первоначального backend ведущего один раз проверяется существующий подтверждённый аккаунт `kiryukhin_nik@bk.ru`, его числовой ID записывается в конфигурацию курса. Production ID пока не установлен и не угадывается. Email не является runtime allowlist; аккаунт/пароль автоматически не создаются.
4. Dry-run/apply конфигурации создаёт lifecycle-bound проекцию, последующие старты подтверждают то же соответствие. Конфликт с admin/другим курсом, отсутствующий аккаунт, tombstoned binding или несовпадение уже закреплённого lifecycle блокируют применение без потери данных. Последний admin не демотируется. Backend_copy автоматически не наследует ведущего. Новое применение не возвращает сознательно отозванные права. Смена ID ведущего при существующем календаре требует отдельной сохранной миграции, без нового admin UI.
5. Существующие сохранённые брони формируют исходную историю с отметкой legacy coverage; уже удалённая/отменённая история не изобретается из outbox. Приписывание старого календаря ведущему подтверждается inventory; затронутые будущие записи и уведомления не теряются.
6. Старые writers не запускаются одновременно с несовместимым новым ключом quota/slot. До cutover либо доказать смешанную совместимость, либо использовать управляемое локальное maintenance окно с остановкой writers. Старый runtime должен отклонять неподдерживаемую схему; blind downgrade после появления course-aware данных недопустим.
7. Изменения сначала проходят на disposable PostgreSQL/Redis и synthetic accounts/sinks; bootstrap имеет dry-run/apply отчёт. Производственная выдача прав, DDL и выкладка — отдельное исполнение по проверенному плану. По текущему поручению создаётся миниспринт, не выполняется production cutover.

## 8. Обязательные сценарии R8

1. User регистрируется без staff прав; поддельные role/course headers и прямые legacy admin endpoints не работают.
2. Ведущий backend открывает свой panel, но не backend_copy, `/admin-platform`, чужой user profile вне разрешённого сценария или глобальную выгрузку.
3. В roster есть три человека с прошлыми/текущими/будущими записями и человек с отменённой историей; нет людей только из чужого курса. Месяц не удаляет историю из области доступа.
4. Поиск находит ещё не записанного человека; выдача 3 занятий на backend не меняет backend_copy и не записывает на слот автоматически. Отдельно продление общей подписки работает в обоих курсах и не выдаёт занятия.
5. Общая подписка не укорачивается продлением; повтор одного command_id не удваивает срок/квоту, две конкурентные команды с разными keys сохраняют оба начисления. Ведущий не делает reset, admin может выполнить разрешённую коррекцию; аудит фиксирует actor и scope.
6. Два ученика конкурируют за один slot; один ученик — за пересекающиеся slots двух курсов; quota не уходит в минус. Разные ведущие могут иметь одинаковое время, один ведущий — нет. Cancel/retry не возвращает баланс дважды; occupied/history slot не исчезает от delete.
7. Admin входит на `/admin-platform` без назначенного курса, видит всех users/сводку/курсы; открывает panel выбранного курса и меняет его расписание, не становясь владельцем календаря.
8. Открыты вкладки backend/backend_copy/platform; смена курса/role/logout/revoke очищает соответствующий scope, запоздавшие ответы не показывают чужие данные. При недоступном источнике показан unavailable, не ноль.
9. Конфигурация `leader_user_id` разрешается в один подтверждённый account/lifecycle ID; повторный старт, смена email или повторное использование числового ID не передают права. Публичные назначения/отзывы/переносы отсутствуют. Проверены конфликт с admin, отсутствующая учётка, lifecycle mismatch и отозванная проекция.
10. Миграция сохраняет существующие общие subscriptions, IDs/timestamps, исходные quotas/bookings/progress; сомнительные mappings не назначаются молча. Restore/recovery/cutover защищают новые course-aware записи; outbox проверяется через sink, не живые сообщения.

Для каждой задачи: revision, owning paths, disposable dataset, команда/URL, expected/actual и ограничения. Отдельно различать проверку контракта/исходников и runtime/browser PASS. R8 не закрывается по сборке или наличию этого плана. Даты/Story Points не являются оценкой производительности и не назначаются без исполнителя.
