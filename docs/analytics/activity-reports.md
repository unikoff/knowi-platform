# Activity reports: isolated local foundation

Status: the query factory installs the router and selects the canonical a010 projection reader when its flag is enabled; the flag defaults off. The focused disposable PostgreSQL suite has 22 passing tests, and the canonical full-chain cross-service scenario passed with cleanup. The earlier reader-parity test uses a stub privacy guard; the cross-service chain provides separate real-process evidence. Month-window capacity and load acceptance remain separate measurements. Production collection and deployment are not enabled. Existing `v2.ReportResponse` and `LearnerReport` remain unchanged. The new `reports_v1.ActivityReport` is a separate contract, so strict old consumers cannot parse it as their existing response. Mixed-version compatibility remains unverified.

The endpoint is `GET /api/analytics/reports/activity`, with `from_time`, `to_time` (timezone-aware UTC timestamps in a half-open interval, aligned to milliseconds), optional `course_id` and `subject_ref`, and fixed `timezone=Europe/Moscow` (fixed UTC+03:00). Initial maximum range is 31 days. Server authentication and verified grants determine scope; selectors do not grant access. User sees own data, a leader sees assigned course and current personal booking roster, platform admin has global scope. Staff actions must never enter learning telemetry. Primitive learner identifiers may be returned only within an authorized scope; names come from Core, not facts. Source wiring alone is not evidence of a deployed endpoint.

The response fields are `schema_version`, `status`, `quality`, `as_of`, `lag_seconds`, `timezone`, `metric_version`, `course_id`, `from_time`, `to_time`, `totals`, `daily`, and optional `trusted_progress`. Totals and each dated daily value contain `unique_visitors`, `active_ms`, `theory_ms`, `practice_ms`; active equals theory plus practice. Distinct counts across days cannot be summed. Progress comes solely from trusted Core progress facts, with state `known` or `unavailable`; duration is not completion. The fixtures are illustrative typed examples, not assertions of actual coverage. `unavailable` has null totals; do not invent zero. `ok` with `quality=unknown` or `partial` means only a bounded observed snapshot; an observed zero is not proof that there were no real visits. `no_data` requires proven complete coverage and zero observations; a timestamp or empty query is not coverage. `as_of` describes snapshot time, not a processing watermark. Lag is null unless established from a trusted watermark. Use `stale` only when staleness is actually established. Never call partial or unknown coverage complete.

The independent calculator consumes already validated, unique and admitted facts. For each subject it chooses one context across all courses and devices before filtering: latest original start, then canonical UUID, then namespace, all descending. Timestamp boundaries floor to milliseconds; daily intervals split at Moscow midnight. Visits count distinct subjects with an accepted course-open or intersecting segment, even when that segment loses attribution. This is observed active time, not proof of learning. A valid v2 segment has visible/focused and expires after 300 seconds without action; uncovered gaps contribute no time. No legacy `user_activity_days` conversion supplies minutes or course attribution.

The raw PostgreSQL fallback provides a bounded scoped aggregate and retains the earlier single-subject primitive. Server-side scope comes from the verified grant: a user is limited to their own subject and granted courses, a leader to the granted course and explicit roster, and an admin to global read. A subject selector can narrow that scope only. The fallback discovers at most 100 candidate subjects, locks actor and candidates in ascending advisory-lock-key order, checks deletion fences, then reads at most 10,000 facts from the common `analytics.activity_facts`. It retrieves competing courses before filtering and counts distinct subjects rather than summing course counts. Overflow fails without returning truncated measurements. SQL uses bounded time, candidate and fact results plus the existing DB operation timeout; this is not a performance measurement. Under concurrent ingestion the two fallback read queries can observe changes; there is no stable complete-source snapshot guarantee. Empty scoped results return `as_of=null` and quality unknown; they reveal no timestamp from unrelated courses. Inputs must originate from trusted collector admission; common storage itself does not attest user role. A missing transaction guard fails closed. Offline tests alone do not prove source coverage, watermark, latency SLO, real database execution, or deletion races. The separate projection reader and its bounds are described below.

The query factory binds the router, grant verifier, trust manifest, privacy probe, guarded database transaction and activity report store; availability still depends on their actual configuration and readiness. Invalid grant is 401, forbidden scope 403, invalid bounded query 400, and unavailable or workload overflow 503. The opt-in disposable-PostgreSQL reader-parity fixture uses a stub privacy guard and does not by itself test the actual privacy authority; the separate canonical cross-service chain covers real-process interaction.

Register an actual activity consumer if a projection is needed, with atomic idempotency and bounded replay; current jobs are synthetic and cannot prove time processing. ## Lesson filter and details

The existing `/api/analytics/reports/activity` response keeps its previous shape; an optional `lesson_id` query parameter requires `course_id`. A lesson is identified by the pair `(course_id, lesson_id)`. Competing segments from every course and lesson are combined first; the lesson/course filters are applied to the winning attribution and observed visitors afterwards. `course_opened` without a lesson is not a lesson visit. Course visitors need not equal a sum of lesson visitors.

`GET /api/analytics/reports/activity/details` accepts the same filters plus `offset` (0–20000) and `limit` (1–100, default 100). It returns `report` (existing `ActivityReport` shape), `lesson_id`, `rows` and `next_offset`. Rows are ordered by course ID, then the course row, then lesson ID; they carry `level`, `course_id`, `lesson_id`, `unique_visitors`, `active_ms`, `theory_ms`, `practice_ms`. The response carries IDs only: Core supplies current or archived titles. Offset pages are independent bounded reads, not a stable snapshot under concurrent ingestion; clients should refresh if consistency is needed. Each request retains 31-day and 100-subject limits and fails closed on overflow. The raw reader also has a 10,000-fact limit; the optional projection reader has separate limits described below. A typed illustrative example is `contracts/fixtures/reports-v1-details.json`.

The `report.trusted_progress` for details is `{state: "unavailable", completed_lessons: null}`: the current Core transfer projection has no source coverage and freshness proof for the authorized report scope. A count of present rows, maximum received timestamp or learning time cannot establish completion coverage. A future implementation may read that projection only after proving complete scoped transfer/processing and freshness while preserving deletion fences. Existing activity response remains compatible and does not fabricate progress.

The raw fallback's global candidate query has no leading time index in a001. Its time predicate, result cap and DB timeout bound the request, but they do not prove bounded scan cost. The canonical chain adds a browser-fact index; its actual plan and cost require independent disposable-PostgreSQL EXPLAIN/load checks.


## Optional subject/bucket projection (a010 source)

The default-off projection path is a separate reader of one common `activity_projection_buckets` table; the existing raw reader and v1 JSON shapes remain available. The pure normalizer processes all accepted facts of one lifecycle and one 15-minute UTC bucket across all courses before any course or lesson filter. It yields non-overlapping winner intervals and compact durations, and separate presence intervals, course-open points and labels so an overlapping segment that lost time attribution still counts as a visit. Per-bucket input is capped at 10,000 facts and 8 MiB; output is capped at 8 MiB. Overflow never publishes a truncated bucket.

The reader uses the configured external dataset-generation UUID, not an ID recovered from the DB snapshot. It discovers candidate subjects without course-filtering dirty rows, acquires all numeric subject lock keys, rechecks the privacy guard, obtains the dataset-generation shared lock, rechecks the guard and performs one READ COMMITTED SQL statement. That statement repeats candidate discovery, checks backfill completion, generation, bucket state and subject epoch, then computes totals/distinct visitors in SQL. It reads compact contributions/presence labels for complete buckets and clipped intervals/points only for boundary buckets; it does not read raw facts on this path. A changed candidate set, deleted actor/selected subject, dirty or stale bucket, missing/mismatched dataset generation, or exceeded cap closes the request. The statement timestamp is a snapshot boundary, not a source-delivery watermark; `quality` remains `unknown` without an independently proven coverage contract.

Initial independent bounds are 100 subjects, 300,000 bucket rows, 1,000,000 compact items/64 MiB and 100,000 edge items/32 MiB. Before array expansion, the reader checks item counts and byte sizes generated by PostgreSQL as the UTF-8 size of each `jsonb::text` array, including its formatting; these are not Python's compact JSON byte lengths or a claim about database RAM. The DB constrains array counts.

On 2026-11-17, a fresh disposable PostgreSQL sparse test passed with 50 synthetic subjects and 12,400 facts over 31 days, processed through the worker store. One reader request took 234 ms; a separate EXPLAIN ANALYZE took 244.641 ms and used the `activity_projection_time_subject` index. The EXPLAIN reported 1,325 temporary blocks read and written; DB size was 39,525,399 bytes. The fixture confirmed cleanup. The test used a stub privacy guard, and this single sparse observation does not establish a p95, full workload capacity or privacy-authority performance. An initial run failed in its test wrapper before measurement, was fixed, and the successful run used a new DB.

A separately gated dense **query-only** synthetic dataset is prepared but not yet measured. It directly inserts ready buckets into a new owned sentinel DB and does not prove browser ingestion, processor correctness, backfill coverage or real privacy authority. The old 10,000 raw-fact cap must not be interpreted as a month-capacity PASS.

The requested `to_time` is echoed unchanged, but candidate discovery and the final statement use an effective upper bound of the earlier of `to_time` and the statement timestamp floored to milliseconds. Only buckets intersecting the effective range participate in dirty checks and aggregation. Edge intervals and point visits are clipped to that same bound, so accepted future facts do not count before the snapshot. Because discovery and aggregation are separate statements, a candidate-set change while locks are acquired fails closed.
