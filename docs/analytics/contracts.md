# CORP-58: предварительный контракт Analytics

Срез 16.11.2026: отдельный исполняемый контракт и synthetic fixtures, **сервис, routes, issuer, проверка подписи, хранилище и интеграция Core не реализованы**. Pydantic 2.13.4, FastAPI 0.139.0. Предшествующая база — [CORP-57](architecture.md), [план](../architecture/ANALYTICS_SERVICE_PLAN_20261115.md) и тестовые c226 fixtures Core. В Analytics до этой работы не было публичных DTO/OpenAPI; новый контракт нельзя считать совместимым с c226 v1. Направления v1 producer → v2 collector и v2 query → существующие потребители: **BREAKING/UNKNOWN**, готового адаптера или потребителей нет. `c226` — тестовый набор, где `course_id` означает track; `map_v1_track` требует явной карты track→product course и не подставляет имя по умолчанию. Миграция и согласование идентичностей — CORP-60, не подключение Core.

Исходники DTO — `services/analytics/pymentor_analytics/contracts/v2.py`; сгенерированные JSON Schema и документ OpenAPI в `services/analytics/contracts/`. Экспорт строит отдельный временный объект FastAPI без запуска сервера. Схемы описывают синтаксис, а Python validators, авторизация и транзакционные условия добавляют семантику: одно наличие OpenAPI не исполняет эти гарантии. ## Collection и идентичность

`POST /api/analytics/events/batch` предполагает bearer grant, envelope `events` и по одному результату на индекс входа. Предельные значения v2, предварительные engineering defaults: **100 items, 256 KiB фактического UTF-8 тела и 4096 байт фактического JSON элемента**. Ограничение элемента считает его от открывающего до закрывающего токена, включая внутренние пробелы; пробелы между элементами входят в размер batch. Заголовки HTTP ограничивает сервер/ingress отдельно. Неверный JSON/envelope или превышение batch отклоняют весь запрос; корректный envelope обрабатывается поэлементно: неизвестная версия/невалидный или oversized item не мешает другим, идентификация через `index`, UUID может быть null. Нельзя отражать произвольный входной ID в логах. Неизвестный catalog → `pending/unknown_catalog` или quarantine; это не успешное сохранение факта и не подтверждение обработки. Browser retry для неподтверждённого элемента ограничен общим deadline/backoff/jitter; timeout означает неизвестный исход и требует reconciliation тем же ID. 429 использует `Retry-After`, 503 означает недоступность; фактические handlers последуют в CORP-440.

Browser отправляет только `BrowserEvent`: версию 2, UUID event, product `course_id`, `catalog_version`, lesson/section, отдельный learning `session_id`, timestamps, `active_ms`, подтверждения видимости/focus и пустой allowlisted payload. Личные данные, код, ответы, URL, cookies и произвольные поля отклоняются. Он не передаёт source, subject, namespace, роль, progress или control. После проверки grant сервер назначает `source=browser`, opaque lifecycle `subject_ref` из `sub` и доверенный стабильный namespace producer; course проверяется по grant. `course_opened` имеет null lesson/section, нулевую длительность и равные начало/конец. Для `activity_segment` lesson и theory/practice обязательны, `visible` и `focused` должны быть истинными на всём отрезке. Отрезок непрерывен, `active_ms` ровно равен его длительности в целых миллисекундах, положителен и не более 60 секунд; `ended_at` не позднее `last_action_at + 300 секунд`. Отсутствие фокуса/видимости закрывает отрезок; пауза и возобновление требуют отдельных отрезков. Эти поля — заявление browser, а не криптодоказательство фокуса, и сами по себе не реализуют tracker, idle timer или расчёт. Нормализация пересечений по всем курсам/сессиям и tie-break (последнее начало, затем event ID) относятся CORP-59. Cadence 15 с, clock skew 120 с, lateness 7 дней и browser buffer 24 ч пока кандидаты, не исполненные правила; порядок и offline-доставку предстоит проверить.

Дедупликация в будущем store имеет ключ `(producer_namespace, event_id)` и сравнивает SHA-256 `canonical_hash`: JSON из `AcceptedEvent` без `received_at`, UTF-8, отсортированные ключи, компактные separators, JSON-формат Pydantic. Hash привязывает namespace, subject и всё содержимое события. Идентичное повторение после commit → duplicate; тот же ключ с иным hash → conflict; accepted и duplicate разрешены только после durable commit факта и необходимых jobs. Приведённая функция hash не выполняет дедупликацию, транзакцию или reconciliation. Версия алгоритма canonical JSON v1 фиксируется в реализующем хранилище; другая нормализация требует отдельной версии/миграции. Это at-least-once с идемпотентной границей, не exactly-once.

## Grants и доверенный control

Контракт header `typ=JWT`, `alg=EdDSA`, `kid`; versioned claims содержат `iss`, `aud=analytics`, `sub`, scope, роль и `iat/nbf/exp` как JWT NumericDate в секундах. Выдача только асимметричным issuer, локальная проверка подписи и фиксированного алгоритма, ключа, issuer, audience и времени обязательны **до** policy; никакой trust по неподписанным claims. `validate_fixture_claims` и `authorize_fixture` — исключительно тестовый policy oracle, не verifier. Допустимый collection TTL ≤300 с, report ≤60 с; ограниченный отзыв grant не быстрее его TTL, удаление lifecycle требует отдельного немедленного deletion fence. Для ротации заранее публикуются старый и новый ключи с перекрытием не менее максимального TTL плюс разрешённый clock skew; точные SLA и operational mechanism — CORP-69/66. Секреты и JWT не логируются.

Collection получает только user на себя и перечисленные курсы; staff не может собирать telemetry даже заявляя source. Report: user видит себя на перечисленных курсах; leader — ровно один назначенный курс и явно перечисленные subject lifecycle, пустой список допустим и даёт no-data; admin имеет global read. URL/body не увеличивает подписанный scope. Лимит 1000 subjects — предел одного page-scoped grant, а не предел roster: полные обзоры должны отдельно безопасно обходить все страницы или использовать будущий доверенный roster port; молча усекать список нельзя. Выдача grants, отзыв назначения и корректная пагинация ещё не реализованы. Синхронной introspection на каждый запрос не предполагается.

`CoreControl` — discriminated DTO для snapshot каталога, подтверждённого progress и deletion fence с независимыми control ID. Progress привязан к lesson; task ID и revision либо оба null для прогресса урока, либо оба заданы для задания. Это проект DTO, полная семантика экспорта заданий и реальный Core producer относятся этапу 2. Эти DTO не являются browser events; требуется отдельный приватный transport и credential для доверенного producer, policy и атомарная проверка deletion epoch при приёме, обработке и чтении. Core сохраняет ownership progress/catalog/roster/deletion; версии и порядок snapshot/delta, outbox, transport, повтор и restore barrier требуют последующей реализации и проверок CORP-60/69/440–442. Предыдущий notification outbox не используется. Выборка и хранение реальных данных не начаты; по решению владельца подробные посещения/время без автоматического TTL, право удаления subject сохраняется.

## Query и проверка

`POST /api/analytics/reports/activity` — проект bounded запроса: период до 366 дней, до 100 строк, IANA timezone и server-side scope. ОС должна содержать базу IANA или пакет `tzdata`; встроенное имя `UTC` поддерживается без неё. `ReportResponse` содержит `as_of`, lag, качество, timezone и версии metric/projection. `ok` с нулём в строке означает измеренный ноль; `no_data` — отсутствие строки; `stale` — устаревшие или частичные данные; `unavailable` — данные не выдаются и качество unknown. Это не обещание freshness/SLO: их устанавливает CORP-113. Доступные примеры включают две разные product course, success/zero/no-data/stale/unavailable, per-item accepted/duplicate/conflict/pending/unsupported, rate limit, отдельный Core control и grants. Тесты проверяют также forged subject/source, staff collection, scoped leader report, пустой roster, expired/unknown key, insufficient scope, лимиты, отказ PII и явный v1 mapping.

Реальный verifier/signature, HTTP status/media types, source credentials, catalog lookup/pending, atomic ACK/hash, multi-worker, privacy fence/restore и E2E здесь не проверены; реализация и runtime failure tests принадлежат следующим карточкам. По каждому изменению схемы нужны повторный экспорт, верификация consumers и оценка обеих направлений совместимости, включая одновременные версии.
