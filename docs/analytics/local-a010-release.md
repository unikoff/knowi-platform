# Подготовка локального release a010

**Статус: source promotion выполнен; локальный synthetic encrypted restore a010 прошёл.** Active migration head теперь `a010`; проверенные `a007`–`a010` перемещены побайтно в `services/analytics/migrations/versions/`. Их исторические docstrings про proposal не меняли, чтобы сохранить точные проверенные bytes. Это продвижение и Helm render не запускали миграцию или upgrade сохранённых DB. CNI и нагрузочный тест этим proof не проверены. Существующие `.local/runtime.json`, отдельный K3s a006, их тома и ранее собранные a006 images сохраняются.

## Promotion после проверки зависимостей

1. Завершено: отдельный full-chain a010 PASS и GO координатора на продвижение исходников.
2. Завершено: четыре файла перенесены с совпадением SHA-256 до/после, active цепочка `a010 → a009 → a008 → a007 → a006`. Новый runtime image ещё не собран. Никакие downgrade, reset, seed или перенос данных между DB не входят в promotion.
3. Подготовить новый synthetic target. `bootstrap_postgres.create(..., revision="a010")` создаёт изолированные роли `migrate`, `collector`, `processor`, `query`, `privacy` и `transfer_status` с `NOINHERIT`; у последней до a007 только CONNECT. Миграция a007 отдельно выдаёт ей ограниченные read grants. Использовать разные credentials; в `transfer_status` не передавать credential Collector. `bootstrap_runtime` для существующей отдельно разрешённой DB перед upgrade записывает `role_pending` с credential до CREATE ROLE; при ошибке сохраняет состояние и требует ручного reconciliation, автоматического повтора нет. Изменение сохранённых a006 targets этим checklist не разрешено.
4. Перед реальным migrate подтвердить DB identity/sentinel, текущую revision и владельца, ожидаемые роли и права, объём свободной памяти/диска, совместимую проверенную резервную копию и путь восстановления. Runtime bootstrap использует operation lock и durable `migration_pending`; приложение берёт транзакционный PostgreSQL advisory lock. В Kubernetes запускать только явную revision, отдельно подтверждённый immutable image и один Job `backoffLimit: 0`; при timeout/неизвестном результате сначала сверить Job, DB revision, sentinel и lock, не повторять вслепую. Изменение схемы только вперёд.
5. После a010 сверить фактические таблицы и точные role grants, проверку отрицательного доступа, privacy barrier/cursor, readiness, replay/идемпотентность, dataset run ID и сохранность данных. Снять evidence и только после этого включать отдельные feature flags. Фактический local release, Kubernetes rollout и новый image требуют отдельных выполненных проверок; этот source checkpoint их не заменяет.

Старый K3s helper намеренно закреплён на истории `a006`; при продвижении общего head он продолжит сверять fingerprint именно старой цепочки. Он не provisioner для новой a010 K3s DB. Для неё нужны отдельные metadata/identity, шестая роль и однократный Job с отдельной проверкой: не переназначать существующий `k3s-runtime.json` и не выдавать старый migration Job за новый.

`synthetic_backup.py fixture-create --fixture <UUID> --revision a006` явно выбирает старый schema target при наличии полной цепочки; без `--revision` выбирается текущий active head. Роли выбираются по target. Для a010 fresh restore проверяет точные миграционные singleton defaults и пустоту остальных таблиц. **До extraction** отдельная транзакция проверяет полную видимость сессий и их отсутствие, отзывает CONNECT у Collector, Processor, Query и transfer_status, проверяет результат и очищает только известные defaults. Само восстановление выполняется как один `psql --single-transaction` с проверкой owner/sentinel/отсутствия иных сессий: отключается только производный `activity_projection_fact_inserted`, затем восстанавливаются данные и включается тот же trigger; отзыв CONNECT повторно закрепляется до commit. Privacy/fence triggers не отключаются. После commit проверяются trigger и отсутствие CONNECT.

Команда `python -B tools/unseal_a010.py --restore <UUID> --authority <UUID> --run-id <новый UUID>` принимает private authority config из `.local/synthetic-backup/keys/<UUID>.authority.json`, не через аргументы. После parity она проверяет quarantine и owner/sentinel, получает свежий signed authority barrier, применяет текущий journal через privacy role, меняет dataset UUID с CAS и выполняет scan/drain owner-процессом с отдельными ограниченными pool1 для privacy и rebuild. Только после завершения и повторной проверки barrier выполняется одна grant-транзакция. При ошибке сохраняются `unseal_pending` или `unseal_grant_pending`; при последнем состоянии grant мог уже завершиться и его исход нужно сверить, не повторяя операцию вслепую. Открытость приложения не считается доказанной до его собственного свежего privacy barrier.

Для отдельного разрешённого runtime окна подготовлен `tests/backup_postgres/test_a010_source_down.py`: источник и новая цель — разные nonce-owned PostgreSQL с tmpfs, запущенные последовательно на localhost:57422; проверяются encrypted backup, недоступность остановленного источника, signed deletion после снимка, quarantine, отказ старого run ID, новый run ID, purge, scan/drain и только затем CONNECT для четырёх ролей. ## Настройки и границы сети

`coreTransfer.enabled`, `coreTransfer.proofEnabled`, `catalog.enabled`, `activityProjection.enabled` по умолчанию `false`. При включении chart требует общий публичный `trustManifest`, общий privacy authority Secret и соответствующую минимальную explicit schema revision. Collector получает отдельный Secret `coreTransfer.statusSecretName` с ключом `DATABASE_URL`, и публичную producer→namespace map из ConfigMap; Query получает namespace и, при необходимости, roster из отдельного Secret. Закрытые Core signing keys в Analytics не передаются. Fixture catalog и активный catalog взаимоисключаются. Projection UUID задаётся один раз на generation dataset в `activityProjection.runId`; Processor и Query получают одно и то же значение, каждый Pod не генерирует свой.

Существующие публичные Traefik routes не расширены. Дополнительный внутренний доступ Core к Collector/Query выключен; при включении `network.coreIngress` требуется либо один exact IP `/32` или `/128`, либо одновременно конкретный namespace и непустой Pod selector. Это source policy, реальное CNI enforcement в новом rollout нужно измерить. Не принимать namespace-only selector и не публиковать внутренние routes через ingress.

## Соединения и конкурентность

При включённом Core transfer каждый Collector имеет основной pool 2 + overflow 0 и отдельный status pool 1 + overflow 0; Processor и Query используют по одному shared pool 2 + overflow 0, Privacy 1, migration 1, admin 2 и backup 2. Верхние резервы для C/P/Q: **13** при 1/1/1, **16** при 2/1/1, **15** при 1/2/1 и 1/1/2, **20** при 2/2/2. Выключенный transfer сохраняет прежнюю матрицу 12/14/14/14/18. Вычесть также системные reserved connections и прочих реальных клиентов; это расчёт caps, не нагрузочный результат.

Processor имеет до двух in-flight задач существующего processor runtime, плюс один Core-transfer async loop и один activity-projection loop с одним compute thread. Эти дополнительные loops используют тот же pool Processor, а не новые DB engines; они конкурируют за две connection slots и могут увеличить ожидание. Collector status использует отдельный engine с pool 1. До включения/масштабирования измерять pool wait, queue lag и ошибки на полном workload; автоматическое масштабирование и capacity/SLO этими расчётами не подтверждены.
