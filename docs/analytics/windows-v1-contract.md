# Контракт 15-минутных окон Analytics

Протокол окон `1`, версия Claims `1`, эталоны `1`. Отдельный путь v3 этапа I CORP-598. Точка отсчёта `399df8548093609eaf168441be8679c8b6d80b37`, исходная схема Analytics `a014`. Исполняемые модели и порты находятся в `services/analytics/pymentor_analytics/contracts/windows_v1.py`. Поля и типы HTTP опубликованы в семи JSON Schema `services/analytics/contracts/schemas/window-*-v1.schema.json`.

## Время и контекст

Ключ окна состоит из `student_id`, московской даты и номера слота. Дата принадлежит сетке Europe/Moscow. Номер вычисляется как `hour * 4 + floor(minute / 15) + 1`. Слот 1 начинается в 00:00, слот 96 в 23:45. Поддерживаемые live-даты от 2015-01-01 до 2100-12-31 относятся к периоду постоянного UTC+03:00. Окно длится 900000 мс и включает левую границу. Событие с концом точно на правой границе не даёт времени следующему окну.

Web измеряет монотонный интервал и проецирует его на UTC по проверенному серверному якорю из grant. Для совместимости с v2 используются целые миллисекунды границ. Web берёт целую часть монотонной длительности, ограниченной последним действием и границей focus/visibility, и строит конец от целого проецированного начала. Часть до границы окна начисляется предыдущему окну, остаток следующему. Серверный `split_interval` округляет обе UTC-границы вниз для уже спроецированного интервала. Локальные настенные часы используются для обнаружения скачка. Потеря валидного якоря, разрыв тика свыше 20 с или расхождение настенного и монотонного интервала больше 1 с прекращают начисление непроверенной части. Историю сна Web отмечает как `clock_untrusted`.

Один координатор владеет партицией browser storage для одного lifecycle. Кандидат должен быть видимым, сфокусированным, с валидным контекстом и действием в пределах пяти минут. Координатор выбирает последнее начало подходящего контекста, при равенстве стабильный ID вкладки по убыванию. Закрывает предыдущий контекст от той же монотонной границы, прежде чем открыть следующий. Heartbeat каждые 5 с, lease 15 с. Захват и сохранение проверяют токен lease одной транзакцией IndexedDB. Новый координатор восстанавливает подтверждённый снимок и локальную накопленную часть, затем начисляет от своей проверенной границы. Без надёжной передачи помечает `lease_lost` и продолжает с новой проверенной границы. Наблюдаемое время ограничено одной активной вкладкой.

V2 выбирает победителя на каждом отрезке по исходному времени начала, затем UUID события и producer namespace по убыванию. Сверка применяет этот выбор ко всем пригодным пересекающимся интервалам субъекта до фильтрации по курсам. При совпадении рабочих входов обе стороны измеряют одну последовательность активных контекстов. Неоднозначность последовательности при двух независимых писателях или недоказанном приоритете требует сверки, а отсутствие пригодного полного эталона даёт unknown.

| Вход | Контекст окна |
| --- | --- |
| Обычная теория урока | `theory/course_id/lesson_id` |
| Практика урока, включая контекст урока в editor | `practice/course_id/lesson_id` |
| V2 `tool_segment` | `payload.tool_id/course_id/null`, для v2 `platform-tools` курс становится `null` |
| V2 `course_opened`, визит нулевой длительности | Присутствие, 0 измеренных мс |
| Boundary credit | Отдельная величина старого отчёта |
| Прогресс Core | Доверенный показатель Core |

В `stats` входят только измеренные миллисекунды. Tool ID переиспользуется из v2. Tool с `lesson_id: null` проверяется по точной паре `tool_id/course_id`, в том числе по разрешённому глобальному `null`. Null курс разрешён только без урока. Урок всегда привязан к курсу и секции theory/practice.

## Grant, batch и подтверждение

| Маршрут | Вход | Успех |
| --- | --- | --- |
| `POST /api/analytics/windows/grant` | Текущая сессия ученика/Core и JSON `protocol_version, writer_id, writer_generation` | `WindowGrantResponse` с подписанным grant, subject_ref lifecycle, writer tuple и серверными часами |
| `POST /api/analytics/windows/batch` | Bearer grant и JSON `{protocol_version, windows}` | HTTP 200 и `WindowBatchAck` после решения по каждому ключу |

Grant выдаётся для актуального разрешённого lifecycle ученика, заданного подписанным `sub`. `sub` равен существующему Analytics `subject_ref` поколения аккаунта. Сессия и учётная запись не присылаются в теле снимка. Claims связывают `iss`, `aud=analytics-windows`, `scope=windows:collect`, обе версии, `iat/nbf/exp`, UUID писателя, его generation, курсы и tool scopes. Проверка EdDSA и issuer/key, конкретного audience, интервала `nbf <= now < exp`, когорты и lifecycle предшествует вызову порта. Писатель сохраняет UUID случайно изолированным для storage partition и lifecycle, generation сохраняет при refresh/reload. Смена lifecycle запрещает повтор со старой очередью. Неудачное хранение идентичности даёт нового писателя и явную причину потери покрытия.

В каждом snapshot обязательны `activity_date, slot_no, writer_id, writer_generation, server_epoch, seq, stats, catalog_versions, client_final`. Проверять действующие курсы и scope перед записью целого ключа, даже если grant выпущен до отзыва. Core выполняет эту проверку при каждом проксировании. Доступ Collector ограничен доверенным Core и валидными grants, а Privacy защищает жизненный цикл в транзакции. Любая запрещённая позиция отклоняет весь ключ, другие корректные ключи batch имеют отдельные транзакции. В одном batch по одному снимку ключа. Непригодная корреляция хотя бы одного элемента или повтор ключа даёт 400 до начала записей. После проверки корреляции остальные ошибки формы возвращаются в соответствующем item. Поля `student_id` и `subject_ref` внутри элемента дают `subject_forbidden`.

`catalog_versions` содержит ровно по одной версии каждого курса, представленного уроком. Версия и lesson ID подтверждаются опубликованным разрешённым каталогом. Разные версии одного course в снимках одного epoch дают `catalog_conflict`. В такой ситуации новый неполный набор позиций не пишется. При сверке конфликт версий с непригодным эталоном остаётся unknown. Позиция tool без урока проверяется по tool scope, и версия учебного каталога для неё не требуется.

Хеш элемента строится по всем полям snapshot, включая дату, слот, writer, generation, epoch, seq, stats, версии каталога и client_final. Позиции сортируются по `tool_id, course_id, lesson_id`, null сортируется как пустая строка. Затем ключи всех JSON-объектов сортируются ASCII лексикографически, пробелы и завершающий перевод строки отсутствуют. UUID приводится к канонической строчной форме, дата к YYYY-MM-DD, числа к десятичному целому. SHA-256 вычисляется от UTF-8 и отдаётся как 64 строчные hex-цифры. Приватный контекст grant, вся обёртка batch и request correlation ID не участвуют. HTTP отклоняет дублирующие поля JSON и ограничивает размер до обработки.

| Статус item | Код | Результат |
| --- | --- | --- |
| `committed` | `committed` | Commit business-строки, receipt и служебного состояния выполнен. |
| `duplicate` | `same_payload` | Равный seq и хеш применённого снимка. Revision и суммы прежние. |
| `stale` | `stale_seq`, `stale_epoch`, `finalized` | Меньший seq, другая база или закрытый снимок. Состояние сохраняется. Rebase разрешён при наличии подтверждённой базы и границы. |
| `conflict` | `payload_conflict`, `non_monotonic`, `catalog_conflict` | Равный seq с другим хешем, уменьшение позиции или смена версии курса в epoch. Business-строка сохраняется. |
| `pending` | `ownership_conflict` | Другой writer или generation. Долговечно помечается ключ на сверку. Business-строка сохраняется. |
| `rejected` | `invalid_snapshot`, `subject_forbidden`, `writer_forbidden`, `course_forbidden`, `tool_forbidden`, `invalid_active_ms`, `window_budget_exceeded`, `catalog_conflict`, `too_large`, `future_clock`, `too_late`, `privacy_forbidden` | Ошибка отдельного элемента. Нет записи по нему. |

ACK возвращает `index, activity_date, slot_no, writer_id, writer_generation, server_epoch, seq, payload_hash, status, code, confirmed`. Subject определяется grant и сверяется с lifecycle очереди. У `confirmed` есть текущая server revision, stats, tuple применённого снимка и `rebase_at`. Для committed/duplicate все поля подтверждают точный снимок. При запрещённом контексте в прежних stats нельзя выдавать `confirmed` для иных статусов. У rejected допустим null digest и отсутствующее подтверждение. Pending подтверждает только постановку ключа на сверку. При потере ответа после частичного batch клиент повторяет исходные элементы и получает точные независимые результаты.

| Статус HTTP | Код ошибки envelope |
| --- | --- |
| 400 | `invalid_request`, `unsupported_version` |
| 401 | `unauthorized` |
| 403 | `forbidden` |
| 404 | `capability_off` или ответ старого маршрутизатора |
| 413 | `too_large` |
| 429 | `rate_limited`, заголовок `Retry-After` |
| 503 | `unavailable`, `privacy_unavailable` |

У старого Core без v3-маршрутов GET-only SPA-router может вернуть HTTP 405 на POST известного capability endpoint. Когда `Allow` явно не содержит POST, Web считает это окончательным unsupported и прекращает автоматические повторы. Для зарегистрированных текущих endpoints действуют коды из таблицы выше.

Ответы ошибок безопасны для журнала и содержат `code, message, correlation_id`. Authz, subject fencing и проверка capability fail closed. Неведомый исход транзакции до ответа остаётся неведомым до безопасного повтора и сверки ACK.

## Пределы и время жизни

| Ограничение | Значение |
| --- | --- |
| Batch | 64 KiB исходного UTF-8 JSON, 1–16 уникальных ключей |
| Snapshot | 16 KiB исходного элемента, 1–32 уникальные положительные позиции, сумма до 900000 мс |
| Grant | До 300 с, до 16 KiB JWT, до 64 курсов и 80 tool scopes. Превышение допустимых прав выдачи не урезает snapshot. |
| Приём | Начало окна максимум на 120 с вперёд, приём до конца окна + 24 ч включительно |
| Темп | Обычная отправка раз в минуту и при финализации, 12 batch/min на lifecycle, лимитировать до чтения хранилища |
| Retry Web | Таймаут запроса 10 с и до 8 попыток всего на тело, jittered backoff 1/2/4/8/16/32/60 с, Retry-After имеет приоритет, срок приёма остаётся верхней границей |
| Outbox Web | До 96 ключей и 512 KiB, до конца окна + 24 ч. Хранятся неизменное неполучившее ACK тело и состояние накопителя, без grant и сессионных токенов |
| Хранение сервером | Business и control до 90 дней от московской даты окна. Кардинальность по одному ключу в каждой таблице, лимиты stats выше. Задача сверки сохраняется как control, входной receipt пригоден для повтора в период приёма. После конца окна + 8 дней не обещается активное восстановление просроченного входа. Доказательства текущего состояния и replay fence сохраняются до истечения control или purge. |

Временная недоступность сети приостанавливает попытки до сигнала возобновления, сохраняя тело до срока. 401 запускает однократное получение нового grant с тем же writer и проверкой subject, 429 учитывает Retry-After, 503 следует бюджету. 404/unsupported завершает активные попытки v3 и оставляет диагностическую причину. Тело удаляется из активной очереди по точному committed/duplicate с совпадающими ключом, writer, generation, epoch, seq и digest. Pending и чужой ACK тело не подтверждают. При явном stale или запрещённом контексте тело переводится в карантин с причиной, исходный неподтверждённый хвост отмечается в покрытии. Истечение, исчерпание попыток, потеря IDB или переполнение оставляют наблюдаемую причину. При смене lifecycle изолированное состояние прежнего субъекта удаляется и запросы прерываются.

## Состояние, DDL и транзакции

| Объект | Поля и инварианты |
| --- | --- |
| `analytics.student_activity_windows` | PK `(student_id UUID, activity_date DATE, slot_no SMALLINT)`, обязательный `stats JSONB` с канонической непустой формой, `revision BIGINT > 0`. Проверка слотов, положительных целых, уникальности контекстов и общей суммы. |
| Служебное состояние одного ключа | Тот же PK. Пара nullable `writer_id UUID, writer_generation BIGINT`, положительный `server_epoch BIGINT` с началом 1, nullable пара `seq BIGINT, payload_hash`, revision последнего результата, `catalog_versions JSONB`, boolean `client_final`, nullable `rebase_at TIMESTAMPTZ`, phase, причины покрытия, `source_generation BIGINT`, `change_generation BIGINT`, `reconciled_generation BIGINT NULL`. Индекс по состоянию dirty/дате для ограниченной выборки. |
| Факт v2 | Остаётся в каноническом v2 журнале. Ключ дубликата v2 остаётся прежним. |
| Fence lifecycle | Существующий `subject_fences` и проверка свежести Privacy. Purge удаляет business/control строки, сохраняя жизненный fence. |

`WindowState` хранит результат в памяти для переходов. В PostgreSQL непустые stats лежат только в business. Для доказанного нуля repair удаляет business-строку, но control сохраняет revision, epoch, seq-фильтр и диагностику. Business revision увеличивается на изменённое содержимое или доверенное происхождение, повтор и увеличение seq без изменения stats её сохраняют. Epoch, seq и generation ограничены JS safe positive integer, хранимая revision положительный BIGINT.

| Вход | Переход |
| --- | --- |
| Ключ отсутствует, первый непустой снимок epoch 1 | Под subject/window lock устанавливается owner и появляется business-строка. |
| Тот же owner, generation и epoch | Полный больший seq сохраняется только без уменьшения прежних позиций и смены версий. Равный seq сравнивается по хешу. |
| Последний снимок клиента | `pending_reconciliation`. `client_final` закрывает отправку этого writer epoch, границу полноты определяет сверка. |
| Другой писатель | `pending_reconciliation` и `writer_conflict`, если он обращается на действующем epoch. При неполном v2 эталоне исход unknown сохраняет business. |
| Сопоставление с доказанным покрытием | `verified` при равенстве, `repaired` при изменении. Repair поднимает epoch и revision, сбрасывает receipt снимка, сохраняет подтверждённую базу. |
| Неполный источник или открытый v2 commit | `incomplete_coverage` с причинами, без изменения business. |
| Новый поздний v2 commit | Увеличивает source и change generation, снова `pending_reconciliation` даже из verified/repaired. |
| Смена owner после покрытой сверки | Увеличивает epoch и revision, возвращает новому owner подтверждённую base и `rebase_at`. Измерять новый хвост лишь с этой границы. При закрытом окне прежний хвост отдельно отмечается как unknown. |

Порт `WindowWritePort.write_window(key, snapshot, received_at=...)` возвращает `Transition` после подтверждённого commit. Store проверяет, что координаты key совпадают с snapshot, затем берёт существующий subject lock и блокировку окна, повторно проверяет Privacy и только потом применяет `receive_snapshot`. ACK собирает transport через `build_ack`. Роли Collector, worker, Privacy и читателя отчёта разделены. Collector не получает общего права менять verified/repaired или выполнять произвольный update. Worker работает через ограниченный порт и CAS, Privacy удаляет данные требуемого lifecycle штатным путём, приложение отчётов читает v2.

`WindowV2ChangedPort.mark_v2_changed(transaction, keys)` вызывается в той же транзакции, что и принятие нового v2-факта. Для каждого пересекаемого ключа ставится dirty marker, increment source/change generation происходит перед commit. Отмечаются обе стороны московской полуночи, соблюдается порядок ключей, duplicate/rollback не увеличивают generation. Без этого доказательства старую версию писателя нельзя считать покрытой. Shadow off на расширенной схеме оставляет hook для уже включённой в наблюдение когорты. Старый бинарник без hook допускается как v2-only, после возврата нужна ограниченная перепроверка v2 и явный интервал неизвестного покрытия до проверки.

`WindowReconciliationPort.changed_windows` даёт ограниченную текущую порцию dirty keys, `read_reconciliation(key)` читает согласованное состояние и пересекающиеся факты всех курсов. Удерживаемый subject lock или индикатор writer in-flight не даёт объявить полный результат. Адаптер затем вызывает `reconcile_window(key, decision, rebase_at=...)`. В одной транзакции блокируются subject и ключ, повторяется Privacy, проверяются обе generation, записывается repair или классификация. Потерянный CAS оставляет исходное наблюдение и dirty ключ доступными. До commit рабочая запись не считается применённой, после commit та же generation повторно не повышает revision. При удалении между чтением и commit применяется fence и repair не воскрешает данные.

Окончание client window и окончательная зрелость независимы. V2 принимает факт до семи суток после окончания факта, событие длится до минуты, Web v2 держит до 200 событий в памяти до 24 ч. `late_deadline` использует слот end + 1 мин + 7 суток. До срока возможно подтвердить сравнение на явно наблюдаемом полном входе конкретного сценария и записать его generation. Возраст, 48 ч наблюдения и отсутствие строк сами по себе дают недостаточное доказательство. По достижении срока обязательны доказательство непрерывности источника, отсутствие in-flight и проверка неизменной generation до commit. Поздний факт снова требует проверки. Если оба канала потеряли измеренный ключ сценария, он всё равно входит в сравниваемое объединение ключей и даёт `absent_both`.

Диагностический экспорт `WindowDiagnostics` содержит key, client-final seq, `v3_confirmed`, подтверждённые v2 event ID/namespace, source/reconciled generations, состояние и `coverage_reasons`. Export для приёмки использует синтетические идентификаторы, снапшоты и причины. Рабочие метрики состояния и ошибок агрегируются без персональных идентификаторов и токенов.

## Совместимость и флаги

- `VITE_ANALYTICS_WINDOWS_ENABLED=false` управляет новой Web-генерацией.
- `ANALYTICS_WINDOWS_INTAKE_ENABLED=false` управляет приёмом и выдачей grant для окон.
- `ANALYTICS_WINDOWS_RECONCILIATION_ENABLED=false` управляет фоновым сравнением/исправлением.
- `ANALYTICS_WINDOWS_COHORT` по умолчанию пуст и содержит разрешённые lifecycle UUID. `ANALYTICS_WINDOWS_T0` по умолчанию отсутствует, при включении обязательна ISO UTC отметка старта.

Expand DDL и purge-совместимый Privacy готовы до первого v3 commit. Старые Web/Collector и новый Collector с выключенными флагами продолжают использовать v2 на базовой и расширенной схеме. Новый Web воспринимает неподдерживаемый маршрут как off. На старой схеме включённый новый приём остаётся закрыт. На этапе I источником отчёта остаётся v2.
