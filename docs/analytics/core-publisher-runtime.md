# Core Analytics publisher: локальный исходный контракт

`python -m pymentor_core.app.analytics_publisher` — отдельный процесс Core, не ASGI worker. По умолчанию отключён и до подключения к БД требует четыре явных значения `1`: `PYMENTOR_ANALYTICS_PUBLISHER_ENABLED`, `PYMENTOR_ANALYTICS_DELIVERY_ENABLED`, `PYMENTOR_ANALYTICS_SNAPSHOT_PROOF_ENABLED` и `PYMENTOR_ANALYTICS_PUBLISHER_BACKFILL_COMPLETE`. Последнее — утверждение оператора, что начальный backfill завершён и старые writers без capture остановлены; оно само по себе не доказывает это. Процесс не выполняет миграции и backfill.

Перед работой `DATABASE_URL` должен содержать PostgreSQL host, пользователя и базу, а `PYMENTOR_ANALYTICS_PUBLISHER_EXPECTED_DATABASE` и `PYMENTOR_ANALYTICS_PUBLISHER_EXPECTED_USER` обязаны совпадать и с URL, и с серверным `current_database(), current_user`. Проверяются revision Core, полная проверка addon версии 2, совпадение двух sealed snapshot barriers activity/progress с их checkpoints и действующий write gate. Для mirror дополнительный activity preparation barrier не требуется; для outbox_only штатный gate дополнительно требует sealed preparation и analytics reads. Это проверка подготовленного состояния, не способ выполнить подготовку.

Нужна та же конфигурация, что у существующего Core relay: `PYMENTOR_ANALYTICS_PRODUCER_ISSUER`, `PYMENTOR_ANALYTICS_PRODUCER_KID`, `PYMENTOR_ANALYTICS_PRODUCER_KEY_FILE`, `PYMENTOR_ANALYTICS_PRODUCER_ID`, `PYMENTOR_ANALYTICS_COMMAND_KEY_FILE`, `PYMENTOR_ANALYTICS_GRANT_PUBLIC_KEY_FILE`, `PYMENTOR_ANALYTICS_AUTHORITY_PUBLIC_KEY_FILE`, `PYMENTOR_ANALYTICS_TRANSFER_URL`, `PYMENTOR_ANALYTICS_AUTHORITY_URL`, `PYMENTOR_ANALYTICS_AUTHORITY_ID`, `PYMENTOR_ANALYTICS_AUTHORITY_ISSUER`, `PYMENTOR_ANALYTICS_AUTHORITY_KID`. Producer, command, grant и authority ключи проверяются на независимость; секреты не должны попадать в аргументы, логи или этот документ. HTTP transport сохраняет существующие ограничения URL и проверку токенов.

## Работа и границы

Dockerfile содержит отдельный target `analytics-publisher`: тот же минимальный
runtime, команда `python -m pymentor_core.app.analytics_publisher`, HTTP
healthcheck отключён, потому что процесс не открывает HTTP listener. Default
target `runtime` по-прежнему запускает API. Target сам не задаёт credentials,
не включает flags и не выполняет DDL. Проверка сборки/запуска нового target
фиксируется отдельно; наличие Dockerfile не является runtime PASS.

Один последовательный цикл: проверка gate, до 10 фактов с существующей обработкой отдельного журнала удаления, keyset страница до 20 текущих пользователей и до 2 попыток подготовки отсутствующего proof, затем до 10 proof relay. NullPool не удерживает соединения; connect/statement/lock имеют лимиты 3/3/1 секунды, каждый сетевой relay имеет общий deadline 5 секунд. Нет сети внутри транзакции подготовки snapshot. У существующих snapshot-функций сохраняются лимиты сущностей и 8 MiB digest. Между циклами есть пауза с jitter, ошибки цикла ограничены backoff до 60 секунд.

Ключ страницы находится в памяти процесса, в конце прохода возвращается к началу. При рестарте возможен повторный просмотр; уникальный `(subject_ref, cut_revision)` и существующая сериализация под блокировкой пользователя сохраняют один proof данного среза. Publisher берёт gate, затем блокировку пользователя, в том числе при создании lifecycle; для существующего значения идентичность повторно сверяется под блокировкой. После этих блокировок в той же транзакции повторно проверяется, нет ли для lifecycle неподтверждённого proof или quarantined outbox event. Пока любой proof не verified, publisher не готовит следующий срез, даже если revision изменился: сначала relay должен подтвердить предыдущий. Ожидающий пользователь не расходует лимит подготовки, остальные продолжают обрабатываться. Удалённые lifecycles не выбираются из текущей таблицы пользователей. Ошибка guard откатывает транзакцию и учитывается в aggregate blocked; обработка других страниц продолжается, следующий полный проход повторит попытку. Если у lifecycle есть quarantined proof или outbox event, новый proof для него не подготавливается до операторского разбора.

Реальные гарантии relay не расширены: после неопределённого ответа существующий worker сверяет receipt по исходному ID до повторной отправки; факт принятия proof ещё не является verified coverage. Отдельный proof relay сверяет статус до verified. После лимита попыток или quarantine требуется операторская диагностика; publisher не сбрасывает состояния автоматически. `publisher_ready`, `publisher_tick`, `publisher_cycle_failed` и `publisher_stopped` дают только агрегаты без ID, запросов и credentials. `blocked`, `fact_blocked`, `proof_blocked` означают необходимость диагностики; отсутствие tick контролируется внешним supervisor. Эти сигналы не доказывают свежесть всех данных и не заменяют проверку реального end-to-end состояния. SIGTERM/SIGINT проверяются между фазами, а не между элементами batch. На весь сетевой этап relay задан общий deadline 5 секунд, но обработка и завершение до 10 claims включают отдельные операции с БД, поэтому пять секунд не являются общей границей остановки процесса. Время остановки зависит также от БД и планирования; мгновенное или гарантированно укладывающееся в определённый grace period завершение не проверено. Принудительное завершение опирается на существующие leases и reconciliation.

Начальный source-history backfill, остановка старых writers, включение capture и cutover управляются существующими операционными процедурами. Publisher не авторизует переключение реальных пользователей. Общая функция `stage_subject`, которую использует и ручная команда staging, под gate и блокировкой пользователя откладывает новый срез при неподтверждённом другом срезе и отклоняет staging при quarantine; повтор того же незавершённого среза сохраняет проверку неизменности и идемпотентность. Остановка процесса не откатывает ранее доставленные данные; при возобновлении очередь и proofs сверяются по сохранённому состоянию. Дополнительный deployment и ingress не создавались; для отдельного deployment потребуются собственные ресурсы и внешний мониторинг, а встроенный HTTP healthcheck serving image следует переопределить.

`publisher_tick` дополнительно показывает `fact_*` и `proof_*` для очередей
фактов и подтверждений. Счётчики `pending`, `claimed` и `quarantined`
ограничены `backlog_cap=1000` на состояние. Флаг `truncated=1` показывает, что
хотя бы одно состояние превысило предел. `eligible_sample` считает доступные
к доставке строки внутри выборки с учётом срока захвата, лимита попыток и
зависимости подтверждений от недоставленных фактов. При усечении это нижняя
граница размера доступной очереди. Если запрос деталей не удался, журнал
пишет `publisher_backlog_detail_unavailable` и сохраняет прежнюю проверку
терминальной блокировки и паузу цикла. Журнал содержит агрегаты очереди.

## Длительный отказ Analytics

При ошибках доставки Core продолжает фиксировать бизнес-изменения и исходящие
факты в одной транзакции PostgreSQL. Если Collector недоступен, растут очередь и
занятое место на диске. `backlog_cap` ограничивает только выборку для журнала.
Резерв определяют по фактическому приросту исходящих таблиц и WAL на целевом
профиле. Для расчёта времени до исчерпания резерва разделите свободные байты
сверх согласованного эксплуатационного минимума на прирост занятого места в
секунду за период отказа. Фиксируйте длительность замера и нагрузку Core. Когда
скорость растёт, используйте более свежую верхнюю оценку. На текущем этапе
длительность безопасного отказа и скорость догоняющей доставки не измерены.

1. Установите границу сбоя по готовности Collector, Query, authority и Core.
   Сопоставьте её с `publisher_cycle_failed`, `fact_*`, `proof_*` и свободным
   местом на PostgreSQL. При `truncated=1` видимый размер очереди является
   нижней оценкой. Сравните размеры таблиц на двух отметках времени, например:

   ```sql
   SELECT now() AS measured_at,
          pg_total_relation_size('public.analytics_transfer_outbox') AS outbox_bytes,
          pg_total_relation_size('public.analytics_transfer_snapshot_proofs') AS proof_bytes;
   ```

2. Если сбой возник до переключения, отложите переключение чтений и записи
   `outbox_only`. Если переключение состоялось, для возврата используйте
   действующий протокол с write gate и replay отметок. Проверьте записи,
   появившиеся после переключения, и состояние удаления перед возвратом.
3. После восстановления дайте исходному Publisher продолжить обработку с теми
   же ID. Истёкшие leases доступны повторному захвату. Для неопределённого ответа
   worker сначала запрашивает квитанцию по исходным ID и fingerprint. Для удаления
   проверьте отдельно запись в authority и подтверждение применения удаления.
4. При `fact_blocked=1` или `proof_blocked=1` выясните состояние исходного факта,
   квитанции и покрытие в Analytics. Сохраните состояние карантина и не сбрасывайте
   попытки автоматически. Готовность роли сама по себе не означает, что очередь
   догнала Core. После восстановления проверьте уменьшение backlog, подтверждение
   proof, чтения и отсутствие повторных эффектов на контрольных фактах.

## Проверки и непроверенные границы

17.11.2026: реальный local PostgreSQL/HTTP `--publisher` run завершился exit0:
без ручного stage/relay после старта процесс исправил cut1→3 и global503→200;
после принудительной Windows остановки и новой business mutation доставка
возобновилась до cut4, ровно одного факта/проекции и self/profile/global200.
Три временные БД, 12 ролей и Redis namespace проверены как очищенные.
Это не graceful Linux SIGTERM и не конкурентный PostgreSQL publisher proof.
Jira CORP-428/comment10330.

Новый локальный Docker target фактически собран (imageID
`sha256:f307128472b60789b400e6f25724a6eb65fc0f4ea3c336263296ef956c9dec02`),
Python3.12.16/nonroot10001/healthcheckNONE. Default-off запуск без сети завершился
санитизированным admission отказом до подключения; operator tools отсутствуют.
Текущие исходники прошли109 tests/analytics_delivery в Linux test image с
readonly mounts, networknone и tmpfs SQLite. Это не проверка сетевого запуска
publisher image. Сетевой сценарий для указанного образа выполнен отдельным
прогоном 19.11.2026.

19.11.2026: команда `python -B tools/test_cross_service.py --run --chain --a010 --publisher --publisher-image sha256:f307128472b60789b400e6f25724a6eb65fc0f4ea3c336263296ef956c9dec02` завершилась с кодом 0 на отдельном локальном стенде. Linux Publisher восстановил устаревшее подтверждение поколения и чтения, остановился по SIGTERM как PID 1 с `publisher_stopped`, а после запуска доставил изменение, записанное во время остановки, с одним фактом и одной проекцией. Harness подтвердил очистку одноразовых ресурсов. Отдельный тест на реальном PostgreSQL проверил гонку двух соединений за одну строку и отказ ACK от прежнего владельца. Два полноценных publisher одновременно по HTTP и ёмкость очереди при длительном отказе этим прогоном не проверялись.

Автономные focused тесты проверяют disabled/wrong identity, текущее revision, нового пустого пользователя, повторное использование numeric ID, ограничения страниц, отказ guard, quarantine, порядок этапов и повторную попытку после ошибки. Для задержанного подтверждения проверена последовательность трёх revisions, продвижение другого пользователя и повторная проверка после устаревшего чтения страницы. Существующие тесты relay покрывают потерянный ответ и lease, а тесты snapshot — откат и повторный staging. Эти focused проверки используют SQLite и заглушки.
