# CORP-66: локальная проверка Analytics grants

Версия 16.11.2026. Реализованы проверка подписи Ed25519, отдельные локальные политики для учебного collection и scoped reports и синтетический issuer для тестов. Контракт [CORP-58](contracts.md), privacy [CORP-69](privacy.md). Реальных Core issuer, HTTP collection/report/control handlers, БД-fence и privacy restore barrier в рамках этой работы нет; штатный `/ready` остаётся 503. Существующая учётная запись Core и аутентификация не изменены.

## Криптографическая граница

`GrantVerifier` принимает только явно переданный `issuer` и непустую локальную карту `kid → public PEM` (до 32 ключей, до 4096 байт каждый). Ключ должен быть Ed25519. `extract_bearer` работает с сырыми ASGI headers и требует ровно один Authorization header, схему Bearer и один ASCII JWT без пробелов. Компактный JWT ограничен 16 KiB, раскодированный header — 1024 байтами; строго проверяются формат Base64URL, три части, отсутствие повторных JSON-ключей и дополнительных полей header. Header остаётся недоверенным и служит только для выбора локального `kid`: сетевого JWKS, Core, Redis и session secret нет.

PyJWT 2.15.1 проверяет подпись c **фиксированным** `algorithms=["EdDSA"]`, issuer, единственную audience `analytics`, обязательные `iss/aud/sub/iat/nbf/exp`, срок и начало действия без leeway. Затем строгий Pydantic `GrantClaims` проверяет версии, типы, роль и scope; максимальное время жизни collection 300 секунд, report 60 секунд. Ошибки не включают сырой токен, claims или ключи. Локальная синхронизация UTC обязательна. Ключи не извлекаются из JWT. `VerifiedGrant` — внутренний результат verifier; приложение не должно создавать его из тела запроса или неподписанных claims. Проверка срока повторяется до и после fence-проверки, но длительная DB-транзакция должна отдельно соблюдать deadline и fence-инварианты.

Контрольный producer имеет `ProducerClaims` и `ProducerVerifier` с отдельными `aud=analytics-control`, `scope=control:write`, issuer, списком разрешённых producer ID и отдельной локальной keyring; его срок не превышает 60 секунд. Для одновременной настройки используйте `build_verifiers`: она отвергает пересечение **материала** публичных ключей даже при разных `kid`. Это только криптографический адаптер: закрытый control transport и настоящие credentials ещё не подключены.

Конфигурация процесса имеет существующий role-specific префикс `ANALYTICS_COLLECTOR_` или `ANALYTICS_QUERY_`: `GRANT_ISSUER` и `GRANT_KEYS_JSON` задаются вместе, JSON содержит карту `kid → PEM public key`. Для collector отдельно доступны `PRODUCER_ISSUER`, `PRODUCER_KEYS_JSON` и `PRODUCER_ALLOWLIST_JSON` (массив producer ID), также только вместе. Query не принимает producer-конфигурацию, processor не принимает эти настройки. JSON keyring ограничен 64 KiB, allowlist 16 KiB и 100 ID; повторные ключи, пустая или некорректная конфигурация останавливают startup с общим сообщением без содержимого ключей, grant или DSN. При отсутствии конфигурации `app.state.grant_verifier` и `producer_verifier` равны `None`; будущие зависимости обязаны отклонять такие запросы. Значения создаются в lifespan и удаляются при остановке. Никаких product routes здесь нет. Приватные ключи в приложение не монтируются. При изменении конфигурации требуется перезапуск процесса с новой keyring; hot reload здесь не реализован. Нормальная ротация сохраняет старый ключ минимум 300 с после последней выдачи плюс задержку распространения; после удаления или компрометации ключа новый verifier немедленно отклоняет его. Роль/назначение, отозванные в Core, ограничивают повторную выдачу, но уже выданный grant действует не дольше своего TTL; остановка Core не мешает локальной проверке действительного grant и не продлевает его.

## Авторизация и удаление

`authorize_collection` принимает только verified user/collect и курс из signed `course_ids`. Subject и `producer_namespace=browser:<subject_ref>` определяются сервером по `sub`, а не browser body. Staff grant не собирает учебное время. `authorize_report` требует явные product course и lifecycle subject: user — только себя в подписанных курсах, leader — единственный подписанный курс и явно перечисленных учеников, admin — global student read. Пустой список leader допустим и никого не разрешает. Неподписанный course/subject, body role и URL не расширяют scope. Одна страница grant может содержать до 1000 subject, но общий лимит JWT 16 KiB обычно ниже; будущая выдача обязана разбивать весь roster на согласованные страницы или использовать доверенный roster port, не обрезая его молча.

Проверка scope предшествует обращению к fence. После успешной проверки вызывается обязательный `SubjectFence.permits`: для collection — subject пользователя; для report — lifecycle **актёра и целевого ученика**, совпадающие проверяются один раз. Закрытый или недоступный fence не разрешает операцию, исключение backend скрывается. На данном этапе это интерфейс и проверки с test doubles; они не заменяют атомарный fence. Будущие handlers должны удерживать совместимые DB locks/CAS до commit/materialization для актёра и целевых subjects в детерминированном порядке, совместно с deletion epoch и readiness barrier по [privacy.md](privacy.md). Только так удаление сильнее действующего grant; без такого подключения live-обработчики включать нельзя.

В будущем Core issuer должен сначала вычислить эффективную staff-роль по авторитетным данным: текущий Core Principal может одновременно содержать student и admin, а leader определяется server-side course binding. Простое присутствие student или default user не разрешает collection сотруднику. Проверка назначений, полного roster и выпуска grants относится этапу 2; этот код использует только synthetic issuer.

## Локальный synthetic issuer

`services/analytics/tools/synthetic_issuer.py keygen --private-key <путь> --public-key <путь>` создаёт новую пару только внутри игнорируемого `services/analytics/.local/`; существующие файлы не перезаписываются. `issue --private-key <путь> --kid <id> --claims-file <json> --kind grant|producer --emit-token` выдаёт JWT в stdout **только** при явном `--emit-token`, после проверки синтетического issuer с префиксом `synthetic-`, срока и схемы. Это инструмент для отдельного synthetic профиля, не Core issuer. Не перенаправляйте выданный токен в общие логи. На Windows разрешения файлов наследуются от каталога: владелец стенда должен ограничить ACL `.local` до создания ключей; сам Python mode не доказывает приватность Windows ACL.

Зависимости закреплены: PyJWT 2.15.1, cryptography 50.0.2, cffi 2.1.1, pycparser 3.12. Проверенные официальные контракты: [PyJWT usage](https://pyjwt.readthedocs.io/en/stable/usage.html), [PyJWT API security](https://pyjwt.readthedocs.io/en/stable/api.html#jwt.decode), [cryptography 50.0.2 Ed25519](https://github.com/pyca/cryptography/blob/50.0.2/docs/hazmat/primitives/asymmetric/ed25519.rst) и [PEM serialization](https://github.com/pyca/cryptography/blob/50.0.2/docs/hazmat/primitives/asymmetric/serialization.rst).

Фактические тесты: `tests/auth` создают и подписывают JWT в памяти; проверяют malformed/duplicate headers и claims, подпись, issuer/audience/время/scope, forged subject, курсы, три роли, пустой roster, удаление актёра/ученика, outage fence, ротацию, изоляцию producer и test-only FastAPI dependency. Отдельный CLI-тест создаёт локальную пару и проверяет явный вывод токена. Это не проверка продуктового HTTP API, хранилища, DB locks, готовности или Core integration.
