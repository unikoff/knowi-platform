# Analytics — архитектура сервиса и план приёмки

Срез на 17 ноября 2026 года. Документ фиксирует решение о полном переносе расчётов учебной активности в Analytics. Фактическое состояние сверено с рабочим деревом ветки `feach/Analitick`, базовый коммит `f787672ff`, и локальными протоколами. Архитектурная карточка — [CORP-438](https://platformpy.atlassian.net/browse/CORP-438).

## Что делает сервис

Цель перехода — оставить в Analytics все расчёты пользовательской учебной активности. Core хранит профиль ученика, роли, статусы, подписки, курсы и авторитетные завершения уроков и задач. Запись на занятия, бронирования и их календарь остаются в Core. Имена и права доступа к ученикам отчёты получают через доверенный контракт Core.

Analytics рассчитывает календарь учебной активности, текущую серию, активность за неделю и другие периоды, время теории и практики, число активных и неактивных учеников, графики и рейтинг по завершениям. Графики и рейтинг строятся в Analytics на переданных Core фактах прогресса. Core продолжает фиксировать сами завершения.

В архитектуре три зоны: **сборщик**, **аналитика** и **PostgreSQL Analytics**. Внутри аналитики обработку, чтение отчётов и удаление можно запускать отдельными процессами. Разделение процессов позволяет подбирать ресурсы под их нагрузку. Первичные факты остаются общими для всех курсов.

## Как проходят данные

```text
Core → Web              права и краткоживущий grant, версия каталога
Web Tracker → Collector → PostgreSQL Analytics / activity_facts
Core → Analytics        доверенные факты завершения уроков и задач
PostgreSQL → Processor → PostgreSQL / проекции интервалов и дней
Web → Query → PostgreSQL / отчёт по разрешённому разрезу
Core → журнал удалений → Privacy → удаление фактов и проекций
```

| Компонент | Обязанность и граница |
| --- | --- |
| Web Tracker | В целевом режиме передаёт отрезки активного времени. Типы времени — теория и практика, включая работу в редакторе. Учитывается видимый учебный контекст в фокусе. После пяти минут бездействия сбор приостанавливается. Покрытие скрытия, сна и возобновления проверяется отдельно в браузере. |
| Collector | Принимает `POST /api/analytics/events/batch`, проверяет grant, область доступа, каталог, версию события и лимиты. Подтверждает принятый факт после commit. Повтор с тем же ID и содержимым идемпотентен, конфликтующее содержимое отклоняется. Обратное давление позволяет ограничить нагрузку на хранилище. |
| Processor | Нормализует интервалы и обновляет производные расчёты. Пересечения устройств и курсов разрешаются по одному контексту на пользователя до фильтрации отчёта. Ревизии a010 и a011 поддерживают проекции по 15-минутным интервалам и московским суткам. При параллельной обработке краткосрочный захват и проверка поколения проекции защищают от записи устаревшего результата. |
| Query | Отдаёт `/api/analytics/reports/activity` и `/api/analytics/reports/activity/details`. Применяет серверную область доступа и пределы периода и детализации. Целевые отчёты различают измеренное время, подтверждённые завершения и перенесённую историю. |
| Privacy | Применяет подтверждённые удаления из Core. Идентификатор поколения аккаунта, отметка об удалении и независимый журнал защищают от повторной записи и выдачи удалённых данных при повторе, пересчёте и восстановлении. В текущем локальном режиме Collector и Query проверяют свежий подписанный источник Core и применение удалений. |
| PostgreSQL Analytics | Одна `activity_facts` для первичных фактов всех курсов. Проекции и служебные записи имеют своё назначение и жизненный цикл. Проекции можно пересчитать из фактов. Миграции и роли Analytics отделены от Core. |

Новые факты хранят псевдонимный ID поколения аккаунта, курс, версию каталога, урок и тип активности, время либо интервал, ID события и служебные признаки приёма. Тексты решений, контакты и токены не входят в payload факта. Автоматическое удаление по возрасту не предусмотрено. Удаление аккаунта включает данные Analytics и его вклад в общие показатели. ## Активный день и перенос истории

**Измеренный активный день** — дата по Москве, на которую приходится положительное учебное время после объединения пересечений. Календарь, серия и сводки по периодам используют одни и те же дневные данные. Открытие платформы с нулём секунд и пустой день не создают активность. После переключения новые отдельные отметки обычного посещения не пишутся. Ученик с измеренным временем считается один раз в выбранной области и периоде. Неактивных можно считать только по известному составу учеников из Core и при достаточной полноте измерений. При неполноте отчёт обозначает неизвестные значения.

**Перенесённая история** — только дата посещения из Core и привязка к поколению аккаунта. Для каждой пары «поколение аккаунта + дата» Analytics задаёт **1 час теории и 1 час практики** с явным признаком «Условное время из перенесённой истории». Это значения на день. Курс, урок, время входа и интервалы из прошлой истории неизвестны. В API и интерфейсе перенесённая история показывается отдельно от измеренного времени. По умолчанию она не влияет на измеренную серию, число активных по замерам, суммы и среднее фактического времени, разрезы по курсам или рейтинги. В календаре такой день виден как исторический. Если на ту же дату появились измерения, день отображается один раз, а условные часы к замерам не прибавляются.

Импорт повторяемый и сверяется по уникальным поколениям аккаунта и датам. Повторный запуск сохраняет итог, удалённые поколения исключаются, а завершения уроков и задач поступают отдельным доверенным потоком Core. Правила текущих отчётов, которые используют отметку открытия или прежние дни Core, меняются через явно версионированный контракт. ## Что видят пользователи

| Роль | Вид и область отчёта |
| --- | --- |
| Ученик | «Личный кабинет → Статистика → Мои данные». Собственное время в курсе, теория и практика, дневная история и данные по занятиям. Подтверждённый прогресс приходит из Core. |
| Ведущий | Существующая панель назначенного курса, метрики курса и детализация по ученикам в разрешённом списке записей на месяц. Один ведущий привязан к курсу через `leader_user_id` в конфигурации курса. |
| Администратор | Панель любого разрешённого курса и общий обзор в `/admin-platform`. Активные и неактивные ученики, время и завершения за период, включая сегодня, с фильтром по курсу. На уровне платформы ученик с измеренной активностью на нескольких курсах считается один раз. |

Учебный Tracker собирает данные роли `user`. Ведущие и администраторы читают разрешённые отчёты об учениках. Новая аналитика работы сотрудников остаётся отдельной задачей. По таймеру рассчитывается наблюдаемое время, а завершение урока подтверждает Core. Если полнота периода неизвестна, пропуски обозначаются как неизвестные. В локальной личной статистике по этой причине учебные дни и среднее пока показаны прочерками.

## Что подтверждено

| Проверка | Результат |
| --- | --- |
| Личный отчёт в локальном браузере | У отдельного QA-ученика закрыта цепочка урок → Collector → PostgreSQL → Processor → Query → «Мои данные». Получено 14 событий и 109,8 с наблюдаемого времени, из них 45,6 с теории и 64,2 с практики. Данные сохранились после полной перезагрузки браузера. Прогресс 9/280 отобразился из Core. |
| Каталог и проекции | Collector подтвердил каталоги `backend` и `backend_copy`. Исправлена обработка русских legacy-алиасов. Обе процедуры заполнения проекций завершились. |
| Параллельный локальный режим | Web направляет сбор и отчёты в отдельный Analytics. Core продолжает прежний учёт посещений. Локальные процессы Collector, Processor, Query и Privacy имеют разные роли БД и пулы, но запускаются вместе. Журнал удалений работает отдельным процессом. |
| Перенос Core | Совместимое чтение календаря и сводок с данными Analytics проверено на изолированном стенде. Основной локальный режим пока параллельный. В Core остаётся группировка завершённых уроков по дням и ученикам для админских сводок. Исторические отметки дня не содержат точной длительности, курса или урока. |
| Нагрузка и восстановление | На плотном синтетическом наборе a011 проверены 20 чтений с p50 328 мс и p95 406 мс. Замер касался Query с готовыми проекциями и заглушкой privacy. Есть успешное изолированное восстановление, а полная матрица текущего локального режима и полный профиль K3s ещё открыты. Первый прогон K3s остановился до разогрева. |

Результат личной статистики записан в [CORP-92](https://platformpy.atlassian.net/browse/CORP-92?focusedCommentId=10355). Локальная работа подтверждена на дату проверки. Формальная приёмка переноса, сравнительный замер нагрузки на Core и серверный запуск остаются открыты.

## Как масштабировать и где искать узкое место

| Что ограничивает работу | Что измерить | Какую часть менять |
| --- | --- | --- |
| Долгое подтверждение приёма или частые 429/503 | p95 приёма и commit, долю отказов, ожидание подключения, блокировки записи | Проверить Collector с 1 и 2 репликами при одинаковом потоке. Если предел в PostgreSQL, добавление Collector увеличит давление на базу. |
| Долго не обновляются отчёты | Возраст старейшей ожидающей работы, скорость обработки, число повторов и конфликтов, время пересчёта | Проверить 1 и 2 Processor. Ограничить одновременный backfill и повторную обработку, если они конкурируют с текущими событиями. |
| Медленно открываются отчёты | p95 по одинаковым фильтрам, план SQL, временные операции и использование пула | Сравнить 1 и 2 Query. Тяжёлый запрос сначала разбирать по плану и объёму чтения. Отдельно проверить, сколько записи и места добавляют дневные проекции. |
| Исчерпывается общий ресурс | CPU, память, IOPS, объём фактов, индексов, WAL и резервных копий, число соединений | Бюджет БД считать по сумме реплик × процессов × (размер пула + переполнение) с резервом на миграции, восстановление и оператора. Решение о выделенном сервере БД принимать по замерам и восстановлению. |
| Замедляется Core или проверка удалений | Задержку Core на тех же запросах и нагрузке, частоту и стоимость проверок источника, задержку применения удаления | Сопоставить режимы до и после переноса. Проверки доступа и удаления входят в измеряемый путь. При недоступности источника выдача закрывается. |

Для K3s подготовлены раздельные workloads и конфигурация ресурсов. План проверки — профиль 10–15 пользователей с последующими ступенями 25/50 и независимым изменением одной роли за прогон. Предварительные ориентиры стенда — p95 Collector ≤300 мс, p95 Query ≤500 мс и задержка обработки ≤60 с. Их нужно зафиксировать вместе с нагрузкой и условиями остановки до сопоставимого прогона. Отдельные реплики на одном узле всё равно делят CPU, память и отказ этого узла. [CORP-113](https://platformpy.atlassian.net/browse/CORP-113) · [CORP-107](https://platformpy.atlassian.net/browse/CORP-107)

Приёмка переноса истории и доверенных фактов прогресса может пройти до включения Tracker. Окончательное отключение прежнего учёта Core ждёт проверки, что учебное время стабильно поступает в Analytics, а чтение, наблюдение и возврат работают. До окончания окна возврата исходная история доступна для сверки. Завершение окна убирает старый рабочий путь Core. Сохранённые исходные копии позволяют проверить происхождение дат и не используются для расчёта текущей статистики.
