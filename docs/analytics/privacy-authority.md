# CORP-427 A: независимый synthetic privacy authority

Отдельный fixture process ведёт собственный SQLite journal вне PostgreSQL Analytics и её backup. Это техническая синтетическая authority, **не Core producer и не production-сервис**. Код сервера лежит внутри `pymentor_analytics.adapters.privacy_authority`, поэтому входит в стандартную сборку Analytics image; тонкий локальный wrapper — `tools/synthetic_privacy_authority.py`. Image и deployment данной работой не собирались.

## Журнал и доверие

Journal создаётся только явной командой `init` в `services/analytics/.local/` (в контейнере — `/app/.local/`): повторное создание существующего файла запрещено, отсутствующий, повреждённый, иной authority ID или journal с пропусками не сбрасывается и не открывается автоматически. В транзакции SQLite с `synchronous=FULL` один writer присваивает непрерывный committed sequence и хранит authenticated producer, `DeletionFence`, полученное authority UTC-время и `deletion_hash(producer, control)`. Этот hash не включает server receipt time или sequence. Удаление/изменение journal rows запрещено SQLite triggers; никакого TTL нет. Повтор одного control ID с тем же hash возвращает ту же seq; другое содержимое или другой producer — conflict. Файл и его storage/backup должны быть независимы от восстанавливаемого Analytics snapshot; отдельный файл на том же хосте сам по себе не устраняет общую потерю диска или хоста.

Privileged `/v1/append` доступен только внутри fixture сети. Требуются оба механизма: короткоживущий Producer JWT (`analytics-control`, `control:write`) и подпись приватным command key по `deletion_command_bytes(producer, nonce, control)`. Producer определяется только после JWT verify. Публичные ключи command отдельно назначаются каждому producer; они не совпадают с ключом JWT issuer или response signing key. `control_id` стабилен при повторе, nonce для каждой попытки новый. Signed `AppendReceipt` подтверждает только durable append в журнал, **не** применение tombstone и не завершение удаления в Analytics. Timeout означает неизвестный исход: повторить тот же producer/control и control ID с новым nonce. Одинаковый ID с изменённым payload запрещён.

Чтение требует отдельный 32-байтный synthetic reader credential; он не разрешает append и хранится как Secret, не в публичном trust manifest. Каждый ответ `attach`, `barrier`, `page`, `observe` подписан Ed25519 отдельным authority response key. Подписываются authority ID, issuer, фиксированная audience, kid, request nonce, session, вид операции, HWM, range, записи и срок кадра; источнику нельзя доверять из булевого флага. `AuthorityClient` проверяет pinned public key, подпись, challenge, authority/issuer/audience, вид, session, непрерывность seq, границы и непрерывный HWM в памяти клиента. Он не следует HTTP redirects и не использует proxy. Ошибка ключа, подписи, nonce, session, срока, gap, rollback HWM или границ закрывает проверку. Полный одновременный откат authority journal и всех независимых наблюдателей к одной старой копии не обнаруживается этими локальными данными: нужен внешний monotonic anchor/проверенная актуальная authority, иначе восстановление должно остаться закрытым.

## Протокол и ограничения

1. Для каждого нового процесса создать `AuthorityClient(AuthorityConfig.from_json(...))`; получить свежий `attach(after)` и H0. Успешный attach выдаёт новую случайную session. Даже неуспешный reattach инвалидирует старую client session. Server restart теряет session, но не durable journal; клиент переподключается и снова проверяет HWM.
2. После attach запросить `barrier(session)` и его свежий B. `page(session, after, through, limit)` выдаёт не более 100 последовательных записей, `observe(session, after)` — свежий HWM. До открытия root-owned coordinator должен атомарно применить полный префикс до B и сопоставить локальный cursor с **последним** проверенным HWM. Если cursor отстаёт хотя бы на одну запись, gate закрыт.
3. В `VerifiedFrame` находятся `request_started_monotonic` и `verified_at_monotonic`; `is_fresh()` требует не более трёх секунд от начала запроса **и** непросроченный signed wall-clock expiry. Время систем должно быть синхронизировано. Околосекундный poll и закрытие при отсутствии свежего кадра дают более строгую границу, чем heartbeat 15 секунд; проверка stale состояния, непрерывного применения, readiness/transaction gate и deletion ACK принадлежат интеграции root/PART B.

В fixture режим нужно войти явно: client config `fixture_mode: true`; HTTP принимается только для loopback или точного внутреннего имени `privacy-authority`, `privacy-authority.knowi-analytics.svc[.cluster.local]`. URL не может содержать credentials, path/query или fragment. Server по умолчанию допускает bind только loopback; `0.0.0.0` разрешён только с явным `--private-fixture-network` и требует изоляции сети снаружи процесса. Публичного Traefik route нет. Body ограничен 8192 байтами, frame — 128 KiB и 100 entries; sequence ограничен положительным диапазоном PostgreSQL bigint. Сервер имеет отдельную ёмкость одного writer и одного reader thread, до семи одновременных reader requests и одного writer request; client использует не более одного socket одновременно. Session на сервере ограничены 128, истекают через 60 секунд без запросов; client хранит только одну session, nonce cache ограничен. Таймаут одной HTTP операции — 3 секунды. Ответы и ошибки не включают credentials, payload или диагностические трассировки; access log отключён.

Fixture server дополнительно ограничивает число принятых сокетов до 16, закрывает соединение с незавершёнными HTTP headers через 3 секунды, отключает WebSocket и закрывает HTTP соединения после ответа. Адаптер протокола использует `H11Protocol` установленного и закреплённого Uvicorn 0.50.0; при обновлении версии требуются повторная проверка исходного API и socket-тест. Зависание файловой системы нельзя надёжно прервать из Python thread: при остановившемся источнике синхронизатор должен закрыть gate по истечении срока свежести, а внешний supervisor отвечает за завершение процесса.

Fixture HTTP не шифрует reader credential и producer JWT. Его допустимо использовать только в изолированной synthetic сети; для реального межсервисного транспорта нужны отдельно спроектированные и проверенные TLS и управление credentials.

## Fixture CLI

Запуск из `services/analytics`; все перечисленные файлы должны находиться внутри его `.local/` и заранее созданные выходные файлы не перезаписываются:

```powershell
python -m pymentor_analytics.adapters.privacy_authority.server keygen --private-key .local/authority.key --public-key .local/authority.pub
python -m pymentor_analytics.adapters.privacy_authority.server reader-secret --output .local/reader.secret
python -m pymentor_analytics.adapters.privacy_authority.server init --journal .local/privacy-authority.sqlite --authority-id synthetic-authority-1
python -m pymentor_analytics.adapters.privacy_authority.server serve --journal .local/privacy-authority.sqlite --authority-id synthetic-authority-1 --config .local/authority-server.json
```

`authority-server.json` содержит только fixture настройки: `fixture_mode`, `bind_host`, `port`, `issuer`, `kid`, `signing_key_file`, `producer_issuer`, `producer_public_keys` (map kid→PEM), `allowed_producers`, `producer_command_public_keys` (map producer ID→PEM), `reader_secret_file`. Частные ключи и reader secret передаются путями к отдельным игнорируемым файлам. Для отправки существующего synthetic `DeletionFence` используется `append --client-config .local/authority-client.json --control-file .local/control.json --producer <id> --producer-token-file .local/producer.token --command-key .local/command.key`. Результат команды — только `accepted` или `duplicate`, без token, subject или payload. На Windows режим `0600` сам по себе не устанавливает изолированный ACL: владелец fixture обязан ограничить доступ к каталогу и файлам.

Client config имеет поля `{url, authority_id, issuer, public_keys, reader_secret, fixture_mode}`; `public_keys` — map kid→response public PEM. JSON содержит credential и потому является секретом. Для runtime все роли должны получать идентичную доверенную конфигурацию из единого Secret; совпадение источников и key separation с существующими grants проверяет deployment/integration gate. Используйте отдельные client instances для управляющей записи и фонового чтения, чтобы контрольный вызов не занимал единственный reader socket синхронизатора.

Фактические проверки выполнялись только на локальных disposable synthetic файлах и HTTP fixture процессе; подробнее — `tests/privacy_authority`. Они не доказывают PostgreSQL deletion/fence, restore barrier, сетевые политики K3s, физическую независимость отказов, гарантии power-loss оборудования или готовность к реальным данным.
