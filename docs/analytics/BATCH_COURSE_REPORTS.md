## Pending deletion в legacy AdminStudentProfile

Источник: Core `administration/api/router.py` возвращает default-off 200 `{deleted:id}`, transfer-enabled 202 `{status:"pending"}`, затем повтор для того же `X-Account-Ref` — 202 или 204 после delivered Analytics deletion. Общий `shared/api/client.ts` не передаёт код ответа и требует JSON для 204; он не менялся.

В `students/AdminStudentProfile.tsx` и локальных `students/deleteStudentRequest.ts`, `students/DeletionStatus.tsx` реализованы: 200 с корректным id / 204 — завершение и callback; 202 — отдельное ожидание без показа старого профиля; неизвестный исход/error — не успех, профиль не возвращается. Одна явная ручная проверка на нажатие повторяет DELETE только с исходным opaque accountRef; без него повтор блокирован. Автоповторов нет, каждый запрос ограничен 12 секундами; после подтверждённого pending ошибка последующей проверки не стирает известный факт Core deletion. Старые незавершённые GET профиля не могут восстановить его после начала удаления. При наблюдаемой смене actor/target и unmount запрос abort и поздние результаты подавляются; профиль имеет независимую подписку на существующий `useAuthSession`, ключ содержит actor id/account_ref/auth_revision и target id. Pending/reference хранятся только в памяти активной карточки; при выходе/смене пользователя/страницы возможность проверить из неё теряется. Abort не откатывает уже принятую сервером операцию; без server-side actor binding смена cookie до наблюдения frontend остаётся отдельной границей, сервер выполняет авторизацию.

Общий `features/admin/api.ts` и `shared/api/client.ts` оставлены без изменений: старый экспорт `deleteStudent` по-прежнему не различает 202/204, production UI данной карточки переведён на локальный `deleteStudentWithStatus`. Platform owner/root: если добавляете удаление в `PlatformAdmin`, используйте/вынесите этот status-aware helper с теми же lifecycle/abort гарантиями; не используйте старый `deleteStudent` или общий `apiRequest` для нового контракта. По источнику `AdminStudentProfile` сейчас вызывается только через legacy `AdminScreen`, а новый `PlatformAdmin` не показывает действие удаления; требуется решение владельца, если оно должно быть доступно в современной platform-панели.
