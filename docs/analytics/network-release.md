# Analytics: подготовка сети и release (CORP-64)

Статус: **локальная подготовка и synthetic route smoke; в кластере не развёрнуто и не проверено**. Первый этап только синтетический. Каркас предоставляет `/live` и `/ready`, но не обработчики событий/отчётов, проверку grants или реальный processor. При корректной конфигурации `/ready` пока возвращает 503; при отсутствующем или неправильном DB URL процесс не стартует. Миграция реализована отдельно в CORP-63. Маршрут не означает рабочую функцию или готовность к реальным данным.

## Граница и маршруты

Chart [analytics](../../infra/helm/analytics) готовит независимые Deployment collector, processor, query, и по явному `migration.enabled=true` отдельный Job. Все используют один настраиваемый образ, без Core DB, Redis, импортов Core или монтирования курсов; Helm values пока ссылается на `knowi-analytics:an1-local`, а локальный Compose по умолчанию — на `knowi-analytics:corp63-synthetic`. Внешний PostgreSQL и ограниченные роли принадлежат Analytics; lifecycle ролей и миграции относится CORP-63. Job не выполняется при старте HTTP-реплик, по умолчанию отключён и не повторяется автоматически (`backoffLimit: 0`); при изменении Job нужен новый управляемый запуск и проверка состояния БД.

IngressRoute по умолчанию отключён. При включении отправляет только точный `/api/analytics/events/batch` в collector, `/api/analytics/reports` и его поддерево с `/` в query; например, `/api/analytics/reports-other` не совпадает. Приоритет 110 выше 100 у Core Helm и 20 у preview Core; точные правила Analytics не совпадают с путями learning. Это сравнение исходников, а не результат совместного теста конкретного Traefik; совместимость с маршрутами Mentor также нужно проверить на целевой конфигурации. Другие пути могут попасть в существующий Core catch-all: такой fallback надо проверить на целевом ingress, он не направляет запрос в Analytics. Processor, БД, probes и control не публикуются этим IngressRoute. Проверка безопасности зависит также от других ingress и сетевых политик кластера.

Политика по умолчанию запрещает вход и выход выбранных pod Analytics. Разрешены только DNS к выбранным pod и TCP к указанному `network.databaseCIDR:databasePort`; пока CIDR пуст, доступ к БД запрещён. Collector и query принимают TCP 8000 только от выбранных pod ingress в выбранном namespace. Нет отдельного control allowance в синтетическом этапе: control endpoint и доверенный отправитель ещё не реализованы. Селекторы DNS и Traefik, фактический CIDR, CNI и возможные другие объединяемые NetworkPolicy необходимо проверить в целевом кластере; NetworkPolicy не является HTTP authorization. Для будущего server-control нужны отдельные transport и credentials, не browser/report grant.

Секреты уже должны существовать в namespace: `analytics-collector-db`, `analytics-processor-db`, `analytics-query-db`, `analytics-migrate-db`, каждый с ключом `DATABASE_URL` и отдельным ограниченным логином к базе Analytics. Имена настраиваются в values; chart не создаёт Secret и не хранит пароль. Значения ConfigMap задают отдельные размеры pool каждого процесса; подключение создаётся по требованию адаптера. Все ServiceAccount и pod отключают automount токена. Изначально по одной реплике; `roles.<role>.replicas=2` меняет только выбранную роль. При стандартных pool 2/overflow 0 бюджет трёх реплик — 6 соединений, с одной увеличенной ролью — 8, плюс 1 на migrator и отдельные резервы администратора/backup; это плановые верхние границы конфигурации, не измерение нагрузки. Requests/limits — стартовые значения, не измеренный NFR; перед увеличением проверить ёмкость и ограничения базы.

Нет CORS middleware, wildcard allow-headers и доверия прокси для приложения: `FORWARDED_ALLOW_IPS` пуст. Приложение не использует присланный клиентом `X-Forwarded-For` как достоверный адрес. При будущей потребности в CORS задавать только утверждённые origins, методы и headers; доверие к ingress требует отдельно проверенного фиксированного диапазона и проверки подделки заголовка. Реальная проверка grant и CORS ещё не реализована.

## Локальный synthetic стенд

Отдельный [compose.postgres.yaml](../../infra/analytics-local/compose.postgres.yaml) принадлежит PostgreSQL-профилю и создаёт сеть `knowi-analytics-01a1df75-net`; [compose.yaml](../../infra/analytics-local/compose.yaml) присоединяется к ней как external и не создаёт свою БД. Внутри сети PostgreSQL — `analytics-postgres:5432`, на хосте только `127.0.0.1:57392`; единственный порт приложения — `127.0.0.1:57400` через Traefik file provider, без Docker socket. Это локальная общая сеть, не эквивалент Kubernetes NetworkPolicy. Все роли получают URL раздельно через `ANALYTICS_COLLECTOR_DATABASE_URL`, `ANALYTICS_PROCESSOR_DATABASE_URL`, `ANALYTICS_QUERY_DATABASE_URL`, а для отдельного миграционного профиля — `ANALYTICS_MIGRATE_DATABASE_URL`. Передавать только ограниченные role credentials, не bootstrap-пароль; provisioning ролей относится CORP-63. Файл маршрутов не содержит секретов. Для запуска сначала убедиться в synthetic DB/network и подготовленных credentials, затем оператор отдельно запускает необходимые профили; на этой стадии они не доказательство готовности.

Структурная проверка без подключения к Docker daemon и без вывода секретов:

```powershell
python -m unittest discover -s services/analytics/tests/deployment -v
```

Для проверки Helm 3.19.0 в подготовленной среде: `helm lint infra/helm/analytics --namespace knowi-analytics` и `helm template analytics infra/helm/analytics --namespace knowi-analytics`; отдельно повторить с `--set roles.collector.replicas=2 --set migration.enabled=true` и с конкретным ограниченным DB CIDR. Это только render; он не доказывает работу CRD/CNI и сетевые запреты.

16.11.2026 локальный `python -B services/analytics/tools/check_routes.py` проверил Docker 29.9.2, `knowi-analytics:corp63-synthetic` и Traefik 3.7.15 в одноразовом проекте с отдельной внутренней сетью приложений и отдельной сетью ingress. Запросы через `127.0.0.1:57400` дошли до нужных collector/query и вернули FastAPI 404, поскольку handlers ещё нет; близкие по написанию и внутренние пути вернули Traefik 404. Вспомогательные synthetic Core/Mentor echo-сервисы подтвердили приоритет маршрутов, но не работу реальных Core/Mentor. У приложений не было host port bindings, лимит каждого контейнера не превышал 128 MiB, readiness каждой роли вернула 503. OPTIONS не вернул wildcard CORS; отдельная проверка middleware внутри образа с искусственным ASGI scope не приняла поддельный X-Forwarded-For. Тестовые контейнеры и обе сети удалены. Этот smoke не подключался к PostgreSQL и не проверяет реальный отказ доступной БД; K3s/CNI, совместный ingress, масштабирование и rollback остаются непроверенными.

## Граница GitOps и CI

[Application](../../infra/gitops/analytics/application.yaml) — пример без autosync, не зарегистрирован и не является разрешением на deployment. Существующий AppProject `preview` не допускает namespace `knowi-analytics` и ServiceAccount; до использования нужен отдельно согласованный bootstrap: namespace, проект или точечно расширенный destination и whitelist необходимых типов (`Deployment`, `Job`, `Service`, `ConfigMap`, `ServiceAccount`, `NetworkPolicy`, `IngressRoute`), права controller и безопасное внешнее provisioning Secrets. Namespace/Secrets не создаются данным chart; TLS Secret при включении TLS также должен заранее существовать в целевом namespace. Проверить установленный Traefik/CRD, его наблюдение этого namespace, сертификат и ingress labels. Не изменяйте существующий Core chart или bootstrap в рамках этого release.

Release CI вызывает Analytics CI, собирает и сканирует образ `ghcr.io/unikoff/knowi-platform-analytics`. Digest проверенного образа записывается в `infra/gitops/preview/release.json` рядом с `source_sha`. Для развёртывания отдельного Application укажите этот репозиторий и digest в `image.repository` и `image.digest`. Публикация метаданных сама по себе Application не включает.

Для кандидата a014 отдельный Job получает `migration.revision: a014`. Проекции включаются явно в порядке `activityProjection`, `activityDay`, `activityCourse`, `activityBoundaryCredit`. Для первой ступени нужен UUID набора данных и заданный trust и privacy authority, для дневной также нужна Privacy. Тесты Helm проверяют разрешённые ревизии, зависимости и digest Job и рабочих ролей. Перед rollout остаются проверки bootstrap, readiness, ресурсов, ingress/CNI и возврата на тестовом адресе.
