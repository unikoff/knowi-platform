# Локальная публикация каталога Analytics

Это код и тестовый протокол до инфраструктурной приёмки, не описание включённой production-системы. Миграция `services/analytics/migrations/versions/a008_catalog.py` включена в проверенную source-цепочку; существующие базы автоматически не изменены.

Core формирует разрешённую проекцию из `CourseRuntime.snapshot`: product, tracks, lessons, tasks, revisions, aliases и tombstones. `catalog_version` равен `sha256:` и SHA-256 от UTF-8 JSON объекта `catalog` с отсортированными ключами, без пробелов и с `ensure_ascii=False`. `fingerprint` так же вычисляется для всего сообщения. При изменениях отправляется полный Delta с последовательной версией и ссылкой на подтверждённую базу. История идентификаторов сохраняется; удаление становится tombstone. Содержимое уроков, тесты и пользовательские данные в каталог не входят.

Collector по отдельному default-off флагу принимает `POST /internal/analytics/catalog/v1` с `{ "message": ..., "fingerprint": "..." }`. P1 Bearer проверяет существующий ProducerVerifier; namespace берётся только из серверной привязки producer. `GET /internal/analytics/catalog/v1/receipts/{course_id}/{catalog_version}?fingerprint=...` проверяет факт фиксации именно этого отпечатка. Повтор идентичного сообщения подтверждается, конфликт возвращает HTTP 409. Предельный размер запроса 2 MiB, дополнительно ограничены числа tracks, lessons и tasks. История хранится в общей таблице Analytics, без subject и связи с удалением аккаунта.

Новые конфигурационные поля Collector: `ANALYTICS_COLLECTOR_CATALOG_ENABLED=true`, `ANALYTICS_COLLECTOR_CATALOG_NAMESPACE`, а также существующий серверный `ANALYTICS_COLLECTOR_CORE_TRANSFER_NAMESPACES_JSON` с привязкой разрешённого P1 producer к namespace. Тестовый fixture каталог одновременно с новым включать нельзя. Ключ P1 отделён от G1 существующим конфигуратором авторизации. Флаг по умолчанию выключен; внедрение требует также включённого доверенного privacy barrier и схемы a008.

Публикация запускается явно через `services/core-api/tools/analytics_catalog/publish.py --courses-root <fixture-root>/courses --course-id backend`. Вместо фильтра по ID она требует UUID4 fixture внутри `services/analytics/.local/cross-service`, актуальные `owner.json` и `fixture.json`, совпадающий приватный `CROSS_SERVICE_OWNER_TOKEN`, именно fixture registry и проверку текущих владельцев и sentinel обеих disposable DB до сетевого запроса. Адрес Collector обязан совпасть с адресом fixture. Запускать только из сценария, который дополнительно проверяет принадлежность локальных listeners своему job: сопоставление DB и файла само по себе не доказывает, что процесс на порту использует проверенную DB.

Publisher использует `PYMENTOR_ANALYTICS_CATALOG_FIXTURE_DIR=<fixture-root>`, существующие настройки P1 `PYMENTOR_ANALYTICS_PRODUCER_ISSUER`, `PYMENTOR_ANALYTICS_PRODUCER_KID`, `PYMENTOR_ANALYTICS_PRODUCER_KEY_FILE`, `PYMENTOR_ANALYTICS_PRODUCER_ID` и `PYMENTOR_ANALYTICS_CATALOG_URL`. Значения ключей и owner token не передаются в аргументах или выводе. Core процесса fixture нужен тот же `PYMENTOR_ANALYTICS_CATALOG_FIXTURE_DIR`: квитанции размещаются в `<fixture-root>/analytics-catalog` и не затрагивают общий Core `.local`. Перед отправкой кандидат сохраняется как pending; при неизвестном результате следующий запуск сначала сверяет сохранённый fingerprint через GET. После подтверждения записывается receipt с digest исходного CourseSnapshot. Локальная блокировка исключает параллельных publishers одного продукта; таблица сериализует их по namespace и продукту.

Core под отдельным флагом `PYMENTOR_ANALYTICS_CATALOG_METADATA_ENABLED=1` предоставляет `GET /api/learning/analytics-catalog?course_id=...`. Существующая проверка C427 разрешает только learner и доступный продукт; ответ `{course_id, catalog_version, lesson_ids}` содержит только доступные этому learner уроки. Нет корректного receipt или digest текущих файлов отличается — возвращаются `catalog_version: null` и пустой список. Ответы не кэшируются. Запись receipt сама по себе не является разрешением на переключение или перенос ранее сохранённых данных.

Проверены синтетические Python/ASGI сценарии, включая потерянный ответ и повторную сверку, а также моделирование интерфейса SQL adapter. PostgreSQL DDL, реальные блокировки между процессами, права ролей и сквозной запуск с настроенными P1 ключами требуют отдельной проверки в изолированном разрешённом окружении после инфраструктурного gate. Откат кода не должен удалять историю каталога; после отключения flags данные остаются, browser admission закрывается до повторного корректного подключения.
