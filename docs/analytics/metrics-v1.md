# CORP-59: формулы и эталон activity-v1

> Этот файл описывает действующий `activity-v1`. Целевая семантика от 17.11.2026 зафиксирована в [обзоре сервиса](service-overview.md#активный-день-и-перенос-истории). Следующая версия определяет активность по положительному измеренному времени и выдаёт перенесённую историю отдельным слоем. Прежний расчёт посетителей по `course_opened` остаётся контрактом `activity-v1` на период совместимости.

Статус: **synthetic однопоточный reference oracle**, не Tracker, Collector, Processor, Query API или рабочий продуктовый расчёт. Источники решений — [план Analytics](../architecture/ANALYTICS_SERVICE_PLAN_20261115.md), [архитектура](architecture.md), [контракт CORP-58](contracts.md) и проверяемый `pymentor_analytics/contracts/v2.py`. Никаких данных пользователей, БД, миграций, Core write, deployment или автоматического TTL подробных посещений и времени здесь нет. Удаление lifecycle обязательно; runtime fence и restore barrier здесь не реализованы.

## Вход и границы

Вход reference — список валидных `AcceptedEvent` v2, уже связанных с opaque lifecycle `subject_ref`, доверенным producer namespace и курсом после авторизации пользователя роли `user`. Это предпосылка, а не проверка подписи, роли, разрешений, каталога, хранения или факта durable commit. Тестовые входы синтетические. Код повторно валидирует DTO, включая сегмент не более **60 секунд**, точную длительность и ограничения `last_action_at`. Browser поля focus/visible являются утверждением, не доказательством. `course_opened` с длительностью 0 — самостоятельное наблюдение посещения. Отрезки полузакрытые `[start, end)`; период отчёта тоже `[from, to)`.

Engineering defaults для этого эталона: heartbeat **15 секунд**, idle **300 секунд**, допуск будущего времени события относительно `received_at` **120 секунд**, опоздание **7 суток** относительно `ended_at`, browser buffer **24 часа**. Контракт CORP-58 называет последние значения кандидатами: их выбор здесь не меняет и не исполняет тот контракт; реальные enforcement, clock policy и буфер ещё потребуют реализации и проверки. Предел 60 секунд уже зафиксирован v2. Факты с `ended_at > received_at + 120 с` или `received_at > ended_at + 7 суток` отклоняются эталоном; равенство границе допустимо. Время получения после `as_of` в снимок не входит. Допустимый clock skew не добавляет время после `as_of`. Восемь минут без действий: первые 300 секунд только при наличии подтверждённых сегментов, затем тишина; действие на 480-й секунде начинает новый сегмент с этого момента. Hide, blur, sleep и смена пользователя закрывают сегмент; после возврата нет заполнения пропуска. Oracle потребляет подтверждения и сам не доказывает, что браузер правильно следил за этими состояниями.

Перед расчётом по `(producer_namespace, event_id)` первый по `received_at` допустимый факт закрепляет identity. Одинаковый canonical hash v2 — duplicate, другой — conflict без второго вклада; при одинаковом `received_at` в синтетическом наборе первым выбирается лексически меньший hash. Это детерминированная модель, не модель атомарного порядка commit при гонках. Невалидные по времени факты identity не резервируют. Предоставленный набор удалённых lifecycle исключается целиком до дедупликации и подсчётов; новый lifecycle — отдельный subject. В реальной системе нужны durable tombstone/epoch и синхронизация приёма, обработки и чтения.

## Формулы и attribution

1. Для каждого subject объединить подтверждённые интервалы **всех** курсов, устройств и сессий, включая факты за границами выбранного курса. В каждой точке активен не более одного контекста. Выбрать активный принятый сегмент с наиболее поздним `started_at`; при равенстве — лексически больший канонический UUID события, при коллизии UUID разных namespace — лексически больший namespace. Это делает выбор однозначным и независимым от порядка входного списка.
2. В v2 нет отдельного поля начала контекста; эталон не восстанавливает его догадками. Очередной heartbeat другого устройства может изменить атрибуцию. Это детерминированное правило наблюдаемых сегментов, а не доказательство реального focus между устройствами. Дополнительные поля и их необходимость — отдельное будущее решение.
3. После глобального выбора ограничить период и курс/subject. Фильтр курса не отдаёт ему секунды, уже приписанные другому курсу. Идентичность урока включает `course_id`: одинаковый `lesson_id` в `backend` и `backend_copy` не объединяет их.
4. `theory_ms` и `practice_ms` — суммы выбранных длительностей. `total_ms = theory_ms + practice_ms`. Работа с кодом относится к practice; личные встречи в учебное время не входят. Платформенное время — сумма по непересекающимся интервалам каждого subject, не сумма независимо вычисленных конкурирующих вкладок. Это позволяет суммировать разные subject, но ограничивает вклад одного subject длиной периода.
5. Посетители — количество **различных subject** с принятым `course_opened` в периоде или пересекающим период `activity_segment`, после фильтра subject/course. Один subject двух курсов — один платформенный посетитель. Посещение существует даже при нулевом времени и даже если его сегмент проиграл глобальному attribution; denominator — именно distinct subjects, не события, сессии или устройства. Нет фактов — 0 в reference; отдельная интеграция определит no-data против измеренного zero по доступности и coverage.
6. Прогресс — только доверенные Core progress facts, отдельно от таймера; продолжительность не означает завершение. Legacy Core global activity days не содержат оснований восстанавливать минуты или принадлежность курсу и не подменяются этими данными.

Тimestamps сравниваются в UTC целочисленной арифметикой, без float. Поскольку v2 допускает микросекундную фазу начала при целой длительности ms, v1 округляет каждую границу события **вниз** до UTC миллисекунды до расчёта пересечений; длительность такого сегмента сохраняется. Границы запроса и `as_of` обязаны быть выровнены по миллисекунде. Например `[00:00:00.000999, 00:00:01.001999)` становится `[00:00:00.000, 00:00:01.001)`; в окне `[.001, 1.000)` вклад 999 ms. При выборе сегмента сравниваются исходные микросекунды начала. Пересмотр этой квантизации требует новой версии метрики.

Дневной срез v1 использует фиксированный UTC+03:00, как Core `activity_policy.MOSCOW_TZ`, обозначение `Europe/Moscow`; календарная полночь разделяет интервал, а не переносит его целиком. Это сохраняет и историческую fixed-offset семантику Core, а не исторические изменения московской зоны IANA. Для исследования других зон reference принимает IANA `timezone_name`, разбивает по локальным полуночам и маркирует ответ `activity-v1-tz-experimental`: это не принятая новая продуктовая версия. Для них необходимы zoneinfo базы ОС или `tzdata`; отдельная версия и правила DST/изменений базы потребуются до продукта. В редких зонах с пропущенной/неоднозначной полуночью общий runtime-контракт отдельно не доказан. `UTC` не требует IANA базы.

## Снимок и качество

`as_of` — верхняя граница времени получения фактов и наблюдаемого времени; это не freshness SLA и не processing watermark реального конвейера. Эталон выдаёт `complete` только если вызывающий явно утверждает полноту входа (`input_complete=True`), `as_of >= to + 60 секунд + 7 суток` и в снимке нет конфликтных, слишком поздних или нарушающих future-skew фактов. Дополнительные 60 секунд учитывают сегмент, начавшийся до `to`, но закончившийся после него; lateness измеряется от конца сегмента. Иначе `partial`; это консервативная классификация всего входного снимка, включая ошибки вне фильтра. Даже `complete` означает полноту только при истинной предпосылке вызывающего, а не доказательство доставки. Runtime должен отдельно определить watermark, источники coverage, reconciliation, доступность и отображение `ok/no_data/stale/unavailable` согласно CORP-58; этот объект не является `ReportResponse` и не обещает lag/SLO. Результат может измениться при допустимом позднем событии до закрытия окна. Отклонённый за пределом семи суток факт не пересчитывается автоматически; требуется отдельная контролируемая процедура reconciliation, ещё не реализованная.

## Golden cases и проверка

`services/analytics/contracts/fixtures/activity-golden-v1.json` содержит **синтетические планы наблюдений, не wire fixtures**. Тест разворачивает длинные планы в сегменты не более 15 секунд, валидируемые v2. Для длительного чтения/работы предусмотрены дополнительные synthetic actions: один action не подтверждает активность за пределом idle 300 секунд. Ожидаемые значения заданы независимо в секундах/миллисекундах:

| Сценарий | Ожидаемый результат |
| --- | --- |
| 8 минут idle, действие и ещё 15 с | до действия 300 с, после 315 с, 1 посетитель |
| hide/blur/sleep, возвраты с новыми сегментами | 4 × 15 = 60 с, 1 посетитель; паузы 0 с |
| backend theory 8 мин + practice 12 мин; backend_copy 10 мин | backend 480 + 720 = 1200 с; платформа 1800 с; 1 посетитель |
| 2 устройства и курса параллельно 1 час, одинаковое начало | платформа 3600 с, победивший backend_copy 3600 с, backend 0 с; посетитель backend остаётся 1 |
| позднее начало и следующий heartbeat первого контекста | первый курс 20 с, второй 10 с, всего 30 с |
| duplicate/conflict/reorder | 30 с; 2 accepted, 1 duplicate, 1 conflict; quality partial |
| задержка на границе 7 суток и после неё | 15 с на границе, следующий факт late, quality partial |
| полночь Москвы | 30 с 1 января и 30 с 2 января |
| New York, DST 2026 | по 30 с по обе стороны полуночи 7/8 марта и 8/9 марта; повтор часа осенью — 60 с, не 3660 с |
| только `course_opened` / без фактов / удаление одного из двух | 1 посетитель и 0 с / 0 и 0 / остаётся 1 посетитель и 15 с |
| миллисекундные границы | 999 ms после отсечения; дробная длина сегмента отклонена v2 |

Для Windows Python 3.12 с zoneinfo из установленного Git проверка выполнена так:

```powershell
$env:PYTHONPATH='services/analytics'
$env:PYTHONDONTWRITEBYTECODE='1'
$env:PYTHONTZPATH='C:\Program Files\Git\mingw64\share\zoneinfo'
services/analytics/.venv/Scripts/python.exe -B -m pytest -p no:cacheprovider services/analytics/tests/reference -q
```

Это не проверка concurrency, реального браузера, clock synchronization, транспорта, долговременного хранения, защиты удаления, прогресса, отчётного ACL или производительности. Результат такой будущей проверки здесь не заявляется.
