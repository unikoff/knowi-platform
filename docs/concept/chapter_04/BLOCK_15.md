### Какие границы объединены

- **71 + 71.1.** Один учебный прогон по одной записи: POST выдаёт id. Ученик читает именно его свежей Session, затем применяет PUT и сверяет полную строку с исходным снимком. Следующая учебная операция переносится на PATCH в 72. Исторический доступ к 71.1 описан ниже.
- **72.1 + 72.2.** Закрытие и удаление отвечают на вопрос, что осталось доступно после команды над одной задачей. Общую область и поиск по id объясняем один раз. Состояние после done, его повтор и исчезновение строки имеют разные контрольные точки внутри одной практики.
- **73 + 73.1.** Отбор по статусу и буквальному фрагменту объясняются в одном ходе SQL-выборки. Для поиска отдельно видны подготовка ввода и результат сравнения двух строк. 73.2 остаётся отдельным, поскольку агрегат меняет форму результата на одну строку счётчиков и требует объяснения CASE/NULL.
- **75 + 75.1.** Подготовка снимка, переключение и вывод старого runtime образуют один переход. После подтверждения переключения отдельные задачи проверяют штатный запуск без архива и отказ без fallback при доступном архиве. 74 остаётся про границу ресурса команды. 74.1 отдельно учит на пробных данных доказывать равенство и готовность, пока обычные писатели всё ещё используют JSON.

## 3. Паспорта занятий

### 71. Создаём и заменяем задачу в SQLite

**1. Назначение.** Добавить SQL-запись в собственный Planner после 70.2. На одной задаче выяснить, когда появляется её id, какие поля меняет PUT и что сможет прочитать другая Session после подтверждения.

**2. Точка A.** В срезе StudyHub `a36ac3885ad7cd18f5afb1f3190ae2e35081331b` в `project/app/DBase/repositories.py` уже есть SQL `list/get`, а SQL `create/replace` отсутствуют. В `project/app/service.py` действуют делегирование создания, сборка полной Task для PUT и выбор полей для PATCH. Используем их как опору. Общая файловая сборка API и CLI работает через JSON. До изменений контрольный SQL get на отдельной учебной базе подтверждает, что схема, явный импорт и фабрика Session применимы. При расхождении сверяем сначала адрес файла, потом схему и подключение провайдера. Освоение этих операций конкретным учеником проверяется по его старту.

**3. Точка B.** Ученик добавляет область записи в существующий сервис и связывает её с той же Session, что использует SQL-репозиторий. Сам пишет `create` и адресный `replace`. После POST открывает свежую Session на том же файле, читает по выданному SQLite id и для PUT использует этот же id. По снимкам объясняет, какие поля цели изменились, какие сохранились и почему соседняя запись осталась прежней.

**4. Подготовка до практики.**

- **00 / LinkedNotes.** **Точка старта** — SQL уже находит задачу по id. **Новый вопрос** — как создать запись и затем заменить именно её? **Результат** — один выданный id связывает создание, чтение и новую версию из PUT.
- **Объяснение.** Короткий связный рассказ на странице. На примере объяснить область записи, выход из `with` до возврата результата и общую Session для репозитория и транзакции. Затем объяснить появление ключа при INSERT, показать короткий фрагмент с `add/flush` и сравнить состояние объекта до и после. Связать commit с чтением новой Session. Через два снимка пояснить, откуда приходят новые поля PUT, почему сохраняются id и метки и зачем пересчитать поисковую копию. Команды подготовки базы и проверки дать в соответствующих карточках.
- **Независимый пример и проба.** В реестре оборудования запись о выдаче получает номер при вставке, а после подтверждения её видит новый читатель. Короткий код показывает один механизм за раз, с пояснением вывода рядом. Затем на одной сохранённой записи сопоставить изменяемый срок выдачи и прежнее примечание. Модель примера проще Planner и оставляет ученику выбор состава полей и адреса изменения в его проекте. Для первой попытки прогноза дать другой вход: два считывания по одному номеру при изменении уже сохранённой записи, одно до подтверждения и одно после. Сначала показать исходные состояния и управление, затем раскрыть результат и его причину.
- **Визуал вне 00.** Связать появление ключа с временной линией «объект → flush → commit → новый читатель» и отделить публичный ответ PUT от полного состояния строки.
- **Интерактив вне 00.** Ученик выбирает момент чтения или сбоя и предсказывает, какую версию увидит новый читатель. Использовать данные, ответ по которым выше не показан. Обратная связь объясняет, почему наличие id в пишущей Session ещё ничего не говорит о состоянии новой Session.

Сверены все 8 паспортов. В 71 область записи и общая Session проверяются отдельными действиями до реализации записи. Id из POST используется при самостоятельном чтении и PUT на том же файле. Одинаковое название соседа различает выбор по id и по заголовку. Свежий снимок выявляет устаревшую поисковую копию при верном публичном ответе. Следующая цель по карте — 72. Фактическая навигация и вход 72 проверяются на выдаче. 404 проверяет авторская регрессия. В 72.1 ответ об успехе не доказывает адресность, поэтому проверяются оба id и все поля соседа. В 73.2 неравные open/done отличают перестановку на первой смешанной сводке. В 74 по наблюдениям ученика видно, какая Session открылась и закрылась ли именно она после исключения. В 73 задачи 3–4 различают ошибку преобразования строки и SQL-совпадения. В 74.1 пустая цель предъявляется до импорта. После возврата обе штатные точки видят запись только из обычного JSON и не находят новый SQL-id. Сравнение байтов отдельно подтверждает сохранность двух исходников. В 75 проверка полной копии обнаруживает изменение более ранней строки даже при совпавшей последней записи. Импорт сверяется отдельно. Совпадение импортированного id в двух копиях не даёт допуска к записи: для допуска оба открытых пути должны совпасть с выбранной целью, после чего новое изменение подтверждается отдельно. Успешный запуск без архива и отказ с доступным архивом проверяются на разных копиях. Задачи 1–6 имеют собственный критерий до перехода. После четырёх объединений в каждом соответствующем занятии остаются связанные задачи с отдельными результатами. Все 12 исходных записей имеют сопоставление по runtime ID и source. Учебные переходы условны до работы ученика. Сквозная проверка приведена в [F2 рамки](COURSE.md#5-приёмка-и-продолжение). Смена выдачи и совместимость зачётов новых составных практик требуют отдельной реализации по карте.
