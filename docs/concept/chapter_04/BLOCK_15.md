## 3. Подробные паспорта

### 71. Создаём задачу и получаем её id из SQLite

**1. Основная тема и назначение.** Первое добавление в уже существующий SqlTaskRepository. Полученный id станет адресом задачи для PUT.

**2. Точка A.** B14, собственный проект после исторического импорта 70.2. Срез a36ac3885… даёт TaskRow, единственный SQL-репозиторий с list/get, фабрику Session и знания о flush/commit из 68–68.1. На a36ac3885… PlannerService ещё не принимает write_scope. После разбора области записи готовая заготовка добавляет её к своему PlannerService и build_service, сохраняя штатную JSON-сборку. Тестовая SQL-сборка использует этот же код сервиса и подменяет зависимость только в тесте. Видимость проверяется в самой операции 71.

**3. Точка B.** Сам реализует create, получает созданную Task с назначенным SQLite id и объясняет, когда этот id становится частью сохранённой записи.

**4. Необходимые темы в порядке изучения.**

- **00 / LinkedNotes** — **Точка старта.** В тестовой базе уже читаются задачи по id, штатные API и CLI работают с одним JSON. **Новый вопрос.** Как добавить SQL-строку без выдуманного id и вернуть сохранённую задачу? **Результат.** Созданная задача получает id. Независимый get видит её после успешной операции.
- **Объяснение.** Показать путь сервиса и репозитория: валидация, область записи, создание строки без id, flush, mapping в Task, commit до успешного ответа. Жизненный цикл знаком. Обвязка write_scope подготовлена. Объяснить title_normalized, копию tags, исходное False и различие id в объекте и видимости из нового ресурса. Обещать уникальность среди существующих строк, без гарантии непрерывности номеров/запрета повторного использования.

В контрольном ходе с исключением до commit карточка из прерванной операции не видна.

Формат — проект.** Применить разобранную заготовку области записи к своему PlannerService и build_service, затем самому реализовать create в существующем SQL-репозитории через прежнюю модель и mapping. Готовый вызов SQL-сервиса/POST override выдаёт результат для синтетической задачи. Самому сверить id и строку из независимой Session, включая tags, False и title_normalized. ### 71.1. Заменяем задачу через PUT и сохраняем теги

**1. Основная тема и назначение.** Первая запись по уже существующему id. Учим замене публичных полей с сохранением внутренних.

Готовая заготовка расширяет собственный PlannerService: replace_task входит в область записи перед чтением прежней строки и остаётся в ней до записи. Перед практикой из готовой фикстуры видны ненулевые теги, соседняя запись и существующий SQL-сервис.

**3. Точка B.** Сам реализует SQL replace для PUT и объясняет, почему id/tags переживают замену тела. Новый заголовок согласован со служебным полем.

### 72. Применяем только переданные поля PATCH

**1. Основная тема и назначение.** Перенести частичное обновление на подготовленную SQL-запись, отобрав поля по прежнему контракту.

**2. Точка A.** 71.1 поставляет рабочую замену SQL-строки и проверку сохранённых tags. Семантика PATCH объяснялась в главе 3 и работает на JSON. Готовая заготовка охватывает patch_task своей областью записи с первого чтения, без вызова другого публичного сценария. В текущем объяснении до применения показывается различие пропуска/null/False и запись только при изменении.

**3. Точка B.** Сам подключает частичное обновление к общей SQL-записи, сохраняя правила выбора входных полей и no-op.

**4. Необходимые темы в порядке изучения.**

- **00 / LinkedNotes** — **Точка старта.** Мы умеем сохранить новую версию найденной задачи. Теперь запрос может передать лишь часть тела. **Новый вопрос.** Как распознать переданное False и не записать поля, о которых запрос ничего не сказал? **Результат.** После частичного запроса меняются только нужные поля. Пустой запрос не делает запись.
- **Объяснение.** Восстановить различие пропуска, null и ложного значения одним контрастом. Показать построение итоговой предметной Task после чтения и вызов update поверх общей записи. Ветка без изменений завершается без UPDATE. Rename использует тот же title_normalized и tags сохраняются.
- **Полный независимый пример.** У заявки (12, «Витрина», 4, true, [внутр]). Передаём только статус false и null для приоритета. Читаем 12, отбрасываем null, сохраняем false. Свежий ресурс получает (12, Витрина, 4, false, [внутр]). Для пустого тела журнал подготовленной проверки не видит UPDATE. Неизвестный id по-прежнему 404.
- **Малая проба.** Предсказать итог записи для поля 'status': пропуск, null, false. Сверить три результата на независимых исходных состояниях.
- **Визуал вне 00.** Таблица входов с линиями «сохранилось», «изменилось», «нет записи». Начальный статус true виден явно.
