## 3. Паспорта занятий

### 76. Распознаём недоступное хранилище

**1. Назначение.** Различить известный отказ открытия SQLite и внутреннюю ошибку по коду причины.

**2. Точка A.** План 75 даёт SQL-only сборку и два разных опыта на копиях. Контрольный GET подтверждает исправную временную SQLite. Из B14 знакомы исключение и закрытие Session. Готовые клиенты запускают отдельные случаи с недоступным файлом и исправным файлом без таблицы.

**3. Точка B.** Ученик сам пишет узкий классификатор, подтверждает безопасный HTTP 503 для недоступного файла и безопасный HTTP 500 по внутренней ветке при отсутствующей таблице. Готовые проверки подтверждают прежний CLI-отказ и восстановление.

**4. Подготовка до практики.**

- **00 / LinkedNotes.** **Точка старта** — Штатная сборка отказала без возврата к JSON. **Новый вопрос** — Как по причине SQLite выбрать ответ, который увидит пользователь? **Результат** — Распознано недоступное хранилище, а другая причина проходит по внутренней ветке.
- **Объяснение.** Сначала показать, как из SQLAlchemy DBAPIError прочитать `orig.sqlite_errorcode` с готовым доступом к необязательному атрибуту. Выделить младший байт целого кода через `& 0xFF`, сравнить его с `SQLITE_CANTOPEN`. Показать узкую ветку `StorageError`, сохранение исходного исключения у другой ошибки и готовые границы обработки HTTP/CLI. Прочитать, что видит тестовый HTTP-клиент и что можно посмотреть только во внутреннем выводе; публичный ответ не раскрывает путь, SQL и параметры.
- **Независимый пример и проба.** На учебном реестре оболочка DBAPIError несёт `orig.sqlite_errorcode = 782` (`0x30E`). `782 & 0xFF` даёт 14, это основной код CANTOPEN, поэтому готовая граница возвращает 503. У искусственного неизвестного кода 127 младший байт остаётся 127, классификатор пропускает исходную ошибку. В пробе ученик прогнозирует ветку при отсутствующем атрибуте; затем на независимом исправном SQLite-файле без таблицы отличает внутреннее сообщение от HTTP 500.
- **Визуал вне 00.** Линия orig → числовой код → младший байт → ветка показывает, где заканчивается диагностика и начинается формирование ответа.
- **Интерактив вне 00.** Ученик подставляет расширенный, неизвестный либо отсутствующий код. Обратная связь показывает результат побитового выделения и выбранную ветку.
- **«Что мы будем делать в практике» / LinkedNotes.** «Классифицируем по коду», «Проверим публичный ответ», «Убедимся, что внутренняя ошибка осталась внутренней» готовят три задачи.

**5. Формат — изменение существующего проекта в редакторе.** Готовы поставщик реальных исключений, краткая проба классификатора, подключение к границам и два отдельных HTTP-случая.

1. Сам выделить и сравнить основной код в классификаторе. В пробе базовый и расширенный CANTOPEN идут в одну ветку, неизвестный целый код и отсутствующий код сохраняют исходную ошибку. При расхождении посмотреть значение `orig.sqlite_errorcode` и результат маски.
2. Подключить свою классификацию к готовой HTTP-границе. На недоступном учебном адресе увидеть безопасный HTTP 503 и сверить публичное тело с договором. При другом статусе начать с фактического кода исключения.

Готовые контроли сверяют понятный CLI-отказ, отсутствие возврата к JSON и успешный запрос после восстановления исправного адреса.

### 76.1. Проверяем, что осталось после сбоя записи

**2. Точка A.** План 76 даёт работоспособный тестовый SQL runtime и исключения, 68.1/71 дают flush и commit. Готовые сценарии управляемого сбоя используют известный write_scope и фикстуру с сохранённой строкой.

**3. Точка B.** Ученик сам пишет проверку отката после flush, сохранённого изменения после commit и последующего успеха из независимых ресурсов.

**4. Подготовка до практики.**

- **00 / LinkedNotes.** **Точка старта** — отказ можно классифицировать. **Новый вопрос** — может ли клиент увидеть ошибку, хотя изменение уже сохранилось? **Результат** — из нового чтения видно, что осталось в обеих точках сбоя.

- **«Что мы будем делать в практике» / LinkedNotes.** «Проверим состояние на обеих сторонах commit» и «Выполним новую операцию» показывают измеримые исходы.

### 77. Прослеживаем одну выборку от HTTP до SQL

**1. Назначение.** Выяснить, где выполнен отбор для известного GET, и различить доказательства, которые дают HTTP-ответ, фактический SQL и план SQLite.

**2. Точка A.** План 73 даёт статус, id-порядок и limit. План 76.1 даёт исправную временную сборку. Известный смешанный набор и один GET подготовлены. Готовы два безопасных следа для одинакового ответа, путь захвата реального запроса и план для этого запроса.

1. Сам отобрать файлы при создании чистой копии. До установки сверить в ней код, зависимости, README, тесты и безопасный образец настроек, исключить рабочие .env, .venv, базы, архивы и журналы. При лишнем или пропущенном файле исправить комплект до запуска.
2. По своему README подготовить отдельную среду и явно увести запуск на пустой тестовый адрес. Сразу проверить фактический Python, наличие зависимостей и путь SQL. При расхождении вернуться к соответствующей строке инструкции.
3. Готовой проверкой подтвердить, что на выбранном пустом адресе таблицы ещё нет. Выполнить явный init по своему README и той же проверкой подтвердить ожидаемую исходную схему `tasks` со всеми шестью полями и нулём строк. Результат задачи — доказанная схема на выбранном адресе до запуска API и CLI. При несовпадении сверить адрес и команду init. Если причина в инструкции, самостоятельно исправить этот шаг README и повторить проверку на чистой цели.
4. Запустить API и CLI по своему README. Готовой оснасткой из 75 получить отдельно для API и CLI фактически открытый нормализованный путь SQLite и сопоставить оба пути с целью из задачи 3. По обеим точкам прочитать пустой список. Критерий запуска — совпали оба пути и получено `[]` с обеих точек. При несовпадении пути сначала сверить команду и адрес конкретного интерфейса. Если пути верны, а список не пуст или чтение не удалось, проверить чтение на подтверждённой цели. Подтверждённый пробел в README исправить и повторить проверку запуска.
5. Провести один опыт: записать задачу и зафиксировать её id и поля, повторить init на том же адресе, перечитать этот id и сопоставить поля с исходными. При расхождении прежде всего сверить адрес повторного init и читателя.

Готовый контроль запускает общую регрессию рабочего проекта и проверку обычных точек входа.

**6. Приёмка и переход.** Есть комплект, сверенный до запуска, подтверждённая до запуска исходная схема, совпадение фактически открытых путей API и CLI с выбранной целью, пустая выдача через обе точки и сравнение одной записи до и после повторного init. 81 использует тот же способ запуска для самостоятельной временной SQLite с исходной схемой.

**7. Глубина теории.** Показать одну связь от содержимого копии к результату запуска и затем один опыт с повторным init. Ученику остаются выбор комплекта, проверка инструкции и сравнение собственного результата.
