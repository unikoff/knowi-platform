# Stage 5: последовательная сборка и ревью

## Роль и инструменты

По [общим правилам](../AGENTS.md) один чат проходит весь назначенный диапазон внутри главы: сначала теория, затем практика, развитие одного проекта, знания, ревью и коммит занятия. Цель — воспроизводимая сборка от входа A до выхода B и конкретные проблемы содержания курса. Модель задаётся запуском; отдельные исполнитель, аналитик, очередь и сервер Stage 5 не нужны. Закончив занятие, продолжай следующее без команды «дальше». Остановись после диапазона, явной остановки или реального препятствия, исключающего дальнейшую доступную работу; не закрывай ход просто отчётом об очередном успешном уроке.

- **Встроенный @Браузер:** только `http://127.0.0.1:5173/`. Читай теорию, выполняй обязательные интерактивы и задания, отмечай фактически выполненное. Для входа используй ранее разрешённые реквизиты из [методички входа](../3%20stage/STAGE_FLOW.md), не записывая их в отчёты и Git. Firefox и production не используй.
- **Файлы и терминал:** изменяй проект и проверяй результат. При недоступности браузера допустим локальный ученический текст; выдача и отметки платформы тогда не проверены. Скрытые тесты, эталоны и будущий код не являются учебными источниками.
- **Git:** точные состояния A/B, поурочные коммиты и обычный push своей ветки. Историю не переписывай.

Если платформа не запущена, подними frontend на `127.0.0.1:5173`, backend на `127.0.0.1:8001` с `backend/test.db` и `PYMENTOR_LOCAL_NOTIFICATIONS=0`; `.env` не меняй. Версию Python для ученического проекта проверь по `sys.version`/`sys.executable` реально запущенного файла один раз и после смены интерпретатора. Версия служебного runtime платформы не определяет версию Python ученика.

## Перед началом и после прерывания

Учебный репозиторий — `unikoff/studyhub-learning`, checkout — `C:\Project Python\studyhub-learning`, код и README приложения — `project/`. Один раз прочитай инструкции репозитория, `CHAPTERS.md`, короткую сводку `knowledge.md` и относящиеся к текущему шагу записи `review.md`. Проверь origin, назначенную `chapter/NN/vN`, HEAD, чужие рабочие/index-изменения и исключение review.md из Git. Порядок и стабильные ID бери из каталога курса; номера подзанятий — строки. Отдельный план-очередь не создавай.

После прерывания сверь назначение, последний поурочный коммит и незавершённый diff со сводкой знаний. Продолжай первый незавершённый шаг; уже созданный коммит не создавай повторно. Если сводка требует «сделать commit/push», а Git показывает их выполнение, устарела сводка. Отметка платформы тоже не заменяет проверку нового прохода; прежний прогресс аккаунта не сбрасывай. Изменившийся HEAD или чужая правка требуют адресной сверки, а не повторного прохождения всей главы.

## Каждое занятие: пять шагов

1. **Теория.** Прочитай доступный материал до практики. Запиши смысл новых инструментов и источник в знания. Перед каждой задачей проверь, где объяснено необходимое: в этой теории или прошлых знаниях. Для очевидного повтора не нужна отдельная таблица. Пробел запиши, восполни только необходимое и обозначь помощь; не подменяй её самостоятельным знанием или объяснением курса.
2. **Практика.** Выполняй обязательные задания и интерактивы в их учебном порядке, включая явно заданный маршрут карточек. Сначала своя попытка, затем при необходимости подсказка/разбор с отметкой помощи. Сверяй наблюдаемое с условием, а не только с зелёной отметкой. При необъяснимом отказе сохрани попытку по правилу ниже и продолжай независимое.
3. **Проект.** Развивай существующие файлы по практике, заменяя прежнюю реализацию. Не создавай папки уроков, архив одноразовых решений, копии функций и неизученные assert в main.py. Разовые проверки выполняй отдельно; временные файлы не включай в commit, если они не результат задания. Урок без проектного изменения сохраняет знания, а не выдуманный diff кода. Модули появляются по потребности практики.
4. **Ревью.** По ходу фиксируй конкретные трудности: связь теории с задачей, недостающие объяснения, точность условия, язык, примеры и перегрузку. Отличай самостоятельное применение от угадывания и помощи. В конце достаточно короткой сверки со сделанными заметками. Материалы курса, checker и прогресс через служебные обходы не исправляй: Stage 5 собирает и анализирует; доработка курса — отдельное поручение.
5. **Фиксация.** Обнови знания и локальное ревью, проверь относящийся к занятию diff. Подготовь только свои файлы, просмотри `git diff --cached`, используй `git commit -m` без списка путей: pathspec может захватить незастейдженные правки этих файлов. Сообщение: `study(ch01/v1): lesson 14`, с фактическими главой, версией, номером; неполный результат обозначь `partial`. Проверь SHA и состав коммита. Не включай чужой index, review.md и изменения правил процесса; не сбрасывай их. Не создавай пустых/повторных коммитов. Отметь фактически выполненное на платформе при доступности и продолжай диапазон.

## Проверки без лишней работы

Проверяй изменённое поведение и обязательные критерии задания; один запуск может подтвердить несколько критериев. Используй его результат дальше в занятии. Полный сценарий повторяй на предусмотренной контрольной точке или после влияющего изменения, а не после каждого подшага. Не запускай сборку платформы, аудит неизменённых функций и общий набор проверок без причины. Не добавляй собственные требования к форме реализации и хрупкие счётчики строк вывода. AST, monkeypatch и новый тестовый стенд не нужны, если требование можно проверить обычным запуском и просмотром кода. Ошибку своей проверки сначала отличи от ошибки проекта.

В браузере сохраняй вкладку и состояние занятия. После группы действий получай требуемое инструментом свежее состояние; используй изменения дерева и нужный участок. Полное дерево нужно при потере контекста или поиске отсутствующего элемента; не запрашивай его после каждого клика и не выводи огромный материал целиком повторно. Группируй детерминированные действия там, где это допускает инструмент; свежие индексы и контроль фактического результата обязательны. Уже выполненные обязательные интерактивы не повторяй ради нового снимка. Визуальная приёмка Stage 3/4 и обход всех интерфейсов не входят в Stage 5.

## Программы и затруднения

VS Code заменяй записью настоящего файла и запуском нужного Python. Postman — доступным агентом/CLI/HTTP-клиентом: нужен реальный запрос и проверка ответа, cookie/сессии, а также коллекция/окружение, если они результат задания. Для других программ выбирай функциональный эквивалент. Пользователь разрешил эту замену для Stage 5 без отдельного подтверждения; установка и ремонт GUI ради его названия не нужны.

Чисто интерфейсный шаг без аналога допускает `SIMULATED_UI`; одна строка ревью указывает замену и непроверенный интерфейс. Это само по себе не PARTIAL и не дефект курса. Имитация не заменяет реальный код, запрос или артефакт; служебные инструменты агента не становятся знаниями ученика и не переносятся в его код. Явную остановку пользователем или инструментом соблюдай; продолжение после неё требует актуального поручения.

**Отказ checker.** После первой неясной ошибки сверь условие, реальный вывод и свою попытку; повторяй только обоснованную исправленную версию. При двух попытках без новых данных прекрати угадывание: сохрани в локальном review.md ID/номер задачи, доступную версию или дату просмотренного материала, точный отправленный код, релевантный ввод/ожидание и видимый ответ. Не сохраняй секреты и скрытые проверки. Это исключение из обычной краткости ревью: исходная попытка нужна для воспроизводимости. Если версия неизвестна, так и напиши. Не объявляй техническое сообщение доказанным багом checker и не выводи обязательные требования из скрытых тестов. При доступном функциональном результате укажи отдельно: «по видимому условию выполнено; checker не подтвердил». Без реального обязательного результата — PARTIAL. Независимые задания продолжай; зависимый проект не строй на выдуманной точке B.

**Консультант Terra.** После двух безуспешных попыток или зацикливания разрешён один штатный субагент на конкретное затруднение: `gpt-6.1-terra / medium`, `fork_context=false`, `agent_type=default`. Передай обычным коротким текстом задачу, изученные опоры, минимальный код/условие, ошибку и попытки; не весь диалог. Схему текущего инструмента проверь, историческую заготовку вызова не копируй. Только чтение и диагноз со следующим шагом: без записи файлов/Git/прогресса, скрытых эталонов и дальнейшего делегирования. Основной чат применяет совет и проверяет результат. Допустимо одно уточнение по новому факту; затем закрой помощника. При неизвестном исходе сначала сверь существующего агента. Явную ошибку формата вызова можно один раз исправить по текущей схеме; она не является состоявшейся консультацией. При недоступности сохрани ограничение и продолжай независимое. Для другой проблемы возможна новая консультация после закрытия прежней; постоянных ролей нет. Помощь отмечается в review.md, а не выдаётся за знание из курса.

## Знания и ревью: два файла

**knowledge.md** хранит короткую текущую сводку и знания по занятиям: смысл, источник, статус «из теории / применено / с помощью», пробелы. Не переписывай в нём условия, пошаговый протокол кликов, список всех старых занятий и таблицы повторных запусков. Краткого проверенного результата достаточно; минимальные детали, необходимые получателю, уместны на контрольной точке передачи. Служебная адаптация среды не является изученной темой Python. Существующий приватный STUDYHUB_LEARNINGS.md сохраняй без дублирования или миграции.

В текущей точке указывай последнее выполненное занятие и **следующее учебное действие**, а не будущую операцию «закоммитить это занятие». Для конца диапазона — «передать результат на приёмку». Собственный SHA коммита извлекается из Git после создания: не нужен дополнительный коммит только ради записи самого себя. Публикацию проверяй по удалённому ref, не по обещанию в знаниях. Перед сдачей/продолжением сводка сверяется с Git.

**review.md** локальный, игнорируемый и неотслеживаемый. Одна краткая текущая сводка заменяется при изменении состояния; подробная история — в разделах занятий. Формат находки: **место/версия → наблюдаемый факт → трудность ученика → предлагаемая правка**. При отсутствии проблемы достаточно одной строки, без похвалы каждому пункту и повторяющегося отчёта о всех проверках. Указывай, где понадобилась подсказка, внешний совет или исправление другим исполнителем. Непроверенную причину обозначай гипотезой; исходные наблюдения сохраняй, поздние коррекции подписывай, не переписывая историю попытки. Полный код нужен лишь для невоспроизводимого иначе отказа/проблемы, как описано выше.

## Git, публикация и версии глав

Запрос пройти диапазон разрешает необходимые локальные изменения и поурочные коммиты. После блока и в конце главы — обычный push **только своей** подтверждённой ветки, например `git push origin HEAD:refs/heads/chapter/01/v1`. Если практика требует опубликованный текущий SHA или чистый clone, push делается **перед** этой проверкой, включая 20.1, затем ещё раз после финального коммита. Это не новое разрешение; ожидание конца блока здесь создало бы тупик. Не используй force, --all, --mirror. При неизвестном исходе сверь remote ref до повтора; ограничения доступа не обходи.

- **main** — принятые снимки. Исполнитель её не меняет, не коммитит, не мержит и не пушит в неё. Начав в main, установи назначенную ветку главы без изменения main. Урок о другой ветке/новом remote адаптируй к существующему checkout; не создавай вложенный .git и не переназначай origin. Расхождение кратко запиши.
- **chapter/NN/vN** — версия главы с целым проектом и знаниями до её выхода. Вход A записан в CHAPTERS.md: для первой главы — исходный main, для следующей — точный принятый B предыдущей. Ветки будущих глав заранее не создавай; главы собираются строго последовательно.
- **Новая версия** начинается от входа A главы, не от её старого B или позднего main. После замены предыдущей главы A берётся из нового принятого B. Старые принятые версии не стирай и не переписывай.
- **Приёмка** — отдельное поручение ответственному за интеграцию. Он проверяет A/B, знания и сценарии, обычным commit/merge переносит в main точный полный снимок project/ и knowledge.md, включая удаления, фиксирует SHA A/B и принятие в CHAPTERS.md. Порядок — в корневом README учебного репозитория. Результат Stage 5 сам main не обновляет.
- **Замена ранней главы:** main получает полный новый снимок, поздние главы отмечаются NEEDS_REPLAY. Прежние выходы остаются в старых ветках; новые версии последовательно собираются от нового входа. Старый поздний код не смешивается с заменой.

Реестр принятия читай из актуального `origin/main:CHAPTERS.md`, обновив refs перед новой главой, без переключения. В самой ветке до приёмки может быть лишь рабочая запись A. Корневые README/AGENTS — правила процесса; инструкция запуска приложения находится в project/README.md и проверяется буквально на опубликованной копии.

## Завершение и граница B→A

Передай итоговый опубликованный SHA B, диапазон и фактический результат, путь к ревью, оставшиеся проблемы и существенную помощь/смену исполнителя. READY_FOR_ACCEPTANCE означает, что итоговый проект воспроизводится и готов к отдельной приёмке; не означает принятия в main или автоматического PASS всех попыток. Не скрывай не принятые checker задачи за числом обработанных занятий/процентом платформы. Если обязательный результат проекта отсутствует — PARTIAL; конкретные неподтверждённые проверки перечисли отдельно.

На границе сверь проект, данные и изученные действия с заявленным входом следующей главы. Источник A следующей — принятая запись B из реестра. Не начинай следующую главу без принятого B и проверки B→A; завершение оператором подтверждает результат проекта, но не самостоятельность исходного ученика.
