## Точка B и границы

Ученик объясняет различие metadata, фактической схемы и строк; называет, почему `create_all` не обновляет существующую таблицу и почему отсутствие SQL DEFAULT не противоречит Python-default. Самостоятельно перечисляет поля, типы, PK, nullable, SQL defaults, CHECK, индексы, внешние ключи, представления и триггеры при наличии; сопоставляет фактические данные с моделью и ожидаемым исходным договором. Делает опись числа строк, ID и всех шести значений каждой задачи. На отдельной одноразовой базе создаёт и обнаруживает другое контролируемое расхождение; несовпадающий экземпляр помечает неизвестным и не допускает к автоматической маркировке baseline. Сам Planner и его таблицы не меняются.

Ожидаемая модель на входном SHA: `id` Integer, PK, not null; `title` String, not null; `priority` Integer, not null, Python default `2`; `is_done` Boolean, not null, Python default `False`; `tags` JSON, not null, Python default `list`; `title_normalized` String, not null. Ожидаемые индексы, FK и иные объекты устанавливать по реальному снимку и сопоставлению с моделью, а не обещать их отсутствие без наблюдения. ## 00. Вступление

Начать с двух синтетических задач, прочитанных через общий Planner: они сохранены, но их наличие не рассказывает, какие ограничения реально защищают файл. Предусмотреть один `LinkedNotes variant="connected"`:

1. **Точка старта:** известны адрес учебной базы и записи после диагностики общего хранилища.
2. **Новый вопрос:** совпадает ли фактическое устройство этой базы с описанием модели, если таблица уже существовала?
3. **Результат:** составить проверяемую опись схемы и данных и отличить согласованную базу от контрольной с расхождением.

После списка пояснить связь: проверка адреса делает наблюдение относящимся к нужному файлу, сравнение показывает условия сохранения данных, а опись станет ориентиром для будущей проверки снимка.

## 01. Модель, реальная схема и строки

**Что объяснить.** Модель `TaskRow` описывает желаемое устройство, схема SQLite хранит фактические определения таблиц и объектов, строки хранят конкретные значения. `create_all` проверяет существование таблицы и создаёт отсутствующую, но не превращает старую таблицу в новую версию. Пустой вывод ошибки не означает сравнения каждого ограничения.

**Независимый пример:** отдельная модель каталога книг `books` с `id`, `name` и `CHECK(length(name) > 0)`; в отдельной временной базе заранее создана одноимённая таблица без CHECK. Полностью показать исходный SQL создания существующей таблицы, отдельное определение metadata с CHECK, вызов `create_all` для этого файла и чтение `sqlite_schema.sql` до и после. Отсутствие ошибки и сохранение SQL без CHECK показывают различие между существованием имени и проверкой определения. Файл Planner не используется. Объяснить `CREATE TABLE`, скобки, типы, `CHECK`, создание engine и `metadata.create_all(engine)` в контексте примера, а также закрытие соединения/`engine.dispose()`.

**Первая проба:** на другом готовом различающемся выводе ученик выбирает, что относится к модели, что к схеме, что к строке, и объясняет, почему повтор создания не восстановил ограничение. Ожидается указание на сохранившийся SQL таблицы, а не только на отсутствие исключения. При затруднении вернуться к трём источникам; далее нужен надёжный способ увидеть именно файл.

**Визуальная функция:** три слоя «модель / схема файла / строки», переключение между совпадением и отсутствующим CHECK. Обратная связь показывает, что успешное создание уже существующей таблицы не меняет слой схемы; значения строк сами по себе наличие CHECK не доказывают.

## 02. Найти нужную базу и открыть только для чтения

**Что объяснить.** Рабочий каталог `project/`, путь к файлу, абсолютный путь и разрешённый учебный каталог; настройки проекта выбирают `DATABASE_URL`, но эта проверка получает путь из зафиксированной передачи. Остановить API/CLI и закрыть соединения перед сверкой, чтобы опись описывала стабильное состояние. Не угадывать путь по стандартному значению и не открывать неизвестный адрес обычным `sqlite3.connect`, который может создать пустой файл.

**Независимый полный пример:** в выделенной учебной копии `project/` есть `books.sqlite3` с таблицей книг, заранее созданная отдельным подготовительным сценарием. Показать полный файл `inspect_books.py` в этой же папке и запуск из `project/` командой PowerShell `.\.venv\Scripts\python.exe .\inspect_books.py`: первый путь выбирает интерпретатор подготовленной среды, второй файл примера. Отдельно разобрать `from pathlib import Path`, `import sqlite3`, `from contextlib import closing`, относительный путь к заранее названному файлу, `Path.resolve()`, `Path.is_file()` и остановку при `False`, `Path.as_uri() + '?mode=ro'`, `sqlite3.connect(uri, uri=True)`, `with closing(...) as connection`, `connection.execute(...).fetchall()` и вывод. Сравнить напечатанный разрешённый абсолютный путь с переданным перед открытием. URI создаётся из `Path.as_uri()`, а не склеиванием сырых Windows-путей; `mode=ro` запрещает запись и создание файла при отсутствии, `uri=True` включает разбор URI. `closing` закрывает соединение и при ошибке; сам контекст `Connection` не закрывает его. Показать имя таблицы через `SELECT name FROM sqlite_schema WHERE type='table' ORDER BY name` и отказ отсутствующего пути без появления нового файла. Новые переменные, строки, кавычки, скобки и значение результата объяснить на этом примере.

**Первая проба и входная диагностика:** ученик прогнозирует, какой из двух указанных путей относится к разрешённому каталогу, затем открывает существующий независимый файл read-only, находит таблицу и пробует отсутствующий путь; наблюдает таблицу или ошибку открытия, а не новую БД. После этого тем же способом показывает свой переданный учебный путь, таблицу `tasks` и по объяснению раздела 03 находит ключ; при неудаче возвращается к соответствующей опоре. Нельзя переходить к практике с неизвестным адресом.

**Опора:** `mode=ro` вместе с `uri=True`, проверка абсолютного пути и явное закрытие. Ошибка открытия является остановкой, не поводом сменить режим на запись. Далее нужно прочитать устройство найденной таблицы.

## 03. Столбцы, ключ, обязательность и defaults

**Что объяснить.** `PRAGMA table_info('имя')` возвращает по строке `cid`, `name`, `type`, `notnull`, `dflt_value`, `pk`: значение `1` в `notnull` означает явно объявленный NOT NULL, `pk` показывает позицию в ключе, SQL default `None` означает отсутствие SQL DEFAULT в определении. У SQLite есть особенности PK: вывод не следует механически трактовать как полную универсальную проверку nullability, сопоставлять с `CREATE TABLE`. `table_xinfo` дополнительно показывает скрытые и генерируемые столбцы; при неожиданном объекте учитывать и их. `SELECT` и `fetchall()` возвращают последовательность строк, а не меняют таблицу. Объяснить имена, кавычки SQL, скобки PRAGMA и чтение каждого поля результата. На независимой модели показать чтение `__tablename__`, `__table_args__`, `mapped_column`, `primary_key`, `nullable` и `default`; сопоставить `Integer` с SQLite `INTEGER`, `String` с наблюдаемым строковым типом `VARCHAR`/`TEXT`, `Boolean` с `BOOLEAN`, `JSON` с `JSON`, пояснив, что тип объявления и значение в строке различаются. Для практического образца брать фактические типы из собственной сверки, а не считать написание разных типов всегда эквивалентным.

**Независимый пример:** на read-only `books.sqlite3` показать полное определение `books(id INTEGER PRIMARY KEY, name TEXT NOT NULL, copies INTEGER NOT NULL DEFAULT 3)` и вывод `table_info` и `table_xinfo`. Сопоставить `copies`, SQL `DEFAULT 3`, признак `notnull` и `pk` у `id`. Во второй модели показать Python-side `default=3` без `server_default`, затем раскрыть, что подстановка клиентом при INSERT и SQL DEFAULT в CREATE действуют на разных сторонах. Показать `None` в `dflt_value` для колонки без серверного default, не называя его значением всех её строк. Модель может описывать ограничения, которые база ещё не содержит.

**Малая проба:** ученик сопоставляет другую колонку независимого примера с выводом PRAGMA, называет ключ и отличает SQL default от отсутствующего серверного default. Для проверки своего Planner самостоятельно находит `tasks` и ключ, не ожидая заранее готового вывода. Ошибку «`notnull=0` всегда разрешает NULL в любом PK» возвращать к определению и правилам SQLite. Далее извлекаем то, чего один `table_info` не показывает.

## 04. CHECK и объекты, которые не видны в списке столбцов

**Что объяснить.** `sqlite_schema` содержит `type`, `name`, `tbl_name`, `sql`; `CREATE TABLE` в `sql` позволяет прочесть именованные CHECK и их выражения. Запрос по типам `table`, `index`, `view`, `trigger` показывает и другие объекты, но SQL автоматически созданного индекса может быть `NULL`. `PRAGMA index_list('books')` показывает имя, уникальность, origin и partial; для каждого найденного индекса `PRAGMA index_info('имя')` показывает ключевые столбцы; при выражениях, сортировке, collation или partial нужны `index_xinfo` и определение индекса, неизвестный случай не объявлять равным. `PRAGMA foreign_key_list('books')` показывает ссылки, а отсутствие строк означает отсутствие объявленных FK для этой таблицы, не доказательство включённой проверки FK.

**Независимый пример:** на `books` с именованным CHECK, отдельным индексом по `name` и отдельной таблицей с FK показать полный SQL создания, запрос `SELECT type, name, tbl_name, sql FROM sqlite_schema ORDER BY type, name`, затем `index_list`, `index_info` для конкретного имени и `foreign_key_list`. Показать вид результата и что каждая колонка означает; отдельный вид или триггер включить в образец, чтобы ученик увидел их в реестре, но не менять данные. Сравнить с вариантом без CHECK: столбцы по `table_info` одинаковы, `sqlite_schema.sql` различается. Объяснить, почему `sql IS NULL` у автоиндекса не означает ошибку. Для имени индекса, полученного из результата, показать отдельный полный вызов `connection.execute('SELECT * FROM pragma_index_info(?)', (index_name,)).fetchall()`: `?` и одноэлементный кортеж передают значение отдельно от SQL; аналогично `pragma_index_xinfo(?)`. Сначала показать этот приём на учебном имени, затем дать малую пробу на другом индексе. Произвольное имя не склеивается с SQL.

**Первая проба:** на второй учебной таблице ученик выбирает, каким из четырёх наблюдений найти CHECK, ключевые поля индекса и FK, и показывает, где искать view/trigger. Локально объясняет пустой список индексов либо FK как наблюдение для конкретного файла, не как общее правило. Опора: столбцы через PRAGMA, CHECK и определения других объектов через `sqlite_schema`; далее строим сравнение с моделью.

**Визуальная функция:** таблица-матрица «вопрос → источник → наблюдение» с переключаемым случаем одинаковых столбцов и пропущенного CHECK. При выборе только `table_info` обратная связь указывает на недостающее определение; правильное сочетание показывает расхождение, не выводя ответ задачи Planner.

## 05. Сверка с моделью и отрицательный контроль

**Что объяснить.** Сравнение ведётся по признакам и семантике выбранного примера: столбцы/типы/PK/nullability/SQL defaults, затем CHECK, индексы, FK и прочие объекты; каждый вывод имеет источник. Отличать Python-default от SQL-default. Текст CREATE может отличаться при одинаковом смысле, поэтому различия исследуются, а неоднозначность остаётся неизвестной; «названия совпали» не является PASS.

**Независимый полный пример:** подготовить два новых учебных файла `books-good.sqlite3` и `books-no-check.sqlite3` в отдельном каталоге, ни один не Planner. В первом создать `books(id INTEGER PRIMARY KEY, name TEXT NOT NULL, copies INTEGER NOT NULL, CONSTRAINT ck_books_copies CHECK(copies >= 0))`; во втором создать такую же таблицу без CHECK. Явно показать `Path.resolve()` и `Path.exists()` для проверки разных незанятых путей, объяснить `sqlite3.connect(путь)` для создания только нового образца, `connection.execute('CREATE TABLE ...')`, `connection.commit()` и `connection.close()`, в том числе скобки, строки, запятые и именованное `CONSTRAINT ... CHECK(...)`. Показать открытие обоих существующих файлов read-only по разделу 02. Учебный каталог изолирован и другие процессы одновременно с ним не работают; проверка `exists()` не является конкурентной защитой занятого пути. Сопоставить одинаковые `table_info` и разные SQL в `sqlite_schema`, пометить второй экземпляр неизвестным для baseline. Никакой выборки из Planner или копии его таблицы в этом примере нет. Подробно разобрать, как определить отсутствие ограничения, а не делать вывод по успеху вызова.

**Своя проба:** в другом одноразовом образце ученик создаёт отличие типа или обязательности, ранее разобранное в 03, самостоятельно предсказывает строку PRAGMA и проверяет её через read-only соединение. Наблюдаемый результат: корректный и отличающийся образец разделяются по конкретному признаку, а не по имени файла. При ошибке вернуться к созданию образца и сверке признака; будущую задачу про `tasks` не решать за ученика.

## 06. Опись данных как независимое свидетельство

**Что объяснить.** Схема отвечает за допустимое устройство, а снимок значений нужен для последующего сравнения содержимого. `SELECT COUNT(*) FROM books` даёт число; `SELECT id, name, copies FROM books ORDER BY id` даёт устойчивый порядок по ключу и все поля выбранного образца. `fetchall()` возвращает строки; распечатанные синтетические значения можно перенести в таблицу. Пустая выборка, разные ID и одинаковое количество с разными значениями различаются. Не использовать приватные данные и не считать совпадение числа строк равенством содержимого. Для JSON в SQLite фиксировать реально прочитанное значение и не путать его с Python-списком без дополнительного разбора; никакое преобразование не должно терять элементы.

**Независимый пример:** в отдельном, заранее подготовленном `books-inventory.sqlite3` записаны две книги с разными id и названиями, например `(2, 'Atlas', 3)` и `(7, 'Notes', 1)`. Из read-only соединения выполнить указанные SELECT и показать вывод count `2` и две полные строки по ID. Во втором наборе то же количество, но другое `copies`; по количеству он выглядит совпавшим, а построчная опись выявляет отличие. Ввести `SELECT`, список полей, `FROM`, `ORDER BY`, `COUNT(*)`, смысл результата и фиксацию в заметке. Первая проба: ученик определяет изменившееся поле и объясняет, почему счётчика мало; при ошибке вернуться к двум строкам, затем переходить к своей описи.

## 07. Что мы будем делать в практике

**Формат и вход:** исследование схемы в редакторе на отдельных SQLite. Планируемая предыдущая B даёт остановленный учебный Planner с двумя синтетическими задачами, разными tags и зафиксированным абсолютным путём; выполнение передачи и собственная диагностика из 02–03 проверяются до начала. В распоряжении ученика `project/app/DBase/models.py`, учебный редактор и интерпретатор подготовленной среды. Учебная копия `project/` является разрешённым каталогом вспомогательных файлов: заметку можно сохранить как `schema-inventory.txt`, свой вспомогательный скрипт как `inspect-planner.py`, одноразовый контроль как `schema-control.sqlite3`. Если одно из этих имён уже занято, выбрать новое и указать его в заметке, ничего не перезаписывая; ни один из путей не равен переданному Planner. Для запуска своего файла использовать ту же форму команды, что в 02, подставив его имя. Все записи для проверки синтетические. Исходная база и единственный оригинал не используются; при неизвестном пути остановка. Подготовленные в теории отдельные `books` не являются решением задачи.

**Связанный маршрут:**

1. **Установить объект и ожидаемый договор → таблица ожиданий.** Контекст: перед сравнением нужно понять, с чем сравнивать файл. Условие: откройте `app/DBase/models.py`, выпишите `tasks` и все шесть полей, их объявленные типы, PK, nullable, клиентские defaults и два CHECK; различите модель и реальную базу. Технически: найдите `TaskRow`, `__tablename__`, `__table_args__`, `mapped_column`, запишите в собственную таблицу `признак / ожидается по модели / источник / факт`. Опора: 01 и 03–05. Локально видно шесть полей и оба именованных CHECK; Python defaults не подписаны SQL defaults. Помощь: вернуться к сравнению двух источников и формам модели. Будущий разбор: объяснить, как атрибуты и ограничения читаются из модели и почему это ожидание, а не наблюдение базы.
2. **Исследовать реальный учебный Planner → подтверждённый состав схемы.** Контекст: известный адрес может содержать таблицу, не совпадающую с моделью. Условие: откройте только переданный существующий файл read-only и установите все признаки без изменения. Порядок: из `project/` убедиться в допустимом абсолютном пути и отсутствии работающих писателей, использовать объяснённые `Path.resolve()`, `is_file()`, `as_uri()`, `sqlite3.connect(..., uri=True)` с `mode=ro` и `closing`; запросить `sqlite_schema` для типов table/index/view/trigger; выполнить `PRAGMA table_info('tasks')`, при необходимости `table_xinfo('tasks')`, `index_list('tasks')`, `foreign_key_list('tasks')`, для каждого найденного индекса применить параметризованный `pragma_index_info(?)` с фактическим именем и при необходимости `pragma_index_xinfo(?)`; прочесть CREATE таблицы и релевантные определения объектов. Закрыть соединение. В собственной таблице сопоставить каждый признак с моделью и указать факт, в том числе пустые списки и отсутствие SQL-default там, где это действительно наблюдается. Опора: 02–05. Локально назван ключ, видны все поля, определения обоих CHECK, индексы/FK и view/trigger либо зафиксировано их отсутствие. При отсутствующей таблице, неизвестном объекте или отличии фиксировать факт и остановиться: ни инициализации, ни исправления базы. Помощь: какой источник показывает CHECK и почему PRAGMA без строк является результатом. Будущий разбор: таблица сопоставления с объяснением каждого источника и границ сравнения.
3. **Зафиксировать строки → опись для будущей проверки.** Контекст: совпадение схемы не доказывает сохранность задач. Условие: в том же read-only файле запишите число строк и все значения каждой задачи. Порядок: открыть в режиме 02; самостоятельно выполнить `SELECT COUNT(*) FROM tasks` и выборку `id, title, priority, is_done, tags, title_normalized` из `tasks` с `ORDER BY id`; сохранить абсолютный адрес, число, ID и полные значения всех шести полей в собственной заметке, закрыть соединение. Сверить IDs и две записи с переданной диагностикой, в том числе разные tags и изменённую/соседнюю задачу; не выводить личные данные. Опора: 06 и предыдущая планируемая B. Локально число согласуется с количеством полных строк, обе записи узнаваемы; одинаковое число при изменённом поле не считается равенством. При несходстве остановиться и уточнить адрес/передачу без записи. Помощь: сравнивать по ID и каждому полю, а не по положению без сортировки. Будущий разбор: показать проверку числа, идентичности и значений и объяснить роль внутреннего поля tags.
4. **Самостоятельно создать отличающийся контроль → обоснованная остановка.** Контекст: нужно убедиться, что способ сравнения замечает ошибку, а не всегда сообщает совпадение. Условие: создайте в отдельном заранее выбранном учебном каталоге новый одноразовый SQLite-файл с таблицей `tasks`, содержащей шесть исходных имён столбцов; самостоятельно задайте их типы и ограничения по изученной модели, сохраните оба именованных CHECK, но добавьте лишний необязательный столбец `audit_note TEXT`. Это иное расхождение, чем отсутствующий CHECK в примере; экземпляр синтетический, не копия и не изменение файла Planner. Порядок: сверить абсолютный путь с путём Planner и удостовериться, что они различны и целевой путь ещё не занят; если занят, выбрать другое новое имя, не перезаписывать. Открыть новый образец для записи, самостоятельно записать `CREATE TABLE` с изученными объявлениями и указанным единственным отличием, подтвердить создание и закрыть соединение; далее открыть read-only и повторить нужные запросы схемы. Самостоятельно отметить лишний столбец и объяснить, почему наличие имени таблицы недостаточно. Опора: 03–05. Локальный результат: `table_info` показывает семь имён, включая отсутствующий в модели `audit_note`; `sqlite_schema` показывает оба именованных CHECK; контроль помечен неизвестным и запрещён для автоматического baseline. Не запускать `create_all` на Planner. Помощь: вернуться к списку полей и примеру сравнения, посмотреть на `__table_args__`, не подставляя готовую команду задачи. Будущий разбор: последовательность создания отдельного файла, чтения и выявления отличия; объяснение границы вывода. Если при создании ошибка, не принимать частичный образец: закрыть соединение и выбрать новый путь.
5. **Собрать вывод → пригодная передача.** Контекст: следующий этап будет проверять снимок по этой же описи. Условие: отдельно перечислите фактическую схему, соответствия и неизвестные случаи, путь учебного Planner и снимок строк; для отрицательного контроля запишите отличие и решение остановиться. Если реальная таблица совпадает с ожидаемым договором в проверенных признаках, обозначьте её согласованным baseline-кандидатом; если найдено отличие или неопределённость, обозначьте неизвестной и остановите переход. Планируемый следующий этап самостоятельно проверит путь и создаст новый снимок; опись сама не является backup. Опора: 01–06. Локально другой человек может сопоставить каждую запись с источником и отличить реальный файл от образца. Помощь: сравнить обе строки таблицы признаков и не скрывать пустой результат. Будущий разбор: согласованный и отличающийся случаи, причина отказа и содержимое передачи.

Шаги идут от ожидания к наблюдению, затем к данным и проверке способности заметить ошибку. Итоговые схема и опись доказывают B в пределах указанных признаков; пример с отсутствующим CHECK и собственный контроль с лишним столбцом проверяют разные причины остановки. При затруднении вернуться к указанному объяснению и повторить малую пробу на независимом образце.
