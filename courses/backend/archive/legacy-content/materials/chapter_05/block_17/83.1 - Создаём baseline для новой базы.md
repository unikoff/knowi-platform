## 02. Первая ревизия: кандидат, а не доказательство

- Пояснить граф: `revision` идентифицирует файл; у первой ревизии `down_revision = None`; `head` на этом шаге единственный. Файл с `upgrade()` содержит операции создания, а `alembic_version` отражает достигнутую версию. Генерация сравнивает metadata с выбранной пустой БД, создаёт **кандидат**, а не гарантированно полную миграцию. `revision --autogenerate -m` означает генерацию с текстом сообщения, `upgrade head` применяет историю, `current` показывает состояние БД, `heads` показывает концы файловой истории; объяснить каждый аргумент до пробы.
- Независимый полный пример: отдельный мини-проект `sandbox/inventory/` с собственными `alembic.ini`, `migrations/env.py`, пустым `versions/`, пустой SQLite и metadata таблицы `books` с `id`, `pages` и именованным CHECK `pages > 0`. Автор показывает необходимые импорты и конфигурацию, выполняет `python -m alembic revision --autogenerate -m "initial books"`, читает полученный файл, ID и `down_revision`, сопоставляет каждую операцию с моделью, затем вручную дополняет отсутствующий CHECK, если кандидат его не содержит. Показывает оба возможных результата генератора и то, что проверка обязательна в обоих. Вход, файл, команда, код операций, наблюдение и причина должны быть полными; версия инструмента фиксируется при создании материала.
- Первая проба: на другой независимой таблице с проверкой положительного количества ученик находит в кандидате первичный ключ и CHECK либо его отсутствие; при отсутствии дописывает ограничение по разбору примера. Ожидает первую ревизию без родителя. Путаница: наличие `head` в файлах не значит, что база уже обновлена. Опора рядом: читать тело `upgrade`, типы, nullable, PK и именованные ограничения, не принимать вывод генератора как сертификат.
- Учебный визуал: показать рядом файл первой revision, пустую базу и базу после upgrade. Состояния: кандидат существует, но БД ещё без revision; upgrade применён и версия записана; модель позже изменилась, а текст старой операции прежний. Ученик выбирает, где сейчас реально существует таблица, и получает объяснение различия истории и состояния. На неверный выбор обратная связь указывает, что один файл сам по себе не выполняет DDL. Имена и данные примера отличаются от проектной задачи.
- Переход: понять, какие именно значения и ограничения должны существовать в SQL, прежде чем утвердить исходный проектный кандидат.

## 03. Зафиксированная схема и значения по умолчанию

- Разобрать, как `op.create_table`, `sa.Column`, типы, `nullable`, `primary_key`, `sa.CheckConstraint` и необязательные операции индексов задают DDL непосредственно в ревизии. Объяснить импорты `from alembic import op`, `import sqlalchemy as sa`, аргументы и порядок на самостоятельном примере, не импортировать живую `Base` в тело исторической `upgrade()` и не подменять её вызовом `create_all`. История должна продолжать создавать старую схему, даже когда модель позднее изменится.
- Независимый полный пример: таблица `packages` с числовым полем количества и отдельными таблицами-примерами с Python `default=3` и SQL `server_default`. Показать файл модели и отдельную ревизию, явный SQL INSERT без значения, наблюдение соответствующего SQL DEFAULT либо отказа NOT NULL при отсутствии SQL DEFAULT; отдельно показать INSERT через SQLAlchemy с клиентским default. Объяснить, что клиентская подстановка не является DDL и SQLite не видит её при прямом SQL. Пример не использует поля Planner.
- Первая проба: ученик по двум определениям предсказывает результат SQL INSERT без поля и сверяет с DDL, затем сравнивает с ORM-вставкой; при отказе объясняет отсутствие server default. Опора: переносить в миграцию реальный DDL, а не автоматически превращать `default` в `server_default`. Для Planner предусмотреть шесть исходных полей, два CHECK и отсутствие SQL defaults; конкретные индексы, FK, триггеры и другие объекты сверять с принятой описью, не изобретать дополнительные. `description` пока нет.
- Переход: после обзора кандидата нужно наблюдать саму созданную базу, а не только исходный Python-файл.

## 04. Upgrade и чтение созданной схемы

- Объяснить порядок: при выбранном одном проверенном URL `python -m alembic upgrade head` исполняет ещё не применённые операции; `python -m alembic current` читает текущую revision, `python -m alembic heads` читает историю. Вывод команды не заменяет чтение структуры. Повтор при уже достигнутой той же revision не должен повторять создание таблицы. `stamp` изменяет метку, но не строит схему; здесь его не применять.
- Независимый пример продолжает `books`: показать команду upgrade к пустому файлу, созданную таблицу и версию, затем новое соединение Python `sqlite3.connect`, `execute`, `fetchall`, закрытие соединения. Показать `SELECT version_num FROM alembic_version`, `PRAGMA table_info(books)`, `PRAGMA index_list(books)`, `PRAGMA foreign_key_list(books)` и запрос `SELECT type, name, tbl_name, sql FROM sqlite_schema WHERE name NOT LIKE 'sqlite_%' ORDER BY type, name`; объяснить столбцы `name`, `type`, `notnull`, `dflt_value`, `pk`, чтение DDL и что автоматические внутренние объекты SQLite рассматриваются отдельно. Пустой список индексов или FK является результатом, а не ошибкой. Значение `pk` и `notnull` сравнивать с зафиксированной SQLite-описью, не выводить универсальный закон из одного типа PK.
- Первая проба: ученик на отдельной таблице прогнозирует до/после upgrade, затем читает версию и структуру; отдельно отличает пустой результат PRAGMA от ошибки имени таблицы по списку `sqlite_schema`. Опора: версия плюс столбцы, DDL и объекты; одна версия или одно имя таблицы не доказывают схему. Переход: проверим не только декларацию CHECK, но и её поведение.
- Учебное сравнение: показать две синтетические базы с одинаковой revision, но в одной отсутствует CHECK; ученик сопоставляет version, DDL и результат вставки. Верный вывод: совпадения метки недостаточно; если выбран только version, обратная связь возвращает к фактическому ограничению. Это учебный сконструированный пример, а не утверждение, что обычный upgrade создал различающуюся схему.

## 05. Ограничения и повтор без потери данных

- На независимой `books` объяснить транзакцию и пробу CHECK: отдельные явные INSERT со всеми обязательными полями, `commit` для допустимой строки; недопустимый ввод в отдельной транзакции вызывает `sqlite3.IntegrityError`, после чего нужен `rollback`; затем новое чтение сохранённой строки. Показать `SELECT`, сравнение всех выбранных значений до/после повторного upgrade, закрытие соединения. Для прямого SQL не полагаться на Python defaults.
- Полный пример: `pages=12` сохраняется; `pages=0` отклоняется; до второго `upgrade head` соединение закрыто, после команды новое соединение показывает прежнюю запись и тот же ID версии. Причина: уже применённая ревизия не должна исполняться повторно. Отдельный неверный случай: если ошибка возникла из-за другого ограничения или отсутствующей таблицы, это не подтверждение нужного CHECK; проверить конкретную причину и корректную строку.
- Проба: ученик меняет значение страниц на другое недопустимое, предсказывает отказ, выполняет и проверяет прежнюю корректную строку. Опора: успешная ветвь, отказ нужного ограничения, rollback, чтение после нового соединения. Переход: перенести доказательство на две независимые базы и автоматизировать проверку.

## 06. Изолированные тесты и исходный договор

- Объяснить назначение `pytest`, `tmp_path`, `assert`, тестового файла и результата команды `python -m pytest`; существующая учебная среда должна иметь зависимости из `requirements-dev.txt`. Тесты не используют реальный URL приложения и не изменяют `project/data`. Объяснить, как фиксированный ожидаемый набор признаков отличается от `Base.metadata`: при изменении модели сравнение старого договора с новой metadata не должно незаметно переписать историю. `head` обозначает текущий конец истории и позднее может измениться; для исторической проверки нужен конкретный ID исходной ревизии, взятый из реально созданного файла и сохранённый в тесте как значение цели.
- Независимый полный пример: у мини-проекта `books` есть две заранее предоставленные связанные ревизии: первая создаёт исходную таблицу с CHECK, вторая добавляет отдельный nullable признак. Автор показывает оба файла и реальные для этого примера `revision` и `down_revision`, не подставляя выдуманный ID Planner. На двух разных путях `tmp_path` для каждого теста создаёт `alembic.config.Config` из того же ini, задаёт `set_main_option("sqlalchemy.url", URL_своего_tmp_path)` и `set_main_option("expected_database_path", абсолютный_свой_tmp_path)`, а `script_location` указывает на ту же принятую историю. Показать создание файлового URL из абсолютного пути, строковые значения аргументов и то, как `env.py` через `get_main_option` читает именно переданные настройки, разрешает и сравнивает пути до подключения, не заменяя их жёсткой строкой или окружением. Для ini-значений, содержащих `%`, объяснить экранирование ConfigParser или выбирать контролируемый путь без него. Первый тест вызывает `alembic.command.upgrade(config, baseline_revision)`, где `baseline_revision` содержит ID первой ревизии из показанного файла; `sqlite3` читает `alembic_version`, исходные столбцы и CHECK и сравнивает с зафиксированным набором. Второй тест на другом пустом файле вызывает `alembic.command.upgrade(config, "head")` и сравнивает текущую версию и актуальную схему с отдельным набором, включающим добавленный признак. Результаты отличаются после появления второй ревизии. Для отрицательной ветви на третьем временном пути показать Config с URL этого пути и чужим ожидаемым путём: вызов upgrade завершается отказом до подключения, ошибочный файл отсутствует. Разобрать импорты, аргументы, связывание переменной с реальным ID и закрытие ресурсов. Не подменять миграционный тест `create_all`.
- Первая проба: ученик на других временных файлах самостоятельно выставляет обе опции Config для каждого вызова, проверяет равенство разрешённых путей и выбирает цель: ID первой ревизии для исходного договора и `head` для актуальной схемы. Он предсказывает версии и столбцы и сверяет их на отдельных новых файлах. Затем меняет только URL, оставив прежний expected path, и подтверждает отказ до подключения и отсутствие ошибочного файла. При подстановке `head` в историческую проверку обнаруживается дополнительное поле; после возврата конкретного ID проверка проходит. Отдельно изменить ожидаемый признак и увидеть отказ `assert`. Опора: `tmp_path` даёт изолированный путь, пара опций проверяет адрес, конкретная revision сохраняет исторический срез, `head` движется вместе с историей, утверждения читают физическую схему. Переход: теперь проектная практика соединит ревизию, два файла и проверяемый образец.

## 07. Что мы будем делать в практике

**Формат и вход:** проектная практика начальной ревизии. В учебной копии есть планируемые результаты настройки истории и описи схемы; перед выдачей они проверяются по разделу A. Ученик работает из `project/` и сам создаёт/правит ревизию и тесты. Готового решения ревизии и готовых тестов ему не выдают.

1. **Подготовить безопасное начало → известный пустой объект.** Контекст: история должна построить Planner без старого заполненного файла. Условие: выбрать отдельный учебный каталог и два отсутствующих файла `baseline_a.sqlite3`, `baseline_b.sqlite3`, не совпадающих друг с другом, исходником, снимком и восстановленной копией. Действия: проверить активный Python, версии Alembic и pytest, структуру `migrations/versions/`, отсутствие файлов, опись и соответствие `models.py`; в `alembic.ini` указать `sqlalchemy.url` первого файла и его абсолютный `expected_database_path`, показать оба разрешённых пути и их равенство до подключения, проверить, что `env.py` останавливает несовпадение до engine и offline configure. На отдельном новом ошибочном пути изменить только URL, вызвать `python -m alembic current`, убедиться в отказе и отсутствии файла; затем восстановить согласованную пару первого пути. Опора 01 и планируемая B настройки. Самопроверка: каталог есть, история пуста, оба разрешённых адреса совпадают с первым новым файлом, отрицательная проба не создала ошибочный файл, исходная схема совпадает с описью; при занятом пути, неясном URL или расхождении остановиться. Помощь: вернуться к проверке адресов, не очищать чужой файл. Будущий разбор показывает почему подключение создаёт файл и почему проверка делается заранее.
2. **Получить и исправить кандидат → одна читаемая исходная revision.** Контекст: autogenerate предлагает начало истории. Условие: сформировать кандидат для исходной модели и изучить его, сохранив договор шести полей и CHECK. Действия: на первом пустом учебном адресе вызвать `python -m alembic revision --autogenerate -m "initial planner"`; открыть новый файл `migrations/versions/`, записать фактический `revision`, убедиться в `down_revision = None` и единственном head через `python -m alembic heads`; самостоятельно сверить и при необходимости исправить типы, PK, nullable, два именованных CHECK, SQL defaults и все значимые объекты по исходному снимку и описи. Ревизия содержит собственные операции создания и не вызывает текущую metadata. Опора 02–03. Локальный результат: понятный файл с ожидаемым исходным договором, без `description`; при пропущенном CHECK или непонятном объекте он не принят до исправления. Помощь: найти соответствие между моделью, исходной описью и каждой операцией, не выдавая готовую ревизию. Разбор сопоставляет неверный кандидат с исправленным и объясняет ограничения генератора.
3. **Применить и обследовать первую базу → проверенная схема и версия.** Контекст: прочитанный файл ещё не создал таблицу. Условие: направить инструмент только на первый адрес и выполнить историю. Действия: повторно проверить `sqlalchemy.url` и `expected_database_path`, показать равные разрешённые пути; выполнить `python -m alembic upgrade head`, затем `python -m alembic current`; отдельным `sqlite3`-соединением прочитать `PRAGMA table_info(tasks)`, `PRAGMA index_list(tasks)`, `PRAGMA foreign_key_list(tasks)`, SQL таблицы и перечень пользовательских объектов из `sqlite_schema`, сравнить с описью и зафиксированным входом. Сравнить значение `alembic_version` с записанной revision; разрешить служебную таблицу Alembic как дополнительный объект истории. Опора 04. Самопроверка: шесть полей, PK и обязательность соответствуют описи, SQL defaults отсутствуют, оба CHECK и ожидаемые индексы/FK/прочие объекты совпадают, текущая версия равна созданной. При несовпадении остановить переход и выяснить причину на одноразовой базе. Помощь: структура и `sqlite_schema`, а не одна строка current. Разбор объясняет, почему metadata и текущая версия сами по себе не доказывают физический DDL.
4. **Проверить границы и воспроизводимость → две согласованные базы.** Контекст: схема должна действовать на данных и создаваться повторно без заполненного оригинала. Условие: только синтетические строки и две независимые БД. Действия: в первой базе напрямую вставить с явными значениями всех полей корректную строку `(id=1, title='Учебная', priority=2, is_done=0, tags='[]', title_normalized='учебная')`; отдельно попробовать `id=0` и `priority=6`, не меняя других корректных значений, проверить `IntegrityError` именно нужного CHECK и выполнить rollback каждой ошибочной транзакции. Закрыть соединение, повторить `python -m alembic upgrade head`, новым соединением прочитать все шесть значений, revision и объекты. Для второго ранее отсутствующего файла переключить в `alembic.ini` и `sqlalchemy.url`, и контрольный абсолютный `expected_database_path`, показать оба разрешённых пути и их равенство до команды, затем применить ту же историю; повторить структурную сверку и положительную/отрицательную проверки с другими синтетическими значениями. При необходимости повторить upgrade и там, сравнив все поля до и после. Опора 04–05. Результат: один revision ID и равный исходный договор в обеих БД, ошибочные строки не сохранены, корректные остались без изменений, повтор не создаёт дублей. Две базы проверяются по очереди: URL остаётся единственным источником соединения, ожидаемый путь только проверяет выбранное назначение. Помощь: отличать отказ CHECK от NOT NULL и от неправильного адреса. Разбор прослеживает commit, ошибку, rollback и новое чтение; при неожиданном состоянии не считать проверку пройденной.
5. **Закрепить проверку в проекте → воспроизводимый тест без оригинала.** Контекст: позднее модель и `head` изменятся, но исходный договор должен остаться проверяемым. Условие: в `tests/test_db_schema.py` сохранить отдельную историческую проверку на явно зафиксированном наборе признаков исходного снимка; не выдавать чтение живой `Base.metadata` за неизменяемый образец. Для каждого нового временного файла создать Config из того же `alembic.ini`, задать `set_main_option("sqlalchemy.url", URL_своего_tmp_path)` и `set_main_option("expected_database_path", абсолютный_свой_tmp_path)` и направить `script_location` на ту же историю; проверить, что `env.py` читает именно эти значения и сравнивает пути до соединения. Отдельно для несовпадающей пары подтвердить отказ и отсутствие ошибочного файла. Исторический тест на новом временном файле вызывает `command.upgrade(config, baseline_revision)`, где значение `baseline_revision` берётся из действительно созданной и принятой ревизии шага 2, и сверяет физическую схему и `alembic_version` именно с этим исходным ID и договором шести полей. Отдельный тест на другом новом временном файле вызывает `command.upgrade(config, "head")` и проверяет текущую ревизию и актуальную схему; сейчас они совпадают с baseline, после расширения его ожидаемый договор необходимо обновить, не изменяя исторический. Существующие проверки текущего поведения не удалять ради прохождения. Проверить столбцы, nullable/PK, SQL defaults, DDL CHECK, ожидаемые объекты и поведение допустимой и недопустимых строк, а также сохранность строки после повторного upgrade к той же цели. Действия: самостоятельно записать тесты, проверить направление каждого подключения на `tmp_path` и выполнить `python -m pytest tests/test_db_schema.py` из активной учебной среды. Опора 06 и 03–05. Локальный результат: обе проверки проходят на изолированных путях и выявляют намеренно неверное ожидание на отдельной пробе; прежний `init_db.py` и runtime не изменены. Помощь: сверить реальный ID baseline, оба значения Config и их проверку в `env.py`, цель каждого `command.upgrade` и физическое чтение вместо `create_all`. Разбор объясняет, почему после продвижения `head` историческая проверка остаётся на исходной ревизии и почему тест нельзя запускать на оригинале.

Эти действия связаны: опись ограничивает кандидат, кандидат строит первую базу, проверка данных и второй независимый путь показывают воспроизводимость, а изолированные тесты сохраняют свидетельство исходного договора. Возврат к разделам 01–06 допустим; итог требует всех наблюдений, а не только успешной команды или записи версии.

Планируемая B предыдущего шага даёт конфигурацию и безопасный адрес; опись даёт сравниваемую исходную схему. Разделы 01–03 объясняют выбор адреса, кандидат и SQL-default на независимых объектах; ученик самостоятельно создаёт и исправляет файл ревизии. Разделы 04–05 готовят реальные проверки версии, DDL, валидной и отклонённой строк; ученик применяет историю на двух новых файлах и доказывает повтор без потери данных. Раздел 01 готовит сверку двух путей и отказ до подключения; раздел 06 готовит ту же проверку в Config временной базы и два вида тестов. Ученик фиксирует старый договор и проверяет реальный upgrade на изолированных путях. Таким образом B достигается без зависимости от будущей изменённой metadata или маркировки заполненной базы.
