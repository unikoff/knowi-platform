## Точка B и границы

Ученик объясняет разницу схемы, данных и revision, ограниченность autogenerate и причину, по которой stamp не выполняет upgrade и не исправляет схему. Сам сопоставляет документированный baseline и заполненную восстановленную копию, фиксирует признаки и только при совпадении ставит **конкретную исходную revision**. На другой копии с намеренным расхождением обнаруживает его и не маркирует. В проектной учебной копии изменяется только состояние истории подходящего файла; все строки с шестью полями сохраняются. Доказательства: опись объектов и значений до/после, current равен реальному ID baseline; у плохого образца состояние версии до и после одинаково.

Передача следующему занятию планируется: проверенная маркированная заполненная копия, две базы после baseline, точная revision, опись и отдельно сохранённый резерв. Получатель перед расширением повторно проверит адреса, резерв и историю. Новая nullable `description`, изменения metadata, согласование `init_db` с историей и upgrade относятся к следующему шагу; tags и description не вводятся в API/CLI. Исходные данные и единственный оригинал не трогаются; JSON-импорт остаётся явным, runtime fallback не вводится.

## 01. Какие файлы участвуют и как остановиться

- Объяснить отдельные роли исходной базы, сохранённого снимка, восстановленной заполненной копии, двух пустых баз из baseline и одноразовой плохой копии. Все команды ниже выполняются из `project/` в изолированной учебной копии, с ранее подготовленным интерпретатором. Перед выдачей автор согласует фактические имена и команды среды с предыдущими материалами, не предполагая установленный Alembic.
- Независимый пример: в каталоге `demo/` есть защищённый снимок `archive.sqlite`, восстановленная `restored.sqlite` и пустой образец `reference.sqlite`. Показать получение абсолютных путей, проверку существования и попарного различия, остановку при отсутствующем файле или совпадающих путях. Для SQLite чтение открыть через `sqlite3.connect("file:demo/restored.sqlite?mode=ro", uri=True)`: разобрать URI, `mode=ro`, аргумент `uri`, закрытие соединения; отсутствующий файл не должен создаваться. Наблюдение: неправильный путь даёт ошибку, а не пустую базу. На Windows автор показывает корректный абсолютный file URI для своей среды.
- Собственная проба: на других демонстрационных путях ученик выбирает безопасную пару, объясняет отказ при совпадении и проверяет отсутствие назначения. Опора: источник, назначение и резерв различны; отказ означает не продолжать запись.
- Визуальная схема четырёх ролей и стрелки восстановления: выделить источник чтения, резерв и единственный файл для записи; состояние «неизвестный адрес» показывает остановку. Это помогает не принять существование файла за восстановимость.

## 02. Сравнение объектов и структуры

- Объяснить, что модель, ревизия и фактическая схема отвечают на разные вопросы. Сравнивать нужно реальную базу после upgrade baseline и восстановленную копию, опираясь также на ревизию и документированную опись. Учесть системные объекты и `alembic_version` отдельно: допустимое различие истории не является различием таблицы задач.
- Полный независимый пример: два файла `demo/reference.sqlite` и `demo/candidate.sqlite`, таблица `notes(id INTEGER PRIMARY KEY, body TEXT NOT NULL, rating INTEGER CHECK(rating > 0))`; во втором файле нет CHECK. Привести полный SQL создания обоих файлов, способ открытия только для чтения, закрытия и вывод результатов. Через `SELECT type, name, tbl_name, sql FROM sqlite_schema ORDER BY type, name` показать таблицы, индексы, представления и триггеры, включая SQL и NULL у автоматического индекса. `PRAGMA table_xinfo('notes')` показывает имя, тип, notnull, default, pk и hidden; CHECK читается из CREATE SQL, а не из table_xinfo. Разобрать каждое выражение и ожидаемое отличие. Одинаковые названия и поля ещё не доказывают одинаковый CHECK.
- Для каждого индекса объяснить `PRAGMA index_list('notes')`, затем `PRAGMA index_xinfo('имя_индекса')`: состав, порядок, уникальность, частичный индекс и SQL. Для связей объяснить `PRAGMA foreign_key_list('notes')`; отдельно прочитать SQL таблицы на предмет CHECK и других ограничений. Отсутствие строк означает отсутствие обнаруженных объектов данного вида, а не ошибку. Сравнивать defaults в SQL, не путать с Python defaults ORM. Для неожиданного объекта, неясного SQL, generated/hidden столбца или неоднозначности остановиться, не объявлять совпадение по похожему тексту.
- Собственная проба: на другой паре маленьких таблиц обнаружить пропущенный NOT NULL и объяснить, почему он виден в table_xinfo. Опора: объекты → поля → ограничения и индексы → неизвестное означает стоп. Далее понадобится сравнить содержимое, которое схема не показывает.

## 03. Снимок значений и контроль данных

- Показать, почему одинаковое количество строк не гарантирует одинаковые значения, а `integrity_check` не проверяет смысл данных. Снимать упорядоченный по ID список полей и число строк до действия и после него на закрытых независимых read-only соединениях.
- Независимый пример: таблица `notes` с двумя разными id и текстами в отдельном файле; `SELECT COUNT(*) FROM notes` и `SELECT id, body, rating FROM notes ORDER BY id`. Пояснить SELECT, список полей, COUNT и ORDER BY, фиксирование полного результата и сравнение строк, включая NULL; одинаковое количество при изменённом тексте не означает сохранность. Ученик на других строках находит изменённое значение при прежнем количестве.
- Для Planner сохранять и сравнивать точные значения `id, title, priority, is_done, tags, title_normalized` всех строк, в том числе обеих непохожих синтетических задач. Не использовать API/CLI как доказательство сохранности внутренних tags.

## 04. Ревизия и предел автоматической сверки

- Объяснить: файл revision содержит исходную операцию создания; его `revision` есть конкретный идентификатор, `down_revision` у первой ревизии отсутствует. `current` читает записанное состояние истории, а `history` показывает доступные ревизии; ни один не доказывает совпадение схемы. `stamp` записывает revision без выполнения операций миграции; `head` означает текущую вершину графа и может позднее означать другое. Autogenerate предлагает различия, но может пропустить ограничения и не подтверждает равенство выражений CHECK. Сверить применимую версию до выдачи.
- Перед командами примера объяснить договор адреса на самостоятельном мини-проекте: в `demo/alembic.ini` секции `[alembic]` находятся `script_location`, `sqlalchemy.url` и `expected_database_path`. URL является единственным источником подключения; expected path лишь контрольный абсолютный путь выбранного учебного файла. В `demo/migrations/env.py` `context.config.get_main_option("sqlalchemy.url")` и `get_main_option("expected_database_path")` читают текущие main options; объяснить импорт `from alembic import context`, аргументы и отсутствие значения. `from sqlalchemy.engine import make_url`, `make_url(raw_url)`, `url.get_backend_name()` и `url.database` разбирают адрес; `from pathlib import Path`, `Path(...).is_absolute()` и `resolve()` позволяют сравнить абсолютные пути. Автор показывает полный исполнимый независимый пример с конкретными файлами, ожидаемым выводом, обработкой отсутствующего/непонятного URL и проверкой SQLite-файла, а не memory/URI/query; относительный путь URL разрешается от рабочего каталога. До создания engine или подключения и до offline `configure` проверяются существование файла, разрешённый учебный каталог и равенство двух нормализованных путей; несовпадение или ошибка даёт отказ. Символы URL и интерполяцию ini автор проверяет для используемой версии, не пряча их от ученика.
- Проба на мини-проекте: задать в ini оба значения для существующего `demo/sample.sqlite`, вывести абсолютный путь из URL и expected path и получить равенство; сменить только URL на ранее не существующий `demo/wrong.sqlite`, оставить expected прежним и увидеть отказ до подключения и отсутствие нового файла. Затем самостоятельно повторить с другими именами и восстановить согласованную пару. Этот же механизм до текущей темы планируется в 83; пример и проба повторяют критическую проверку перед командами здесь.
- Независимый пример: мини-проект с отдельной конфигурацией и таблицей notes, два готовых файла схемы из 02 и своя исходная revision. Показать как из файла ревизии взять фактическое значение, как в активной среде из корня мини-проекта выполнить `python -m alembic current`, затем после сравнения `python -m alembic stamp <фактический_ID>` и снова `python -m alembic current`. Угловые скобки обозначают подстановку, не буквальный аргумент. Показать эффективный адрес до каждой команды, результат отсутствующей версии и наличие ID после stamp; повторное чтение схемы и строк показывает, что таблица не пересоздана. На несовпадающем notes показать отказ до stamp. Если история уже содержит неожиданную revision, остановиться; не стирать её и не применять `--purge`.
- Малая проба: ученик для второй независимой пары выбирает маркировать или остановиться и объясняет, почему `stamp head` не исправит отсутствующее ограничение. Опора: сначала сравнение, затем точный ID, повторная проверка.
- Интерактив решения: входы «схема совпадает/отсутствует CHECK/неизвестный триггер», «история пустая/неожиданная» и выбор сравнения, stamp или остановки. Обратная связь объясняет причину и показывает, что метка не меняет SQL. Данные и имена отличаются от практики; визуал не выдаёт её решение.

## 06. Что мы будем делать в практике

**Формат и вход:** проектное исследование и маркировка копии. Предыдущие B планируются; до выдачи проверяются как описано в A. Даны изолированная копия проекта, окружение и история, реальный ID baseline, две проверенные пустые базы, опись и восстановленная заполненная база минимум с двумя различными синтетическими задачами, отдельный проверенный резерв. Имя файла ученик берёт из фактической передачи, не из предположения. Результаты записываются в собственную рабочую опись ученика; формат свободный, но признаки и значения должны быть видимы.

1. **Подготовить безопасный вход.** Контекст: есть несколько файлов Planner и снимок. Условие: нельзя менять исходную базу или резерв. Действия: из `project/` найти пути заполненной копии, образца, резерва и будущего плохого экземпляра; проверить существование первых трёх, различие всех путей, возможность восстановления и подтверждённый настоящий ID первой ревизии из файла `migrations/versions/`. При проверке истории образца и заполненной копии поочерёдно выбрать каждый файл как цель, синхронно выставить `sqlalchemy.url` и `expected_database_path`, показать и сравнить оба абсолютных пути по 04–05; только после этого выполнять `python -m alembic current`. Результат: отдельная заполненная копия и образец доступны, история копии известна и пока не содержит неожиданной ревизии. Нет резерва, файл отсутствует, адрес неизвестен, два пути различаются или версия неожиданна: остановиться. Помощь: вернуться к схеме ролей и настройке адреса; в будущем разборе разобрать ошибочный путь и выбор нового файла.
2. **Сравнить исходную схему.** Контекст: у копии есть данные, а образец создан историей. Условие: проверить структуру, а не довериться названию таблицы или пустому diff. Из read-only соединений собрать выводы `sqlite_schema`, `table_xinfo('tasks')`, `index_list('tasks')`, `index_xinfo` каждого найденного индекса и `foreign_key_list('tasks')`, как в 02. Сопоставить таблицы, колонки, типы, PK, nullable, SQL defaults, CHECK, индексы, FK, триггеры, views и прочие объекты с образцом, ревизией и сохранённой описью; `alembic_version` отнести к истории отдельно. Записать факт для каждого признака, включая подтверждённое отсутствие. Локальная готовность: признаки совпадают либо конкретное расхождение/неизвестность указано и действие остановлено. Помощь: вернуться к 02; разбор покажет, где искать CHECK и почему ORM default не равен SQL default.
3. **Проверить отказ на плохой копии.** Контекст: похожий файл может иметь неверное ограничение. После примера и пробы из 05 создать одноразовую копию командой `python -m app.DBase.backup_snapshot SOURCE DEST` из `project/`: SOURCE подставить как проверенную восстановленную базу, DEST как новый, отсутствующий и отличный от всех остальных путь плохой копии. Проверить успешный выход, открытие и сохранность записей; ошибку не считать готовым файлом. По 05 синхронно переключить `sqlalchemy.url` и `expected_database_path` на плохую копию, вывести и сравнить абсолютные пути до `current`. На этом экземпляре создать контролируемое расхождение: лишнюю таблицу `unexpected_marker` с одним целочисленным столбцом, не изменяя tasks; подготовка и проба находятся в 05. Найти лишний объект, отказаться от stamp, повторить проверку обоих адресов и `current` плохой копии. Готовность: расхождение названо и состояние истории одинаково до/после; если текущую версию нельзя достоверно прочитать, остановиться и не утверждать успех. Помощь: 02, 04 и 05; разбор объяснит, почему отсутствие ошибки открытия не подтверждает совпадение.
4. **Пометить только подходящую копию.** Контекст: схема и восстановимость доказаны, а история заполненного файла ещё не содержит неожиданной версии. Снять количество и полный набор шести полей по 03: `SELECT COUNT(*) FROM tasks` и `SELECT id, title, priority, is_done, tags, title_normalized FROM tasks ORDER BY id`. Переключить `sqlalchemy.url` и `expected_database_path` обратно на подходящую заполненную копию, вывести и сверить оба абсолютных пути и текущую версию по 05. Перед stamp повторить сверку адресов. В активной среде из `project/` выполнить `python -m alembic stamp <фактический_ID_baseline>`, подставив ID из ревизии, а не текст в скобках и не `head`. Проверить оба адреса и повторить `python -m alembic current`, затем прочитать schema и все строки заново. Локальная готовность: current показывает исходный ID; данные и схема tasks до/после равны, различие только ожидаемое состояние истории. При ошибке не повторять вслепую: сначала прочитать фактическую историю и схему, при неизвестном результате остановиться. Помощь: 03–05; разбор отдельно объяснит, что stamp не запускает upgrade.
5. **Подготовить передачу.** Сопоставить собственную опись, ID, адреса копий и резерва, доказательства отказа и сравнение строк; объяснить на примере плохой копии, почему `stamp head` не исправляет CHECK или лишний объект. Передать отмеченный файл, неизменённый резерв, образцы и опись; обнаруженное расхождение или неизвестный объект блокируют передачу как готовой baseline.

Каждый результат становится входом следующего: безопасный адрес позволяет исследовать структуру, доказанное совпадение и контроль данных дают основание для единственной записи версии, а отрицательный случай проверяет границу решения. Для затруднений возвращаться к указанным объяснениям, а не угадывать команду. Никакой runner или готовое решение для этой проектной практики не предполагается.
