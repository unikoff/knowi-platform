## Точка B и границы

Ученик объясняет согласованность снимка, роль журнала/WAL, зачем остановить учебные процессы, почему копирование одного файла активной WAL-базы не универсальный backup и почему открытие копии ещё не доказывает восстановление. Самостоятельно создаёт учебную обёртку для SQLite Backup API и получает отдельный открываемый снимок заполненного Planner по новому адресу. Проверяет неизменность записей источника по описи, отказ для занятого адреса с побайтовой сохранностью файла, отсутствующего источника и совпадающих путей. Ошибка после резервирования означает остановку: частичный файл не считать снимком и не передавать дальше.

Это не восстановление, проверка полноты снимка, миграция, изменение схемы, API или CLI Planner. Восстановление и сравнение всех данных и ограничений запланированы в соседнем занятии «Проверяем восстановление». Передаются только успешно созданный и открытый снимок, точный путь и опись исходной базы; при ошибке или неясном результате переход запрещён. Никакая фактическая копия сейчас не создаётся.

## 01. Состояние базы и граница снимка

- Объяснить: запись может быть в процессе; SQLite использует журнал отката либо WAL для согласованной работы. В WAL подтверждённые изменения могут находиться вне основного файла. Остановка учебных процессов упрощает опыт, но не делает копирование одного файла активной WAL-базы общим безопасным способом. Backup API работает с согласованным состоянием SQLite; восстановление и проверка содержимого отдельны.
- Независимый мысленный пример: маленький каталог библиотеки, в основном файле старое состояние, в WAL подтверждённое изменение. Сравнить копию одного файла во время работы с обращением через SQLite Backup API; показать, почему по одному основному файлу нельзя заключить о полноте. Это иллюстрация роли WAL, не обещание конкретного физического расположения любой записи.
- Первое действие: ученик выбирает, можно ли считать появление файла доказательством восстановления, и объясняет, какой следующий опыт нужен. Ожидание: нет, нужно открыть и далее восстановить и сравнить данные. Опора: остановка записи, отдельный источник, снимок и будущая восстановленная копия. Переход к выбору адресов.
- Визуал: схема состояний «идёт запись / процессы остановлены / резервирование / снимок открыт / восстановление ещё не проверено» с отдельным обозначением основного файла и WAL. Ученик определяет, что подтверждает каждый переход; обратная связь различает доступность файла и полноту данных. Не изображать восстановление уже выполненным.

## 02. Путь источника и защита назначения

- Объяснить `from pathlib import Path`, объект `Path`, относительный путь от текущего `project/`, `resolve()` для сравнения нормализованных путей, `is_file()` для существующего обычного файла; передавать только разные адреса в выделенном каталоге. Оговорить, что проверка не заменяет защиту от сторонних изменений и не обнаруживает все варианты hard link; учебный каталог без одновременного доступа обязателен. Не открывать отсутствующий источник через обычный `sqlite3.connect`: тот способен создать пустую базу.
- Разобрать `Path.open("xb")`: `x` создаёт только новый файл, `b` задаёт двоичный режим; занятый путь вызывает `FileExistsError` без усечения. Закрыть файловый объект до открытия SQLite; `Path.read_bytes()` возвращает байты контрольного файла. `exists()` до записи не заменяет исключительное создание. Ошибку пути/доступа не представлять успешным результатом.
- Независимый пример в отдельном учебном каталоге `demo_backup/`: заранее подготовить `library.sqlite3`, новый `occupied.bin` с байтами `b'KEEP'` и свободное имя `library-copy.sqlite3`. Показать точные импорты, создание `Path`, сравнение `resolve()`, проверку `is_file()`, подготовку контрольных байтов через эксклюзивный `open("xb")` и `write(b'KEEP')` с закрытием, чтение байтов до/после отказа `open("xb")`, затем успешное резервирование свободного имени. Объяснить аргумент `write` и не использовать режим усечения для подготовки. Автор Stage 3 приводит полный исполняемый пример создания этих демонстрационных данных и ожидаемый вывод, включая почему занятый файл остаётся тем же.
- Собственная проба до практики: на другом синтетическом `demo_trial/` ученик сам выбирает существующий и новый адрес, получает отказ на заранее подготовленном занятом файле и сравнивает байты; новый путь создаётся один раз. При повторе на нём ожидается отказ. Вернуться к отличию `x` от `w`, если файл изменился; не пробовать на исходной базе.
- Переход: зарезервированное пустое имя ещё не содержит снимок, нужны два соединения.

## 03. Два соединения и Backup API

- Объяснить `import sqlite3`, `sqlite3.connect(path)` с аргументом пути и возвращаемым соединением; источник проверен до открытия, назначение уже эксклюзивно создано и закрыто. Указать `source_connection.backup(destination_connection)`: метод вызывается у источника, аргумент есть соединение назначения. Обычный контекстный менеджер соединения управляет транзакцией, но сам соединение не закрывает: показать явный `close()` в `finally` либо `contextlib.closing` с объяснением. Закрывать оба соединения также при исключении, в том числе если второе подключение не удалось.
- Полный независимый пример продолжает `demo_backup/`: создать маленькую SQLite `library.sqlite3` с таблицей книг и двумя известными строками, подтвердить их сохранение и закрыть соединение; выполнить проверку источника и адресов, занятую ветвь с контрольными байтами, затем на другом свободном имени резервирование `xb`, два соединения и `backup`. После закрытия открыть полученный снимок отдельным соединением, выполнить простой `SELECT` демонстрационных строк и закрыть его; отдельно перечитать исходник. Указать все импорты, аргументы, SQL создания/заполнения/чтения, `commit`, закрытие и ожидаемые строки. Пример использует другой сюжет и имена, а не готовый модуль Planner.
- Объяснить нормальное завершение без исключения: `backup` не возвращает код успешности и не защищает занятый путь. Проверка открытия и чтения показывает доступность полученного файла, но не доказывает полноту всех данных. Исключение в любом месте означает отсутствие подтверждённого снимка.
- Первая собственная проба: на другой маленькой синтетической базе ученик записывает вызов на двух соединениях после резервирования, открывает результат и видит заранее известную строку; меняет направление в мысленном прогнозе и объясняет ошибку. Возврат: метод принадлежит источнику, аргумент есть назначение; закрытие отделено от транзакционного `with`.
- Визуал: интерактивная трассировка с отдельными состояниями «занято», «создан пустой файл», «соединения открыты», «backup завершён», «файл открыт», «исключение». Действие ученика: выбрать следующий допустимый шаг и увидеть причину отказа; неверный выбор не раскрывает готовый проектный код. Отдельная обратная связь показывает, что файл после исключения не является подтверждённым снимком.

## 04. Отказ, закрытие и безопасное повторение

- Объяснить `try` / `finally` для закрытия ресурсов и `try` / `except` для понятного сообщения об ошибке; сообщение об успехе только после завершения backup и открытия снимка. Отсутствующий источник, одинаковый путь и занятое назначение останавливают работу до создания/изменения назначения. После ошибки уже зарезервированный новый файл может быть пустым или частичным: закрыть соединения, отметить путь как непригодный, не перезаписывать прежний файл, выяснить причину и повторить с другим новым именем. В этом занятии автоматическое удаление частичных файлов не требуется.
- Независимый пример: для демонстрационной базы источник отсутствует, затем занятая цель, затем намеренно вызванная ошибка после резервирования на отдельном новом пути. Показать, какой файл был создан самим опытом, что закрыто, что не передаётся и почему новый запуск выбирает другой путь. Не утверждать одинаковый вид частичного файла при всех сбоях.
- Собственная проба: ученик объясняет, что остаётся после ошибки до и после резервирования, и выбирает безопасный путь повтора. Проверка: занятая цель не меняется, созданный при неудаче файл не маркируется успешным. Возврат к порядку «проверка → резервирование → соединения → backup → закрытие → открытие».

Ожидание: отказ, байты идентичны, источник по описи не изменён; не принимать только сообщение об ошибке как доказательство сохранности. Помощь: сравнить `xb` с обычным открытием; разбор показывает путь исключения до подключения назначения.
4. **Получить снимок → проверить успешную ветвь.** Вход: тот же остановленный источник и другое ещё не занятое имя в учебном каталоге; опоры 03–06. Самостоятельно вызвать модуль с этими двумя аргументами, дождаться завершения без ошибки, открыть полученный файл отдельным SQLite-соединением и выполнить простое чтение, закрыть его. Результат: снимок открывается, исходные записи совпадают; при ошибке закрыть ресурсы и не передавать частичный путь, повторять только с другим новым именем. Помощь: различить файл, соединение и аргумент `backup`; будущий разбор прослеживает обе стороны вызова и результаты на независимой базе.

Эти действия последовательно защищают вход и существующий файл, создают отдельный снимок и проверяют сохранность исходника. Каждая проверка доступна до следующего действия; открытие снимка не заменяет последующее восстановление и сравнение. Существующие API/CLI и схема не меняются, а полная регрессия нетронутого Planner здесь не назначается. Нужные операции подготовки контрольных файлов, чтения байтов, SQL и команды снабжаются полным примером и собственной малой пробой до практики; реализация TSX и точные задания относятся к Stage 3.
