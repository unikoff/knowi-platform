## 01. Какие данные хранить о будущем пользователе

**Вопрос и новая способность.** Имя в запросе сообщает, кем человек представляется. Проверка секрета позднее подтвердит, что заявление можно принять; решение о доступе определит разрешённое действие. Из присутствия `role="admin"` в чужих данных нельзя получить подтверждённого администратора. Сейчас создаётся только место для будущих записей, без сервиса проверки секрета.

**Независимый пример границ.** На каталоге участников кружка показать три явно названных объекта: входные данные `handle="  BOOK-7  "`, внутренняя запись с `id/handle/private_marker/category`, общедоступная карточка `id/handle`. `private_marker="DEMO_ONLY_NOT_A_SECRET"` является учебной меткой, а не паролем. В полном примере Stage 3 каждый объект задан непосредственно перед использованием; вывод карточки показан и объяснён через явный выбор двух полей. Участник не присылает `category`, каталог определяет её сам. Это объясняет границу данных, не реализует регистрацию.

Провести сравнение с Planner: `login` понадобится как имя, `password_hash` как внутреннее поле будущего парольного модуля, `role` как внутреннее значение. Хеш нельзя возвращать даже при условии, что это не открытый пароль. Схема хранения и схема ответа отвечают на разные вопросы. Не обучать обработке настоящего пароля на фиктивной строке и не применять к нему правило имени.

**Учебный визуал вне 00.** Схема «вход → внутренняя запись → безопасная проекция» с отдельной неподвижной таблицей `tasks`. Данные: четыре User-поля, будущий password только на стороне будущего входа, стрелка к будущему hash-процессу с подписью о следующем блоке. В текущую запись поступает только синтетический `password_hash`. Действие ученика: проследить путь каждого поля и назвать, где оно появляется. Наблюдение: `role/password_hash` остаются внутри, в ответ идут только `id/login`, задачи пока ни с кем не связаны. Объяснение: наличие поля в БД не делает его публичным; стрелка к tasks появится только вместе с будущим владельцем. Схема не изображает уже работающую аутентификацию.

**Первая проба.** После примера ученик из внутренней записи другого участника с `private_marker` и `category="staff"` самостоятельно составляет безопасную карточку и объясняет исключение обоих полей. Критерий: ровно `id/handle`, без придуманного подтверждения личности. Возврат: явный выбор полей в примере, различие хранения и ответа. Переход: выбор полей понятен; теперь нужно определить, какие имена обозначают одну запись.

## 02. Одно правило имени до записи в базу

**Механизм.** Нормализация приводит допустимые варианты к одному значению; валидация отвергает недопустимое. Порядок важен: непустая строка ещё может иметь плохие символы. До самостоятельной записи разобрать проверку типа, смысл ASCII, удаление пробельных символов по краям, регистр, длину, перебор символов с проверкой принадлежности разрешённому набору, возврат и `ValueError`. Конкретные формы `str.isascii()`, `strip()`, `lower()` и условие длины объяснить на видимых значениях, а не перечислить как API. Регулярные выражения не являются обязательной новой темой: для этого договора достаточно знакомых условий и перебора.

**Полный независимый пример.** Один раз выбрать и создать свободный корень `project/scratch/member-schema-<свободный суффикс>/`, сохранить там member_contract_demo.py и из этого каталога запустить `python member_contract_demo.py` тем же Python. В 04 в этот уже выбранный корень добавится новый подкаталог history, а не повторное создание корня или перезапись файла. Полный исходник появляется в теории на Stage 3; сейчас файла у ученика нет. Правило каталога намеренно другое: строка ASCII, trim, uppercase, 4–12 знаков из `[A-Z0-9-]`. Показать `"  book-7  " → "BOOK-7"`, повтор уже канонического значения, слишком короткое `"A-1"`, внутренний пробел `"BOOK 7"`, None и Unicode `"ВOOK-7"`. Во всех случаях назвать вход, возвращённую строку либо отклонение, причину и следующий допустимый шаг. Для первого результата не нужны SQL, HTTP или файлы SQLite.

В этом же примере явно отвергнуть не-ASCII до преобразования регистра: Unicode-символ вроде `K` может превратиться в ASCII после `lower()`, но договор не разрешает такую подмену. При любой проверке с ошибкой исходное значение не становится исправленным именем. Пример закончен запуском и точным разбором вывода; он не содержит функции Planner или его набора ограничений.

**Точный договор собственного login.** Один публичный помощник `normalize_login(value: object) -> str` добавляется в существующий `project/app/validators.py`, сохраняя прежние Task-валидаторы:

- Принимается только строка; приведение числа/`None` к строке отсутствует.
- Любой не-ASCII во входной строке отклоняется, включая Unicode-пробел и похожие на латиницу символы. Это уточняет границу ASCII, а не разрешает транслитерацию.
- У допустимой ASCII-строки удаляются пробельные символы только по краям, ASCII-буквы приводятся к нижнему регистру; внутренние символы не удаляются и не заменяются.
- После нормализации длина 3–32 включительно, допустимы только `a-z`, `0-9`, `_`. Пустая строка, внутренний пробел, дефис, точка и иные символы отклоняются с `ValueError`.
- Результат повторной нормализации равен первому. Все будущие записи и поиск по login используют эту единую функцию; пароль не передаётся в неё.

Граница ASCII до trim означает, что неразрывный Unicode-пробел по краю также не принимается. Stage 3 показывает этот случай явно. Это служебный договор для согласования с repository, а не скрытое требование теста.

**Первая самостоятельная проба и снижение помощи.** После независимого кода ученик сначала прогнозирует результат для нового кода участника `"  club-9  "`, затем меняет только правило длины и проверяет граничный код без полной подсказки. В проектной практике он уже самостоятельно пишет функцию login с другим алфавитом, регистром и границами; готовая реализация этой функции в теорию не переносится. Ошибка «принимаю внутренний пробел после удаления всех пробелов» обнаруживается различающим примером.

**Содержательный интерактив вне 00.** Две связанные операции на независимом каталоге: выбрать «принять с каноническим значением / отклонить» для `" book-7 "`, `"BOOK-7"`, `"BOOK 7"`, `"ВOOK-7"`; затем распределить `id/handle/private_marker/category` между внутренней записью и публичной карточкой. Исходные данные и правило постоянно видны. Наблюдение: два допустимых написания получают один ключ, плохое имя не получает строки, скрытые поля не появляются в карточке. Обратная связь объясняет конкретный шаг правила, причину конфликта канонических значений или утечку поля. Она не выдаёт код normalize_login, UserRow или миграции Planner. При ошибке предложен изменённый случай, а не только повтор того же ответа.

**Опора для возврата.** В месте полного примера оставить порядок «тип/ASCII → края/регистр → длина/алфавит → результат либо отказ», значения до/после и различие изменения/проверки. Переход: единое имя готовит одно значение для хранения, но два одинаковых insert должна остановить сама БД.

## 03. Как новая таблица получает ограничения

**Механизм и независимый пример.** Продолжить каталог участников, не заводя второе приложение. В отдельной демонстрационной истории добавить таблицу `members(id, handle, category)` с UNIQUE handle, NOT NULL и CHECK category из `guest/staff`, SQL-default `guest`. Здесь нет password_hash и готовой User-модели. Полный пример показывает ORM-описание, соответствующее тело новой revision и наблюдаемую схему после её применения. Объяснить `Mapped`, `mapped_column`, `__tablename__`, `__table_args__`, `primary_key`, `nullable`, `UniqueConstraint`, `CheckConstraint`, `server_default` и форму списка ограничений внутри `op.create_table`. Прежний TaskRow служит ориентиром синтаксиса, не доказательством личного освоения.

Разобрать ограничения по причинным парам: PK определяет строку, NOT NULL требует значение, UNIQUE не допускает второй одинаковый хранимый ключ, CHECK ограничивает допустимую категорию. Нормализация действует до insert, UNIQUE сравнивает уже переданную строку и сам её не исправляет. Проверка «сначала SELECT» не подменяет UNIQUE; двухклиентский конфликт будет отдельным самостоятельным результатом следующей темы.

**Глубина примера и наблюдения.** `BOOK-7` и `CLUB-9` принимаются, повтор `BOOK-7` отклоняется; `category="owner"` отклоняется именно CHECK, NULL handle именно NOT NULL. Проверочные insert выполняются в отдельных явных транзакциях с безусловным rollback и закрытием соединения; для UNIQUE две одинаковые строки пробуются внутри одного такого scope. Сначала показать успешное наблюдение внутри scope, затем отсутствие пробных строк новым чтением после rollback. Это проверка ограничения, не сохранённый аккаунт. Полный независимый пример объясняет begin/execute/rollback/close и известные параметры SQL до переноса, не требует новых pytest-фикстур или savepoint. Сначала вручную прочитать фактическое ограничение, потом на том же случае показать, как проверочное утверждение сравнивает ожидание с результатом. Наличие произвольного исключения не доказывает CHECK; наблюдаемый SQLite-код/колонка отличают UNIQUE от другого отказа без написания универсального классификатора repository.

Python `default` не записывает SQL DEFAULT в DDL. Показать SQL-insert без category: именно server_default позволяет БД поставить guest; явный NULL не является пропуском значения. Default действует при INSERT, не при простом конструировании ещё не сохранённого ORM-объекта. Сравнить с Python-default в знакомом TaskRow. String(32) в SQLite не проверяет длину: границы login проверяет единая функция. В этом плане БД требует NOT NULL/UNIQUE для login; не обещается, что произвольный прямой SQL автоматически нормализует или валидирует его алфавит. Все штатные будущие writers обязаны использовать помощник.

**Договор самостоятельной User-схемы, до собственного upgrade.** В существующем `project/app/DBase/models.py` добавляется `UserRow(Base)`, `__tablename__="users"`; TaskRow не редактируется. Колонки: `id` INTEGER PK и явно NOT NULL; `login` String(32) NOT NULL, именованный `uq_users_login`; `password_hash` String без искусственного короткого лимита, NOT NULL; `role` String NOT NULL, SQL-default `'user'`, именованный CHECK `ck_users_role_allowed` с множеством `user/admin`. UNIQUE не дублируется отдельным уникальным индексом. Выбранные имена ограничений повторяются в ORM и ревизии. Ввод роли из публичного запроса и реальный hash-процесс здесь отсутствуют.

Безопасная проекция в этом шаге выражается уже знакомым словарём с явным выбором `id/login` из внутренней записи. Полный независимый пример показывает выбор `id/handle` и точный вывод, без копирования `__dict__`. В практике ученик составляет такую же проекцию User на синтетических значениях с известным id. Отдельный Pydantic-модуль, from_attributes и HTTP-router не создаются. Следующий принятый план repository самостоятельно оформит `user_to_public(row)`; этот план передаёт его точный состав полей, а не второй параллельный serializer.

**Первая проба.** По уже разобранному `members` ученик сам указывает, какое из трёх ограничений нарушит каждый изменённый insert, и пишет маленькое проверочное утверждение для категории вне разрешённого множества. В практике оставлены собственная ORM и договор её фактической схемы. Возврат: пары «операция → конкретное ограничение → неизменное число строк», различие Python/SQL default и пример двухполенной проекции. Переход: описание ORM пока не изменило файл SQLite; теперь нужен проверенный исполняемый переход истории.

## 04. Одна ревизия для двух исходных состояний

**Полный независимый опыт и его цена.** Продолжить малый книжный контур принятого плана исходной истории: его `.lesson-lab/baseline-demo/`, `book_stock(id, copies)` и revision `b_demo` уже конкретно запланированы. При выдаче подтвердить их наличие; при утрате использовать полный доступный пример поставщика, не выдуманный starter. Скопировать только его ini, env.py и `b_demo_book_stock_baseline.py` в отдельное свободное дерево `scratch/member-schema-<свободный суффикс>/history/`. Это демонстрационная история книг, не копия Task-DDL и не ещё один веб-сервис. Если применяется генерация revision, копируется script.py.mako; полный предъявленный файл можно сохранить без генерации. Источник каждого файла и новое script_location показаны до первого запуска. Сейчас эти ресурсы не объявляются уже созданными.

Минимальный воспроизводимый комплект: три перенесённых файла настройки/истории, один новый полный файл revision добавления `members`, уже сохранённый `member_contract_demo.py` и новый `member_schema_demo.py` с готовыми техническими режимами создания учебных строк, чтения/сравнения и изолированных insert. Итого шесть файлов, при необходимости переноса script template семь. Первый файл не перезаписывается поздней подготовкой. Код драйвера, импорты и режимы предъявляются полностью на странице Stage 3, без придуманного starter URL. Логика guard/backup/read берётся из уже запланированных полных примеров и не переписывается учеником заново. Автор проверяет, что env не вызывает runtime/create_all и что демонстрационные пути явно заданы. Подготовка не бесплатна: ученик переносит настройку, выбирает свободный каталог, получает два новых DB-файла и работает одним Python-процессом за раз; новых venv/зависимостей/HTTP-процессов нет. Первый полезный результат правила имени получен до этой настройки в одном файле раздела 02.

Две цели примера имеют разные явно сохранённые URL. Одна получает b_demo с пустой book_stock, другая ту же схему с книгами `id=7, copies=2` и `id=9, copies=0`. Данные создаёт объяснённый setup драйвера; пользовательская БД не читается. До расширения снять строки и схему. Новая revision создаёт только members, её parent равен b_demo. Затем отдельно открыть каждый существующий файл, подтвердить current и применить одну новую revision. Наблюдения: members/ограничения/default есть в обеих целях, все прежние значения book_stock сохранены; повтор upgrade ничего не добавляет. Предварительная проверка режима обновления отвергает отсутствующий файл до подключения Alembic. В 03 код ограничений и их наблюдения предъявляются как объяснённые фрагменты этого единого опыта; самостоятельный запуск целого примера следует только здесь, после видимой подготовки. Так до подготовленных файлов не требуется скрытый запуск.

**Что объяснить до переноса.** Файл истории и head отличаются от current конкретной БД. Новая revision содержит замороженные колонки/ограничения, не обращается к Base.metadata.create_all; исходная revision остаётся побайтно прежней. `python -m alembic revision -m "add users"` создаёт заготовку, её содержимое ученик пишет сам. В проектной практике сохраняется ручной путь и target_metadata=None. Autogenerate рассматривается на предъявленном кандидате как принцип: результат требует корректной metadata и ручного обзора. Его запуск и перенастройка env.py не обязательны. UNIQUE/CHECK входят в op.create_table, отдельный ALTER для них не нужен. История остаётся линейной, один parent и один head.

В примере обзор кандидата сравнивает желаемое изменение, ORM и текст revision до исполнения. Непредвиденный `drop_table`, изменение tasks, новый FK, импорт mutable metadata или отсутствие нужного CHECK являются причиной остановиться. Показать независимый неверный кандидат с изменением прежней tasks и вернуть ученику выбор: исправить кандидат до запуска, а не принять его по сообщению autogenerate.

**Проверка факта.** По существующим schema-read и описи прочитать `sqlite_schema`, table_info, index_list/index_info и SQL с CHECK/DEFAULT. На примере объяснить, как увидеть UNIQUE столбец и отличить его от обычного индекса, как проверить role/category default и что current сам по себе не доказывает наличие таблицы. На той же малой базе довести сравнение свойств до понятной проверки в тесте; будущий тест Planner не появляется впервые в решении. Имена автоматически созданных SQLite-индексов не фиксировать, сравнивать уникальность и набор колонок.

**init_db и код.** На S `create_schema()` вызывает `Base.metadata.create_all(engine)`. С добавлением User этот вызов мог бы молча создать users в базе без истории. Выбранный новый договор: прежняя явная команда `python -m app.DBase.init_db` завершает работу с ненулевым статусом и понятной инструкцией явного применения Alembic к выбранному URL, до открытия/создания SQLite. API/CLI также не выполняют upgrade при запуске. Объяснить `SystemExit`, ненулевой код завершения и проверку, что отсутствующий путь не возник. Это согласованный отказ, а не переписывание старого runtime во вторую точку миграции. Интеграционные проверки схемы создают её историей, не обходом этой команды.

**Первая проба.** Ученик на изменённом кандидате `members` сам находит лишнюю операцию, затем сверяет один фактический UNIQUE с ожидаемым и обосновывает отличие от простого current. К практике он приходит с навыком чтения кандидата и проверки результата, но без текста User-ревизии. Возврат: полный файл независимой revision, связь parent/current/head, пример чтения ограничения. Переход: успешный upgrade показал нужную B; теперь проверим, какое свидетельство остаётся после прерванного изменения.

## 05. Ошибка не определяет состояние базы

**Подготовленный отказ, а не поиск неисправности вслепую.** Продолжить тот же независимый опыт. После успешной revision `members` сохранить согласованный backup и перечень исправных файлов истории. Сделать отдельное одноразовое дерево конфигурации/версий, перепривязать его script_location и URL к отдельной восстановленной disposable копии. Только в этой истории добавить непубликуемую дочернюю revision: сначала создать явно демонстрационную таблицу `_failure_probe`, затем выполнить заранее показанный `raise RuntimeError(...)`. Нужные вызовы/исключение и порядок полностью разобраны до практики. Оригинальная история не получает ошибочную revision, успешные применённые файлы не редактируются.

Причину отказа можно предсказать, но состояние после него нужно читать. SQLite поддерживает транзакции, однако поведение DDL зависит от драйвера/режима транзакции; нельзя обещать универсальный откат всех DDL только по исключению. Проверить три независимых результата новым соединением: фактическую схему (есть ли `_failure_probe`), revision (осталась ли успешная или получено другое состояние) и все прежние строки. В full-примере автор фиксирует версии Python/sqlite3/SQLAlchemy/Alembic и реальный вывод. Если режим даёт откат DDL, объяснить именно этот результат; если таблица осталась, объяснить, почему метка не равна полной схеме. Ученика не заставляют получить искусственно заданный след конкретного драйвера.

**Восстановление согласованного состояния.** Ошибочная БД остаётся закрытой и помеченной непригодной к продолжению. Никакого повторного upgrade, stamp успешной/head или ручного удаления таблицы ради «зелёного current». Сохранённый до отказа backup восстанавливается методом уже подготовленного restore в ещё один новый путь. Результат проверяется по целостности, всем строкам, схеме и ожидаемой успешной revision; запуск выполняется с исходным исправным набором миграций без одноразовой дочерней. Так код модели, доступная история и восстановленная БД соответствуют одному успешному состоянию. Применять старую сборку к новой схеме или новую сборку к baseline без upgrade не предлагается.

**Первая проба.** По двум наблюдениям, например «current прежний, probe осталась» и «current прежний, probe отсутствует», ученик сам формулирует, какие части согласованности уже известны и почему ни один вариант не разрешает слепой повтор. Затем выбирает новый свободный адрес и правильное дерево истории для восстановления другого учебного экземпляра. Критерий: согласованность подтверждена отдельно, исходный backup и ошибочный экземпляр не затронуты. Возврат: три свидетельства после ошибки и restore независимого каталога. Переход: в проектной работе те же действия применяются к собственному User-расширению.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** изменение существующего Planner в редакторе/терминале. Вход планируется паспортами истории и восстановления; задача не выполняется на единственной пользовательской БД.

1. Зафиксировать исходные ресурсы и значения → две проверенные рабочие baseline и опись до изменения.
2. Самостоятельно написать правило login → одно каноническое значение либо понятный отказ на недопустимом входе.
3. Описать ORM и безопасную проекцию → согласованный контракт четырёх внутренних и двух публичных полей.
4. Написать и прочитать новую ревизию, согласовать init_db → кандидат без изменений tasks и без скрытого создания схемы при запуске.
5. Применить одну историю к обеим копиям и проверить ограничения/Task → одинаковая User-схема, прежние задачи и рабочие API/CLI.
6. Выполнить объяснённый отказ на disposable копии и восстановить новый экземпляр → установленное состояние ошибки и пригодная согласованная передача.

После списка связать результат: правило определяет данные, модель описывает строку, ревизия создаёт её хранилище, две траектории проверяют воспроизводимость, а восстановление позволяет продолжить работу после отказа. При затруднении путь возврата конкретен: правило в 02, ограничения/проекция в 03, история в 04, отказ/restore в 05. Список на странице остаётся кратким мостом; подробные карточки ниже создаются Stage 3 в ручной проектной практике и видны до раскрытия разбора.

### Практическая карточка E. Проверить одну историю на двух траекториях

**Контекст.** Подготовленный кандидат ещё не применён, данные до изменения сохранены. Новая таблица полезна только если её фактическая схема соответствует договору в обеих историях происхождения.

**Условие.** При остановленных писателях отдельно подтвердить существование и current каждой рабочей цели, затем применить одну User-revision к new.sqlite3 и filled.sqlite3. Снять схему/current/строки новыми соединениями и сопоставить с описью. На обновлённой новой цели проверить ограничения синтетическими insert в объяснённых отдельных rollback-scope, без сохранения пробных User. Затем проверить обычное чтение задач в API/CLI на обновлённой заполненной цели. Не запускать приложение новой версии на ещё не обновлённой baseline.

**Объект и опора.** Две существующие рабочие копии, исполняемая revision и `tests/test_user_schema.py`; 03 готовит ограничения/проверочные утверждения, 04 готовит применение/чтение, A готовит обычные Session/API/CLI. Самостоятельная работа: применить собственный переход, построить сравнение факта с договором и объяснить конкретные причины отказов. Пример members не содержит тела этих проверок Planner.

**Технические критерии.** Оба current равны User-revision. Схема users соответствует ORM/ревизии по колонкам, PK, nullable, UNIQUE login, CHECK роли и SQL-default; повтор upgrade оставляет данные/метку прежними. Исходная tasks целиком сохранена по схеме и всем ID/значениям, не только числу строк. Проверки фиксируют именно ожидаемые ограничения: допустимые канонические имена проходят; повтор одного нормализованного значения отвергается UNIQUE; `role="operator"` отвергается CHECK; отсутствие обязательного login/hash отвергается NOT NULL; пропуск роли в SQL получает `user`. Случай с `NULL role` отвергается, а не подменяется default. Синтетические значения hash имеют явные имена `SCHEMA_ONLY_NOT_A_HASH_A/B`, не используются в login или реальной регистрации.

Произвольный raw SQL не является штатным writer: проверка длины/алфавита остаётся в normalize_login, String(32) не выдаётся за SQLite-валидацию. Проверка двух эквивалентных имён сначала нормализует их, затем вставляет одно и то же хранимое значение. Она не подменяет будущий двухклиентский repository-сценарий. Каждый отрицательный insert изолирован, rollback и закрытие ресурса явно показаны прежней/текущей опорой; просто пойманное «любое исключение» не засчитывает UNIQUE.

**Локальная готовность и самопроверка.** Ученик может указать строку schema-read для каждого свойства, видит новую Session после операций и сравнивает tasks с сохранённым «до». API и CLI последовательно читают обновлённую filled по тому же явному URL; их публичные Task-поля прежние, tags остаются внутренними и сравниваются SQL-чтением. В обеих передаваемых БД users пуста: каждый пробный insert завершён rollback, это явно проверено свежим соединением. Tests/test_user_schema.py проверяет чистый нормализатор/описание; отдельные SQL-пробы используют уже разобранную транзакционную обвязку, новые fixtures/БД не собираются. Новых требований к полному CRUD-регрессионному набору нет; берутся затронутые проверки схемы, нового init_db и прежнего запуска/чтения. Если прежние тесты завязаны на явный create_schema, обновляется именно их предпосылка на явную историю. Локальная ручная проверка не выдаётся за платформенную автопроверку БД ученика.

**Помощь и будущий разбор.** Подсказка сначала отличает уникальный индекс от обычного и current от DDL, затем возвращает к изолированным insert каталога. Будущий разбор показывает два набора команд/наблюдений с настоящими URL, точную сверку полей и работу каждого ограничения. После готовности создаётся защищённый `user-head.checkpoint.sqlite3`; его опись включает revision и отсутствие фиктивных аккаунтов. Это вход следующей карточки, а не новый backup-алгоритм.

### Практическая карточка F. Выяснить след ошибки и восстановить новый экземпляр

**Контекст.** Исправные working-копии и история готовы, сохранён успешный head-checkpoint. Проверка отказа нужна, чтобы сообщение об ошибке не стало основанием для слепого повторения миграции.

**Условие.** В новый `failed.sqlite3` восстановить head-checkpoint. Скопировать исправную конфигурацию/versions в `failure-history`, явно сменить script_location/URL и добавить только там объяснённую одноразовую дочернюю revision из 05. Предсказать место отказа, запустить один раз, записать фактическую схему/current/данные новым соединением. Закрыть ошибочную цель. Восстановить из того же успешного checkpoint другой новый `recovered.sqlite3`, проверить его и подключить Planner с исходным исправным деревом истории.

**Объект и опора.** Новые адреса failed/recovered, одноразовое дерево истории и успешный backup; полное независимое продолжение раздела 05 и планируемая A restore. Самостоятельно: выбрать допустимые пути/кодовую конфигурацию, установить фактическое состояние по трём свидетельствам и обосновать возможность запуска восстановленного экземпляра. Полный код намеренного отказа разрешено дать готовым после объяснения: B требует диагностику/восстановление, не изобретение поломки.

**Технические критерии.** Отказ воспроизведён только на disposable цели. Основная история, исправные working-копии и backup неизменны. После отказа сохранены наблюдаемые схема, revision и все прежние данные либо конкретная ошибка их чтения; неизвестный результат не назван успешным rollback. `_failure_probe` может сохраниться или отсутствовать согласно наблюдаемому режиму DDL, это не критерий угадывания конкретного драйвера. Ошибочная копия не получила фиктивный stamp и не использована для повторного upgrade. Новый recovered проходит проверку целостности, схемы users/tasks, успешной User-revision и содержимого checkpoint; основной исправный код не содержит одноразовой revision.

**Локальная готовность и различающий случай.** Наблюдения «ошибка была» и «данные/схема согласованы» разнесены. На recovered API/CLI новым процессом читают те же Task; users не содержит фиктивных аккаунтов. В state.md указаны рабочий URL и исправная история, путь failed явно исключён из передачи. Если один путь занят, исходные байты остаются прежними и выбран новый свободный адрес. Ученик объясняет, почему current успешного checkpoint вместе с теми же schema/data и правильной историей позволяет продолжить, а один current после отказа не позволяет.

**Помощь и будущий разбор.** Первая подсказка возвращает к трём свидетельствам после ошибки, вторая к выбору отдельного restore-назначения и правильного дерева кода. Будущий разбор покажет реальные следы отказа на закреплённых версиях и полный путь восстановления без ремонта ошибочной БД. В нём нет нового способа rollback, скрытого в ответе.
