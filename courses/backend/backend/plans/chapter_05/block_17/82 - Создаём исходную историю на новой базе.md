## 01. Выбираем пустую цель и различаем историю, схему и метку

Начать с действия практики: создать исходную tasks, не трогая ни одной сохранённой задачи. Объяснить три независимых объекта: Python-файлы ревизий хранят порядок изменений; таблицы SQLite имеют фактическую структуру и данные; `alembic_version` хранит метку применённого шага. Наличие любого одного не доказывает двух других. Revision есть стабильное имя шага, parent задаётся `down_revision`; `None` означает отсутствие родителя. Head есть конец файловой истории; current читается из выбранной БД. Пока одна цепочка и один head.

Учебный визуал вне 00: три колонки «файлы», «структура и строки», «метка» для независимого книжного реестра. Данные: отсутствующий файл БД, созданная таблица `book_stock`, метка `b_demo`; стрелка upgrade ведёт от файла ревизии к DDL и метке, стрелка stamp только к метке. Наблюдение: одинаковая метка на двух карточках не гарантирует наличие таблицы. Объясняющая подпись связывает разницу с отсутствием DDL у stamp. Действие читателя: проследить две стрелки и назвать, какое наблюдение ещё нужно. Форма схемы выбирается на Stage 3.

Явно сменить прежний режим «открываем только существующий источник» на новый «создаём собственную пустую цель». Не убирать защиту backup-wrapper: он здесь не вызывается. На простых абсолютных путях показать `Path.resolve()`, сравнение с защищёнными адресами и `Path.touch(exist_ok=False)`: новая пустая цель резервируется исключительно, занятый путь даёт отказ до подключения. Разобрать отсутствие родительского каталога и занятое имя; не удалять файл, чтобы повторить команду. Пустая БД в этом плане означает отдельный новый файл без пользовательских таблиц и метки, а не очищенную восстановленную копию. Все соединения закрываются до смены файла; в каталоге опыта нет других писателей.

Первая проба: из четырёх подписанных адресов (исходник, backup, восстановленная копия, свободный путь) ученик выбирает цель, резервирует её и при повторной попытке видит отказ. Этот файл станет `books.sqlite3` примера. На изменённом наборе подписанных адресов ещё раз выбирает допустимую роль без создания дополнительного файла. Опора при возврате: роли путей, форма исключительного создания, смысл отказа. Теперь можно дать инструменту только этот явный URL.

## 02. Настраиваем один малый миграционный контур

Спроектировать один полный воспроизводимый пример с `book_stock(id, copies)`, не Task и не второй CRUD-проект. Сюжет: воспроизводимый склад экземпляров; `id` целый PK/NOT NULL, `copies` целый NOT NULL с SQL-default `1`, именованный CHECK `copies >= 0`. Исходное состояние: свободный каталог `.lesson-lab/baseline-demo/` внутри ученического `project/`, тот же активированный venv; в нём нет БД, модели или приложения. При занятом каталоге выбрать новое имя и последовательно подставить его во все пути. `.lesson-lab/` создаётся явно, без скачиваемого starter и вымышленного URL.

До команд разобрать терминал против Python-интерпретатора, текущий каталог, кавычки и смысл `python -m`: исполняется модуль выбранного Python. Сначала показать `python --version`, `python -m pip --version`; затем объяснённая `python -m pip install "alembic==1.20.1" "SQLAlchemy==2.0.55"` и `python -m alembic --version`. В текущем Stage ничего не устанавливается. Если входной Python ниже 3.10 или зависимости не согласованы, установка не продолжается вслепую, сначала восстанавливается окружение проекта. В будущей практике Alembic добавляется в существующий requirements, прежние pins сохраняются.

Из каталога примера выполнить `python -m alembic init migrations` и до редактирования раскрыть назначение каждого результата:

| Файл/каталог | Что объяснить и что делает ученик |
| --- | --- |
| `alembic.ini` | `script_location = %(here)s/migrations` указывает на историю рядом с ini; `%(here)s` есть каталог ini. `prepend_sys_path` относится к импортам, `path_separator = os` оставляется с объяснением, что пути разделяет ОС. `sqlalchemy.url` задаёт одну явную цель. Логирующие секции стандартного шаблона сохраняются |
| `migrations/env.py` | Стандартная конфигурация Alembic, выполняемая в нужных командах. `fileConfig` настраивает логирование; `engine_from_config` читает настройки с префиксом `sqlalchemy.`; `pool.NullPool` не удерживает соединения между выдачами; `context` связывает конфигурацию, соединение, миграцию и метку |
| Ветви online/offline в env.py | Online открывает соединение, передаёт его `context.configure`, затем `begin_transaction`/`run_migrations` исполняют нужный шаг. Offline выводит SQL без подключения; эту ветвь объяснить при чтении шаблона, не требовать самостоятельного расширения |
| `target_metadata = None` | Для написанной вручную baseline достаточно явных операций. Приложение и Base сюда не импортируются. Для autogenerate нужна metadata, её роль позже сравнить с историей; писать дополнительный демонстрационный ORM-файл не требуется |
| `migrations/script.py.mako` | Шаблон будущего Python-файла, а не уже применённая миграция. Mako не изучается и шаблон не переписывается |
| `migrations/README`, `migrations/versions/` | Сгенерированная справка и место файлов истории; само наличие пустого каталога таблиц не создаёт |

В ini указать явно показанный абсолютный SQLite URL на предварительно зарезервированный `books.sqlite3`. Для Windows разобрать форму `sqlite:///C:/.../books.sqlite3`, для POSIX `sqlite:////.../books.sqlite3`; использовать простой синтетический путь без `%`, URI-параметров и сети. Пробел в пути не заменять другим адресом. Настройка Alembic намеренно независима от `.env`/DATABASE_URL приложения: чтения `.env` в стандартном env.py нет. Изменение `$env:DATABASE_URL` само по себе цель Alembic не меняет. Перед каждым подключением ученик читает фактический `sqlalchemy.url` и сверяет с описью путей.

Первое полезное наблюдение до DDL: файлы конфигурации созданы, `python -m alembic heads` не показывает ревизий; БД пока без таблиц. Ученик сам объясняет, почему установленный инструмент ещё не создал схему. При ошибке имени драйвера или неверном `script_location` возвращается к соответствующей строке ini, а не меняет Python проекта.

Цена подготовки: один новый корневой каталог опыта, один каталог migrations и вложенный versions; init генерирует четыре файла (ini, env.py, README, mako), revision позже пятый. Один SQLite-файл, один venv, ни одного API-процесса/сервера, дополнительной модели/проверяющего модуля/пакета нет. Ученик вручную выбирает каталог, резервирует цель, меняет две значимые настройки ini, читает env.py и пишет одну двухколоночную ревизию. Чтение схемы и insert проводятся в короткой открытой Python-сессии с полностью показанной обвязкой. В 04 к ней добавляется краткий опыт с одной SQLite в памяти для отличия defaults; новых файлов он не требует. Это реальная подготовка до первого результата, её нельзя оставить необъяснённой копией файлов.

Опора для возврата: таблица ролей файлов и разобранный путь online. Переход: пустую структуру инструмента теперь наполним исполняемым шагом.

## 03. Записываем и применяем исходную ревизию

Продолжить тот же полный книжный пример до результата, без внешнего starter. `python -m alembic revision --rev-id b_demo -m "book stock baseline"` создаёт `migrations/versions/b_demo_book_stock_baseline.py`. Разобрать `revision`, `down_revision = None`, `branch_labels`/`depends_on = None` как оставленные служебные значения одной цепочки. Сгенерированные type hints и typing-импорты объяснить как описание типов служебных идентификаторов, они не запускают DDL. `from alembic import op` даёт операции текущей миграции, `import sqlalchemy as sa` даёт типы/описания колонок и ограничений; `sa` только короткое имя модуля.

Stage 3 показывает полный независимый upgrade книжного примера: `op.create_table`, `sa.Column`, `sa.Integer`, `primary_key`, `nullable`, `server_default`, `sa.CheckConstraint` и `name`. Объяснить позиционные аргументы, именованные параметры, кавычки SQL-выражения и разницу описания операции и её исполнения. Не использовать `Base.metadata.create_all` и импорт текущей ORM-модели. Ревизия есть снимок DDL на момент её создания: будущая новая модель не должна изменять смысл `b_demo`. Для downgrade явно обозначить границу: команда не используется; в учебной baseline тело даёт понятный `RuntimeError` о неподдерживаемом удалении исходной схемы. Разобрать `raise RuntimeError` с текстом как явный отказ операции; пустой `pass` не означает выполненного отката.

До команды предложить прогноз: `revision` изменил Python-файлы, таблицы ещё нет. Затем `python -m alembic upgrade head`; показать новую таблицу и ровно одну строку `alembic_version`, прочитанные с новым соединением. `python -m alembic history`, `heads`, `current` разобрать на этой одной цепочке: history перечисляет связи файлов, heads показывает конец, current читает выбранную БД. Эти команды не взаимозаменяемы; `current` может открыть файл, поэтому не используют его для проверки существования источника. Объяснить, что сообщение успешной команды не заменяет чтения структуры.

Полное наблюдение примера: sqlite_schema и PRAGMA подтверждают обе колонки/PK/NOT NULL/SQL-default/CHECK; допустимая запись с пропущенным `copies` получает 1 благодаря SQL-default, явный 0 допустим, -1 даёт ошибку CHECK. После отдельного rollback прежние записи сохраняются; исключение не выдаётся за успешный insert. В 05 тот же образец доводится до повторного upgrade и чтения новой Session. Прямое соединение закрывается явно: sqlite3 context-manager сам по себе не обещает закрытия.

Первая собственная проба до Planner: на той же книжной схеме ученик сам выбирает свободные положительные ID и записывает проверочные insert для `copies=4` и `copies=-2`, заранее предсказывает результат, сравнивает и объясняет отказ. Повтор на другом отрицательном значении проверяет причину, не запоминание -1 из примера. Ревизия и CHECK при этом не меняются; после rollback ошибочная запись отсутствует. Книжные файлы не входят в проектную историю. Проверенная и принятая baseline сохраняет смысл; будущие изменения схемы потребуют нового шага. Файл-кандидат до проверки ещё не объявлен достоверной baseline и не передаётся соседу.

Содержательный интерактив вне 00: два независимых виртуальных книжных состояния: пустая БД без таблицы/метки и готовая `book_stock` без метки. Ученик выбирает исходное состояние, действие `upgrade b_demo` либо `stamp b_demo`, отдельно предсказывает таблицу, строки и метку, затем запускает модель перехода. Обратная связь: на пустой upgrade создаёт таблицу и метку; stamp пишет метку, но не создаёт `book_stock`; на уже готовой таблице upgrade с CREATE конфликтует, а stamp ничего не доказывает о соответствии. Нельзя предлагать исправлять это через слепой stamp. Ошибочное предсказание получает причину по конкретной изменившейся/неизменившейся части, а не только «неверно». Это симуляция, ни один реальный stamp ученик здесь не запускает. Она не содержит Task-DDL и решения практики.

Опора при возврате: ревизия описывает DDL, upgrade выполняет необходимые шаги, stamp только утверждает метку. Переход: такую же исполняемую историю ученик запишет для уже известной исходной схемы Planner.

## 04. Переносим механизм на исходную Task-схему

Открыть реальный `project/app/DBase/models.py` на S и исходную schema-опись, не менять их и не показывать готовую Task-ревизию. Опись должна согласоваться с моделью, иначе остановиться до DDL. Ниже спецификация исходной структуры для автора и видимое требование практики, не готовое решение:

| Колонка | Тип в TaskRow / существенное DDL-свойство | SQL-default | Клиентский default, остающийся в модели |
| --- | --- | --- | --- |
| `id` | Integer, PK, NOT NULL | отсутствует | отсутствует |
| `title` | String, NOT NULL | отсутствует | отсутствует |
| `priority` | Integer, NOT NULL | отсутствует | `2` |
| `is_done` | Boolean, NOT NULL | отсутствует | `False` |
| `tags` | JSON, NOT NULL | отсутствует | `list`, вызывается для новой коллекции |
| `title_normalized` | String, NOT NULL | отсутствует | отсутствует |

Обязательны `ck_tasks_id_positive`: `id > 0`; `ck_tasks_priority_range`: `priority >= 1 AND priority <= 5`. Нет User, owner, description, FK, отдельного UNIQUE, пользовательских индексов и триггеров. PK учитывается отдельно от дополнительных индексов. Сопоставлять SQLite DDL/PRAGMA семантически, не требовать побайтового равенства SQL, регистра слов и пробелов. У Boolean на S нет дополнительного SQL-CHECK `IN (0, 1)`; не добавлять его как улучшение. Тип JSON сохраняется как в SQLAlchemy SQLite, без выдуманного CHECK валидности JSON.

На книжном примере сравнить `server_default="1"` с клиентским `default=1`: первый попадает в CREATE TABLE и работает даже для сырого SQL, второй подставляет SQLAlchemy при подходящем INSERT и не появляется в DDL. SQL DEFAULT NULL и отсутствие DEFAULT не объявлять равными. Полный малый фрагмент до действия открывает отдельную `sqlite3.connect(":memory:")`, явно создаёт `stock_probe(id INTEGER PRIMARY KEY, copies INTEGER NOT NULL)` без DEFAULT и делает прямой insert только с новым id: ожидается NOT NULL. После rollback выполняется insert с обоими полями, чтение показывает переданное copies; соединение закрывается. Рядом дать понятную форму клиентского `default=1` и показать, что она отсутствует в этом DDL. Дисковый книжный реестр с SQL-default при пропуске copies ранее получил 1. Это два законченных различающих наблюдения без второй миграционной среды.

Затем ученик сам классифицирует три Task-defaults и прогнозирует, почему сырой insert без priority не должен незаметно получить 2. Не переносить defaults модели в `server_default` ревизии. Разобрать `sa.String`, `sa.Boolean`, `sa.JSON` как те же типы из TaskRow, записанные через объяснённый alias sa: строка, булево значение, сериализуемое JSON-значение; не приписывать им новых SQL-ограничений. В коротком разборе значения вне БД сопоставить Python-список `["book"]` и строку JSON `'["book"]'`: в параметр сырого SQL передают заданный JSON-текст, а не Python-список. Нового поля в книжной таблице или библиотеки сериализации для этого не требуется. Исходная модель сохраняет своё прикладное поведение без изменения.

Autogenerate объяснить как сравнение целевой metadata и выбранной БД, выдающее файл-кандидат. В основном пути baseline пишется вручную; для знакомства дать отдельный небольшой кандидат книжного DDL с пропущенным/изменённым CHECK и попросить сверить с условием. Не заявлять, что любая версия autogenerate никогда не видит CHECK: текущие версии имеют ограниченные возможности, выражение и полноту всё равно проверяет человек. В этом уроке не включают plugins и не требуют второго ORM-файла. В будущей конфигурации можно подключить Base.metadata для получения кандидата, но файл исходной ревизии всегда содержит явные операции и не вызывает изменяемую модель. Именно исходная опись S определяет требуемую историю.

Собственная микрооперация: ученик находит в предложенном независимом кандидате, какое обязательное свойство потеряно, и называет наблюдение, которое это обнаружит. Возврат: таблица исходной схемы, различие default/server_default, пример ручного CHECK в 03. Переход к контролю двух новых целей сохраняет одну собственную Task-baseline.

## 05. Проверяем воспроизведение и повтор

Сначала завершить независимый книжный пример полным чтением результата и повтором. Показать объяснённый Python-фрагмент с `sqlite3.connect` для собственной уже существующей цели, `execute`/параметрами/`fetchall`, чтением sqlite_schema, `PRAGMA table_info`, `index_list` и `foreign_key_list`; отметить смысл полей PK/notnull/dflt_value, отделение служебной `alembic_version`, отсутствие дополнительного индекса/FK как осмысленный результат. Эта короткая форма продолжает schema-read поставщика; при пробеле вернуться к его полному книжному примеру. Ошибка insert требует rollback, а не последующего commit ошибочного состояния. Не собирать автоматический универсальный schema-comparator.

Новую метку прочитать также SQLAlchemy Session: разобрать `create_engine`, `Session(engine)` как отдельный контекст, `text("SELECT version_num FROM alembic_version")`, `session.execute(...).scalars().all()` как список значений одной колонки; контекст закрывает Session, затем engine освобождается. Объяснить `text` для явного SQL и почему чтение открытой ранее ORM-коллекции не доказывает запись на диске. На книжном примере новая Session видит список из `b_demo`, повтор `upgrade head` сохраняет одну метку и контрольную строку. Новый Python-процесс читает тот же файл, не память прежней Session. Это полная наблюдаемая опора, не готовый проверяющий модуль.

Первое самостоятельное наблюдение: ученик до повторного upgrade записывает контрольную книжную строку и метку, прогнозирует отсутствие CREATE и сравнивает после. После ошибки сравнения сверяет URL и открывает новый процесс, не удаляет version table. Нормальный повтор есть отсутствие новых DDL/строк/меток, а не обещание, что upgrade исправит самовольно повреждённую таблицу.

Для Planner схема проверяется на обеих новых БД. На первой сохранить одну синтетическую контрольную строку для проверки повтора; на второй чтение/проверочные вставки не оставляют строк, она остаётся чистым baseline-образцом. В обоих случаях исходные данные Planner не копируются. Проверка ошибочной записи и rollback отделена от уже сохранённой контрольной строки. На модели S Python-defaults остаются, но прямой SQL не подставляет их. Если upgrade завершился ошибкой, состояние DDL/метки не объявлять автоматически откаченным: прочитать фактический результат, пометить цель неэталонной и остановить перенос. Это не повод ставить метку вручную.

Опора при возврате: что сравниваем до/после, где взят адрес, какая ошибка ожидается и что читается новой Session. Переход к самостоятельной практике: ученик уже видел весь инструментальный путь на двухколоночном реестре и теперь сам собирает его для реальной схемы.

## 06. Что мы будем делать в практике

**Формат и контекст.** Изменение проекта в редакторе/терминале. У Planner уже есть проверяемый резерв и восстановленная рабочая копия; теперь нужно уметь создать исходную структуру без копирования готовой БД. Вход пока проектный: результаты поставщиков фактически подтверждаются перед выдачей. Работать в ученическом `project/`, не в исходниках платформы курса. Выданного Task-решения, starter-архива или готового migration-wrapper нет.

**Видимое условие.** Сохраните исходный файл, backup и восстановленную заполненную копию. Создайте рядом с приложением собственную конфигурацию и первую ревизию, которая строит именно исходную Task-схему. Примените одну и ту же историю к двум новым пустым SQLite, проверьте не только метку, но и структуру/ограничения, затем повторите upgrade и убедитесь, что сохранённая проверочная запись осталась прежней. Запишите фактические адреса и результаты чтения. Заполненную копию в этом задании не маркируйте и не используйте как цель upgrade.

**Место результатов.** В существующий `project/README.md` добавить короткий раздел «Исходная история схемы»: роли и фактические URL всех файлов, `p0001`, исходная schema-опись или ссылка на её ранее сохранённое место, наблюдения до/после и команды воспроизведения. Это рабочая опора для следующего действия, не отдельный большой отчёт. Имя исходной описи не придумывается: ученик указывает своё существующее место из резервирования.

1. **Отделить новые цели от сохранённых файлов.** Вход: собственная schema/data-опись и три защищённых адреса из восстановления; объект: новые пути `project/data/baseline-new-a.sqlite3` (E1) и `project/data/baseline-new-b.sqlite3` (E2). Опоры: входные паспорта, 01 и разобранная настройка 02. Самостоятельно: назвать роли, проверить абсолютные пути, убедиться, что они различны и не совпадают с защищёнными, исключительно зарезервировать оба отсутствовавших файла без пользовательских таблиц. При занятом имени выбрать новый свободный суффикс, записать его и использовать везде; не перезаписывать и не удалять занятое. Локально готово: записаны пять различимых ролей (исходник, backup, восстановленная копия, E1, E2), E1/E2 новые; повтор резервирования даёт отказ, неизменность защищённых файлов не нарушена. До этого этапа никакая migration-команда к БД не исполняется.
2. **Настроить проектный контур.** Вход: успешная малая книжная проба и те же согласованные Python/venv; объект: `project/requirements.txt`, `project/alembic.ini`, `project/migrations/`. Опора: 02, все роли файлов/импорты/две настройки ini уже объяснены. Самостоятельно: добавить pin Alembic 1.20.1 без изменения прежних pins, создать стандартное окружение из корня project, настроить путь scripts и явный URL E1, прочитать стандартный env.py и объяснить online-путь. Новые файлы создаются только при свободных именах; неожиданная существующая история требует выяснения, не повторного init поверх неё. `target_metadata = None` остаётся сознательным выбором ручного пути; app/main, app/api и init_db в env.py не импортируются. Локально готово: нужный Python видит Alembic, ini указывает E1, каталог versions пока пуст, `heads` не показывает ревизий; никакая tasks ещё не создана. Файлы книжного опыта не копируются в проект как его история.
3. **Самостоятельно записать Task-baseline.** Вход: TaskRow S и совпавшая исходная опись; объект: собственный файл `project/migrations/versions/p0001_tasks_baseline.py`, созданный `python -m alembic revision --rev-id p0001 -m "tasks baseline"`. Опоры: 01/03 дают форму ревизии и DDL; 04 даёт требования реальной схемы и различие defaults. Самостоятельно: заполнить upgrade явными операциями для шести колонок и двух CHECK, проверить полноту против описи, оставить единственного родителя `None` и один head. Полный Task-DDL не дан в starter/теории/интерактиве. Изменяемая metadata, `create_all` и runtime-функции не вызываются из ревизии; исходный TaskRow не редактируется. Downgrade явно отказывает понятной ошибкой, удаление исходной схемы не исполняется. Локально готово до применения: файл читается как самостоятельное описание исходной схемы, `history` показывает один корневой шаг, `heads` показывает `p0001`, E1/E2 по-прежнему без tasks/метки. Объяснить, почему сгенерированный файл сам по себе не подтверждает состояние БД.
4. **Получить и проверить две схемы.** Вход: проверенная исходная ревизия и E1/E2; объект: сначала E1, затем E2. Опоры: 03–05 и schema-read из входной описи. Самостоятельно: перед каждым upgrade сверить фактическую цель ini; применить историю к E1; новым соединением снять структуру, сравнить с S, затем закрыть соединения, явно переключить ini на E2 и повторить без редактирования baseline. Проверить все признаки таблицы из 04, не ограничиваться совпадением E1 с E2: одинаково неверные схемы B не доказывают. Локально готово: обе БД воспроизвели шесть нужных колонок, PK, NOT NULL, отсутствие SQL-defaults, оба именованных CHECK, состав индексов/FK/прочих объектов; в каждой ровно `p0001`. На E1 записать и отдельно commit контрольную строку: `id=2001`, `title="Baseline check"`, `priority=5`, `is_done=0`, `tags=["baseline-check"]` в корректном JSON-представлении, `title_normalized="baseline check"`. На каждой цели известная ошибочная запись с новым `id=2002`, остальными теми же непустыми полями и `priority=0` отвергается именно CHECK, а не PK; после rollback не появляется. Следующий сырой insert с новым `id=2003`, остальными обязательными полями и пропущенным priority отвергается NOT NULL, поскольку серверного default нет; после него отдельный rollback. Проверки на E2 не оставляют строк; она сохраняется как пустой образец исходной схемы.
5. **Проверить повтор и передать наблюдаемый результат.** Вход: обе применённые БД, сохранённая строка E1 и записи наблюдений; объект: та же ревизия и оба прежних URL. Опора: 05, полный независимый повтор/новая Session. Самостоятельно: для каждой цели повторить `upgrade head`, закрыть соединения, новой Session прочитать version; новым Python-процессом повторить чтение строки E1. Сравнить все шесть значений с записью до повтора, не только количество. Проверить, что E2 пуста, схемы и единственные метки прежние. В рабочей восстановленной копии обычным ранее освоенным чтением проверить сохранённые ID/поля против входной описи; приложение всё ещё использует её явный DATABASE_URL, а не E1/E2. Локально готово: повтор не создал строк/нового шага и не изменил контрольную строку; исходник, резерв и восстановленная копия сохранились. Объяснить на различающем книжном случае, почему один stamp не дал бы этот результат. Финальное значение ini E2 записано явно; следующий шаг будет менять цель на существующую копию осознанно.

Эта цепочка переводит знакомую восстановимую структуру в собственную исполняемую историю: сначала ученик получает локально проверяемую конфигурацию, затем сам пишет DDL, наконец доказывает результат на независимых целях и повторе. При затруднении возвращается к конкретным 01, 02, 03, 04 или 05, а не к скрытому ответу. Проверка обычного чтения восстановленной копии сохраняет прежнюю возможность Planner; полный CRUD/вся тестовая матрица нетронутого проекта здесь не требуются.

### Технические критерии полученного решения

- В project есть стандартная конфигурация, pin Alembic и одна ревизия `p0001` с `down_revision = None`. Все её операции явные; старые модели и init_db сохранены. Порядок проверяется history/heads и чтением файла, автоматический runner не обещан.
- Обе новые схемы соответствуют S по таблице 04 и исходной описи, а не будущей модели. Ни SQL-default для priority/is_done/tags, ни лишний Boolean CHECK/UNIQUE/FK/поле не добавлены. Python-defaults в модели прежние.
- Метка читается из каждой физической БД новой Session. CHECK-ошибка и NOT NULL при пропуске priority наблюдаемы, rollback не теряет ранее commit-контрольную строку E1.
- Повтор upgrade при той же истории не меняет структуру, строку E1 и единственную метку; E2 остаётся без Task-строк. Заполненная восстановленная копия не получила alembic_version из этого задания.
- README содержит реальные роли/адреса, выбранный root revision, результаты сравнения и явное финальное состояние ini. Исходная опись и восстановленная копия доступны для следующего шага; ни один защищённый файл не был заменён.

**Локальная готовность ученика.** Может показать файлы и обе БД, объяснить связь parent/head/current, отличить SQL-default от Python-default и назвать, какое нарушение обнаружила каждая проверка. Успешный вывод команды без DDL/данных этим критериям не соответствует. При неправильном CHECK/default/schema остановиться на сравнении, исправить ещё не принятую ревизию и использовать новые свободные disposable-цели; не чинить результат stamp или ручным удалением таблиц. Прежние ошибочные цели помечаются как неэталонные, их состояние не скрывается. После передачи baseline уже не переписывается.

**Помощь.** Первый уровень возвращает к роли файла/адреса и чтению ini из 01–02; второй к независимому create_table/CHECK из 03; третий к различию defaults из 04 и чтению ошибки/rollback из 05. Ни один уровень не содержит Task-upgrade или пошагового алгоритма заполнения всех колонок. Автор Stage 3 создаёт отдельный будущий разбор: на другом малом реестре прослеживает конфигурацию, ревизию, DDL, версию и повтор; затем объясняет самопроверку и типичные причины ошибок практики, сохраняя её самостоятельность. Разбор не вводит новых обязательных команд.
