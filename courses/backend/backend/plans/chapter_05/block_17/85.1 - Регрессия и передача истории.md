## 01. Что доказывает каждая проверка

Объяснить: структура отвечает за таблицы и ограничения; контракт за наблюдаемый ответ на известный запрос; сквозной сценарий за взаимодействие нескольких частей и сохранение состояния после запуска нового процесса. Независимый пример для автора: отдельный мини-каталог с SQLite `catalog`, строкой `id=1, name='чай'`, простым читающим процессом и проверкой, ожидающей имя. Показать совпадение схемы при неверном ответе, затем правильный ответ без доказательства повторного запуска и наконец чтение из нового процесса. Указать вход, файл, команды запуска, вывод и причину каждого отличия. Первая проба: ученик на другом товаре сопоставляет три наблюдения с тремя гарантиями и объясняет, что не доказано. Визуал: три уровня, выбор наблюдения и обратная связь о недостающей гарантии; неверный выбор объясняет границу, не выдавая решение проектной практики.

**Спецификация независимого примера.** В отдельном каталоге `demo_levels/` подготовить файл `catalog.sqlite3` с таблицей `items(id INTEGER PRIMARY KEY, name TEXT NOT NULL)` и строкой `(1, 'чай')`. Файл `read_item.py` открывает только этот путь, читает по `id` и печатает значение; автор показывает независимую проверку схемы через `PRAGMA table_info(items)`, контрактную проверку ожидаемого `чай` и отдельный запуск `python read_item.py` после завершения первого процесса. На второй копии заменить ответ функции на `кофе`, не изменив SQLite: структура прежняя, контракт не совпал. Затем показать успешный вызов в том же процессе и объяснить, почему он не доказывает новый процесс. Для другого товара учащийся выбирает, какое свидетельство доказывает каждый вывод, и проверяет новый запуск. Опора на возврат: таблица «наблюдение / что подтверждает / чего не подтверждает»; наличие файла не проверяет поведение приложения.

## 02. Безопасный адрес и сравнение до и после

Объяснить, что `DATABASE_URL` приложения для конкретного процесса и `sqlalchemy.url` Alembic Config должны указывать на один явно проверенный учебный файл, а не на исходник. Единственный источник подключения Alembic: `sqlalchemy.url` в Config; `expected_database_path` в том же `project/alembic.ini` хранит только абсолютный ожидаемый путь для контроля, не второй URL. Показать в независимом каталоге две разные SQLite-базы: вывести абсолютные пути и выбранный URL, получить до и после количество и упорядоченные строки, отдельно сравнить схему и версию. Первая проба: подменить адрес второй учебной базы, предсказать несовпадение и остановиться. До каждой команды объяснить аргументы, происхождение URL и способ безопасно проверить их; пример и проба не обращаются к файлам Planner. Подготовить сравнение `id`, `title`, `priority`, `is_done`, `tags`, `title_normalized`, а после расширения и `description`; различать SQL NULL и текст.

**Настройка и первая проба.** На Windows PowerShell разобрать отдельный учебный каталог, откуда выполняются команды: `py -3.12 --version` показывает выбранный Python; `py -3.12 -m venv .venv` создаёт среду только в новом каталоге; `.\.venv\Scripts\python.exe --version` выбирает её интерпретатор, `.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt` устанавливает зависимости из данного файла, а `-m` запускает модуль именно этим Python. Активация не нужна; для других систем Stage 3 обязан показать эквивалент и не смешивать интерпретаторы. Показать `python -m pip show alembic` и `python -m pytest --version`: первая команда сообщает версию установленного пакета, вторая тестового инструмента; отсутствие пакета или несовпадение с согласованными файлами означает остановку. Никакую версию Alembic не назначать за предыдущий урок.

Независимый пример `demo_paths/`: заранее остановить писателей, сохранить `source.sqlite3` и снимок разными файлами; две новые цели `sample_a.sqlite3`, `sample_b.sqlite3` в отдельном каталоге. `Path(...).resolve()` даёт абсолютное имя, `Path.exists()` проверяет занятость; `read_bytes()` показывает побайтовое содержимое контрольного файла, но не гарантирует согласованный снимок активной WAL-базы. В отдельном демонстрационном примере настройки используют собственный простой загрузчик пути; затем отдельно в учебном checkout Planner показывают его реальный `load_settings`. Переменная `$env:DATABASE_URL = 'sqlite:///./sample_a.sqlite3'` относится к текущему процессу PowerShell и его дочерним процессам; `.\.venv\Scripts\python.exe -c "from app.core.config import load_settings; print(load_settings().database_url)"` выводит фактически разрешённый приложением адрес; `-c` выполняет указанную строку Python, импорт берёт настройки приложения, `print` показывает результат. Для приложения переменная задаёт адрес runtime; Alembic не читает её как замену Config. Автор показывает, что учебный `env.py` читает `sqlalchemy.url` и `expected_database_path` из Config, а не из окружения или зашитой строки. На копиях с таблицей `items` и разными значениями через `sqlite3.connect` показать `SELECT COUNT(*) FROM items`, `SELECT id, name FROM items ORDER BY id`, `PRAGMA table_info(items)` и `SELECT type, name, tbl_name, sql FROM sqlite_master ORDER BY type, name`; объяснить `COUNT`, `ORDER BY`, строки результата и назначение `sqlite_master`. Закрыть соединения. Первая проба: ученик устанавливает путь второй копии, находит расхождение значений и не записывает в первую. При возврате сравнивать разрешённый адрес, а не только текст относительного URL. В основной практике команды схемы применяют только к существующей проверенной копии: обычный `sqlite3.connect` на ошибочном пути может создать пустой файл.

**Снимки разных состояний.** До действия показать в независимом примере, что snapshot до расширения и snapshot после расширения не взаимозаменяемы. Первый нужен, чтобы восстановить legacy в новый свободный путь и проверить переход baseline → upgrade; второй нужен для восстановления последнего проверенного состояния после отказа. Проверять оба файла по их описи, а не по имени. Не восстанавливать частичный файл после ошибки резервирования. При занятом целевом пути учебная обёртка из темы согласованного снимка должна отказать без изменения известных байтов; планируемый интерфейс `.\.venv\Scripts\python.exe -m app.DBase.backup_snapshot SOURCE DEST` подготовлен в темах снимка и восстановления: оба аргумента позиционные файловые пути, не URL; перед выдачей проверить фактическую реализацию.

**Полный независимый пример двух контрольных значений.** В `demo_guard/` автор заранее создаёт отдельную историю `migrations/`, `alembic.ini` с секцией `[alembic]`, `script_location` этой истории и учебной исходной ревизией для `parcels(id, label)`. Рядом создаёт каталог `sandbox/`; в нём `good.sqlite3` и `wrong.sqlite3` пока не существуют, а независимый снимок `source.sqlite3` никогда не выбирается целью. В примере `sqlalchemy.url` представляет SQLite URL для абсолютного `good.sqlite3`, а `expected_database_path` содержит абсолютный путь того же файла. На обоих путях сравнивают результат `Path(...).resolve()`; контрольный путь не используется для создания второго engine или как источник URL.

До `create_engine`/подключения и до `context.configure` в offline-ветке `migrations/env.py` демонстрации прочитать оба ключа через `config.get_main_option("sqlalchemy.url")` и `config.get_main_option("expected_database_path")`. Объяснить `config` как объект Alembic, имена и возвращаемые строки; отсутствие или пустое значение даёт остановку. Импортировать `make_url` из `sqlalchemy.engine`, разобрать URL, проверить разрешённый SQLite driver, непустой файловый `url.database`, отсутствие `:memory:` и неоднозначных параметров, затем разрешить путь `Path(url.database).resolve()`; отдельно проверить абсолютность и разрешить `Path(expected).resolve()`. При неверном формате, непонятном пути или различии отказать до любых соединений, в том числе offline; сообщить оба разрешённых адреса, если они получены. Относительный путь SQLite разрешать относительно рабочего каталога процесса, абсолютность ожидаемого пути обязательна. Не назначать исходную базу или снимок целями. Отдельно изменить только `sqlalchemy.url` на путь `wrong.sqlite3`, оставив expected прежним: ошибка до подключения, `wrong.sqlite3` не появился, `source.sqlite3` остался прежним. ## 03. Два маршрута истории и прежняя команда

Объяснить роль `project/alembic.ini`, `project/migrations/env.py`, `project/migrations/versions/`, исходной revision, `current`, `upgrade head` и маркировки конкретной baseline revision. `stamp` записывает метку, не меняя схему, и допустим только после сравнения; revision брать из реально созданного файла истории, не выдумывать ID. Исходная baseline неизменна и не зависит от текущей mutable metadata. На независимом примере с таблицей заметок показать новую пустую базу через историю и отдельно восстановленную заполненную исходную копию: сравнение всех значимых объектов, метка исходной revision, upgrade; показать несовпадение как остановку без stamp. Повторить upgrade на head и сравнить данные. Первая проба: другая совпадающая и несовпадающая пара, собственная диагностика до выбора действия.

Объяснить, что `create_all` создаёт отсутствующие таблицы, но не обновляет существующую. На независимой таблице показать отсутствие новой колонки после изменения metadata и повторного `create_all`, затем новую базу через историю. Проба: ученик объясняет причину и выбирает явный путь. Согласованная ранее `app/DBase/init_db.py` должна вести через историю или безопасно отказывать с инструкцией; её прежний вызов остаётся понятным рабочим переходом. Не возвращать старый обход истории.

**Пошаговая опора для автора Stage 3.** В независимом каталоге с собственными `alembic.ini`, `migrations/env.py` и двумя учебными revision для `notes(id, body)` и nullable `memo` заранее показать, как `env.py` получает единственный URL и ожидаемый контрольный путь из Config и сравнивает их до любого подключения и offline configure по разделу 02. При каждом новом целевом файле изменить оба ключа и показать их разрешённые абсолютные пути до вызова команды. Одна ветвь: для свободного `new.sqlite3` `python -m alembic current`, затем `python -m alembic upgrade head` и снова `current`; на новой базе до первой команды version table может отсутствовать. Вторая ветвь: восстановить отдельную заполненную исходную копию, переключить оба значения ini на неё и подтвердить равенство адресов до соединения, без изменения содержимого сравнить `PRAGMA table_info(notes)`, `PRAGMA index_list(notes)`, `PRAGMA foreign_key_list(notes)` и записи `sqlite_master` с образцом baseline, включая CHECK, индексы, триггеры, nullable, PK и defaults. Не считать одно совпадение PRAGMA доказательством всей схемы. Снять данные `SELECT id, body FROM notes ORDER BY id`, получить настоящий идентификатор базовой revision из файла истории; только при полном совпадении выполнить `python -m alembic stamp <фактическая-базовая-revision>`, проверить `current`, затем `python -m alembic upgrade head`. Угловые скобки обозначают заменяемое значение, их не печатают как символы команды. На том же независимом учебном соединении до начала транзакции показать `PRAGMA foreign_keys`: результат 0 или 1 относится только к этому соединению. Проверить `PRAGMA index_list(notes)` и `PRAGMA foreign_key_list(notes)`, объяснить пустой список и строки объектов; PRAGMA читает свойства SQLite, не доказывает совпадение CHECK и триггеров. На отдельной таблице со связью выбрать новое соединение, увидеть его настройку и сравнить с первым; самостоятельная проба показывает, почему нельзя переносить настройку между соединениями. Проверить данные, новый nullable столбец и повтор `upgrade head`. На иной копии с дополнительным ограничением остановиться до stamp, убедиться, что revision не изменилась. `current` наблюдает записанную revision, но не подтверждает схему. `head` применим лишь при одной согласованной конечной revision; неизвестная история или несколько heads требуют остановки и диагностики. Первый самостоятельный опыт: выбрать между пустой, совпадающей и несовпадающей копиями и выполнить только допустимую ветвь, объяснив результат.

Для прежней точки входа на независимой `shelves` с колонкой `name` показать сначала `Base.metadata.create_all(engine)`, затем добавление `location` в модель и повтор на том же файле: колонка не появляется; на отдельной базе применение истории создаёт ожидаемую схему с version table. Пояснить `Base`, `metadata`, `engine` и закрытие ресурса, до пробы проверить путь. Ученик меняет другую учебную колонку и наблюдает тот же результат. Опора: запуск по истории явный, `stamp` не обновляет схему, обычный старт не должен тайно менять данные. Документация Alembic: [команды](https://alembic.sqlalchemy.org/en/latest/api/commands.html), [ветви](https://alembic.sqlalchemy.org/en/latest/branches.html).

## 05. Состояние между интерфейсами

Независимый пример: отдельный мини-проект записывает синтетическую строку через один интерфейс, читает и изменяет другим, завершает процесс и в новом процессе читает состояние. Показать, почему разные Session не означают разные базы, если URL одинаков; и почему чтение прежнего объекта в памяти не подтверждает сохранение. Первая проба: сменить путь второго процесса и объяснить ошибку сопоставления. Визуал показывает файл, отдельные процессы и сеансы; переключение URL даёт явную обратную связь о несогласованном состоянии. Не строить из интерактива готовую последовательность теста Planner.

**Спецификация наблюдения.** Независимый мини-проект `demo_counter/`: первый процесс записывает в таблицу `counters(id, value)` строку `(4, 2)` и завершает соединение с commit; второй читает тот же абсолютный путь, изменяет значение на 3 и закрывается; третий процесс при новом запуске выводит `3`. Показать команды `python write_counter.py`, `python change_counter.py`, `python read_counter.py`, что каждый файл получает один и тот же явно проверенный путь, и результат каждого. На другой БД чтение не находит строку: совпадение относительных имён не заменяет сравнение путей. Первая проба на счётчике с другим ID: предсказать результат, указать путь для всех трёх процессов и проверить после завершения первого. Опора: один файл, отдельные процессы и Session; закрытие ресурса не означает автоматический commit, он должен быть выполнен в границе записи.

## 06. Публичный и внутренний договор

На самостоятельном независимом примере разделить публичные поля и внутренние данные: изменение разрешённого поля сохраняет внутренние значения, а не делает их публичными. Показать различающиеся NULL и непустую строку, чтение непосредственно из SQLite до и после, отказную операцию с неизменными строками. Первая проба: ученик предсказывает сохранность обеих строк при замене и частичном обновлении, затем проверяет на иных синтетических данных. Дать опору на фактические схемы/тесты проекта и пояснить, что отсутствие публичного поля не означает обязательного отклонения лишнего JSON.

**Спецификация независимого примера.** В отдельной SQLite таблица `books(id, label, private_note)` содержит `(1, 'атлас', NULL)` и `(2, 'роман', 'синий корешок')`; маленький учебный адаптер возвращает только `id` и `label`, а разрешённое изменение `label` не записывает `private_note`. До сравнения показать `UPDATE books SET private_note = 'зелёная обложка' WHERE id = 2` и commit на отдельной копии: SET задаёт поле и значение, WHERE ограничивает нужный ID; без WHERE изменятся все строки. Ученик на другой копии выбирает ID и проверяет, что соседняя запись осталась неизменной. Два отдельных чтения `SELECT id, private_note FROM books ORDER BY id` до и после изменений показывают соответственно `None` и текст, в публичном ответе поля нет. Затем показать отказ проверки неверного `label` и неизменность всех строк; объяснить, что Python `None` при чтении SQLite соответствует SQL NULL, а непустая строка не является NULL. Первая проба: предсказать и проверить другую пару записей и найти ошибку реализации, которая записывает `None` при отсутствии входного поля. Для PUT/PATCH и CLI Planner использовать договор на входном SHA, а не переносить напрямую правила учебного адаптера. Опора: сравнение полного набора значений по ID до/после; отсутствие поля в ответе не является доказательством его сохранности.

**Повторение доступных контрактов до проектной практики.** На самостоятельном примере HTTP-запроса показать метод, путь, JSON и статус/тело; `PUT` передаёт все обязательные публичные поля, `PATCH` только изменяемые, `204` не содержит тела, `404` обозначает отсутствующий положительный ID, `422` невалидные данные. На независимом наборе с тремя объектами отдельно показать фильтр, сортировку по ID и ограничение количества; сравнить результат с неверным порядком limit → фильтр. Опора для Planner: README на входном SHA и `tests/test_api.py`, `test_contract.py`, `test_preferences.py`, `test_cli.py`. В примере тройка учебных книг: ID 2 доступна, ID 5 выдана, ID 8 доступна. Фильтр доступных, сортировка по убыванию ID и limit 1 дают ID 8; limit до фильтра может исключить нужную книгу при изменённом порядке. Ученик меняет фильтр и заранее объясняет результат. Для cookies пояснить отличия заголовков ответа и cookie jar: `Set-Cookie` задаёт `planner_view` и `Path=/preferences`, повторный GET возвращает сохранённое предпочтение; DELETE сбрасывает его. `/health` подтверждает процесс, не состояние БД. Эти проверки и ввод действующего контракта перед практикой автор Stage 3 показывает на учебном HTTP-примере и даёт ученику первую пробу с другой последовательностью состояний.

**Импорт и ошибки.** На независимом мини-импортёре показать JSON-массив двух записей, валидацию до записи и транзакцию, которая откатывает обе записи при ошибке до commit. Сравнить пустую и непустую цель: повтор отказывает, не очищая таблицу; источник сравнить побайтно до и после. Пояснить параметры `--source` и `--database` как пути к разным существующим файлам; для Planner входной `app/DBase/import_tasks.py` требует именно их. В учебном `demo_import/` использовать, например, записи `[{"id": 21, "name": "перо"}, {"id": 22, "name": "бумага"}]`, пустую таблицу `supplies(id, name)` и отдельный файл `incoming.json`; сравнить `SELECT id, name FROM supplies ORDER BY id` и байты JSON после успешного импорта, повтора и контролируемой ошибки. Показать возврат ненулевого кода при ошибке. На отдельном искусственном недоступном пути показать ошибку открытия хранилища, её преобразование на границе и ответ 503 без внутреннего пути; отличить отсутствующую таблицу от `SQLITE_CANTOPEN`. Первая проба: ученик выбирает непустую цель и проверяет неизменность строк, затем объясняет, почему не надо подставлять JSON автоматически. Возврат: явный импорт отделён от runtime.

### 2. Воспроизвести два пути схемы

**Контекст и условие.** Нужны два независимых доказательства: создание с нуля и переход старых данных, а не два повтора на последней версии. Сравнить типы, PK, nullable, defaults, CHECK, индексы, FK и триггеры с исходной схемой, а не с изменяемой актуальной metadata. Если есть непонятное расхождение, остановиться. Для совпавшей legacy-копии взять фактический ID первой revision из `migrations/versions/`, проверить цепочку `down_revision`, выполнить `.\.venv\Scripts\python.exe -m alembic stamp <фактическая-базовая-revision>`, затем `.\.venv\Scripts\python.exe -m alembic current` и `.\.venv\Scripts\python.exe -m alembic upgrade head`. Не использовать `stamp head` как починку схемы. Зафиксировать исходные поля до/после и наличие NULL у старых строк; на синтетических данных сохранить у одной задачи непустое описание, у другой NULL и после повторного `upgrade head` прочитать оба значения SQL-запросом по ID. При изменении данных на этом дополнительном образце отделить собственную учебную запись от исходного сравнения. (в) Для специально изменённой disposable `mismatch.sqlite3` выставить в ini оба значения и до соединения проверить равенство разрешённых путей; до stamp продемонстрировать несовпадение одного исходного ограничения или объекта. Проверить наличие `alembic_version` через `sqlite_master` и, если таблица есть, снять её revision до/после принятого решения; отсутствие таблицы зафиксировать как отсутствие метки, а не как ошибку при чтении несуществующей таблицы. Убедиться, что маркировка не выполнялась. При восстановлении через обёртку предварительно проверить свободный путь и результат восстановления; при ошибке не использовать оставшийся частичный файл.

**Готово:** обе ветви пришли к той же согласованной схеме и revision, исходные строки не потеряны, NULL и текст различимы и сохраняются, повтор не меняет данные; несовпадающая копия не маркирована. **Помощь:** вернуться к разделу 03 и сравнить фактическую схему раньше revision. **Разбор:** на другой таблице объяснить, чем новая база отличается от заполненной копии и почему `stamp` не исполняет миграции.

### 3. Согласовать тестовые базы с историей

**Контекст и условие.** Быстрый тест модели может проходить даже при сломанной истории. Нужно сделать так, чтобы тесты контрактов и интеграции проверяли настоящий upgrade, не стирая полезные старые проверки. Объекты: `tests/conftest.py`, `tests/test_db_schema.py`, `tests/test_task_import.py`, `tests/test_sql_readiness.py`, `tests/test_workflow.py`, имеющиеся API/CLI и отказные тесты. Опора: разделы 03–04 и реальные фикстуры входного SHA.

**Действия.** Самостоятельно изменить фикстуры API и интеграционного сервиса: для каждого теста получить из `tmp_path` отдельный SQLite-файл, создать `Config` из того же `alembic.ini`, задать `set_main_option("sqlalchemy.url", URL_своего_tmp_path)` и `set_main_option("expected_database_path", абсолютный_свой_tmp_path)` как строки, применить реальный `command.upgrade(config, "head")` и проверить revision до подключения клиента или сервиса. Формирование URL через `URL.create` и проверка двух разрешённых путей подготовлены в разделах 02 и 04; `script_location` указывает на ту же принятую историю, а `env.py` читает переданные main options без подмены. Добавить отрицательную пробу с другим новым URL при прежнем expected path: отказ до соединения и ошибочный файл не появился. Явно закрыть engine/Session и восстановить изменённое состояние `app.state` после теста. Не полагаться на `Base.metadata.create_all` как свидетельство истории; быстрые изолированные unit-тесты допускают metadata или подмены с обозначенной областью гарантии. На отдельной временной схеме добавить проверки пустого пути и заполненной копии от исходной baseline до upgrade, включая отличающий случай неизвестной revision, отсутствующей обязательной revision после маркировки или несовпавшей схемы: он не может считаться успешным переходом. До первого upgrade пустая база закономерно не имеет revision; сравниваемая исходная legacy-копия может не иметь метки до разрешённого stamp. В `test_db_schema.py` на отдельном временном файле и собственном Config применить `command.upgrade(config, фактический_baseline_revision)` к реально созданной первой revision, после чего проверить исходный договор по схеме и ограничениям без `description`; revision берут из файла истории, не придумывают. На другой отдельной временной базе применить `command.upgrade(config, "head")` и проверить актуальную схему и metadata, включая nullable `description`; не требовать от актуальной модели прежний точный список столбцов без неё. Проверить мигрированную схему в тестах импорта, readiness, API/CLI workflow и отказов, не удаляя смысл старых проверок; определить отдельные фикстуры там, где тесты создают схему самостоятельно. Запустить из `project/` `.\.venv\Scripts\python.exe -m pytest -q`, при расследовании использовать `.\.venv\Scripts\python.exe -m pytest tests/test_db_schema.py tests/test_task_import.py tests/test_sql_readiness.py -q`. Эти команды не заменяют остальные модули; сохранить вывод и итог без скрытия ошибок.

**Готово:** каждая контрактная/интеграционная проверка видит свою мигрированную временную базу и фактическую revision; исходный и актуальный договоры проверяются раздельно, временные ресурсы закрыты, полный набор прошёл. **Различающий случай:** схема из metadata без version table не засчитывается как миграционный путь; неверная revision или схема даёт отказ. **Помощь:** сначала посмотреть фактический URL фикстуры и `current`, затем её потребителей. **Разбор:** объяснить, почему одинаковые колонки в тесте ещё не доказывают работоспособность истории.

### 4. Проверить общий Planner и сохранность скрытых полей

**Контекст и условие.** Два интерфейса работают с одной временной базой, а новый процесс не должен зависеть от старых объектов в памяти. Начать с базы из успешного upgrade и тестовых данных; сохранить диагностический снимок полей по ID. Опоры: разделы 01, 02, 05, 06, README и тесты входного проекта; перед выдачей подтвердить ранее подготовленные HTTP/CLI навыки.

**Действия.** Запустить API из `project/` через `.\.venv\Scripts\python.exe -m uvicorn app.api:app --host 127.0.0.1 --port 8000` с проверенным учебным `DATABASE_URL`; значение host ограничивает локальный адрес, port выбирает свободный локальный порт. Отдельно запустить `.\.venv\Scripts\python.exe -m app.main` с тем же URL. Создать через `POST /tasks` синтетическую задачу с `title` `Купить бумагу` и `priority` 2, записать возвращённый ID; в CLI выполнить `find`, затем `done` для этого ID, закрыть CLI и первый API, запустить новый API-процесс с тем же URL, получить `GET /tasks/{id}` и `/stats`. Сверить изменения и счётчики. В CLI выполнить `search` с фрагментом названия и проверить найденный ID; в API через `GET /tasks` сравнить фильтр `is_done`, сортировку `sort_desc` и `limit` на нескольких задачах с разными ID и состояниями, чтобы неверный порядок фильтр/сортировка/limit дал другой результат. Выполнить полную замену `PUT` с `title`, `priority`, `is_done` и частичный `PATCH`, затем `DELETE`, проверить 204 и пустое тело, отдельный GET 404; неверные body/query и неположительный ID дают 422. До и после отказов сравнить строки, включая соседнюю задачу.

Отдельные две синтетические задачи после миграции имеют NULL и непустой `description`; присвоение непустого значения выполнить прямым SQL в учебной базе и записать снимок всех полей. Для образца объяснить `UPDATE tasks SET description = 'синтетическая заметка' WHERE id = <ID>`: `SET` меняет только названное поле, `WHERE` ограничивает выбранную задачу, ID берут из результата создания и подставляют без угловых скобок; выполнить только на учебной копии и зафиксировать commit. На обеих выполнить допустимые PUT/PATCH и CLI done, затем в новом соединении прочитать `id, title, priority, is_done, tags, title_normalized, description` по ID; оба значения описания и внутренние теги сохраняются, ожидаемые изменения публичных полей отражены. SQL проверяет синтетические `tags` и нормализованное название; ответы и CLI не добавляют поддержку ввода/вывода tags или description. Не требовать отклонения лишних JSON-полей, если существующий контракт этого не обещает. Непустой текст и NULL должны сохраниться независимо для каждой задачи; при потере остановить передачу.

Проверить GET `/health`, GET/PUT/DELETE `/preferences`, заголовки `X-Client-Version` и `X-Planner-Version`, cookie `planner_view` с Path `/preferences` и повторное использование cookie; запросы не требуют новых Origin/CSRF. Для каждого сохранить статус и существенное тело/заголовки. **Готово:** новый процесс видит изменения, все перечисленные позитивные и отказные случаи дают действующий контракт, SQL подтверждает сохранность внутренних полей. **Помощь:** проверить URL каждого процесса и сравнивать строки по ID, не только текст в интерфейсе. **Разбор:** почему 200 и работа health не доказывают сохранности скрытых значений и чтения после перезапуска.

### 5. Проверить импорт и изоляцию отказов

**Контекст и условие.** Импорт JSON остаётся явной отдельной операцией, а недоступность SQLite не должна незаметно переключать приложение на файл. Объект: `app/DBase/import_tasks.py`, синтетический JSON и отдельная мигрированная пустая `import.sqlite3`; опора: разделы 04 и 06, подготовленный ранее сценарий rollback.

**Действия.** Создать учебный UTF-8 JSON-массив из двух корректных записей с разными положительными ID, `title`, `priority`, `is_done`, у одной синтетические `tags`: например, ID 11, title `План поездки`, priority 2, is_done false, tags `["дом"]`; ID 14, title `Запись к врачу`, priority 4, is_done true, tags `[]`. Указать значения в JSON с двойными кавычками и строчными `false`/`true`; выбрать отдельный исходный файл, не использовать реальные снимки. Перед миграцией `import.sqlite3` установить в ini оба значения на этот путь, вывести оба разрешённых абсолютных адреса и подтвердить равенство до соединения; применить upgrade head. Для каждой другой новой цели повторить это переключение и проверку. После миграции пустой цели выполнить `.\.venv\Scripts\python.exe -m app.DBase.import_tasks --source <путь-к-учебному-json> --database <путь-к-import.sqlite3>` с реальными путями вместо угловых скобок. Сверить число строк и все исходные поля, нормализованное название и NULL в новом поле. Сравнить байты источника до/после. Повторить импорт в непустую цель: отказ, прежние строки и источник без изменений. На отдельной пустой мигрированной цели, после установки обоих значений ini и проверки их равенства до её upgrade, проверить ошибочную запись и контролируемую ошибку внутри транзакции до commit через существующие тестовые точки, проверить rollback и пустой результат; не внедрять ошибку в принятую историю. В изолированном тесте задать недоступный SQLite-путь и проверить существующее преобразование `SQLITE_CANTOPEN` → `StorageError` → HTTP 503 без утечки пути, отсутствие изменений JSON и fallback. Отдельно проверить отдельную SQL Session на запрос и известную CLI-команду, закрытие ресурсов и rollback до commit; различать ошибку отсутствующей таблицы и `SQLITE_CANTOPEN`.

**Готово:** явный успешный импорт и отказные ветви различимы по статусу и состоянию, повтор не удаляет данные, rollback не оставляет частичных строк, runtime не использует JSON как запасное хранилище. **Помощь:** сначала проверить разные абсолютные пути и существование пустой мигрированной цели. **Разбор:** на независимой паре данных объяснить, почему ошибка до commit и повтор на непустой цели требуют разных наблюдений.
