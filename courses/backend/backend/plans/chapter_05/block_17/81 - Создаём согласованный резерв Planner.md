Они подтверждают имена и договоры, а не новый runtime PASS. Запуск выбранного прежнего теста и выполнение примеров относятся к авторству Stage 3.

Контракты новых средств проверены по первичной документации, CPython 3.12 и SQLAlchemy 2.0.55 выбраны в Context7 по среде входа:

- [sqlite3](https://docs.python.org/3.12/library/sqlite3.html): URI `mode=ro` с `uri=True`, `execute`/`fetchall`, `Connection.backup(target)` и контекст соединения, который сам не закрывает ресурс.
- [pathlib](https://docs.python.org/3.12/library/pathlib.html) и [open](https://docs.python.org/3.12/library/functions.html#open): `resolve`, `is_file`, `as_uri`, `open("xb")`, `read_bytes`. Исключительное создание отказывает существующему файлу; предварительный `exists()` не заменяет его.
- [SQLite Backup API](https://www.sqlite.org/backup.html) и [WAL](https://www.sqlite.org/wal.html): backup читает состояние через SQLite; WAL может содержать подтверждённые изменения. Назначение backup может быть заменено, поэтому его защищает наша операция.
- [sqlite_schema](https://www.sqlite.org/schematab.html) и [PRAGMA](https://www.sqlite.org/pragma.html#pragma_table_info): объекты/SQL и признаки колонок читаются отдельно; CHECK читается из CREATE SQL, индексы и FK из отдельных PRAGMA.
- [SQLAlchemy defaults](https://docs.sqlalchemy.org/en/20/core/defaults.html): `default` на Python-стороне не обещает SQL DEFAULT в DDL. В TaskRow S нет `server_default`.
- [Запуск Python](https://docs.python.org/3.12/using/cmdline.html): файл, `-m` и `-c` имеют разные входы; команды для текущей среды даются полностью рядом с первым применением.

До исполнения на Stage 3 автор фиксирует фактические Python и `sqlite3.sqlite_version`, проверяет готовый пример в этой среде и обычное открытие WAL через SQLite. Ученик не устанавливает новую библиотеку резервирования и не меняет зависимости проекта. Не используются `immutable`, отключение блокировок или ручное удаление sidecar-файлов.

## 02. Открываем существующий файл и закрываем соединение

**Вопрос и новая способность.** Почему опечатка в имени может выглядеть как пустая база? Обычный `sqlite3.connect(path)` способен создать новый файл; чтение известного источника требует другого режима.

**Полный независимый пример: часть открытия.** Stage 3 печатает накопительный `backup_lab.py` целиком после объяснения частей. Подготовка создаёт `books-source.sqlite3` в свободном каталоге только один раз: `Path.open("xb")` резервирует отсутствующее имя, закрывает файловый дескриптор; затем sqlite3 создаёт таблицу `books(id INTEGER PRIMARY KEY NOT NULL CHECK(id > 0), title TEXT NOT NULL, shelf TEXT NOT NULL DEFAULT 'reading')`. Для первой строки INSERT задаёт только id=4 и title='Лес', SQL заполняет shelf='reading'; для второй заданы все значения `(9, 'Море', 'archive')`. Затем commit и закрытие соединения. Подготовка дана как видимый небольшой блок: объяснить CREATE/INSERT, список колонок, `?` и tuple параметров, commit как фиксацию до закрытия. Это создание данных опыта, не целевая backup-функция. При существующем books-source подготовка отказывает, не очищает его.

**Разбор формы и порядка.** Импорт `sqlite3`, `Path` и `contextlib.closing`; `/` в Path соединяет части пути, `resolve(strict=True)` для источника требует существования, `is_file()` отличает файл от каталога, `resolve()` назначения убирает `..` и разрешает символические ссылки. `as_uri()` требует абсолютного Path и корректно кодирует пробелы; к нему добавляется `?mode=ro`, `uri=True` включает разбор параметра SQLite. Показать значение каждого промежуточного имени, а не одно вложенное выражение. Успешное `connect` ещё не доказывает наличие нужной таблицы: в следующем разделе читаем схему.

`closing` вызывает `.close()` при выходе, включая исключение. Контекст `with sqlite3.connect(...)` отвечает за транзакцию, но сам соединение не закрывает. Контекст `with path.open(...)` закрывает именно файловый дескриптор. Соединение источника, соединение назначения и файловый дескриптор не один ресурс. В подготовке commit выполняется до закрытия; резервирование не идёт по незавершённой записи.

На функции подготовки книг кратко восстановить `def`, параметры с Path, вызов, return созданного Path и аннотацию результата. Возвращаемый адрес не выполняет копирование. На этом же независимом файле объяснить `if __name__ == "__main__"`: импорт определяет средства, запуск выполняет выбранный демонстрационный вызов. Это подготовительная функция создания книг, не готовая backup-функция. Резервирование ниже остаётся полным линейным примером. Все изменяемые строки нижнего вызова показаны буквально, без CLI-парсера.

**Первое самостоятельное применение.** После полного открытия существующего источника и понятного сообщения о соединении ученик предсказывает результат для `books-missing.sqlite3`, сам меняет выбранный Path и запускает пробу открытия, затем проверяет отсутствие этого файла. Ожидается понятный отказ, не пустая новая SQLite. Второй короткий перенос: существующий каталог вместо файла, отказ до чтения; возвращаемся к is_file. Для повторения источник книг уже существует, подготовку больше не вызываем; в нижнем месте вызова `backup_lab.py` остаётся только текущая операция открытия. Чтение схемы/строк объясняется в следующем разделе.

**Опора и переход.** Краткая памятка рядом: режим нового ресурса выбираем намеренно, существующий источник открываем ro, освобождение соединения не равно commit. Далее прочитаем через это соединение фактические schema/data.

## 03. Снимаем опись схемы и всех значений

**Вопрос и новая способность.** Что именно должно сохраниться? Два названия в API не показывают всю структуру и внутренние значения. Опись хранит исходное состояние для последующего сравнения, а не задаёт новую схему.

**Независимый пример чтения books.** В том же `backup_lab.py` открыть существующие книги ro и показать `execute(...).fetchall()`: сначала список объектов `SELECT type, name, tbl_name, sql FROM sqlite_schema ORDER BY type, name`, затем `PRAGMA table_info(books)`, `PRAGMA index_list(books)`, `PRAGMA foreign_key_list(books)`, затем `SELECT id, title, shelf FROM books ORDER BY id`. Разобрать список строк, tuple и порядок выбранных колонок; пустой результат для индексов/FK не означает пустую таблицу. Показать точный SQL таблицы и где видны CHECK, PK, NOT NULL и DEFAULT, затем их связь с полями `cid/name/type/notnull/dflt_value/pk` PRAGMA. CHECK не ищется в table_info. У книжной таблицы и исходной tasks нет отдельного индекса для INTEGER PK; пустой index_list сохраняется как наблюдение. Не вводить дополнительный индекс ради демонстрации. Неожиданный объект/непустой список у данного входа сначала выясняется и фиксируется, а не автоматически считается известным.

Книжный SQL-default shelf виден уже на первой исходной строке: INSERT из подготовки не передавал shelf, а чтение показывает reading. Ученик сам предсказывает, что даст такой же пропуск по показанному DDL и почему явный archive второй строки не заменён default. Новых строк и повторной подготовки для этого прогноза не требуется. Никакой скрытой правки books-source после описи.

**Перенос на реальный Planner.** Сопоставить TaskRow S с DDL фактической tasks и полями PRAGMA. В models.py `default=2`, `default=False`, `default=list` поставляются SQLAlchemy при записи, а SQL-defaults в DDL здесь не заявлены. Отсутствующий dflt_value не означает поломку схемы. id положителен; priority ограничен 1–5; все шесть колонок обязательны; title_normalized и tags не видны в TaskRead/CLI, но обязаны войти в опись. При неизвестной таблице/триггере или несоответствии остановиться и выяснить вход, не применять init_db к заполненному источнику как ремонт.

**Завершение синтетической подготовки до описи.** Две задачи из 01: `Сверить резерв`, priority 2; `Проверить перенос`, priority 4. Их ID берутся из ответов, не назначаются заново. После остановки API/CLI на этом учебном источнике короткий видимый подготовительный блок sqlite3 задаёт tags соответственно текстом JSON `["учёба","резерв"]` и `["перенос"]`, второй задаче is_done=1; title_normalized остаётся полученным сервисом. До исполнения разобрать параметризованный UPDATE, tuple значений и условие по сохранённому ID; каждый из двух UPDATE затрагивает одну строку, `cursor.rowcount` должен быть 1. Показать смысл результата и commit только после обеих проверок; при расхождении rollback/закрытие и остановка подготовки. Этот блок только готовит внутренние контрольные данные, не реализует резерв. Никаких прямых записей в обычный пользовательский planner.sqlite3.

**Своя проба.** После books-разбора ученик сам записывает чтение шести колонок tasks с явным ORDER BY id и schema-запросы по переносу механизма, а не получает готовый SELECT tasks в шаблоне. Сохраняет исходные строки полностью в observations.md, включая `0/1`, текст JSON tags и title_normalized, отдельно DDL/PRAGMA и полный адрес. Число строк, множество ID и все значения читаются отдельно; один `COUNT(*)=2` не доказывает сохранность. Визуальное сравнение двух шестиэлементных записей посильно и не требует нового сериализатора или генератора отчётов.

**Опора и переход.** Возврат к расшифрованной строке PRAGMA и различию SQL/Python-default. После commit подготовки и закрытия всех соединений наступает зафиксированная точка: опись больше не меняют, источник больше не записывают. Теперь нужен согласованный снимок этого состояния.

## 04. Получаем согласованный снимок по новому адресу

**Вопрос и новая способность.** Как сделать резерв, не перепутав его с источником или будущей рабочей копией? Файл SQLite и логическое состояние базы не всегда совпадают: при WAL подтверждённые страницы могут ещё находиться в `-wal`. Его не удаляют и не собирают резерв ручным копированием пары файлов.

**Механизм.** В учебной процедуре завершаем записи, останавливаем API/CLI/редактор БД и закрываем их соединения до описи и backup; DB Browser с открытым файлом тоже ресурс. Backup API умеет работать при других клиентах, но этот урок не проверяет online-режим: остановка делает точку сравнения фиксированной. Не обещать, что остановка автоматически устраняет любой оставшийся WAL. Источник читается через SQLite ro вместе с доступным состоянием журналов; новый target открывается своим соединением. Вызов `source_connection.backup(target_connection)` переносит базу, а не возвращает готовый файл как значение. Это API не проверяет, был ли target ценным существующим файлом.

**Полный независимый пример: часть резервирования.** Продолжить books-опыт законченным линейным сценарием: объявленные разные абсолютные Path, существующий проверенный ro-источник, отсутствующее назначение и существующий родительский каталог; отказ на равенстве разрешённых адресов; исключительное резервирование имени `books-reserve.sqlite3` через `open("xb")` и закрытие файлового дескриптора; отдельное target-соединение; полный backup; закрытие обоих; новое ro-открытие books-reserve и чтение books. В Stage 3 этот пример целиком запускаемый, а не отдельные несовместимые куски. Он не оформляется в готовую многоразовую функцию Planner, не содержит её сигнатуру/готовый обработчик всех отказов и не импортируется в практику.

**Состояния и объяснение.** `exists()` помогает показать состояние, но между проверкой и созданием файл может появиться; решающий guard есть у самого исключительного открытия. После создания цели владение относится только к файлу, созданному этой попыткой. Ресурс освобождается при выходе из контекста; путь назначения остаётся. Не обещать атомарную защиту от намеренной подмены файла между резервированием и SQLite-open другим процессом: здесь каталог локальный, другие писатели остановлены. Существующее назначение никогда не открывается на запись и не переименовывается автоматически. Возврат/сообщение успеха допустимы после завершения backup, закрытия и контрольного открытия. Проверка полноценного восстановления позже.

**Учебный визуал вне 00: «Куда идёт согласованное состояние».** Данные: books-source с двумя строками, возможный books-source-wal, новое books-reserve и ещё отсутствующий адрес рабочей копии. Показать два независимых SQLite-соединения, отдельный короткий файловый дескриптор xb и границы их жизни. Читатель прослеживает стрелку логического чтения SQLite из source/WAL в reserve; стрелка обычного копирования только основного файла оставляет отмеченную WAL-строку вне копии. Наблюдение: наличие файла и источник логических данных различаются, будущая рабочая цель пока не затронута. Пояснение ограничивает вывод: изображение не доказывает, что у конкретного учебного файла WAL существует, и не предлагает ручной перенос sidecar.

**Содержательный интерактив вне 00: «Выбираем безопасную попытку».** Фиктивные пути и таблица состояний: books-source существует; books-reserve свободен; books-occupied содержит известные байты; restore-адрес свободен. Ученик сам выбирает источник, назначение и состояние писателей, затем подтверждает попытку. Значимые случаи: корректные разные пути и закрытые писатели; источник отсутствует; назначение равно источнику через `..`; назначение занято; писатель ещё работает. Результат показывает, какой файл операция собиралась читать/создать, где она остановлена, что осталось неизменным и почему. При активном писателе отказ относится к нашему учебному протоколу, а не к утверждению о невозможности backup API. При занятом назначении объясняется отсутствие права перезаписи; при совпадении опасность затронуть источник. Feedback раскрывает причину по состояниям, не код wrapper и не строки его алгоритма. Сброс возвращает сценарий без реальных файловых действий.

**Первая своя проба до большой интеграции.** После разобранного books-reserve ученик сам выбирает другой свободный `books-trial.sqlite3`, предсказывает существование и содержимое до/после, меняет только данные вызова линейного опыта, запускает и читает две книги новым соединением. Затем объясняет, почему повтор того же имени должен отказать. Это первый перенос с малой поддержкой; собственная комбинация guard/ресурсов в функцию Planner остаётся практике.

**Опора и переход.** Рядом схема порядка ресурсов и смысл xb/ro/backup. Даже созданный target может оказаться неполным, если операция не дошла до конца; следующий раздел готовит эту развилку.

## 05. Отличаем успешный резерв от неполного результата

**Вопрос и новая способность.** Почему «файл появился» не равно «резерв готов»? Различаем отказ до создания цели, сбой после её создания и успешное завершение с контрольным открытием. Открываемая SQLite тоже может быть пустой или неполной, поэтому последующее восстановление должно сравнить опись.

**Независимые различающие случаи в том же books-опыте.** Для books-occupied через xb один раз записать `b"KEEP BOOKS\n"`; до попытки сохранить результат read_bytes в переменную, после ожидаемого отказа сравнить байты, а не только размер/имя. Объяснить `b`, перевод строки, возвращаемые bytes и сравнение; повторная подготовка не использует wb. Пропавший источник даёт отказ и не создаёт ни его, ни цель. Совпавшие разрешённые пути отказывают до xb. На отдельном новом `books-interrupted.sqlite3` намеренная учебная остановка `RuntimeError` после xb, до backup, оставляет негодную цель; это моделирует незавершённость, а не сбой движка SQLite. Эта проба не пишет в books-reserve и не требует физически портить источник.

**Как обрабатываем результат.** До изменения разобрать `try`/`except`/`finally` или `closing`, продолжение исключения через `raise` и правило: ресурсы закрываются и при ошибке, успех не печатается. Отказ до владения новым файлом не даёт права назвать существующий занятый файл «наш неполный резерв». Для созданного этой попыткой файла ошибка означает INCOMPLETE в observations.md и исключение вызывающей стороне. Частичный файл сохраняется под его отдельным именем, не удаляется и не считается входом восстановления. Автоочистка, автоповтор и атомарная публикация находятся вне B. Новый явный запуск использует другой свободный путь.

**Своя короткая проба.** Ученик сначала предсказывает сохранность контрольных байтов и вид результата прерывания, затем сам выбирает, какое наблюдение отличит отказ до создания от неполной цели. После проверки называет путь, оставшийся файл и статус с причиной. Ложный ответ «ошибка значит, что ничего не создано» опровергается новым пустым target; ложный ответ «открывается значит полный» опровергается отсутствием книг. Без готового обработчика Planner.

**Опора и переход.** Таблица трёх исходов рядом с объяснением. Буквальные сообщения могут различаться, но успешный путь не возвращается при ошибке; незавершённый файл не передаётся дальше. Теперь все части подготовлены для собственного модуля сохранения Planner.

## 06. Что мы будем делать в практике

**Формат и простой контекст.** Изменение существующего учебного проекта в редакторе, с локальными проверками в терминале. Planner уже хранит задачи; перед изменением схемы нужен собственный инструмент сохранения. На входе только проект S и проверяемая среда. Реальные SQLite ученика не используются. Готовой backup-функции, starter-файла или скачивания на входе нет. Видимый книжный пример даёт механизмы и техническую подготовку опыта; ни один его готовый wrapper не переносится в Planner.

**Условие, которое будет видно до помощи.** На отдельном учебном адресе подготовим две задачи и убедимся, что API и CLI читают одну SQLite. Сохраним исходную структуру и все значения, включая внутренние поля. В существующем SQL-пакете напишем свою функцию резервирования, которая не создаёт отсутствующий источник и не заменяет существующее назначение. Проверим отказ на неверных адресах и сохранность контрольного файла, а на отдельной новой цели воспроизведём незавершённую попытку. После неё получим успешный резерв по другому свободному адресу, откроем его и сохраним понятную передачу для восстановления. Все эти группы действий обязательны и названы до будущих подсказок/разбора.

### Связанный маршрут самостоятельных действий

1. **Выбрать известный учебный источник → подтвердить общий вход.** Вход: S/README и свободный каталог из комплекта, личная готовность пока не проверена. Объект: `planner-source.sqlite3`, URL двух терминалов и observations.md. Опора: 01 с полным запуском модуля/одного теста, настройками, формой POST и командами CLI. Самостоятельно: выбираем полный адрес, проверяем отсутствие файла до init_db, запускаем входной тест для своей версии Planner, явно создаём учебную схему, делаем две API-записи с указанными title/priority и сохраняем выданные ID; читаем CLI и ещё одним новым процессом. Локальный критерий: тест завершился успешно; API и оба CLI-чтения показывают те же две задачи. Результаты и URL записаны. Несовпадение останавливает дальнейшие записи и возвращает к настройкам 01, а не к резервированию неизвестного файла.
2. **Завершить подготовку и снять опись → зафиксировать точку сравнения.** Вход: ровно две задачи с сохранёнными ID, API и CLI остановлены. Объект: этот же источник и observations.md, разделы schema-before/data-before. Опора: 02 для открытия/закрытия, 03 для SQL/PRAGMA/tuple/параметров/commit. Готовый видимый короткий setup дополняет tags и is_done по двум сохранённым ID; его роль и все формы объяснены, backup он не реализует. Самостоятельно: сверяем число затронутых строк, commit и закрытие; затем сами записываем запросы чтения схемы и всех шести Task-полей, расшифровываем результаты и сохраняем обе строки без сокращений. Локальный критерий: известны таблицы и DDL, колонки/PK/nullable/SQL-default/CHECK/индексы/FK; две строки содержат ID, title, priority, is_done, tags, title_normalized. Отдельно объяснено, почему Python-default не обязан появиться в SQL. После этой точки записи и изменение описи запрещены до завершения backup-проверок.
3. **Написать своё средство → получить вызываемую операцию Planner.** Вход: зафиксированный источник, разобранные books-примеры и новые свободные назначения. Объект: новый `app/DBase/backup.py` рядом с существующими init_db/models; API/CLI не переписываются. Опора: 02, 04 и 05; функции/параметры/return и ветвления восстановлены на читаемых формах примера до собственной записи. Самостоятельно: создаём `backup_database(source: Path, destination: Path) -> Path`, выбираем порядок отказов и границы контекстов, пишем чтение существующего source, исключительное создание destination и backup между разными соединениями. Внизу модуля явные Path и вызов под `if __name__ == "__main__"`; формы guard объяснены, точный wrapper в теории и заготовке не дан. Локальный критерий: модуль импортируется без запуска файловой операции, а запуск `.venv/Scripts/python.exe -m app.DBase.backup` вызывает ровно выбранную попытку. Самопроверка исходника на преждевременный connect к target/сообщение успеха доступна до дальнейших опытов; следующие проверки наблюдают действительное поведение.
4. **Проверить защиту и незавершённость → различить три исхода.** Вход: свой модуль, неизменный источник, известные контрольные байты `b"KEEP PLANNER\n"`, новый `planner-interrupted.sqlite3` и ещё отсутствующий `planner-never-created.sqlite3`. Объект: входные Path функции и записи case-results в observations.md. Опора: 04 для разрешённых адресов/xb, 05 для bytes, исключения, владения целью и неполного результата. Самостоятельно: создаём planner-occupied.bin через xb, фиксируем его байты до вызова; выполняем сценарии таблицы ниже и сравниваем результат с договором. Для управляемой остановки временно добавляем видимый `raise RuntimeError(...)` после успешного создания именно interrupted, затем убираем строку до окончательного запуска и снова просматриваем модуль. Это учебная инъекция в собственном коде, не заявленный отказ SQLite. Локальный критерий: занятый файл побайтно прежний, source не изменён, пропавший source и never-created не появились, interrupted помечен INCOMPLETE, успешного пути при ошибке нет. Частичный файл не удаляется и не используется повторно как новое назначение.
5. **Применить инструмент и подготовить передачу → получить открываемый резерв.** Вход: рабочий модуль без учебной остановки, закрытые писатели, зафиксированная опись, свободный planner-reserve.sqlite3. Объект: reserve и итог observations.md. Опора: 02–05 и результаты предыдущих действий. Самостоятельно: вызываем собственную функцию с нужными Path, закрываем её ресурсы, новым ro-соединением открываем reserve и читаем sqlite_schema/tasks и одну исходную строку; новым ro-чтением source сравниваем исходные DDL/PRAGMA, множество ID и все шесть полей с сохранённой описью. Локальный критерий: успешный вызов вернул разрешённый путь только после backup и контрольного открытия; резерв открывается и содержит tasks, исходник полностью прежний, контрольные байты прежние. Пишем SUCCESS для reserve, оставляем INCOMPLETE для interrupted, указываем третий свободный адрес planner-restored.sqlite3 и что полноту резерва ещё проверит восстановление.

Эта последовательность сначала устанавливает источник и эталон, затем соединяет изученные операции в собственный модуль и проверяет его на случаях, где опасная реализация казалась бы рабочей. При затруднении открываем соответствующий раздел 02, 03, 04 или 05, а не будущий ответ задачи. Книжная проба даёт первый наблюдаемый backup до интеграции; практика добавляет самостоятельную функцию и реальную schema/data-передачу Planner. Полученный SUCCESS означает завершённое резервирование и открытие; доказательство полноты через восстановление остаётся отдельным следующим действием.

### Технические критерии полученного решения

ТЗ Stage 3 формулируется как последовательные свойства готового результата, не как скрытый алгоритм:

- Учебный источник имеет отдельный явно показанный DATABASE_URL; обычная база Planner сохранена. Две задачи возникли из видимых действий и имеют сохранённые исходные ID/все значения.
- В observations.md есть абсолютные source/reserve/future-restore Path, учебный URL, свидетельство API/CLI/нового процесса, исходные schema/data, результаты случаев и статусы конкретных файлов.
- `backup_database` принимает два Path и возвращает разрешённый destination только при успешной попытке. Отсутствующий/нефайловый источник не создаётся; source и destination после разрешения не совпадают; отсутствующий родитель цели вызывает отказ, а не скрытое создание дерева.
- Источник открыт как существующий SQLite ro и до выделения destination прочитан sqlite_schema. Наличие нужных задач подтверждено описью вызывающего сценария, функция не превращается в валидатор модели Task. Неверный или неоткрываемый источник не оставляет новую цель.
- Существующее назначение, включая обычный не-SQLite файл или каталог, не заменено. Проверка exists сама по себе недостаточна: при выделении имени используется исключительное создание. Проверка не требует удаления чужого файла для повтора.
- Разные SQLite-соединения и файловый дескриптор закрыты и при исключении. Незавершённая запись подготовки не передаётся backup; опись и backup выполняются без новых писателей. Копирование основного файла средствами ОС вместо SQLite backup не удовлетворяет договору.
- Успех объявлен после полного backup, закрытия его ресурсов и нового контрольного ro-открытия. Ошибка передаётся вызывающей стороне, а созданная этой попыткой цель получает INCOMPLETE в наблюдениях; уже существующий защищённый файл не объявлен нашим неполным резервом.
- Ни автоматическое переименование/удаление/повтор, ни ручное исправление исходных данных не маскируют неуспех. Новый повтор использует новый явно выбранный свободный путь. Source schema/data и занятый файл сравниваются с состоянием, снятым до опытов.

### Существенные случаи и способ самопроверки

| Случай | Дано до вызова | Наблюдение, которое различает правильное и опасное поведение |
| --- | --- | --- |
| Существующий source, новый reserve | Писатели закрыты, source описан; reserve отсутствует | Возврат успешного пути, новое ro-открытие reserve/tasks; source schema/data прежние. Совпадение только числа задач не объявляется полным доказательством backup. |
| Источник с опечаткой | `planner-missing.sqlite3` и `planner-never-created.sqlite3` отсутствуют | Отказ до создания назначения; оба имени отсутствуют после вызова. Пустая автоматически созданная source считается дефектом. |
| Один разрешённый адрес | Source и destination равны напрямую, затем через вариант `..` внутри выбранного каталога | Отказ до записи, source схема и все строки прежние. Сравниваем не только исходные строки путей. |
| Занятое назначение | planner-occupied.bin существует с сохранёнными bytes; source корректен | Отказ, точное равенство read_bytes до/после. Одинаковый размер не достаточен. |
| Нефайловый source/занятый каталог цели | Выбран существующий каталог вместо файла | Отказ, каталог и source сохранены; destination-соединение не открывалось для исправления ситуации. |
| Нет родителя назначения | Source известен, `data/backup-work/no-parent/` не существует | Отказ, no-parent и target не созданы; source прежний. Операция не скрывает ошибку пути созданием дерева каталогов. |
| Учебная остановка после xb | planner-interrupted.sqlite3 был свободен; временная строка остановки объяснена | Нет SUCCESS/возвращённого успешного пути, ресурсы освобождены, отдельная цель сохранена со статусом INCOMPLETE. По ней восстановление не начинается. |
| Повтор уже успешного имени | planner-reserve.sqlite3 уже существует | Отказ с сохранением снимка; для новой попытки выбирается другой свободный адрес, исходный резерв не стирается. |

Имена новых диагностических файлов и правила повторов видны до попыток. Для нормального результата проверяем ручной исходник и наблюдаемое поведение вместе; эти требования не объявлены автоматическими hidden tests платформы. Исходные API/CLI-контракты подтверждает входная диагностика и тест для выбранной версии Planner, а целевое изменение только добавляет модуль сохранения. Нет обязательной новой полной регрессионной главы.

### Готовность, помощь и будущий разбор

Локальная готовность каждой карточки есть в её результате. Общая готовность: модуль написан учеником, все адресные отказы проверены, контрольный файл прежний, source schema/data прежние, резерв SUCCESS открывается, опись и три разных адреса сохранены, будущая restore-цель свободна. Неполный backup никогда не даёт готовность к передаче.

Помощь убывает: сначала указать соответствующую модель ресурсов в 02/04 либо расшифровку PRAGMA в 03; затем предложить проверить один различающий случай и назвать затронутый файл; при трудности с ошибкой вернуться к трём исходам 05. Подсказка не выдаёт полный порядок строк Planner-wrapper. После возврата ученик повторяет малую книжную пробу с новым свободным именем и затем своё действие. Нового обязательного средства в подсказках нет.

Будущий разбор Stage 3 идёт в порядке «адреса и состояние → опись → собственное средство → отказы/неполнота → успешный резерв и передача» и объясняет причину каждого результата. Для редакторной практики закрытый эталон остаётся авторским; видимый разбор использует независимые книги и наблюдения, не публикует целевой wrapper. Ни точный алгоритм, ни код решения Planner не передаются теорией или интерактивом. Учебные номера в тексты карточек/подсказок/обратной связи не переносятся.
