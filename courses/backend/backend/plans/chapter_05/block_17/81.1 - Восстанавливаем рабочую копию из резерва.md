## Границы и договор передачи

Работа только с локальными синтетическими данными. Используются прежние библиотеки и способы запуска Planner. Не переписываем API/CLI и модель; не выполняем init_db над восстановленным файлом, миграции или ручное исправление потерянных значений. Негодный кандидат не переименовывается в успешный, исходный резерв не заменяется.

Входные имена выбираются по фактически сохранённым артефактам предыдущего шага. Роли, а не выдуманные имена его wrapper, составляют обязательный договор:

| Роль | Происхождение и состояние на входе | Допустимое состояние на выходе |
| --- | --- | --- |
| `SOURCE` | Исходная синтетическая SQLite предыдущей практики; писатели остановлены | Сохранена без изменений, не становится новой целью |
| `BACKUP` | Именно успешно завершённый резерв SOURCE, с исходной описью | Сохранён, открывается только для чтения; не используется runtime |
| `RESTORED` | Новый отсутствующий адрес, отличный от SOURCE/BACKUP | Сначала кандидат; только после сверки становится заполненной рабочей копией |
| `BASELINE_NEW` | Другой новый отсутствующий адрес | Остаётся отсутствующим, даже пустой SQLite-файл здесь не создаётся |
| `BAD_SNAPSHOT` и `REJECTED` | Отдельные новые адреса отрицательного опыта | Изолированные неполный образец и отвергнутый кандидат, никогда не передаются как рабочие |

Все адреса сравниваются после приведения к абсолютному пути. Сохраняем прежний отказ на существующем назначении, включая пустой файл; повтор требует нового имени, а не очистки. Переход режима явный: BACKUP открывается read-only, RESTORED создаётся исключительно как новое назначение, затем открывается для чтения проверкой и обычным runtime. BASELINE_NEW до следующей темы вообще не открывается.

Служебная передача по паспортам 82/83: восстановимая точка `BACKUP + исходная опись + совместимый код S + инструкция восстановления`, принятый заполненный RESTORED, его явный URL и отдельный BASELINE_NEW. Будущее занятие 82 создаёт историю только на BASELINE_NEW и ещё одном новом адресе, не на RESTORED; 83 позднее потребляет заполненную копию. До применения поставщик/получатель проверяют эти роли и состояния. Изменение схемы в будущих занятиях не делает поздний код совместимым с исходным резервом автоматически.

## 01. Три адреса и точка возврата

**Вопрос ученика:** «Мы уже сделали снимок. Почему нельзя просто дать приложению его адрес?» Начать с назначения резерва как сохраняемой точки возврата. Runtime может писать; поэтому он получает отдельную восстановленную копию. Восстановление переносит содержимое BACKUP в новую RESTORED, а не возвращает запись в SOURCE. Новый адрес baseline нужен для другого режима следующей темы и сейчас остаётся только строкой пути.

**Механизм и напоминание формы.** Разобрать абсолютный `Path`, приведение пути и сопоставление адресов, read-only URI через `Path.resolve().as_uri()` с `mode=ro` и `uri=True`, существующий источник против нового назначения. Отдельно пояснить: обычный `sqlite3.connect` может создать отсутствующий файл; read-only открытие этого не делает. Имена SOURCE/BACKUP/RESTORED являются ролями в плане, в ученическом тексте это исходная база, резерв и восстановленная копия. Защита нового назначения прежняя: исключительное создание, отказ при существующем файле; не заменять её одним `exists()` перед записью. Рабочий каталог и пути с пробелами обсуждаются на абсолютном адресе.

**Учебный визуал вне 00.** Наглядная схема трёх независимых файлов: исходная база → резерв → восстановленная копия; рядом отдельная ещё не созданная цель baseline без входящей стрелки записи. Для каждой вершины показать роль, существует ли файл и кто может его открыть. Независимая сохранённая опись направлена к двум воротам после restore: «структура» и «содержимое»; integrity_check относится к состоянию SQLite, а не заменяет эти ворота. Запуск Planner допускается только после ворот. Данные схемы: условные пути в каталоге опыта, два исходных ID, флаги существования и открытия. Действие ученика: проследить стрелку restore и назвать открываемый для записи файл. Наблюдение: изменяется только новая цель. Пояснение: резерв сохраняется для повторения операции, а опись не берётся заново из проверяемого кандидата. Это статический визуал, интерактив расположен в 03.

**Короткая проба.** Даны существующие `source.sqlite3`, `snapshot.sqlite3` и два отсутствующих пути. После объяснения ученик назначает путь восстановления и оставшийся путь для новой истории, прогнозирует отказ при выборе снимка как назначения. Наблюдаемый критерий: ни источник, ни снимок не становятся целью; оба новых адреса различаются. При ошибке возврат к ролям на схеме, затем повтор с существующим пустым файлом вместо одного свободного имени. Пустой существующий файл тоже занят.

**Переход.** Безопасный адрес ещё не содержит данных. Теперь нужен полный опыт создания отдельной копии.

## 02. Восстанавливаем отдельный файл

**Назначение:** восстановить файл через уже объяснённый SQLite backup API, сохранив guard и явно поменяв роли соединений. Вызов `backup` направлен от читаемого соединения снимка к соединению новой цели; метод сам не защищает занятую цель от замены содержимого. Разобрать обе переменные/аргумент до вызова. Соединения закрываются и при успехе, и при исключении: `with connection` управляет транзакцией, но сам не закрывает sqlite3 connection. Показать явное закрытие в `finally` либо ранее объяснённый closing без скрытой новой формы.

**Полный независимый пример для Stage 3.** Один файл `restore_books_demo.py` создаётся учеником по полному показанному тексту в корне его `project/`; никаких скачиваемых starter или ссылок на будущие файлы. Автор выдаёт все импорты, подготовку, вызовы и ожидаемые наблюдения в одном месте. Пример не реализует Task-проверку и не импортирует будущий Planner restore-wrapper.

- Вход и подготовка: прежняя `.venv` проекта, отдельная новая папка `data/restore_books_demo/`. Небольшой реестр в памяти имеет `books(id INTEGER PRIMARY KEY, title TEXT NOT NULL, copies INTEGER NOT NULL CHECK(copies >= 0))`, строки `(4, 'Маяк', 2)` и `(9, 'Сад', 1)`. Эталон строк и опись реальной схемы сохраняются в переменных до backup. Две строки с разными ID/значениями позволяют обнаружить потерю строки и подмену значения.
- Получение существующего ресурса: тем же уже объяснённым backup API полный текст примера создаёт `books_snapshot.sqlite3` из зафиксированного реестра в памяти, завершает запись и закрывает соединение снимка. Это явная подготовка независимого опыта, не обещание, что файл уже доступен. Пример не повторяет API/CLI Planner и не строит вторую прикладную архитектуру.
- Выбор и открытие: показываем абсолютные адреса `books_snapshot.sqlite3` и отсутствующего `books_restored.sqlite3`; снимок открывается read-only после проверки источника, новое назначение защищено исключительным созданием. Результат создания файла ещё не считается успешным восстановлением.
- Действие: отдельные соединения снимка и новой цели, вызов backup в правильном направлении, закрытие обоих ресурсов. Затем цель открывается заново; 03 продолжает этот же пример проверками, 04 завершает новой SQLAlchemy Session. Для автора это одна полная программа с последовательными участками, а не три несвязанных фрагмента с невидимыми переменными.
- Наблюдение после копирования: появился только новый файл, снимок сохранился; после нового открытия видны обе строки. Ошибочный случай: отсутствующий снимок не создаётся автоматически, повтор на том же существующем назначении останавливается до backup. Достаточно этих случаев в исполняемом примере, поскольку неполноту отдельно различают 03 и практика.
- Причинный разбор: направление определяет, откуда берутся страницы, guard сохраняет занятые ресурсы, повторное открытие проверяет файл после завершения операции. При исключении частичная новая цель помечается непригодной, не передаётся дальше; соединения закрываются. Не внедряем автоматическую очистку неизвестного пути или повтор с перезаписью.

**Первое применение до проектного переноса.** После разбора и прогноза направления, до первого запуска полного примера ученик сам выбирает другое свободное имя назначения вместо показанного и меняет его во всех связанных участках чтения. Локальный критерий после запуска: выбранный новый файл содержит оба исходных ID, резерв не затронут, показанное исходное имя назначения осталось свободным. Это управляемая проба, а не доказательство самостоятельного проектного решения. Не предлагаем слепо запустить всю подготовку заново на занятых именах. Для повторной пробы меняется только вызов restore-процедуры по уже существующему снимку, без повторного создания реестра/снимка; Stage 3 показывает этот отдельный короткий вызов и объясняет импорт из демонстрационного файла, если выбирает такой способ. Демо-подготовка выполняется только при явном запуске файла, не при импорте. При ошибке адреса возврат к 01; при ошибке направления к двум соединениям этого раздела.

**Цена подготовки и минимальный комплект.** До первого полезного наблюдения ученик создаёт одну папку и один демонстрационный Python-файл, запускает один короткий процесс прежним Python; первый участок программы создаёт два SQLite-файла. Реестр в памяти не требует третьего исходного файла, ORM-моделей, сервера или отдельного venv. Отрицательный опыт 03 затем создаёт ещё два явно новых файла, плохой снимок и отвергнутый кандидат; это полная стоимость основного книжного примера. Повторная проба, если нужна после ошибки, требует нового имени назначения и ещё одного короткого вызова. Синтаксис создания реестра/commit/backup объясняется рядом; готовый текст подготовки не объявляется освоением. Ожидаемый первый вывод: абсолютные адреса, завершение restore и два ID. Проверки 03-04 идут в той же программе, без самостоятельного написания вспомогательного фреймворка. Stage 3 обязан выполнить программу и сопоставить вывод, а не заменить её ссылкой на ещё не выданный starter.

**Опора на возврат:** роли двух соединений, `backup(target)`, исключительное создание цели, различие транзакционного контекста и закрытия. Далее открываемый результат предстоит проверить независимо.

## 03. Проверяем структуру и все значения

**Вопрос:** «SQLite открыла файл. Значит, всё сохранилось?» Объяснить четыре разных свидетельства: файл открывается; SQLite сообщает о внутренней целостности; фактическая схема совпадает с исходной; все ожидаемые записи и значения совпадают с независимой описью. `PRAGMA integrity_check` без ошибок возвращает одну строку `ok`; произвольный непустой вывод или отсутствие исключения не означают успеха. Проверка не знает, сколько задач мы ожидали, и не доказывает правильный выбранный файл. FK-проверку не добавляем как новую практику: на этом входе связей ещё нет, и integrity_check вообще не проверяет FK.

**Продолжение полного книжного примера.** После закрытия restore-соединений новая read-only connection читает `PRAGMA integrity_check`, `sqlite_schema`, `PRAGMA table_info(books)` и все `id/title/copies` с явным `ORDER BY id`. Сопоставление с сохранённой до backup описью показывает ту же таблицу, PK, NOT NULL, CHECK и две строки с исходными значениями. Автор объясняет форму результата `fetchall` как список строк-кортежей и отличие сравнения всего результата от одного счётчика. Схема должна извлекаться из реального файла, не строиться заново из Python-описания. Малый SQL для таблицы/чтения подготовлен в полном примере; здесь разбирается причина каждой сверки.

**Различающий интерактив вне 00.** Даны эталон книг `(4, 'Маяк', 2)`, `(9, 'Сад', 1)` и три образца с одинаковой схемой и `integrity_check = ok`: A содержит эталон; B потерял ID 9; C содержит оба ID, но `copies` у ID 9 равно 7. Ученик выбирает, какой образец можно принять, и отмечает недостающее свидетельство/несовпадающую ячейку, а не просто отвечает да/нет. После выбора видит матрицу «целостность / схема / множество ID / значения» и конкретную причину. Обратная связь для B: SQLite внутренне согласована, но отсутствует ожидаемый ID; для C: число строк и ID совпали, однако изменилось значение; для A: пройдены все показанные сверки, запуск приложения ещё отдельный шаг. Изменённая повторная проба скрывает один `title` вместо `copies` и меняет порядок показанных строк. Правильный вывод не зависит от позиции строки, полный эталон практики и её код не раскрываются.

**Мост к Task.** В практике опись берётся до резервирования, а не из BACKUP после restore. Сравниваются множество ID и полные строки по ID, без потери `tags` и `title_normalized`, которые API/CLI не показывают. В SQLite `is_done` читается как 0/1, в публичном ответе как false/true; это представления одного состояния. Для tags сохраняется исходное JSON-значение и порядок элементов, пустой список не равен отсутствующему полю. Достаточно сравнить сохранённое SQL-представление поля с таким же чтением после restore; не требуется писать новый JSON-нормализатор. Не пересчитываем `title_normalized` по придуманному правилу вместо сравнения сохранённого значения.

**Схема и ограничения.** Вернуться к описи предыдущей практики: состав колонок/типов, PK, nullable, SQL-default, CHECK, индексы через sqlite_schema, table_info, index_list/index_info. Реальные CHECK `id > 0` и `priority >= 1 AND priority <= 5` должны остаться; Python-default в TaskRow не превращается в SQL-default. Здесь можно сравнить исходные SQL-описания и результаты PRAGMA напрямую, поскольку восстанавливаем снимок той же схемы; учебного универсального schema-diff не требуем. Новых неверных insert в принятую копию не выполняем: это не изменение схемы, а сверка уже известной структуры. Любое несовпадение останавливает приёмку и возвращает к исходной описи/backup, а не к ручному «лечению» строк.

**Подготовка отрицательного файлового опыта.** Показать в том же полном книжном примере роли ещё двух новых путей, `books_incomplete.sqlite3` и `books_rejected.sqlite3`: плохой снимок создаётся отдельным backup из хорошего, только в этой disposable копии `DELETE FROM books WHERE id = 9` с commit убирает строку. Исходный снимок не открывается для записи. После закрытия плохой снимок снова открывается для чтения и восстанавливается в другой новый кандидат с прежним guard. Его integrity_check может дать ok, но сверка ID отказывает; кандидат остаётся отвергнутым и runtime к нему не подключается. Это объяснение получения отрицательного входа, без целевого SQL/ID задач. Пример подготовки использует уже объяснённые соединение, commit и guard; условие практики назовёт все эти группы до ответа.

**Первая собственная проверка.** После интерактива ученик на данных книжного примера формулирует результат отдельно для пропавшего ID и изменённого значения при прежнем количестве строк. Локальная готовность: указывает точное расхождение и какую проверку оно опровергает. Опора при возврате находится здесь: список кортежей, явная сортировка, роль описи до backup и границы integrity_check. Далее проверяем, видит ли эти данные прежняя сборка приложения.

## 04. Возвращаем Planner к восстановленным данным

**Зачем отдельный шаг.** Правильная SQL-копия может оказаться не тем файлом, который читает уже запущенный Planner. Настройка считывается при сборке ресурсов; смена строки окружения не переносит существующий engine/соединение на другой файл. Новая Session проверяет новое чтение сохранённых данных, новый процесс дополнительно проверяет повторное применение настройки и отсутствие зависимости от прежних объектов в памяти. Это разные доказательства.

**Завершение полного независимого примера.** Для принятого книжного файла показать явный URL через `URL.create` с драйвером `sqlite` и аргументом `database`, содержащим выбранный абсолютный путь, затем `create_engine` и новую `Session(engine)` с `text`-SELECT тех же колонок и явным порядком. Разобрать назначение аргумента database, engine, Session, текстового SQL и чтения строк до запуска; используются установленные зависимости Planner, новая ORM-модель не создаётся. Выход: ID 4 и 9 с прежними значениями, контекст Session закрыт, затем engine.dispose. Не смешивать SQLAlchemy Session, sqlite3 connection и процесс. Это последняя часть одной книжной программы, не ещё один проект.

**Настройка существующего Planner.** По S/config.py показать, что `DATABASE_URL` из окружения имеет приоритет над `.env` (`override=False`), относительный путь разрешается относительно `project/`, а после проверки нормализуется в абсолютный. Для работы используем явный абсолютный URL и тот же `.venv` из корня `project/`. Показать в Stage 3 полный короткий пример запуска с временным окружением текущего терминала, печатью эффективного `load_settings().database_url` перед новым запуском и восстановлением прежнего значения после проверки. Не менять постоянный `.env` и не полагаться на наследование от уже работающего сервера. `Path`/SQLite URI read-only и SQLAlchemy DATABASE_URL имеют разный синтаксис, не подставляются друг вместо друга. На Windows пример URL имеет вид `sqlite:///C:/.../planner_restored.sqlite3`; путь внутри него автор получает из выбранного абсолютного пути, не копирует чужой адрес.

**Узнаваемые действия интерфейса.** В прежнем CLI запуск `.venv\Scripts\python.exe -m app.main`, внутри меню `list`, затем `exit`. После его завершения в том же терминале с тем же URL запускается API тем же Python `-m uvicorn app.api:app --host 127.0.0.1 --port 8000` после остановки прежнего локального сервера или с явно выбранным свободным портом. Через уже знакомый HTTP-клиент, например Swagger `/docs`, GET `/tasks` с достаточным limit читает обе синтетические записи; затем сервер останавливается и CLI запускается заново. Параллельных интерфейсных процессов не требуется. Если порт изменён, адрес запроса меняется вместе с ним. Если выбран второй терминал, URL задаётся и проверяется в нём отдельно: новое окно не обязано наследовать изменённое окружение первого. Отсутствие таблицы/строк не исправляется init_db над кандидатом. `/health` доказывает доступность HTTP, а не чтение задач.

**Проба и перенос.** На двух показанных настройках ученик прогнозирует файл нового процесса и объясняет, почему старый процесс сам не переключится. После объяснения сам выбирает восстановленный URL, читает принятые данные через API и CLI, завершает CLI и повторяет `list` после нового запуска. Сохранение скрытых полей по публичному выводу не утверждается; их доказательство уже получено SQL-сверкой. Только чтение без add/done/delete сохраняет исходную заполненную точку для будущей истории.

**Опора для возврата:** момент чтения настроек, абсолютный URL, остановка/новый запуск, публичные и внутренние поля. Переход в практику: теперь каждое средство продемонстрировано на другом объекте, а перенос к Task и решение о пригодности ученик выполнит сам.

## 05. Что мы будем делать в практике

**Формат и исходная опора:** проектная работа в редакторе/терминале. Успешный резерв, исходная schema/data-опись двух синтетических задач и прежняя среда Planner являются планируемым результатом темы согласованного резервирования; перед началом выполняется проверка A. Новая функциональность создаётся в том же проекте, отдельный CLI или учебный сервис не пишется. Автопроверка script/solve паспортом не назначена; критерии проверяются локальными наблюдениями и обзором написанной процедуры, автоматический результат платформы не обещается.

**Замысел простого контекста для Stage 3.** Перед изменениями схемы нам нужна заполненная копия, которую можно независимо проверить и открыть обычным Planner. Резерв остаётся точкой возврата, поэтому рабочим адресом станет другой файл. Вступительный контекст не содержит готового алгоритма.

**Видимое условие, которое автор развернёт спокойным связным текстом.** На имеющемся успешном резерве мы самостоятельно добавим операцию восстановления и проверку её результата в проект. Назначим свободные пути, получим отдельную копию, сравним её с сохранённой до backup описью и прочитаем прежним Planner. Затем создадим отдельный неполный образец, восстановим его в ещё один новый кандидат и докажем отказ с причиной. Условие до раскрытия помощи обязательно называет все эти группы, все шесть Task-полей, сохранность SOURCE/BACKUP, чтение новым процессом и отдельный свободный путь будущей baseline. Нельзя прятать отрицательный опыт, внутренние поля или выбор нового URL в разбор.

**Место работы и минимальный комплект.** Корень существующего `project/`, тот же `.venv`, источники API/CLI с совместимым кодом S. Собственная restore/check-процедура размещается в новом `app/DBase/restore_db.py` либо добавляется к реально написанному backup-модулю, если его структура это допускает; exact import/API предыдущего wrapper здесь не выдумывается. Если рекомендуемый файл уже занят, выбирается другое свободное имя и оно фиксируется. Для наблюдений достаточно одной записи `docs/restore-check.md` либо дополнения уже имеющейся описи с ясным разделением эталона до backup и новых результатов. Это проектируемые артефакты практики, они не созданы этим Stage и не обещаны как готовые starter.

Новые данные удобно разместить в отдельной свободной папке `data/restore_planner/`: например, `planner_restored.sqlite3`, `planner_incomplete.sqlite3`, `planner_rejected.sqlite3`. Имена являются рекомендацией, все реальные абсолютные адреса записываются до действия. `BASELINE_NEW`, например `planner_baseline_new.sqlite3`, остаётся отсутствующим файлом. Источник и резерв берутся по фактическим адресам предыдущей практики, не копируются под новые условные имена. Получается один изменяемый/новый Python-модуль, одна запись наблюдений и три новых SQLite-файла; исходная пара файлов уже существует. Не нужны новый venv, пакет, web-UI, отдельная библиотека сверки или новая база с вручную набранными потерянными задачами.

Цена запуска практики: выполнение своей restore/check-процедуры на хорошем и плохом входе, отдельные закрываемые соединения для подготовки неполноты, один запуск API и два запуска CLI с их завершением. Подготовку/проверки можно последовательно выполнять в одном Python-модуле; не требуем набора одноразовых служебных скриптов. Команды запуска/место ввода и роль каждого процесса объясняются в 02/04 до выполнения. Весь исходный пример и отрицательная подготовка являются реальной работой ученика; уменьшение числа файлов не заменяет понятного пошагового разбора.

Связанный маршрут «действие → локальный результат»:

1. **Выбираем адреса и подтверждаем точку возврата → вход однозначен, файлы сохранены.**
   - Вход/объект: фактические SOURCE, BACKUP, исходная schema/data-опись и код S. Опора: планируемая A предыдущего паспорта, 01 и 04. Ученик сам читает одну ожидаемую запись, сопоставляет абсолютный путь с эффективным URL, назначает RESTORED, BASELINE_NEW, BAD_SNAPSHOT и REJECTED и записывает их роли.
   - До начала писатели SOURCE остановлены; неизвестный/частичный backup не принимается. Исходная опись содержит обе полные строки: ID, title, priority, is_done, tags, title_normalized, включая синтетические tags из подготовки поставщика. Фактические значения не перенабираются под новый эталон; различение потери строки и подмены значения уже подготовлено книжным примером. Если исходные две строки/внутренние поля ещё не зафиксированы, возврат к подготовке и новому успешному backup у поставщика, без изменения существующего резерва здесь.
   - Локальный результат: таблица адресов показывает существующие SOURCE/BACKUP и отсутствующие новые цели, все попарно различны; опись читается без зависимости от будущего шага. Состояние исходника и резерва фиксируется до операции: содержимое/структура из описи и контрольные байты `Path.read_bytes()` для двух остановленных файлов. Байтовая проверка касается их неизменности, не используется вместо логической проверки восстановленной SQLite.
   - При затруднении возвращаемся к ролям 01 или диагностике поставщика; готовность входа не заменяется созданием пустого SQLite через connect.

2. **Самостоятельно записываем и применяем restore → появляется отдельный кандидат.**
   - Вход: проверенный BACKUP и свободный RESTORED из первого действия. Объект: собственный restore/check-модуль проекта; опора 01-02. Технически готовой может быть только прежняя guard-функция, если ученик её уже написал и может объяснить; выбор направления, соединения restore и проверяющая часть остаются его работой.
   - Ученик сам строит операцию с входом-снимком и назначением, использует отказ на отсутствующем источнике/одинаковых адресах/занятом назначении и создаёт новую цель исключительно; открывает BACKUP для чтения, выполняет backup в новом направлении ролей, закрывает ресурсы. Полного Task-wrapper и кода сравнения в теории нет. Здесь фиксируется завершение копирования, а не готовность Planner.
   - Локальный критерий: после завершения процесс закрыт, RESTORED существует и открывается заново, BACKUP/SOURCE сохранили контрольные байты. Повтор на том же имени обязан отказать до изменения принятого файла; чтобы продолжить после сбоя, выбирается новый адрес. Проверить существующее назначение можно уже полученным RESTORED без отдельного контрольного файла: до/после отказа его байты совпадают. Отсутствующий источник не должен появиться как пустая база.
   - Помощь при ошибке направления возвращает к двум соединениям книжного примера 02; не выдаёт целевой вызов с адресами ученика. Частичная цель остаётся негодной, до проверки не передаётся runtime.

3. **Самостоятельно сверяем и различаем плохой снимок → пригодность имеет доказательство, неполный кандидат отвергнут.**
   - Вход: RESTORED, сохранённая до backup опись, новые BAD_SNAPSHOT и REJECTED. Объект: собственная проверяющая часть модуля и запись наблюдений. Опора 03: полный книжный пример, PRAGMA/SQL-чтение, список строк, сортировка и различающий интерактив. Ученик сам записывает чтение и сравнение Task, не заменяет его выводом API или числом строк.
   - Для RESTORED новая connection после закрытия restore читает integrity_check; схема сверяется с исходной описью по колонкам/типам/PK/nullable/SQL-default/CHECK/индексам. Множество ID и все значения шести полей сравниваются по ID. Наблюдение сохраняет результат каждой группы отдельно, при несовпадении указывает конкретный ID/поле либо элемент схемы. Результат `ok` принимается только как точный результат integrity_check, а не общий статус всех проверок.
   - Отрицательный вход не даётся загадочным готовым файлом. Ученик сам делает отдельную новую копию BACKUP в BAD_SNAPSHOT с уже написанной restore-операцией. Только в BAD_SNAPSHOT отдельным write-соединением удаляет одну выбранную существующую строку по её записанному ID, выполняет commit и закрывает connection; RESTORED и хороший BACKUP не меняются. Затем BAD_SNAPSHOT открывается read-only и восстанавливается тем же способом в новый REJECTED, проверка сравнивает его с исходной описью. Этот кандидат физически может открываться и иметь `ok`, однако теряет выбранный ID; итоговая проверка сообщает отказ с причиной, не печатает общий успех и не разрешает запуск Planner по этому адресу. Умышленную порчу страниц и случайные байтовые правки не требуем.
   - Локальная готовность: на хорошем кандидате все группы совпали; на плохом назван потерянный ID и объяснён предел integrity_check. Отдельно на изменённом случае интерактива объясняется, почему равное число строк не спасает изменённое поле. Если возникает sqlite3 DatabaseError вместо `ok`, это тоже отказ, а не пустой успешный результат; точный текст SQLite-ошибки не фиксируется как контракт.
   - При затруднении помощь сначала возвращает к матрице доказательств 03, затем к независимым книжным данным. Несовпадение не исправляется вставкой потерянной задачи вручную: проверяется опись/резерв, восстановление повторяется на новом свободном имени. REJECTED сохраняется изолированно с пометкой и не включается в точку возврата.

4. **Подключаем прежний Planner и повторяем чтение → восстановленная копия пригодна для продолжения.**
   - Вход: только RESTORED, прошедший все проверки, совместимый код S и явный эффективный URL; объект существующие настройки/процессы, без переписывания API/CLI. Опора 04 и диагностированный прежний запуск из A. Ученик сам формирует адрес из своего абсолютного пути, временно задаёт DATABASE_URL до создания ресурсов, сверяет значение load_settings и записывает его.
   - Новым CLI-процессом выполнить `list`, выйти; API-процесс с тем же URL читает обе строки через GET `/tasks` без фильтра и с limit не меньше числа синтетических строк. Сравнить четыре публичных поля по ID с ожидаемой публичной проекцией описи. Завершить процессы, заново запустить CLI и повторить `list`; сохранённые значения должны совпасть без добавления задач и повторной инициализации. Новые запросы API/CLI создают короткие Session по прежнему контракту, новый запуск дополнительно проверяет настройку/ресурсы процесса.
   - Локальный итог: два интерфейса и повторный CLI видят ожидаемые ID/title/priority/is_done; SQL-сверка уже отдельно доказала tags/title_normalized. SOURCE/BACKUP после завершения сохраняют исходную опись и контрольные байты, RESTORED не мутировал от проверок. Негодный REJECTED не был адресом runtime. BASELINE_NEW всё ещё отсутствует. Восстановить прежнее окружение терминала и остановить учебный API после чтения.
   - Помощь возвращает к моменту чтения настройки и различию URI/URL в 04. Пустой вывод или ошибка таблицы сначала требуют проверить эффективный URL и выбранную копию, а не выполнить init_db. Итог не заменяется `/health` и не требует новой полной регрессии нетронутых write-маршрутов.

Пояснение после маршрута: новая цель появляется только после выбора безопасных адресов. Сравнение опирается на уже сохранённый эталон, поэтому хороший SQLite-файл с потерянными задачами не пройдёт как успешный. Обычные интерфейсы проверяют публичное чтение, отдельный SQL-контроль сохраняет внутренние поля, а новый процесс проверяет повторный запуск по нужному адресу. Эти частные результаты вместе дают проверенную рабочую копию и воспроизводимую точку возврата.

**Последовательные технические критерии для будущего ТЗ, описанные как свойства полученного решения:**

- В существующем проекте есть собственная restore/check-процедура и запись фактических адресов/наблюдений; успешный резерв и исходная опись имеют объявленное происхождение.
- Источник-снимок открывается только для чтения; новое назначение защищено, одинаковый/отсутствующий/занятый адрес не приводит к перезаписи или созданию ложного источника; ресурсы закрываются при успехе и ошибке.
- Успешный RESTORED совпадает с исходной фактической схемой и всеми сохранёнными ID/значениями, включая внутренние поля; итоговая пригодность не устанавливается одним integrity_check.
- Неполный BAD_SNAPSHOT и его REJECTED изолированы от рабочей копии. Проверка выдаёт отказ с конкретной причиной и не считает их рабочей точкой; хороший резерв сохранён.
- Прежние API/CLI и новый CLI-процесс читают ожидаемую публичную проекцию только RESTORED по явному URL; настройки терминала после опыта восстановлены, писатели остановлены.
- Передача содержит источник описи, адрес BACKUP, совместимый код, принятый RESTORED и другой отсутствующий BASELINE_NEW. Нигде не утверждается, что будущая baseline должна создаваться поверх восстановленной заполненной копии.

**Готовность:** ученик может показать сравнения, назвать конкретный потерянный ID плохого образца и по записи повторить восстановление из сохранённого резерва в новый путь. Критерии самопроверки видимы до решения. Визуальное оформление задач на Stage 3 должно показывать условие, ТЗ, готовность и помощь вместе с проектной работой; важные действия не помещаются только в скрываемые ручные карточки.

**Граница помощи и будущего разбора:** сначала адресная ссылка на 01/02 для пути и соединений, на 03 для свидетельств, на 04 для URL/процесса; затем небольшая книжная вариация с другими ID/полем. Полный разбор на Stage 3 объясняет причину каждого наблюдения и возможные ошибки на независимом книжном случае. Не публикует готовый Task-модуль, точный набор строк решения и алгоритм, который остаётся обязательной самостоятельной работой.
