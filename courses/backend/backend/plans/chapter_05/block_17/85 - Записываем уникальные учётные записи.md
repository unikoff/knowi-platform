## 01. Читаем запись и управляем её транзакцией

**Вопрос и цель.** Как получить сохранённую строку и не перепутать её с ещё не подтверждённым объектом? Восстановить короткую Session и подготовить собственные create/get. Отдельно проговорить, что соединение связывает процесс с файлом, Session ведёт ORM-работу, а auth-сессии в этой теме нет.

**Объяснение и формы до первого запуска.** На одном запросе раскрыть `select(LabelRow).where(LabelRow.code == value)`, `session.scalars(statement).one_or_none()` и `session.get(LabelRow, id)`: объект/None, смысл фильтра и первичного ключа. Проверка `is None` предшествует чтению поля. `one_or_none` не скрывает несколько строк выбором первой; уникальное поле гарантирует не более одной. Показать `add` как подготовку ORM, `flush` как запись SQL внутри транзакции с возможным получением id, commit как подтверждение и rollback как отмену. Разобрать явный `try/except` у владельца Session, включая отказ commit, и закрытие в `with`; `with Session` сам по себе не обещает commit. Не требовать знания декораторов нового transaction helper.

**Независимый полный опыт, часть чтения и записи.** На новом временном ресурсе создать labels, сохранить `kept` с weight=1 и фиктивным внутренним note. Закрыть setup. Открыть каталог новой Session, прочитать существующую метку по code и полученному id, затем отсутствующую `missing`; показать копию id/code без note. Отдельной Session добавить `cancelled`, выполнить flush, увидеть выданный id, затем rollback. Свежим чтением установить отсутствие строки по сохранённому id и наличие `kept`. Пояснить, почему одного напечатанного id недостаточно. Фактический результат и команды публикует/проверяет Stage 3.

**Малая самостоятельная проба.** До User-задания ученик выбирает в этом же примере новый свободный code, сначала прогнозирует результат чтения, затем сам меняет только его и заменяет откат на подтверждение отдельной допустимой записи. Видит строку новой Session и объясняет отличие от `cancelled`; при затруднении повторяет с другим code после возврата к flush/commit. Изменение примера является подготовкой, не доказательством самостоятельного User-repository.

**Проекция и существенная путаница.** На labels независимо собрать словарь из id/code: перечень допускаемых полей выбирается явно, внутренний note не печатается целиком. Ученик прогнозирует, сохранится ли скопированный словарь после закрытия Session. Разобрать ORM-объект, safe-копию и срок жизни: при стандартном expire после commit не читать требующие загрузки атрибуты ORM вне Session. Для User позже наружу копируются id/login, внутренний hash и role не показываются. Правило нормализации из схемного занятия переносится единой функцией: trim краёв, ASCII lowercase, 3–32 ASCII `[a-z0-9_]`, без внутреннего пробела и Unicode. Пароль здесь вообще не принимается.

**Опора на возврат и переход.** В этом разделе остаются формы запроса, None, различие flush/commit и явное владение транзакцией. Создание одной допустимой записи уже объяснено; следующий вопрос состоит в том, может ли предшествующее чтение гарантировать отсутствие второй.

## 02. Два чтения ещё не резервируют имя

**Назначение и механизм.** Предварительное чтение сообщает о состоянии в момент проверки и не является резервированием. БД проверяет уникальный code при реальной записи; второй клиент не получает право вставки из старого None. Чередование управляется последовательностью в одном процессе, без потоков, часов, sleep и обещания воспроизвести все гонки.

**Независимый опыт, часть двух попыток.** Продолжить тот же каталог labels, где `draft` ещё отсутствует. Одновременно открыть два разных `engine.connect()` для одного файлового URL и явно связать отдельные Session с connection A и connection B через `bind`. Объяснить, почему два имени одной Session или одна in-memory БД с неясным пулом не доказывают независимость. В каждой короткой read-Session получить None для `draft`, явно закончить чтение rollback и закрыть read-Session, не закрывая два удерживаемых Connection. Это освобождает чтения до записи и не превращает старое наблюдение в новый запрос.

Далее новая write-Session на A добавляет `draft` и завершает commit до записи B. Write-Session на B пытается вставить тот же code с другим note. UNIQUE отклоняет вторую запись. Объяснение отказа и cleanup полностью разбираются в разделе 03 до самостоятельного переноса. После завершения всех операций новая Session прочитает одну `draft`, причём note первой попытки не заменён второй. Порядок «A подтвердил, затем B пишет» нужен для управляемого опыта: удержание A незавершённой транзакции может дать блокировку вместо нужного конфликта. Нельзя выдать такую блокировку за доказанный UNIQUE.

**Учебный визуал вне 00.** Две дорожки A/B и общий столбец «строки labels в файле». Данные: один `kept`, code=`draft` свободен; два read-окна, два write-окна. Наблюдение: после обоих None строка всё ещё не зарезервирована; после A commit число `draft` равно 1; после B отказа остаётся 1. Границы закрытых чтений и окончание commit A отмечены на схеме. Действие ученика: проследить точку, в которой появляется строка, и указать, какой более ранний результат уже устарел. Пояснение связывает ошибку с UNIQUE БД, а не с числом открытых Python-объектов. Визуал не состоит из кода или одинаковых карточек терминов.

**Содержательный интерактив вне 00.** На тех же независимых метках ученик собирает допустимое чередование текстовых событий: чтение A/B, завершение чтений, insert/commit первого, insert второго, rollback. До раскрытия выбирает прогноз: число сохранённых `draft`, состояние Session второй попытки и класс исхода. Компонент не собирает строки Python и не выдаёт решение User-практики. Для взаимной перестановки завершённых A/B прогнозируется смена победителя при одной строке. Для двух разных code ожидаются две записи. При незавершённой первой записи ответ обозначает возможную блокировку/неподходящий опыт, не обещанный конкретный lock-code. Обратная связь показывает состояние на выбранном шаге и причину: None не резервирует, commit делает первую запись видимой, UNIQUE отклоняет дубль, rollback восстанавливает Session. Ошибочный порядок подсвечивает именно незавершённый ресурс; после объяснения даётся изменённый случай с другими code.

**Первая самостоятельность и возврат.** Ученик до исполнения меняет местами роли A/B, сохраняет завершение чтений и прогнозирует содержимое. Затем на разных code объясняет, почему сам факт двух соединений ещё не означает конфликт. Возврат к дорожкам помогает проверить, закрыты ли чтения, без подсказки User-алгоритма. Подготовленная обвязка двух Connection и управляемое чередование доступны полностью до User-задания, а не появляются в его ответе.

**Переход.** Одна строка вместо двух защищает данные; теперь нужно различить причину отказа и вернуть Session к работоспособному состоянию.

## 03. Разбираем отказ и восстанавливаем Session

**Точная причина до понятного сообщения.** SQLAlchemy IntegrityError оборачивает ошибку драйвера в `error.orig`. На независимом labels разобрать `getattr(original, 'sqlite_errorcode', None)` и `sqlite_errorname`: значение по умолчанию означает отсутствие доказательства, не UNIQUE. Код `SQLITE_CONSTRAINT_UNIQUE` подтверждает класс ограничения; дополнительно нужна связь с `labels.code`, а не с любым уникальным индексом. Для учебного SQLite-адаптера допустим узкий сопоставитель этого extended code и точной проверенной сигнатуры колонки в сообщении драйвера. На User перенести проверку на `users.login`. Одного базового `SQLITE_CONSTRAINT` или наличия слова UNIQUE недостаточно. Имена SQLite-constraint не считаются надёжно доступными в сообщении.

Формат сообщения не объявляется универсальным API. Stage 3 фиксирует фактические Python/SQLite/SQLAlchemy версии и на реальном дубле проверяет сигнатуру; если extended code/сигнатура неизвестны, ошибка сохраняется отдельной ошибкой хранения, не `LoginAlreadyExists`. Код классификатора не анализирует целиком строку SQLAlchemy-исключения с SQL/parameters, не печатает ORM, hash или note. Пользователь получает только понятную причину «Имя уже используется» после подтверждения и rollback. Не вводить повторный SELECT как замену доказательству причины исходного исключения.

**Продолжение полного опыта.** После failed flush `draft` write-Session B требует явный rollback, хотя драйвер уже отменил неудачную транзакцию. В контролируемой диагностической ветви того же листинга сначала показать, что новое чтение без rollback даёт PendingRollbackError, затем выполнить rollback и продолжить именно этой Session. Основной нормальный путь сразу откатывает отказ; диагностическая ветвь не является шаблоном приложения. В B создать `review` с weight=2, commit, закрыть Session и оба Connection. Совсем новая Session проверяет: `kept` сохранилась, `draft` одна и принадлежит первой записи, `review` есть. ID не обязаны идти подряд и не сравниваются с заранее выдуманными значениями.

**Различающий отказ.** В том же временном каталоге отдельной попыткой записать свободный code с weight=7. CHECK отклоняет запись; после rollback строка отсутствует, причина не превращена в «code занят». BUSY показать как отдельную документально объяснённую ситуацию блокировки из незавершённой записи, не требовать нового многопроцессного запуска. В практике нужен фактический отрицательный CHECK и проверка, что классификатор отвергает прочие причины; принудительный BUSY на пользовательской БД не требуется.

**Малая проба до переноса.** Ученик по трём наблюдениям «UNIQUE конкретного code», «CHECK weight», «BUSY» выбирает допустимый смысл сообщения и объясняет, какие данные подтверждают выбор. Затем сам добавляет в labels новую допустимую метку после rollback ошибочного weight и проверяет её свежим чтением. При непонимании возвращается к месту failed flush, отличает откат строки от восстановления логического состояния Session и повторяет на другом code. Это причинная диагностика, а не ещё одна проверка факта о commit.

**Мост к Planner и опора на возврат.** Прикладная ошибка и rollback выполняют разные задачи: первая объясняет отказ, второй возвращает возможность новой транзакции. На S repository не владеет Session; User-код сохраняет этот договор. Ошибка flush поднимается к владельцу, который откатывает любую неуспешную запись, включая неподтверждённую ошибку БД. Нельзя молча проглотить ошибку, вернуть safe-успех до commit или повторять запись вслепую. Здесь доступны конкретные признаки классификации, порядок восстановления и безопасное чтение результата; полный User create/get остаётся самостоятельной работой.

## 04. Что мы будем делать в практике

**Формат и контекст.** Изменение проекта. В существующем Planner есть Task-repository; User-схема и правило имени подготовлены отдельно. Нужно добавить операции User и проверить их в изолированном учебном контуре, прежде чем принимать настоящий пароль. Практика не является задачей встроенного редактора с `script`/`solve` и не обещает автоприёмку платформой. Наблюдения в собственном скрипте и локальные assert доступны ученику; фактическое выполнение проверяется позже на Stage 3.

**Видимое условие до подсказки.** Работать из корня `project` тем же Python. Дополнить `app/DBase/repositories.py` и `app/errors.py`, сохранив Task-код, и самостоятельно написать `project/check_user_repository.py`, то есть файл `check_user_repository.py` в текущем корне. Запуск из этого корня: `python check_user_repository.py`. Такое положение сохраняет обычный импорт `app` без правок sys.path; отличие каталога скрипта сверено по [Python sys.path](https://github.com/python/cpython/blob/v3.12.16/Doc/library/sys.rst) через Context7. Запустить свой сценарий последовательно на двух разрешённых одноразовых рабочих SQLite: траектории новой схемы и траектории восстановленной заполненной копии, уже доведённых до User-revision в теме схемы Planner. Взять их точные URL/ревизию из своей сохранённой записи того шага; исходный пользовательский файл, успешный backup и несовместимая аварийная копия не являются целями. До записи прочитать по URL реально существующие users/tasks и метку версии; отсутствующий файл не создаётся вызовом connect. При неверном адресе или недостающей схеме остановиться и восстановить соответствующий предыдущий результат, не вызывать create_all, stamp/upgrade вслепую.

Внешняя подготовка окружения уже объяснена в маршруте резервирования/схемы. Здесь Stage 3 обязан показать на независимом каталоге, как из корня импортируются существующие `make_engine`/`create_session_factory`, читается явно выбранный учебный URL, проверяется существующий путь и открываются/закрываются соединения. Проверочный скрипт получает один URL из явно проверенной учебной настройки, не угадывает default и не обращается к рабочим данным. Точная настройка берётся из окончательного предыдущего материала, без введения второго конфигурационного протокола.

До изменения данных сохранить в отдельном подразделе существующего README: обозначения двух целей и происхождение, ревизию, исходную опись T0 и исходные User U0. T0 содержит все id/title/priority/is_done/tags/title_normalized с сопоставлением по ID; U0 содержит id/login для счёта и проверки сохранности. Внутренние поля существующих User сравниваются в памяти внутри доверенного скрипта, не копируются в публичный журнал. Полные User-строки/ORM/hash и ошибки с parameters не печатаются. Отсутствующий User показывается как None, не как обращение к полям None.

Имена будущего опыта: `lab_alpha`, `lab_beta`, `lab_gamma`, `lab_delta`, `lab_missing`, `lab_check`. До первой записи убедиться, что все шесть нормализованных имён отсутствуют в каждой цели. Если имя уже существует, выбрать один новый общий ASCII-префикс для этого запуска, чтобы каждое имя оставалось в 3–32 символах; записать соответствие в README. Предыдущие фикстуры не удалять. Повторный запуск выбирает новые свободные имена и считает прирост от своего U0, а не ждёт пустую users или ID подряд. Два значения hash берутся из объявленных фиктивных констант, никогда из пароля.

**Связанный маршрут самостоятельных действий.**

1. **Создать и найти User → две подтверждённые безопасные записи.** Вход: разрешённая существующая User-схема, U0/T0 и свободные имена. Объект: новый SqlUserRepository в существующем модуле и отдельная safe-проекция. Опоры: 01, договор входа схемы и реальные S-операции. Ученик сам пишет create/get-by-login/get-by-id, вызов общего normalize_login, создание user-role и явный выбор безопасных полей. В своём скрипте создаёт alpha/beta с двумя фиктивными hash, подтверждает записи внешним commit, закрывает Session и новой Session читает по полученным ID и эквивалентным именам с регистром/краевыми пробелами. Дополнительно выбирает положительный ID, отсутствие которого установлено по текущему набору, и проверяет get-by-id без совпадения. Локально: две новые строки, совпадающие ID при обоих способах поиска, только id/login в safe-результате; missing и отсутствующий ID дают None. Можно проверить эту ступень до работы с конфликтом.
2. **Проверить два независимых отсутствия → сохранить единственный gamma.** Вход: сохранённые alpha/beta, gamma ещё отсутствует. Объект: собственный сценарий проверки и классификатор/прикладная ошибка, не новый API. Опоры: 02 и полный labels-опыт 03, включая bind, завершение чтений и rollback. Ученик сам переносит порядок в свой скрипт, открывает два разных Connection одного файла, привязывает read-Session и получает два None для эквивалентных `" LAB_GAMMA "`/`"lab_gamma"` с фактически выбранным префиксом. Завершает оба чтения, отдельно подтверждает первую create, второй create вызывает с другим fixture hash. Пишет распознавание именно UNIQUE users.login; на подтверждённом конфликте получает LoginAlreadyExists, владелец сразу делает rollback. Локально: одна gamma, не перезаписанная второй попыткой, alpha/beta и U0 не изменены; BUSY/непонятная ошибка не засчитывается как успешная проба конфликта. Нет повторного SELECT перед insert, который отменял бы саму вторую попытку.
3. **Восстановить работу и различить иной отказ → сверить итог новым чтением.** Вход: Session второй записи после явного rollback, та же разрешённая цель и свободные delta/check. Объект: продолжение собственного скрипта и предикат причины. Опоры: 03 и восстановленное 01 владение транзакцией. Ученик в той же B-Session создаёт delta, завершает commit и закрывает ресурсы. Отдельной короткой Session на свободном check делает низкоуровневую ORM-пробу с role=`invalid_role` и фиктивным hash, получает CHECK, устанавливает False у is_login_unique_conflict и выполняет rollback. Проба не расширяет публичный create параметром role. Свежей Session сравнивает все строки и T0, затем прежней сборкой читает список задач через API/CLI по проверенному URL: на пустой новой траектории список пуст, на заполненной дополнительно читается один сохранённый Task по исходному ID. Локально: для текущего набора U0+4 строки, отсутствуют missing/check, gamma ровно одна с первым внутренним значением, delta сохранена; CHECK не назван занятым login. Все T0-поля и U0 сохранены. Второй URL проходит тот же маршрут с собственной U0/T0 и свободным набором.

Первая ступень доказывает написанные операции и границу данных. Вторая переносит подготовленный опыт двух попыток на единое правило имени. Третья отличает сохранность строк от восстановления Session и проверяет пригодность накопленного Planner. При затруднении возвращаемся к соответствующему механизму 01/02/03; подсказка не дописывает методы за ученика. Самостоятельный код сохраняется в одном Planner, а labels остаётся отдельным малым учебным примером.

### Технические критерии готового результата

- В существующем модуле определены SqlUserRepository и safe-проекция; исходный Task-repository сохранён. Session передаётся снаружи; repository не выполняет commit/close и не создаёт глобальную Session. Create делает flush, принимает login/password_hash, хранит нормализованный login и server-side user-role. Успех всей операции зависит от внешнего commit.
- Get-by-login использует то же правило имени, get-by-id принимает положительный существующий/несуществующий ID; найденное возвращается как внутренний UserRow, отсутствие как None. Safe-копия содержит ровно id/login и пригодна после закрытия Session. В hash сохраняется переданное fixture-значение без hash/verify или преобразования; публичного приёма пароля нет.
- Предикат причины принимает SQLAlchemy-ошибку и возвращает True только для подтверждённого UNIQUE именно users.login. LoginAlreadyExists представляет только эту причину. CHECK, BUSY, отсутствие диагностических признаков и остальные ошибки остаются отдельным отказом; они не дают safe-успеха и не запускают автоповтор.
- Два соединения фактически независимы и работают с одним существующим файловым URL. Оба read-scope закончены до записей. Первая запись подтверждена до второй; вторая действительно доходит до ограничения БД, несмотря на два прежних None. Для проверяемого нормализованного gamma есть ровно одна строка; её поля принадлежат первой попытке.
- После неуспешной записи владелец делает rollback. Новая успешная delta создана именно той Session, которая получила отказ, после чего закрыта. Отдельное финальное чтение подтверждает commit; закрытые ресурсы и отсутствие незавершённой первой записи различимы в структуре скрипта, это не обещанная автоматическая проверка stdout.
- После настоящего CHECK свободный check отсутствует, предикат возвращает False; исходный gamma и остальные User не изменены. Для каждой цели итоговый прирост равен четырём, ID могут иметь пропуски. Произвольный неизвестный положительный ID даёт None при условии, что его отсутствие заранее проверено, а не выбрано по предположению об auto-increment.
- На новой и восстановленной траекториях совпадают ревизия и предметный договор схемы; исходные T0/все Task-поля и U0 сохранены. На пустой траектории прежний API/CLI показывает пустой список, на заполненной читает сохранённый Task; поле tags сверяется внутренним SQL-чтением, а не несуществующим публичным полем. API/CLI не получают новых User-маршрутов. В README есть фактические безопасные наблюдения, без фиктивных аккаунтов как данных для входа.

### Локальная готовность, помощь и будущий разбор

Готовность первой ступени видна в safe-результатах и None свежей Session. Для второй ученик сохраняет короткую трассировку «два None, завершены чтения, первый commit, подтверждённый конфликт, rollback», не полный traceback. Для третьей есть успешная delta, отдельно отказ CHECK, окончательная U0+4 и равенство T0. Без одной из этих частей результат не принимается по фразе «дубликат пойман».

Уровни помощи Stage 3: сначала вопрос о наблюдаемом состоянии; затем адрес 01 для flush/commit/проекции, 02 для двух Connection и завершённых read-scope, 03 для error.orig/rollback; затем напоминание соответствующего labels-фрагмента. Ни одна подсказка не содержит полный User-repository или готовый проверочный скрипт. Неизвестные API/параметры не появляются впервые в помощи.

Будущий пошаговый разбор проходит конкретные видимые требования: нахождение точки изменения в Planner, контракт Session, правило имени, чтение/проекция, причина ошибки, своё чередование, восстановление и сравнение исходных данных. Полный независимый объясняющий код остаётся каталогом меток с другими значениями; готовые User-методы не перемещаются в теорию или интерактив. Stage 3 реализует форму разбора согласно ручной проектной практике, без выдачи будущих парольных решений.

### Передача практического состояния

Входные URL и ревизия имеют происхождение из завершённого схемного шага; T0/U0 и префикс записываются до первой операции. `unique_label_probe.py` использует только свою автоматически создаваемую временную БД и не передаёт её практике. `check_user_repository.py` использует только одну явно выбранную существующую учебную цель за запуск; две цели не смешиваются в одном URL. При занятых именах файлов выбирается свободный суффикс и соответствующая команда, без перезаписи старого разбора.

Источник и backup сохраняются; записи разрешены только на двух обозначенных одноразовых рабочих копиях. Это продолжает разрешение изменять восстановленную цель из темы restore, а не ослабляет запрет записи в backup. Новый парольный опыт использует другой новый тестовый путь, который создаётся применением уже проверенной истории после явного перехода к режиму создания. Файл с hash-фикстурами не переименовывается в «пустую базу» и не переносится в login-набор. На этом завершается учебный маршрут; служебная приёмка плана фиксируется отдельно.
