## 01. Как два интерфейса находят одну базу

Штатный вход означает запуск приложения через его обычную команду. В API каждый запрос берёт свою Session, а CLI открывает свою при обработке команды. Сессия задаёт область работы с базой. У каждой отдельные объекты в памяти, но после commit следующая сессия может прочитать сохранённую строку из того же файла. `DATABASE_URL` указывает на этот SQLite-файл. Абсолютный путь однозначно называет файл независимо от каталога запуска. Init создаёт пустую исходную схему по заданному адресу. Запись в один файл меняет строки только в нём. Второй файл с такой же схемой остаётся пустым.

**Учебная схема вне 00.** Показать API A и отдельный CLI B с собственными областями работы и стрелками к одному дисковому файлу `warehouse.sqlite3`. После stop A рядом появляется API C, с новой областью работы и стрелкой к тому же файлу. Подписать, кто записал id и кто позже его прочитал. На боковой ветке CLI указывает на `warehouse-other.sqlite3`: программа запускается штатно, искомой строки в этом файле нет. Схема отвечает на вопрос, что именно должно совпасть при смене интерфейса и что, напротив, начинается заново.

Первый короткий прогноз после схемы. Два процесса запустились успешно, и у каждого напечатан абсолютный путь. Ученик сопоставляет пути и выбирает, какое чтение подтвердит общую строку. Обратная связь показывает полный путь и поясняет, зачем следом читать конкретный id. Опора для возврата: URL отвечает «где читаем», id отвечает «что читаем». Это подводит к полному примеру с двумя файлами.

## 02. Что доказывает чтение после перезапуска

**Полный независимый пример «Склад».** Stage 3 поставляет готовую последовательность с расшифрованными запросами и выводами в теории. Для воспроизведения автор готовит и проверяет один самоисполняемый файл `warehouse_trace.py` со стандартной библиотекой Python, показывает его отдельным видимым блоком. При желании ученик сохраняет один файл в отдельный каталог и запускает командой `python warehouse_trace.py`. Файл сам создаёт временный каталог и две пустые схемы, вызывает отдельные процессы API и консоли, освобождает их и свои временные файлы. Ученик может пройти полное объяснение на странице с нулём созданных файлов и нулём запусков. Пример использует складские записи и свои интерфейсы:

| Этап | Вход и действие | Наблюдение и причина |
| --- | --- | --- |
| Выбор ресурса | Два заранее подготовленных пустых файла `warehouse.sqlite3` и `warehouse-other.sqlite3`. Первый API A открывает основной файл по напечатанному абсолютному URL, например `sqlite:///C:/Temp/warehouse-demo/warehouse.sqlite3`. GET `/health` даёт HTTP 200, отдельный GET `/summary` даёт `total=0, open=0, closed=0`. | Health сообщает, что процесс отвечает. Нули сводки получены отдельным чтением хранилища. |
| Создание | В A отправляют POST `/stock` с `{"name":"Набор"}`. | HTTP 201, запись `{"id":1,"name":"Набор","state":"open"}`. Ответ даёт id из записи, подтверждённой commit. |
| Чтение и изменение | Отдельный терминальный процесс B открывает тот же файл. Команда `lookup 1` читает «Набор, open», `close 1` меняет состояние, `summary` показывает счётчики `total=1, open=0, closed=1`. | Тот же id найден в другом интерфейсе. Команда `close` сохраняет `closed` через commit, сводка теперь учитывает одну закрытую запись. |
| Новое чтение | A завершён. C открывает существующий основной файл с тем же абсолютным адресом, без повторной подготовки или переноса данных. GET `/stock/1`, затем GET `/summary`. | HTTP 200, «Набор», `closed`, та же сводка. У C нет памяти A или B, он читает сохранённый результат. |
| Контраст | В отдельной повторной ветке после создания A CLI B открывает подготовленный, но пустой `warehouse-other.sqlite3`. Запрос `lookup 1` использует фактический id. | B сообщает, что запись отсутствует. Первый разрыв виден на чтении CLI: схема доступна, но адрес другой. В этой ветке не переходят к изменению строки. |

Пояснить границу вывода: новый запрос в A получает новую Session и может читать правильную строку. Чтобы отдельно доказать новый запуск, нужен завершённый A и наблюдение в C. Повторный health в A этого свидетельства не даёт. Файлы с одинаковым именем в разных каталогах сравниваются по полному адресу. Держать рядом короткую опору «адрес → id → значение до и после → поколение процесса».

**Малая управляемая проба и интерактив вне 00.** После примера дать три конфигурации двух файлов и процессов со складским id 1. Ученик выбирает режим и отмечает первый переход, который не сможет подтвердить, затем открывает результат. При общем файле и новом C видит `closed` и `(1, 0, 1)`. При смене адреса только у B видит поиск без совпадения, потому что открыт второй пустой файл. При общем файле и оставленном A видит, что значение может быть правильным, но чтение в новом процессе ещё не состоялось. Обратная связь выделяет соответствующее ребро и называет недостающее наблюдение. После смены режима прогноз можно сделать снова. Проверяются перенос id, выбор первого расхождения и сила свидетельства. Команды Planner применяются в практике.

## 03. От наблюдения на примере к своему Planner

Заранее объяснить, как пользоваться готовой оснасткой в своём Planner. Она подготавливает пустой файл, показывает адрес локального API и полный адрес SQLite, управляет первым запуском и перезапуском, открывает CLI как отдельный процесс. В примере и проекте переход между запусками сохраняет существующий файл. Для чтения HTTP используется знакомый Swagger UI по напечатанному адресу с `/docs`: развернуть метод и путь, нажать `Try it out` для ввода, заполнить тело запроса или положительный id, нажать `Execute` и прочитать новый статус и JSON. В теле `title` означает строку названия, `priority` число от 1 до 5. В пути `{task_id}` подставляется конкретный id из ответа. В консоли Planner `find` и `done` принимают id по приглашению, `exit` возвращает управление помощнику. Устойчивые точки возврата: в Swagger смотреть тело и статус, в CLI сверять отображаемый id и состояние, в оснастке сверять адрес базы и отметки запуска A/C.

Напомнить, как читать сводку на независимом складе: открытие одной тестовой записи даёт `total=1, open=1, closed=0`. После изменения `total` тот же, открытых ноль, закрытая одна. У Planner признак называется `is_done`, а счётчики `total/open/done`. Поля `id/title/priority/is_done` публичны, внутренние tags проверяются готовой регрессией. Короткая проба перед практикой: по напечатанным двум адресам и отметкам запуска из примера выбрать, какой вывод пока допустим после health и какой дополнительный запрос нужен для подтверждения сохранённого состояния. Сопоставить ответ с таблицей из раздела 02.

Готовая регрессия повторно проверяет прежние свойства продукта. На складском примере объяснить разницу между «маршрут жив» и «строка читается», а также между «запись отсутствует в другом готовом файле» и «хранилище недоступно». В проекте первое обнаруживается при `find` на контрастном файле. Отдельный известный отказ контролирует готовый тест: безопасный 503 и сообщение CLI, затем успешная операция на исправном адресе. Предметный 404 и входной 422 проверяются отдельно. По выводу pytest читаем итог и первое имя упавшей проверки. Обвязку и причины её внутреннего устройства достаточно понимать на уровне этих наблюдений.

API запускается через `python -m uvicorn app.api:app` на выделенном loopback-порту без reload, CLI через `python -m app.main` в отдельном дочернем процессе с доступным терминальным вводом и выводом. Меню «Запустить API», «Открыть CLI», «Перезапустить API», «Открыть CLI с другим файлом», «Входные проверки», «Регрессия», «Завершить». Stop ждёт завершения A до старта C; C использует тот же URL и порт, схему повторно не создаёт. Помощник показывает отметки запусков и PID, проверяет health с ограниченным ожиданием. Отдельно метит контрастную команду и её URL. Сбой старта показывает причину; при завершении убираются только собственные процессы и временные файлы. Ни одна проба не обращается к рабочему SQLite, JSON или настройкам в `.env` для выбора базы.
- **`tests/test_planner_acceptance_contract.py` и режим «Регрессия».** Готовый адресный набор сохраняет внешние CRUD/404/422, health и preference-cookie, внутренние tags и SQL-only договор, известный отказ и восстановление. Ориентир на исторические `tests/test_contract.py`, `test_preferences.py`, `test_sql_create.py`, `test_sql_runtime.py` и `test_sql_replace.py`, с учётом фактически реализованной новой редакции. Тесты используют отдельные временные БД, контрольный JSON для проверки отсутствия fallback и восстановление собственного тестового окружения. «Входные проверки» запускают знакомый `python -m pytest -q` с готовым адресным списком из текущей редакции проекта: собственные проверки отказа, отката, наблюдения SQL и выборки. «Регрессия» повторяет этот список и запускает поставленный файл. Процессы pytest получают отдельный тестовый URL, отличный от обоих файлов истории. Автор проверяет состав списка, обнаружение каждого набора и отсутствие обращений к рабочим данным. Ученик читает факт прохождения и первый сбой. Число тестов не закреплено.
- **Граница поставки.** Помощник предоставляет старт, stop, health, изоляцию и запуск проверок. В нём нет автопрогона целевой истории, HTTP POST/GET задач для практики, CLI-ввода find/done за ученика, переноса id или заполненного листа наблюдений. Ученик вводит операции и связывает ответы сам. Временный процессный контраст и регрессионные фикстуры не являются входом следующего занятия.

Перед выдачей Stage 3 воспроизводит инструкцию с обоими открытыми блоками и закрытым разбором: подготовка и обычный запуск, один путь на правильном адресе, отсутствие записи на другом, новое чтение, автоматические проверки и выход. Для сокращения первого опыта пример склада целиком читается на странице, в практике копируются только два готовых технических блока. Сборка ещё одного приложения и написание кода управления процессами ученику не нужны.

## 04. Что мы будем делать в практике

**Формат и старт.** Одна проектная задача на собственном Planner. Готовый SQL runtime и собственные проверки из A берутся из текущего проекта. Оснастка берётся из видимой «Подготовки к проверке» и применяется по инструкции выше. Перед историей проверить готовые собственные тесты и запустить API A. Адрес удачного health указывает, куда отправлять HTTP-запросы.

**Идея для условия.** Проверим, сохранилось ли изменение задачи после завершения первого API. Начинаем с входных проверок и пустого основного файла. В API создаём задачу «Проверить расписание» с приоритетом 3, берём её id и работаем с ним в отдельном CLI. После перезапуска сами читаем эту задачу и сводку через новый API. Затем ищем тот же id в CLI с другим временным файлом, объясняем первое расхождение и запускаем готовую регрессию. По ходу записываем адреса, отметки двух стартов, фактический id, состояния до и после, сводку и результаты проверок в свободно оформленный локальный лист. Оснастка отвечает за запуск и временные файлы, запросы и выводы делаем сами.

**LinkedNotes для обзора**

1. **Проведём один id через интерфейсы.** Получим id из POST, найдём эту запись в отдельном CLI и отметим её выполненной.
2. **Перезапустим API.** Из свежего процесса увидим тот же id, сохранённое состояние и согласованные счётчики.
3. **Проверим расхождение и прежний договор.** Найдём границу, на которой второй файл разрывает историю, и прочитаем результат готовых проверок.

Ответ POST даёт вход CLI. Его изменение даёт ожидаемое значение для GET из C. При расхождении вернёмся к схеме адресов и сверим, какой запуск ответил и было ли изменение сохранено.

**Техническое задание и локальная приёмка**

**Критерий готовности.** Лист позволяет другому человеку восстановить из ответов и отметок запусков один непрерывный маршрут и отличить его от случая с другим файлом или старым процессом. Доказательства собраны с обычных точек входа, на тестовых данных, с прошедшей готовой регрессией. Формат листа свободный. Сверяются значения и происхождение каждого наблюдения.

**Подсказка для Stage 3.** Вернуть к схеме адресов и опоре «адрес → id → значение → процесс». Предложить найти последнюю строку листа, где подтверждены и адрес, и состояние. Не добавлять новую команду, предпосылку или точную последовательность ответа.

**Будущий разбор.** После самостоятельной попытки коротко восстановить причинную цепочку по отдельному набору наблюдений: найти id из ответа, сопоставить два адреса, определить, откуда известно новое состояние, и указать, где контраст оборвал бы доказательство. Полный код оснастки доступен раньше, а демонстрационная запись о практике появляется только в разборе.
