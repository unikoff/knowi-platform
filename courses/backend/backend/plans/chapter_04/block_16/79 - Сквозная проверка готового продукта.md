## 01. Что именно доказала проверка

Сначала определить термины. Проверка доступности отвечает, обрабатывает ли процесс команды или HTTP. Адресное чтение спрашивает конкретную запись по её id. Первый расходящийся факт находится между последним подтверждённым совпадением и несовпадением для одного объекта. Два одинаково успешных старта допускают разные ответы о данных.

**Знакомая ситуация и рабочая модель.** В реестре выдачи оборудование приняли обратно; в списке на стойке только открытые заявки. Следующий самостоятельный вопрос о записи, а не повторный взгляд на индикатор. Полная модель на Python без файлов и установки: сохранить закрытую заявку, открыть список по текущему параметру, прочитать существующий id напрямую, сменить условие видимости, снова прочитать. В примере отдельно открыть промах для отсутствующего id.

```python
tickets = {21: {"item": "штатив", "state": "закрыта"}}

def visible(state):
    return [number for number, ticket in tickets.items() if ticket["state"] == state]

print("стойка отвечает")
print(visible("открыта"))  # []
print(tickets.get(21))  # штатив, закрыта
print(visible("закрыта"))  # [21]
print(tickets.get(99))  # None
```

Пояснить по выводу, почему отсутствие в отфильтрованном списке совместимо с прямым попаданием и почему при `None` прежнего объяснения уже недостаточно. В Planner открытая опора позволяет выбирать между проблемой списка, отсутствием строки и неправильной целью запуска. Пример даёт различающий запрос, а собственная причина определяется по измерениям.

**Интерактив вне 00.** Готовый блок выбора с отложенной обратной связью. Новый вход: в списке закрытых нет заявки 34, а стойка отвечает. Ученик выбирает следующее наблюдение из «повторить проверку доступности», «прочитать №34 напрямую», «сразу сменить параметр». После первой попытки раскрыть ответ адресного чтения: №34 найдена, состояние «открыта». Повтор доступности уже известен, смена параметра до чтения меняет условия. Вторая проба меняет вход на адресный промах №48. Фильтр списка теперь не объясняет этот промах, остаётся проверить, где и какие данные читаются. Не использовать данные и результаты Planner в обратной связи.

## 02. Где процесс читает и откуда взял адрес

Действующая настройка означает значение, с которым запустился конкретный процесс. В реестре каждая стойка берёт выбранный каталог при включении; изменение на пульте относится к следующему запуску. Короткий рабочий пример на том же реестре. В открытом Python-примере §01 выполнить:
```python
import os

selected_state = os.environ.get("REGISTER_VIEW", "открыта")
print(selected_state, visible(selected_state), tickets.get(21))
```
Задать `$env:REGISTER_VIEW = 'закрыта'` перед новым запуском всего примера, затем повторить с `открыта`. При `закрыта` выводится `[21]`, при `открыта` список пуст, а `tickets.get(21)` одинаков. Объяснить наследование при старте и предел модели: в Planner выбирается SQLite-файл, а фильтр и адрес проверяются разными наблюдениями.

**Справка рядом с применением.** В Planner `load_settings().database_url` возвращает разрешённый адрес для нового Python с текущим окружением. `$env:DATABASE_URL` действует в текущем PowerShell и его дочерних процессах; `.env` загружается с `override=False`. Вывод из нового терминала сам по себе ничего не сообщает об уже работающем API. Фактический файл виден в `main` запроса `PRAGMA database_list` той Session, которая только что читала запись. Вернуться к объяснению штатного переключения; показать, как читаются колонки «номер, имя, путь», и что проверка сама ничего в БД не записывает. Для сверки строки открыть только найденный существующий синтетический файл через `path.as_uri() + "?mode=ro"`, `sqlite3.connect(..., uri=True)` и параметризованный `WHERE id = ?` с одноэлементным кортежем. Это самостоятельное наблюдение о содержимом выбранного файла. Если путь отсутствует, режим чтения даёт ошибку вместо создания файла. При совпадающих id сравнить ещё название, приоритет и исходный статус.

**Минимальный вход в практику.** В том же учебном Planner, из `project/`, открыть один отдельный PowerShell с прежним venv. Сразу показать в открытом тексте один готовый вставляемый блок запуска, с небольшим пояснением операций и способом повторить его в новом запуске. Требования к блоку для Stage 3:

## 03. Как проверить сохранение после перезапуска

Фиксация изменения делает его доступным следующему читателю. В журнале выдачи сохранённый возврат видит другая смена, когда открывает ту же ведомость. В независимом реестре из §01 тот же штатив №21. Подготовка уже внутри примера, одна вставка в Python и один автоматически удаляемый файл. Пояснить `TemporaryDirectory` и `closing` как готовую обвязку: они освобождают файл и каталог. `commit()` фиксирует запись, отдельное чтение заново обращается к тому же файлу.

```python
import sqlite3
from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as folder:
    journal = Path(folder) / "tickets.sqlite3"
    with closing(sqlite3.connect(journal)) as writer:
        writer.execute("CREATE TABLE tickets (id INTEGER PRIMARY KEY, item TEXT, state TEXT)")
        writer.execute("INSERT INTO tickets VALUES (?, ?, ?)", (21, "штатив", "на выдаче"))
        writer.commit()
        writer.execute("UPDATE tickets SET state = ? WHERE id = ?", ("возврат", 21))
        print(writer.execute("SELECT state FROM tickets WHERE id = ?", (21,)).fetchone())
        writer.commit()

    with closing(sqlite3.connect(journal.as_uri() + "?mode=ro", uri=True)) as reader:
        print(reader.execute("SELECT * FROM tickets WHERE id = ?", (21,)).fetchone())
```

В первом выводе `('возврат',)`, во втором `(21, 'штатив', 'возврат')`. Повторить на изменённом входе, пропустив только второе подтверждение транзакции: писатель ещё видит «возврат», свежее чтение показывает «на выдаче». В Planner новый процесс проверяем по завершению старого PID и адресу базы, а статус через знакомый GET. В отдельной короткой пробе ученик прогнозирует №21 после закрытия без фиксации и сверяется с выводом после ответа.

**Визуал вне 00.** Готовая статическая схема из элементов курса. Ряд «health → прямое чтение одной строки → изменение и чтение через другой интерфейс → чтение после нового запуска». Под каждым узлом показать одно доказанное свойство на реестре выдачи. Рядом с последним чтением показать два значения состояния по одному id и пункт проверки адреса. По схеме можно назвать, какое свойство ещё неизвестно между узлами; она не предлагает порядок инструментов или причину сбоя именно в Planner.

**Отдельная сводка.** Объяснить и дать рядом с контрольным запуском готовую сверку без тестового файла. Результат GET одной задачи описывает только эту строку. На независимом реестре показать сводку по трём заявкам: две открыты, одна закрыта. SQLite `SELECT is_done, COUNT(*) FROM tasks GROUP BY is_done ORDER BY is_done` в Planner выдаёт число строк на группу (`0` открыта, `1` завершена, отсутствующая группа означает 0). Публичный `GET /stats` отображает счётчики `total/open/done`, где `total` соответствует внутреннему `all` и равен сумме. Повторяемый готовый контроль использует готовую команду чтения с выбранным файлом и этой короткой выборкой и сверяет готовый вывод с HTTP. Команда для открытой выдачи (в `$labFile` уже подтверждённый полный путь к существующему файлу; `-` велит Python прочитать код из терминала, путь попадает в `sys.argv[1]`):

```powershell
@'
from contextlib import closing
from pathlib import Path
import sqlite3
import sys

database = Path(sys.argv[1]).resolve()
with closing(sqlite3.connect(database.as_uri() + "?mode=ro", uri=True)) as session:
    rows = session.execute(
        "SELECT is_done, COUNT(*) FROM tasks GROUP BY is_done ORDER BY is_done"
    ).fetchall()
    counts = dict(rows)
open_count = counts.get(0, 0)
done_count = counts.get(1, 0)
print({"total": open_count + done_count, "open": open_count, "done": done_count})
'@ | & $labPython -X utf8 - $labFile
```

Сравнить три именованных поля с `GET /stats` нового API; при ошибке открытия сверить путь из заметки. Диагностика при несовпадении возвращается к именованным счётчикам, составу той же базы и сопоставлению `all → total` из объяснения сводки SQL. Пример нарушенного ответа `{total: 3, open: 1, done: 2}` отбрасывается благодаря различающимся группам.

## 04. Что мы будем делать в практике

В своей учебной копии Planner, с готовым стартом двух синтетических экземпляров:

- Зафиксируем одну запись и найдём первый факт, в котором показания двух интерфейсов расходятся.
- Установим причину и повторим чтение по тому же id после исправления.
- Изменим статус через CLI, проверим его в двух API-процессах и сохраним команды запуска.

Эти наблюдения связывают исходную запись и итоговое состояние в одну проверяемую историю.

### Практические карточки

Общий вход виден до первой попытки. Используем действующий `$labApi`, локальный адрес, оба учебных файла и доступную справку из §02. Записываем фактический id, название, приоритет и статус в свою заметку. `POST /tasks` принимает `title` и `priority`, например приоритет 3. HTTP возвращает четыре публичных поля; CLI форматирует значения в тексте. Поиск и изменение адресуются положительным id после команды, следующей строкой. В разборе каждой карточки использовать штатную кнопку `tasks[].answer` ручной практики, подобрать другой учебный вход и объяснить наблюдение. Решение, полный маршрут подстановок и тесты новой задачи не выдаются в теории, подсказках, раскрывашках или файлах.

1. **Закрепить исходную запись.** Контекст: известно только, что API отвечает. Условие: в своём API создать открытую синтетическую задачу с выбранным новым названием и приоритетом, записать id из фактического POST и подтвердить эту же строку отдельным GET. Опора: «Что именно доказала проверка» и команды «Где процесс читает и откуда взял адрес».
