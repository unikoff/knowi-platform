## 01. Данные, на которых видно ошибку

Сначала объяснить **различающий набор**: на нём два правдоподобных правила дают разные наблюдения. Аналогия: на стойке выдачи реестровые квитанции должны лежать от меньшего номера к большему. Одна квитанция подойдёт при любом направлении. На тех же квитанциях в короткой Python-консоли показать вызовы `sorted` с обычным порядком и `reverse=True`. Для одной квитанции 4 оба дают `[4]`. После добавления квитанции 12 промежуточный ряд на стойке равен `[4, 12]` или `[12, 4]`. Причина различия в направлении. Порядок ввода квитанций сам по себе его не доказывает.

**Визуал.** Штатная `InteractiveTable` курса с двумя входами (одна квитанция и две) и двумя результатами. Выделить позицию первого различия и связать её со вторым номером. Компонент уже используется для сравнения строк в теме про SQL-выборку.

**Прогноз.** Два коротких штатных `QuizCard`: выбрать, изменит ли вывод повтор той же квитанции или добавление квитанции с отличающимся номером, затем предсказать пару порядков для новых номеров 19 и 6. До выбора видны только новый вход и предложенные ответы. После выбора объяснить, почему повтор одинакового значения оставляет порядок неразличимым и почему `[6, 19]` и `[19, 6]` расходятся. Не дублировать правильный ответ ниже виджета до попытки.

Перенос: при новом спорном правиле сначала сравнить промежуточные списки двух вариантов, потом уже фиксировать ожидаемый ряд и писать утверждение. В Planner выбор ученика касается статуса и предела, и их сочетания с направлением сортировки. Теория не публикует для этой задачи правильные id, размещение записей относительно предела или последовательность действий ошибочной реализации.

## 02. Одинаковый ответ, разные SQL-следы

**Форма SQL** показывает операции, записанные в фактически отправленном SELECT. Аналогия: кладовщик может выдать ведомость только фонарей или передать всю ведомость, чтобы человек выбрал фонари сам. В той же ведомости две строки: фонари id 31 и штативы id 14. Короткий рабочий опыт в одном Python-сеансе с `sqlalchemy.text` и SQLite `sqlite://`: создать `equipment(id, category)`, вставить две строки связанными параметрами, закрыть подготовительную транзакцию, выполнить два SELECT из новой области чтения. В первом взять категорию через `WHERE category = :category`, во втором прочитать те же поля без условия и отобрать фонари в Python. Оба итоговых списка равны `[31]`. Из SQLite в промежуточном результате пришли соответственно `[31]` и две строки. При отсутствующей категории в обоих итогах `[]`, хотя полное чтение по-прежнему принесёт обе строки. Показать текст запросов рядом с выводом двух исполнений. `text(...)` оформляет SQL-команду, `:category` оставляет место связанному параметру, а результат запроса даёт поля `id` и `category` каждой строки. Готовый пример запускается в одном сеансе и выводит короткие ряды, без pytest и отдельного файла.

Повторить знакомое `with capture_sql(engine) as records` вокруг одного чтения. Подготовка и чтение списка записей выполняются вне окна. Новая Session получает соединение внутри окна. Объяснить, что `.statement` содержит SQL, подготовленный к отправке драйверу, как узнать нужный SELECT среди служебных команд и как читать текст после приведения регистра и сведения пробелов через `split()` и `join()`. Открытый пример разбирает один признак `WHERE category` на ведомости. В Planner ученик сам выбирает признаки трёх операций. Брать Engine из тестовой сборки, которой принадлежит запрос. Новый Engine с тем же URL откроет ту же базу, но эти команды пройдут мимо подписки. Значения связанных параметров скрыты в представлении записи. Буквальный текст SQL остаётся видимым. Поэтому в окне параметризованные запросы и синтетические данные. [SQLAlchemy: событие перед выполнением](https://docs.sqlalchemy.org/en/20/core/events.html#sqlalchemy.events.ConnectionEvents.before_cursor_execute), [снятие подписки](https://docs.sqlalchemy.org/en/20/core/event.html#sqlalchemy.event.remove), [скрытие параметров Engine](https://docs.sqlalchemy.org/en/20/core/engines.html#hiding-parameters).

**Визуал и прогноз.** Штатные `InteractiveTable` и `QuizCard` для новой поставки: четыре строки, среди них две батарейки. Две панели ведомостей дают один итоговый ответ, а следы показывают SELECT с предикатом категории и без него. До выбора спросить, какой след позволяет утверждать, что необходимый отбор сделал склад. После выбора раскрыть, сколько строк передаёт каждый путь, где именно стоит предикат и почему совпадение id оставило вопрос открытым. Предикат не объясняет, как SQLite обошла таблицу. [SQLite SELECT](https://www.sqlite.org/lang_select.html).

## 03. Как перепроверить, какой сбой пойман

Регрессионная проверка сохраняет однажды установленное ожидание и сигналит, когда поведение от него отходит. В ведомости выдачи коротко показать запуск по имени для двух наблюдений: одна проверка отвечает за ряд квитанций, другая за место отбора оборудования. Прочитать в выходе pytest имя остановившегося теста, ожидаемое и фактическое значения. При расхождении первым делом сверить промежуточное наблюдение, которое тест проверяет. Общая памятка: ответ расходится, след расходится, либо расходятся оба. Сначала повторить на тех же данных и найти слой расхождения. Строка SQL с условием сама по себе не проверяет правильность результата.

Подготовка первого запуска размещается здесь рядом с применением: повтор прежней безопасной пробы из «Контракт запуска и доступный комплект», сборка фикстуры из знакомых частей по открытым шагам, проверка, что два обязательных теста можно адресовать отдельно. Объяснить свежий `tmp_path`, временную подстановку адреса через `monkeypatch`, порядок `lifespan` при входе в `TestClient` и два места очистки. Показать, почему два Engine с одним URL дают тот же ответ и разный след. `with session_factory.begin()` подтверждает подготовительные записи, HTTP открывает отдельную Session. Нового CLI и запуска dev-сервера для этого не нужно.

**Повторяемый контроль.** Заранее дать открытый порядок «факт → контрольное наблюдение → снова факт» с одной и той же командой запуска. Показать на аналоге, как временная подстановка другого *наблюдения* проверяет, что своё утверждение различает две версии. Источник ожидаемого значения остаётся фиксированным. В карточках контроль результата вычисляется учеником по его собственным строкам, контроль формы дан как нейтральная текстовая карточка наблюдения с совпадающим ответом и SELECT, в котором отсутствует отбор. Для подстановки достаточно временно заменить локальное наблюдаемое значение перед своим утверждением и затем вернуть чтение факта. Это проверка чувствительности утверждения. Реальный ошибочный запрос автор отдельно воспроизводит на изолированной копии проекта. Контроль безопасности выполняется открытой пробой на своём временном Engine. Для общего smoke используются обычные команды из уже имеющегося проекта.

## Спецификация практики для автора

Карточки проектные, отдельные. Условие каждой связывает действие с названным открытым разделом. Кнопка «Разбор» в штатной ручной практике открывает пояснение через связку наблюдение → причина → повторная проверка. Полный код тестов, готовое решение, точные авторские данные и реализации подмен не входят в разбор, подсказку или готовые ученические файлы.

### Карточка 1. Свой набор обнаруживает ошибочную границу

**Контекст и условие.** Planner должен выдать завершённые задачи по убыванию id, максимум две. После входа в клиент подставить учебную фабрику и сверить её Engine через короткую Session. На пустой временной SQLite создать свой смешанный набор и спроектировать проверку ответа. По разделу «Данные, на которых видно ошибку» выбрать, какую правдоподобную ошибку вокруг границы двух строк проверить. На своих строках воспроизвести правильную и альтернативную последовательности операций в промежуточных списках, например короткой пробой в консоли, затем выписать полученные id и первое различие. Ученик сам выбирает id, порядок добавления и статусы. Для решения полезно, что значения id определяют порядок независимо от порядка добавления.

**ТЗ.** В `test_task_selection_result` записан свой прогноз и проверка `HTTP 200` и точного, упорядоченного списка id для `GET /tasks?is_done=true&sort_desc=true&limit=2`. Для выбранных строк правильный результат содержит две задачи. Временная подстановка собственного контрольного результата перед утверждением даёт воспроизводимый отказ при тех же ожидаемых id. В конце сравнивается фактический ответ.

**Готовность и помощь.** Два ряда различаются по понятной причине. Если оба ряда одинаковы, сопоставить, какие строки в каждом варианте дошли до границы, и пересмотреть данные. Простой случай с двумя подходящими строками без помехи может скрыть ошибку. Для объяснения слабого набора вернуться к примеру с квитанциями.

**Разбор.** Проверить учебный URL и восстановить порядок запуска: войти в клиент, сохранить активную фабрику, поставить учебную и вернуть сохранённую до выхода. На входе ученика сравнить доступные для каждой операции строки. Выбрать первый отличающийся ряд и показать, почему проверка его отвергает. Итог оставить в файле ученика для следующей карточки. Автор отдельно убеждается, что набор действительно отбрасывает вариант с ограничением до фильтрации.

### Карточка 2. Отдельная проверка формы запроса

**Контекст и условие.** Ответ из предыдущей попытки совпал. С теми же своими данными проверить Engine активной фабрики внутри клиента и открыть `capture_sql(engine)` только на тот же GET. По разделу «Одинаковый ответ, разные SQL-следы» решить, как на фактическом SELECT доказать статусный отбор, направление id и ограничение размера. Наблюдаемый ответ уже проверяется отдельно.

**ТЗ.** В `test_task_selection_sql` записано самостоятельное утверждение о форме единственного подходящего SELECT к `tasks`: статус участвует в условии отбора по `is_done`, выдача упорядочена по id по убыванию, предел присутствует в SQL. Операции привязаны к своим частям SELECT. Упоминание `is_done` среди возвращаемых полей не подтверждает фильтрацию. Регистр, переносы строк и вид параметров не изменяют смысл проверки. Момент подготовки записей, лишние SELECT и ошибки HTTP отличимы от штатного наблюдения.

**Готовность и помощь.** При правильном ответе можно показать один SELECT и назвать фрагменты, доказывающие три операции. Для повторяемого контроля взять из открытой карточки наблюдений тот же ответ и безопасный контрольный след `SELECT id, is_done FROM tasks ORDER BY id DESC`. На время одного прогона подставить этот след в проверку формы. Утверждение результата не меняется, утверждение формы отклоняет контрольный SELECT. Повторить со снятой подстановкой. Если неверный след проходит, сначала сверить, проверена ли конструкция WHERE с колонкой, а не наличие имени поля. Если SELECT отсутствует или их несколько, проверить HTTP 200, порядок входа в `TestClient`, привязку через `session.get_bind() is engine` и границы окна.

**Разбор.** При пустом следе сначала исключить перезапись учебной фабрики при старте клиента. С правильным Engine показать, чем синтетический след с теми же id отличается от настоящего. Объяснить, что пропуск в форме оставляет возможным отбор после полного чтения. Локальный результат передаётся в третью карточку как второй отдельный тест.

### Карточка 3. Прогоняем регрессию на Planner

**Контекст и условие.** По разделу «Как перепроверить, какой сбой пойман» запустить оба теста на своей сборке. При падении выбрать первое наблюдаемое расхождение: фактические id либо форма запроса. Установить его причину по текущему ответу и SELECT, прежде чем менять запрос.

**ТЗ.** Из `project/` запускается готовая команда `python -m pytest -q tests/test_task_selection_contract.py` (ученик использует выбранное им имя). На нормальном Planner оба теста зелёные. Сохранить фактическую адресную команду в заметке к практике для следующего занятия. При обнаруженном дефекте меняется только доказанная причина, например в существующей цепочке `get_selected_tasks` → `PlannerService.select_tasks` → `SqlTaskRepository.select`. Публичные параметры и схема сохраняются. При зелёном исходном прогоне сохранить регрессию без изменения рабочего запроса. Снять подстановки наблюдений и повторить оба теста. Фикстура по-прежнему подставляет фабрику на время открытого клиента и восстанавливает до закрытия.

**Готовность и помощь.** Налаженный прогон показывает две отдельные проверки. Прежняя параметризованная проба на временном Engine подтверждает отсутствие маркера в видимом следе и снятие подписки. Для готовой проверки совместимости из существующих тестов v2 доступна команда `python -m pytest -q tests/test_storage_availability.py::test_smoke_api_and_cli_read_the_same_task` (работает с временной БД). На историческом v1 её парой служит `python -m pytest -q tests/test_sql_runtime.py::test_cli_main_uses_configured_sql_database_not_json`. При расхождении сначала прочитать, упал ли тест нового GET или прежний общий путь. Подготовленная авторская проверка дополнительно сверяет обычный публичный минимум из договора главы: значения по умолчанию, границы 1/50, 422 за 0/51 и полный список репозитория. Ученик повторяет доступный общий контроль.

**Разбор.** Сопоставить наблюдавшиеся отказы: ранняя граница обедняет список, поздний отбор в Python может сохранить список, но лишает след нужных частей. На исправной сборке закрыть разбор решением сохранить тесты ученика. Если был дефект, показать первое изменившееся наблюдение после точечной правки и повтор всех адресных проверок. Авторские подмены служат для проверки чувствительности и не становятся частью финальной сборки ученика.
