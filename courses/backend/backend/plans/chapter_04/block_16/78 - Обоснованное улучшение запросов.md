## 01. Когда одного ответа мало

**Что объяснить.** Результат выборки показывает, какие строки получил вызывающий код. SQL-след показывает, какую работу приложение поручило SQLite. Логический порядок выбора для этого примера: отобрать подходящие, упорядочить их, взять первые N. SQLite самостоятельно выбирает способ исполнения. По одному счётчику SELECT видно число чтений в выделенном окне, для проверки отбора надо ещё прочитать форму команды. [Семантика SELECT в SQLite](https://www.sqlite.org/lang_select.html).

**Полный независимый пример для Stage 3.** Встроенный готовый опыт «Карточки витрины», целиком на странице. Перед показом автор выполняет его на встроенной SQLite с таблицей `inventory(id INTEGER PRIMARY KEY, label TEXT, state TEXT)`, без дополнительных индексов. Исходные строки по возрастанию id: `(1, «Север», closed)`, `(2, «Смена», open)`, `(3, «Запас», open)`. Берём первую открытую карточку по id, limit 1. Для правильного варианта показать целиком запрос `SELECT id, label, state FROM inventory WHERE state = ? ORDER BY id ASC LIMIT ?`, отдельные учебные аргументы `open` и `1`, строку `(2, «Смена», open)` и список id `[2]`. Показать перенос полей из строки в обычную карточку витрины перед извлечением id.

Для раннего лимита запрос той же витрины оставляет `ORDER BY id ASC LIMIT ?`, возвращает строку 1, а Python отбрасывает её как закрытую. Итог `[]`. При полном чтении SQL упорядочивает все три строки, Python отбирает открытые и оставляет первую. Итог `[2]`, в SQL отсутствуют `WHERE` и `LIMIT`. Показать SQL и результат каждого варианта рядом. Данные загружены до окна чтения. Объяснить, что `?` обозначает место для отдельно переданного значения, а DDL, seed и сообщения о транзакции за пределами счётчика SELECT.

**Учебный визуал.** Таблица из трёх строк «реализация / строки из SQLite / id после Python / верный ответ / отбор с limit в SQLite». На контрастном наборе индикаторы соответственно: правильный `да/да`, ранний `нет/нет`, Python `да/нет`. Акцент на различии между двумя последними столбцами.

**Управляемая проба.** В отдельном интерактиве выбрать набор и реализацию, предсказать id и затем открыть короткий след и объяснение. Набор «первая подходит» меняет только статус карточки 1 на `open`, поэтому все варианты дают `[1]`. Набор «первая закрыта» возвращает исходное состояние. Обратная связь сравнивает прогноз с фактом, показывает отброшенную первой карточку при раннем limit и все три переданные строки при Python-отборе. Ученик называет, какой набор ловит ранний limit и какая проверка ловит полный SELECT при том же ответе. Более короткий контроль переноса: для того же набора объяснить, почему две подходящие строки после отбора помогают проверить limit. Возврат к таблице показывает, на какой стороне произошло каждое действие.

## 02. Как сделать наблюдение проверкой

Сначала покажи готовое наблюдение над витриной как пару «результат + список SELECT в окне одного вызова». На этом же независимом примере разверни один полный учебный тест: `assert` сравнивает список id с ожидаемым, `len` подтверждает один SELECT до обращения к элементу `[0]`, `in` проверяет смысловые фрагменты для предиката витрины, порядка и лимита. Покажи обычный `assert` и смысл его падения отдельно по результату, числу SELECT и форме. Нормализацию регистра и пробелов делает готовый capture. Сравни записи с другими переносами и отступами и с отсутствующим фильтром. Значение заглушки `?` не восстанавливается из лога. Текущая узкая проверка связывает ответ с формой SQL для выбранных входов, полного SQL-парсера и сравнения всей строки ей не требуется.

**Первая попытка.** Дай три уже снятых пары «id и SQL» из примера витрины. Ученик указывает, где падает сравнение id, где проходит id, но падает проверка формы и почему одного `len` хватает только для вопроса о числе чтений. Для возврата оставь рядом схему «сначала ответ, затем один SELECT, затем значимые части этого SELECT». Команда `python -m pytest <путь к файлу> -q` запускается из `project/` знакомым интерпретатором; пояснить, что pytest собирает функцию `test_...`, `-q` сокращает вывод, а FAIL указывает конкретную проверку.

**Мост к проекту и входам теста.** До задания показать, где готовый `read_selection` повторяет знакомое окно `caplog.at_level(logging.INFO, logger=selection_lab.logger_name)` вокруг одного GET. Имя связывает окно с отдельным Engine, а выход из `with` восстанавливает уровень логгера. Затем объяснить договор `seed_selection` и `read_selection`. Когда эти имена стоят в параметрах `test_...`, pytest подставляет готовые функции по имени. В аргументах seed `True` означает завершённую задачу, `False` открытую. Возвращённые id следуют порядку добавления и читаются из списка. Разобрать на других данных короткую пару вроде `([7], ["select …"])`: первый список содержит id из ответа, второй строки SQL в нижнем регистре с одинарными пробелами. Два результата распаковываются в два имени. В Planner `is_done` задаёт подходящий статус, `sort_desc=false` фиксирует порядок id, `limit=1` оставляет первый id среди подходящих. Сверку HTTP 200 и публичной формы ответа выполняет готовая поставка. Ученик выбирает данные и пишет утверждения после получения результатов.

## 03. Запрос, полученный объект и план SQLite

Заверши пример витрины тремя карточками. Покажи сам SQL с `WHERE`, `ORDER BY`, `LIMIT`, уже материализованную `Task` с `id=2`, `title=«Смена»`, `is_done=False` и готовый фрагмент плана `SCAN inventory` для того же SQL и той же схемы. Для карточки `Task` в этой демонстрации готовое преобразование переносит `id` и `label` в `id` и `title`, переводит `open` в `is_done=False`, выставляет учебный `priority=2` и пустые `tags`. В Planner аналогичный переход от строки к предметному объекту выполняет существующий mapping. Назови, какой вопрос решает каждый артефакт: что просили вернуть, что получили в Python, как SQLite решила искать и при необходимости сортировать строки. В этом плане виден просмотр таблицы. `SCAN` совместим с `WHERE` и с остановкой после нужного числа совпадений, поэтому он сам по себе не сообщает, сколько строк фактически просмотрено, или сколько занял запрос. Пояснить, что отдельного шага сортировки здесь не видно, id является первичным ключом. Выдавать готовое наблюдение, не включать запуск `EXPLAIN` в обязательные действия ученика или в тест. [SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html).

**Малая проба.** Ученик сопоставляет три перемешанные карточки с этими вопросами, затем своими словами объясняет смысл `SCAN inventory`. Обратная связь указывает по одному признаку: условия выбора в SQL, значения полей в объекте, способ доступа в плане. При попытке прочитать скорость или id из плана возвращает к вопросу о способе исполнения. Переход к практике: для нужного утверждения достаточно ответа и строки SELECT.

### Спецификация карточки практики для Stage 3

**Доступная поставка и старт.** Автор поместит полный копируемый блок «Оснастка для теста» прямо в видимое условие над подсказкой и разбором, вместе с путём `project/tests/test_sql_selection_guard.py`. Логгер этого Engine исходно выключен на уровне SQL INFO. Автор сверяет свободный путь и запускает блок с рабочим тестом до выдачи. Для копирования нужны видимая карточка и своя рабочая копия. Файл наблюдения служит источником при подготовке оснастки, импортировать его или сохранять прежнюю временную SQLite ученику не требуется. До записи своей функции адресный запуск сообщает, что в новом файле ещё нет тестов.

- `seed_selection(done_flags)` заменяет фиксированный набор наблюдения. Фикстура один раз на тест добавляет синтетические задачи через фабрику Session того же `selection_lab`, задаёт их статус по списку флагов и возвращает новые id в порядке создания. Синтетические title, priority, tags и `title_normalized` готовит оснастка. Запись завершается, подготовительная Session закрывается до наблюдения. Ученику достаточно передать свой список флагов.
- `read_selection(is_done)` использует тот же сброс `caplog.clear()` после подготовки и то же окно `with caplog.at_level(logging.INFO, logger=selection_lab.logger_name)` вокруг одного `selection_lab.client.get(...)`. Параметры `GET /tasks`: заданный статус, `sort_desc=false`, `limit=1`. После окна готовый код применяет перенесённый из наблюдения отбор сообщений своего логгера, оставляет только команды SELECT и очищает SQL от переносов и лишних пробелов, приводя его к нижнему регистру для утверждений. Инициализация, seed, транзакционные сообщения и строки со сведениями о параметрах в список SELECT не входят. Уровень логгера восстановлен, сырые записи не выводятся. Готовый код проверяет HTTP 200 и публичный набор полей, возвращая `(selected_ids, selects)` со всеми SELECT этого вызова, в том числе пустой список или несколько команд. Открытый пример показывает этот готовый фрагмент целиком.
- Поставка оставляет ученику выбор контрастных данных, имя и тело функции `test_...`, расчёт ожидаемых id и все утверждения про id и SQL. Локальный запуск по указанному пути не требует файла из скрытого ответа, настройки рабочего `DATABASE_URL` или запуска сервера.

**Контекст и условие.** Мы уже наблюдали один GET списка. Теперь для той же операции создаём короткую защиту от двух ошибок: раннего лимита и чтения всего списка. В одном тесте на своей временной SQLite подбираем порядок флагов так, чтобы первая по id задача не подходила для основного фильтра открытых задач и в базе было хотя бы две открытые. Просим ровно одну по возрастанию id. Проверяем отдельно простой контроль на том же наборе: переключаем статус на тот, которому соответствует первая задача, и видим её id. Каждое чтение получает свой список SELECT. Основное утверждение о форме SQL относится только к чтению открытых задач. До запуска запишем в тесте ожидаемые id, опираясь на порядок и выбранные флаги. Полный адрес `GET /tasks`, значения параметров и договор результата показаны до раскрытия помощи.

**ТЗ и локальная готовность.** В `tests/test_sql_selection_guard.py` одна новая функция `test_...` принимает обе готовые фикстуры. На простом контроле возвращается ровно id первой подходящей задачи. На контрасте возвращается ровно id первой открытой задачи, который отличается от минимального id набора. Ранний limit даёт пустой результат и проваливает сравнение списка. Полное чтение с фильтром и срезом в Python может вернуть верный id, но проваливает условие формы. Для контраста тест проверяет, что есть ровно один SELECT и что в этом SELECT расположен предикат по `is_done`, порядок `id` по возрастанию и SQL-ограничение `LIMIT`. Сравниваются смысловые фрагменты нормализованной команды, SQLite может оставить `?` и добавить `OFFSET`. Полная строка, формат плана и значения bound parameters не участвуют в сравнении. На нормальном коде `python -m pytest tests/test_sql_selection_guard.py -q` из `project/` показывает `1 passed`.

**При расхождении.** По месту падения сначала сверить собственные флаги, ожидаемый id и границу capture с опорой 02. **Подсказка при затруднении.** Вернёмся к таблице витрины. Какая строка первой попадёт под ранний лимит? Какое наблюдение отличит полный SELECT, если id совпал? Для синтаксиса `assert`, `len` и `in` вернёмся к примеру проверки витрины.
