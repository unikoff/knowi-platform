## 01. Что получает другой человек вместе с README

- Начать с двух папок одного склада инструментов. В рабочей есть готовая `.venv`, локальный `.env` и `stock-demo.sqlite3` с таблицей. В чистой есть исходники, тест, requirements, README и `.env.example`. Объяснить, почему фраза «у меня работает» не указывает, откуда появились пакеты, локальный адрес и схема. Инструкция проверяется на тех байтах, которые передаются, а не на одном номере ревизии.
- Объяснить процедуру подготовки: указать исходный каталог и новое назначение, сверить предлагаемую опись с чек-листом и подтвердить. Путь в кавычках передаётся целиком, даже при пробеле в названии. Реальный `.env` хранит выбранные для этой машины значения, переменная процесса может иметь приоритет. `.gitignore` объясняет обычное исключение из Git, но не доказывает состав собранной папки.

## 02. Почему порядок команд можно проверить

- Полный независимый пример для Stage 3 на готовом микропроекте склада. В теории показать исходную папку `stock-demo/` с `README.md`, `.env.example`, `requirements.txt` (FastAPI, Uvicorn, python-dotenv), `requirements-dev.txt` (runtime-зависимости и pytest), `stock.py` (init/list/add), `stock_api.py` (GET `/items`) и `tests/test_stock.py` с изолированной SQLite. CLI и API используют одну таблицу `items` с полями `id` и `name`. Init выполняет `CREATE TABLE IF NOT EXISTS` согласно схеме примера. В исходной инструкции чтение списка расположено перед init. В чистой копии изначально есть только эти файлы. В Stage 3 автор проверит и покажет в теории весь ход с командами и результатами. Ученику достаточно открыть пример и сделать прогноз.
- Показать целиком причинный ход. Из `stock-demo/` создать `.venv` командой `py -3.12 -m venv .venv`, использовать `.venv/Scripts/python.exe` для `--version`, `-m pip install -r requirements-dev.txt` (этот файл включает runtime requirements) и всех следующих запусков. Объяснить, что `-m` запускает указанный модуль выбранным интерпретатором. Показать `STOCK_DB=stock-demo.sqlite3` в `.env.example` и команду `Copy-Item .env.example .env` из корня примера. Оба интерфейса читают этот файл настроек, а путь к SQLite расположен прямо в уже существующем корне склада. Перед init убедиться, что базы в корне ещё нет. `stock.py list` до init даёт «no such table». Файл SQLite может появиться уже при открытии, поэтому сам факт наличия файла не доказывает наличие таблицы.
- Уточнить README склада: перенести `stock.py init` перед чтением и повторить с новой чистой копии. Через выбранный Python `stock.py list` печатает пустой список. После локального запуска `-m uvicorn stock_api:app --host 127.0.0.1 --port 8010` запрос GET `/items` возвращает `[]`. Через CLI `stock.py add "Ключ 10"` появляется строка `{id: 1, name: "Ключ 10"}`. После остановки своего API, повторного init и запуска нового процесса CLI и GET возвращают ту же строку. `-m pytest -q` проходит на отдельной фикстуре. Init добавил отсутствующую таблицу. Повторный init сохранил строки совместимой схемы. Проверки с другой SQLite не свидетельствуют о состоянии файла запуска.
- **Интерактив вне 00.** На данных склада упорядочить пять шагов: новая venv, зависимости, адрес, init, первое чтение. Предсказать первую точку расхождения, затем нажать «Проверить». В нормальном варианте видно `[]`. При перестановке init с первым чтением видно «no such table» в чистой копии и успешное чтение в рабочей с готовой таблицей. При удалении venv заявленный исполняемый файл отсутствует. Обратная связь называет недостающий объект и его готовый источник в рабочей папке. Ученик пробует один изменённый порядок и объясняет, какую часть инструкции следует проверить. Вставка подготавливает перенос без текста исправленного README Planner.

## 03. Какие наблюдения доказывают запуск

- Показать на данных склада, что успешный ответ процесса и чтение нужной базы отвечают на разные вопросы. Сначала создают строку и записывают id и значения. После init и запуска нового процесса повторяют чтение и сравнивают значения. Два ответа по разным адресам могут быть успешными и читать разные файлы. В первой проверке ученик отмечает, каких свидетельств ещё не хватает, если есть только health или значение сразу после записи. Объяснить проверку состава и образца перед передачей: в образце склада только безопасный локальный адрес, а полученный из него `.env` и созданный файл SQLite исключены из описи.
- Связать с уже знакомым Planner. Рабочий каталог с `app/` и `tests/` нужен для запуска модулей и тестов. Подать локальный `DATABASE_URL` по README всем процессам. Для исторического Settings относительный путь разрешается от корня проекта, а переменная процесса имеет приоритет над `.env`. На своём проекте ученик ориентируется на проверенный адрес и указанный каталог. Пояснить, что синтетическая строка видна в `GET /tasks/{id}` и в CLI `find`. Фактический id берётся из ответа на создание. Успешный health помогает найти запущенный процесс, а пустой список после init подтверждает реальное чтение первоначальной схемы. Достаточно повторить один маршрут и готовую регрессию. Матрицу всех операций и tags заново вручную не проходить.
- **Разбор ветвей до практики.** В исправленном складском README первый запуск от пустой папки проходит. Если строка шага уже точна, свидетельством служит запись успешного прогона. Если документации не хватает, искать первый недостающий вход, менять ближайшее указание и повторять с состоянием до этого шага. Ошибка «no such table» после перескока через init возвращает к порядку в инструкции. Тот же симптом после успешного init возвращает к сравнению адресов. Если прежний пробный шаг уже создал проверяемый файл или установил недостающий пакет, повторить из свежей цели по той же оснастке, чтобы эффект не скрыл пробел. Рабочий проект и локальные данные при диагностике не использовать. Отсюда переход к самостоятельному решению о пригодности своего README.

## 04. Что мы будем делать в практике

Один проектный маршрут. Обзор будущей теории оформить одним `LinkedNotes`:

1. **Запустим свой README с чистого места.** Подготовим отдельную папку из своего проекта и увидим, получает ли новый пользователь окружение и пустую исходную SQLite по инструкции.
2. **Проверим запуск и состав передачи.** Сверим одну пробную задачу между API и CLI после повторного init и нового запуска, запишем результат и проверим, какие файлы можно передать.

Первая проверка показывает, хватает ли инструкции для старта. Вторая проверяет, что оба интерфейса читают подготовленный файл и что следующий человек сможет получить те же входы.

### План единого задания

**Контекст и условие.** Другому разработчику предстоит получить ваш работающий Planner. Возьмите свой проверенный SQL-проект и его README. В видимых материалах задания откройте комплект «Проверка чистого запуска» и по инструкции подготовки получите отдельную копию. Пройдите собственный README из этой папки с новой средой и явным адресом новой учебной SQLite. Зафиксируйте результат окружения, init, тестов и двух интерфейсов. Сохраните наблюдения об одной пробной задаче до и после повторного init и нового процесса. Если команда отсутствует, указана не там или не работает, уточните нужный фрагмент README и перепроверьте участок. Если всё работает, отметьте это в записи прогона. По открытому чек-листу проверьте передачу безопасного образца настроек и состав отдаваемых файлов. Своими остаются исполнение README, вывод о причине первого сбоя, правка при необходимости и сверка передачи. Команды проверок и управление процессом подготовлены.

**ТЗ и локальная приёмка** (для автора: опоры §01–03 приведены служебно, при выдаче связывать по названию темы).

1. **Проверенный старт.** Входом служит свой проект после сквозной проверки, его README и описанная оснастка. Ученик сверяет источник и опись, выбирает свободное назначение и подтверждает подготовку. После копирования проверяет файлы и начальное состояние по §01. Нормальный случай: код, документация, объявленные зависимости, тесты и проверенный образец на месте. В копии нет локального `.env`, среды и SQLite. Если каталог занят или в описи рабочая база, остановить подготовку, выбрать свободный путь или уточнить выбор файлов. Никакая рабочая папка не перезаписывается. Записать источник и опись в выданные заметки.
2. **README и первый запуск.** Входом служит отдельная папка из шага 1. Ученик сам выполняет команды из README, ставит объявленные зависимости через новый Python, указывает отдельный учебный SQLite-адрес и выполняет явный init перед первой операцией с задачами. Опоры §02 и проверка адреса из §03. Локально видны интерпретатор внутри новой `.venv`, адрес до init, отсутствие пробной базы на старте и `[]` из рабочего чтения после init. Различающий случай: меню или health могут открыться, но при пропуске init на новой цели чтение не вернёт `[]`. Если README действительно приводит к такому сбою или требует невидимую настройку, записать первый провал, уточнить документ и повторить с предшествующего чистого состояния. Если штатный путь проходит, подтвердить его по тем же наблюдениям без искусственной правки.
3. **Прежнее поведение в новой копии.** Входом служат исходная схема шага 2, готовые проверки и процессная памятка. Ученик в том же учебном файле создаёт через API задачу «Пробный запуск» с приоритетом `2` (HTTP 201), сохраняет её фактический id, повторяет знакомые `find` и `done` из CLI, перечитывает задачу с флагом выполнения и фиксирует id, заголовок, приоритет и выполненный статус до повторного init. Останавливает свой API, повторяет init на том же файле, открывает новый API-процесс и сравнивает `GET /tasks/{id}` (HTTP 200, те же значения, `is_done: true`) и CLI `find` по тому же id. Опора §03 и собственная сквозная проверка на входе. Пустой ответ, отсутствующий id или успех только в старом процессе не закрывают этот шаг: сверить URL и факт перезапуска. Запустить готовую регрессию проекта через ту же venv на изолированных фикстурах, записать команду и фактический итог. Фактический счётчик зависит от проекта.
4. **Передаваемые файлы.** Входные материалы включают итоговый README, запись прогона, видимая опись и исходные настройки. Ученик сам сверяет итоговый список и содержимое `.env.example` (или фактического образца, на который ссылается README) по §01 и решает, что входит в передачу. Проверенный образец содержит локальный тестовый SQLite-адрес без учётных данных. README указывает, как применить образец. Передаваемые файлы включают код, объявленные зависимости, тесты и инструкции. Рабочие `.env`, venv, базы, архивы и журналы с данными исключены, даже если оказались рядом после прогона. Если образец ссылается на рабочую базу или содержит секрет, сверка не проходит до исправления и повторной проверки применения образца. Итоговый README и образец из пробной копии возвращаются в собственный проект только если ученик исправил выявленный пробел. Исправленный состав передачи зафиксировать по описи, синтетические данные для следующего занятия хранить локально.

**Подсказка.** Вернуться к первому расходящемуся наблюдению и проверить, какое состояние было до этого шага. Для различия пустого списка и отсутствующей таблицы открыть опыт со складом. Для различия ответа процесса и общего файла вернуться к сравнению по id.

**Будущий разбор после попытки.** На отдельном варианте склада показать запуск с локальным переопределением пути: сравнить первый сбой с нормальным чистым запуском, найти условие, которого не было в инструкции, и повторно проверить только затронутый участок с чистой целью. Затем на уже точной инструкции показать запись фактов без правки. Закончить сверкой безопасного образца, сохранённой строки и содержимого передачи. Не давать готовую редакцию README ученика.

**Итог готовности.** По заметкам можно восстановить, какие файлы и команды проверены, что подтвердилось и почему понадобилась правка либо почему она не потребовалась. Общий SQLite-файл и одна и та же задача видны после нового процесса. Готовая регрессия подтверждает прежнее поведение, а передаваемый набор проверен отдельно от состояния папки после запуска.
