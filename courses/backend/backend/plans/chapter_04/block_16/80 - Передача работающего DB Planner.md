## 01. Что действительно получает другой человек

Сначала назвать **комплект**: файлы, которые получатель может использовать сразу или явно создать по инструкции. Аналогия с передачей учёта выдачи: бланк нужен всем, заполненный журнал принадлежит прежней смене. Короткий рабочий пример для автора: `needed = {"stock.py", "guide.txt", "settings.example"}`, `sent = {"stock.py", "guide.txt", "shift.db"}`, `print(sorted(needed - sent), sorted(sent - needed))`. Разобрать две разности множеств. Первая показывает пробел, вторая указывает кандидатов на лишние файлы. Вывод `['settings.example'] ['shift.db']` обнаруживает оба разрыва при одинаковом числе файлов. Фактический проект выбирает файлы по смыслу, в том числе относительные ссылки README и зависимости тестов, поэтому подсчёта или подстановки списка из примера мало.

Первая попытка: добавить безопасный бланк и убрать архивный журнал. Предсказать и затем увидеть обе пустые разности. Другой вход для проверки переноса: инструкция ссылается на `labels.csv`, файла в папке нет. После выбора показать, что отсутствие замечается при сверке ссылки даже при наличии «всех файлов с кодом». Для практики оставить открытый чек-лист состава и показать список фактически видимых файлов в редакторе, включая скрытые. Свою опись и решение об исключениях составляет ученик. После проверки коробки можно проверять инструменты и адрес.

## 02. Откуда берутся Python, зависимости и адрес

Назвать **чистую среду** и **адрес запуска**. У новой смены свой ящик инструментов и отдельный пронумерованный журнал. Рабочий стол прежней смены может скрыть, что инструкция забыла положить ключ или указать номер шкафа.

Короткий опыт на той же аналогии без второго проекта. Сначала проверить `py -3.12 --version`. В первом терминале задать `$env:STOCK_LABEL = "shelf-7"`, в двух терминалах выполнить `py -3.12 -c "import os, sys; print(sys.executable, os.getenv('STOCK_LABEL'))"`. Опыт требует только установленного Python. Напомнить, что `-c` выполняет текст Python, `sys.executable` даёт путь запущенного интерпретатора, а `getenv` читает окружение процесса. У дочернего Python первого терминала та же метка, у второго вывод `None`. Для опыта выбрана новая метка, чтобы второй терминал её не унаследовал. После прогноза ученик один раз задаёт метку во втором и видит её у обоих. Тот же пакет можно поставить в один Python и пытаться импортировать в другом. Сверяем полный путь исполняемого файла до установки и после, вывод установки и его перечень объявленных пакетов.

Открытая справка к действиям: `py -3.12 --version` показывает доступный Python 3.12, `-m venv .venv` создаёт среду, `-m pip install -r` читает файл пакетов, запись `-r requirements.txt` подключает второй список. Указать роль обеих зависимостей и `-m pip show` с именем установленного пакета. Запуск по полному относительному пути Python не требует активации. Команды выполняются из каталога с `app/` и `tests/`. Именно от корня проекта проверенный Settings разрешает относительное имя в SQLite URL. Для Planner показать только способ получить факт `load_settings().database_url`, как сопоставить URL с выбранным абсолютным путём, как проверить родителя и свободное имя файла. Новый родительский каталог создают до init. `.env.example` сам по себе не загружается. Явное окружение процесса имеет приоритет над `.env`. Перед первым init два свежих терминала должны видеть один выбранный учебный URL. Ученик выбирает свой свободный адрес и выясняет, хватило ли его README.

## 03. Пустой файл, пустая таблица и явный init

Назвать **схему**: правила, по которым может храниться строка. Аналогия с листом учёта: чистый лист без колонок, пустой бланк с разметкой и заполненный бланк дают разные возможности. **Init** готовит отсутствующую разметку. В исходном Planner явный модуль вызывает `Base.metadata.create_all`, а повтор на совместимой схеме оставляет её строки. Успешный запуск процесса не читает схему сам по себе.

Независимый опыт с одной временной картотекой выдачи. Короткий пример охватывает два соседних состояния. Через `TemporaryDirectory` и `Path` выбрать новый `loans.db`. Сначала `Path.exists()` ложно. Автор создаёт пустой файл, чтобы показать второе состояние, и отдельное чтение `SELECT sql FROM sqlite_schema WHERE type='table' AND name=?` с параметром `("loans",)` даёт `None`. Выполнить `CREATE TABLE IF NOT EXISTS loans (id INTEGER PRIMARY KEY, item TEXT NOT NULL)` и закрыть запись. То же чтение возвращает DDL, `PRAGMA table_info(loans)` показывает `id` и `item`, `SELECT COUNT(*) FROM loans` даёт `0`. Пояснить `pk`, `notnull`, `dflt_value`, как читать `fetchone()` и почему счётчик проверяют после обнаружения таблицы. В открытой справке показать также `PRAGMA index_list(loans)` и `PRAGMA foreign_key_list(loans)`: пустые результаты означают, что таких объектов нет. Отсутствие `dflt_value` совместимо с Python-default ORM. Для первой пробы показать бланк с таблицей `returns`, предложить до вывода решить, создана ли `loans`. После ответа показать: файл существует, нужная таблица отсутствует.

**Готовая наблюдательная опора в открытой теории.** Встроенный маленький фрагмент на том же примере с выбором файла, проверкой его существования и чтением схемы без создания. Использовать `Path.resolve().as_uri() + "?mode=ro"`, `sqlite3.connect(..., uri=True)` и `closing`. Объяснить, что `as_uri()` строит файловый URI даже с пробелами, флаг включает его разбор, `mode=ro` даёт отказ на отсутствующем файле, а `closing` закрывает соединение. Читаемые SQL-команды и назначение каждой строки видны рядом. Дать запуск через Python из venv или вставку блока в его консоль. Фрагмент печатает факты и не исправляет данные. Ученик задаёт собственную цель и сравнивает вывод с `TaskRow`. Минимум сверки: шесть `NOT NULL` колонок `id/title/priority/is_done/tags/title_normalized`, `id INTEGER PRIMARY KEY`, `CHECK id > 0` и `CHECK priority 1–5` в DDL, отсутствие SQL DEFAULT, FK и дополнительных индексов, `COUNT=0`. Один вывод без DDL, как и наличие файла, критерия не закрывает. Следующий шаг начинается с уже подтверждённого файла.

## 04. Как узнать, какой файл открыл каждый процесс

**Фактически открытый файл**: путь из SQLite-соединения, которое обслужило обычный запрос. Два окна выдачи могут показать одинаковые пустые журналы из разных шкафов. Короткий рабочий опыт: взять автоматическую подготовку двух журналов из открытого `OPENED_DATABASE` в разделе «Подключаем оба входа и проверяем открытый файл». Адаптировать оба журнала к нулю строк, показать два одинаковых результата чтения и два разных `main`. После SELECT та же открытая Session выполняет `reader.execute(text("PRAGMA database_list"))`; строка `main` содержит имя основного файла. `Path(opened).resolve()` нормализует отображаемый адрес. При пустом `opened` файловое свидетельство отсутствует. Подготовку примера выполнять целиком одной командой или интерактивом. Ученик обойдётся без сборки отдельного сетевого приложения.

**Готовая опора из открытой теории.** Повторить сам фрагмент считывания `main` на Session журнала вместе с назначением `text`. Показать, как временно применить эту диагностику на копии после фактического SELECT в точке, через которую проходит обычное чтение. Для проверенного Planner HTTP `GET /tasks` идёт в `SqlTaskRepository.select`, CLI `list` в `SqlTaskRepository.list`, хотя оба класса используют `self.session`. Ученик открывает свой `app/DBase/repositories.py`, находит эти методы и подставляет свою уже открытую Session, запускает оба чтения по README, сравнивает три адреса и удаляет временный вывод до записи. Не использовать отдельную Session для доказательства чужого пути. Настройки считываются процессами при запуске, поэтому правка переменной требует нового запуска. Вывод оставлять только в терминале данной учебной копии. HTTP показывает JSON `[]` и 200. CLI показывает «Список задач пуст.». `/health` проверяет процесс и может успешно отвечать при неподготовленном файле.

**Визуал вне 00.** Готовые `Diagram`, `DiagramLane`, `DiagramNode` и `DiagramArrow`: две дорожки «HTTP → выборка → её Session», «CLI → список → его Session», от каждой один `main` до целевого файла. Два состояния: оба указывают в A, либо один в A и другой в B. Выдачи в обоих случаях пустые. Подписи показывают, что ответ подтверждает содержимое, а `main` адрес. Чтение дорожек готовит сравнение двух независимых наблюдений.

**Интерактив вне 00.** Готовый `QuizCard` с прогнозом по журналу выдачи: на стойке A забрали последний инструмент, A пуста; у второй стойки открылась другая уже инициализированная пустая картотека B. Перед показом следа ученик выбирает, какой факт лучше различит причины, и прогнозирует, какой из двух путей совпадёт с выбранным A. После выбора показать обе выдачи `[]` и отдельно два пути. При выборе health объяснить, почему ответ процесса не касается журнала; при выборе сравнения списков показать, что у двух пустых журналов одинаковое содержимое. Изменённый вход для второй пробы: у стойки B файла нет, успешный health совместим с отказом чтения. После попытки объяснить, какое свидетельство отсутствует. Карточка обучает чтению улик, без операций или строк README Planner.

## 05. Как доказать сохранность после повторного init

**Идемпотентность** в этом опыте означает, что повтор явного init на том же уже подготовленном файле не меняет схему и записанные там данные. В журнале выдачи одна строка «18, Ключ 10». Короткий опыт продолжает пример из «Пустой файл, пустая таблица и явный init»: записать и подтвердить эту строку, 1) прочитать `SELECT id, item FROM loans WHERE id = 18` в отдельном чтении и сохранить кортеж, 2) ещё раз вызвать ранее показанный `CREATE TABLE IF NOT EXISTS`, 3) закрыть запись, заново прочитать тот же id, вывести сравнение кортежей. `True` объясняется совпадением обоих значений, а подтверждённая запись переживает закрытие ресурса. Прогноз на другом входе: номер 21 присутствует до опыта, после него вернулись 21 и другое название. После попытки объяснить, почему прежний id без сравнения полей не доказывает сохранность.

В Planner до повтора фиксируем фактически выданный id и четыре HTTP-поля, плюс полный кортеж той же строки по известному id из проверенного SQL-файла. Скрытые в публичном интерфейсе `tags` и `title_normalized` проверяются только чтением SQL. Ученик сам выбирает синтетические данные, сравнивает с сохранённым наблюдением и объясняет первый разрыв. В CLI или API показываем только форму прежних команд: POST с `title` и `priority`, GET одного id, `find` с id, `exit` и Ctrl+C для своего API. Как обратиться к той же строке после повтора, ученик связывает из уже проверенных наблюдений.

**Готовый повторяющийся контроль.** В открытом условии дать точный вызов `.\.venv\Scripts\python.exe -m pytest -q tests/test_storage_availability.py::test_smoke_api_and_cli_read_the_same_task` и общий `.\.venv\Scripts\python.exe -m pytest -q` из проверочной копии. Объяснить `-m pytest`, `-q`, `путь::имя`, отличие «test not found» от упавшего теста и смысл результата `passed`. Адресный тест из проекта ученика сам готовит временную SQLite, запускает обычные точки и проверяет чтение общего маркера. В обновлённом плане 76 этот маркер создаётся через штатный POST, сверяются id и название. Выбранный для чистого запуска файл проверяют своими наблюдениями. При отсутствии node ID восстановить собственную проверку по предыдущему материалу об отказах, раздел «Как два запуска подтверждают общее хранилище». Готовых тестовых тел, файлов проверки, решения README и вложений авторской лаборатории для этой практики не требуется.

- **Проверим исходную схему**. После init получили пустую `tasks`.
- **Запустим оба входа**. Список пуст, оба открытых пути совпали.
- **Повторим init**. Та же задача пережила повтор и читается из нового запуска.

Так другой человек сможет повторить запуск, а мы будем знать, по каким признакам отличить ошибку инструкции от ошибки проекта.
