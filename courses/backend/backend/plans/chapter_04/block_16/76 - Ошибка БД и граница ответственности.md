## Точка B, границы и передача

Ученик сам пишет правило в SQL-инфраструктуре Planner. Код семейства `SQLITE_CANTOPEN` приводит к общему `StorageError`, HTTP 503 и штатному отказу CLI. Ошибка выборки на открываемой БД без таблицы остаётся внутренней, с безопасным HTTP 500 и общим сообщением об ошибке при запуске CLI. При неизвестном или отсутствующем коде штатный отказ о доступности не срабатывает. Обычная операция успешна, неизвестный id даёт 404, неверный параметр даёт 422. Ошибки схемы и целостности не дают 409, ложный успех или возврат к JSON. Публичные ответы, вывод CLI и проверяемый журнал свободны от SQL, значений параметров, путей и traceback.

Пока достаточно различать ровно одну причину, пользоваться существующим `Session.begin` и закрывать ресурс прежним способом. Проверка выполняется на временных БД. Инъекция сбоя после flush, доказательство отката, автоматические повторы и новая схема выходят за рамку. Передача в 76.1 опирается на планируемые готовые изолированные проверки, общий SQL-путь и разграничение известных и внутренних отказов. По паспорту следующего урока его проверка создаёт собственную временную БД и использует новую Session, так что предыдущие учебные файлы базы сохранять для неё не нужно.

## 00. Вступление

Один `LinkedNotes` с тремя пунктами по порядку, без интерактива.

1. **Точка старта**. API и CLI Planner уже работают с одной SQLite. Проверить сбой можно на временной базе.
2. **Новый вопрос**. Как по причине сбоя отличить невозможность открыть БД от ошибки запроса к открываемой базе?
3. **Результат**. При недоступной базе оба интерфейса сообщат об отказе. При сбое запроса к открываемой базе API покажет общую ошибку сервера, а CLI сообщит о внутреннем сбое.

Оба сбоя могут выглядеть одинаково в Python. Поэтому сначала посмотрим, где хранится причина, затем проследим, как она влияет на ответ пользователю.

## 01. Две одинаковые обёртки, разные причины

- Объяснить на каталоге инвентаря. Адрес указывает на файл, Engine описывает способ подключения, реальный `SELECT` требует открыть соединение. SQLAlchemy может передать в `OperationalError` обе причины. Это подкласс `DBAPIError`. `orig` хранит исходное исключение драйвера, `sqlite_errorcode` хранит число, когда его предоставила SQLite. До демонстрации разобрать чтение атрибута и `getattr(объект, имя, None)`, отсутствие значения, проверку целого числа и смысл сравнения.
- Полный независимый пример для Stage 3: один готовый листинг `inventory_probe.py` в теории, читаемый от импорта до результата. По желанию его можно сохранить под этим именем в свободном каталоге и запустить одной командой `python inventory_probe.py` из этого каталога с тем же окружением Python 3.12 и SQLAlchemy 2.0, что у Planner. Листинг сам создаёт временный каталог, задаёт три адреса и готовит входы из таблицы ниже. Для каждого выполняет запрос в короткой Session, вне закрывшегося контекста показывает `тип обёртки, код или None` либо результат чтения. Закрывает Engine до уборки временных файлов. Встроенная подготовка объясняется по её роли. Для первого наблюдения достаточно прочитать вывод в теории, а затем выполнить пробу из раздела 03 в браузере. Не требуются ручная сборка каталога, API-сервер, правки конфигурации или установка ещё одного проекта.

| Вход каталога | Действие и показание примера | Представление по договору каталога |
| --- | --- | --- |
| `open/catalog.sqlite3`, таблица `inventory` со строкой `(1, "Лампа")` | Выполнить `SELECT name FROM inventory ORDER BY id` в новой Session. Список `["Лампа"]` | HTTP 200 со списком, CLI показывает «Лампа» |
| `missing-parent/catalog.sqlite3`, родительский каталог не создан | Тот же SELECT приводит к `OperationalError`, `orig.sqlite_errorcode` сообщает `SQLITE_CANTOPEN` (типичный код 14). Область Session закончилась | HTTP 503 с общим сообщением о недоступности, CLI сообщает, что команда не выполнена |
| `empty/catalog.sqlite3`, файл создан и открыт, таблица отсутствует | Тот же SELECT приводит к `OperationalError`, `orig.sqlite_errorcode` сообщает `SQLITE_ERROR` (1). Область Session закончилась | HTTP 500 с общим сообщением, CLI показывает внутреннюю ошибку |

Листинг показывает реальные результаты чтения и причины отказов, а схема и проба показывают, как наблюдение связано с HTTP и CLI. После первых двух отказов предложить назвать поле, по которому их можно различить. Опора для возврата в этом разделе: `ошибка SQLAlchemy → orig → sqlite_errorcode`. Текст SQL-исключения может включать внутренние данные и для выбора ветки не нужен.

## 02. Основной код внутри расширенного

- На отдельном учебном числе из примера про уникальную метку инвентаря показать `2067` (`SQLITE_CONSTRAINT_UNIQUE`) и основной код `19` (`SQLITE_CONSTRAINT`). Разобрать, что `&` оставляет биты, которые присутствуют с обеих сторон, а `0xFF` оставляет младшие восемь. В одной небольшой таблице дать вход, вычисленное `2067 & 0xFF` и наблюдаемый результат `19`. Для `19` операция оставляет `19`. Имя константы полезнее числа в условии, потому что читается назначение.
- До первой попытки объяснить форму «сначала убедиться, что код является целым числом, затем выделить основной код и сравнить его с нужной именованной константой». Для отсутствующего значения результат классификации отрицательный: побитовая операция с `None` не выполняется. Для любого другого основного кода результат тоже отрицательный. В примере разобрать чтение готового сравнения на семействе `SQLITE_CONSTRAINT`, без готовой функции Planner и без целевого условия на `SQLITE_CANTOPEN`.
- Малая проба: три карточки с одинаковой обёрткой `OperationalError` и кодами `14`, `1`, отсутствующим полем. Ученик для каждой выбирает «считаем базу недоступной» или «оставляем внутреннюю ошибку», затем открывает фиксированную категорию журнала и объяснение. В примере с кодом 1 файл уже открыт и сбой вызван запросом к отсутствующей таблице. При отсутствии кода оснований для штатного отказа о доступности нет. Как короткий перенос после разбора дать расширенный код `SQLITE_CANTOPEN_ISDIR` (526) и попросить назвать основной код. Проверка показывает `14` и объясняет, почему проверка полного числа пропустит этот вариант.
- Опора для возврата: `getattr` может вернуть `None`, маска применяется только к числу, сравнение ведётся с именем основного кода. После выбора причины проследить, где она превращается в ответ.

Справочные источники для автора. [SQLAlchemy 2.0: DBAPIError](https://docs.sqlalchemy.org/en/20/core/exceptions.html#sqlalchemy.exc.DBAPIError), [Python 3.12: sqlite3.Error](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Error), [SQLite: основные и расширенные коды](https://sqlite.org/rescode.html#primary_result_codes_versus_extended_result_codes).

## 03. Сначала закрываем ресурс, затем сообщаем об отказе

- Показать путь `вызов API или CLI → сервис → SELECT или изменение в Session → выход из области → классификация → представление`. Для изменения прежний `Session.begin` завершает транзакцию до выхода из Session. Готовая обвязка смотрит на исключение после выхода из области ресурса. Классификатор возвращает признак, а перевод в `StorageError` или дальнейшее распространение исходной ошибки делает готовая граница. Ответы и безопасная диагностика строятся из фиксированных текстов. Не передавать в них `str(error)`, SQL, параметры, полный адрес или traceback.
- **Отдельный визуал.** На данных каталога разделить схему на области «операция», «Session закрыта», «HTTP / CLI». Стрелки от 14 показывают `StorageError → 503 / штатный отказ`. От 1 и отсутствующего кода показывают внутреннюю ошибку и безопасный публичный результат. Входные ветки 422 (некорректный параметр) и 404 (корректный неизвестный id) не проходят классификатор ошибок драйвера. Попросить проследить стрелку от 1 и назвать границу, на которой ответ получает статус. Это готовит интерпретацию теста с пустым файлом.
- **Интерактив.** Ученик выбирает один из трёх адресов каталога по двум признакам (открывается ли файл, есть ли `inventory`), предсказывает итог HTTP и нажимает «Выполнить SELECT». Последовательность подсветки показывает результат запроса, код или отсутствие исключения, выход из Session, затем HTTP и CLI. Для недоступного адреса обратная связь указывает невозможность открытия. Для открываемого файла без схемы объясняет, что соединение удалось и ошибка произошла при запросе таблицы. В штатном случае видно, почему классификатор не вызывается. Ученик переключает только наличие таблицы при открываемом адресе и проверяет, что 500 сменяется на 200. Данные и тексты каталога не совпадают с заданием Planner, код решения интерактив не выдаёт.
- Мост к практике: прочитать сигнатуру `is_sqlite_unavailable(error: DBAPIError) -> bool`. `error` получает одну обёрнутую ошибку, аннотации помогают прочитать договор, `True` передаёт случай готовому переводу, `False` оставляет исходную ошибку. Для локальной проверки объяснить назначение временного адреса, разницу между проверкой штатного запуска и проверкой классификации, как читать имена сценариев и итог `pytest`. Конструкция тестов и регистрации обработчиков дана готовой.

- `project/tests/test_storage_availability.py`: открытая готовая оснастка. Сама создаёт отдельные `tmp_path`-адреса исправной БД, недоступного пути под несозданным каталогом и открываемого файла без схемы. Подставляет временный `DATABASE_URL` до создания Engine и запускает настоящие `GET /tasks` и CLI-команду `list` через штатные сборки, с нормальным выходом из ресурсов. Для контрастного HTTP-запроса используется отдельный `TestClient` с `raise_server_exceptions=False`, а для остальных проверок неожиданные исключения видны тесту. Для проверки утечек готовый контрастный POST с маркером title производит ошибку схемы при наличии SQL и параметров в исходной ошибке. Проверки фиксируют безопасные тексты и лог, отсутствие fallback и совпадение временного контрольного JSON до/после, а также последующий результат на исправной временной БД. Кейсы имеют имена по сценарию, чтобы после запуска были видны по отдельности нормальный, недоступный и открываемый без схемы. Базовый случай помечен именем `smoke`. Расширенный `CANTOPEN`, неизвестный и отсутствующий код дополнительно подаются как контролируемые входы тому же классификатору, без подмены реального отказа открытия в проверках API/CLI.

### Задание и наблюдаемая готовность

**Контекст и условие.** Программа может одинаково назвать два сбоя, хотя в одном случае база не открылась, а в другом открылась и в ней нет таблицы. Возьми патч из блока «Подготовка проекта» в разделе «Что мы будем делать в практике» и примени его к своему Planner. Из корня Planner (`project/`) запусти `python -m pytest -v tests/test_storage_availability.py -k smoke` своим интерпретатором проекта. Сценарий `smoke` проходит ещё со стартовым `False`. Это подтверждает успешное чтение подготовленной задачи обоими интерфейсами. Если эта проверка падает, сначала сверить штатный SQL-путь с подготовкой проекта. Затем в `app/DBase/session.py` самостоятельно замени тело `is_sqlite_unavailable`, чтобы готовая обвязка узнавала выбранную причину. Запусти полную проверку того же файла и сравни три сценария. Вся подготовка, исходник и критерии доступны до подсказки.

**ТЗ для результата.**

1. Классификатор возвращает `True` только при целом SQLite-коде, чей основной код равен `SQLITE_CANTOPEN`. Обычный и расширенный варианты проходят, другой или отсутствующий код даёт `False`. Произвольный текст ошибки не участвует. Способ записи тела свободный. Имя, вход и логический результат заданы для готовой обвязки.
2. Исправная временная SQLite с одной задачей «Проверить фонарь» даёт 200 с этой задачей и успешный `list`. При неверном временном адресе тот же запрос даёт 503 с фиксированным detail, `list` сообщает о недоступности без выдачи списка, следующая команда может быть принята. При пустом файле без таблицы HTTP даёт безопасный 500, CLI идёт по пути внутренней ошибки.
3. На исправной временной БД запрос `GET /tasks/999` даёт 404, `GET /tasks?limit=0` даёт 422. Отсутствие таблицы и прочие неподходящие причины не дают 409, 503 или ложный успех. В ответах, выводе CLI и проверяемом логе нет маркера входных данных, SQL, параметров, пути или traceback. Для известного отказа в журнале видна только фиксированная классификация причины. Контрольный JSON во временной копии совпадает до и после, его контрольной записи нет в ответах. Рабочие файлы базы не используются.

**Локальная приёмка.** Из `project/` выполнить `python -m pytest -v tests/test_storage_availability.py`. Учебное доказательство: на неверном пути проверка проходит по ветке 503/штатного отказа, а на файле без схемы проходит по ветке 500/внутренней ошибки, хотя обе причины приходят как `OperationalError`. Обычная операция и проверки 404/422 завершают сверку. Сначала ученик прогнозирует причину на стороннем примере, затем пишет своё правило, затем проверяет перенос в оба интерфейса одной командой.

**Подсказка и будущий разбор.** Подсказка возвращает к двум отказам каталога и спрашивает, где в обёртке хранится различающее их значение. При трудности с расширенным кодом дать ссылку на уже разобранное число из раздела о младшем байте. После самостоятельной попытки автор Stage 3 объясняет путь «сигнал драйвера → выбранная ветка → результат» на выводе проверок, отдельно разбирает ошибку слишком широкого условия и вариант сравнения полного числа. До раскрытия все необходимые понятия и проверочные входы уже видны.
