## 00. Вступление

Подвести через знакомый отказ: старый архив доступен, а штатный список задачи не вернул. За одним внешним отказом могут стоять разные причины.

1. **Точка старта:** на исправном временном адресе штатное чтение работает. При отказе SQLite старый архив не подменяет результат.
2. **Новый вопрос:** как понять, что хранилище не открылось, и выбрать безопасный ответ?
3. **Результат:** по коду различаем отказ открытия и внутреннюю ошибку, затем возвращаемся к рабочему чтению.

После одного LinkedNotes кратко связать внутреннее наблюдение с публичным сообщением. Сначала выясняем причину, затем решаем, что увидит пользователь.

## 01. Как прочитать код причины

Начать со смысла. Драйвер сообщает причину числом, SQLAlchemy передаёт своё исключение с исходным исключением в `orig`. Атрибут `sqlite_errorcode` доступен у ошибок из SQLite в Python 3.11+, но может отсутствовать. Разобрать `getattr(obj, "name", None)`, что проверяет `isinstance(value, int)` и почему без числа вычислять маску нельзя. `OperationalError` может обозначать разные причины.

**Аналогия и рабочий пример.** В журнале выдачи оборудования посылка содержит квитанцию с номером сбоя. У двух закрытых шкафов общая категория «доступ закрыт» и разные уточнения. В учебной квитанции `0x030E` справа две шестнадцатеричные цифры `0E`. Это младшие 8 бит. В одной короткой запускаемой ячейке использовать учебную квитанцию с кодом 782 в `receipt` внутри обёртки и вторую квитанцию с искусственным кодом 127. Напечатать извлечённые значения, затем младший байт. `0xFF` оставляет его целиком: `782 & 0xFF` даёт 14, `127 & 0xFF` даёт 127. Для числовой справки сопоставить 14 с `sqlite3.SQLITE_CANTOPEN`. Чтение номера в квитанции может вернуть `None`. Значение этого наблюдения закрепить самостоятельным прогнозом. Затем на реальном `DBAPIError` из опыта в следующем разделе указать, что роль квитанции у `orig`, а номера у `orig.sqlite_errorcode`. Код примера печатает диагноз квитанции, с которым готовая стойка отвечает 503 для категории 14. Показать эту связь на выводе, а развилку настоящих исключений разобрать на следующем опыте. Само ветвление с исключениями Planner остаётся в карточке 1.

**Визуал.** Готовые `Diagram` и `DiagramFlow`: «внешнее исключение» → «исходное исключение» → «номер причины» → «основной код» → «граница ответа». На преобразовании выделить младшие два шестнадцатеричных знака цветом роли темы. Готовый `QuizCard` просит выбрать прогноз для трёх новых квитанций: `0x050E`, `0x0205` и без номера. После выбора показать промежуточные значения `14`, `5` и `None` и объяснить три ветки: подтверждённая категория 14, неизвестная категория и недостаточные данные. Дать обратную связь и у правдоподобных ошибок: сравнили полное 1294 или решили, что любой старший байт означает закрытый шкаф. После сравнения перейти к тому, где одна подтверждённая категория меняет ответ. [Коды SQLite](https://sqlite.org/rescode.html#primary_result_codes_versus_extended_result_codes) · [sqlite3.Error](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Error) · [SQLAlchemy DBAPIError](https://docs.sqlalchemy.org/en/20/core/exceptions.html#sqlalchemy.exc.DBAPIError).

## 02. Где причина становится ответом

**Смысл и аналогия.** Граница обработки решает, что получает вызывающий. В пункте выдачи сотрудник при закрытом шкафе отвечает «выдача временно недоступна». Если журнал открылся, но нужного раздела в нём нет, специалисту понадобится причина из журнала. Посетитель получит короткий общий ответ.

**Рабочий пример и первое наблюдение.** Один короткий запускаемый опыт на том же журнале, одна временная папка создаётся кодом. Готовая техническая часть создаёт отдельный учебный файл для выдач, записывает данные выдачи №8 в `loans` и делает отдельно открываемый файл с таблицей `equipment` без `loans`. Разобрать, как выбрать каждый существующий файл, открыть его через SQLAlchemy, выполнить один SELECT и закрыть ресурс. Сначала прочитать «Штатив» из первого файла. Затем на том же запросе ко второму показать открытие и реальный `no such table: loans` вместе с типом `OperationalError`. Маленький FastAPI-контур того же сюжета получает простой заранее известный отказ стойки `CounterClosed`, фиксированный JSON 503 и оставляет ошибку отсутствующей таблицы внутренней. С готовым TestClient показать статус и тело обоих ответов. `with` выполняет lifespan, `raise_server_exceptions=False` позволяет увидеть HTTP 500, обычный режим отдельного локального прогона даёт исходное исключение, если для него нет зарегистрированного обработчика. Объяснить `raise` внутри `except` как повторный проброс той же ошибки, `raise ... from ...` как связь нового исключения с исходным, и почему `finally` освобождает ресурс на обоих путях. Вывести только безопасное тело наружу; локально для учебной причины достаточно `orig.sqlite_errorcode` и короткого сообщения `orig` на синтетических данных. Опыт не содержит целевого запроса Planner и подключения его классификатора.

**Перенос к проекту.** После примера показать карту штатного вызова. `GET /tasks/{id}` → `get_planner` → репозиторий `get` → реальный SQL-вызов внутри Session из `get_db`. `find` → `run` → `with context_factory()` → `sql_service_context` → тот же SQL-путь в Session команды. SQLAlchemy открывает соединение при обращении к данным. Создание Engine или Session и `GET /health` подтверждают сборку процесса. Код причины можно увидеть только после запроса к данным. На HTTP-ветке обработчик задан по типу `StorageError`. На CLI кратко показать готовую границу вывода вокруг выполнения одной команды и то, как она оставляет меню доступным даже после отказа. Чтение и запись по-прежнему используют прежний ресурс: для записи исключение может дойти от операции или commit в существующей области `session.begin`. Закрытие Session и dispose Engine объяснить по их прежним местам. После независимого примера спросить, почему успешное открытие файла ещё допускает отказ чтения. Ответ опирается на наблюдаемое отсутствие таблицы.

## 03. Как два запуска подтверждают общее хранилище

**Смысл и аналогия.** Две стойки могут выдать одинаковую старую квитанцию из двух копий. Свежий талон, созданный только на одной стойке и найденный на другой по выданному номеру, различает эти случаи.

**Рабочий пример.** Вернуться к выданному примеру «Два отдельных запуска читателя» и дать его короткую проверяемую вариацию на журнале выдачи. Отдельный Python читает отметку по пути, взятому из переданного аргумента. После подтверждённого обновления второй запуск печатает `True` вместо `False`. Один `assert` связывает реальный вывод с новым состоянием, прогноз для копии журнала даёт прежнее `False`. Для подготовки теста разобрать `tmp_path` как новый каталог pytest, `TestClient` как HTTP-вход и `response.status_code` / `response.json()` как наблюдения. Один дочерний URL передаётся в штатный init, процесс TestClient до импорта приложения и обычный CLI, чтобы работала и сборка с фабрикой внутри lifespan. Показать форму `subprocess.run` на читателе журнала: список аргументов, `sys.executable`, отдельный `env`, `input` со строками, `capture_output=True`, `encoding="utf-8"`, `check=True` и `stdout`. Для обычного Planner вызвать `-m app.main` из `project/`: команды и ответы на запросы меню идут каждый на своей строке. `PYTHONIOENCODING=utf-8` в окружении дочернего процесса согласует чтение и захват текста в Windows. `DATABASE_URL` у дочерних процессов должен указывать на один временный файл. HTTP-проба возвращает полученный id и название JSON-строкой в pytest. Клиент закрывается внутри дочернего процесса, а окружение родителя остаётся прежним. Самому ученику предстоит связать выданный POST id, собственные утверждения о GET и строку из CLI в одном тесте.

### 2. Превращаем подтверждённый отказ в безопасный HTTP 503

**Дано и условие.** Проверенное правило, архивный маркер и недоступный учебный адрес. Открытая теория показывает обработчик той же роли на независимой стойке. В HTTP ученик сам выбирает точку для вызова своего правила в `app/core/dependencies.py:get_db(request)`, где видно исключение, дошедшее от запроса внутри выданной Session. Связать с разделом «Где причина становится ответом». Операция начинается после `yield`, поэтому обработка охватывает этот `yield`; определить ветви и место повторного проброса ученик должен сам. Ученик сам подключает положительный результат к `StorageError` и сохраняет исходный `DBAPIError` при отрицательном. Готовый HTTP-адаптер занимается форматом ответа. Для внутренней отметки подтверждённой ветки дать фиксированное `SQLITE_CANTOPEN` без строки исключения или пути. После первого 503 перейти к CLI. Предложить ученику в `app/cli.py` обработать `StorageError` вокруг выполнения команды и вернуть меню; полный проектный фрагмент находится в штатном разборе. В `app/main.py:sql_service_context(session_factory)` ученик переносит своё правило на реальный вызов команды с закрытием Session и сохранением исходного исключения для других причин. **ТЗ и локальный результат.** Выполнить штатный `GET /tasks/901`, дождаться запроса к SQLite.
