## 00. Вступление

По списку открытых задач в ответе можно проверить, что Planner вернул нужную запись. Чтобы понять, где выполнился отбор, посмотрим журнал базы рядом с этим ответом.

Один стандартный `LinkedNotes`, без интерактива.

- **Точка старта.** Умеем сверить ответ выборки по возвращённым задачам.
- **Новый вопрос.** Как увидеть, выполнила ли фильтр сама база?
- **Результат.** Возьмём след одного запроса и найдём фильтр, порядок и лимит, сохранив значения параметров закрытыми.

Сначала научимся отделять запись о чтении от служебных строк. Затем сами выберем короткое окно, где виден только нужный вызов.

## 01. Что видно по одному SELECT

**Назначение и порядок.** Показать на знакомом результате выборки, зачем смотреть на ответ с выбранной записью рядом с командой, отправленной в базу. `WHERE` отбирает подходящие строки, `ORDER BY` задаёт их порядок, `LIMIT` оставляет нужное количество. SQLite может записать параметры как `?`, а некоторые части условия скомпилировать в SQL-литерал, например булево сравнение с `0`. Объяснить bound-параметр как значение, передаваемое отдельно от текста команды. `hide_parameters=True` оставляет форму SQL и скрывает отдельные значения в сообщениях Engine. Этот флаг сам по себе не включает журнал и не скрывает значения, вручную вставленные в SQL, тела HTTP-ответов или строки результата при `DEBUG`. Поэтому используем `INFO`, синтетические данные и не печатаем тело ответа.

**Независимый пример, часть 1.** Stage 3 показывает полный запускаемый пример в одном блоке кода теории на воображаемом инвентаре, со встроенными данными и подготовкой. Во временной SQLite в памяти таблица `inventory(id, state)` содержит закрытую запись 1 и открытые 2 и 3. Готовый пример открывает этот Engine, создаёт и наполняет таблицу до наблюдения, выполняет независимую контрольную проверку количества строк и закрывает подготовительное соединение. Цель запроса знакома. Нужно получить первый открытый предмет. Операция чтения передаёт статус и размер как отдельные значения для `:wanted` и `:size`. В выводе для разбора есть `SELECT id FROM inventory WHERE state = ? ORDER BY id LIMIT ?`, отдельная отметка о скрытых параметрах и результат `[2]`. Показать, почему строка 1 отсеяна, 2 идёт перед 3 и остаётся одна запись. Допустить, что журнал драйвера разносит одну команду и пометку о параметрах по разным сообщениям.

**Первая проба и возврат.** Дать короткий фрагмент этого журнала с SELECT, отметкой о сокрытии и транзакционными строками. Попросить отметить, где условие, где порядок, где лимит и где подтверждение сокрытия. Сверка показывает, что `?` сам по себе совместим с отдельной строкой открытых параметров. На бумажном контрасте показать, почему след с заполнителями и открытым списком параметров нельзя сохранять. При сомнении возвращаемся к команде и соседней записи о параметрах. Как получить такой фрагмент только для нужного вызова?

## 02. Где начать и закончить наблюдение

**Механизм.** Продолжить тот же пример из 01. Готовая подготовка создаёт Engine с `hide_parameters=True` и `echo=False`, schema/seed и контрольное чтение проходят при выключенном наблюдении. Объяснить журнал как поток сообщений, а `caplog` как готовую фикстуру pytest, которая в тесте хранит сообщения в памяти. Разобрать форму `with caplog.at_level(logging.INFO, logger=имя_логгера)`: уровень INFO делает видимыми команды, аргумент `logger=` выбирает источник, отступ ограничивает действие настройки, выход из `with` восстанавливает предыдущий уровень даже при исключении. Новый ресурс чтения получает соединение после входа в окно. Менять уровень в уже активном соединении поздно. Пояснить, как готовое имя связывает логгер с отдельным Engine.

**Независимый пример, часть 2.** Stage 3 показывает в том же полном примере запуск одного чтения инвентаря внутри окна и повтор того же чтения снаружи. Внутри есть `BEGIN (implicit)`, один SELECT, скрытые параметры и `ROLLBACK` после закрытия ресурса чтения. Снаружи снова `[2]` без SQL-сообщений этого запуска. Уровень до и после окна совпадает. На изменённом учебном входе без открытых записей ответ `[]` при одном SELECT, потому что команда всё равно была выполнена. В примере с открытием окна перед подготовкой счётчик SELECT вырастает из-за контрольного чтения количества строк, хотя ответ `[2]` прежний. Весь пример автор запускает на Stage 3 в готовом окружении. Ученику достаточно полного примера и показанного вывода на странице. Для желающих повторить опыт Stage 3 указывает, как сохранить один файл `test_inventory_observation.py` во временной папке и выполнить там `python -m pytest -q -s test_inventory_observation.py` из имеющегося проектного окружения.

**Визуал вне 00.** Две дорожки показывают вызов и результат сверху, события SQL снизу. На данных инвентаря по горизонтали расположить подготовку, контрольное чтение при подготовке, старт чтения, SELECT, закрытие ресурса и ответ `[2]`. Выделить окно только вокруг чтения, связать SELECT с ответом, подписать роль BEGIN и ROLLBACK. Ученик по дорожкам прослеживает, почему в окне одна команда чтения при нескольких сообщениях.

**Интерактив вне 00.** На тех же данных ученик сначала прогнозирует число SELECT, затем выбирает начало окна до подготовки, перед чтением или после него. Модель показывает соответственно два, один или ноль SELECT и выделяет их источники. Обратная связь для широкого окна указывает на контрольный SELECT подготовки, для опоздания объясняет, что чтение уже выполнено, для точного окна связывает один SELECT и `[2]`. В изменённом случае с ответом `[]` ученик отмечает, что отсутствие записей и отсутствие запроса различаются. Это управляемая модель записанного вывода, где можно повторить попытку.

**Перенос к Planner.** Прочитать будущий starter до задания. `selection_lab.client` отправляет запрос к существующему приложению, `selection_lab.logger_name` выбирает только диагностический Engine, `client.get` принимает путь и `params`, а объект ответа сохраняется в `response`. Сводка берёт из ответа HTTP-статус и список `id` из JSON. Показать на независимом примере, как читать отметку о восстановлении уровня и использовать отступы для проверки границ. При затруднении сверяем три момента. Подготовка завершена перед окном, новый ресурс получает соединение внутри, результат и журнал читаем после выхода.

Справка автору Stage 3 по использованным API. [SQLAlchemy 2.0, настройка журнала и сокрытие параметров](https://docs.sqlalchemy.org/en/20/core/engines.html#configuring-logging), [pytest, захват журнала](https://docs.pytest.org/en/stable/how-to/logging.html#caplog-fixture).

## 03. Что мы будем делать в практике

**Формат и исходная опора.** Проект. Берём свой SQL-only Planner и готовый тестовый старт, проверяем знакомую выборку, затем собираем безопасное свидетельство об одном её вызове.

Финальный `LinkedNotes` для ученика.

- **Снимем журнал выборки.** Ограничим сбор моментом одного запроса и проверим, что после него режим журнала восстановился.
- **Сопоставим с ответом.** Покажем, какие части SQL отвечают за выбор первой открытой задачи, и сохраним след со скрытыми параметрами.

Ответ определяет, какие данные получили. Короткое окно позволяет связать с ним конкретную команду базы.

Если отбор был бы выполнен после ограничения одной первой строкой, ответ оказался бы пустым. В условии дать короткий готовый фрагмент для проверки границы. В широком окне видна подготовительная команда при прежнем ответе. Ученик сравнивает со своим следом и видит, почему такой фрагмент нельзя принять.

**Подсказка.** Вернуться к двум дорожкам и отметить момент начала чтения и момент, когда можно посмотреть журнал, затем отделить SELECT от событий вокруг него. Параметры и ожидания уже приведены в условии.

**Будущий разбор.** На ином учебном вызове объяснить выбор окна, чтение подготовительного шума, затем показать связь одного SELECT с полученным id и порядок безопасного сохранения свидетельства. Ученический результат читается по сводке и заметке. Эталон задаётся отдельно при реализации.
