## 01. Окно наблюдения за одним действием

**Смысл и термин.** SQL-след здесь означает команды, которые Engine подготовил для передачи SQLite в выбранный момент. Подписка вызывает функцию-наблюдатель перед каждой такой командой. Аналогия: наблюдатель у стойки каталога отмечает только поручения, которые прошли через эту стойку между открытием окна и его закрытием.

**Короткий рабочий пример.** Один полный блок на уже установленном SQLAlchemy: SQLite в памяти, каталог `equipment(id, category)` без индекса категории, записи `(12, 'stand')`, `(17, 'cables')`, `(23, 'case')`. Сначала создать и наполнить таблицу. Показать, как `event.listen(engine, 'before_cursor_execute', on_sql)` привязывает функцию к экземпляру Engine. Разобрать `statement` и `parameters` в сигнатуре `on_sql(conn, cursor, statement, parameters, context, executemany)` и пояснить остальные аргументы как сведения о вызове. Показать, как `yield` отдаёт список в `with`, `finally` выполняет `event.remove` с теми же Engine, именем события и функцией. Сначала открыть окно, затем получить соединение внутри окна. Закрыть его до подготовки плана. В окне выполнить чтение кабелей через `WHERE category = :category` и один служебный `PRAGMA database_list`, открыто объяснить его назначение. Вызов выполнен на стойке каталога, от которой подписались.

**Первое наблюдение и отличающаяся ошибка.** В списке после закрытия окна есть ровно команда `SELECT ... FROM equipment WHERE category = ?` и служебная команда `PRAGMA`. Выдача содержит `[17]`. В списке нет подготовки таблицы. `PRAGMA` описывает соединение, `SELECT` читает выдачу. Границы `BEGIN` и `ROLLBACK` могут появляться в журнале Engine, это не отдельные SELECT нашего события. Если подписать другой Engine или выйти из окна до чтения, чтение может вернуть правильный id, а список будет пуст в обоих случаях. Чтобы найти причину, сравнить объект, к которому привязано рабочее соединение, и положение вызова относительно `with`. Если открыть окно до подготовки, в списке появятся команды подготовки.

**Открытая опора.** Показать компактный нейтральный `capture_sql(engine)` на примере каталога. Он выдаёт список записей с `.statement`, скрытыми из `repr` внутренними DBAPI-параметрами и методом `.explain(engine)` для следующего раздела. Для нашего вывода помощник отдельно исключает значения из представления записи; `hide_parameters` сам эту функцию и данные внутри неё не меняет.

## 02. Где выполнен отбор

**Смысл и термин.** Предикат задаёт условие отбора. Аналогия продолжает работу каталога: сотрудник стойки может отдать только кабели по условию на талоне, а может отдать весь каталог, после чего получатель выберет кабели из полученного. Видимый итог у получателя совпадает.

**Короткий рабочий пример.** Продолжить тот же пример во втором вызове. В одной ветке SQLite выполняет `SELECT id FROM equipment WHERE category = ? ORDER BY id` с отдельно переданной категорией. В другой `SELECT id, category FROM equipment ORDER BY id` передаёт приложению три строки, затем Python выбирает `cables`. Показать обе остановки: SQLite отдала `[17]` или `[12, 17, 23]`, внешний итог в обеих ветках `[17]`. Дать выбор другого талона `case`, попросить предсказать оба промежуточных списка. После попытки показать `[23]` из SQLite в одной ветке и все три id в другой, затем `[23]` на выходе обеих.

**Опора и типичная путаница.** Результат HTTP сообщает, что получил клиент. `WHERE category = ?` указывает, что условие категории передано в SQL; сам заполнитель не раскрывает выбранную категорию. `ORDER BY` задаёт порядок, `LIMIT` оставляет часть результата. Булево условие SQLAlchemy на SQLite может быть литералом `0`, а предел может прийти как `LIMIT ? OFFSET ?`. Из знакомого агрегата перенести то же чтение границы: `COUNT(CASE ...)` показывает, что счётчики посчитаны в SQLite ещё до отображения `all` как `total`. Наличие SELECT или совпадение id само по себе место работы не устанавливает.

**Сравнение и интерактив.** Использовать доступный `QuizCard` или `RecallCard` с поэтапными прогнозами вне 00. Сначала показать два совпадающих результата и предложить выбрать, что запросить для проверки места отбора. Затем дать два перемешанных следа каталога и спросить, в каком случае до приложения дошли все три строки. Обратная связь указывает на наличие предиката категории и промежуточный набор. В практике ученик переносит критерий на статус задачи, в том числе если форма запроса расходится с ожиданием.

## 03. Как SQLite добирается до строк

**Смысл и термин.** `EXPLAIN QUERY PLAN` даёт краткое описание способа доступа. Аналогия с той же стойкой: сотрудник может пролистать каталог целиком в поисках кабелей. Это его маршрут по каталогу; правило, что из него выдать, записано на талоне.

**Короткий рабочий пример.** На том же Engine после закрытия окна попросить SQLite показать план для двух ранее снятых команд каталога. Дать `connection.exec_driver_sql('EXPLAIN QUERY PLAN ' + statement, parameters).all()` внутри готового `.explain(engine)`. Объяснить, что берём записанный текст и те же позиционные параметры внутри помощника, а наружу читаем только описание плана. Предложить прогноз, изменится ли надпись `SCAN`, если тот же каталог читается с условием по категории. После попытки показать `SCAN equipment` в обоих вариантах при отсутствии индекса категории; условие по-прежнему определяет, какие строки SQLite передаст дальше. `SCAN` может сопровождать `WHERE`. План описывает стратегию, без подсчёта измеренного времени или гарантии постоянного текста вывода.

**Различающий результат и перенос.** Подставленная на глаз другая команда, другой Engine или потерянные значения `?` отделяют план от пойманного запроса. В примере потерянный кортеж даёт ошибку числа параметров. Если выполнить план внутри того же окна, в след попадёт лишняя команда `EXPLAIN`. В практике ученик сам выбирает запись, вызывает готовое чтение после закрытия окна и поясняет разницу между фразой в плане и предикатом в SQL.
