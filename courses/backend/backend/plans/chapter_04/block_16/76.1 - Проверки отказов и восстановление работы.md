## 00. Вступление

Мы умеем получить понятный ответ при недоступном хранилище. А что останется в таблице, если SQLite доступна, но ошибка прервала уже начавшуюся запись?

Одна группа `LinkedNotes`.

1. **Точка старта.** Planner сохраняет задачи в SQLite. Проверки отказов можно проводить на отдельной временной базе.
2. **Новый вопрос.** Как убедиться, что вставка уже дошла до базы, а после ошибки ни она, ни прежние строки не изменили сохранённый набор задач?
3. **Результат.** Свежая Session покажет прежние задачи, а следующий вызов записи сохранит новую задачу.

Отметка flush ответит, успела ли попытка выполнить SQL. Независимое чтение ответит, какие данные остались. Для проверки восстановления понадобится ещё одна запись.

## 01. Где прервать запись, чтобы проверить откат

**Механизм.** Внешний `with session_factory() as writer` открывает Session и закрывает её при выходе. Внутренний `with writer.begin()` очерчивает транзакцию. `flush()` отправляет INSERT внутри неё. При обычном завершении `begin()` подтверждает транзакцию. Если учебное исключение вышло из её области до commit, менеджер откатывает транзакцию и передаёт исключение дальше. `close()` освобождает ресурс. Исход транзакции проверяют чтением из другой Session. Если исключение возникло до flush, отсутствие строки ещё не показывает, что выполнившийся INSERT был отменён.

**Визуал.** Дорожка Session содержит дорожку транзакции с метками «вставка», «flush», «commit». Показать независимые ветки для ошибки после flush до commit и после успешного commit, затем финальную точку чтения в новой Session. В каждой ветке у контакта «Пункт выдачи» подписаны состояния «в транзакции», «отменён» или «сохранён» текстом. Схема показывает, что закрытие Session и итог записи наблюдаются отдельно.

**Переход.** Чтобы доверять этому выводу, нужны данные до попытки, признак состоявшегося INSERT и чтение после выхода из Session.

## 02. Что увидит новая Session

**Полный независимый пример для Stage 3.** В теории показать целиком один файл `contact_rollback_demo.py`. Для необязательного запуска можно сохранить этот блок под свободным именем в `project/` и выполнить `python contact_rollback_demo.py` в окружении Planner, подставив выбранное имя. Изложить синтаксис у соответствующих строк примера. Файл сам создаёт временный каталог, отдельный SQLite Engine и схему маленького справочника `contacts(id, name)`. В каждом варианте своя временная база с уже подтверждённым контактом `(1, "Склад")`. Опыт использует прямые ORM-операции над справочником.

- В первом варианте прочитать исходный набор, закрыть читающую Session, открыть Session записи и внутри `begin()` добавить `(2, "Пункт выдачи")`. После явного `flush()` сделать SELECT по id в той же транзакции с отключённым autoflush и показать находку. Готовый переключатель стенда вызывает учебное исключение в выбранной точке. Для ветки до commit показать перехват **снаружи обоих контекстов**, состояние ресурса после выхода и новый SELECT, дающий только `(1, "Склад")`. Следующая Session штатно добавляет `(3, "Мастерская")`. Ещё одна Session читает `[(1, "Склад"), (3, "Мастерская")]`.
- Во втором варианте подтвердить вставку успешным выходом из `begin()`, затем поднять то же учебное исключение. Независимый SELECT показывает `[(1, "Склад"), (2, "Пункт выдачи")]`. Объяснить, что при ошибке после подтверждения запись уже есть. Автоматическое повторение create может добавить ещё одну строку.
- Пример печатает отметку вставки, признак закрытия, пойманную учебную ошибку и отсортированные строки для каждого чтения. Закрыть ресурсы до удаления временного каталога. Полный пример в теории доступен для чтения без настройки стенда. Для запуска достаточно получить один готовый файл и выполнить одну команду, схема и данные создаются внутри него.

**Управляемая проба и интерактив.** На данных справочника предложить выбрать точку «до flush», «после flush, до commit» или «после commit», предсказать список имён и нажать «Прочитать новой Session». До flush экран показывает только «Склад» и объясняет, что INSERT не выполнялся. Между flush и commit экран показывает подтверждение выполненного INSERT внутри первой Session, затем только «Склад» из новой Session и причину отмены. После commit выводит «Склад» и «Пункт выдачи» и объясняет, почему запись осталась. Сначала провести пробу для промежуточной точки, затем поменять её и предсказать результат самостоятельно. В варианте с откатом дать открыть шаг «Следующая запись» и увидеть «Мастерская» после отдельного вызова.

**Опора для возврата.** Снимок состоит из обычных значений, скопированных до первой попытки. ORM-объект, удержанный в памяти Session записи, не служит независимым наблюдением. После освобождения её ресурса отдельная читающая Session работает с тем же тестовым файлом. Сравнение исходного и нового снимков отличает отсутствие новой строки от потери или изменения старых.

## 03. Как перенести доказательство в тест Planner

Связать прямой INSERT справочника с прежним `PlannerService.add_task(title, priority, tags=...)`. Обычный сервис выполняет INSERT через `SqlTaskRepository.create`, который сам вызывает flush. Сервисная операция запускает переданный `write_scope`. На отдельном фрагменте объяснения показать смысл двух допустимых аргументов `write_scope` без тела итогового теста.

- `session.begin` передаёт методу сборки способ открыть транзакцию, который сервис вызовет, когда начнёт запись. Скобки `session.begin()` открыли бы область раньше. Сначала открыть свежую Session, чтения для проверок держать в других Session, чтобы запрос не начал транзакцию записи преждевременно.
- `stop_before_commit(session, title)` готовит такой же вызываемый объект, настроенный только на выбранную Session и заголовок. Внутри он позволяет сервису выполнить реальную запись, находит отправленную строку в той же транзакции без autoflush, сохраняет её id как `session.flushed_id` и поднимает `ControlledWriteError` до выхода из `session.begin()`. Достаточно понять этот контракт. Обвязку контекстного менеджера и низкоуровневую проверку INSERT ученик получает готовыми.
- На коротком примере со справочником объяснить форму `pytest.raises(ControlledWriteError)`. Узкий блок проверяет ровно ожидаемое исключение из вызова. Он расположен снаружи транзакции, чтобы она увидела ошибку и откатилась. По выходе из внешнего `with` учебный признак `session.closed` подтверждает вызов `close()`, а `session.flushed_id` хранит число, которому не нужен доступ к ORM. Обычный `assert` проверяет факт и указывает на условие, которое не выполнилось.
- `read_rows(session)` возвращает словарь по id с копиями `(title, priority, is_done, tuple(tags), title_normalized)`. Показать на контактах сравнение двух снимков, доступ к результату по ключу и различие между «новой строки нет» и «снимки равны целиком». Для штатной записи брать id из возвращённой Task. SQLite может выдать следующий успешной вставке id, ранее выделенный внутри откатившейся транзакции. Отсутствие отменённой записи проверяется **до** новой вставки. Заголовки у попыток разные.

**Первая попытка переноса.** В небольшом фрагменте чтения справочника предложить выбрать, какой аргумент открывает штатную транзакцию, а какой задаёт учебный сбой, и определить место, откуда независимый читатель получит уже завершённое состояние. Показать обратную связь: чтение после выхода из Session и проверка узкого типа ошибки отвечают на разные вопросы. При затруднении вернуться к дорожкам из 01.

## 04. Что мы будем делать в практике

Формат **проект**. В своём рабочем Planner ученик добавит один тест сервисного создания задачи. Для опытов используют отдельные временные SQLite, которые создаёт pytest. К началу работы в проекте есть каталог `project/tests/` и тестовое окружение из `project/README.md`.

Одна группа `LinkedNotes`.

1. **Остановим незавершённую запись.** Поставим учебный сбой после отправки INSERT и увидим, что ошибка вышла наружу, а Session закрылась.
2. **Перечитаем и запишем снова.** На той же учебной базе сверим исходные строки в новой Session, затем сохраним другую задачу обычным вызовом и перечитаем её.

Первая часть показывает, что тест проверяет состоявшуюся попытку. Вторая показывает итог rollback и возможность следующей записи в этой же временной SQLite. Контраст после commit запускается отдельно и даётся готовым.

Попытка со сбоем создаёт «Отменённая черновая задача» с приоритетом 4 и тегом `черновик`. Следующая штатная операция создаёт «Подготовить отчёт» с приоритетом 3 и тегом `отчёт`. Используются допустимые данные, чтобы проверка прошла дальше валидации.

### ТЗ и локальная приёмка

1. Один новый тест использует `rollback_sessions`. До записи отдельная Session снимает исходный набор по всем шести полям и завершает чтение. Локальный результат: два id из таблицы и исходные значения в переменной-снимке. Опора в 02–03.
2. Собственная проверка проводит реальный вызов создания через тестовый `write_scope`. После выхода из контекстов наблюдаются `ControlledWriteError`, назначенный id в `flushed_id` и `closed == True`. Ошибка валидации и отказ до SQL не удовлетворяют этому критерию. Свежая Session, открытая после Session записи, видит ровно исходный набор. Снимок равен первому по всем полям, отменённой задачи нет. Локальный результат можно принять независимо от ещё не написанной части на восстановление. Опора в 01–03.
3. Тот же тест проводит второй вызов создания в отдельной свежей Session с обычным `session.begin`. Ещё одна Session после её закрытия видит исходный набор и ровно одну новую запись с возвращённым id. У неё ожидаемое название, приоритет 3, `is_done=False`, `tags=["отчёт"]` и `title_normalized="подготовить отчёт"`. Обе исходные строки сохраняют все значения. Опора в 02–03. Проверка не зависит от непрерывности id.

Для промежуточного прогона своего теста из `project/` добавить к команде pytest путь `tests/test_write_recovery.py::test_rolls_back_before_commit_and_recovers`. Для итоговой проверки запустить `python -m pytest -q tests/test_write_recovery.py tests/test_sql_create.py tests/test_dbase_transactions.py`. Ожидается, что собственная проверка, готовый контраст и прежние адресные тесты проходят. Для самопроверки причинности на устном прогоне достаточно объяснить, какое утверждение упадёт в своём тесте при сбое до flush и какое упадёт, если первая строка сохранится. Править адаптер для этой самопроверки не требуется.

**Помощь.** Первый ориентир можно дать двумя вопросами. «Какая отметка подтверждает отправку INSERT? Какая Session видит содержимое после завершения транзакции?» Затем дать ссылки на объяснение границы транзакции, независимого снимка и передачи области записи. После попытки разбор Stage 3 последовательно сопоставляет исходный снимок, признак flush, факт закрытия, чтение после rollback и чтение после следующей штатной записи. Для пошагового объяснения использовать независимые данные.
