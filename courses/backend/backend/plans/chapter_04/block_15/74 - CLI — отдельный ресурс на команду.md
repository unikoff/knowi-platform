## 01. От распознанной команды до освобождения ресурса

**Механизм.** По знакомому меню провести один проход: ввод, нормализация, выбор обработчика, действие, возврат к меню. Объяснить синтаксис на независимом прокате: имя функции хранит способ получить ресурс, вызов этой функции в выражении `with` даёт контекст, а `as` связывает выданный объект с именем для тела блока. Фабрика может хранить ссылку на одну SessionFactory. Каждый вход в контекст выдаёт сервис с новой Session. Отступ определяет, какие действия выполняются до закрытия. Если действие выбрасывает исключение, контекст завершает работу с Session до передачи исключения наружу. При записи внутренний `write_scope` фиксирует успешное изменение до выхода из операции сервиса. При чтении commit для записи не нужен. Контекст охватывает и ввод аргументов уже распознанной команды, например номера задачи для поиска. Следующее приглашение меню появляется после закрытия ресурса. Закрытие Session освобождает ресурс, а сохранённая строка остаётся в SQLite.

**Полный независимый пример для Stage 3 · прокат фонарей.** Представить весь запускаемый пример одним видимым блоком кода рядом с разбором. Он сам готовит отдельный временный файл `rental.sqlite`, пустую таблицу выдач, одну фабрику и контекст. Для объяснения выбирать уже подготовленный файл и указать, что каждый следующий вход открывает Session к этому же файлу. В сюжете оператор сначала определяет вид операции. Комплект показывает готовый сценарий из отдельных действий с контекстом проката, без Planner, его имён, сигнатуры run или реализации общего диспетчера. В коде и выводе проследить следующую последовательность.

| Ввод | Что наблюдает ученик и почему |
| --- | --- |
| «внести фонарь» | C1 открыта. Выдача «Фонарь» с id 5 записана, внутренняя транзакция подтверждена, C1 закрыта. |
| «показать 5» | C2 открыта. Чтение показывает «Фонарь», C2 закрыта. Новая Session видит строку в том же файле после commit из C1. |
| «показать 9» | C3 открыта. Отсутствие выдачи вызывает предметную ошибку внутри действия. C3 закрывается, внешний код демонстрации фиксирует «Выдача не найдена». |
| «покзать», «выход» | Видны сообщение об опечатке и остановка сценария. Журнал остаётся с тремя открытиями и тремя закрытиями. |

В видимой теории объяснить изучаемые строки и порядок результата. Технические строки создания временной базы и фикстуры уже входят в готовый блок. Для первого наблюдения достаточно страницы, на которой даны вход, результат и трасса. По желанию из `project/` можно выполнить уже собранный пример. Сохранить блок как `examples/lantern_rental_session.py` и запустить `python examples/lantern_rental_session.py` привычным интерпретатором проекта. Если каталога `examples` нет, для этой пробы достаточно сохранить файл рядом с `app` и запустить его по имени. При занятом имени выбрать свободное. Для обязательного маршрута ученик ничего не создаёт и не настраивает.

**Отдельный визуал вне 00.** Лента с полосой «меню и ожидание» и рамками C1, C2, C3 из примера. Внутри C1 показать запись и commit, после них закрытие и новое приглашение. В C2 отметить только чтение, в C3 показать выход по ошибке. Опечатку и выход показать на ленте без рамок. При ошибке прогноза пояснить причину: опечатка не выбрала действие, отсутствующая выдача обнаружилась после открытия, а выход завершил цикл ещё до выбора обработчика. Использовать события и состояния, без сборки строк решения для Planner.

## 02. Как прочитать стартовый код Planner

**Точка переноса.** На открытом учебном фрагменте указать `run(service=None, read=input, write=print, *, context_factory=None)` и `execute_command(service, command, read=input, write=print, *, context_factory=None)`. Объяснить, что `*` делает `context_factory` именованным аргументом. Это функция без аргументов, подготовленная снаружи для конкретной базы. `service=None` обозначает вызов без готового сервиса, когда передаётся SQL-фабрика. В привычной форме вызывающий код передаёт собранный JSON-сервис. `read` и `write` принимают готовые функции ввода и вывода, поэтому одна проверка может передать заранее известные ответы и собрать сообщения. Если вызывающий код передал обычный сервис, готовый адаптер `choose_context_factory` выдаёт функцию, контекст которой возвращает этот сервис без создания SQL Session. Сама `choose_context_factory` только подготавливает или выбирает функцию. SQL-оснастка передаёт свою фабрику, которая открывает реальный командный контекст при входе.

**Первое применение к старту.** Ученик находит в стартовом `run` внешний `with` и сравнивает длительность этой области с лентой проката. При вводе одной опечатки и exit старт откроет одну Session на весь цикл. Предложить заранее предсказать счётчик и подтвердить это готовым запуском. Внутри `execute_command` уже видны два ранних результата: `False` для exit, `True` после неизвестной команды. Объяснить значение для цикла и связать со знакомой таблицей обработчиков. Попросить выбрать, какие ветки должны пользоваться фабрикой, а размещение области и запись соединения оставить для практики.

**Чтение проверки.** В готовом журнале `open` соответствует созданию реальной Session с локальной меткой, `close` её закрытию. Две пары с разными метками доказывают два ресурса, даже если обе команды вывели знакомый текст. При записи сверяется и строка, прочитанная новой командой по выведенному id. Пояснить, как отличить «Задача не найдена.» после вызова find от «Неизвестная команда.» до вызова обработчика. Для первых двух SQL-команд журнал должен последовательно показать open/close, open/close с разными метками. Самопроверка выделяет события технического чтения итоговой строки отдельно от CLI, чтобы счётчик отражал только команды. Контролируемый сбой в готовом вводе показывает выход с исключением, даже если этот сценарий останавливает цикл.

**Будущая открытая оснастка Stage 3.** В начале ручной проектной карточки разместить подраздел «Готовые материалы» с двумя полностью доступными для копирования блоками. Оба берутся прямо с карточки до раскрытия разбора.

1. **Стартовый фрагмент для `project/app/cli.py`.** Цельно заменяет существующий хвост файла от `def execute_command(` до конца, с чётко указанными границами. Использует меню и обработчики из остальной части файла и сохраняет внешний договор старых вызовов `run(service)` и `execute_command(service, ...)`. В самом фрагменте готовы сигнатуры выше, адаптер `choose_context_factory(service, context_factory)` с `nullcontext` для прежнего сервиса, выбор фабрики в обеих функциях, цикл, нормализация, единая таблица обработчиков и оба ранних возврата. Выбор фабрики ничего не открывает. Исходный `run` открывает выбранный контекст вокруг всего цикла и передаёт выданный сервис диспетчеру. Диспетчер умеет принять фабрику именованным аргументом и выбрать её для предметной команды, но исходный вызов обработчика всё ещё получает сервис от внешней области. Старт показывает проблему на работающем CLI. Готовой передачи фабрики между функциями и командной области в нём нет. `app/main.py` уже умеет собрать JSON-сервис для старой формы запуска и SQL-контекст для учебной формы.
2. **Самопроверка в `project/check_cli_session.py`.** Готовый единый файл с режимами `--baseline` и запуском без аргументов. Он берёт реальный `app.cli.run`, подставляет учебную фабрику на основе `app.main.sql_service_context`, создаёт схему в новой файловой SQLite по явному временному URL, использует готовый сценарий ответов, различает метки Session и пишет open/close по фактическим событиям создания и закрытия. Журнал показывает, закрыта ли Session на каждом следующем приглашении, и даёт сравнение ожидаемого с полученным. В отдельном прогоне он запускает `python -m app.main` с `JSON_PATH` на временный файл и `DATABASE_URL` на отдельную пробную цель. Источники проекта он только импортирует и запускает. В комплекте нет альтернативной реализации CLI, SQL-репозитория, требований дописать фикстуры или настройки рабочего окружения.

**Как применить.** В том же проекте открыть `project/app/cli.py` и заменить указанный участок готовым фрагментом, сохранив остальной файл. Перед заменой скопировать текущий участок в черновик редактора, если в нём есть свои изменения. Сохранить готовую самопроверку рядом с каталогом `app` под указанным именем. Если имя уже занято собственным файлом, взять свободное имя и использовать его в командах ниже. Из `project/` запустить привычным интерпретатором `python check_cli_session.py --baseline`. Режим принимает ввод «покзать», «exit» и показывает одно раннее открытие с последующим закрытием. Это исходное наблюдение перед собственной правкой. Сборка отдельного проекта, установка дополнительных библиотек, создание SQLite вручную и написание тестов для первого наблюдения не нужны.

## 03. Что мы будем делать в практике

**Оформление Stage 3 · LinkedNotes**

1. **Ограничим ресурс одной командой.** В существующем CLI выберем место, в котором обработчик уже известен, и проведём к нему фабрику.
2. **Проверим следующий ресурс.** Запишем задачу через CLI, найдём её в следующей команде и по журналу выясним, где ресурс открылся и закрылся в каждом случае.

После списка связать два наблюдения. Независимое чтение подтверждает сохранённую строку, а журнал показывает, в какой момент CLI отпустил ресурс. Если журнал расходится с прогнозом, вернуться к ленте и стартовому вызову.

### Проектная карточка «Session на время команды»

**Контекст и исходник.** У ученика рабочий Planner после полной SQL-реализации с обычным JSON-запуском. Исходник задания · существующий `project/app/cli.py` с готовым к вставке фрагментом в разделе карточки «Готовые материалы». Соседний `project/check_cli_session.py` из того же раздела даёт открытый запуск и данные. После подготовки ученик видит одно открытие при опечатке с выходом. Опоры · механизм и проба в 01, разбор стартовой сигнатуры и журнала в 02.

**Условие.** Сейчас тестовый SQL-контекст охватывает всё время работы меню. Измени только связь `run` с существующим `execute_command` и область вызова существующего обработчика. Сам проведи фабрику через вызов из цикла и реши, где начинается и заканчивается `with`. Воспользуйся прежним способом выбора команды и сообщениями. После правки выполни открытые сценарии: добавление и повторное чтение, поиск отсутствующей задачи, опечатка и выход, а также отдельно сбой внутри распознанного действия. Сверь журнал и результат нового чтения, затем проверь временный JSON-запуск тем же готовым файлом.

**ТЗ.**

1. `run` использует готовую сигнатуру и передаёт в диспетчер выбранную фабрику, меню само ресурс не удерживает. Обычный вызов с JSON-сервисом проходит через готовый адаптер.
2. `execute_command` по-прежнему использует один путь нормализации и выбора обработчика. Exit завершает цикл, неизвестный ввод показывает прежнее сообщение и возвращает к меню. Оба случая дают ноль открытий.
3. Вызов выбранного обработчика получает сервис из своего контекста. Session освобождается до следующего ожидания команды либо при выходе с исключением. Существующий `write_scope` отвечает за завершение записи. Обработчики, публичные сообщения и обычная точка входа сохраняются.
4. Каждая SQL-команда получает отличимую Session. Новая команда чтения видит подтверждённую запись с прежним форматом вывода. Штатная JSON-сборка работает на переданном ей временном JSON-файле.

**Локальная приёмка.** Из `project/` запустить `python check_cli_session.py` и сравнить наблюдения. В сценарии используется пустая изолированная база; файл проверки извлекает фактический id из результата `add` для следующего `find`.

| Вход и собственная проверка ученика | Наблюдаемый критерий |
| --- | --- |
| `add` «Проверить проект», приоритет 3, затем ` FiNd ` по только что выведенному id | Две разные пары open/close. Формат вывода прежний и содержит одну и ту же задачу с приоритетом 3 и исходным статусом. Между командами активных Session нет. Строка остаётся в SQLite после закрытия сессий. |

Суммарная готовность · ученик показывает свою область вокруг одного обработчика и называет причину различия между неизвестной командой и известным поиском отсутствующего id. Локальная проверка открыта. Она сверяет поведение и журнал, расположение области ученик показывает в исходнике. Стартовый сценарий с одной Session на всё меню этот критерий не проходит.
