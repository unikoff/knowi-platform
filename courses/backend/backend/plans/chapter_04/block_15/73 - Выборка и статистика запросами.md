## 00. Вступление

Когда Planner отдаёт список, клиент может попросить только открытые задачи и указать, сколько строк вернуть. Та же просьба должна работать при чтении из SQLite.

Спроектировать один `LinkedNotes` с тремя элементами:

- **Точка старта:** Planner уже выполняет в SQLite операции с отдельными задачами. Прежний список умеет отбирать открытые задачи и ограничивать ответ.
- **Новый вопрос:** Как попросить базу вернуть нужные строки, чтобы завершённая задача в начале списка не заняла место открытой?
- **Результат:** При запросе одной открытой задачи получим первую подходящую задачу по выбранному порядку.

Чтобы понять, какая задача окажется первой, проследим, какие строки проходят условие, в каком порядке они встают и где обрезается список.

## 01. Прежняя выборка как договор

- Начать с вопроса «покажи одну открытую задачу первой по id». `is_done` задаёт подходящий статус, `sort_desc` выбирает направление, `limit` задаёт размер ответа. Взять знакомый путь запроса: `GET /tasks` и его зависимость чтения → `PlannerService.select_tasks` → `repository.select`. Меняется место, где производится выборка.
- На независимом наборе билетов с id `1, 2, 4` показать три запроса к одним данным. Билет `1` закрыт, `2` и `4` открыты. Предложить сначала назвать подходящие id для «все», «только открытые» и «только закрытые». Сверка: `1, 2, 4`, `2, 4`, `1` соответственно. Здесь сравнивается состав, порядок разберём отдельно.
- Опора для возврата: `None` означает пропуск фильтра, `False` является значением статуса открытой строки, `True` является значением статуса закрытой строки. Предложить объяснить, почему обычное `if status` пропустит выбор открытых. Теперь выразить этот договор через условие запроса.

## 02. Собираем запрос до выполнения

- На модели билета показать знакомое `select(TicketRow)` и новый шаг на имеющемся выражении: `statement.where(TicketRow.closed == status)` добавляет условие по значению, возвращая новое выражение. `==` с колонкой задаёт сравнение для базы. Объяснить переприсваивание результата метода, форму проверки `status is not None` и причину задавать значения через выражение ORM, которое оформляет их для SQL. Сборка методов ещё ничего не считывает.
- На тех же билетах дать короткую самостоятельную пробу: выбрать, добавлять ли условие при `status=False`, и записать только это выражение для билетов. Проверка в объяснении показывает ветку с условием и id `2, 4`; при `None` условие отсутствует и среди id остаётся `1`. Сверить со случаем потерянного `False`. Оставить в теории форму и назначение `where`, а проектную ветку ученик собирает сам.
- Результат проверки фильтра определяет, среди каких билетов выбираем первый. Сама таблица порядка выдачи не обещает: для этого нужен явный порядок по уникальному id.

## 03. Определяем порядок и только затем берём первые строки

- Показать, как `order_by` принимает ключ и направление: `TicketRow.id.asc()` даёт меньшие id первыми, `TicketRow.id.desc()` даёт большие первыми. `limit(n)` ограничивает число строк SQL-ответа; `None` означает отсутствие вызова `limit`. Эти методы тоже возвращают новое выражение. Порядок «отбор → порядок → первые N» описывает результат запроса, а порядок вызовов методов сборки сам по себе не моделирует физическое выполнение SQLite.
- **Отдельный визуал.** Исходные билеты в порядке показа `4 открытый, 1 закрытый, 2 открытый`. На снабжённых подписями полосах для запроса «открытые, id по возрастанию, одна строка» показать `[4, 2]` после отбора, `[2, 4]` после сортировки, `[2]` после лимита. Различие видно по id и тексту статуса. Короткий контрпример использует тот же исходник: если сначала взять первый по id из всех, остаётся закрытый `1`, после отбора список пуст.
- **Полный независимый пример для Stage 3.** Дать один видимый, целиком копируемый `CodeBlock` «Пример с билетами» в этой секции. В одном файле `planner_tickets_select_demo.py` разместить готовые импорты, маленькую ORM-модель `TicketRow(id, closed)`, SQLite в памяти, создание таблицы, три известные строки, Session и её закрытие. В разборе выполнить фиксированный вариант «открытые, ASC, 1» одним выражением, затем показать эффект смены направления, снятия фильтра и снятия лимита. Использовать настоящие `select`, `where`, `order_by`, `limit` и выполнение `session.scalars(statement).all()`; вывести id из полученных ORM-строк. Ожидаемые подписи и списки: «Открытые, ASC, 1» `[2]`, «Открытые, DESC, 1» `[4]`, «Все, ASC, 1» `[1]`, «Открытые, ASC, без лимита» `[2, 4]`. Для пустого результата в том же примере использовать условие по отсутствующему id `99`: вывод `[]`, так как совпадений нет. Разобрать фиксированные запросы без готового универсального метода или сигнатуры Planner.
- Первый полезный вывод доступен из примера на странице. Для повторения в терминале Stage 3 даст инструкцию: из корня своего Planner с обычным окружением скопировать блок в один файл `planner_tickets_select_demo.py` и выполнить `python planner_tickets_select_demo.py`. Если имя занято, сохранить копию под свободным именем и указать его в той же команде. Выбран именно SQLite в памяти: скрипт сам открывает, заполняет и освобождает учебную базу; нужен только уже используемый проектом интерпретатор с SQLAlchemy. Самостоятельная сборка схемы, каталогов, зависимостей или приложения для примера не нужна.
- **Управляемая проба до проекта.** На билетах предложить назвать первый id для открытых при ASC и лимите 1, затем показать ответ интерактивом. Дать переключатели «все / открытые / закрытые», «по возрастанию / по убыванию», «1 / без лимита» и режим «ограничить раньше фильтра». Показать состав строк на каждом шаге и итог. Для правильного режима объяснить, что закрытый `1` не участвует в заполнении слота. В ошибочном режиме при открытом фильтре, ASC и лимите 1 показать `[]`, потому что выбранный до фильтра `1` был закрыт. Пока лимит снят, пояснить, почему ошибочный порядок перестаёт быть заметен. Ученик меняет направление и до открытия результата прогнозирует `[4]`, затем возвращает ASC, переключает «все» и объясняет, почему теперь доступен `[1]`. Проба не выдаёт проектный код.
- Опора для возврата: `order_by` определяет «первую» строку, `limit` задаёт, сколько строк с начала взять. Статическая схема даёт порядок рассуждения, а переключатели позволяют проверить самостоятельный прогноз. Следующий шаг показывает, как этот же запрос возвращается из существующего репозитория.

## 04. Возвращаем задачи и проверяем прежние интерфейсы

- Связать с `SqlTaskRepository.list`: `select(TaskRow)` строит выражение, `self.session.scalars(statement).all()` выполняет его и получает ORM-строки, `task_from_row(row)` создаёт доменную задачу с id, заголовком, приоритетом, статусом и тегами. Объяснить, что выражение выбирает ORM-модель целиком, а `scalars` возвращает её экземпляры. Преобразование выполняется, пока открыта переданная Session. Владельцем Session остаётся вызывающая сторона. Чтение не требует `commit`. Сопоставить пустые списки в примере и в проекте.
- На билетах сопоставить вызов без лимита и запрос с лимитом в одну строку. В проекте `PlannerService.select_tasks(limit=None)` получает все подходящие строки. Прежний `GET /tasks` без параметров берёт первые 10 по возрастанию id; явный `limit` принимает 1–50 и вне диапазона даёт 422. CLI-команда `list` идёт через `list_tasks` → `repository.list` и выдаёт все задачи. Предложить прогноз для 12 задач без фильтра: HTTP по умолчанию показывает 10, прямой сервис с `None` и CLI показывают 12. Привязать ответ к месту, где появился HTTP-лимит.
- Подготовить чтение локальной проверки до работы с проектом. Объяснить, что готовый тест создаёт временную базу, а SQL-provider даёт прежнему GET тестовый сервис с отдельной Session для запроса. Дать легенду к выводу: список id говорит, какие строки вернулись; записанный SELECT показывает, выполнила ли база фильтр, сортировку и ограничение. Подготовительные записи в журнал выборки не входят. Готовая проверка показывает форму SELECT с позициями параметров, без вывода значений параметров. Обозначения `-k` (выбирает тест по имени), `-q` (краткий вывод) и `-s` (показывает диагностический вывод теста) пояснить рядом с командами. Ученику достаточно применить команду и по выводу соотнести экземпляр запроса со знакомой схемой; настройка фикстур, HTTP-клиента и счётчика не требуется.

### Одна задача: получить список задач прямо из SQLite

**Контекст и условие.** В Planner уже есть прежняя команда чтения списка и отдельная выборка по фильтру, направлению и размеру ответа. Нужно добавить SQL-выборку к существующему репозиторию в `app/DBase/repositories.py`. Получи готовую проверку, запусти её входную часть и выпиши id, который должен вернуться для одной открытой задачи по возрастанию. Затем сам напиши `SqlTaskRepository.select` и запусти все проверки этого файла. Сверь прежние результаты сервиса, HTTP и CLI, а по записанному SELECT объясни, почему ограничение не отсекает первую подходящую строку.

**Старт и локальная проверка входа.** Из корня Planner запусти `python -m pytest -q -s tests/test_lesson_sql_selection.py -k test_input_sql_selection`. Входной тест создаёт три задачи через SQL-сервис, завершает первую и в новом ресурсе показывает следующее состояние. `A, B, C` обозначают выданные SQLite id, упорядоченные как `A < B < C`.

| id | Задача | Приоритет | `is_done` | `tags` |
| --- | --- | --- | --- | --- |
| A | Закрыть счёт | 3 | `True` | `["архив"]` |
| B | Забрать заказ | 5 | `False` | `["город"]` |
| C | Выбрать обложку | 1 | `False` | `["макет"]` |

Первое наблюдение: входная проверка прошла, в новом чтении видны три строки и оба статуса, а в прогнозе по схеме первое открытое место занимает `B`. При провале входной проверки проверить сообщения о создании, завершении или перечтении в своей SQL-сборке; состояние SQLite для нового шага собирает сама проверка. Опоры: договор из §01, схема из §03 и объяснение запуска из §04.

**ТЗ к полученному решению.**

1. В существующем классе доступен `select(self, is_done=None, sort_desc=False, limit=None)`. Один SELECT выражает фильтр `is_done` только при переданном статусе, порядок по id по возрастанию или убыванию и SQL-лимит только при переданном `limit`. Имена локальных переменных и форма эквивалентной сборки свободны.
2. Метод возвращает список доменных `Task` через существующее преобразование, сохраняя `tags`. При отсутствии совпадений возвращается пустой список. Метод использует переданную Session и не делает запись. Доменный список собран до закрытия ресурса и читается после него.
3. Прежний `PlannerService.select_tasks` передаёт аргументы репозиторию. `GET /tasks` в тестовой SQL-сборке сохраняет поля `id/title/priority/is_done`, default 10, границы 1–50 и 422 для неверного лимита. CLI `list` через готовую регрессию выводит все строки. Обычный provider и переходный JSON-путь остаются прежними.

**Наблюдаемые случаи и локальная готовность.** После своего изменения запусти `python -m pytest -q -s tests/test_lesson_sql_selection.py`. Готовый файл покажет результаты сервиса и тестовых интерфейсов:

- Нормальный случай: фильтр открытых, ASC, без лимита возвращает `[B, C]` с исходными тегами. Фильтр завершённых возвращает `[A]`. Без фильтра и лимита ASC даёт `[A, B, C]`. На пустой базе выборка возвращает `[]`.
- Различающий случай: фильтр открытых, ASC, лимит 1 возвращает `[B]`. Ранний лимит дал бы `[]`, а потеря явного `False` дала бы `[A]`. Для DESC и того же фильтра с лимитом 1 ожидается `[C]`; без фильтра ASC с лимитом 1 даёт `[A]`. Приоритеты отличаются от порядка id.
- Доказательство размещения вычисления: для различающего вызова виден ровно один SELECT к таблице задач с предикатом статуса, порядком по id и SQL-лимитом. Проверка сверяет эти части и итоговые id. При варианте `None` для обоих ограничителей остаётся порядок, а предикат статуса и лимит отсутствуют. Проверка отличает один SQL-запрос с ограничением от полного чтения с последующим срезом в Python.
- Прежние интерфейсы: `GET /tasks?is_done=false&sort_desc=false&limit=1` под тестовым SQL-provider даёт 200 и одну запись с id `B` в прежнем публичном формате. На отдельном готовом наборе из 12 задач HTTP без параметров даёт первые 10 по id, `limit=1` даёт первую, `limit=50` даёт все 12, `0` и `51` дают 422. На тех же 12 задачах прямой сервис с `limit=None` и CLI `list` дают все 12 в порядке id.

**Помощь и будущий разбор.** Подсказка возвращает к уже показанной схеме с билетами: сначала выпиши подходящие id, затем реши, какой из них первый. Если получился пустой ответ или вернулась закрытая задача, сравни условие и предел выдачи в записанном запросе с тремя проекциями схемы. В разборе после попытки автор проведёт от смысла трёх аргументов к одному выражению, затем к чтению и преобразованию строк.
