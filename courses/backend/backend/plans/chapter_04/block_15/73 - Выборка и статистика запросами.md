Ученик сам пишет статусную, упорядоченную и при требовании ограниченную выборку, готовит фрагмент в Python и реализует буквальный SQL-поиск. Для списка он различает `None`, `False` и `True`, показывает выбранные id и подтверждает место отбора по выполненному SELECT. HTTP и CLI совместимость проверяются готовым контролем после четвёртой карточки. Штатный путь на JSON и исходная схема продолжают действовать до общего переключения.

## 01. Как условие оставляет нужные строки

**Термин и действие.** `SELECT` задаёт, что читаем. `WHERE` задаёт вопрос про каждую строку и пропускает строки, для которых ответ положительный. `False` обозначает открытое состояние, `True` обозначает закрытое, `None` во входном аргументе обозначает отсутствие пожелания о статусе. Для аргумента подходит явное сравнение с `None`. Раскрыть на бытовой записи `asked_status is None`, почему проверка истинности значения смешивает полученное `False` с отсутствием пожелания. Отдельно показать, что сравнение ORM-колонки со значением через `==` строит условие для SQLite. Вызов `where` возвращает новое описание запроса. Запрос выполняется при `scalars`; `all` читает все элементы результата.

**Ситуация и тот же набор в коде.** В реестре на столе лежат четыре карточки. Сотрудник слышит «покажите открытые» и сравнивает отметку на каждой, а при просьбе «покажите все» сверки отметки нет. В независимом примере это четыре строки `EquipmentRequest`; вносим их в таком порядке:

| id | Название | is_closed |
| --- | --- | --- |
| 10 | Лампа | True |
| 9 | Крепёж AX | False |
| 11 | Крепёж 'X' | False |
| 8 | КРЕПЁЖ_% | True |

Полный фиксированный запрос примера проецирует только колонку `EquipmentRequest.id`. Показать `select(EquipmentRequest.id)`, потом отдельным присваиванием `where(EquipmentRequest.is_closed == False)` на этом объекте запроса и выполнение `session.scalars(...).all()`. Прочитать вывод как **набор** `{9, 11}`. В примере упорядочить полученные id только для печати наблюдения и явно оговорить, что порядок SQL появится в следующем разделе. Причина результата видна в каждой отметке таблицы. Без `WHERE` набор содержит все четыре id. Переиспользование старого описания после вызова без сохранения результата также вернёт все id.

**Первая проба и возврат.** Перед выполнением запроса с фиксированным `True` ученик отмечает подходящие карточки. После выбора раскрыть `{8, 10}` и причину для каждой отклонённой строки. В карточке практики возвращаемся сюда за сравнением значения с колонкой, сохранением нового запроса и различием «передали `False` / не передали фильтр». Теория использует фиксированный отбор id. Ученик в проекте сам проектирует ветку с аргументом из внешнего вызова и сохраняет сборку предметных Task.

**Подготовка наблюдения.** В Section 01 штатная InteractiveTable показывает тот же набор. Один короткий открытый пример объявляет EquipmentRequest и создаёт четыре строки в собственной SQLite в памяти. В нём заранее определены Session, id, caption_lower и is_closed. Это данные реестра, без методов выбора и поиска. Фрагменты теории выполняются дальше в той же консоли. Две пробы по статусу и направлению используют QuizCard: ученик сначала выбирает выдачу, затем получает объяснение.

## 02. Порядок строк и предел выдачи

**Термины и действие.** `ORDER BY` договаривается, по какому ключу и в каком направлении SQLite расставит подходящие строки. `asc()` даёт меньший id первым, `desc()` больший. `LIMIT` задаёт максимальное число уже упорядоченных строк. Фиксированная форма `order_by(колонка.asc())` и та же форма с `desc()` строят новый запрос, `limit(1)` строит вариант, где останется одна строка. Проговорить знакомое правило необязательного значения: `None` означает, что предел не задан. Когда ни одной строки нет, ограничивать нечего.

**Ситуация и код.** Ответственный отложил закрытые карточки, расставил оставшиеся по id от нового к старому и взял верхнюю. Дать продолжение того же запускаемого примера на `EquipmentRequest`: запрос открытых id из раздела 01, применить `order_by(EquipmentRequest.id.desc())`, вывести `[11, 9]`, затем показать полный вызов `limit(1)` на этом запросе, вывести `[11]`. Видны обе остановки. Повторить на фиксированном возрастании после прогноза: выдача `[9]`. В этом опыте ошибочный порядок «сначала взять минимальный id из всех» оставил бы закрытую 8 и дал пустой ответ после фильтра. Так два запроса становятся различимы.

**Визуал вне 00.** На карточках реестра показать дорожку `10, 9, 11, 8` → остаются открытые `9, 11` → порядок по убыванию `11, 9` → с пределом одна строка `11`. На последнем шаге визуально снять только 9. Отметить, что первоначальное расположение карточек показывает данные, SQL-порядок задаёт только `ORDER BY`. Рядом коротко научить читать готовый след `SELECT / WHERE / ORDER BY / LIMIT` с отдельно показанными параметрами: результат id сам по себе ещё не доказывает работу внутри SQLite. В SQLite-следе SQLAlchemy после `LIMIT` может выводиться `OFFSET 0`. Это деталь диалекта, её не нужно писать. Порядок дорожки объясняет результат запроса. Внутренний план выполнения SQLite может быть устроен иначе.

**Проба и возврат.** Ученик предсказывает, какой id станет первым при смене направления на возрастание; ответ QuizCard объясняет, почему из открытых 9 стоит первой. Из практики возвращаемся за формой направлений, местом предела и чтением SQL-следа. В теории фиксированные запросы с разной сортировкой и числовым пределом. Ученик сам связывает оба необязательных решения с входами своего метода. Дальше та же SQLite решит другой вопрос к строке: содержится ли в названии буквальный фрагмент?

## 03. От ввода к буквальному совпадению

### Подготовка строки поиска

**Термин, ситуация и код.** Нормализовать ввод значит привести его к привычному виду для сравнения. На стойке реестра заявку ищут по слову из записки, игнорируя регистр букв и зазоры по краям. В Python `strip()` убирает пробельные символы на краях, `lower()` переводит буквы в нижний регистр, кавычки, внутренние пробелы, `%` и `_` сохраняются. В этом же примере показать полную форму `print(repr(raw.strip().lower()))` для `"  ЛАМПА  "` и пробельной записки. `repr` показывает границы и управляющие символы, поэтому видно `'лампа'` и `''`. Это чистая проба, обращений к базе здесь нет.

**Пустой ввод.** В прежнем JSON-поиске уже различали запись без фрагмента и непустой запрос. Переносим тот же ранний выход до чтения на SQLite. На разных записках показать совпадающий пустой список и разный след: без SELECT у пустой и с SELECT у непустой записки без совпадений. Ученику пригодится это различие в третьей карточке.

**Проба и возврат.** Сначала прогноз на `"  КРЕПЁЖ_%  "`, затем показать `'крепёж_%'` и причину сохранения двух знаков. Ученик обращается сюда за опорой для самостоятельной подготовки входа и решения, когда остановить вызов. В теоретическом коде строковая проба и ранний возврат подписи выполняют самостоятельные демонстрационные роли; из них не получается готовая проектная ветка.

### Буквальный фрагмент в запросе

**Термин, ситуация и код.** Буквальный поиск ищет подряд именно написанные символы. На бумажных карточках реестра ищем метку `'X'` вместе с двумя кавычками. Сначала посмотреть нормализованное название на уже заполненной карточке. SQLite `instr(строка, фрагмент)` возвращает позицию первого совпадения с 1 либо 0 при отсутствии. Показать в отдельной SQLAlchemy-проекции на том же реестре `select(EquipmentRequest.id, func.instr(EquipmentRequest.caption_lower, "'x'"))`, затем выполнить и прочитать пары id/позиция через `session.execute(...)`. В 11 позиция 8, в остальных строках 0. Пояснить, почему для пар используем `execute`: `scalars` оставил бы только первую колонку.

Затем добавить в диагностическую проекцию полное сравнение положения с нулём. Ученик видит одновременно id, числовую позицию и результат сравнения. Только карточка 11 даёт True. Это объясняет, какую строку оставит условие в проекте. SQLite получает искомый текст отдельно от SQL и кавычки остаются символами значения. Пример показывает проверку совпадения в проекции. Ученик сам переносит её в отбор предметных строк и строит запрос в своём методе.

**Различающий случай.** В обоих вариантах используем карточки 8 и 9 из исходного реестра. Для одиночного `%` у 8 положительная позиция, у 9 ноль. В отдельно показанном условии `LIKE` знак процента в шаблоне допускает любую последовательность, в том числе пустую, а подчёркивание допускает ровно один произвольный символ. Поэтому шаблон `%` способен выбрать обе строки. В нашем договоре ввод `%` или `_` ищет эти знаки, а ввод из пробелов вообще не ведёт к SQL. Пустой результат непустого поиска отличается: SQLite выполнила SELECT и ничего не нашла.

**Интерактив вне 00.** Ученик выбирает новую для разобранного поиска записку `" _ "`, `"  "` либо `" КРЕПЁЖ "` и сначала предсказывает id или отсутствие SQL. После выбора показываются нормализованный фрагмент, выполняется ли запрос, позиции там, где он выполняется, и набор id. Для `_` это {8}, для пробелов `[]` с пропуском SQL, для `крепёж` это {8, 9, 11}. Обратная связь объясняет, почему в первом случае одной карточке хватает знака подчёркивания, во втором поиск завершился раньше, а в третьем три положительные позиции. В отличие от визуала порядка, здесь ученик различает подготовку текста и эффект сравнения. Примеры и интерактив остаются в реестре оборудования, дают диагностическую проекцию id и результата сравнения и не публикуют метод Planner.

**Переход к проекту.** В Planner строка берётся из аргумента метода; сравнивается с поддерживаемой при записи колонкой `title_normalized`. Ученик решает, как провести свой подготовленный фрагмент через SQL-предикат, получить предметные задачи и сохранить порядок. В нормализацию колонку и прежние заголовки повторно не прогоняем.
