## Точка B

Ученик завершает выбранную задачу SQL Planner, подтверждает изменение свежим чтением и объясняет, почему повтор даёт успешный результат без вызова update и без нового SQL UPDATE. Реализует SQL delete, получает обычную Task с прежними полями после закрытия рабочей Session и None на промахе. Сам выбирает целевой ключ в паре, сверяет отсутствие выбранного id и целого соседа. Авторский прогон защищает прежние ответы HTTP и CLI. Практический результат остаётся в `project/app/service.py` и `project/app/DBase/repositories.py`, обычные точки входа используют прежний JSON до урока о переключении.

## 00. Вступление

В Планнере уже можно изменить флаг задачи по id. В журнале заявок на оборудование разберём, что видит новый читатель после завершения, повтора и удаления. Список `LinkedNotes`: «Точка старта», «Новый вопрос», «Результат». Результат назвать через три наблюдения: сохранённый статус, след команды и состав таблицы. Конкретный ответ на прогноз появляется внутри общего интерактива после выбора.

## 01. Как выбрать одну запись и проверить результат после записи

Ключ похож на номер карточки в журнале. В маленьком примере открыть по номеру заявку 9 на стойку и проверить, что номер 99 отсутствует. Обычный словарь показывает выбор по ключу и `None` на промахе. Затем напомнить точный смысл `Session.get(RequestRow, number)` в ORM. Чтение и запись одной команды проходят внутри области сервиса. Выход из области подтверждает изменение, а новая Session читает сохранённое состояние. Связать с готовым `sql_service_context` и фабрикой из проекта после PATCH. Для наблюдения выбрать отдельный учебный адрес SQLite способом предыдущей работы, включить вывод SQL на своём Engine и держать один файл между карточками. Открытое объяснение не должно содержать программу запуска.

## 02. Когда завершение требует записи

Переход означает изменение сохранённого статуса. Диспетчер находит открытую заявку 9 и ставит отметку о выполнении. В коротком Python-примере на той же стойке показать старый и новый флаги с `if not closed`. Отдельно объяснить разницу между полученным флагом и сохранённой записью. Для переноса вспомнить, что обычную Task передаёт в SQLite общий `update`, в отличие от учебного примера с одной отметкой.

Сразу после примера использовать общий `QuizCard`. Условие меняет вход: кабель под номером 8 уже закрыт. Ученик выбирает показание новой Session и число UPDATE, затем получает объяснение внутри компонента. До выбора те же данные и результат в другом блоке не показывать. После действия объяснить, почему отсутствие SQL UPDATE само по себе не доказывает отсутствие вызова репозитория. Знакомый вывод SQL и временная метка в начале `update` различают эти наблюдения. Метку удалить после практики.

## 03. Что остаётся после удаления

Материализовать результат значит собрать обычное Python-значение, пока исходные поля доступны. Диспетчер заполняет квитанцию по заявке 9 на стойку. Небольшой пример собирает отдельные поля и копию списка меток в кортеж. После примера показать, что именно `Session.delete(orm_row)` принимает для удаления и где подтверждается действие. В случае отсутствующего номера из журнала невозможно собрать квитанцию. В проекте прежняя граница сервиса превращает `None` репозитория в предметную ошибку. Полную сборку метода из этих действий ученик делает сам.

Адресность означает, что после команды исчезла строка именно по переданному номеру. В общем `InteractiveTable` показать снимки заявки 9 и соседней 8 до и после. В снимке соседа видны заголовок, количество, состояние, метки и поисковое название. Номер задаёт строку таблицы. После удаления поиск цели даёт `None`, соседняя строка совпадает по всем полям. Если бы диспетчер убрал первую карточку или повредил её метки, расхождение видно именно на двух независимых чтениях. После таблицы перейти от журнала к собственному снимку Planner.

## 04. Что мы будем делать в практике

На ученической странице только короткий `LinkedNotes`: «Завершим и повторим» и «Удалим и сверим оба id». При необходимости одна связующая фраза. Ни подготовительный код, ни прогоны, ни разборы в теорию не включаются.

### Старт и сквозные данные

Из прежней темы переходят свой `project/` и рабочие чтение, запись, PATCH и область Session. Никакая ячейка из прежней теории или путь к временной базе не требуются. Из корня проекта в прежнем Python-окружении ученик знакомым способом открывает отдельную SQLite с явно выбранным свободным файлом. Опоры из проекта: `make_engine` в `app/core/engine.py`, `create_session_factory` в `app/DBase/session.py`, схема `Base.metadata.create_all(engine)` и `TaskRow` в `app/DBase/models.py`, `sql_service_context` в `app/main.py`. Фабрика чтения и область записи используют один тестовый Engine. Для вывода SQL использовать `engine.echo = True`. Эта настройка применяется только к экземпляру в консоли, прежняя конфигурация проекта остаётся прежней.

В отдельной SQLite подготовить две записи через уже написанный `add_task`. Первая «Проверить АРХИВ», приоритет 2, метка «бумаги». Вторая «Сдать КЛЮЧИ», приоритет 4, метки «срок» и «офис». Завершить первую явным `is_done=True` через знакомый PATCH. По свежему чтению убедиться, что вторая открыта и обе записи имеют разные ключи. Записать фактически выданные id и выбранный учебный адрес. Для промаха взять положительный id, которого в этом файле нет. После правки модулей открыть свежий Python на том же файле, без повторного добавления строк. Внешние регрессии проверяет автор. Ученик выполняет описанные наблюдения самостоятельно.

### Карточка 1. Сохраняем завершение выбранной задачи

Доработать существующий `PlannerService.mark_done` в `app/service.py`. По разделам «Как выбрать одну запись и проверить результат после записи» и «Когда завершение требует записи» самостоятельно определить место границы, сохранить проверку id и передать изменённую обычную Task общему `update`. Перед операцией вторая запись открыта. После выхода из рабочей области свежий get второй записи даёт `True`, прочие поля совпадают с исходными. У пропущенного id сохраняется прежняя предметная ошибка. При работоспособной области SQL показывает один UPDATE для первого перехода. Первая карточка заканчивается сохранённой закрытой задачей.

### Карточка 2. Подтверждаем повтор без записи

У той же второй задачи уже `True`. В исходном `mark_done` есть ранний возврат до `update`. Его сохраняют, а ученик сам проектирует различающую проверку повтора. По разделу «Когда завершение требует записи» выбрать два вызова и границы наблюдения. Добавить временную метку с `print` в начале `SqlTaskRepository.update`, включить SQL-след. Положительный контроль: создать открытую «Пробу удаления» и впервые её завершить. В окне этого вызова видны метка и один UPDATE, а новый читатель видит `True`. В отдельном окне повторить `mark_done` для закрытой второй записи. Совпавшая Task, ноль меток и ноль UPDATE подтверждают повтор без записи. При совпавшем снимке и видимой метке репозиторий вызван зря. Перед третьей карточкой убрать метку и сохранить id пробной задачи для удаления.

### Карточка 3. Получаем Task после удаления

По разделам «Что остаётся после удаления» и «Как выбрать одну запись и проверить результат после записи» дописать `SqlTaskRepository.delete` в `app/DBase/repositories.py` и подключить его в существующей сервисной команде. Выбрать порядок получения обычной Task и удаления ORM-строки, самостоятельно написать ветку промаха. На прямой пробе в самостоятельно открытой транзакции использовать отсутствующий ключ, затем проверить прежнюю предметную ошибку сервиса. Для успешной проверки взять «Пробу удаления» из положительного контроля второй карточки и проверить пригодность всех полей возвращённой Task после закрытия Session. Сквозная пара остаётся доступной для следующей карточки.

### Карточка 4. Доказываем, какой id исчез

По разделу «Что остаётся после удаления» сохранить снимок двух исходных строк в шести полях `id, title, priority, is_done, tags, title_normalized`. Метки сохраняются отдельным списком. Использовать собственные ключи из первого шага. Вызвать сервисное удаление второй записи и перечитать обе в новой Session. Для цели ожидается `None`. Для соседа требуется совпадение всех шести полей, включая метки и поисковый заголовок. При ошибке сравнить первый пропавший id и первое изменившееся поле. Эта проверка завершает написанную учеником операцию удаления.

### Приватные разборы

У каждой карточки сохраняются `explanation`, `steps`, `checks`. На данных стартовой пары разобрать границу записи и переход False → True, чтение при повторе без сохранения, отдельный объект результата после удаления и доказательство адресности по двум ключам. В разборе объяснить симптомы позднего `begin`, лишнего вызова `update`, перепутанного id и потерянных меток. Разборы располагаются только в закрытом поле `answer` и содержат ход рассуждения и сравнения без готового цельного метода, патча, сценария запуска или теста.
