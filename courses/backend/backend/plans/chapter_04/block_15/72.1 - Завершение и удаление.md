## 01. Когда команда меняет состояние

Вывести правило из состояния выбранной карточки. Булев флаг описывает текущее состояние ресурса. У открытой карточки команда создаёт переход к закрытой. У закрытой уже есть нужное состояние, поэтому ранний возврат отдаёт найденную карточку. Если id отсутствует, операция завершается предметной ошибкой ещё при поиске. На независимом сюжете показать чтение булева поля в форме `if order.closed:` и ранний `return order`. Пояснить, что первая строка проверяет найденную карточку, а вторая сразу отдаёт её вызывающему коду. Для открытой карточки управление продолжается, и изменение достигает операции сохранения.

**Полный независимый пример для Stage 3.** На странице дать под подписью «Закрываем заказ» готовый пошаговый разбор с исходной таблицей, действием, ответом и свежим чтением. Пример открывается в самой теории без файлов, терминала и отдельного проекта. Модель иллюстрирует обращение к существующему ресурсу, а работа с реальной Session проверяется в проекте.

| Вызов | Выбор и чтение в области операции | Ответ и сохранение | Свежий просмотр |
| --- | --- | --- | --- |
| Закрыть заказ 9 «Витрина» | Из пары (9, «Витрина», `closed=False`), (10, «Полка», `closed=False`) выбрали id 9 и открыли его карточку | Флаг изменился, общий путь записи сохранил заказ 9. Возвращается закрытая карточка, `UPDATE` за вызов: 1 | После завершения операции новый ресурс видит 9 закрытым, 10 открытым |
| Снова закрыть 9 | Открываем 9 и видим `closed=True` | Возвращается найденная закрытая карточка, `UPDATE` за вызов: 0 | Те же строки и флаги |
| Закрыть 99 | В существующем хранилище карточки с таким id нет | «Заказ не найден», `UPDATE` за вызов: 0 | Обе прежние карточки на месте |

**Визуал.** Показать схему из двух состояний и подписать стрелки «Открыт → Закрыт, одна запись» и «Закрыт → Закрыт, ноль записей». Отдельной пометкой перед стрелками показать, что выбор по отсутствующему id останавливает операцию до перехода. У стрелки повторной команды ученик видит успешный результат при прежнем состоянии.

**Переход к проверке.** Совпавший ответ и флаг после двух команд сами по себе не показывают, был ли лишний вызов сохранения. Нужны счётчики рядом со свежим чтением.

## 02. Как отличить повторный успех от повторной записи

На тех же заказах разобрать два наблюдения. Общая запись получила карточку один раз, а SQL выполнил один `UPDATE`. За повтор оба приращения равны нулю. Счётчик за вызов показывает разницу между показанием после и перед одной командой. Свежий просмотр после выхода из области показывает сохранённое состояние. Передать неизменённый объект в хранилище лишний раз можно даже при нуле SQL-команд, если хранилище само пропустило запись. Для раннего выхода существенны и отсутствие запроса на сохранение, и отсутствие SQL-записи.

**Интерактив и малая проба.** В учебном макете ученик выбирает исходный статус заказа 9, прогнозирует число записей от двух вызовов, дважды нажимает «Закрыть заказ», затем открывает «Свежий просмотр». Макет сохраняет новое состояние между нажатиями и сбрасывает оба заказа и счётчики при смене исходных данных. При исходном `False` обратная связь показывает приращения 1 и 0, для исходного `True` показывает 0 и 0 с объяснением, что требуемое состояние уже было достигнуто. Карточка 10 остаётся прежней. Если прогноз оказался неверным, ученик сверяет причину на схеме и делает второй прогноз после смены исходного статуса. Макет показывает состояния и наблюдения без сборки строк кода из будущей задачи.

**Мост к Planner и опора на возврат.** Разобрать только интерфейсы знакомых частей. `with self.write_scope():` открывает готовую область перед первой работой с базой. Весь отступ относится к одной операции. При выходе из области после успеха контекст завершает транзакцию, в том числе при раннем `return`. `self.get_task(task_id)` ищет валидный id и передаёт вызывающему коду обычную Task либо поднимает существующую ошибку. `task.is_done` читается как булев флаг. Вызов `task.mark_done()` меняет флаг объекта в памяти и возвращает `None`. Изменённую Task по-прежнему хранит переменная `task`. Вызов `self.repository.update(task)` передаёт её готовому общему update, который возвращает сохранённую Task либо `None` при отсутствии строки. Последний случай уже распознаётся в прежнем сервисе и переводится в `TaskNotFoundError`. `handle_done` делает один вызов сервиса с выбранным id и печатает результат. Показать назначение аргументов `service`, `read` (готовый ввод id), `write` (готовый сбор сообщений). Ученик запускает готовую проверку, читает сообщения, два счётчика и снимки строк. Внутренности наблюдателей SQL, сборки сервиса и меню не нужны для изменения метода.

Готовый файл выполняет реальный `handle_done` с подготовленным вводом и сбором сообщений. Для каждого вызова готовый `sql_service_context` передаёт обработчику отдельный SQL-сервис на короткой Session. Общий update и SQL `UPDATE` по таблице задач считаются с нуля за вызов, без фоновых операций подготовки. Обёртка счётчика делегирует вызов реальному репозиторию. После закрытия каждой рабочей Session проверка открывает новую и сравнивает обе строки с исходным снимком, включая `title_normalized`. В конце успешного прогона из этих свежих чтений выводятся подписанные словари `DONE_TASK` и `CONTROL_TASK` со всеми пятью полями Task, включая tags. Ученик сохраняет их из вывода. Проверка закрывает ресурсы и очищает временные файлы. Каждый повторный запуск воспроизводит свои данные, рабочая база и JSON Planner не используются. В комплект входят запуск, изоляция, фикстура и проверки. Реализацию `mark_done`, второе приложение или настройки штатного запуска этот файл не поставляет.

**ТЗ к результату.**

1. В `PlannerService.mark_done` поиск и возможная запись находятся в уже подготовленной области. Для перехода используется прежнее изменение Task и общий `repository.update(task)` этой области. Внутри метода используется одна область. Вызов публичного `patch_task` и ручной commit в `mark_done` исключены. Ученик сверяет это в своём изменённом методе.
2. Открытая цель после первой команды даёт «Задача выполнена.», приращения вызовов update и SQL `UPDATE` равны 1 и 1. Новая Session видит `is_done=True`; прочие поля цели и вся соседняя строка совпадают с исходными.
3. Повторная команда даёт «Задача выполнена.», оба приращения равны 0. Повторное независимое чтение подтверждает прежние строки. Для отсутствующего id сообщение «Задача не найдена.», оба приращения равны 0, строки не меняются.

**Локальная готовность.** Проверка показывает исходные данные, три результата, совпадение строк с ожидаемыми и оба словаря для продолжения работы. Ученик по своему файлу подтверждает единственную область записи и объясняет, почему успешный повтор не вызывает общий update. Даже при правильном `True` ненулевой счётчик вызовов update у повтора выявляет ошибку ветвления.

**Подсказка.** Вернуться к схеме выбора состояния в разделе «Когда команда меняет состояние». Сравнить переход открытой карточки и результат уже закрытой. Для интерпретации счётчиков вернуться к «Как отличить повторный успех от повторной записи».

**Будущий разбор Stage 3.** После попытки проследить причины по данным собственного прогона: найденная завершённая задача возвращается до сохранения, открытая проходит через прежнее предметное завершение и общую запись в той же области, отсутствие переводится в прежнюю ошибку. Сопоставить каждую ветвь с сообщением, двумя счётчиками и новым чтением; код решения остаётся в раскрываемом разборе.
