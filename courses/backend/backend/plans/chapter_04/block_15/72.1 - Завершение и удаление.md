## 01. Как выбрать одну запись и проверить результат после записи

Короткий возврат к темам SQL-чтения и области записи из точки A. Ключ id ведёт к одной карточке, как номер заявки в журнале. На тех же данных показать полный знакомый вызов `session.get(RequestRow, 9)` в уже открытой области с `with sessions.begin() as session`. Номер передаётся вторым аргументом. Совпавший номер даёт ORM-строку заявки, неизвестный номер 99 даёт `None`. Рабочая область включает первый поиск и возможное изменение. Выход из неё подтверждает изменения, затем новый читатель того же ресурса проверяет результат своим `get`. В проекте область открывает сервис через готовый `write_scope`, а репозиторий работает с выданной Session. Достаточно напомнить, что преждевременный поиск в той же Session уже может открыть транзакцию. Передача функции `session.begin` была разобрана при сборке SQLite-сервиса.

Заявка 9 «СТОЙКА», 3 шт., открыта, метки `["сцена", "выдача"]`, поисковая копия `"стойка"`. В примере ниже меняется состояние заявки 9. ## 02. Когда завершение требует записи

**Переход состояния** означает, что записанный флаг получил новое значение. Диспетчер сначала смотрит отметку на найденной заявке. Если заявка открыта, он закрывает её. Если она уже закрыта, он может подтвердить тот же результат, ничего снова не изменяя. Вернуться к знакомым булеву условию, изменению объекта и измерению UPDATE из темы PATCH.

В готовом независимом примере диспетчер внутри области открывает 9 и печатает короткий результат для журнала. Показать целиком проверку прежнего флага, например `if not request.closed:` с присваиванием `request.closed = True` на той же ORM-строке. Коротко напомнить, как выглядит уже знакомый ранний `return` на небольшой функции, которая выбирает подпись по текущему флагу. Это объясняет, где продолжается выполнение, без второй реализации команд или аналога `repository.update`. Для каждого вызова замер начинается с нуля. После первого закрытия выводится «заявка закрыта», новая Session видит `True` и счётчик равен 1. Второй раз подпись та же, флаг уже `True` и SQL UPDATE равен 0. Для 99 показать пустой результат поиска и сообщение журнала «Заявка не найдена», UPDATE 0. Сервис Planner по знакомому договору отдаёт предметную ошибку для отсутствующего id. Условие на флаг рассматривается после получения существующей записи.

Причину проверить двумя наблюдениями: «строка осталась той же» и «запроса UPDATE не было». В Planner есть ещё отдельный след вызова общего `update`. Повтор может показать ноль SQL даже при лишнем вызове репозитория, если ORM не увидела изменившихся полей. Коротко пояснить, что поэтому в проекте для повтора пригодятся оба числа. Готовый счётчик показывает значение за выбранный вызов. Для первой попытки изменить вход: начать с уже закрытой заявки 8, предсказать результат и число UPDATE до показа вывода. Затем пояснить, почему результат можно подтвердить без перехода.

Перенос в Planner. Пример менял отслеживаемую строку напрямую и писал сообщение журнала. Сервис получает отдельную Task через get и передаёт её знакомому репозиторию только для сохранения нужного перехода. В практике ученик соединит границу операции со старым поведением и сам проверит, что получил последующий читатель.

## 03. Что остаётся после удаления

**Материализовать результат** значит сейчас собрать обычный Python-объект из полей найденной строки. Диспетчер сначала заполняет квитанцию по заявке, затем вынимает карточку из действующего журнала. Квитанция остаётся доступной, а поиск по номеру в журнале после подтверждения удаления пуст. Прежний `task_from_row` уже делает обычную Task для чтения. Теперь её доступность важна, когда строка будет удалена, а рабочая Session закрыта.

Продолжить тот же сценарий после закрытия заявки 9. В рабочей Session уже выбран её id из пары 8 и 9. В коде учебного журнала полностью показать создание независимой квитанции до удаления с копией списка меток. Например, готовая форма результата квитанции содержит номер, название, число единиц и метки. В том же блоке показать полный вызов `session.delete(request_row)` со строкой, а не с id, и завершение `with`. `Session.delete` отмечает объект к удалению, подтверждение выполняется на границе операции. Снаружи прочитать поля обычной квитанции `9 / СТОЙКА / 3 / ["сцена", "выдача"]`. В пустом случае после того же поиска квитанции нет (`None`) и удалять нечего. Объяснить на этом примере `is None`: просмотрщик квитанции отличает её отсутствие от существующей квитанции и печатает выбранный результат. Это код сценария журнала с квитанцией, без метода репозитория, возвращающего удалённый объект сервису, и без кода маршрута Planner.

**Адресность** означает, что исчез именно заданный id. Как в журнале после изъятия одной карточки, сверяются номер отсутствующей карточки и содержимое соседней. В примере на соседней заявке 8 показать полный перенос читаемых полей и меток в снимок до операции. Обычные значения снимка можно прочитать после закрытия Session. В другой Session после подтверждения удаления показать два обращения: `get(9)` пуст, у 8 совпадает весь снимок, включая метки и поисковую копию. У целевой заявки 9 квитанция остаётся доступна с ранее прочитанными полями. Объяснить семантику сравнения снимков целиком и отдельного сравнения с `None`. Успех команды или уменьшение числа строк сами по себе оставляют неясным, какую запись удалили.

Показать рядом два проектных договора без готовых тел методов. Репозиторий возвращает обычную `Task | None` и владеет способом работы с ORM. Сервис читает `None` как промах и через прежний путь даёт предметную ошибку, а при успехе сохраняет прежний договор публичного вызова. Граница записи остаётся в сервисе. Ученик решит, в какой точке репозитория собрать Task из ещё доступных полей, как передать результат через сервис и какие сравнения подтвердят адресность.

**Интерактив после объяснения.** Ученик меняет исходное состояние выбранной учебной заявки (открыта, закрыта, отсутствует), выбирает один id и команду done или delete. До запуска предсказывает действие записи и ответ свежего поиска. Отдельная проба предлагает удалить уже закрытую 8 из пары, где 9 ещё открыта. После попытки показать пустой get для 8, прежнюю открытую 9 с полным снимком и причину результата: состояние 8 позволяло удалить строку, а ключ 9 команды не получал. Для закрыта + done явно объяснить петлю и 0 UPDATE. Для отсутствует + любая команда объяснить промах до изменения. Дать сброс сценария. Интерактив работает по значениям и эффектам, без сборки строк проектного кода.

**LinkedNotes**

- **Завершим и повторим.** Новая Session увидит сохранённый статус. Повтор покажет ту же задачу, а оба счётчика записи останутся на нуле.

### Подготовка и учебные данные

Диагностика доступна в раскрываемом блоке самого урока как готовая ячейка Python. Из `project/` в прежнем окружении запускаем `python`, вставляем ячейку в появившееся приглашение, затем вызываем `start_lab()` для открытой строки или `start_lab(closed=True)` для опыта удаления. Первый вызов показывает путь временной базы и исходные строки. Проверку совместимости подключаем отдельной ячейкой после проверки двух id. После правки Planner начинаем свежий сеанс, чтобы загрузился сохранённый код. Оснастка не требует файлов под копирование, переноса прежних сценариев, правки `DATABASE_URL` или запуска сервера. `exit()` завершает сеанс.

На каждой карточке открывать новый независимый сеанс проверки, который создаёт собственную временную базу с исходной схемой Planner. Оснастка берёт из текущего проекта модели, сервис, SQL-репозиторий и фабрику сессий, сама готовит строки и закрывает Session. Для карточек 1–2 строка 42 открыта, для опыта удаления в карточках 3–4 та же строка заранее закрыта. Повтор в карточке 2 относится к тому же id в том же сеансе. Из одного этапа в другой передаётся написанный код. Каждая проверочная сессия использует свои данные, без переноса рабочих файлов SQLite. Перед выдачей автор подтверждает SQL-вход из точки A на фактическом результате PATCH, в том числе совместимость `build_service` и `write_scope` с этой оснасткой.

| id | title | priority | is_done в начале 1–2 | tags | title_normalized |
| --- | --- | --- | --- | --- | --- |
| 17 | Проверить АРХИВ | 2 | True | `["бумаги"]` | проверить архив |
| 42 | Сдать КЛЮЧИ | 4 | False | `["срок", "офис"]` | сдать ключи |

В промахах использовать корректный положительный id 99, которого нет среди подготовленных строк. Оснастка заранее даёт простые команды `done(id)` и `delete(id)` через сервис, `repo_delete(id)` для отдельной пробы SQL-репозитория и `read_rows(first_id, second_id)` для свежего просмотра. Уточнить при выдаче, что обозначение `id` здесь заменяется выбранным числом, `read_rows` в новой Session получает оба значения и возвращает словарь по запрошенным ключам, где значение либо полный снимок из шести полей с копией меток, либо `None`. Команда `repo_delete` возвращает результат работы репозитория после подтверждения операции и закрытия Session, чтобы его обычные поля можно было прочитать в приглашении Python. Отдельно есть готовые `reset_counts()` и `counts()`. Последняя показывает число вызовов общего update и число SQL UPDATE по таблице задач с момента сброса. Счётчики начинаются с нуля. Оснастка также показывает, была ли открыта область перед первым поиском. Готовая ячейка добавляет команду `regression()`, которая проверяет совместимость на собственных временных копиях. Это служебные наблюдения, код предметных методов пишет ученик.

### Карточка 1. Сохраняем завершение выбранной задачи

**Контекст и открытое условие.** В `app/service.py` уже есть команда `PlannerService.mark_done`. Подключить её к SQL-записи так, чтобы открытая задача сохраняла новый статус до того, как результат проверит следующий читатель. Опора «Как выбрать одну запись и проверить результат после записи» помогает найти владельца области и отделить ответ команды от свежего чтения. Опора «Когда завершение требует записи» помогает выделить переход из открытого состояния.

**ТЗ и собственный выбор.** В существующем методе выбрать границу одной области, которая охватит поиск и возможное изменение. Применить переход к уже найденной Task и сохранение общим update. Ученик решает, где начинается область в фактическом ходе метода, как связать знакомый переход с общим путём записи, как сохранить прежнюю валидацию и предметную ошибку. Входной ранний выход сохранять при переработке метода. Проверка первой команды не зависит от готовности удаления.

**Готовность.** Сначала увидеть `False` у 42, вызвать `done(42)`. Результат имеет id 42 и `True`. После закрытия рабочей Session `read_rows(17, 42)` покажет `True` у 42 при сохранении пяти остальных полей и полного снимка 17. След показывает область до поиска, один вызов update и один UPDATE. Для `done(99)` прежняя ошибка и отсутствие записи. Пустая или прежняя строка после ответа направляет к границе области и ключу.

**Подсказка.** В какой момент прежний объект уже изменился в Python и когда его состояние сможет прочитать другая Session?

### Карточка 2. Подтверждаем повтор без записи

**Контекст и открытое условие.** Открытая 42 уже успешно завершается. Закончить SQL-ветку команды для закрытой задачи и показать, что вторая команда возвращает закрытую Task без нового обращения к update. **ТЗ и собственный выбор.** Ученик размещает или переносит прежний ранний выход в общую область так, чтобы результат брался из найденной Task, а сохранение было только у перехода. Если этот выход уже оказался внутри рабочей области при первой карточке, ученик сохраняет его и самостоятельно пишет последовательность вызовов проверки повтора. В обоих случаях нужно выбрать момент сброса и объяснить, как учёт вызовов отличит лишний update от поведения ORM. Для наблюдений доступны `done`, `read_rows`, `reset_counts`, `counts`.

**Готовность.** Первое завершение уже подтверждено в том же сеансе. Счётчики обнулены перед вторым `done(42)`. Команда возвращает прежнюю Task по содержимому, свежий снимок не меняется, вызовов update и SQL UPDATE по нулю. При `1 / 0` повтор дошёл до репозитория, хотя ORM ничего не записала.

**Подсказка.** Какой флаг возвращает поиск перед второй командой и какое из двух чисел выдаст лишний вызов репозитория?

### Карточка 3. Получаем Task после удаления

**Контекст и открытое условие.** Закрытая задача 42 должна исчезнуть по номеру, а вызывающему коду нужны прежние данные удалённой задачи. В `app/DBase/repositories.py` добавить `SqlTaskRepository.delete(task_id)`. В `app/service.py` соединить его с существующим `PlannerService.delete_task`. Опора «Что остаётся после удаления» помогает перенести работу с ORM-строкой, обычным объектом и промахом. Опора «Как выбрать одну запись и проверить результат после записи» помогает выбрать место области.

**ТЗ и собственный выбор.** Ученик сам пишет обе ветви репозиторного метода, определяет момент получения обычной Task, выбирает аргумент для `Session.delete` и сохраняет проверку `is None` на сервисной границе. Положительный отсутствующий id даёт `None` в репозитории и прежнюю предметную ошибку в сервисе. Запись подтверждает сервисная область. Для прямой пробы репозитория оснастка сама открывает и подтверждает область. На штатный успех вызова `delete_task` распространяется прежний договор сервиса.

**Готовность.** В свежем сеансе `repo_delete(42)` возвращает обычную Task `42 / Сдать КЛЮЧИ / 4 / True / ["срок", "офис"]`. Задача готова до проверки адресности на паре.

**Подсказка.** Какие поля ещё можно прочитать из найденной строки до того, как она покинет журнал? Что сможет прочитать вызывающий код после закрытия?

### Карточка 4. Доказываем, какой id исчез

**Контекст и открытое условие.** В новой копии базы обе записи снова есть. Выбрать второй id в таблице, удалить именно его через сервис и по свежему чтению доказать, какая запись исчезла. Опора «Что остаётся после удаления» помогает сравнить отсутствие цельной записи и сохранность всех шести полей соседа. Опора «Как выбрать одну запись и проверить результат после записи» помогает открыть новое чтение после подтверждения операции.

**ТЗ и собственный выбор.** Ученик берёт ключи из вывода подготовки, назначает цель и соседа, сам собирает проверочную последовательность в Python: сохраняет исходные наблюдения, вызывает сервис со своим целевым id, сверяет оба id после commit. Он выбирает, какое сравнение отвечает за отсутствие цели, а какое отличит неизменного соседа от соседа с изменённой меткой или поисковым названием. Проверка работает по снимкам после закрытия Session, включает `id, title, priority, is_done, tags, title_normalized` и не требует нового метода репозитория.

**Готовность.** Изначально видны оба id. После успешного `delete` выбранный 42 даёт `None`, а снимок 17 равен сохранённому до операции по всем шести полям. Первый лишний, пропавший или изменившийся элемент указывает, какой ключ или поле сверить. После этого ученик запускает готовую `regression()`. Она на отдельных копиях проверяет done в CLI и прежнее сообщение для промаха, успешный DELETE с пустым HTTP 204, GET и второй DELETE с 404, прежние сообщения CLI и выбор другого id 17. Ответы HTTP и CLI подтверждают внешний договор. Сравнение двух снимков ученик делает сам.

**Подсказка.** Если случайно удалить первый id, какую из двух проверок поломает операция? Если сосед останется, но потеряет метку, каким будет сравнение?
