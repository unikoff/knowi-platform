## Точка B

Ученик объясняет, как при пропуске поля и при null сохраняется его текущее значение, а явный False применяется. Сам выбирает значения новой `Task`, повторно использует рабочий `replace` через публичный `update` SQL-репозитория и сохраняет прежнее правило возврата без записи. Затем сам подбирает порядок запросов для проверки этого правила. Проверяет сохранённый False, каждое неизменённое поле и tags свежим get и снимком строки. Для `{}` и тела только из null подтверждает прежний ответ, прежнюю строку и ноль UPDATE.

## 01. Какие значения просит изменить PATCH

Заявка 9 на проектор закрыта. В бланке диспетчера может отсутствовать графа статуса, стоять отметка null или «нет». В Planner null означает отсутствие нового значения для поля. Показываем три коротких JSON-тела на одном исходном статусе True. Декодируем JSON, читаем наличие ключа и значение; простой выбор через `is None` сохраняет True для первых двух форм и принимает False для третьей. Указать, почему `if value` теряет False.

`InteractiveTable` показывает три входа, наличие ключа и итог для исходного True. Кратко напомнить цепочку из прежней темы: `exclude_unset` убирает неприсланное, `exclude_none` убирает None. Смешанный запрос с False и null передаёт сервису только False. Для возврата к приёму чтения `.get(key, fallback)` взять готовый словарь бланка с одной графой и показать, что у присутствующего ключа сохраняется False, а при отсутствии берётся запасное значение. Сборку новой Task оставляем для проекта.

## 02. Когда запрос обходится без записи

Ввести no-op как запрос, который возвращает найденную запись без сохранения. Диспетчер может отправить список поручений или оставить его пустым. Короткий пример печатает переданные поручения для двух списков в той же ситуации. Пустой список не даёт вызова внутри цикла, список с одной отметкой False даёт одну строку. Сопоставить этот опыт с SQLite: подтверждение обычной записи видно в свежем чтении, а отсутствие UPDATE в выбранном запросе проверяем в SQL-журнале. Пустой вход разрешает чтение, и поиск существующей задачи нужен даже при отсутствии правок.

Оставить один прогноз через `QuizCard`: у другой закрытой заявки 12 приоритет 2. В бланке задан только приоритет 3. До ответа показать вход и варианты. После выбора объяснить, что статус останется True, а приоритет 3 требует одного поручения. Это проба переноса правила пропуска на другое поле.

Коротко вернуть к разделам «Одна Session для изменения и транзакции», «Когда появляется id и что видит читатель» и «Что сохраняется при замене». Область начинается до первого поиска, сохранение использует ту же Session. Номер и метки берём из найденной задачи. В качестве непосредственной проверки SQL показать `engine.echo = True` и `engine.echo = False` на Engine из предыдущей работы. Журнал печатает команды SQLite, в интервале PATCH смотрим строки UPDATE, относящиеся к `tasks`. SELECT и границы транзакции допустимы. Пояснить на закрытой заявке проектора. Ранний возврат завершает пустую правку до `update`. Если сервис всё же поручит сохранить прежнее True, SQLAlchemy может пропустить UPDATE, поскольку значение совпало. В обоих случаях журнал может показать ноль UPDATE. Для подтверждения раннего возврата прослеживаем, достигает ли пустая ветка вызова `update`.

## 03. Что мы будем делать в практике

Короткий `LinkedNotes`. «Применим частичную правку» с результатом False у задачи с прежними данными. «Проверим пустой запрос» с прежним ответом и нулём UPDATE. При необходимости одна фраза о переносе на повтор команды завершения.

**Общий вход.** Если прежняя учебная SQLite доступна, ученик подключается из свежего Python локальным клиентом с доработанной SQL-подменой из 71, выбирает закрытую задачу по id и заново снимает её состояние в отдельной Session.

Если старая база недоступна, номер неизвестен или подходящей закрытой задачи нет, в `project/` открывает новую временную SQLite, создаёт пустую схему и повторяет доработанную подмену `get_planner` из [«Сборка использует Session одного файла»](71%20-%20Создание%20и%20серверный%20id%20из%20базы.md#карточка-2-сборка-использует-session-одного-файла) на фабрике новой базы. В поставщике SQL-репозиторий получает Session запроса, а `write_scope` открывает транзакцию на этой же Session. Отправляет POST с «Проверить кабель» и приоритетом 4, берёт id из 201. В короткой Session добавляет `tags = ["учебная"]` найденной `TaskRow` и подтверждает. PUT по тому же id задаёт прежние название и приоритет и True. Для обеих веток перед PATCH в новой Session записывает фактические id, заголовок, приоритет, True и метки. Достаточно кода проекта и нового учебного файла; старые данные и консоль не требуются.

### Карточка 1. Выбираем поля и сохраняем частичное изменение

- Открытые опоры «Какие значения просит изменить PATCH» для выбора источника значений и «Когда запрос обходится без записи» для границы Session и последующего чтения. Из «Что сохраняется при замене» перенести знакомую запись полной задачи.
- Ученик сам меняет `PlannerService.patch_task` в `app/service.py`: выделяет конкретно заданные значения трёх полей, собирает следующую Task по старой и запросу, сохраняет обработку промаха и транзакцию вокруг чтения и записи. В `app/DBase/repositories.py` добавляет `SqlTaskRepository.update` с прежним договором `Task | None`, переиспользуя `replace`. Существующую ветку пустого входа сохранить внутри области после поиска.
- На своём id отправляет `{"is_done": false, "title": null}` с пропущенным приоритетом. HTTP 200 и свежее чтение подтверждают False, старые id, title, priority и tags. Внутренняя поисковая копия остаётся прежней. Следующая карточка использует ту же учебную базу и самостоятельно восстанавливает сравнимый исходный статус True.
- Приватный разбор проходит реальный пример, когда True стал False, объясняет отбор и сборку, прежнюю границу и пути ошибок. Код разбора ограничен изменяемыми методами. Самопроверка повторяет видимый PATCH и чтение.

### Карточка 2. Возвращаем текущую задачу без записи

- Открытые опоры «Когда запрос обходится без записи» для различия чтения и UPDATE и «Какие значения просит изменить PATCH» для отличия пустого ввода от False. Самостоятельная работа заключается в выборе исходного состояния и порядка запросов, на котором разницу можно заметить и в ответе, и в SQL. Реализация пустой ветки уже доступна в своём сервисе.
- На SQLite из первой карточки готовим сравнимый исходный статус True на том же id, по необходимости меняем только статус привычным способом до измерения. Включаем `echo` у того же Engine. Три тела для сравнения: `{}`, тело только из null и `{"is_done": false}`. Ученик решает, в каком порядке их отправить, чтобы каждый запрос начался с True без лишнего восстановления строки. Для каждого записывает ответ и число UPDATE к `tasks`, затем возвращает прежнее значение `echo`.
- Для обоих тел без нового значения ответ 200 с True, ноль UPDATE. Положительный контроль на True даёт False и один UPDATE. Если False отправить раньше и оставить строку открытой, следующие ответы с False уже не покажут разницу по статусу. Промах по положительному id с пустым телом остаётся 404 по прежнему поиску. Для компактности он проверяется автором.
- Приватный разбор объясняет, как устроить сравнение на одном исходном статусе, почему нужны три разных тела, что показывает SELECT и почему положительный контроль исключает ошибку наблюдения. В разборе один воспроизводимый порядок и ожидаемые эффекты. В следующую тему переходит способ увидеть отсутствие UPDATE.
