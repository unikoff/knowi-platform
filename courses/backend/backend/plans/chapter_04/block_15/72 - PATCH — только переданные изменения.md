## 00. Вступление

PUT уже сохраняет новую версию задачи по её id. В PATCH клиент может указать только одно поле, а остальные значения нужно взять из найденной задачи.

Один `LinkedNotes` через `items` в следующем порядке.

1. **Точка старта**. Мы умеем найти задачу по id и сохранить её новую версию.
2. **Новый вопрос**. Как применить переданное False, если другие поля пропущены или равны null?
3. **Результат**. После частичного запроса меняются только выбранные поля. Пустой запрос возвращает задачу без записи.

Сначала проследим, какие значения дойдут до записи. Затем сравним сохранённую строку и число записей после запроса.

## 01. Какие значения получит сохраняемая задача

- На знакомом пути разграничить JSON `false` и `null`, Python `False` и `None`. Существующий маршрут использует `payload.model_dump(exclude_unset=True, exclude_none=True)`. Первый параметр исключает пропущенные поля, второй исключает поля со значением null. Покажем получившийся словарь и его передачу как именованных аргументов знакомому сервису. Проверка истинности выкинула бы False. Если набор изменений пуст, сервис всё равно ищет задачу. Для известного id возвращается текущая Task, для неизвестного срабатывает прежняя ошибка.
- Начало независимого примера о заявках на публикацию. В отдельном учебном наборе заявка 12 содержит `name="Витрина"`, `rank=4`, `published=True`, `labels=["внутр"]`, `name_key="витрина"`. Ввод `{"published": false, "rank": null}` даёт только `published=False`. Полное состояние берёт имя, ранг и метки из текущей заявки, флаг из входа. Продолжение примера в 02 показывает открытие ресурса и эффект записи.
- **Отдельный визуал.** Схема на этих данных показывает путь от входа через отбор полей к полному состоянию. Подписать три линии для переданного `published`, явного null в `rank` и пропущенного `name`. Ученик прослеживает каждую линию и по подписи у результата объясняет, почему флаг стал False, а ранг остался 4. У пустого входа линия заканчивается на чтении. Это объяснение происхождения полей перед SQL-записью.
- В короткой попытке до записи предложить поменять вход на `{"rank": 2}` и назвать источник флага и ранга. Сверка показывает `published=True` из исходной записи и `rank=2` из входа. При затруднении ученик возвращается к словарю после отбора и стрелкам на схеме.

## 02. Когда полное состояние становится записью

- Продолжить тот же **полный независимый пример** в одном самодостаточном `patch_request_demo.py`, который Stage 3 подготовит и покажет в теории. В примере готовые модель заявки и данные для изолированной SQLite в памяти: заявка 12 из 01 и заявка 13 с `name="Архив"`, `rank=1`, `published=False`, `labels=["контроль"]`, `name_key="архив"`. Сценарий открывает Session примера и входит в готовую область записи перед чтением, выбирает запись 12 по id, применяет полное состояние из 01 и выходит из области. В новой Session читает обе заявки: у 12 изменился только флаг, у 13 все значения прежние, счётчик для операции равен 1. Затем пустой запрос к заявке 12 возвращает то же состояние с 0 UPDATE. Для id 99 с `{}` фиксируется отсутствие строки и 0 UPDATE. В полном примере виден порядок от выбора ресурса до вывода и объяснено, почему пустой вход всё равно требует поиска. На странице показаны готовые выводы. Автор проверит файл отдельным запуском на SQLAlchemy учебного окружения. Для ученика первая проба проходит прямо на странице без копирования файлов, установки зависимостей и запуска сервера.
- Пояснить использованные формы. `session.get(Модель, id)` берёт строку по первичному ключу или возвращает `None`. Присваивание атрибутов существующей ORM-строки изменяет её состояние в Session. `flush()` отправляет накопленные изменения в рамках текущей транзакции, а выход из готовой области подтверждает их перед успешным ответом. Отдельное чтение после выхода проверяет сохранённое состояние. В той же базе отдельный запрос меняет имя заявки 12 на «Летняя Выставка». Свежая Session показывает ключ «летняя выставка», полученный через Python `lower()`, и прежние метки. Счётчик показывает один UPDATE. В Planner это знакомые `title_normalized`, `tags`, `task_from_row(row)` и работа в переданной Session. Объяснить `update(self, task: Task) -> Task | None`. Метод принимает собранное состояние, адресуется по `task.id`, возвращает сохранённую предметную задачу либо `None` при отсутствии строки. В готовой обёртке `with self.write_scope():` вход предшествует первому `get_task`. Область закрывается после чтения, проверки и возможной записи. При исключении область откатывает изменения. Публичные сценарии PUT и PATCH имеют отдельные области, а общий способ записи живёт в репозитории.
- **Интерактив и управляемая проба.** На той же модели заявки дать переключатель «пропущен / null / false» для `published`. До нажатия «Проверить» ученик предсказывает итоговый флаг и число UPDATE. Каждая попытка стартует с `published=True`. Обратная связь показывает выбранные поля, флаг после чтения и счётчик (True/0, True/0, False/1). При ошибочном прогнозе объясняет, почему ключ отсутствовал, был отфильтрован из-за null либо сохранился со значением False. Интерактив моделирует выводы разобранного примера. Для повторной попытки дать вариант с `rank=2` при пропущенном флаге. Флаг останется прежним, а счётчик покажет один UPDATE из-за смены ранга.
- Перед практикой показать короткую линию «прочитать по id → проверить изменения → сохранить при непустом наборе → завершить область → перечитать». Счётчик берётся у готовой проверки по фактически отправленным UPDATE к таблице задач за один запрос. Нулевое число при неизменённой строке отличает no-op от записи, которая оставила значения прежними.

Работаем в формате проекта. Начинаем с собственного Planner, где PUT уже сохраняет изменения в тестовой SQLite. Готовая оснастка даёт исходные задачи, тестовый запрос и способ перечитать результат.

Для перехода к заданию использовать отдельный `LinkedNotes` через `items`.

**Технические критерии результата.**

1. `update` работает с существующим `TaskRow` по id из переданной Task в Session репозитория. Сохранённый результат возвращается в знакомом предметном формате. При отсутствии записи метод возвращает `None`. Готовая проверка интерфейса передаёт валидную Task для отсутствующего id и сверяет этот результат. Логику адресной записи можно переиспользовать внутри SQL-репозитория. В области `patch_task` чтение и обновление используют одну Session. Подтверждением записи управляет готовая область.
2. Существующий HTTP PATCH принимает прежнее тело, возвращает HTTP 200 и прежние четыре публичных поля. Свежая Session подтверждает сохранённое частичное изменение, а для пустого набора подтверждает отсутствие изменений вместе со счётчиком UPDATE. Переименование сохраняет `title_normalized = title.lower()`; id, tags и соседняя строка сохраняются.
3. Неизвестный положительный id даёт прежний 404, даже с пустым телом. Проверочный запуск также сверяет прежний ответ 422 для приоритета 6 и прежний PATCH во временном JSON после снятия SQL-подмены. Ученик не добавляет маршруты, настройки, модели, тесты или обработчики для этих проверок.
