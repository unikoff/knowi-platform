## 00. Вступление

PUT мог сохранить новое состояние публичной части задачи. Теперь нужно понять, что хотел изменить клиент, оставив часть полей за рамками запроса.

1. **Точка старта**. По id уже находим и заменяем задачу.
2. **Новый вопрос**. Как решить, какие значения взять из частичного запроса, а какие из найденной задачи?
3. **Результат**. False откроет задачу. Пропуск и null сохранят поле. Для тела без заданных изменений увидим прежнюю задачу и ноль UPDATE.

Начинаем с одной заявки на оборудование и смотрим, как ввод связан с результатом записи. Затем применяем это к своему Planner.

## 01. Какие значения просит изменить PATCH

**Учебный вопрос.** Сначала понять, что клиент сказал, затем решить, какое значение попадёт в следующую версию записи. PATCH означает частичную правку. Представить бланк диспетчера по заявке на оборудование. Пропущенная графа означает, что просьбы по ней нет. Написанное «значение не задано» приходит явно, но в Planner по договору также сохраняет прежнее значение. Отметка «нет» это конкретное новое значение. Подчеркнуть, что такое толкование null относится к договору Planner.

**Реестр заявок, первый фрагмент.** В одном небольшом примере заявка 9 на «Проектор» имеет приоритет 4, статус True, метки `["зал Б"]`. Показать действительные JSON-тела `{}`, `{"is_done": null}` и `{"is_done": false, "title": null}`. Пояснить, что `json.loads` читает текст JSON и даёт Python-словарь с None и False. На поле статуса напечатать наличие ключа, значение при чтении и результат `value is None`. Для пропуска наличие ложно, а чтение через `.get()` даёт None. Для null ключ присутствует, значение None. Для false ключ присутствует, значение False и сравнение с None ложно. Дать целиком конструкцию двух ветвей выбора *одного* значения. Показать на том же вводе, что `if value` или подстановка через `or` ошибочно оставят исходное True. На том же реестре коротко разобрать `.get(key, fallback)` на фиксированном наборе выбранных полей, например `{"is_done": False}`. Печатаем выбранный False и приоритет 4 для отсутствующего ключа. Значение по умолчанию используется только при отсутствии ключа, поэтому до такого чтения важно понимать, какие ключи попали в набор. Этот диагностический фрагмент не строит набор из параметров сервиса, новую запись и путь сохранения.

Возврат к теме «Пропуск поля в TaskPatch». У существующего маршрута `exclude_unset` отсеивает отсутствующие поля, `exclude_none` отбрасывает явное None. Значение False проходит оба фильтра. Пропуск и null видны как разные входы до фильтров, после фильтров оба не передают аргумент. Сервис видит значения его параметров по умолчанию, а в прямом вызове может получить и явный None. Для сохранения Task по id старые значения берутся из прочитанной записи. Выбор каждого поля и хранение этого выбора в сервисе остаются за учеником.

**Учебная схема вне вступления.** Три дорожки одного поля с общим исходным True. В каждой показать JSON, наличие ключа до фильтров, значение, доступное сервису, и итоговое состояние. Отличить надпись «поле отсутствует» от клетки с `null`. Под схемой пояснить, почему первые две дорожки сохраняют True и откуда на третьей берётся False.

**Интерактив, переход к записи.** Заявка 12 на «Кабель», приоритет 2, статус True. Ученик убирает ключ статуса, выбирает null либо false и до открытия ответа отмечает ожидаемый статус. Ответ показывает тело, статус после применения и объяснение, почему проверка истинности теряет false. В связанной пробе ученик заранее называет будущий снимок и наличие UPDATE для `{"priority": 3}` без `is_done`. После попытки показать приоритет 3, прежний статус True и один UPDATE. Проба требует применить правило к другому полю. Открытая часть интерактива оперирует значениями, не собирает код Planner.

## 02. Когда запрос обходится без записи

**Учебный вопрос.** Сначала нашли адресата. Затем определили, есть ли у заявки хоть одна команда на изменение. Сравнить непустой бланк с отметкой «нет» и пустой бланк: в первом есть поручение, во втором есть только адресат. На данных того же реестра показать полные условия для отсутствующего значения и для пустого набора. Пояснить на `{}` и `{"is_done": False}`, что логическая проверка словаря отвечает про наличие записей, тогда как проверка самого False отвечает про значение. Этот набор сообщает, какие значения заданы, сравнение с сохранёнными значениями в него не входит.

**Независимый запуск в одном готовом фрагменте, продолжение реестра.** Небольшой демонстрационный Python-скрипт для отдельного запуска. В памяти создать мини-таблицу реестра с уже внесённой после PUT заявкой 9 и названными полями. В видимом фрагменте открыть учебную SQLite из стандартной библиотеки, выбрать строку по id, показать возврат найденной записи, а на несуществующем id 99 показать отсутствие результата. В демонстраторе один заполненный пункт превращается в одну команду в списке поручений диспетчера. Отдельный цикл исполняет команды из списка, затем один общий SELECT читает снимок. Напечатать список поручений перед выполнением вместе с фактом наличия или отсутствия UPDATE. Показать исполнение только данных команд: при пустом списке цикл не делает ни шага. Заголовок и метки в опыте видны как сохранённые колонки. Для `{"is_done": false, "title": null}` получить строку `(9, "Проектор", 4, False, ["зал Б"])` после подтверждения и один UPDATE. Следующий вызов с `{}` возвращает тот же снимок и ноль UPDATE. Показать целиком заполнение списка, его исполнение и общее чтение результата на этих данных. Сценарий с одним явным приоритетом 3 подтвердит пробу для другой заявки. Код демонстратора работает через одиночные SQL-команды в памяти. Он не решает сборку полной Task из трёх параметров, связь вызовов репозитория и транзакции в Planner или общее решение об изменениях в сервисе.

**Почему виден результат.** Готовый счётчик фиксирует выполненные запросы к таблице, начинающиеся с UPDATE, только в окне одного вызова. На экране рядом выводятся результат и счётчик. SELECT может быть нужен даже при нуле UPDATE. Совпадающие снимки отвечают на вопрос о данных. Счётчик отвечает на вопрос об SQL. В проектной проверке ещё видим число вызовов `repository.update`: присваивание прежнего значения через ORM может дать ноль UPDATE, хотя сервис вошёл в ветку сохранения. Ученик читает эти числа и не пишет счётчик. Не считать транзакцию или чтение за UPDATE и не обещать ноль SQL для пустой правки.

**Возврат к известному.** «Одна Session для изменения и транзакции» даёт область, которая охватывает первый поиск и сохранение. «Когда появляется id и что видит читатель» даёт самостоятельное чтение после выхода из этой области. «Что сохраняется при замене» и «Заменяем поля задачи по её номеру» дают `replace(Task)`, сохранение внутренних полей и расчёт нормализованного названия. Для PATCH достаточно применить тот же путь записи полной Task в найденную строку. На опыте с id 99 объяснить, почему поиск нужен и для пустого запроса. Из раздела «Одна Session для изменения и транзакции» вспомнить, что первое SQL-чтение уже может открыть транзакцию и что сервис открывает свою область до чтения. Показать команду проверки и расшифровать названия этапов запуска до практики.

**Стоимость демонстрации.** Ученику видны вход и вывод в теории, поэтому первый прогноз доступен сразу. Для запуска нужен один готовый фрагмент и обычный Python из окружения курса. Фрагмент запускается в своём интерпретаторе или одним временным файлом вне Planner, без сервера, модели ORM и отдельной настройки. Обвязку открытия базы обозначить коротко и сверить в Stage 3 до выдачи. Сюжет и id остаются общими для обоих фрагментов.

## 03. Что мы будем делать в практике

Две ручные карточки в существующем Planner. Показать в `LinkedNotes` после теории два связанных результата.

1. **Соберём новую Task**. Явный False доходит до базы. Свежий читатель видит прежние данные, для которых клиент не задал нового значения.
2. **Проверим пустую ветку**. Пустой запрос к найденной задаче возвращает её текущее состояние. Счётчики показывают, была ли попытка записи, а неизвестный номер по-прежнему даёт 404.

Первый результат проверяет происхождение каждого поля. Второй проверяет решение о записи на том же представлении выбранных значений.

**Общий вход и только диагностическая оснастка.** Работать из `project/` своего Planner. Stage 3 показывает в теории отдельный раскрываемый блок «Диагностика для локального запуска». В нём один готовый блок для Python-консоли, вызываемый через `observe_write`. Ученик вставляет его целиком в консоль из каталога `project/` в знакомом окружении и получает команды для ближайшего наблюдения. В своём Planner он пишет только код задания. Это диагностический запуск с данными, подменой и наблюдением. В нём нет метода или фрагмента для вставки в Planner, выбора полей или ветки no-op. Он использует существующие зависимости проекта, отдельный временный файл SQLite, реальный HTTP-маршрут через `TestClient`, существующий `get_db` и временную передачу той же Session в репозиторий и в область записи. Запуск выводит ответ и обе строки из новой Session по окончании запроса. В фазе `no_op` он дополнительно выводит число вызовов настоящего `update` и число SQL UPDATE к `tasks`. Счётчики сбрасываются на каждый запрос, фикстуры и чтение снимков находятся за окном измерения, подмена и ресурсы снимаются и при ошибке. Хранилище в обычной сборке этим запуском не заполняется.

### Карточка 1. Выбираем поля и сохраняем частичное изменение

**Контекст и открытое условие.** У задачи 120 уже есть заголовок, приоритет, закрытый статус и внутренняя метка. В открытом условии дать точные ссылки «Какие значения просит изменить PATCH» для выбора поля и диагностики False и «Когда запрос обходится без записи» для области, готового запуска и чтения результата. Готовой реализации общего отбора, полной сборки с ним и нового SQL-пути в материалах нет.

**ТЗ в порядке результата.**

1. `PlannerService.patch_task(task_id, *, title=None, priority=None, is_done=None)` обрабатывает запрос в существующей `write_scope` с первого поиска. Поиск и запись используют Session репозитория. Сигнатура и поведение JSON сохраняются.

**Локальная готовность.** Выполнить ранее описанный PUT до изменений, затем в свежем Python запустить указанные в условии три вызова `observe_write` для PATCH. Новый GET после каждого PATCH подтверждает публичный результат. Независимая Session показывает внутренние поля. Это различает выбор значений всех трёх полей и переиспользование `replace` по одному связному сценарию. Первая контрольная точка уже работает без новой пустой ветки.

### Карточка 2. Возвращаем текущую задачу без записи

**Контекст и открытое условие.** В своём результате первой карточки уже можно увидеть, какие значения клиент просит применить. Теперь в том же `PlannerService.patch_task` ученик сам правит решение о сохранении. Если клиент не просит изменить ни одного поля, для существующего id нужно показать текущее состояние и обойти запись. Для неизвестного id пустое тело по-прежнему даёт 404. Ученик выбирает место ветки относительно поиска и сохранения и делает выбор по своему представлению заданных полей. Смысл правки в одной согласованной проверке для выбора новой Task и для решения о записи, без двух отдельных наборов условий для каждого поля. Предварительные примеры учат прочитать пустой набор и измерить эффект. Точную форму ветки для Planner ученик пишет сам.

В условии сослаться на «Когда запрос обходится без записи» для различия пустого набора, чтения и счётчиков и на «Какие значения просит изменить PATCH» для случая с единственным False. Данные и запуск доступны до открытия ответа.

**ТЗ в порядке результата.**

1. В `app/service.py` найденная Task возвращается для отсутствия заданных значений. Решение использует тот же отбор, что и сборка Task. Поиск сохраняет прежний 404 даже при пустом теле.
2. На `{}` и теле только с null для существующего id путь не вызывает `repository.update`. В учебной SQLite оба запроса дают ноль UPDATE и полное совпадение снимков до и после. Ответ сохраняет прежние публичные поля.
3. Явный False остаётся заданным значением. Условие о пустом входе не поглощает запрос из первой карточки.

**Локальная готовность.** В свежем Python запустить отдельные наблюдения `observe_write` с входами этой карточки. Для задачи 120 со стартовым False ответ 200 и прежний снимок при каждом из двух запросов, `{}` и `{"title": null, "priority": null, "is_done": null}`. Для каждого выводится `update calls=0` и `SQL UPDATE=0`. `PATCH /tasks/999` с `{}` возвращает 404, оба счётчика нулевые, обе строки прежние. Короткий положительный контроль внутри того же запуска на отдельной исходной задаче с True подтверждает, что вход с одним False продолжает вызывать сохранение и даёт False в новой Session. В конце ученик поясняет, что доказывают чтение, счётчики и различие между двумя типами пустого тела.

**Подсказка.** По симптомам выбрать опору. Если неизвестный номер даёт успех, проверить момент поиска. Если совпал снимок, но счётчик вызовов ненулевой, проверить ветку из раздела «Когда запрос обходится без записи».

**Закрытый разбор этой карточки.** В отдельном `tasks[].answer` дать:

- `explanation`: какие сведения нужны, прежде чем вернуть текущую запись, и почему этого должно хватить без её повторного сохранения.
- `steps`: (1) найти 120 с исходным False внутри области; (2) провести `{}` и тело из null до результата отбора и объяснить, почему входы различаются до фильтра, но дают один исход в Planner; (3) на пустом результате показать возврат текущей Task до записи и оба нулевых счётчика; (4) на 999 показать прежний путь ошибки до выдачи успешного ответа; (5) на отдельном стартовом True провести единственный False через непустое представление к сохранению. - `checks`: обе строки, оба счётчика, статус 404 и положительный контроль False. Уточнить, что доказанное здесь отсутствие записи касается входа без заданных значений, а повтор команды done использует отдельное правило следующей темы.
