## 01. Снимок, пустая таблица и явные адреса

**Что объяснить.** Снимок сохраняет данные на один момент. Init создаёт таблицу, импорт заполняет её один раз. `DATABASE_URL` для init и изолированных сборок указывает на SQLite с абсолютным путём. Импортёр принимает два файловых пути. Абсолютный путь указывает на один файл из разных каталогов запуска. Пробная БД и снимок живут отдельно от штатного JSON.

**Начало независимого примера.** Ведомость проката содержит две записи вида Planner. Показать исходный `rentals-snapshot.json` как UTF-8 JSON, где у id 2 значения `"Шлем", 2, false, ["детский"]`, у id 8 значения `"Фонарь", 4, true` и ключа `tags` нет. Представить уже подготовленную папку `C:/Temp/rental-demo/` и напечатанный адрес `sqlite:///C:/Temp/rental-demo/rehearsal.sqlite`. Ученик смотрит готовый след прогона, второй репозиторий и файлы для теории не собирает.

1. Из корня примера готовая команда запускает `python -m app.DBase.init_db` с временным `DATABASE_URL` для этого процесса. Показать появление `rehearsal.sqlite` с пустой `tasks`. Процесс init получает временный URL, глобальные настройки не редактируются.
2. `python -m app.DBase.import_tasks --help` показывает флаги. Разобрать `python -m app.DBase.import_tasks --source "C:/Temp/rental-demo/rentals-snapshot.json" --database "C:/Temp/rental-demo/rehearsal.sqlite"`. `-m` запускает модуль проекта, именованные флаги указывают, откуда читать и в какой существующий файл писать. Кавычки удерживают путь с пробелами одним аргументом. CLI делегирует `import_snapshot(source, database)`; результат функции равен числу импортированных записей. В примере вывод `Импортировано задач: 2`.
3. До показа результата предложить сопоставить три значения на карточке путей с init и двумя флагами. При выборе URL для `--database` показать, почему импортёр не откроет его как существующий файл. Если init пропущен, существующей цели с таблицей нет и импорт не стартует. При возврате использовать один ориентир: URL для настроек, путь к файлу для флага.

**Схема вне 00.** Показать отдельную линию штатных API и CLI к рабочему JSON. На пробной линии два файла с адресами из примера: снимок → импортёр → SQLite; перед стрелкой импорта отдельная стрелка init к той же SQLite, с подписью `DATABASE_URL`. Временные API и CLI указывают на тот же URL. Обвести границы Session отдельно у запроса и у команды. Схема отвечает, где именно окажутся новые данные. Из числа перенесённых задач ещё нельзя вывести совпадение записей.

## 03. Проверяем общий адрес через действия двух интерфейсов

**Завершение примера.** После успешной сверки и проверки непустой цели команда терминала `done` с вводом `2` закрывает выдачу. Отдельный `GET /tasks/2` читает для неё `is_done=true`. Затем `POST /tasks` с `title="Насос"` и `priority=3` возвращает 201, положительный свободный id и `is_done=false`. Следующая команда терминала `find` получает этот id и показывает «Насос». На иллюстрации id 9 для конкретной демонстрационной базы, в практике ориентиром служит фактический id. У двух действий короткие независимые ресурсы. Видимость изменения в новом запросе или команде объясняется подтверждённой записью в том же файле. Если адрес CLI указывает на другую SQLite, успех HTTP сам по себе общего состояния не докажет. Штатный запуск в примере продолжает показывать свой отдельный JSON со строкой «Перчатки», а «Насос» виден только в пробной SQLite.

**Интерактив вне 00, после примера.** Ведомость проката, две карточки адресов `rehearsal.sqlite` и `other.sqlite`. Второй файл подготовлен с другой выдачей, созданного «Насоса» в нём нет. Ученик выбирает адрес CLI и при желании меняет `tags` у id 2 в пробной SQLite; перед кнопкой «Проверить» предсказывает, можно ли запускать пробные записи и что увидит второй интерфейс. В показе результатов два последовательных состояния. При расхождении тега видны id, поле, значения и блокировка записи. При совпадении строк открывается трасса HTTP create → CLI find и CLI done → HTTP read. Разный адрес даёт отсутствие новой выдачи или старое состояние; общий адрес даёт свежие значения. После обратной связи предложить сменить только провалившийся параметр и повторить. Ученику остаётся самостоятельно сопоставить реальные файлы и результаты другого набора на своём Planner.

**Опора к практике.** По выводу готового smoke читать три разных наблюдения: совпали абсолютные адреса; новый запрос и новая команда прочитали фактически записанные значения; знакомые маршруты и команды сохранили видимые ответы. `GET /health` сообщает о доступности API. Связанные чтения по id доказывают общий источник. При несовпадении адреса вернуться к схеме; при несовпадении строки к сверке по id.

**LinkedNotes для моста из теории в практику.** Три заметки с действиями и наблюдениями.

1. **Выберем снимок и пустую базу.** Напечатанные пути покажут, какой файл читаем и куда переносим задачи.
2. **Сверим данные до пробных записей.** В отчёте увидим все совпадения или точную строку и поле с различием.
3. **Проверим общий адрес.** Запишем, что другой интерфейс прочитал после каждого изменения, и примем решение по прогону.

Под списком связать результаты. К связанным проверкам переходим после сверки. Ошибка пути возвращает к схеме, ошибка значения возвращает к сопоставлению строк, а ошибку чтения после записи ищем по результату соответствующего интерфейса.

**ТЗ для карточки, по порядку готовых результатов.**

1. **Подготовка и импорт (§01).** В новой папке есть синтетический снимок и пустая таблица в отдельной SQLite, явный init виден в выводе подготовки. Ученик проверяет флаги через `python -m app.DBase.import_tasks --help` и сам составляет команду с `--source` на напечатанный снимок и `--database` на напечатанный SQLite-файл. Локальный результат: успешный статус и `Импортировано задач: 2`. URL или отсутствующая цель не проходят по договору импортёра.
2. **Сверка и защита цели (§02).** До любого smoke ученик получает отчёт `compare` и отмечает полный набор id и поля, которые он подтверждает, включая `tags=[]` у записи 24 и вычисленные имена. Запускает ту же команду импорта на заполненной цели, получает ожидаемый отказ и повторно сверяет неизменные строки и байты снимка. Два совпавших счётчика при различном теге по-прежнему дают запрет перехода к записям. Локальная приёмка: полный отчёт совпадает, отчёт повторного импорта показывает отказ, после отказа данные совпадают снова.
3. **Два направления и прежний договор (§03).** Ученик запускает готовый smoke после сверки и записывает общий адрес, фактический id и результат обоих чтений. Ожидаемый связанный сценарий: HTTP `POST /tasks` создаёт открытую задачу с новым id вне набора {17, 24}, следующая команда CLI `find` читает её, другая команда `done` меняет флаг, новый `GET /tasks/{id}` видит `is_done=true`, `GET /stats` видит `total=3, open=1, done=2`. Готовый маршрутный набор затем проверяет фильтр/сортировку/limit, поиск буквального `%`, PUT и PATCH с сохранением внутренних тегов, 204 с пустым телом при удалении, 404 после удаления, 422 для невалидного ввода, health, preferences, а также прежний вывод CLI для list/search/stats. Автор готовит данные и команды этого набора. Связанный сценарий и его след читаются отдельно от регрессии. Локальная приёмка: совпали адреса и оба эффекта на свежих ресурсах, маршрутный набор прошёл, штатные точки читают опознавательную JSON-задачу в контрольной сборке, рабочий JSON и снимок прошли проверку неизменности. Положительный ответ health при пропавшей задаче в CLI общий адрес не подтверждает.
4. **Локальный вывод (§02–03).** Ученик сохраняет в своём каталоге прогона `result.md` с путём к снимку и тестовой базе, результатом полной сверки, ожидаемым отказом, фактическим id и состоянием в API и CLI, состоянием прежнего JSON и решением. Допуск есть, если прошли все перечисленные наблюдения. При сбое назвать первую проверку, её ожидаемый и фактический результат. Запись годится как памятка для нового прогона с актуальными данными. Путь к пробной базе нужен для воспроизведения этой проверки.

**Помощь и разбор.** Первая подсказка возвращает к схеме адресов и вопросу, какой аргумент указывает на уже созданный файл. Вторая возвращает к строке того же id и вопросу, где последнее подтверждённое состояние. Все параметры и способы чтения отчёта разобраны до задания. В будущем пошаговом разборе показать ход отдельного контрольного прогона, объяснить значение результата каждой проверки и остановку при первом неожиданном расхождении. Обязательные условия, фикстура и рабочий помощник доступны при закрытом разборе.
