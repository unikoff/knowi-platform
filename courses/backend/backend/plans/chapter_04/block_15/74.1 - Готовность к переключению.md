## 01. Источник, адрес и пустая цель

**Снимок, цель и явный init.** Снимок фиксирует вход на один момент; цель получает отдельную таблицу. Представить реестр заявок. У него есть заполненная ведомость и отдельная новая картотека с подписанными полями. В первой остаются заявки 4 и 9, во второй пока ни одной. У уже использованной картотеки может быть та же разметка и две старые карточки.

**Независимый пример.** Учебный реестр заявок, общий для средних разделов теории. В ведомости 4 «Проверить вход», категория «доступ», активна; 9 «Заявка на СКЛАД», категория «склад», закрыта. Stage 3 готовит одну самодостаточную демонстрацию на стандартной библиотеке Python, встроенную в теорию. Изолированный временный каталог с двумя предварительно заполненными примерами содержит `zayavki.json` и `used.sqlite`. На тех же данных показать законченный фрагмент выбора и проверки ресурса: `Path.resolve()` приводит имя к абсолютному пути, отдельным вызовом инициализируется новая `trial.sqlite` с таблицей `requests`, из уже существующей базы читается имя таблицы и `COUNT(*)`. В коде объяснить открытие выбранного файла, запрос на наличие таблицы, чтение единственного числа и закрытие соединения. Прочитать сначала новую цель, потом `used.sqlite`. Видны `requests / 0` и `requests / 2`, потому что создание схемы даёт структуру, а второй файл содержит строки. Готовый образец использует учебную таблицу и простой счётчик. Ученик в Planner выбирает адрес и оценивает состояние `tasks` по её собственной оснастке.

**Возврат к изученному.** По теме «ORM-модель и исходная схема» напомнить отдельный запуск `python -m app.DBase.init_db` с учебным `DATABASE_URL`. По теме «Однократный перенос прежних задач» напомнить полную форму `python -m app.DBase.import_tasks --source <путь JSON> --database <путь SQLite>`, где угловые обозначения описывают места аргументов. Путь с пробелами вводится в кавычках. URL для настроек Engine описывает тот же SQL-файл, а импортёр принимает два пути файлов. Наличие файла, наличие таблицы и ноль строк проверяются отдельно. Ошибка пути или отсутствующая схема отличаются от успешного счётчика со значением ноль.

**Визуал.** Одна схема на тех же двух заявках. От ведомости идут чтение и сверка к новой SQLite, перед стрелкой переноса видны табличка `requests / 0` и отдельный использованный файл `requests / 2`. Вторая ветка ведёт от обычной ведомости к прежним читателям, пробная запись появляется только в SQLite после сверки. В конце стрелки запуска снова идут к JSON. Подписи у стрелок указывают, какую операцию и в какой файл ученик сейчас проверяет.

**Первый прогноз.** Перед показом второй части вывода дать новый адрес, по которому есть SQLite с другой таблицей. Спросить, можно ли считать таблицу заявок пустой. После попытки показать «`requests` отсутствует»: счётчик `requests` применим после подтверждения самой таблицы.

## 02. Сверка по id перед первой записью

**Сверка и допуск.** Сверить значит сопоставить каждую запись с её копией по номеру и сравнить её свойства. В знакомом реестре сравнить два комплекта, в каждом по две карточки, но на одной копии потеряли наклейку «склад». Количество карточек совпадает и не обнаруживает потерю наклейки.

**Независимый пример.** В том же реестре независимо прочитать две заявки из готовых входов, в SQL-копии убрать категорию именно у 9. В полном примере показать отображение «номер → данные» из двух выборок, сравнение наборов номеров и затем значений одной номерной пары, с явным выводом первой разницы. Объяснить доступ по ключу, значение отсутствующего номера, зачем сопоставлять при разном порядке строк, и что в возвращённой строке означает каждая сторона. Два числа `2/2`, номера `4, 9` совпадают, у 9 ожидается `"склад"`, в копии поле пустое. Это отдельное наблюдение для остановки. На исправной копии видны те же номера, совпавшие значения и отсутствие расхождений. Пример сравнивает данные реестра; готовый компаратор Planner читает свои шесть колонок.

**Договор Planner.** Показать ожидаемую сторону по снимку и фактическую из свежего чтения SQLite. `id` обнаруживает потерю, добавление или перенумерацию; `title` сохраняет исходный текст, `priority` сохраняет приоритет, `is_done` состояние, `tags` внутренние метки и их порядок. Отсутствующий прежний ключ `tags` становится `[]`, а `title_normalized` вычисляется Python `title.lower()` для поиска. Одинаковый заголовок может быть у разных id. Готовый отчёт указывает отсутствующие и лишние id, а для найденной пары поле, ожидаемое и фактическое значения. Продолжение разрешено при полном совпадении и исходных байтах входа. При первой разнице ученик фиксирует расхождение, проверяет вход и цель и повторяет на новой пустой базе; старые строки сохраняются для диагностики. Пробная запись изменила бы перечень id и разрушила бы исходную точку сравнения.

**Интерактив и прогноз.** Вне 00 предложить выбрать `requests / 0` или `requests / 2` и для пустой цели выбрать исправную копию либо дефект со значением категории у 9. На первом экране видны адреса и счётчики, при выборе свидетельства раскрываются имя таблицы или пара значений по id. После решения показать первую границу остановки и причину. Для отдельной попытки дать другой вход: те же номера и число строк, изменён признак закрытия у 4, исход скрыт до ответа. Обратная связь показывает пару значений по 4 и объясняет, почему только категории здесь недостаточно.

## 03. Одна база и новое чтение по id

**Подмена адреса и перекрёстное чтение.** Подмена задаёт адрес на один пробный запуск. Перекрёстное чтение означает, что один интерфейс записывает, а другой открывает свой ресурс и читает по выданному номеру. Представить, что диспетчер принял заявку, а сотрудник по номеру ищет её в картотеке. По названию он может найти старую заявку, потому что названия повторяются.

**Независимый пример.** Использовать исправную `trial.sqlite` реестра и её учебного двойника со старыми 4 и 9. Спроектировать законченный фрагмент, где функция диспетчера на выбранном файле добавляет заявку с названием, уже встречавшимся у 9, получает новый ключ `10`, делает commit и закрывает соединение. Функция сотрудника получает адрес и ключ, открывает отдельное соединение и читает ровно один номер; одинаковый вызов для `10` выполнен на выбранном и втором файле. Показать вход обращения, ключ из результата записи и строку или пустое чтение. На общей цели видна новая строка `10`, в двойнике видна `9` и отсутствует `10`, потому что он сохранил состояние до записи. В коде дать все аргументы и состояние соединения, включая закрытие. Ученик не пишет эти функции для Planner. Из темы про SQL-создание вернуть точную связь `201` → id → `GET /tasks/{id}`, из темы про ресурс CLI вернуть `find`, ввод id и новую Session на команду. Один id переносят между интерфейсами, а адрес берут из утверждённой цели.

**Проба.** До вывода дать независимый вариант: в журнале у второго читателя отмечен другой файл, он нашёл старую `9` и не нашёл `10`. Ученик выбирает первую проверку для отсутствия `10`. После попытки показать фактические файлы и объяснить, почему успех со старым id совместим с двумя разными копиями. Если оба фактических пути совпали, продолжать поиск от успешного POST и его id, сохраняя состояние. Готовое чтение исходной ведомости показывает отсутствие `10`. Если номер уже встречается в ведомости, для пробы нужно выбрать следующую новую запись с отличимым номером.

## 04. Возврат к обычному JSON

**Возврат настроек и контрольный id.** Записать до старта, какие параметры и какой JSON использовали обе обычные точки. Снять пробный режим означает завершить использовавшие его процессы и заново запустить обычные точки с сохранённым исходным набором. В примере на время пробы два сотрудника ходили к временной картотеке, затем снова открыли обычную ведомость. Смена ярлыка рядом с уже открытой картотекой сама по себе не меняет открытую папку.

**Независимый пример.** Продолжить тот же реестр. В маленькой демонстрации две функции чтения используют ведомость по умолчанию, а параметр адреса при создании читателя временно выбирает SQLite. Показать полностью создание двух временных читателей, их завершение, создание обычных читателей с исходными параметрами и таблицу вызовов для `9` и `10`. В пробном режиме обе точки видят оба номера, после возврата обе видят `9`, обе не находят `10`. В ошибочном варианте один читатель остаётся с временным адресом и выдаёт `10`. Объяснить, что старый id доказывает доступность прежних данных, а отсутствие нового вместе с ним различает два режима. Готовое побайтное сравнение учебной ведомости до и после подтверждает сохранность файла независимо от источника текущего ответа.

**Проба.** На изменённом входе обе точки пропустили `10`, но у одной отсутствует и `9`. После самостоятельного вывода показать ожидаемый адрес этой точки и фактический пустой JSON. Обсудить, почему один ответ «не найдено» возможен также при неправильном пустом источнике. Перенос в Planner: прежний режим в обеих точках проверяется двумя чтениями и исходной записью параметров каждого запуска.

**Стоимость подготовки.** Один готовый учебный реестр проходит через разделы 01–04. При чтении теории ученик видит код, входы и выводы на странице; для прогноза меняет один вход и сравнивает результат на странице. При самостоятельном повторении достаточно одного готового автономного примера в Python и одного запуска, временные учебные файлы создаёт пример. Второй проект, SQLAlchemy, сервер и ручная подготовка SQL-файлов для демонстрации не требуются. В самой практике ученик продолжает собственный Planner с его текущим окружением.

## 05. Что мы будем делать в практике

Проектная работа в редакторе и терминале. Исходная схема, импортёр и обычные интерфейсы уже доступны из предыдущей работы. Одна группа `LinkedNotes`.

1. **Выберем снимок и цель.** Запишем два адреса и проверим пустую `tasks`.
2. **Сверим перенос.** Сравним записи по id и полям и обоснуем допуск или остановку.
3. **Прочитаем новую задачу из CLI.** Возьмём id из пробного ответа API и проверим его в другом интерфейсе и в исходном JSON.
4. **Вернём прежний запуск.** В обеих обычных точках прочитаем старую задачу и проверим отсутствие пробной.

После списка связать результаты: адрес несёт выбранную цель в импорт, сверка даёт решение перед новой записью, фактический id из ответа делает проверку возврата различающей. Ученик сохраняет эти свидетельства по мере работы.

## Поставка практики для Stage 3

Граница файлов Stage 3 исключает отдельный распространяемый инструмент. Готовые read-only проверки поставляются в теории как отдельные команды для локального Python из корня Planner. Они читают схему и строки, выводят расхождения и сверяют байты. Они не запускают приложение и не решают, продолжать ли репетицию. Временные API и CLI ученик запускает через уже использованные в своём проекте `TestClient`, подмену `get_planner`, `run` и `sql_service_context`.

- Даны значения двух коротких синтетических JSON. Ученик создаёт их в новом каталоге `data/rehearsal/<имя>` и до запуска снимает побайтные контрольные копии. `import-source.json` содержит 17 «Сверить СКЛАД», приоритет 3, `false`, `["склад"]` и 24 «Убрать коробки», приоритет 1, `true`, без ключа `tags`. `routine.json` содержит обе записи и 8 «Обычная отметка», приоритет 2, `false`. Во всех процессах `JSON_PATH` указывает на `routine.json` этого каталога, а выбранный `DATABASE_URL` ведёт внутрь того же каталога.
- В первой карточке доказательство пустоты получается отдельным init и готовым read-only наблюдением `tasks / 0`. Кандидат, обнаруженный занятым, исключается. Во второй карточке случай одинакового числа строк и одного различного тега воспроизводит отдельный JSON `tags-variant.json` с изменённым тегом при сравнении с той же SQLite. Этот файл только читается компаратором. Источник, результат импорта и обычный JSON сохраняются.
- В третьей карточке ученик связывает один SQL-адрес с двумя известными сборками, сам выполняет POST и независимую команду CLI. В четвёртой завершает пробные Python-процессы и заново запускает обычный HTTP-клиент и штатный CLI с исходным синтетическим `JSON_PATH`. Различие активного режима и выбранного адреса выводится по фактическим наблюдениям.
- Первый результат и все следующие свидетельства записываются учеником в `observations.md` внутри каталога прогона. Отдельных установок, изменений кода Planner, рабочего `.env` и рабочих файлов данных упражнение не требует.

## Практика. Четыре последовательные карточки

В каждой видимы контекст, условие, ТЗ и локальная готовность. Короткая подсказка возвращает к указанному заголовку. Пошаговый разбор открывается отдельно после попытки через собственный `tasks[].answer` ручной проектной карточки. Опоры в открытом условии указываются буквальными заголовками.

### 1. Подтвердить отдельную пустую цель

**Контекст и условие.** Синтетический каталог подготовлен. В `observations.md` ученик сначала записывает обычный режим обеих точек, путь к `routine.json` и исходное чтение записи 17 в обеих точках. Применить **«Возврат к обычному JSON»**, чтобы записать исходные параметры и контрольное наблюдение до пробных запусков. Затем показать, какой JSON пойдёт в импорт, выбрать новое имя SQLite в том же учебном каталоге и проверить происхождение и различие двух путей. Доступны готовый запуск init и проверка состояния. Применить **«Источник, адрес и пустая цель»**: различать файловый путь, URL выбранной SQLite и состояние её таблицы. Ученик сам пишет команду с выбранным URL, проверяет появление `tasks` и фиксирует результат до импорта.

**ТЗ и готовность.** В `observations.md` есть исходные параметры обеих обычных точек, читаемый `import-source.json`, иной абсолютный путь новой цели, соответствующий URL и наблюдения `tasks / 0` после явного init. Любой существующий кандидат исключён из выбора новой цели. Непустую таблицу отличают по фактическому числу строк. Отсутствующая `tasks` также исключает импорт. Локально можно предъявить выбранные пути и проверенную схему, которая пока пуста.

**Свой выбор и помощь.** Ученик назначает новый адрес среди текущих файлов и выбирает свидетельство, которое доказывает пустоту. Подсказка просит показать два независимых факта: имя таблицы и её число строк.

**Закрытый разбор для автора.** `explanation` связывает изоляцию с отличием пути к снимку, URL и файла. `steps` на именованном прогоне «репетиция один» ведут от записи обычного запуска и старого id к проверке свободного имени, выбору нового имени внутри каталога, запуску явного init и чтению `tasks / 0`. `code` содержит точные команды из корня проекта для этого прогона и проверку адресов на одной и той же цели. `checks` показывают два наблюдаемых отказа: у занятой цели `tasks / 2`, у пути с пропущенным init нет таблицы. Завершить повторной проверкой уже подготовленного пустого файла до импорта.

### 2. Сверить перенос и принять решение

**Контекст и условие.** Есть запись адресов и `tasks / 0` из первой карточки. Ученик сам пишет вызов импортёра на выбранных путях, затем открывает отчёт компаратора. Применить **«Источник, адрес и пустая цель»** для двух файловых аргументов и **«Сверка по id перед первой записью»** для сопоставления ожидаемого и фактического. До запуска API/CLI оценить набор id и каждое поле, назвать основание решения. Для различающего случая создать отдельную копию снимка `tags-variant.json`, изменить ровно один тег и прочитать отчёт сравнения с той же SQLite.

**ТЗ и готовность.** Для выбранной цели зафиксированы показания по `id, title, priority, is_done, tags, title_normalized`, исходная статичная копия использована по записанному адресу. При полном совпадении отмечен допуск к записи; при первом несовпадении указаны id и поле либо конкретный недостающий/лишний id, а допуск закрыт. Отчёт по варианту показывает равный счётчик и отличие ровно по одному полю. В рабочей репетиции повтор после расхождения идёт к новой пустой цели. Локально решение уже можно объяснить по двум отчётам без пробной записи.

**Свой выбор и помощь.** Ученик выбирает аргументы на основе прошлого шага и сам выводит допуск по фактам, в том числе различает отсутствующий старый ключ и испорченную метку. Подсказка предлагает сопоставить одну пару с тем же id и вспомнить, откуда берётся техническое поле.

**Закрытый разбор для автора.** `explanation` выводит необходимость сравнения по id ещё до контрольного POST. В `steps` показать сбор аргументов из записи карточки 1, успешный импорт с двумя строками, пары для 17 и 24, `tags=[]` у записи 24 и `title_normalized` из двух заголовков. Затем сверить учебный вариант `tags-variant.json`: у 17 ожидается `[]`, фактически `["склад"]`. Оба счётчика равны двум, решение по этой паре «остановиться». Указать проверку пути и новый пустой адрес как восстановление при реальном расхождении. `code` содержит точный вызов импорта и пару вызовов компаратора для исходного и изменённого JSON. `checks` закрепляют допуск только по совпавшим строкам, включая теги и вычисленное поле.

### 3. Прочитать новый id из другой точки

**Контекст и условие.** При положительном решении из карточки 2 ученик выбирает проверенный URL для двух временных запусков. Применить **«Источник, адрес и пустая цель»** для типа аргумента и **«Одна база и новое чтение по id»** для передачи id из ответа в новую CLI-команду. Ученик пишет обе формы запуска и запрос `POST /tasks` с выбранными допустимыми названием и приоритетом, сохраняет фактически полученный id, читает запись командой `find` и готовым чтением проверяет отсутствие id в `import-source.json` и `routine.json`. Если CLI не видит задачу, сверяет фактически открытые файлы перед новыми записями. Если id уже есть в контрольном JSON, фиксирует коллизию и создаёт ещё одну пробную задачу на проверенной SQLite. Для следующих чтений берёт id из нового ответа после проверки его отсутствия в обоих JSON.

**ТЗ и готовность.** В `observations.md` есть выбранный URL, успешный `201`, фактический положительный id и его заголовок, чтение того же id и значения из отдельной CLI Session, а также отсутствие id в обоих исходных JSON. Открытие двух разных файлов объясняет случай, в котором CLI находит старый id, а новый пропускает. До возврата у ученика уже есть новый id, который доказан в пробном SQL и различим от старых данных.

**Свой выбор и помощь.** Ученик выбирает пробную задачу, собирает два запуска из результата сверки, переносит id из своего ответа и определяет первую диагностику по наблюдению. Подсказка предлагает проверить, какой id выдал сервер и какой файл реально открыл CLI.

**Закрытый разбор для автора.** `explanation` связывает свежий commit, отдельную Session и адрес файла. В `steps` показать подстановку проверенного URL в оба запуска, конкретный корректный POST на учебном наборе и получение id из тела ответа; провести этот id через `find` и оба JSON. Для примера с id 25 явно отметить, что берётся ответ собственного запуска. Показать, какой вывод даёт чтение того же id из второй SQLite-копии с прежней задачей 17, и как проверить фактические пути до повторной записи. `code` даёт точные команды запуска, POST, ввод для CLI и вызов read-only проверки JSON. `checks` сопоставляют id и заголовок, наличие в выбранной SQLite и отсутствие в двух JSON.

### 4. Восстановить обычные запуски и проверить их

**Контекст и условие.** В `observations.md` есть исходные параметры из карточки 1 и фактический новый id из карточки 3. Применить **«Возврат к обычному JSON»**: восстановить две исходные настройки, различить режимы по старому и новому id и отдельно проверить файл. Ученик сам завершает временные процессы и записывает, как запускает обе обычные точки. В API и CLI выполняет два чтения: контрольного 17 и своего нового id. Затем запускает готовую сверку исходных файлов. При неожиданном результате проверяет активный режим и адрес только у той точки, где есть расхождение, и повторяет контроль после исправления.

**ТЗ и готовность.** Вновь запущенные обычные API и CLI указывают на синтетический `routine.json`. API читает старую запись с `200`, на новый id отвечает `404`. CLI находит старую запись и сообщает «Задача не найдена» для нового id. Исходные байты `import-source.json` и `routine.json` сверены. Старая запись присутствует и в репетиционной SQLite, поэтому её наличие само по себе совместимо с забытым пробным режимом. В `observations.md` записан результат каждой из четырёх проверок и вывод о возврате. При расхождении итог остаётся открытым до восстановления нужного режима.

**Свой выбор и помощь.** Ученик сопоставляет команды со своим исходным состоянием, переносит собственный маркер и определяет, какую точку и какой параметр проверить при асимметрии. Подсказка просит определить, какое наблюдение отличает оставшийся SQLite от ошибочного пустого файла.

**Закрытый разбор для автора.** `explanation` связывает остановку процессов и возврат прежнего источника. В `steps` показать, что именно было записано на входе, завершение пробных API и CLI, повторный обычный запуск с базовым JSON и четыре чтения для `17` и `25`, где `25` получен в предыдущем примере. Разобрать отдельно один пробный override, оставшийся в CLI (новая задача найдена), и неверный пустой JSON (старая задача пропала). `code` показывает команды остановки и запуска, GET для двух id, две команды `find` и вызов готовой сверки байтов. `checks` фиксируют матрицу API `200/404`, CLI «найдена/не найдена», совпадение двух файлов с исходными байтами.
