## 00. Вступление

Подводка от коротких Session API и CLI к вопросу о данных, которые читают обе точки. Одна группа `LinkedNotes`.

1. **Точка старта.** Обычный Planner хранит задачи в JSON. Для проверки API и CLI уже можно запустить с SQLite.
2. **Новый вопрос.** Как доказать, что задачи полностью перенеслись на один учебный адрес и что после прогона обе обычные точки снова читают JSON?
3. **Результат.** Подтвердим пустую цель, примем решение по сверке, прочитаем новую запись из другого интерфейса и проверим возвращённые настройки.

После списка связать порядок с наблюдением: пока в SQLite только результаты переноса, любую неожиданную строку или значение можно рассматривать как расхождение. Новая запись позже станет меткой, по которой можно отличить режимы.

## 01. Источник, адрес и пустая цель

У реестра есть ведомость и картотека. Снимок фиксирует, какие карточки должны перейти. Пустая цель означает, что отделение для них уже есть и в нём ноль карточек. В коротком примере создать временный учебный файл `register.sqlite3` с пустой `requests` и закрыть запись. Заново открыть существующий файл с `Path.as_uri()`, `mode=ro` и `uri=True`. В `sqlite_master` видно имя `requests`. Для счётчика объяснить отдельный запрос с `COUNT(*)`. При опечатке в имени открытие даёт ошибку без создания файла. Поменять имя таблицы в прогнозе: если нужного имени нет, её пустота ещё не установлена. Файловый URI для `sqlite3.connect` и SQLite URL для движка Planner имеют разные формы и назначения. Диагностика ученика сама выбирает цель, устанавливает наличие `tasks` и только затем считает строки.

Вернуть явный init и URL в `DATABASE_URL`. Команда курса принимает путь JSON через `--source` и SQLite URL через `--target`. В историческом StudyHub цель может передаваться файловым путём через `--database`. Перед запуском ученик уточняет форму через `--help`. Схема разводит снимок, пробную цель и обычный JSON. Интерактив даёт выбрать, какое свидетельство достаточно при пропавшей таблице, пустой или заполненной цели. До первой практической команды объяснить, как установить абсолютные пути и записать исходные параметры двух обычных запусков в изолированном каталоге.

## 02. Сверка по id перед первой записью

В реестре выдали камеру с чехлом по заявке 9. Разность множеств номеров показывает, что перестановка строк не меняет состав. В одной ячейке камеры исходный список `["чехол"]` сравнивается с SQLite-строкой, содержащей JSON `["чехол"]`. Сырое сравнение даёт `False`. После `json.loads` списки равны. Другая ведомость хранит `[]`: после декодирования остаётся `False`, чехол потерян. Таблица показывает это при счёте `2/2`. Для первой самостоятельной попытки выбрать другой случай: меняется признак закрытия, состав совпадает. После прогноза объяснить, на каком шаге надо остановиться.

Для Planner назвать представления: `id` сопоставляет две записи, `is_done` хранится в SQLite как `0/1`, `tags` лежит в её строке как текст JSON и сравнивается после `json.loads`. У прежней записи без ключа ожидается `[]`, а `title_normalized` берётся из Python `title.lower()`. Открытая теория объясняет операции и признаки, отдельный отчёт для этого набора ученик пишет сам. Ученик определяет состав и сверяет все поля до пробного изменения. Изменённая копия снимка меняет одну метку. Повтор с ней даёт другой вывод при том же счёте.

## 03. Одна база и новое чтение по id

Номер из квитанции диспетчера связывает новую заявку с записью. У старой и новой заявок одинаковые названия. На коротком примере показать один новый номер в свежем реестре и его отсутствие у читателя со старой копией. Это модель наблюдения. В Planner доказательство даёт сохранение через собственный пробный HTTP-provider и отдельная команда в SQL CLI. Ученик возвращается к `TestClient` и подмене `get_planner` из разбора HTTP-ресурса, а в CLI использует `run(None, context_factory=...)` из предыдущего занятия: `None` занимает позицию готового сервиса, а фабрика передаётся как функция.

Видимый результат `201` и фактический id предшествуют чтению той же записи. При промахе CLI сперва сопоставить настройки двух пробных запусков с выбранным адресом, затем проверить id и подтверждённость записи. Доказательство дают новая запись и её чтение отдельной командой. Проверка фактически открытого файла штатных Session относится к следующему занятию. Номер должен отсутствовать в обоих исходных учебных JSON, чтобы служить маркером при возврате. Если совпал с прежним номером, сохранить другую пробную задачу на проверенной цели и отдельно зафиксировать новый маркер.

## 04. Возврат к обычному JSON

После пробы два читателя снова открывают обычную ведомость; тот, кто остался на пробной, продолжает видеть новую заявку. На независимом реестре выбрать номер 4, который есть только в обычной ведомости, и номер 10, который появился только в пробной картотеке. Пары в этом порядке: ведомость «есть / нет», ошибочный снимок переноса «нет / нет», пробная картотека «нет / есть». Общий номер 9 встречается везде и не различает JSON. Пара «нет / нет» также возможна для пустого файла, поэтому проверяют `JSON_PATH` затронутой точки. Отдельно показать, как `read_bytes()` даёт последовательность байтов и почему сравнение со своим снимком отличает исходный файл даже при равном размере. Ученик сам выбирает два исходных файла и их две контрольные копии, пишет чтение и проверку для фактического id. Ни смена читателя, ни побайтная сверка по отдельности не закрывают обе задачи.

## 05. Что мы будем делать в практике

Короткий `LinkedNotes` с четырьмя действиями: подтвердить цель, сверить перенос, прочитать новую запись из другого запуска, подтвердить возврат. В описании каждого пункта один наблюдаемый результат. При необходимости одна фраза о связи этих результатов.

## Практика. Четыре последовательные карточки

### 1. Подтвердить отдельную пустую цель

Открытые опоры **«Источник, адрес и пустая цель»** и **«Возврат к обычному JSON»**. Ученик создаёт два JSON и их копии, выбирает две роли файлов и отдельную цель, снимает обычное чтение id 8 обеими точками и отмечает, что этот id есть только в `routine.json`. Вызвав init на выбранном учебном URL, сам пишет два наблюдения по SQLite: наличие имени `tasks` и число строк после этой проверки. Локальный результат `tasks / 0` до импорта, с абсолютными адресами и исходным режимом в `observations.md`. При отсутствующей таблице либо занятой цели продолжение исключено. Приватный разбор последовательно прослеживает выбор путей, запись исходных условий, открытие существующего учебного файла только на чтение и две независимые проверки.

### 2. Сверить перенос и принять решение

Открытые опоры **«Источник, адрес и пустая цель»** и **«Сверка по id перед первой записью»**. Ученик определяет флаги импортёра через `--help` и сам составляет вызов с исходным путём и выбранной целью. Пишет чтение SQLite и JSON, сопоставляет набор id и все шесть колонок после приведения полей к сопоставимой форме. Указывает первое различие и решение до записи. На отдельной `tags-variant.json` с единственным изменением проверяет свой способ ещё раз. Локально полное совпадение подтверждает допуск, а счёт 2/2 со сломанной парой `17/tags` останавливает перенос этой пары. Приватный разбор проводит данные от вызова до полей отчёта и разбирает пустые, различающиеся и совпавшие значения.

### 3. Прочитать новый id из другой точки

Открытые опоры **«Одна база и новое чтение по id»** и **«Возврат к обычному JSON»**. Ученик сам собирает два пробных запуска с одним адресом из подтверждённых после предыдущей практики интерфейсов. Пишет POST, переносит выданный id в отдельную команду CLI, затем пишет чтение исходных JSON по тому же id. Локальный результат включает успешное чтение записи из CLI и отсутствие нового id в обоих исходниках. При промахе сравниваются настройки пробных запусков и фактический id. Приватный разбор связывает provider, коммит, выбор ключа, новую Session команды и различающее чтение источника.

### 4. Восстановить обычные запуски

В **«Возврат к обычному JSON»** ученик берёт пары наблюдений и приём проверки байтов. Завершает пробные процессы, заново запускает обе точки в обычном режиме над исходным учебным `JSON_PATH`. Сам читает id 8 перед фактическим пробным SQL-id в каждой точке и пишет сравнение каждого JSON со своей контрольной копией. Локально API даёт `200/404`, CLI даёт «найдена / отсутствует», байты совпадают. Приватный разбор показывает для ошибочного `import-source.json` пару `404/404` и для оставшейся SQL-подмены `404/200`; в CLI им соответствуют «отсутствует / отсутствует» и «отсутствует / найдена».

## P4. Сверка результата

Четыре независимых результата доступны в порядке работы: пустая цель до импорта, сверка содержимого до записи, перенос нового id между двумя точками, подтверждение обычных запусков и сохранности файлов. Для упражнений определены исходные данные, точные заголовки опор, собственная запись действий и следующий полезный результат. Различающий случай счёта 2/2 проверяется на отдельном изменённом снимке. Передача из занятия о ресурсе команды использует отдельный HTTP-provider и CLI-контекст; следующий переход начинает со штатного JSON и свежего архива после паузы писателей. Исторический Planner `cefe505` ранее подтвердил эти интерфейсы на синтетических файлах. Независимые примеры и новый прогон проверки после поправки относятся к Stage 3.
