## 00. Вступление

Подвести от вопроса «какие заявки сейчас открыты?» к вопросу «сколько заявок в каждом состоянии?». Использовать один `LinkedNotes`.

1. **Точка старта**. Запрос по статусу возвращает подходящие задачи.
2. **Новый вопрос**. Как SQLite из одного набора строк получит сразу три числа?
3. **Результат**. Одна строка запроса даёт сводку с именами `all`, `open`, `done`.

Сначала станет виден вклад одной задачи. После этого можно объяснить, почему общий и условные счётчики дают разные числа.

## 01. Как одна строка попадает в счётчик

**Данные связного примера.** Реестр заявок на оборудование. Поле «Штук» есть у каждой заявки. Полка заполняется, когда её назначили. Состояния видны с начала примера.

| id | Заявка | Состояние | Штук | Полка |
| --- | --- | --- | --- | --- |
| 8 | Рулетка | Завершена | 1 | R2 |
| 9 | Маркеры | Открыта | 3 | NULL |
| 10 | Кабели | Завершена | 2 | R5 |

**CASE, условное значение строки.** Представить стол выдачи. Для списка заявок на два предмета и больше кладём номер талона в ячейку, при остальных оставляем её пустой. В SQL условие вычисляется для каждой строки. При совпадении CASE возвращает её id, иначе SQL NULL, то есть значения в этой ячейке нет. Из темы отбора вернуть точное различие: False соответствует открытой задаче, True завершённой, а отсутствие фильтра оставляет оба статуса. Условие в CASE вычисляет значение для строки, поэтому она остаётся доступной общему счётчику.

**Независимый код в том же реестре.** В демонстрации с `EquipmentRequest` показать полный SQLAlchemy CASE, исполняемый вместе с id в обычном SELECT по реестру. Условие `EquipmentRequest.quantity >= 2` и два результата (id, `else_=None`) дают пары `(8, None), (9, 9), (10, 10)` по порядку id. Объяснить пару «проверка, значение для истинного условия», переход `None` ⇄ SQL NULL на этой ячейке и почему заявка 8 всё ещё видна в первой колонке.

**COUNT, число заполненных ячеек.** На том же столе посчитать заполненные места в колонке талонов. В одном коротком полном SQL-запросе к реестру показать условный `COUNT(CASE WHEN quantity >= 2 THEN id ELSE NULL END)`, общий `COUNT(id)` и сопоставить 2 и 3. Так видно композицию CASE внутри COUNT. Смена пустой ветки на 0 даёт 3, потому что ноль тоже значение. Показать два условных столбца по статусам на заявке 9. Для открытых получается id 9, для завершённых NULL, а общий COUNT(id) учитывает 9. До раскрытия предложить провести 10 через обе колонки и объяснить вклад. Обратная связь показывает NULL для открытых, 10 для завершённых и единицу в общем счёте.

**Учебный визуал вне 00.** Одна таблица с тремя строками реестра, двумя вычисленными столбцами по статусам и общим столбцом id. Под ней три именованных итога `all=3, open=1, done=2`. При фокусе на строке выделяются учтённые ячейки. Связать клетки с разными итогами так, чтобы ход счёта можно было прочитать также по тексту.

**Опора и переход.** Краткая опора в конце раздела связывает «проверка строки → id или NULL → число заполненных ячеек». По одному COUNT понятно, какие строки он учитывает. Дальше важно прочитать, какому вопросу отвечает каждое из нескольких чисел.

## 02. Как прочитать итоги по именам

**Метка и одна агрегатная строка.** На столе выдачи пересчитываем талончики и вносим два числа в одну строку отчёта, каждое под своим заголовком. В запросе метка `.label(...)` называется как поле отчёта. Несколько агрегатов в одном SELECT без группировки сводят входные строки к одной строке, даже если таблица пуста. Разобрать чтение `execute(...).mappings().one()`: выполнение, доступ к результату как к отображению и ожидание ровно одной строки. Показать обращение `row["имя"]` и объяснить, как из знакомых ключей получается словарь. Источники для автора: [CASE и выражения SQLAlchemy 2.0.55](https://github.com/sqlalchemy/sqlalchemy/blob/rel_2_0_55/doc/build/core/sqlelement.rst), [строки результата и MappingResult](https://github.com/sqlalchemy/sqlalchemy/blob/rel_2_0_55/doc/build/core/connections.rst).

**Независимый код на тех же данных.** Полный SELECT SQLAlchemy считает назначенные полки через `func.count(EquipmentRequest.shelf_code).label("with_shelf")` и заявки через `func.count(EquipmentRequest.id).label("registered")`. Обе колонки уже есть в схеме. Здесь `with_shelf=2`, `registered=3`. Прочитать `registered` первым по ключу, хотя в SELECT раньше указан `with_shelf`. Для короткого прогноза поменять порядок выражений в SELECT, сохранив метки. После попытки показать, почему результат по именам совпал. Напомнить, что `scalars()` возвращает один элемент строки результата и полезен для прежнего `select(TaskRow)`. Здесь нужны все именованные колонки.

**Интерактив вне 00.** На исходных трёх заявках предложить перевести заявку 8 из завершённой в открытую. Ученик сначала выставляет прогноз id или NULL для обоих CASE на этой строке и три числа для подписанных итогов, затем подтверждает ответ. Обратная связь показывает перенос id 8 между двумя столбцами, постоянное значение общего счёта 3 и новые `open=2, done=1`. Ошибка с обменом групп видна по подписям и по перемещению id. Предусмотреть сброс, чтение состояния текстом и доступ с клавиатуры.

**Воспроизведение.** Теория использует один компактный подготовленный фрагмент для временной SQLite в памяти на всё объяснение. Его можно прогнать в Python окружения Planner с установленной SQLAlchemy. Создание схемы и три строки вводятся готовой обвязкой примера, без нового каталога, файла или процесса API. Автор объясняет, откуда берётся Session и какие из строк примера строят запрос. Полная открытая форма CASE относится к количеству предметов, условный COUNT показан целиком в SQL для того же вопроса, именованный SQLAlchemy-запрос считает готовые колонки. Практика требует перенести связь выражений в SQLAlchemy, составить два статусных условия и проверить их соответствие именам. Примеры не содержат метода Planner или SQLAlchemy-фрагмента с двумя статусными агрегатами.

**Опора и переход.** Метка указывает смысл числа, `mappings().one()` даёт одну строку, значения читаются по ключам. Прогноз с одной задачей из первой карточки поможет сверить смысл каждого ключа во второй.

В терминале из корня `project` готовый блок запускает знакомый Python окружения проекта, создаёт отдельный временный SQLite-файл через текущую схему и открывает Session. На Windows запуск через `.\.venv\Scripts\python.exe`, по README проекта доступен также активированный интерпретатор. Автор даёт блок целиком как вспомогательный запуск из терминала. Он загружает фикстуру и вызывает уже существующие точки проекта. Ученику достаточно выбрать режим пробы или локального вызова метода, сохранить свой ответ и сравнить вывод. Обычную базу и файлы проекта подготавливающий блок не трогает. Файл фикстуры удаляется самим запуском после закрытия ресурсов. После правки метод вызывается новым процессом на таком же наборе.

| id | title | is_done |
| --- | --- | --- |
| 24 | Сверить опись | False |

Поля priority, tags и title_normalized заполнены фикстурой по существующему договору. Проба по id показывает только два полученных значения и использует учебные данные, без выдачи запроса будущей статистики. Порядок номеров в выводе не влияет на смысл счётчиков.

**Обзор для `LinkedNotes`.**

1. **Проследим одну строку.** Выберем задачу по статусу среди одинаковых названий, запишем два значения и сверим их с пробой.
2. **Сверим именованные числа до HTTP.** Напишем метод сводки и увидим значения трёх ключей на тех же строках.

Первая карточка оставляет заметку о том, какая ячейка содержит id для выбранного статуса и почему. Во второй это служит проверкой смысла ключей. Код отдельного демонстрационного запроса переносить в проект не требуется.

### Карточка 1. Проследим одну строку

**Условие.** В разделе «Как одна строка попадает в счётчик» вспомним, когда CASE оставляет id, что означает NULL и какую ячейку учитывает COUNT. Среди двух задач «Сверить опись» найдём завершённую, запишем её id и заранее решим, что для неё получится в столбцах открытых и завершённых. Рядом запишем, изменяет ли она общий счёт и почему. Затем сверим прогноз готовой пробой по выбранному id. В черновике рядом с редактором оставим id, прогноз и причину для каждой колонки. Этой записью воспользуемся во второй карточке.

**ТЗ.**

1. Выбрана завершённая строка из двух одноимённых по данным таблицы. Её id указан в записи и передан в пробу.
2. Записаны предсказанные значения обоих CASE как id либо NULL (`None` в Python) и объяснён вклад строки в каждый из трёх счётчиков.
3. Наблюдение получено на выбранной строке до написания агрегата.

**Готовность.** Проба, запущенная по записанному id, подтверждает значения в обеих колонках, а из заметки понятно, почему id учитывает общий COUNT. При расхождении сначала сравнить выбранные id и статус с исходной таблицей.

**Подсказка.** У одинаковых заголовков разные статусы. Что проверяет каждая из двух подписанных колонок?

**Самостоятельное решение.** Выбор строки, два отдельно вычисленных значения и их объяснение. Ни данные, ни проба до попытки не называют нужный id и результат для него вместе.

**Будущий закрытый разбор `tasks[].answer`.**

- `explanation`. Один заголовок соответствует двум id. Статус позволяет выбрать строку, а CASE определяет её вклад отдельно для каждой колонки.
- `steps`. Сначала сопоставить строки 24 и 41 по `is_done`, выбрать 41. Затем провести 41 через обе проверки: условие для открытых даёт NULL, завершённое даёт 41. Общий счёт видит id 41, поэтому вклад равен 1 в `all`, 0 в `open`, 1 в `done`. При сравнении объяснить, почему ошибочный выбор 24 даёт id в другой колонке. Если вместо NULL проставить 0, COUNT засчитает значение.
- `code` и `checks`. В отдельном разборе показать запуск готовой пробы с аргументом 41 и её фактический вывод `open_case=None`, `done_case=41`. Повторить по 24 как короткое объяснение ошибки выбора. Проектный файл в этой карточке не нужен.

### Карточка 2. Сверим именованные числа до HTTP

**Условие.** В разделе «Как одна строка попадает в счётчик» используем правило вклада id и NULL, а в «Как прочитать итоги по именам» возьмём способ дать колонкам имена и затем прочитать значения по ключу. В `project/app/DBase/repositories.py` допишем `statistics()` у `SqlTaskRepository`. Нужно одним обращением к SQLite посчитать все задачи, открытые и завершённые. Сверим смысл подсчёта с заметкой из первой карточки, затем вызовем метод напрямую на подготовленных задачах. После совпадения готовый контроль проверит пустую таблицу, изменение счётчиков после завершения и удаления, форму SQL и прежний ответ `/stats`.

**ТЗ.**

1. В существующем репозитории реализован публичный метод `statistics(self) -> dict[str, int]`. Используется Session, которой уже владеет вызывающий код.
2. Один агрегатный SELECT над `tasks` выдаёт одну строку с тремя именованными колонками. `all` включает весь набор, `open` только открытые, `done` только завершённые. Оба статусных COUNT считают условные значения. Чтение результата происходит по именам, без загрузки списка задач и Python-подсчёта.
3. Прямой вызов на данной фикстуре возвращает `{"all": 3, "open": 1, "done": 2}`. На пустом наборе те же ключи содержат нули. Готовый HTTP-контроль ожидает `{"total": 3, "open": 1, "done": 2}` через тестовую подмену.

**Готовность.** Первое сравнение производится сразу после прямого вызова, до HTTP. Проверить все три значения по ключам. Если группы равны 2 и 1 в обратном порядке, начать со связи метки и условия в соответствующем агрегате. После этого запустить готовый контроль этой же карточки. В его коротком отчёте видно по именам, что после завершения id 24 ожидаются 3, 0, 3, а после удаления той же задачи 2, 0, 2. Исходный смешанный набор для HTTP создаётся заново.

**Подсказка.** Вернёмся к заметке про выбранную строку. Под каким именем она должна прибавить единицу? Что должно появляться в колонке другой группы, чтобы её COUNT ничего не добавил?

**Самостоятельное решение.** Ученик переносит смысл статусного фильтра в два вычисляемых столбца, выбирает аргумент для общего счёта и связывает каждое выражение с меткой. Он собирает свой один SQLAlchemy-запрос и возвращает числа из его именованной строки. В подготовке есть данные, Session и вызов метода. Выражения и тело метода доступны только в отдельном разборе.

**Будущий закрытый разбор `tasks[].answer`.**

- `explanation`. Один запрос сохраняет весь набор для общего счёта. Каждый условный счётчик внутри того же запроса получает id только от своей группы.
- `steps`. Взять общий счёт по непустым id. Для двух условий вывести вклад всех трёх строк. У открытых на вход COUNT идут 24, NULL, NULL, у завершённых NULL, 41, 58. Закрепить имя на каждом выражении по смыслу и собрать один SELECT. Выполнить запрос той же Session, прочитать одну именованную строку и вернуть словарь. При обмене меток `open` покажет 2, `done` 1 при верном `all=3`. При `ELSE 0` оба условных подсчёта дадут 3, потому что 0 учитывается. Глобальный фильтр по одному статусу уберёт строки также из общего счёта.
- `code`. На Stage 3 приложить рабочее тело `SqlTaskRepository.statistics()` и необходимые импорты в закрытом поле карточки. Дать границу вставки в `project/app/DBase/repositories.py` и точную команду прямой проверки из корня `project`. В открытой части остаются контракты, данные и подготовка.
- `checks`. Прямой метод возвращает три заданных ключа и значения. В готовом контроле пустой набор даёт `(0, 0, 0)` в порядке all/open/done, затем на независимой смешанной фикстуре done(24) даёт `(3, 0, 3)`, delete(24) даёт `(2, 0, 2)`. Снимать SQL только на вызове statistics после подготовки, подтвердить один SELECT с агрегатами и отсутствие вызова `list()`. На исходной смешанной фикстуре проверить HTTP `all → total` и восстановление прежней зависимости. Исключения, управление транзакциями и точное форматирование SQL не являются отдельными ученическими критериями.
