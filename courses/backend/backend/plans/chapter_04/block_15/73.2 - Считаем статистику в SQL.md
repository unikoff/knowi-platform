## 01. Как строки участвуют в подсчёте

**Смысл и порядок.** Ввести агрегат как итог по набору строк. На заказах показать `COUNT(id)` и пояснить, почему у каждой строки есть id. Затем для каждого статуса показать, как SQL для каждой входной строки вычисляет `CASE`: подходящая строка отдаёт свой id, остальные дают `NULL` (значение отсутствует). `COUNT(выражение)` считает все значения, кроме `NULL`. Для различения показать, что ноль и логическое ложное значение также присутствуют. Например, `ELSE 0` заставит счётчик учесть и неподходящую строку. Два условия относятся к отдельным столбцам результата, поэтому оба статуса и общий итог считаются по всей таблице.

**Статический визуал.** После объяснения показать матрицу заказов. Входные строки `2 false`, `6 true`, `9 false` имеют столбцы участия «все», «ожидают», «закрыты». Для id 6 показать `6 | NULL | 6`, для id 2 и 9 показать id в первых двух столбцах и `NULL` в третьем. Внизу видна единственная итоговая строка `(3, 2, 1)`. Ученик прослеживает маршрут id 6 до двух счётчиков и объясняет пропуск в третьем.

**Малая проба.** На двух отдельных карточках заказов `4 false` и `7 true` ученик до раскрытия отмечает вклад в каждую колонку и предсказывает `(2, 1, 1)`. Затем предсказывает результат для таблицы без заказов. Обратная связь показывает ячейки id/`NULL`, итог `(0, 0, 0)` и причину: считать нечего в каждом из трёх столбцов. Для возврата оставить рядом форму «условие → значение или `NULL` → количество имеющихся значений», после чего перейти к чтению результата в Python.

## 02. Как запрос отдаёт одну строку

**Форма запроса и результата.** В SQLAlchemy показать отдельно назначение `select`, `func.count` и `case`. Из `sqlalchemy` импортируются `func`, `case` и `select`. Обращение `func.count(...)` строит вызов SQL `COUNT`. Пояснить позиционные аргументы `select` как столбцы результата и пару `(условие, значение)` в `case`. Для заказов разобрать `OrderRow.is_closed.is_(False)` и `.is_(True)` с одним булевым аргументом, а при отсутствии `else_` неподходящий заказ даёт SQL `NULL`. Ссылки на столбцы задают исходную таблицу. Один общий запрос без группировки, внешнего фильтра и лимита даёт один итог на весь набор. `session.execute(statement)` выполняет запрос, а `one()` проверяет, что в результате ровно одна строка. Сам итог вычисляет SQLite. Показать позиционную распаковку трёх значений в порядке аргументов `select`. Напомнить, что знакомая цепочка `scalars().all()` собирает список значений первого столбца.

**Полный независимый пример для Stage 3.** В этом разделе страницы дать одним видимым блоком законченный запускаемый пример на SQLAlchemy с подготовленной `OrderRow` (`id`, `is_closed`), временной SQLite в памяти, созданием схемы, вводом трёх заказов из матрицы и готовой Session. Ясно отметить границу подготовки, роли Session и таблицы, затем разобрать три выражения и чтение одной строки по частям. Результат примера выводится тремя числами в порядке «все / ожидают / закрыты», без проектного словаря и маршрута. Показать последовательность наблюдений: начальное состояние `(3, 2, 1)`, закрытие заказа 9 даёт `(3, 1, 2)`, удаление 6 даёт `(2, 1, 1)`, пустая таблица даёт `(0, 0, 0)`. Операции подготовки и изменения заказов автор предоставляет целиком. На странице видны вход, запрос, вывод и причина каждого изменения. Для первого наблюдения достаточно страницы, схема заказов и отдельный локальный проект не нужны.

**Интерактив после примера.** Дать четыре заказа `2 false`, `6 true`, `9 false`, `12 true`. На старте виден итог `(4, 2, 2)`. Ученик выбирает «закрыть 2», указывает ожидаемые изменения трёх счётчиков и нажимает «Проверить». Видит `(4, 1, 3)` и объяснение, что id 2 сменил столбец участия, а общее число заказов сохранилось. Далее ученик прогнозирует эффект действия «удалить 9». Проверка показывает `(3, 0, 3)` и объясняет, какие вклады исчезли с удалённой строкой. Режим «Пустая таблица» проверяет прогноз о числе строк результата и раскрывает одну строку `(0, 0, 0)`. Для повторной попытки есть сброс.

**Переход к проекту.** По пути `statistics() → get_statistics() → GET /stats` отметить, где раскладываются три значения по ключам и где `all` становится `total`. В собственной модели Planner `TaskRow.is_done` принимает `False` для открытой задачи и `True` для завершённой. Показать смысл сигнатуры нового метода `statistics(self) -> dict[str, int]`. `self.session` уже выдана репозиторию. Ключи словаря являются строками, значения являются целыми числами. В CLI готовый обработчик берёт те же три числа и выводит долю завершённых. Ввести чтение результата локальной проверки: значения сводки показывают правильность подсчёта, число SELECT и факт агрегации отличают его от загрузки списка. При затруднении вернуть к порядку трёх выражений и распаковке строки.

## 03. Что мы будем делать в практике

**Контекст.** В своём Planner проверяем статистику на тестовой SQLite. После завершения и удаления задач пользователь должен видеть прежний формат сводки и актуальные числа.

**Условие.** Открыть `project/app/DBase/repositories.py` в своём проекте после практики буквального поиска и найти `SqlTaskRepository`. Самостоятельно написать его `statistics()` и добавить нужные импорты. Нужно попросить SQLite посчитать все задачи, открытые и завершённые, прочитать три числа и вернуть их сервису. Затем установить готовый файл проверки из теории, сверить отдельно результат репозитория и прежние ответы сервиса, HTTP и CLI на пустой базе, на смешанных данных и после знакомых операций. В видимом задании назвать все случаи и способ запуска. Следующие два пункта оформляются как `LinkedNotes` в последнем учебном разделе.

- **Получим сводку запросом.** В собственном репозитории ученик строит выражения, выполняет SELECT, читает строку и собирает словарь. Подготовка в разделах 01–02. Быстрая локальная проверка показывает числа на пустом и смешанном наборах и результат контроля SQL.

Первая проверка показывает форму запроса и результата. Полный прогон подтверждает, что тот же метод обслуживает прежние интерфейсы и считает новое сохранённое состояние. Попросить объяснить на пустой базе, почему в результате одна строка и почему все её поля равны нулю.

### Техническое задание и локальная готовность

- У `SqlTaskRepository.statistics()` один агрегатный SELECT с тремя целыми числами в одной строке результата. Подсчёт выполняет SQLite с `COUNT` и условными `CASE`. Остальные методы сохраняют свою роль. На этапе подсчёта отсутствуют дополнительные SQL-вызовы, загрузка исходных строк, создание объектов `Task`, запись, commit и закрытие чужой Session.
- Сервис и репозиторий возвращают словарь с ключами `all`, `open`, `done`. HTTP `GET /stats` отвечает 200 с ключами `total`, `open`, `done`. Проверка сравнивает значения и набор ключей. CLI проверяется через существующий обработчик с тем же SQL-сервисом. Формат и процент совпадают с прежней реализацией, в том числе `0.0%` при нуле задач.
- Случаи ниже фиксированы для выдачи. Смешанные состояния различают счётчики, пустой набор проверяет количество строк результата и нули, done и delete различают изменение статуса и удаление записи. Числа приведены в порядке «все / открытые / завершённые».

| Сценарий для локальной проверки | Данные и действие готовой оснастки | Сервис `all/open/done` и HTTP `total/open/done` |
| --- | --- | --- |
| Пустая база | Схема создана, задач 0. | `0 / 0 / 0` |
| Смешанная база | id 11, 18, 21, 25 открыты, id 14 завершён. | `5 / 4 / 1` |
| После done | Завершить id 21 и прочитать сводку после сохранения через свежий ресурс. | `5 / 3 / 2` |

Критерий готовности для ученика: оба локальных прогона прошли, сводка в каждом случае совпала с таблицей, подсчёт в базе подтверждён. В коде видно, что метод читает одну строку и использует уже выданную Session без собственного commit и close. Ученик может объяснить, почему на пустой таблице получается одна строка с тремя нулями. Зафиксировать вывод проверки и одно предложение с объяснением в ответе на ручную карточку. При расхождении статусов подсказка возвращает к матрице участия и порядку столбцов из теории. При неверном ключе подсказка возвращает к пути сводки через сервис в HTTP. В будущем разборе автор проследит один запрос на иных данных и покажет, как распознавать ошибку по проверке, затем сверит существующую границу HTTP. Само решение остаётся в закрытом разборе.
