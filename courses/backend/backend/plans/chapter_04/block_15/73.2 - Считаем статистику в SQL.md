## 00. Вступление

Подвести от вопроса «какие заявки сейчас открыты?» к вопросу «сколько заявок в каждом состоянии?». Использовать один `LinkedNotes`.

1. **Точка старта**. Запрос по статусу возвращает подходящие задачи.
2. **Новый вопрос**. Как SQLite из одного набора строк получит сразу три числа?
3. **Результат**. Одна строка запроса даёт сводку с именами `all`, `open`, `done`.

Сначала станет виден вклад одной задачи. После этого можно объяснить, почему общий и условные счётчики дают разные числа.

## 01. Как одна строка попадает в счётчик

**Данные связного примера.** Реестр заявок на оборудование. Поле «Штук» есть у каждой заявки. Полка заполняется, когда её назначили. Состояния видны с начала примера.

| id | Заявка | Состояние | Штук | Полка |
| --- | --- | --- | --- | --- |
| 8 | Рулетка | Завершена | 1 | R2 |
| 9 | Маркеры | Открыта | 3 | NULL |
| 10 | Кабели | Завершена | 2 | R5 |

**CASE, условное значение строки.** Представить стол выдачи. Для списка заявок на два предмета и больше кладём номер талона в ячейку, при остальных оставляем её пустой. В SQL условие вычисляется для каждой строки. При совпадении CASE возвращает её id, иначе SQL NULL, то есть значения в этой ячейке нет. Из темы отбора вернуть точное различие: False соответствует открытой задаче, True завершённой, а отсутствие фильтра оставляет оба статуса. Условие в CASE вычисляет значение для строки, поэтому она остаётся доступной общему счётчику.

**Независимый код в том же реестре.** В демонстрации с `EquipmentRequest` показать полный SQLAlchemy CASE, исполняемый вместе с id в обычном SELECT по реестру. Условие `EquipmentRequest.quantity >= 2` и два результата (id, `else_=None`) дают пары `(8, None), (9, 9), (10, 10)` по порядку id. Объяснить пару «проверка, значение для истинного условия», переход `None` ⇄ SQL NULL на этой ячейке и почему заявка 8 всё ещё видна в первой колонке.

**COUNT, число заполненных ячеек.** На том же столе посчитать заполненные места в колонке талонов. В одном коротком полном SQL-запросе к реестру показать условный `COUNT(CASE WHEN quantity >= 2 THEN id ELSE NULL END)`, общий `COUNT(id)` и сопоставить 2 и 3. Так видно композицию CASE внутри COUNT. Смена пустой ветки на 0 даёт 3, потому что ноль тоже значение. Показать два условных столбца по статусам на заявке 9. Для открытых получается id 9, для завершённых NULL, а общий COUNT(id) учитывает 9. Затем ученик выбирает прогноз для №10. Только обратная связь QuizCard показывает NULL для открытых, 10 для завершённых и единицу в общем счёте.

**Учебный визуал вне 00.** Таблица показывает уже разобранные строки №8 и №9, общий id и оба условных столбца. Результат №10 оставлен вопросу с обратной связью после выбора. Имена и итоги полного исходного набора вводятся перед отдельным прогнозом при смене статуса №8.

**Опора и переход.** Краткая опора в конце раздела связывает «проверка строки → id или NULL → число заполненных ячеек». По одному COUNT понятно, какие строки он учитывает. Дальше важно прочитать, какому вопросу отвечает каждое из нескольких чисел.

## 02. Как прочитать итоги по именам

**Метка и одна агрегатная строка.** На столе выдачи пересчитываем талончики и вносим два числа в одну строку отчёта, каждое под своим заголовком. В запросе метка `.label(...)` называется как поле отчёта. Несколько агрегатов в одном SELECT без группировки сводят входные строки к одной строке, даже если таблица пуста. Разобрать чтение `execute(...).mappings().one()`: выполнение, доступ к результату как к отображению и ожидание ровно одной строки. Показать обращение `row["имя"]` и объяснить, как из знакомых ключей получается словарь. Источники для автора: [CASE и выражения SQLAlchemy 2.0.55](https://github.com/sqlalchemy/sqlalchemy/blob/rel_2_0_55/doc/build/core/sqlelement.rst), [строки результата и MappingResult](https://github.com/sqlalchemy/sqlalchemy/blob/rel_2_0_55/doc/build/core/connections.rst).

**Независимый код на тех же данных.** Полный SELECT SQLAlchemy считает назначенные полки через `func.count(EquipmentRequest.shelf_code).label("with_shelf")` и заявки через `func.count(EquipmentRequest.id).label("registered")`. Обе колонки уже есть в схеме. Здесь `with_shelf=2`, `registered=3`. Прочитать `registered` первым по ключу, хотя в SELECT раньше указан `with_shelf`. Для короткого прогноза поменять порядок выражений в SELECT, сохранив метки. После попытки показать, почему результат по именам совпал. Напомнить, что `scalars()` возвращает один элемент строки результата и полезен для прежнего `select(TaskRow)`. Здесь нужны все именованные колонки.

**Интерактив вне 00.** На исходных трёх заявках предложить перевести заявку 8 из завершённой в открытую. Ученик сначала выставляет прогноз id или NULL для обоих CASE на этой строке и три числа для подписанных итогов, затем подтверждает ответ. Обратная связь показывает перенос id 8 между двумя столбцами, постоянное значение общего счёта 3 и новые `open=2, done=1`. Ошибка с обменом групп видна по подписям и по перемещению id. Предусмотреть сброс, чтение состояния текстом и доступ с клавиатуры.

**Воспроизведение.** Теория использует один компактный подготовленный фрагмент для временной SQLite в памяти на всё объяснение. Его можно прогнать в Python окружения Planner с установленной SQLAlchemy. Создание схемы и три строки вводятся готовой обвязкой примера, без нового каталога, файла или процесса API. Автор объясняет, откуда берётся Session и какие из строк примера строят запрос. Полная открытая форма CASE относится к количеству предметов, условный COUNT показан целиком в SQL для того же вопроса, именованный SQLAlchemy-запрос считает готовые колонки. Практика требует перенести связь выражений в SQLAlchemy, составить два статусных условия и проверить их соответствие именам. Примеры не содержат метода Planner или SQLAlchemy-фрагмента с двумя статусными агрегатами.

**Опора и переход.** Метка указывает смысл числа, `mappings().one()` даёт одну строку, значения читаются по ключам. Прогноз с одной задачей из первой карточки поможет сверить смысл каждого ключа во второй.

## 03. Что мы будем делать в практике

В финале один короткий `LinkedNotes` из двух пунктов: «Проследим одну строку» и «Сверим именованные числа до HTTP». При необходимости одной фразой связать заметку первой карточки с именами второй.

### Старт практики

Ученик составляет три пробные строки Planner: две одноимённые с разным статусом и третью завершённую с другим названием. Номера выбирает сам и держит в заметке. Так на первом наборе `all=3, open=1, done=2`, а две одноимённые различаются по id и состоянию.

Открыть Python из `project`. Повторить по знакомой SQL-сборке создание временной SQLite в памяти (`create_engine("sqlite://")`), создание схемы `Base.metadata.create_all(engine)` и передачу `Session` в `SqlTaskRepository`. Подготовить три строки из своей заметки обычным `session.add(TaskRow(...))` и подтвердить запись. После сохранения метода повторить этот же старт в новом Python. В явном старте названы импорты, модель и имена созданных объектов. Ранее открытая консоль и данные предыдущей темы не требуются.

### Карточка 1. Проследим одну строку

Открытая опора «Как одна строка попадает в счётчик». Ученик выбирает завершённую из двух одноимённых задач, записывает id, два результата CASE и вклад в три итога. Затем вызывает знакомые выборки `repo.select(is_done=False)` и `repo.select(is_done=True)`. Сверяет объяснение с наличием выбранного id в каждой группе. Это наблюдение реального отбора по столбцу, из которого ученик сам выводит ожидаемые значения CASE. Во второй карточке он воссоздаёт те же строки по заметке.

Приватный разбор `tasks[].answer` ведёт от сравнения двух одноимённых строк к условным значениям и вкладу 1/0/1, объясняет обратный случай для открытой задачи. Номера 24 и 41 служат примером. Разбор сопоставляет прогноз с фактическими группами id из двух SQL-выборок до реализации агрегата.

### Карточка 2. Сверим именованные числа до HTTP

Открытые опоры «Как одна строка попадает в счётчик» и «Как прочитать итоги по именам». Ученик пишет `SqlTaskRepository.statistics()` в существующем `project/app/DBase/repositories.py`: один SELECT, три именованных COUNT, одна строка, словарь `all/open/done`. По заметке определяет, к какому имени относится каждый статус. Список задач для подсчёта в Python не загружается.

Из новой сессии Python создать учебную базу по разделу «Старт практики». После наполнения включить `engine.echo`, самостоятельно сравнить `repo.statistics()` на своих трёх строках с `all=3, open=1, done=2` и увидеть один SELECT. Затем очистить только эту учебную таблицу знакомым `repo.delete(id)` для своих трёх id, подтвердить изменения через `session.commit()` и повторить тот же вызов. Пустая таблица даёт ту же строку по форме и три нуля. Вывод по ключам различает перестановку статусов, 0 вместо NULL даёт лишний вклад. Связь `all → total` остаётся контрактом перехода. В открытой карточке остаётся ручной запуск в Python.

Приватный разбор `tasks[].answer` проводит три строки через оба условных значения, объясняет общий счёт, метки, чтение именованной строки и пустой случай. В существенных ошибках показывает перестановку групп, непустой ноль и потерю строк при общем фильтре. Фрагмент реализации доступен только в отдельном разборе карточки.

## Сверка P4

- Опоры покрывают обе остановки. Карточку 1 можно завершить без метода сводки и HTTP. Полученная заметка нужна, чтобы объяснить выбор двух предикатов и подписей в карточке 2. Первый прогон карточки 2 проверяет сам созданный метод.
- На SQLAlchemy 2.0.55 и SQLite 3.49.1 выполнены представительные запросы в памяти с данными обеих таблиц. В теории проверены пары CASE, COUNT с NULL и с нулём, перестановка статусного вклада и читаемые по ключам метки. В практике использована модель `TaskRow` из указанного среза v1. Проверены обе одноимённые строки, пустой набор, смешанная сводка, обмен счётчиков, дельты и ровно один SELECT на вызов пробного агрегата.

Это проверка контракта и репрезентативных данных. Авторизованная выдача v2 и фактическая передача в CLI относятся к последующим прогонам. Локальная сборка каталога уже до правки отклоняла несовпадение `content_version` с авторскими файлами. Идентификатор вычислен исходным алгоритмом из прежнего пути и совпал с паспортом.
- Существующий H1 сохраняет каталожное название. Название по паспорту указано отдельной строкой. Исторический `source_file`, ID и TSX-привязка сохранены. В исходнике YouTube-комментария не было.
