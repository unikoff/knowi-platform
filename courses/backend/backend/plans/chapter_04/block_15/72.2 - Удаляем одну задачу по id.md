Когда задача завершена и больше не нужна, мы хотим убрать из списка именно её. Будущая подача использует один `LinkedNotes` с тремя пунктами.

## 01. Как отметить одну строку к удалению

- Ввести строку ORM как объект Python, связанный с записью в таблице. У `session.get(Model, id)` первый аргумент задаёт, где искать, второй задаёт первичный ключ. Результат `None` означает, что по этому ключу строки нет. На месте объяснить `is None` как проверку именно отсутствующего объекта, а `Model | None` в аннотации как два возможных результата. `session.delete(row)` принимает найденный объект, поэтому поиск выполняется в той же Session, которой передают строку для удаления. Удаление `None` и передача числа вместо объекта не соответствуют этой форме вызова.
- Объяснить, зачем до вызова сохранить обычную карточку с данными выбранной строки. Она хранит значения без обращения к Session и доступна после её закрытия. Вернувшаяся карточка сообщает вызывающему коду, какую запись нашёл репозиторий. Успех сохранения определяет завершение транзакции. `Session.delete` помечает объект. `flush` отправляет SQL `DELETE` внутри текущей транзакции. При обычном выходе из `with session.begin():` область фиксирует изменения, при исключении откатывает их. Удаление может быть отправлено при flush до commit, поэтому проверяем итог новым ресурсом после завершения области. [Документация SQLAlchemy 2.0.55 о Session](https://github.com/sqlalchemy/sqlalchemy/blob/rel_2_0_55/doc/build/orm/session_basics.rst).
- **Полный независимый пример для Stage 3.** В каталоге броней `11` содержит «Проектор» с пометкой «вечер», `12` содержит «Зал» с пометкой «утро». Разместить в теории один полный готовый блок «Отмена брони» с начальной таблицей и наблюдениями. Код для этого блока сам поднимет отдельную SQLite в памяти, создаст две брони и сохранит их. В одном линейном сценарии с уже известной фабрикой открыть Session каталога, начать область записи до чтения и найти `BookingRow` с ключом `11`. Сохранить обычную карточку `(11, "Проектор", "вечер")`, передать найденный объект в `session.delete` и выйти из области. На выходе карточка читается, новая Session вернёт только бронь `12`. В повторной попытке по `11` поиск вернёт `None`, область не получит ни одной строки к удалению, свежий просмотр по-прежнему покажет `12`. Не оформлять пример методом репозитория Planner. Рядом с основным фрагментом объяснить роль готовых импорта, модели, временной таблицы и фабрики. Для желающих повторить весь блок обещать один файл `booking_delete_demo.py` в отдельной пустой учебной папке и одну команду `python booking_delete_demo.py` из этой папки своим Python с SQLAlchemy из окружения проекта. Обязательный путь проходит по видимой трассировке и интерактиву на странице, без копирования примера и сборки второго проекта.
- **Отдельный визуал.** Изобразить две строки и указатель на ключ `11`, затем область записи с развилкой «строка найдена» / «получили None». У найденной ветви показать обычную карточку, уход строки при фиксации и новую Session с `12`. У пустой ветви оставить таблицу в прежнем состоянии. Вопрос для чтения схемы: где мы ещё видим пометку «вечер» после удаления? Направляющая от обычной карточки к результату объясняет, почему эти данные доступны за пределами Session.
- **Опора для возврата.** Рядом с примером оставить короткое пояснение к поиску по ключу, к аргументу `delete` и к обычной карточке. Схему используем дальше, чтобы отличить найденную строку от успешного ответа.

## 02. Когда DELETE сообщает об успехе

- Продолжить на том же примере броней. Развести три наблюдения: хранилище может передать карточку или `None`, область записи может подтвердить изменение или прерваться, обработчик формирует HTTP-ответ. Для каталога показать отдельные ожидаемые итоги `11 → карточка → commit → 204, пустое тело` и `11 повторно → None → ошибка отсутствия → 404`. Это иллюстрация HTTP-контракта, код демонстрации работает с SQLite в одном процессе. Если до commit сломается запись, `204` не формируется. Ошибка отсутствия означает, что с указанным ключом уже нечего удалять. Карточка с прежними данными используется как внутренний результат операции.
- Перенос в Planner. Вернуться к прежнему `get` в репозитории. `self.session` даёт методу уже открытый ресурс для поиска, `task_from_row(row)` создаёт `Task` со всеми полями и отдельным списком tags. Проследить, где `PlannerService.delete_task` получает результат репозитория. В тестовом SQL-вызове `with self.write_scope():` открывает область той же Session до первого чтения и фиксирует изменение до успешного возврата управления HTTP-обработчику. Проверка `deleted is None` выражает прежний контракт файлового репозитория. Обработчик `/tasks/{task_id}` преобразует предметную ошибку в `404`, при успехе формирует пустой `204`. CLI с тем же сервисом сообщает «Задача не найдена.» для отсутствующего id.
- Перед первым запуском проверки пояснить два копируемых словаря. Строка начинается `DONE_TASK =` или `CONTROL_TASK =`, внутри фигурных скобок лежат подписанные поля. `id` и `priority` целые, `title` в кавычках, `is_done` принимает `True` или `False`, `tags` содержит список строк. Обе строки копируем целиком. `python -m pytest` запускает проверочный модуль, `-k ready` выбирает входные проверки по имени, `-v` показывает имя и исход каждой проверки, например `test_ready_restores_tasks PASSED`. Ученик читает результат готового прогона без настройки фабрики и подмены.
- **Интерактив и малая самостоятельная проба.** В новом состоянии каталога есть `12 «Зал» (утро)`, `16 «Экран» (вечер)` и `20 «Стойка» (день)`. Ученик выбирает `12` или `99`, до подтверждения прогнозирует, что получит хранилище, какой будет HTTP-статус и что останется в свежем просмотре. После подтверждения отдельное действие «Открыть свежий просмотр» показывает фактические id. Для `12` обратная связь показывает карточку, `204` и `[16, 20]`, объясняя, что удалён один объект с выбранным ключом и изменение подтверждено. Для `99` показывает `None`, `404` и неизменившийся набор, объясняя отсутствие объекта. Повтор `12` после первого удаления даёт `None` и `404` при тех же `[16, 20]`. Сброс восстанавливает исходные три брони. После неверного прогноза вернуться к развилке схемы, сбросить состояние и попробовать другой ключ. Интерактив показывает состояния, без сборки целевого Python-метода.
- **Опора для возврата.** Сравнить 204 и 404 по моменту формирования ответа и состоянию при независимом чтении. Следующий шаг переносит этот договор в уже существующий проект.

## 03. Что мы будем делать в практике

Формат по паспорту: проект. Цель карточки «Удаляем завершённую задачу» состоит в том, чтобы дописать одну операцию SQL в своём Planner и показать её результат на временных данных. Список для будущего `LinkedNotes` связывает собственные действия с наблюдением.

- **Подготовим знакомую задачу.** Перенесём две записи из вывода проверки завершения. Входная проверка найдёт прежние id, флаг завершённой цели и поля соседа в новой учебной базе. Опора уже знакома по свежему чтению после done.
- **Реализуем удаление.** Напишем тело нового метода в существующем SQL-репозитории. Проверка репозитория покажет прежние поля удалённой задачи или `None` для отсутствующего id. Опора: выбор строки и карточка из раздела 01.
- **Проверим ответ и соседа.** Запустим готовую проверку прежнего HTTP DELETE и CLI. Увидим пустой `204`, затем `404` для того же id, и сравним оставшуюся запись с исходной. Опора: транзакция и разбор ответа из разделов 01–02.

Входная проверка подтверждает, с какими данными мы начнём. Затем проверка репозитория показывает, какие данные получил сервис, а проверка интерфейсов подтверждает фиксацию удаления и сохранность соседа.

Модуль готовит новую временную SQLite на каждый сценарий и восстанавливает две строки с переданными `id`, `title`, `priority`, `is_done` и `tags`. Внутри модуля полностью поставлены создание схемы, фабрика Session, подмена `get_planner` с `get_db` и `write_scope=session.begin` и восстановление настроек. Для CLI используется готовый `sql_service_context` в `app/main.py` из темы создания задачи. Он передаёт `write_scope=session.begin` сервису на той же короткой Session. В проверке `ready` отдельный прогон вызывает прежний `add_task` через этот контекст на ещё одной временной базе. Новая Session после закрытия контекста подтверждает, что запись зафиксирована. При сбое проверка предлагает восстановить выданную версию контекста из темы «Создаём задачу и получаем её id из SQLite». Зависимости взяты из прежнего `requirements-dev.txt`. Тело нового метода репозитория поставка оставляет ученику.

Из `project/` в своём окружении запускаем `python -m pytest -v tests/test_lesson_task_delete.py -k ready`. Проверка сверяет наличие обоих словарей, разные положительные id и флаг завершения цели. Затем новая Session читает обе восстановленные строки и сравнивает все предметные поля с входом. Группа `ready` проходит ещё до реализации удаления.

Для прямой проверки репозитория каждый существующий id передают методу на отдельном экземпляре набора. Для случая отсутствия готовый модуль выбирает положительный id вне пары и создаёт ещё один экземпляр. HTTP и контролируемый отказ получают две свежие базы из тех же словарей. Цель берётся из `DONE_TASK["id"]`. Перед действием снимаются все поля обеих строк, включая `title_normalized`, чтобы после запроса сравнить соседа из `CONTROL_TASK`. Для каждого HTTP-запроса открывается отдельная Session, контрольные чтения открываются после завершения соответствующей области записи.

### Условие, видимое до разбора

В проверке завершения мы сохранили данные двух задач. Подключим готовую область записи, скопируем файл проверки и перенесём туда два словаря. На временной базе они дадут нам ту же завершённую задачу и её соседа с прежними id. После успешной входной проверки откроем `project/app/DBase/repositories.py` и сами добавим `delete` в `SqlTaskRepository`.

Для найденного id сервису понадобится прежняя задача со всеми её данными. Для отсутствующего id он должен получить `None`. Готовая проверка репозитория по очереди выбирает разные id в отдельных экземплярах базы и читает данные результата после закрытия Session. Затем проверим знакомые HTTP DELETE, GET и CLI для уже удалённого id. Сравним поля соседа до и после и посмотрим, что прочитает новый ресурс при ошибке перед фиксацией.

### Техническое задание и локальная готовность

| Критерий готового решения | Как видим его локально |
| --- | --- |
| Метод `SqlTaskRepository.delete` принимает `task_id: int`, возвращает `Task` или `None`, использует существующую Session и выбирает строку по переданному первичному ключу. | В группе `repository` при выборе id из `DONE_TASK` остаётся запись `CONTROL_TASK`, при выборе id из `CONTROL_TASK` остаётся запись `DONE_TASK`. Вызовы используют отдельные экземпляры исходной пары. Самопроверка в методе подтверждает использование аргумента `task_id`. |
| При наличии строки результатом является обычная `Task` с прежними `id`, `title`, `priority`, `is_done`, `tags`. Преобразование выполняется до `Session.delete` по правилам раздела 01. Репозиторий передаёт найденный ORM-объект в `Session.delete`. Фиксацией, откатом и закрытием управляет готовая обвязка. | `python -m pytest -v tests/test_lesson_task_delete.py -k repository` сверяет тип и все поля после закрытия Session, а затем читает состояние в новой. Порядок преобразования и границы метода видны при самопроверке исходника. |
| Для id вне исходной пары репозиторий возвращает `None`, обе строки этого сценария сохраняются. | Та же группа `repository` отличает `None` от `False` и сверяет обе строки в новой Session. |
| Успешный `DELETE /tasks/{task_id}` для `DONE_TASK["id"]` даёт 204 и пустое тело (`b""`) после commit. Новый SQL-ресурс подтверждает отсутствие цели. Последующий GET и повторный DELETE по тому же id дают 404. Сервис использует прежнюю проверку `deleted is None`. | Группа `interfaces` выполняет запросы и вызов существующего CLI `delete`. Для того же удалённого id CLI выдаёт «Задача не найдена.». Все поля соседа с id из `CONTROL_TASK`, включая tags и `title_normalized`, совпадают со снимком до операции. |
| При контролируемой ошибке до commit успех HTTP отсутствует, цель остаётся в базе. | Готовая проверка группы `interfaces` поднимает ошибку после flush внутри области записи на отдельной SQLite. Тестовый клиент получает HTTP-ответ даже при исключении из приложения. Статус отличается от 204, новая Session видит обе исходные строки. Ученик читает результат готовой проверки знакомого rollback. |

Итоговый локальный запуск из `project/` выполняем командой `python -m pytest -v tests/test_lesson_task_delete.py`. Готовность означает, что прошли `ready`, `repository` и `interfaces`, а ученик может показать в своём методе, где формируется обычная `Task`, и объяснить HTTP 404 при повторе. Внутренние имена временных переменных свободны. Если падает `ready`, сверить два словаря с выводом проверки завершения и прочитать, отмечен ли сбой подготовки CLI. Если падает `repository`, вернуться к развилке в 01. Если падает `interfaces`, убедиться, что проверка репозитория проходит, затем сверить статус, тело ответа или данные свежего чтения по имени упавшей проверки.

**Подсказка.** Вернуться к схеме из 01 и ответить, что получит вызывающий код на каждой ветви поиска. Если поля верны, а повторный запрос отвечает успехом, вернуться к различию `None` и пустого HTTP-ответа в 02. Подсказка отсылает к знакомому механизму.

**Будущий разбор после попытки.** Сначала показать выбор по id и отдельно развернуть отсутствующую ветвь. На найденной ветви объяснить раннее сохранение обычной карточки и отметку её строки. После этого связать наблюдения локальной проверки с выходом из области записи и сравнить повторный запрос с первым. Для разбора использовать тот же готовый запуск и область записи.
