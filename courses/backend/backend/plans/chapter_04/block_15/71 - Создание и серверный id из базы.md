## 00. Вступление

Мы уже можем найти задачу по номеру в тестовой SQLite. Теперь хотим получить такой номер при добавлении новой задачи.

Одна группа `LinkedNotes` в точном порядке.

1. **Точка старта**. В тестовой базе читаем задачи по id. Обычные API и CLI работают с одним JSON.
2. **Новый вопрос**. Как вставить новую строку и получить номер, по которому её найдёт другое чтение?
3. **Результат**. SQLite назначает id. После успешной записи находим задачу по этому id в новой Session.

Проследим, в какой момент SQLite выдаёт номер и в какой момент другое чтение видит строку. Затем проверим оба события в Planner.

## 01. Как новая строка получает id

- Начать с привычного `POST /tasks`. В запросе обязательны `title` и `priority`. Полученная `Task` имеет `id`, а HTTP отдаёт четыре прежних публичных поля. Показать тот же сервис для SQL, точку добавления `create` в существующий класс и готовое преобразование `task_from_row`. Назвать ORM-строку объектом, который SQLAlchemy связывает со строкой таблицы, и объяснить разницу между этим объектом и обычной `Task`.
- Сопоставить знакомый импорт с новой вставкой. При импорте старый номер нужен для сохранения адреса записи. Для новой строки `INTEGER PRIMARY KEY` поручает SQLite выбрать свободный номер, когда ключ пропущен. Ручной `max(id) + 1` делает выбор номера обязанностью приложения. Отдельное чтение максимума само по себе не резервирует номер. `Session.add(obj)` принимает объект в работу, `flush()` отправляет `INSERT` и даёт прочитать `obj.id` в той же Session. До `flush` значение в новом объекте ещё отсутствует. [Ключ SQLite](https://www.sqlite.org/autoinc.html), [получение ключа ORM](https://docs.sqlalchemy.org/en/20/orm/persistence_techniques.html#case-4-primary-key-returning-or-equivalent-is-supported).
- Разобрать данные до сборки строки. В готовой области сервис вызывает прежние `validate_title`, `validate_priority` и `validate_tags` до попытки записи. На понятных значениях объяснить, откуда берутся значения. Например, строка `"  Коробка  "` превращается в `"Коробка"` после `strip()`, `"Коробка".lower()` даёт отдельное значение `"коробка"`, исходное отображаемое название сохраняет регистр. У новой задачи `False` означает «открыта». Для отсутствующих меток используется новый пустой список, `list(метки)` создаёт отдельный список, и `task_from_row` тоже забирает копию. Модель `Task` требует полученный положительный id. Показать наблюдение на списке `["зал"]`, когда добавление `"вход"` в копию оставляет исходный список прежним. Пояснить именованные аргументы конструктора строки, запись `tags=None` и способ проверить отсутствие значения до копирования. Ученик переносит эти правила в `create`, пользуясь знакомыми валидаторами через готовый сервис.
- В первой части полного примера дать начальную строку `4 / Футляр / 1` и новую карточку «Чехол» с остатком `2`. Попросить предсказать значение id сразу после создания объекта и после `flush`. На этом наборе результаты `None` и `5`. При затруднении вернуться к моменту отправки `INSERT`. Следующий вопрос уже о второй Session.

## 02. Когда другой читатель увидит запись

- Назвать область записи участком, который завершается подтверждением целиком. Готовый сервис получает `write_scope` как функцию, вызываемую при входе в `with`. Тестовый provider и готовый `sql_service_context` передают связанный метод `session.begin` без скобок. Это функция, которая уже знает, с какой Session работать. При передаче она ещё не вызвана. `with self.write_scope()` вызывает её для конкретной операции. Нормальный выход подтверждает изменения, исключение до подтверждения отменяет их. В HTTP Session закрывает зависимость запроса, а в прямом вызове её открывает и закрывает `sql_service_context`. В обоих случаях репозиторий и область записи получают одну Session. `nullcontext` даёт той же форме вызова выполняться на прежнем JSON-пути без SQL-транзакции. Развести `flush`, `commit` и `close`. Даже если результат вычислен внутри `with`, сервис вернёт его обработчику после успешного выхода. В обычном `create` тело репозитория работает с уже переданной Session. [Область транзакции и Session](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#framing-out-a-begin-commit-rollback-block).
- **Полный независимый пример для Stage 3.** В теории дать один готовый файл `stock_insert_demo.py` целиком. В нём есть импорты, маленькая модель `StockRow` (`INTEGER PRIMARY KEY`, название, остаток), создание одноразовой файловой SQLite в отдельном временном каталоге, фабрика Session и начальная строка `4 / Футляр / 1`, уже сохранённая. Файл получает всё для запуска из этого блока. В терминале из папки файла команда `python stock_insert_demo.py` на прежнем окружении показывает два хода. Ученик копирует один файл, запускает одну команду. Без ручной подготовки схемы, импорта, пакета и сервера. Файл освобождает ресурсы и удаляет свой временный каталог. Автор Stage 3 реализует и запускает этот пример до выдачи.
  - **Успех.** Открыть Session для записи и её транзакцию. Вставить карточку «Чехол», остаток `2`, ключ не передавать. Разобрать добавление объекта, `flush` и чтение `row.id = 5` на этих данных. Собрать обычный кортеж `(5, "Чехол", 2)` внутри области. Короткое чтение другим соединением до `commit` ищет `5` и получает `None`. Оно завершается до подтверждения. После выхода из транзакции и закрытия Session записи новая Session читает карточку `5` и неизменную `4`. Объяснить аргументы `get(StockRow, id)`, смысл `None` и почему в проверке используются тот же файл и новый ресурс.
  - **Отмена.** В том же примере добавить «Крепление», остаток `1`, запомнить полученный при `flush` id и вызвать контролируемое исключение до `commit`. Снаружи перехватывается только эта демонстрационная ошибка. После выхода из контекстов новое чтение по запомненному id возвращает `None`, строки `4` и `5` остаются. Показать, что выведенный ранее номер не равен сохранённой записи. [Видимость между соединениями SQLite](https://www.sqlite.org/isolation.html).
- **Отдельный учебный визуал.** Два ряда времени на данных инвентаря. Верхний ряд ведёт от `add` через `flush` (объект получает `5`) к `commit`, нижний показывает два независимых чтения одного файла по `5`. До подтверждения пусто, после подтверждения видна карточка «Чехол», `2`. От развилки до `commit` провести ветвь «исключение → откат», в ней новое чтение по id пусто. Подпись разделяет уже видимый внутри записи номер и состояние, доступное другому читателю.
- **Интерактив и управляемая проба.** Дать независимый журнал для склада с одной сохранённой карточкой `11 / Ящик / 3`. Новая карточка «Крышка», `1`, получила `12` при `flush`. Ученик предсказывает результат `get(12)` и выбирает когда начать второе чтение. Варианты идут сразу после `flush` и после `commit`. Экран рядом показывает `id=12` у автора записи и `None` либо `12 / Крышка / 1` у читателя. Обратная связь объясняет, какое действие сделало запись видимой, и предлагает объяснить, что увидит новая Session при отмене между этими событиями. Затем ученик сверяет прогноз с двумя ходами готового файла. Интерактив проверяет видимость и момент чтения, целевой метод Planner остаётся за учеником.
- **Перенос в Planner.** Найденная `Task` с совпадающим номером подтверждает предметные поля. Чтение соответствующего `TaskRow` нужно, чтобы отдельно увидеть техническое `title_normalized`. До практики разобрать, как в готовом отчёте сопоставить id ответа, id из нового чтения и снимок старой строки, где видны ошибочный статус или пустой результат. Команда проверки и расшифровка её вывода публикуются рядом с условием.

Копируем фрагменты только в указанные места своего рабочего проекта. Если файл проверки с таким именем уже занят, публичная инструкция предлагает `check_sql_create_local.py` и соответствующую команду. После применения сервис и сборка принимают `write_scope`, явный `sql_service_context` передаёт область записи из своей Session, прежний JSON-путь доступен, SQL `list/get` остаются в том же классе. Поставка использует файл репозитория как есть. Тело `SqlTaskRepository.create` целиком пишет ученик, а проверка только вызывает этот метод через сервис. Уже имеющиеся `TaskRow`, `task_from_row`, схема, импортёр, маршруты и CLI переиспользуются. Не нужно строить второй Planner или писать собственный provider.

### Поведение готовой проверки

- Каждый запуск выделяет новый временный каталог с префиксом `planner-sql-create-`. Файлы `planner.sqlite3` и синтетический `tasks.json` создаются только там. Проверка явно поднимает имеющуюся схему для этой SQLite, даёт проверенному набору исходных данных одну строку с id `40` и выводит её снимок до записи. Она подключает существующий `app.api` через временный override `get_planner`, фабрику Session для этого SQLite и `build_service(..., write_scope=session.begin)`. По завершении прогона восстанавливает override и состояние приложения. После закрытия всех Session и освобождения Engine готовая проверка очищает выделенный для неё каталог. Системе не нужен работающий сервер. SQL-проверка не открывает и не перезаписывает базу импорта или рабочий JSON.
- Прямая проверка с метками выполняется внутри `with sql_service_context(session_factory) as planner`. `session_factory` та же, что у тестового HTTP-provider. `planner.add_task` начинает область записи до любого обращения этой Session к базе. После выхода из контекста отчёт открывает новую Session и сверяет полученный id и строку. Отчёт раздельно показывает публичный ответ, `Task` из независимого SQL `get` на новой Session после окончания запроса/сервиса, служебное поле прочитанной строки и снимок соседа до и после. Для отказа отдельный готовый прогон через тот же SQL-сервис поднимает контрольное исключение после выполнения операции в `write_scope`, до нормального выхода из транзакции. Проверка ловит только это исключение, затем сверяет прежние строки новой Session и отсутствие вставленной записи. Прежняя проверка входа показывает 422 для POST без `priority` и совпадение SQL-снимка до и после. Для регрессии без SQL override готовый POST пишет в изолированный JSON, а привычный CLI-путь через прежнюю сборку на том же тестовом JSON читает результат. Синтетический JSON не подменяет рабочий файл.
- После успешного прогона отчёт печатает подтверждённые id, поля задачи с метками и снимок соседа. Ученик отмечает успешную сверку. Повторный запуск работает на новом наборе тестовых файлов. Передача в практику PUT опирается на код и форму данных проверенного сценария. При ошибке отчёт указывает проблемную стадию и помогает найти расхождение между ответом, записью и новой Session. Автор проверит копирование публичной поставки на состоянии B14. До реализации должна быть понятная остановка из-за отсутствующего SQL `create`. После реализации должны быть видны все результаты.

## 03. Что мы будем делать в практике

Ручная практика в существующем проекте. Исходник берём из своей работы после импорта. Сначала берём готовые фрагменты из «Подготовки Planner», затем дополняем только SQL-создание и проверяем результат в созданном для прогона файле.

Для Stage 3 здесь один непустой `LinkedNotes` с тремя связанными пунктами.

1. **Подключим область записи.** Скопируем готовые фрагменты в указанные части Planner. После подготовки видно, что `build_service` передаёт `write_scope` реальному сервису и что тестовый `sql_service_context` берёт эту область у открытой им Session. Это даёт тестовому добавлению границу транзакции, когда мы допишем метод. Если неясно, кто завершает запись, возвращаемся к разделу «Когда другой читатель увидит запись».
2. **Создадим строку.** В существующем репозитории сами напишем SQL-метод `create`. Готовый вызов покажет id, который SQLite назначила новой задаче. Если id ещё не появился, возвращаемся к разделу «Как новая строка получает id».
3. **Перечитаем после записи.** Запустим готовую проверку и сверим id, содержимое задачи и строку, которая уже лежала в таблице. Зафиксируем результат проверки и форму задачи с метками для практики про PUT. При расхождении вернёмся к линии `flush` и `commit`.

Номер из ответа приводит к точно той же задаче в новом чтении. Готовый метод позволит подготовить такую же тестовую задачу для изменения по её собственному id.

### Спецификация одной карточки для автора практики

**Контекст и условие.** В действующем Planner запрос на добавление уже работает через JSON. На тестовой SQLite теперь хотим создать задачу тем же сервисом. В условии названы исходный `app/DBase/repositories.py`, класс `SqlTaskRepository`, готовые фрагменты и команда проверки. Ученик применяет опубликованную подготовку, сам пишет только `create` и вручную сверяет результаты отчёта. В условии перечислены POST и прямой вызов с метками через готовый `sql_service_context`, проверка нового чтения и соседа, отмена и штатный JSON. Из 01 берёт смысл полей, форм вызова и преобразования, из 02 понимает результат из нового чтения и область записи. Вне целевого метода требуются только копирование указанной поставки и запуск проверки. Если свой вход расходится по схеме, URL или расположению репозитория, инструкция помогает найти фактический аналог в собственном результате импорта и сохранить единственный класс.

**ТЗ готового решения.** `create(self, title, priority, tags=None)` работает через переданную Session, принимает проверенные сервисом данные, формирует `TaskRow` с исходным `False`, собственным списком меток и `title_normalized` через `lower()` от уже очищенного заголовка. id в конструктор не передаётся и не вычисляется приложением. Результат есть обычная `Task` с настоящим id SQLite, подготовленная до завершения области записи с переиспользованием `task_from_row`. `flush` относится к репозиторию. Подтверждение и отмена принадлежат подготовленному сервису. Session закрывает её владелец. После успешного запроса действует старый формат HTTP. HTTP-схему, `list/get` и штатное подключение требуется сохранить.

**Локальная приёмка.** Готовый запуск показывает результаты всех случаев для сверки. Ученик сравнивает вывод и свой метод с открытыми критериями.

| Случай | Наблюдение |
| --- | --- |
| Обычный POST `{"title": "  Купить ЧАЙ  ", "priority": 3}` рядом со строкой `40 / Купить ЧАЙ / 2 / True / ["архив"] / купить чай` | 201 с четырьмя полями, id положительный и отличается от `40`, видимое название `Купить ЧАЙ`, приоритет `3`, `is_done=false`. Новая Session находит именно этот id, `tags=[]` и `title_normalized="купить чай"`. Исходная строка со всеми полями прежняя, одинаковое название допустимо. |
| `add_task` через готовый `sql_service_context` с названием `Оплатить СВЕТ`, приоритетом `5` и `tags=["дом", "счёт"]` | Возвращает `Task`, другой положительный id совпадает с новым `get`. Чтение после закрытия контекста подтверждает название `Оплатить СВЕТ`, приоритет `5`, обе метки в том же порядке, `is_done=False` и `title_normalized="оплатить свет"`. Отчёт показывает оба id текущей проверки. |
| Контрольный отказ после `flush` внутри области записи | Независимое чтение показывает отсутствие строки этого вызова и совпадение прежних снимков. Ученик объясняет, почему присвоенный объекту id сам по себе не доказывает сохранения. |
| Прежний публичный договор и JSON-путь | POST только с `title` на тестовой SQL-сборке отвечает 422. Снимок SQLite до и после совпадает. После снятия SQL override обычный POST создаёт задачу в тестовом JSON, CLI читает её по тому же id. |

Кодовая самопроверка отличает назначение SQLite от `max(id) + 1`, который на одном наборе может вернуть то же число. Ученик сверяет, что ключ не передаётся в строку и отдельного запроса для вычисления id нет. Конкретное значение нового id в проекте не фиксируем. Отчёт не требует ручного SQL и не зависит от следующего занятия.

**Подсказка и разбор.** Адресная подсказка возвращает к наблюдению с «Чехлом» и вопросу о том, когда объект получает id и когда новую строку увидит другой читатель. Она не содержит шаблона целевого метода. После попытки Stage 3 даст пошаговый разбор на инвентаре с другими данными, проведёт от входных полей к вставке, затем через наблюдения в первой и новой Session к выводу о `commit`. Разбор показывает причинные проверки, код решения Planner остаётся самостоятельным.
