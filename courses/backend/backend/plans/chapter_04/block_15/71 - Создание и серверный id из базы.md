## 00. Вступление

В Planner уже можно найти задачу в отдельной SQLite. Теперь по одному номеру проверим, что приложение сразу сохранило новую строку и позже обновило именно её.

1. **Точка старта:** SQL-репозиторий уже находит строку задачи по id.
2. **Новый вопрос:** как сохранить изменение так, чтобы другой читатель увидел нужную строку?
3. **Результат:** номер из POST совпадёт с номером свежего чтения и с номером строки после PUT.

Подтверждённое сохранение наблюдаем по данным. Для этого сначала собираем путь одной операции, затем проверяем обе версии.

## 01. Когда можно сказать «сохранено»

В журнале выдачи `trace_scope` с `contextmanager` печатает вход и выход. `run_change(action, open_write)` запускает операцию внутри `with`, поэтому зовущий код получает результат после завершения области. Штатная файловая сборка использует `nullcontext`. PUT в Planner охватывает одной областью и первый поиск, и изменение найденной записи.

## 02. Одна Session для изменения и транзакции

Для воспроизводимого входа показать компактную подготовку: модель LoanRow, таблица во временном файле SQLite и сохранённая запись проектора с id 8. Блоки 01–04 идут по порядку в одном сеансе Python с SQLAlchemy 2.x. На проекторе показать изменение примечания. В `run_change` передаётся связанный метод `writer.begin` той же Session, через которую ищется и меняется строка. Область открывается при вызове метода внутри сервиса до первого SQL. В HTTP-подмене из темы «Ресурс на один запрос» `get_db` владеет ресурсом, `get_planner` собирает с открытой Session репозиторий и направляет её `begin` в сервис. `sql_service_context` соединяет те же роли вне запроса. Подмена сохраняется для проверок записи и последующего PATCH.

## 03. Когда появляется id и что видит читатель

В учебной таблице есть проектор с id 8. Создаём выдачу «Стойка» на 3 дня с примечанием «склад А» и вычисляем 72 часа. `register_loan` использует `add/flush` и возвращает номер и название для квитанции. С помощью `run_change` выполняем два прогона. Первый использует `nullcontext`: квитанция получена, Session закрывается без commit, свежее чтение по номеру печатает «выдача не найдена». Второй передаёт `begin` этой же Session: commit выполнен до квитанции, новое чтение показывает `9 / Стойка / 3 / 72 / склад А`. Сравнить обе последовательности на схеме. В Planner `task_from_row` собирает `Task` после flush, а проверка сохранения использует SQL `get` в отдельной Session.

## 04. Что сохраняется при замене

Продлеваем сохранённую выдачу по фактическому номеру с 3 до 5 дней. Показать новое чтение по тому же номеру после commit: видны 120 часов, прежние номер и примечание. Затем освободить соединения и удалить временную папку. В Planner PUT использует прежние id и tags, берёт новые публичные поля из тела запроса и пересчитывает `title_normalized`. Выдача 12 «Удлинитель» остаётся отдельным интерактивным прогнозом: читатель до завершения видит 2 дня, после commit видны 6 дней, после отката 2 дня. Исход раскрывается после ответа.

## 05. Что мы будем делать в практике

В `LinkedNotes` показать три результата: готова область записи на той же Session, созданная задача найдена через свежий ресурс, после PUT сверены цель и сосед. Путь временной SQLite сохраняется на весь прогон, id берётся из собственного POST. Штатная сборка использует JSON.

### Карточка 1. Подключаем транзакцию записи

Ученик добавляет `write_scope` в `PlannerService`, охватывает прежние `add_task` и `replace_task` с первого обращения к репозиторию, проводит область через `build_service` и подключает её в `sql_service_context`. Вложенная проверка: тесты прежних веток сервиса, GET по известному id на временной базе, область на той же Session в локальном контексте и в HTTP-подмене. Для контрольного GET использовать строку с отличимыми id, статусом и метками. В разборе отличить работающий GET от готовности записи и связать `get_db`, репозиторий и `write_scope` по ролям.

### Карточка 2. Создаём задачу с номером от SQLite

Ученик пишет `create(self, title, priority)`, возвращает `Task` с id SQLite после flush. Вложенная проверка: получить POST 201 через учебную подмену, записать фактический id и публичные поля, открыть свежую Session на том же файле и найти именно этот id с пустыми tags. Разобрать случай, когда номер был в ответе, но новая Session строку не нашла. Работающий GET и выполненный INSERT сами по себе не доказали commit.

### Карточка 3. Заменяем поля задачи по её номеру

Ученик пишет `replace(self, task)`, ищет строку по `task.id`, меняет публичные поля и вычисляет `title_normalized`. Вложенная проверка: в учебной SQLite добавить созданной задаче непустые tags через знакомую ORM-запись и подтвердить её. До PUT снять полный снимок цели и соседней строки с тем же исходным заголовком. Выполнить PUT по id из POST и перечитать обе строки через новую Session. Сверить id, заголовок, приоритет, статус, tags, поисковую копию и набор ключей. В разборе проследить, почему HTTP 200 не выявляет старый `title_normalized` и как сравнение обнаруживает запись в соседа.
