## 00. Вступление

В Planner уже можно найти задачу в отдельной SQLite. Теперь по одному номеру проверим, что приложение сразу сохранило новую строку и позже обновило именно её.

1. **Точка старта:** SQL-репозиторий уже находит строку задачи по id.
2. **Новый вопрос:** как сохранить изменение так, чтобы другой читатель увидел нужную строку?
3. **Результат:** номер из POST совпадёт с номером свежего чтения и с номером строки после PUT.

Подтверждённое сохранение наблюдаем по данным. Для этого сначала собираем путь одной операции, затем проверяем обе версии.

## 01. Кто открывает и подтверждает запись

Объяснить различие владения ресурсом и завершения операции. В независимом примере «журнал выдачи» передать функцию `open_scope`, печатающую «вход» и «выход» через `contextmanager`. Короткий вызов с `with make_scope(): return action()` показывает, что сначала идёт выход, затем результат у вызывающего. Для отсутствующей области показать `nullcontext` на том же непишущем действии. Дать форму передачи связанного метода без скобок на независимой фабрике `loan_sessions`: фабрика открывает Session, репозиторий и область `session.begin` получают один объект. Внутри области до первого SQL проверить, что in_transaction() возвращает True на этой Session. Срок жизни транзакции отличается от срока жизни Session. Показать связь с готовым `get_db` и примером SQL-подмены в существующих тестах 70.1.

Перенос в Planner. Ученик меняет ctor и две операции в `app/service.py`. В `app/main.py` передаёт выбранную область через `build_service` и расширяет уже существующий `sql_service_context`. С чтения для PUT начинается та же область, поэтому прежние ветки `replace_task` остаются внутри неё. Подготовка отдельной базы использует знакомый адрес, схему и явный импорт. Дать короткий независимый фрагмент выбора пути в `tempfile.mkdtemp` и открытия фабрики на указанном файле. На него опираются свои команды ученика из корня Planner. Первый процесс Python создаёт базу, при новом открытии этот шаг пропускается. Ресурсы закрываются, файл живёт до финальной сверки.

## 02. Когда появляется id и что видит новый читатель

Независимый малый вход реестра оборудования: выдача 8 «Проектор», 2 дня, «проверить пульт». Новая `LoanRow` «Стойка», 3 дня, «склад А», без id. Короткий фрагмент `writer.add(loan)`, `print(loan.id)`, `writer.flush()`, `print(loan.id)`. Вывод `None` → `9` на этих данных. Вставка отдаёт ключ SQLite, а при импорте ключ уже известен. `TaskRow` в Planner содержит публичные поля, отдельный пустой список tags и `title_normalized` из очищенного title через Python `lower()`. После flush готовый `task_from_row` собирает `Task`.

Рядом с объяснением прочитать по `reader.get(LoanRow, loan_id)` внутри новой `with loan_sessions() as reader`. Перед commit виден `None`, после commit видны `9 / Стойка / 3 дня / склад А`. При исключении между flush и commit следующий читатель вновь получает `None`. Код открытого примера работает с выдачей, а ученик переносит механизм на `SqlTaskRepository(session).get` и ключ из POST. Визуал показывает время появления id и момент видимости строки. Ученику доступны фрагменты и ожидаемые наблюдения на странице, без подготовки отдельного файла примера.

## 03. Как заменить одну строку и проверить результат

В том же реестре открыть выдачу по выданному id и изменить срок с 3 до 5. Короткий фрагмент `writer.get(LoanRow, loan_id)` и присваивание `days` при найденной строке. Свежий читатель вернёт 5 дней с прежними id и примечанием. По отсутствующему id чтение даст `None`, запись пропускается. Для Planner источники: id и tags из прежней строки, title/priority/is_done из PUT, `title_normalized` от нового title. Показать на «Кабель» → «Кабель USB», как верный HTTP 200 скрывает старую поисковую копию. Схема отделяет публичный ответ от полного снимка; сверяются цель, сосед и набор id.

**Интерактив после объяснения.** Выдача 12 «Удлинитель» на 2 дня с примечанием «вернуть в зал». Писатель меняет срок на 6 и делает flush. Ученик выбирает commit или отмену, затем прогнозирует результат двух свежих чтений. До выбора ответа видны вход и шаг писателя. После ответа показать первую строку с 2 днями и вторую с 6 после commit либо 2 после rollback. Примечание сохраняется. В пояснении связать результат с тем, успела ли запись подтвердиться.

## 04. Что мы будем делать в практике

В `LinkedNotes` «Настроим запись в Planner», «Создадим и перечитаем по id», «Заменим ту же строку и сверим снимки». Для всех карточек путь сохраняется в заметке, а после POST записывается фактический id. Перед запуском после правки модулей открыть свежий Python из корня Planner и повторить собственные команды подключения к прежнему файлу. Init и импорт выполняются только один раз. Прежний JSON остаётся штатным. Временное чтение и HTTP-подмена живут только в проверочном процессе.

### Карточка 1. Сервис завершает область записи

В `app/service.py` ученик добавляет совместимый необязательный аргумент `write_scope` с `nullcontext` по умолчанию и охватывает прежние `add_task` и `replace_task`, включая первый поиск PUT. Локально `python -m pytest -q tests/test_services.py` проверяет прежние ветки. В Python с `MemoryStorage` и собственным контекстом из §01 ученик видит «вход / выход» до печати результата для обеих операций. Отдельный разбор показывает на «Тестовая лампа» и последующем PUT порядок входа и выхода, код изменения только трёх методов и как отсутствие области сразу заметно по трассе.

### Карточка 2. Сборка использует Session одного файла

Ученик в `app/main.py` передаёт область через `build_service` и связывает `session.begin` с той же Session в `sql_service_context`. В проверочном Python выделяет временную папку, выбирает `planner.sqlite3`, строит Engine и фабрику, создаёт исходную схему и через известный `import_snapshot` переносит одну учебную JSON-строку `40 / Купить ЧАЙ / 2 / True / ["архив"]`. Хранит путь. Контроль: внутри переданной области in_transaction() возвращает True ещё до первого SQL. `sql_service_context` возвращает задачу 40, а локальный `TestClient` с собственной временной подменой из знакомого шаблона `tests/test_sql_provider.py` даёт GET 200. В подмене ученик связывает фабрику в `app.state` и передаёт `db.begin` как callable. Отдельный разбор показывает обе сборки, точную последовательность init, импорт, GET и симптом другого файла или другой Session.

### Карточка 3. Новый id из POST

Ученик пишет `create(self, title, priority)` в `app/DBase/repositories.py`. После правки запускает новый Python, открывает тот же файл и временный SQL-клиент без повтора init/import. Через `client.post("/tasks", json=...)` отправляет title «  Купить ЧАЙ  » и priority 3. Локально 201, новый положительный id, отличный от 40, публичные поля «Купить ЧАЙ», 3, False. Записывает ответ. Разбор на этом входе показывает новую строку с пустыми tags, ключ после flush, Task и роль commit. Ручной максимум может совпасть с фактическим числом, поэтому проверяем и способ в коде.

### Карточка 4. Самостоятельное свежее чтение

После POST в том же проверочном Python ученик открывает новую отдельную Session через свою фабрику и вызывает знакомый `SqlTaskRepository.get` с записанным id. Локально возвращается та же `Task` с пустыми tags. Ключ 40 отличается приоритетом, статусом и метками. Разбор на данных POST показывает код вызова, момент закрытия, расхождение по 40 и проверку причины при `None` для верного id.

### Карточка 5. Адресный PUT

До PUT ученик открывает короткую область на записанном файле, находит ORM-строку по записанному id, добавляет непустые метки `["дом","вход"]` и сохраняет. Из отдельной Session записывает шесть колонок цели, шесть колонок соседа и набор id. Пишет `replace(self, task)` в существующем классе. После правки открывает свежий Python на том же пути и посылает PUT по id из POST: title «  Оплатить СВЕТ  », priority 5, is_done true. Локально 200, тот же ключ, «Оплатить СВЕТ», 5, True. Разбор показывает создание входного снимка и полный метод, отличает id из адреса от выбора по заголовку, объясняет None, оставшиеся id и tags и причину пересчитать lower.

### Карточка 6. Доказательство по свежим снимкам

Ученик сам читает обе `TaskRow` в новой Session и сверяет шесть колонок и набор id с записью из карточки 5. У цели остаются id и `["дом","вход"]` и появляются «Оплатить СВЕТ», 5, True, «оплатить свет». Строка `40 / Купить ЧАЙ / 2 / True / ["архив"] / купить чай` прежняя. Закрытый разбор показывает команды чтения, сравнение двух записей и проверку: ошибочный PUT по 40 заметен сразу по id/соседу, пропущенный lower оставляет «купить чай» при правильном HTTP 200. Проверка 404/422/rollback и JSON может быть отдельным авторским прогоном.
