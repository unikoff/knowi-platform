## 01. Исходное название и его копия для поиска

Показать прежний смысл на учебной витрине. Запрос `  ЧАЙ 50%  ` после `strip().lower()` становится `чай 50%`: края обрезаются у ввода, внутренний пробел остаётся. Заголовок `ЧАЙ 50%` выглядит так же при выдаче, а его поисковая копия равна `чай 50%`. Две стороны сравнения приводятся к одному виду, пока вывод читает исходное значение.

В полном примере из следующего раздела вывести две версии `ЧАЙ V2`. Python `lower()` даёт `чай v2`, стандартная SQLite `lower()` даёт `ЧАЙ v2`. Попросить сначала предсказать, найдётся ли `чай` во втором результате, затем открыть сравнение: на таком значении буквального совпадения нет. `  ` после `strip()` становится пустой строкой. В Planner это отдельный ранний результат, потому что пустой фрагмент входит в любую строку.

**Учебный визуал.** Две дорожки с явно подписанными значениями. Верхняя показывает оригинал `ЧАЙ 50%` и подготовленную копию `чай 50%`. Нижняя ведёт от `  ЧАЙ 50%  ` через снятие краевых пробелов и `lower()` к `чай 50%`. Подсветить совпавшие буквы, пробел и знак в копии, исходный заголовок оставить на дорожке выдачи. Предложить найти, откуда взялся показанный пользователю верхний регистр. Пояснение под схемой связывает напечатанное название с оригиналом, а решение о совпадении с копией.

**Для возврата.** Нормализация ввода применяется к краям и регистру. В уже подготовленной колонке лежит только результат `title.lower()`. При записи нового названия готовый путь PUT/PATCH обновляет и эту колонку. Теперь нужно передать подготовленный фрагмент в SQL.

## 02. Буквальное вхождение и значение запроса

`instr(строка, фрагмент)` возвращает позицию первого вхождения от 1 или 0 при отсутствии, поэтому положительная позиция означает совпадение. Для двух текстовых аргументов пустой второй аргумент даёт 1. В обычном `LIKE` внутри шаблона `%` означает любую последовательность, включая пустую, а `_` означает один символ. Объяснить разницу на `50%` и `500`. Для запроса по фрагменту сравниваем `instr` с `LIKE` на шаблоне из фрагмента с добавленными `%` по краям; оба режима получают ту же нормализованную строку.

**Полный независимый пример для Stage 3.** В теории поставить один готовый копируемый Python-блок `Витрина` для имеющегося окружения SQLAlchemy. Включить импорты, открытие SQLite в памяти, готовую учебную таблицу `catalog` с `id`, `label` и `searchable_label`, заполнение четырьмя строками и их копиями после Python `lower()`, исполнение запроса, печать пар `id, позиция` и закрытие ресурса. Данные витрины: 1 `ЧАЙ 50%`, 2 `Чай 500`, 3 `Чай_подарок`, 5 `Чай 'сбор'`. Открытие и заполнение дать в готовом блоке; ученик читает ключевое выражение и результат в уроке. Для желающего повторить командой достаточно целиком вставить блок в один временный файл вне пакета `app` и запустить своим Python; рабочий проект и дополнительные файлы для чтения теории не нужны.

- На учебной таблице разобрать форму `func.instr` с колонкой первым аргументом и нормализованной строкой Python вторым. В независимом SELECT вывести id и позицию, отобрать положительные позиции, упорядочить id и прочитать пары результата. В форме SQLAlchemy `func` представляет SQL-функцию, а обычная строка Python в аргументе становится bound parameter, то есть передаётся драйверу отдельно от текста SQL. Показать на вводе `'` один знак как значение, отдельно от шаблона SQL с местом параметра. Нулевую позицию прочитать на `Чай 500` при поиске `%`.
- Ожидаемые результаты примера: `  ЧАЙ 50%  ` даёт `[(1, 1)]`, `%` даёт `[(1, 7)]`, `_` даёт `[(3, 4)]`, `'` даёт `[(5, 5)]`, `чай` даёт ids `[1, 2, 3, 5]`, отсутствующий `кофе` и строка из пробелов дают `[]`. Для пробелов отдельно показать ранний выход и объяснить, как он связан с `instr(строка, '')`. В `LIKE`-сравнении для `%` и `_` проходят все четыре строки. Для `50%` буквальный режим возвращает id 1, шаблонный также захватывает id 2.
- Учебная форма выводит пары про витрину. В проекте ученику предстоит самому собрать метод существующего репозитория и получить `Task`, применив нужный предикат к своей модели.

**Управляемая проба в интерактиве.** До первого запуска ученик выбирает прогноз id для двух строк `ЧАЙ 50%` и `Чай 500` с фрагментом `%` и режимом буквального поиска. После действия открыть результат и строковые позиции 7 и 0; переключение на шаблонный режим показывает обе строки и поясняет значение `%`. Затем ученик повторяет прогноз на четырёх строках, вводя `_`, `'` или `  ЧаЙ  `. Интерфейс показывает введённый и обработанный фрагменты, совпавшие id и позиции в буквальном режиме. Для `LIKE` показывать id и смысл шаблона. При пустом вводе отдельное состояние сообщает о раннем выходе. При ошибке прогноза обратная связь называет конкретную строку и причину и предлагает повторить пробу с другим фрагментом.

**Для возврата.** Смотреть на пару `текст и фрагмент`, положительную позицию и отдельное значение параметра. Справка для автора: [функции SQLite](https://www.sqlite.org/lang_corefunc.html#instr), [правила LIKE](https://www.sqlite.org/lang_expr.html#like), [параметры SQLAlchemy](https://docs.sqlalchemy.org/en/20/core/sqlelement.html#sqlalchemy.sql.expression.bindparam).

## 03. От выражения витрины к методу Planner

Перенести смысл из витрины в границу `handle_search → search_tasks → repository.search`. Показать точку вставки в `SqlTaskRepository` рядом с готовым методом выборки. Напомнить знакомую трассу `WHERE и порядок → self.session.scalars(...).all() → task_from_row`. `WHERE` отбирает строки в базе, `scalars` получает выбранные ORM-объекты и mapping сохраняет их исходные title и tags в `Task`. Для прошлого метода можно открыть этот фрагмент прямо в своём файле. Полный код нового метода оставить практике.

Объяснить чтение будущей локальной проверки до первого запуска. Для непустого поиска в отчёте рядом видны отдельные поля `SQL` и `Параметры`, порядок и id совпадений. Для пустого фрагмента нужно читать строку прямой проверки репозитория с 0 запросов; сообщение CLI о пустом вводе появляется ещё до его вызова. Проба для ученика: по двум отчётам о витрине, один с отбором в запросе и один с чтением всей таблицы, определить, где сработал SQL-фильтр. Критерий выбора: в первом есть условие, место значения и список параметров, а в выдаче только совпавшие id. Ответ указывает на `WHERE` и значение отдельно.

Разобрать короткий перенос про запись на витрине. При смене `Чай_подарок` на `Чай коллекция` исчезает поиск по `_`, а `коллекция` находит id 3. Старая копия в колонке дала бы старое совпадение. Предложить предсказать оба результата и объяснить, зачем проверять чтение уже после записи. В Planner готовые PUT/PATCH обновляют два поля одной строки, исходное название и его поисковую копию, в одной операции записи. Локальная проверка снимет исходные title и tags, выполнит готовую запись и прочтёт новое состояние через свежую Session. Для возврата дать соответствие `исходный title для выдачи, его поисковая копия для условия` и пример чтения отчёта. Дальше ученик пишет одну операцию и проверяет её готовым запуском.

## 04. Что мы будем делать в практике

Проектная работа в своём Planner. Начинаем с репозитория, который уже умеет выбирать и обновлять задачи, и берём готовую проверку из этой практики.

После списка связать технический результат с поведением: вывод команды показывает привычный поиск, отчёт о SELECT подтверждает место фильтрации, чтение после записи подтверждает актуальность заголовка.

При запуске до изменения этот вывод показывает готовый вход, затем проверка сообщает об отсутствующем методе. Ошибки подготовки данных или готовой записи отчёт связывает с соответствующей исходной опорой. Блок содержит запуск, данные, вызовы и критерии. Метод `search`, готовый предикат для `TaskRow` и эталон реализации появляются только в будущем разборе. Проверка использует одноразовые данные, закрывает ресурсы и удаляет свой временный каталог. Ученическое изменение ограничено методом и отдельным файлом проверки.

### Технические критерии и локальная готовность

- `search` принимает строку, использует прежнее правило `query.strip().lower()` и возвращает `[]` до обращения к Session, если фрагмент пуст. Условие сравнивает буквальное вхождение в существующей `title_normalized`. SELECT получает нормализованный фрагмент как параметр и явно сортирует совпадения по id по возрастанию. Наружу выходят `Task` со всеми прежними данными.
- Для непустого ввода, включая отсутствие совпадений, проверочный отчёт фиксирует один SELECT с фильтром по `title_normalized` и явной сортировкой по id. Результат `strip().lower()` виден в параметрах драйвера отдельно от SQL. Дополнительный параметр для сравниваемого числа допустим. Полное чтение с последующей фильтрацией не удовлетворяет этому наблюдению. Для `''` и пробельной строки прямой вызов возвращает `[]`, счётчик SQL остаётся 0.
- Открытые данные проверки: id 4 `СВЕРКА 50%` с tags `['work']`, id 6 и 15 `Сверка 500`, id 7 `Сверка_май` с tags `['work']`, id 11 `Сверка 'май'`, id 19 `TEAM Sync`. Прочие поля фикстуры видны в файле. Запрос `свеРКА` возвращает `[4, 6, 7, 11, 15]`, `  СВЕРКа 500  ` даёт `[6, 15]`, `  TEAM SYNC  ` даёт `[19]`. `%`, `_` и `'` дают соответственно `[4]`, `[7]` и `[11]`; `черновик` даёт `[]`. Результат для id 4 сохраняет исходное `СВЕРКА 50%` и tags. Строки CLI для команды с `%` показывают только id 4 в привычном формате; отсутствие совпадений и пустой ввод дают соответственно `Совпадений не найдено.` и `Введите фрагмент названия.`.
- Для id 7 сверяются три состояния. До записи `сверка_май` даёт `[7]`. Готовый PUT меняет название на `Расчёт_июнь`: старый фрагмент даёт `[]`, новый `[7]`. Готовый PATCH меняет его на `Отчёт_июль`: `расчёт_июнь` даёт `[]`, `отчёт_июль` даёт `[7]`. Оба перечитывания сохраняют id и исходные tags. Так проверяется, что поиск читает актуальную копию, которую поддерживает существующая запись.
- Признак готовности: локальная проверка показывает группы `Совпадения`, `SQL и параметры`, `CLI` и `Переименование` с наблюдениями выше. Быстрая сверка состава изменений подтверждает один предметный метод, сохранение штатной сборки, схемы и существующих маршрутов. Результат самой проверки можно повторить с чистыми данными тем же запуском.

### Подсказка и будущий разбор

Если `%` находит лишнюю запись, вернись к пробе витрины и сравни, как два режима понимают этот знак. Если `'` даёт ошибку, посмотри в примере, в какой части отчёта лежит введённая строка. Если расходится поиск после записи, сначала сравни в отчёте исходное название и его поисковую копию. Эти опоры открыты до карточки.
