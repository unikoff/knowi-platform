## Точки A и B

**Вход из репетиции.** «Возврат к обычному JSON» и одноимённая карточка оставляют обычные API и CLI без пробных SQL-подмен. В обоих читается контрольная задача №17 и отсутствует пробный id. Ученик берёт зафиксированные стартовые настройки, фактически использованный обычный учебный JSON, его контрольную копию и свои контрольные id. Пробный исходный снимок и заполненная SQLite остаются отдельными. Например, на проверенном входе обычный JSON содержит задачи 8, 17 и 24, а №17 имеет приоритет 3. Факт прохождения проверяется по заметке и собственным результатам ученика.

**Доступные приёмы.** «Источник, адрес и пустая цель» даёт явный init и проверку существующей пустой `tasks`. «Сверка по id перед первой записью» объясняет сверку ключей и шести полей. Ученик пользуется своим прежним способом чтения либо воспроизводит сопоставление на этих данных по независимому примеру. Канонический импортёр из «Импорт задач в SQLite» принимает путь архива с `--source` и SQLite URL с `--target`. Если справка `--help` показывает исторический `--database`, ему передают путь к файлу SQLite. Границы коротких SQL-ресурсов уже показаны в темах об HTTP-provider и Session на одну CLI-команду. Исторический вход `a5c81da` подтверждает `JSON_PATH`, `DATABASE_URL`, `get_db`, `sql_service_context` и явный импорт. Штатная SQL-сборка после вывода файлового кода сверяется с `f85b594`.

**Результат B15.** Обычные API и CLI работают с одним фактически открытым SQLite-файлом. Исходная схема, полный SQL-репозиторий, короткие Session, транзакции и публичное поведение сохранены. Ученик обосновывает шесть разных свидетельств. Файловая сборка выведена из обычного запуска, а архив и отдельный импортёр остаются доступны. Историческая запись `"75.1"` (`lesson-68a97f28ebcb4f5e7776430b`, legacy 32) соответствует карточкам 5–6. Для [входа 76](../../../../../../docs/concept/chapter_04/BLOCK_16.md#76-распознаём-недоступное-хранилище) сохраняем исправную учебную базу и контрольный GET. Классификация отказов и коды ответа относятся к следующей теме.

## 00. Вступление

LinkedNotes с «Точка старта», «Новый вопрос», «Результат». Обычный JSON восстановлен после учебной репетиции. Теперь проводим реальный переход в этой же синтетической копии и проверяем, что происходит при сбое. После списка перейти к независимому сюжету журнала выдачи оборудования.

## 01. Замораживаем источник и проверяем архив

Заморозка означает паузу всех процессов, которые меняют файл. Два пункта выдачи закончили работу, но перед этим срок штатива №8 вырос с двух до четырёх дней. Кабель №11 одинаков в обоих файлах. Независимый пример копирует закрытый журнал и читает все байты через `Path.read_bytes()`. Старый снимок отличается, свежая копия совпадает. Для переноса ученик берёт действующий путь из заметки, свою прежнюю копию и приём побайтной сверки из примера.

## 02. Сверяем содержимое после импорта

Точная копия ведомости сохраняет байты. Перенос в картотеку отдельно проверяется по ключам и полям. В примере совпадают номера 8 и 11, у штатива в другой картотеке пропадает метка. Код читает отдельный журнал через SQLite в режиме только чтения, сравнивает представления и печатает номер и поле. В Planner переносим прежний способ сверки или сравниваем небольшой набор самостоятельно. Пустоту цели подтверждает прежний способ. В старом представлении заявки отсутствие списка меток трактуется как пустой список. Для Planner сравнивать поля через `Task.from_dict()` и считать отсутствие `tags` эквивалентом `tags=[]`. Побайтовость проверяет совпадение остановленного источника со свежим архивом и неизменность самого архива.

## 03. Подключаем оба входа и проверяем открытый файл

Два пункта читают кабель №11 из двух одинаково заполненных картотек. Наблюдаем реальный файл той Session, которая прочитала заявку. Независимый пример выполняет `PRAGMA database_list` через SQLAlchemy `Session.execute(text(...))`, выбирает строку `main`, сопоставляет абсолютный путь с целью. Ученик прогнозирует оба ответа и оба результата сравнения до раскрытия вывода. В примере стойки `asynccontextmanager` открывает один общий журнал на весь `FastAPI(lifespan=...)`. Два запроса читают тот же журнал, каждый открывает и закрывает свой талон. Вывод подтверждает закрытие двух талонов и освобождение журнала только после обоих запросов. Связать этот порядок с `dispose()` Engine и отдельным закрытием Session каждого запроса или команды. Диагностика в Planner создаётся учеником в штатной Session только для чтений и убирается перед записью. Отдельный наблюдатель и диагностические запуски из открытой теории не требуются.

## 04. Проверяем новое состояние из другого процесса

Выдача №11 у второго читателя меняется только после записи и commit первого. Пример открывает тот же журнал отдельным процессом до и после отметки о возврате. В Planner ученик сам выбирает разное старое и новое значение, переносит id и проверяет его из другого процесса. Архив показывает прежнее состояние.

## 05. Убираем файловую сборку и проверяем два исхода

Старое обращение к папке вывесок мешает обычному чтению нового журнала. Пример показывает этот вызов, чтение только журнала, отдельное явное открытие старого экспорта, отказ обычной операции при недоступном журнале и читаемом экспорте. Таблица связывает условия и свидетельства двух запусков. Прогноз на изменённом случае спрашивает, достаточно ли отказа, когда старого файла тоже нет. Код очистки Planner и выбор связей остаются самостоятельными.

В небольшом примере фикстура pytest отдаёт один временный SQLite-файл двум обращениям и отдельный файл каждому тесту. Связать это со сбоем `tests/conftest.py` на входе A15: старый `build_service(JsonStorage(...))` прерывает подготовку запроса после смены сборки. Ученик сначала прогоняет `tests/test_api.py` с `-x`, переводит общие HTTP и CLI-проверки на временную SQLite, повторяет первый прогон, затем проверяет публичные контракты и настройки. Исторические JSON-проверки остаются отдельными unit-тестами с явным адаптером. Полный pytest закрепляет выход карточки.

## 06. Что мы будем делать в практике

Три коротких пункта LinkedNotes · сохраним и перенесём данные, переведём оба входа, проверим независимость. За ними одна фраза о фиксации промежуточных результатов.

### Практические карточки

| Карточка и открытая опора | Действие и локальное свидетельство | Закрытый разбор |
| --- | --- | --- |
| 1. «Замораживаем источник и проверяем архив» | Из прежней заметки восстанавливает обычные настройки. Меняет приоритет одной синтетической задачи через штатный HTTP, закрывает оба запуска, снимает свежий архив. Сравнивает архив и контрольную копию обычного JSON с остановленным источником по байтам. Неизменность второй задачи сверяет по предметным полям, включая `tags=[]` у старой записи без ключа. | Проследить паузу, обе пары файлов и, например, 3 → 4 у №17 при прежних полях №24. |
| 2. «Сверяем содержимое после импорта» | Берёт свежий архив, выбирает новую пустую цель, применяет знакомые init, импорт и сверку полей. На отдельной контрольной копии свежего архива без одного id, например №8, получает список с лишней строкой SQLite и повторно принимает решение о подключении обеих точек. | Показать 0 строк, результат для допущенного архива и запрет при несовпавшем наборе id. |
| 3. «Подключаем оба входа и проверяем открытый файл» | Сам переводит обычные API и CLI. До записи запрашивает `main` из тех же штатных Session при GET и CLI find по неизменному контрольному id. Сопоставляет оба пути с выбранной целью, при расхождении исправляет настройку. После проверки убирает временный вывод. | Дать закрытые фрагменты двух сборок, место временной диагностики, пример ложного успеха на зеркале и повтор с правильным адресом. |
| 4. «Проверяем новое состояние из другого процесса» | Выбирает новое значение у известной задачи, например статус №17 после CLI done. Другой штатный процесс видит новое значение у того же id. Архив остаётся со старым. | Объяснить сохранение до успеха, чтение после нового запуска и диагностировать старое значение. |
| 5. «Убираем файловую сборку и проверяем два исхода» | Сам прослеживает оставшиеся зависимости и выводит файловую ветку. Сохраняет явный импорт и преобразования `Task`. Исправная копия без старого JSON выдаёт изменённую задачу в API и CLI. Переносит общие фикстуры на SQLite под `tmp_path`, сохраняет явные JSON unit-проверки, прогоняет регрессии публичного договора и настроек. | Показать место сбоя старой фикстуры, временную схему и фабрику для штатных входов, отдельные тесты адаптера, восстановление параметров после `lifespan` и порядок первого, адресных и полного прогонов. |
| 6. «Убираем файловую сборку и проверяем два исхода» | Другая учебная копия. Направляет SQLite на каталог, а по прежнему активному адресу кладёт читаемый JSON с маркером №901. Подтверждает отказ GET и CLI без архивной записи. Затем восстанавливает адрес и контрольный GET. Явный импорт проверяет на третьей пустой цели. | Показать положительный контроль читаемости маркера, обе ошибки, восстановление и отдельный импорт. |

Открытые материалы дают самостоятельные примеры, наблюдения и ссылки на уже доступные приёмы. Полный разбор находится в `tasks[].answer` каждой карточки. Снять необязательные проектные команды из финала и убрать зависимость от собственной оснастки занятия.

## Сверка P4

Учебный вход прослеживается от восстановленного обычного JSON и его контрольной копии. Карточка 1 создаёт новое различие до заморозки. Карточка 2 выбирает допуск обеих точек по свежему архиву. Удалённый только в контрольной копии id даёт второй отчёт без вмешательства в импортированную цель. Карточки 3–4 разделяют совпадение открытого файла и новое состояние. Карточка 5 отдельно подтверждает вход общих фикстур из A15, перенос регрессии после удаления штатной файловой сборки и сохранение явных проверок адаптера. Карточки 5–6 используют раздельные учебные копии и разные условия. У каждого шага свой результат до следующего и соответствующая тема до практики. Проверки материалов и синтетического маршрута выполняются на итоговой правке Stage 3.
