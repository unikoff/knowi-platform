## 01. Как получить актуальный снимок

Начать с выбора источника в отдельной учебной копии Planner. Готовая оснастка создаёт новый файл с вымышленными задачами и печатает абсолютный путь. Показать форму PowerShell `$env:JSON_PATH = 'C:/Temp/club-demo/catalog.json'`. Оба учебных процесса получают одинаковое значение из своих терминалов при запуске, а оснастка сверяет его с фактическим `load_settings().json_path`. Перед остановкой добавить одну задачу через знакомый CLI `add`, записать выданный id и прочитать его через знакомый HTTP GET. Это наблюдение отличит актуальное состояние от первоначальной заготовки.

Объяснить паузу в записях. После контрольного чтения дождаться конца учебных запросов и команд, завершить CLI через `exit`, остановить свой локальный API через `Ctrl+C` и увидеть возврат приглашения в обоих терминалах. В течение переноса оставить эти процессы остановленными и сохранить прежнее значение `JSON_PATH` для подготовки снимка. Режим `prepare` после остановки сравнивает разрешённый путь учебного запуска с путём подготовленного синтетического файла и копирует его текущие байты. При расхождении путей копирование не начинается. Остановку ученик проверяет по своим процессам.

Начать один полный независимый пример про клубный каталог на готовых данных и следе работы. В `C:/Temp/club-demo/catalog.json` пробный снимок содержал три вещи (id 2 «Фонарь», 4 «Компас», 7 «Аптечка»). После репетиции через обычный терминал добавлен id 11 «Коврик», приоритет 3, `false`, `["зал"]`. После остановки терминала и HTTP-сервера файл из настроек копируют целиком в `C:/Temp/club-demo/cutover/catalog-snapshot.json`. В карточке наблюдений показать четыре id и совпадение отпечатка архива с текущим файлом. Для маленькой пробы предложить выбрать, годится ли снимок, взятый перед появлением id 11. В выводе сравнения с текущим файлом виден пропущенный id. Снимок, сделанный после остановки, сохраняет последнюю запись.

Учебный визуал вне 00 · временная шкала с добавлением id 11, остановкой обоих писателей, актуальным снимком, полной сверкой, заменой двух входов и первой новой SQL-записью. ## 02. Как решить, что перенос можно принять

Продолжить пример каталога одной подготовленной памяткой. Показать путь к отдельному ранее не существовавшему файлу `C:/Temp/club-demo/cutover/catalog.sqlite3` и URL `sqlite:///C:/Temp/club-demo/cutover/catalog.sqlite3`. Init открывает этот URL и создаёт пустую таблицу. Импорт принимает пути файлов `--source` и `--database` после явного init. При кавычках путь с пробелами передаётся одним аргументом. На готовом следе указать `python -m app.DBase.import_tasks --source "C:/Temp/club-demo/cutover/catalog-snapshot.json" --database "C:/Temp/club-demo/cutover/catalog.sqlite3"` и вывод `Импортировано задач: 4`. Готовый импортёр проверяет вход и записывает снимок одной транзакцией, а непустую цель отклоняет. Отдельно показать, что существующее имя занятого каталога или неподходящая схема означают остановку; автоматическая очистка могла бы уничтожить данные пользователя.

Для демонстрационного следа использовать полный набор полей в исходнике и в чтении из новой Session. `id` связывает строки вне зависимости от порядка. В примере значения остальных строк фиксированы.

| id | title | priority | is_done | tags после переноса | title_normalized |
| --- | --- | --- | --- | --- | --- |
| 2 | Фонарь | 2 | false | [поход] | фонарь |
| 4 | Компас | 1 | true | [] | компас |
| 7 | Аптечка | 4 | false | [поход, склад] | аптечка |
| 11 | Коврик | 3 | false | [зал] | коврик |

У id 4 ключ `tags` отсутствовал в JSON; ожидание `[]` соответствует историческому формату. Названия и списки сравниваются с архивом, служебное имя с Python `title.lower()`. Допустимые старые заголовки сверяются по историческому договору импортёра; ограничение HTTP для нового ввода здесь не применяется. Показать строку отчёта `id=11, tags, ожидалось [зал], получено []` с тем же числом строк. Ученик объясняет, почему здесь решение «остановиться» и почему одинаковый хеш двух JSON отвечает на вопрос об исходнике, а совпадение полей из новой Session отвечает на вопрос о переносе. При несовпадении до смены проверить фактические пути, исходник и отчёт, оставить штатную сборку на прежнем источнике. При исправлении для нового импорта выбрать свободную цель. Эти наблюдения допускают только переход к настройке обеих сборок.

## 03. Как подключить одну базу к двум штатным входам

В готовом примере клуба показать две короткие пары «до → после» в вымышленном `club_web.py` и `club_console.py`. Сайт меняет поставщика файлового сервиса на готовый SQL-provider запроса и хранит фабрику, консоль передаёт обычному циклу готовую функцию получения контекста команды. Оба процесса получают один напечатанный абсолютный SQL URL. Фабрика создаётся на сборку процесса; каждый запрос к данным и каждая распознанная команда получают отдельную Session. Показать, что передача функции с `context_factory=` откладывает открытие до команды, а параметр `Depends(…)` получает ресурс во время запроса. Commit внутри области записи происходит до сообщения об успехе. Знакомый код каталога при этом не меняет правила обработки операций.

Завершить пример с наблюдениями. Обычный HTTP создаёт открытую «Карту» с новым id 12. Обычная команда терминала находит 12 и завершает её. Новый HTTP-запрос читает `is_done=true`, новый процесс повторяет чтение 12 с тем же состоянием. Архив и исходный файл остались на четырёх прежних записях. Когда изменён только HTTP-вход, он успешно создаёт 12, а консоль ищет в JSON и задачу не находит. Если сбой замечен до новых SQL-записей, можно вернуть оба прежних запуска к исходному JSON. После сохранения id 12 возврат к архиву теряет эту запись. Для восстановления потребуется сохранить и отдельно учесть новые SQL-изменения.

Интерактив вне 00, после полного примера. Дать карточку с двумя настройками: тестовый снимок до появления id 11 или свежий после остановки; какие штатные входы переведены на SQL. До проверки ученик предсказывает, есть ли id 11 в импорте и увидит ли терминал новую запись API. В отклике показать цепочку и таблицу «JSON / SQLite / чтение CLI». Со старым снимком id 11 отсутствует, поэтому сценарий останавливается на сверке с актуальным источником. Со свежим снимком можно посмотреть, что произошло бы при разных связках. Если переведён только API, id 12 появится в SQLite и терминал его не увидит. Если переведён только CLI, новая запись API останется в JSON и терминал снова её не увидит. При двух файловых входах терминал увидит запись в JSON, переход ещё не выполнен. При двух SQL-входах терминал увидит запись в SQLite, а новый HTTP-запрос подтвердит смену её статуса. После объяснения дать изменить одну настройку и пересмотреть только изменившееся наблюдение. Все действия проходят на странице. Ученику не нужно создавать каталог примера или писать его код.

**Опора для переноса в Planner.** Показать карту существующих мест, оставив выбор и соединение ученику. В `app/api.py` обычная сборка сейчас кладёт готовый файловый сервис в состояние приложения; фабрика Session должна жить на уровне сборки. В `app/core/dependencies.py` маршруты зависят от `get_planner`, а `get_db` выдаёт запросу ресурс и закрывает его. Объяснить смысл `Depends(get_db)` и то, что имя зависимости при объявлении provider уже должно быть определено. В `app/main.py` обычный запуск CLI выбирает прежний способ получить сервис. У знакомой формы `run` именованный `context_factory` получает функцию без аргументов, которая возвращает контекст на команду. Готовая обвязка ниже принимает Session для HTTP, фабрику для CLI и `settings.database_url` для сборки. Одной общей переменной достаточно для адреса. На Windows дать скопировать готовую строку вида `$env:DATABASE_URL = 'sqlite:///C:/Temp/club-demo/cutover/catalog.sqlite3'`. Одинарные кавычки передают URL целиком. Запуски из того же PowerShell наследуют значение. Напечатанное значение сверяется с `load_settings().database_url`, откуда оба входа берут его при старте. Передачи URL в аргументы импортёра и открытия Session на уровне модуля карта не предполагает.

## 04. Что мы будем делать в практике

**Формат и исходник.** Один проектный маршрут в своей безопасной учебной копии Planner после успешной репетиции, из `project/` в прежнем Python-окружении. Вход · существующие `app/api.py`, `app/core/dependencies.py`, `app/main.py` и отдельный штатный учебный JSON из открытой поставки. Рабочую базу для перехода создаём заново в свободной папке; данные тестовой репетиции от неё отделены.

**Связка в теории через непустой `LinkedNotes` с `items`.**

1. **Возьмём актуальный снимок.** После остановки в отчёте увидим совпавшие байты источника и архива и отдельную пустую цель.
2. **Сверим данные и переведём оба входа.** Полное совпадение позволит указать проверенный адрес и переключить API и CLI.
3. **Прочитаем результат после перезапуска.** Найдём по фактическому id новую задачу, проверим её статус и сравним отпечатки файлов.

После списка связать результаты. При сомнении об адресе вернуться к напечатанной паре пути и URL. При различии в данных обратиться к сравнению по id. Новое чтение проверяет результат совместного включения.

**Условие для будущей карточки.** В отдельной учебной копии своего Planner подготовь синтетический JSON готовой командой и выбери его для обоих обычных запусков. Добавь вымышленную задачу через знакомый CLI и прочитай её через учебный API. Останови эти два процесса, возьми архив актуального учебного файла и повтори знакомую подготовку, импорт и сверку. По отчёту реши, можно ли продолжать. Если перенос точен, подключи к штатным входам готовые SQL-ресурсы, используя общий адрес сверенной базы. Проверь новое добавление через обычный API, чтение и завершение в обычном CLI, чтение из перезапущенного API и сохранность JSON. Укажи, что делать, если расхождение обнаружилось до смены и если уже сохранена новая SQL-запись.

**Поставка Stage 3 в открытом разделе карточки «Готовые материалы», перед заданием.** Автор размещает два полных копируемых файла и памятку с командами. Ученику достаточно сохранить эти блоки в своей имеющейся учебной копии. Памятка ведёт в её `project/` и отдельные терминалы, а готовый режим `seed` создаёт данные. При занятых именах в памятке показать, как выбрать свободный суффикс имени до копирования и подставить его во все команды или импорты этого файла, например `check_cutover_local.py` или `app/cutover_wiring_local.py`. Нужны существующие зависимости проекта; код примера каталога, закрытый разбор и файлы из папки репетиции не требуются. До собственной правки обычные входы продолжают пользоваться JSON.

- `project/app/cutover_wiring.py` · готовые `make_session_factory(database_url)` поверх существующих Engine и фабрики Session, `make_http_planner(session)` поверх того же `PlannerService`, `SqlTaskRepository` и `session.begin`, `make_cli_context(session_factory, service_context)`, возвращающая функцию без аргументов. Объяснить при чтении заготовки, что `service_context` здесь обозначает уже существующую функцию `sql_service_context`, которую точка запуска передаёт по имени. Вызов возвращённой функции даёт контекст для одной команды. Модуль обвязки не импортирует `app.main` и сам при импорте не открывает ресурс. В поставке нет правок default-входов, установки URL или временного HTTP override.
- `project/check_cutover.py` · готовая оболочка с командами ниже. Переиспользовать алгоритм сверки репетиции, принимая актуальный архив и отдельную новую цель. Памятка доступна рядом с блоками, с фактическими командами и трактовкой результатов. Скрипт читает только явный учебный источник прогона, создаёт синтетический исходник при подготовке и сохраняет его байты после штатной учебной записи. Исходники и настройки учащийся меняет сам. Запись в SQL после импорта выполняют только запущенные штатные процессы после решения ученика.

| Команда из `project/` | Ожидаемое состояние и наблюдение |
| --- | --- |
| `python check_cutover.py seed "run-a"` | Создаёт новый `data/cutover-input/run-a/tasks.json` и сохраняет отметку происхождения для этого учебного прогона. В файле две вымышленные записи: id 3 «Сверить фонари», 2, `false`, `["прокат"]`; id 8 «Вернуть кабель», 1, `true`, `[]`. Занятое имя даёт отказ без изменений. Печатает готовую строку PowerShell с абсолютным `$env:JSON_PATH`. |
| `python check_cutover.py source "run-a"` | Сверяет фактический путь из `load_settings().json_path` с путём синтетического файла этого прогона и печатает оба адреса. Проверка разрешённых путей учитывает их фактическое расположение. Если выбран другой файл, отказывает до чтения записей. |
| `python check_cutover.py prepare "run-a"` | После остановки, подтверждённой учеником, повторяет ту же проверку пути и происхождения до чтения. Занятая папка, отсутствующий исходник или ошибка init дают отказ. Печатает оба абсолютных файловых пути, готовую команду импортёра и готовую строку PowerShell для будущего запуска. |
| `python check_cutover.py compare "run-a"` | До любых пробных записей новой Session сравнивает всю таблицу с архивом, даёт ожидаемое и фактическое значение по каждому различию, список лишних/пропущенных id и итог. Сверяет оба JSON с исходными отпечатками из описи. Ошибка импорта, неполный отчёт или изменение байтов означают остановку до смены входов. |

Оба получают выбранный URL; защитный `JSON_PATH` их дочерних процессов указывает на отдельный контрольный JSON внутри прогона с одной отличимой записью и id вне архива. Оболочка не подменяет provider, CLI-контекст и маршруты. Она проверяет фактические HTTP-ответы и вывод CLI, перезапускает API и проверяет чтение, показывает начало новых записей и состояние всех трёх JSON до/после, в конце завершает свои процессы. |

В командах `run-a` обозначает одно свободное имя пары «учебный источник и итоговая SQLite». До первого запуска ученик переносит напечатанную строку `JSON_PATH` в терминалы из этой учебной копии и запускает `source` в каждом. Памятка даёт готовые обычные команды запуска API на свободном локальном порту и CLI, а также HTTP GET по полученному id. Контрольная запись через CLI `add` имеет вымышленные данные «Сверить карту склада», приоритет 3. Записанный id понадобится для сверки свежего архива. Проверку контрольного JSON разъяснить прямо в памятке: обычные точки входа получают штатные настройки, а защитный путь удерживает ошибочный файловый сценарий внутри учебной папки. При чтении контрольной записи через один из входов smoke останавливается до пробной записи и показывает, какой вход всё ещё читает JSON. При позднем сбое отчёт показывает, какие операции уже подтверждены. Для дальнейшего обычного запуска в новом терминале памятка повторяет ту же строку `DATABASE_URL` перед знакомыми `python -m uvicorn app.api:app` или `python -m app.main`. После smoke файл `planner.sqlite3` сохраняют как рабочую базу.

**ТЗ для карточки, в порядке готовых результатов.**

1. **Источник и готовая цель (§01–02).** Готовый `seed` создал отдельный синтетический файл. В обоих учебных терминалах такой же путь подтверждён перед запуском. Ученик добавил контрольную задачу в CLI, прочитал её API по выданному id и остановил оба учебных процесса. В выводе `prepare` видны та же задача и id, совпадение байтов учебного исходника и свежего архива, пустая таблица и пара абсолютных путей плюс URL. Если путь ведёт к иному файлу или имя занято, оснастка останавливается до чтения данных из другого файла или перезаписи. Архив без контрольной задачи не проходит допуск.
2. **Допуск по данным (§02).** Ученик запускает из памятки фактическую команду импортёра для напечатанной пары; видит успешный импорт. До включения входов в `compare` совпадают полный набор id, `title`, `priority`, `is_done`, `tags` и производный `title_normalized`. Отсутствующие исторические `tags` дают `[]`. Ученик объясняет решение на своём отчёте и на коротком открытом контрольном отчёте карточки, где число и id совпали, но у одной строки разошлись `tags`. На контрольном отчёте результат «остановиться до смены» с указанием id и поля. Для этого случая не нужно портить свою SQLite.
3. **Собственное переключение (§03).** После допуска ученик сохраняет прежний способ запуска достаточно, чтобы вернуть обе точки до первой новой записи при сбое. По карте сам соединяет готовую фабрику и запросный provider в штатных `app/api.py` и `app/core/dependencies.py`, а готовый командный контекст в штатном `app/main.py`. Открытые исходники показывают один SQL-путь для каждого default: API хранит фабрику и получает запросный сервис на отдельной Session, CLI передаёт функцию контекста в обычный `run`. Ни временные overrides, ни запуск отдельного harness как приложения не требуются. Оба входа используют один напечатанный абсолютный URL, который ученик задаёт готовой строкой в одном PowerShell до старта. Локальная проверка перед записью · проследить в исходниках от `PlannerDep` до `get_db`, от CLI `run` до контекста, затем сверить напечатанное значение URL. Оба переключения готовятся при остановленных входах.
4. **Проверенный запуск и передача (§03).** Готовый smoke сначала читает штатными входами известную перенесённую задачу и проверяет отсутствие контрольной JSON-записи. Пустой снимок `[]` остаётся отдельным тестовым контрастом для оснастки и разбора. У него оба списка до записи пусты, а полная сверка даёт ноль строк. В основном прогоне контрольная учебная задача уже есть в актуальном снимке. Затем HTTP `POST /tasks` создаёт открытую учебную задачу (`201`, положительный id вне импортированного набора), CLI `find` читает этот фактический id, CLI `done` сохраняет изменение, новый `GET /tasks/{id}` и такой же запрос после перезапуска API показывают `is_done=true`. Комплект дополнительно сверяет прежний формат CLI и `GET /stats` (относительно исходного состояния `total +1`, `done +1`, `open` прежнее). Запуск health или совпадение прежних строк само по себе общий источник не доказывает. Отчёт сравнивает SHA256 исходника, архива и контрольного JSON с их начальными значениями. Ученик сохраняет в своём каталоге `data/cutover/run-a/` файл `result.md` с источником и архивом, адресом, полным результатом сверки, полученным id и чтениями, контрольными отпечатками и границей восстановления. При сбое после новой SQL-записи в SQLite уже есть более свежие данные; оба входа останавливают и сохраняют SQLite для отдельного восстановления.
