- **Объяснить.** Тело PUT задаёт новые публичные поля, путь выбирает строку по id, найденная задача даёт прежние tags. Служебный заголовок вычисляется из нового названия. Успех виден после подтверждения операции.

- **Границы.** Область записи сервиса, фикстура, запросы и сверка выдаются готовыми. Сохраняются HTTP handler, `TaskUpdate`, `TaskRead`, SQL create/get и штатный JSON. Частичный выбор полей, новые маршруты, правка тегов через API, изменение схемы и штатное переключение относятся к другим задачам.

Сохраняются прежние id/tags и правило вычисления `title_normalized`. Публичный сценарий PUT отдельно открывает свою область, поэтому следующий сценарий переиспользует репозиторную запись. ## 02. Как сохранить и перечитать ту же запись

**Завершить цельный пример с книгами.** Место действия в будущей теории: одна готовая демонстрация на странице. Для автора Stage 3 подготовить один полный автономный пример SQLAlchemy на временной SQLite с моделью книги, подготовкой двух строк и ветками успеха, отсутствия и отказа до подтверждения. На странице заранее показать вход, порядок операций и результат каждой ветки. Ученик приходит к первому полезному наблюдению прямо на странице без создания файлов, отдельного запуска или ручного набора демонстрационной обвязки. При публикации автор проверяет, что показанный вывод воспроизводится исходником примера.

1. Перед первым чтением открыть ресурс Session и войти в область записи. В ней загрузить книгу 7 по первичному ключу и подготовить проверенную новую карточку. Объяснить отдельно формы на данных примера: `session.get(BookRow, 7)` возвращает объект строки либо `None`, а проверка `is None` выделяет ветку отсутствия. Присваивание свойства загруженной строки меняет её ORM-состояние. Вызов `copy()` у списка даёт отдельный список, а функция преобразования возвращает обычную карточку из строки. Для неизменной метки достаточно сохранить старое содержание. Новую метку через тело добавлять нельзя.
2. Показать, что изменяется уже загруженная строка, по прежнему ключу. `flush()` отправляет изменения в пределах открытой транзакции. Обычную карточку можно сформировать внутри области, но наружу она выходит после успешного завершения `with`. На выходе область подтверждает запись, ресурс закрывается отдельно. Показать обычные конструкции на книге и результат шагов без сборки точного метода Planner из готовых строк.
3. Открыть независимую Session и вывести книгу 7 как `(7, "Карта", True, 2, ["дар"], "карта")`, а книгу 8 с прежними значениями. Публичная карточка книги отображает первые четыре значения, а чтение строки отдельно показывает метку и техническое имя. Для id 99 показать `None` при чтении и прикладной ответ «книга не найдена» без новой строки. Объяснить, что в Planner отсутствие получает прежний 404. Для управляемого сбоя после flush и до commit показать ещё один запуск на исходных данных: ошибка выходит наружу, независимое чтение снова показывает «Север» и прежние поля. Такой прогон поясняет роль области, подробный отказ разбирается позднее.

**Перенос к готовой обвязке Planner до практики.** Напомнить точную линию `with self.write_scope():` → первое `self.get_task(task_id)` → проверка новой Task → запись → выход из `with` → ответ. Фабрика вызывается скобками, чтобы получить область для текущей операции. У SQL первый SELECT способен сам начать транзакцию Session, поэтому область сервиса ставится снаружи первого чтения. Репозиторий пользуется уже выданной Session, `flush` выполняет внутри неё, commit/rollback принадлежат области сервиса, закрытие ресурса делает provider. В штатной JSON-сборке тело блока выполняется как обычно: пустая область не управляет транзакцией. Если сервис не находит задачу, он поднимает `TaskNotFoundError`; контракт репозитория использует `None` на отсутствующей строке. Перед первым самостоятельным шагом напомнить, что аннотация `Task | None` обозначает эти два возможных результата, показать существующий `get` как опору для поиска и mapping, а `create` как опору для `lower` и `flush`.

## 04. Что мы будем делать в практике

Формат: одна ручная проектная карточка. В своём Planner добавим SQL-замену для прежнего PUT и сверим, что сохранилось после ответа. В итоговой теории дать один `LinkedNotes` с действиями и видимыми результатами:

1. **Найдём задачу для проверки.** Готовый запуск покажет id из нашего create, прежние теги и соседнюю запись. С этими данными сможем сверить результат после замены.
2. **Заменим публичные значения.** Сами допишем одну операцию в SQL-репозитории. PUT вернёт новые публичные поля под прежним id.
3. **Перечитаем результат.** В отдельном чтении сравним теги, служебное название и соседа. Запрос с отсутствующим id покажет прежний 404.

Если поменялось лишнее поле, вернёмся к схеме источников. Если результат разошёлся после нового чтения, проследим границу от первого чтения до commit. Подробные данные и команды идут в самой карточке.

Оснастка использует интерфейсы собственного Planner и установленное ранее тестовое окружение. Подготовка запускает существующие `create` и `get` на отдельной базе. Она создаёт пару синтетических задач через сервис, получает id из результата и снимает исходные значения заново открытой Session. Каждый сценарий получает свою временную базу. Override даёт запросу свежую Session и `write_scope=session.begin`. `finally` восстанавливает прежние overrides и фабрику, временный Engine освобождается. Проверку JSON запускать на отдельном временном JSON через имеющуюся тестовую фикстуру без SQL override. Рабочий JSON и штатную конфигурацию не использовать. Оснастка содержит только подготовку, запросы, чтение и проверки; в ней отсутствуют реализация SQL `replace`, дополнительные методы репозитория и изменения маршрута.

### Контекст и условие карточки

В своём Planner мы уже можем создать задачу и прочитать её по id. Готовая проверка создаст две задачи тем же методом в отдельной тестовой базе. Скопируем подготовку по указанным путям и из каталога `project` своим привычным интерпретатором выполним:

```text
python -m pytest -q -s tests/test_put_replace_lab.py -k baseline
```

Готовый сценарий `baseline` работает через create/get без вызова нового метода. Он показывает id цели и соседа, исходные поля и теги. Если они не читаются, возвращаемся к проверке создания, затем повторяем команду.

Добавим сами один метод `replace` в `project/app/DBase/repositories.py`, в существующий `SqlTaskRepository`. У него на входе уже проверенная Task. Нужно записать её на место прежней задачи и вернуть сохранённую Task. Сохраним id и внутренние теги, обновим копию названия для внутреннего поиска, затем посмотрим на ответ PUT и на данные, прочитанные отдельно. Запрос для отсутствующей задачи должен показать привычное сообщение об отсутствии. Прежний JSON PUT проверяется готовым временным прогоном.

### Технические критерии и различающие случаи

1. `SqlTaskRepository.replace(self, task: Task) -> Task | None` работает по `task.id` и обновляет существующую ORM-строку. На месте прежней строки остаются прежний id и содержимое tags. Три публичных значения совпадают с проверенной Task, `title_normalized` равен Python `task.title.lower()`. Метод возвращает предметную Task, доступную после закрытия Session. Используются существующие модель, Session и mapping. Метод отправляет изменения через flush в уже открытой области. Репозиторий не начинает отдельную область записи, не коммитит и не закрывает Session. В реализации нет вставки взамен старой строки или массовой перезаписи.
2. **Нормальный случай.** Цель до PUT: `("Черновик", 2, False, ["личное"], "черновик")`. Сосед: `("ЁЛКА В КЛАССЕ", 4, False, ["архив"], "ёлка в классе")`. Id обеих задач взяты из собственных create. PUT по id цели с `title="ПЛАН ДНЯ", priority=3, is_done=true` даёт 200 и четыре публичных поля. После запроса новая Session видит `("ПЛАН ДНЯ", 3, True, ["личное"], "план дня")` под тем же id. Сосед и набор id совпадают со снимком до PUT.
3. **Различающий случай.** Второй PUT в том же сценарии по тому же id с `title="ЁЛКА В КЛАССЕ", priority=1, is_done=false` меняет прежнее `true` на `false`. Ответ и новое чтение различают изменение и сохранение старого флага. Теги сохраняют прежнее содержание, техническое имя теперь «ёлка в классе». Совпадение названия с соседом допустимо, сосед остаётся прежним. Этот вход различает потерю tags, старый технический заголовок и ошибочную проверку истинности.
4. **Отсутствие.** Готовый запрос использует положительный id, отсутствующий в исходном наборе, например максимум двух id плюс 100. PUT возвращает прежний 404 с `"detail": "Task not found"`, снимок строк совпадает. Дополнительная готовая проверка вызывает `replace` с валидной предметной Task на отсутствующем id и видит `None`, так как HTTP-ветка 404 заканчивается раньше, в сервисном поиске.
5. **Защита и регрессия.** Готовая проверка тела без обязательного поля видит 422 и прежние строки. Управляемый отказ между flush и commit через готовую область видит ошибку и неизменный снимок после открытия новой Session. Ученику достаточно прочитать этот результат, собирать сбой самому не требуется. Готовая регрессия подтверждает SQL create/get и прежний JSON PUT после снятия SQL override, на изолированном JSON. Роутер и HTTP-схемы остаются прежними.

**Локальная готовность.** Запустить из `project`:

```text
python -m pytest -q -s tests/test_put_replace_lab.py
```

Сверить строки «до» и «после» для цели и соседа, 200 и 404, видимое `false` во втором PUT, «ёлка в классе» и прежние «личное». Готовые проверки ничего не требуют сверх видимых критериев. В своей реализации отдельно видно, что обновляется найденный объект, а не добавляется строка. Завершить кратким объяснением, откуда пришли id, tags и технический заголовок. Код остаётся в своём проекте для следующей практики, временную SQLite переносить не требуется.
