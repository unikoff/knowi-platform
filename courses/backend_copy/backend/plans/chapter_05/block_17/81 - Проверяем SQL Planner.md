## 05. Внутренние tags и опись SQL

- **Объяснение:** в Planner API создаёт `title` и `priority`, возвращает `id, title, priority, is_done`; `tags` и `title_normalized` остаются внутренними. Значения tags для диагностики задаются только синтетически в выбранной учебной БД, а не через API/CLI. Разобрать таблицу, строку и идентификатор; `SELECT`, `UPDATE`, `WHERE id = ?`, параметр `?`, `fetchall()`, `commit()`, `close()`, JSON-массив строк и `json.dumps`. Объяснить, что `WHERE` ограничивает изменение одной строкой, параметры отделяют значения от SQL, commit закрепляет запись, а закрытие освобождает соединение. Остановленные операции и проверка существования файла до `sqlite3.connect` важны: обычный connect способен создать новый файл при ошибочном пути.
- **Полный независимый пример:** в отдельном `demo_notes/data/demo/notes.sqlite3` создать таблицу заметок с двумя ID и JSON-колонкой меток. Показать весь исполняемый файл-пример: импорт `sqlite3` и `json`, проверку существования выбранного файла, соединение, чтение обеих строк, параметризованный `UPDATE` по одному известному ID с `json.dumps(['дом'])`, commit, повторный SELECT и закрытие. Наблюдение: изменилась только метка выбранной заметки, соседняя строка прежняя; при несуществующем ID ни одна строка не меняется. Пояснить `cursor.rowcount` и различать отсутствие строки и успешную запись. Дать отдельную пробу с другими ID и другой меткой, затем сверить обе строки; при ошибке вернуться к `WHERE` и параметрам.
- **Применение к проекту:** объяснить, что проверенный `load_settings().database_url` является URL SQLAlchemy, а не буквальным путём для `sqlite3.connect`; для практики ученик уже знает отдельный полный путь к файлу и сравнивает его с разрешённым адресом. При выключенных записывающих процессах и после проверки `Test-Path` использовать этот путь в Python-интерпретаторе той же venv; показать ввод и выход из интерпретатора. На Stage 3 разобрать параметры `UPDATE tasks SET tags = ? WHERE id = ?`, `SELECT id, title, priority, is_done, tags, title_normalized FROM tasks ORDER BY id` и преобразование JSON-строки обратно в список через `json.loads` на независимой заметке. Это форма механизма, не готовые конкретные значения двух практических записей.
- **Опора:** проверить адрес и ID до изменения, убедиться в одном совпадении для каждого обновления, затем сравнить все шесть полей. Не менять другие колонки и не считать tags публичными. Переход: сравнение после нового процесса покажет сохранность внутренних данных.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проектная диагностика в учебном Planner. У ученика отдельная копия снимка B главы 4 и доступ к `project/`; личные знания ещё не подтверждены, а разделы 01–06 дают объяснения и малые пробы. Ни база, ни результаты следующих занятий не выдаются готовыми. Ученик действует сам, используя открытую теорию; автор Stage 3 подготовит условия, но не готовый итоговый сценарий.

1. **Адрес и запуск → проверяемый пустой учебный старт.** Контекст: необходимо проверить Planner, не затрагивая чужие данные. Условие: изолированная копия содержит `app/`, `tests/` и требования; выбрать отдельный новый каталог `project/data/stage17/` и файл `planner.sqlite3`, если они свободны, иначе выбрать другое новое имя и последовательно использовать его. В PowerShell из `project/` проверить `Get-Location`, `Test-Path` каталога и файла; создать только новый каталог, установить `$env:DATABASE_URL = 'sqlite:///data/stage17/planner.sqlite3'` для указанного имени или URL с выбранным другим новым путём, распечатать разрешённый URL через `load_settings` и сравнить с выбранным полным путём. В каждом терминале повторить установку и проверку. Подготовить venv из 01, если её ещё нет, затем тем же Python выполнить `-m app.DBase.init_db`. Результат: новый файл по ожидаемому адресу, исходный рабочий файл не выбирался; если адрес неизвестен, файл занят, команда упала или URL не совпал, остановиться до записи. Помощь: разделы 01–03; разбор покажет происхождение URL и объяснит, почему `create_all` не исправляет схему.
2. **Создание и отказ API → две различимые записи.** Контекст: нужны две искусственные задачи, чтобы проверить не только изменяемую строку, но и соседа. В отдельном терминале с тем же URL запустить команду Uvicorn из 04, открыть локальный `/docs`, проверить именно свой сервер, отправить `POST /tasks` с JSON `{"title":"Подготовить заметки","priority":2}`, затем `{"title":"Проверить расписание","priority":4}`. Записать реально возвращённые ID, оба ответа 201 и начальное `is_done: false`. Отправить отдельный `POST /tasks` с `{"title":"Ошибочная задача","priority":6}`: ожидается 422; через `GET /tasks` проверить, что записей по-прежнему две. При ином статусе или числе остановиться и выяснить причину. Опора 04: тело, статус, чтение; помощь возвращает к проверке адреса и тела. Будущий разбор объясняет разницу между отказом и доказательством отсутствия записи.
3. **Синтетические tags → исходная опись.** Контекст: публичные ответы не показывают все данные, которые необходимо сохранить. Остановить API и закрыть CLI, проверить существование именно выбранного файла; с помощью `sqlite3` и приёмов 05 сначала прочитать две строки, затем для первого фактического ID задать JSON-массив `["учёба"]`, для второго `["планы"]`. Проверить, что каждый UPDATE затронул одну строку, выполнить commit, закрыть соединение, вновь прочитать обе строки и записать количество и шесть полей. Никакие другие поля не менять. Результат: разные внутренние tags и неизменные остальные поля; при неизвестном ID, ином количестве или ошибке не продолжать, проверить адрес и транзакцию. Помощь: `WHERE`, параметры, commit и повторное чтение в 05; разбор объясняет, почему API-ответ не подтверждает сохранность tags.
4. **API → CLI → новый процесс → сохранённое изменение.** Контекст: исходная опись готова и адрес известен. Снова запустить API с тем же явно проверенным URL, найти первую запись через `GET /tasks/{id}` по реально полученному ID и сравнить четыре публичных поля. В другом PowerShell-терминале установить и проверить тот же URL, запустить `.\.venv\Scripts\python.exe -m app.main`; внутри меню выполнить `find`, ввести первый ID, затем `done`, тот же ID, и `exit`. Остановить первый API, в новом процессе с тем же проверенным URL запустить API снова и выполнить GET обеих записей. Первая имеет прежние ID, title и priority и `is_done: true`; вторая остаётся открытой и её публичные поля не изменились. Затем остановить API, открыть выбранную SQLite и повторить SQL SELECT шести полей из 05: tags обоих и `title_normalized` сохранены, у первой изменился только статус; вторая строка совпадает с описью целиком. Если данные не совпали, зафиксировать различие, проверить URL процессов и не считать переход выполненным. Помощь: разделы 02, 04 и 05; разбор последовательно прослеживает процессы и сохранённое состояние.
5. **Существующие тесты и передача → проверяемое свидетельство B.** Вход: та же учебная копия и опись до/после. Из `project/` запустить `.\.venv\Scripts\python.exe -m pytest -q` после проверки подготовленности окружения; записать фактический итог и ошибки. Составить краткую опись с полным учебным путём, двумя ID и всеми шестью полями после проверки, числом записей, исходным и текущим статусами, результатами HTTP/CLI, отказом 422 и результатом тестов. Если тесты не прошли, записать ошибку и восстановить предпосылку до передачи. Помощь: 06; будущий разбор показывает, какие выводы дают тесты, а какие только сквозной сценарий. Опись не является резервной копией.

Эти действия связаны: проверенный адрес делает допустимым создание схемы; реальные ID задают точные границы SQL-подготовки; исходная опись позволяет обнаружить потерю tags и изменение соседа; новый процесс проверяет сохранённое состояние. При затруднении вернуться к указанному объяснению и повторить независимую малую пробу, затем свой шаг. Совокупность свидетельств, а не отдельный успешный статус, составляет B.
