## Точка B и границы

- Объяснить различие модели, существующей таблицы и истории; почему nullable расширение, осмысленное заполнение и отдельное возможное ужесточение являются разными решениями.
- Самостоятельно добавить nullable `description` в metadata, создать и прочитать кандидат ревизии, исправить его при необходимости и применить к двум учебным базам; согласовать `app/DBase/init_db.py` с историей через понятный отказ с инструкцией, без тихого `create_all`.
- Подтвердить неизменность прежних шести полей, идентификаторов и числа строк; у старых строк `description IS NULL`; затем только на синтетических строках сохранить непустой текст у одной и NULL у другой. Повторный `upgrade head` не меняет ни одно из значений. У обеих баз согласованная schema и revision; новый процесс и прежние выборки, создание задачи, API и CLI сохраняют прежний контракт.
- Не вводить description или внутренние tags в API/CLI, пользователей, владельца, обязательность поля или автоматический backfill. JSON-импорт остаётся явным; fallback не добавлять. Batch move-and-copy только обзор, не обязательная операция. До завершения сохраняются старая совместимая версия приложения и проверенный резерв. До upgrade новой модели на каждой базе не запускать. При неизвестной revision, несоответствии схемы, неверном пути или непроверенном резерве остановиться.
- Планируемая передача в 85: обе проверенные схемы, история и metadata, исходный проверенный snapshot и отдельно снимок после расширения с синтетическими данными; следующий паспорт использует отдельную disposable-копию для отказа и восстановления. В 85.1 эти результаты используются для регрессии, повтор на head не заменяет проверку пути от baseline.

## 04. Nullable расширение и проверка данных

- Объяснить `ALTER TABLE ... ADD COLUMN`, старые строки с NULL при добавлении необязательного поля без server default, ограничения SQLite на ADD COLUMN и зависимость некоторых проверок от версии. Показать полный независимый вызов `python -c "import sqlite3; print(sqlite3.sqlite_version)"`, объяснить импорт, атрибут и вывод версии, дать ученику первую пробу и не обещать одинаковую семантику всех драйверов. `batch` может перенести данные через пересоздание таблицы, что требует отдельной проверки CHECK, индексов и FK; для простого добавления здесь не требовать пересоздания.
- Независимый пример: перед каждым `upgrade` и `current` для новой цели согласовать `sqlalchemy.url` с `expected_database_path` и проверить оба пути по 01; в той же базе книг выполнить проверенную ревизию `note`, `python -m alembic upgrade head`, затем `current` и через Python `sqlite3` запросы `PRAGMA table_info(books)` и `SELECT id, title, note FROM books ORDER BY id`. Показать входные строки, SQL, подключение к явному существующему пути, закрытие соединения, вывод NULL как `None` и причину. Повторный upgrade, повторная выборка и неизменность данных: версия уже head, новая операция не запускается повторно. Разобрать `IS NULL`, а не `= NULL`, и параметризованный `UPDATE ... WHERE id = ?`, commit и чтение из нового соединения на синтетической книге. Ученик в отдельной таблице сам пробует upgrade, повтор и выборку с NULL; наблюдает одну новую колонку и сохранённую строку.
- Визуал-трассировка: старые строки → nullable колонка с NULL → отдельное осмысленное заполнение → проверка → возможное отдельное ужесточение. Ученик выбирает, что уже произошло, а что нет; обратная связь объясняет, что текущая миграция не заполняет значения и не делает поле обязательным. Далее нужно защитить старую команду создания.

Объяснить, что обе опции строки, `set_main_option` заменяет значения ini для этого Config, а `script_location` по-прежнему указывает на ту же историю; `env.py` обязан читать переданные значения. Показать равенство путей и созданную тестовую базу, а при изменении только URL отказ до создания неправильного файла. До проектных тестов ученик повторяет пробу на другом `tmp_path`; версия SQLAlchemy 2.0.55, API Alembic и интерполяция `%` сверяются по документации и окружению перед выдачей.
- Для старого контракта напомнить из входного README: `python -m app.main` с `list`, `add`, `exit`; `python -m uvicorn app.api:app --host 127.0.0.1 --port 8000`, `GET /tasks`, `POST /tasks`, `GET /stats`. Перед первым запуском объяснить `DATABASE_URL`, остановку процесса, отдельный порт и повторный запуск для нового соединения. На отдельном примере показать JSON `{"title":"Подготовить встречу","priority":3}` для POST, статус 201 и ответ с полями `id`, `title`, `priority`, `is_done`; GET возвращает список этих представлений. Сравнить значения и структуру до/после; описание и tags в публичном ответе не появляются. Поля не добавляются в схемы запроса: не обещать отказ от лишних JSON-полей, поскольку это отдельный договор валидации. Health сам по себе не проверяет чтение задач. Данные проверки создаются в отдельной тестовой копии, чтобы не загрязнять сравнение двух целевых баз. Далее проектная работа объединяет эти проверки.

## 07. Что мы будем делать в практике

**Формат и вход:** проектная практика миграции двух баз. Готовы из принятых будущих результатов baseline, версия истории, две учебные базы, отдельный проверенный резерв и старая версия приложения; перед выдачей проверить условия A. Работа из `project/`, файлы и данные изолированы. Ни один пример выше не является готовым решением задачи.

1. **Подготовить безопасный вход → известные адреса и неизменённое исходное состояние.** Контекст: хотим изменить две разные базы без риска для оригинала. Ученик выбирает по описи изолированного каталога абсолютные пути пустой базы baseline, заполненной проверенной копии и резерва. Для каждой новой целевой базы сначала выставляет в `alembic.ini` `sqlalchemy.url` и её `expected_database_path`, показывает оба разрешённых абсолютных пути и их равенство; отдельно выставляет `DATABASE_URL` приложения на ту же базу. Проверяет существование файла до соединения, затем `current`, `heads`, реальный ID исходной ревизии, опись схемы и две разные строки с шестью полями. На отдельной disposable-цели повторяет отрицательную пробу: меняет только URL, сохраняет expected и видит отказ без появления ошибочного файла; затем восстанавливает согласованную пару. Резерв сверяет через подготовленный способ восстановления в отдельный новый путь. При несоответствии, неизвестной ревизии или занятом пути останавливается; оригинал не открывать на запись. Опора: 01, 06 и паспорта 82.1, 83.1, 84. Локальный результат: записи адресов, baseline ID и сравнения до изменений, подтверждённый резерв. Помощь: вернуться к различию current и heads; разбор покажет, почему один успешный вывод не доказывает правильный файл.
2. **Подготовить metadata и ревизию → проверенный кандидат.** Контекст: старые задачи должны допустить отсутствие описания. В `app/DBase/models.py` ученик сам добавляет nullable `description`, не меняя старые поля и преобразование в публичную модель. На отдельной базе после baseline сначала согласует `sqlalchemy.url` и `expected_database_path`, показывает оба абсолютных пути и их равенство и только затем создаёт кандидат `python -m alembic revision --autogenerate -m "add task description"`, читает файл в `migrations/versions/`, сопоставляет `down_revision` с реальным baseline, оставляет только оправданное добавление nullable колонки без server default и проверяет импорт, upgrade и корректность предусмотренного downgrade. Не меняет базовую ревизию. До запуска проекта на новой модели сначала выполняет upgrade. Опора 02–04. Критерий: кандидат имеет одного известного родителя, не удаляет данные/ограничения, старая фактическая таблица ещё без колонки. Помощь: сверить состояние metadata и базы, а не копировать готовый файл; разбор объяснит, почему автогенерация только предлагает изменения.
3. **Применить к двум базам → одинаковая схема и сохранённые строки.** Контекст: чистая установка и заполненный Planner должны прийти к одной истории. Для каждой базы ученик по очереди выставляет `sqlalchemy.url` и `expected_database_path`, показывает оба разрешённых абсолютных пути и их равенство, после чего выполняет `python -m alembic upgrade head`, проверяет exit status и `current`, сравнивает фактическую таблицу, ограничения и индексы с baseline плюс одна nullable колонка. В заполненной копии сравнивает записанные до upgrade ID, число строк и все шесть старых полей, через `SELECT ... WHERE description IS NULL` подтверждает NULL у обеих старых строк. Пустая база остаётся без строк. Если ошибка или схема неожиданна, прекращает работу, сохраняет наблюдения и возвращается к резерву, не делает stamp или слепой повтор. Опора 01, 03, 04, 06. Локальный критерий: одинаковая структура и новая фактическая revision без потери данных. Помощь: проверить URL и различить схему от version table; разбор покажет оба независимых пути.
4. **Проверить два значения и повтор → подтверждённая неизменность.** Контекст: необязательность не должна стирать уже введённый текст. На изолированных синтетических данных заполненной копии ученик выбирает два известных разных ID, через параметризованный SQL записывает непустой текст `учебное описание` одной строке, оставляя другую NULL; фиксирует commit и читает обе в новом соединении. Перед повтором для заполненной копии снова проверяет URL, expected path и совпадение разрешённых путей; повторяет `python -m alembic upgrade head`, снова читает обе строки и старые поля. Значения должны остаться текстом и NULL соответственно; неизвестный ID или отсутствие строки это не успех. Опора 04 и 06. Помощь: сравнить `IS NULL` и пустую строку; разбор показывает причинную связь с уже применённой revision.
5. **Согласовать инициализацию и проверить прежние интерфейсы → один штатный путь.** Контекст: старая команда не должна обходить историю. В `app/DBase/init_db.py` ученик самостоятельно заменяет прежний путь понятным ненулевым отказом с инструкцией использовать Alembic; прямой вызов `create_schema()` тоже явно отказывает без создания схемы, а не только запуск модуля; обновляет зависимые инструкции и тесты в учебной копии, сохраняя отдельный исторический тест конкретной baseline на зафиксированном образце и отдельные тесты актуальной head-схемы, созданной через историю. Изолированные тесты используют `Config` того же ini и обе явно установленные main options своего `tmp_path` по примеру 06; `env.py` не подменяет их. На отдельной отсутствующей и существующей тестовых базах проверяет отказ без создания файла или изменения схемы и данных, затем на новой тестовой базе согласует URL и expected path, показывает оба абсолютных пути и их равенство и применяет историю. На отдельной копии после upgrade сравнивает прежний `GET /tasks`, создание через старый `POST /tasks`, CLI `list` и `add`, затем новое чтение после перезапуска. Сверяет прежние публичные поля и отсутствие description/tags в API/CLI, не используя health как доказательство чтения. Для POST использовать `{"title":"Проверить отчёт","priority":2}` и ожидать 201 с `id`, `title`, `priority`, `is_done`; сверить GET и созданную строку после перезапуска. Эти поля подтверждены `app/routers/tasks/router.py` и `schemas.py` входного SHA. Опора 05–06. Помощь: отличить отказ старой команды от успешного пути миграции; разбор объяснит, почему создание схемы без истории не равно upgrade.

Эти шаги образуют цепочку: проверенные входы позволяют подготовить ревизию, две независимые проверки показывают её эффект, повтор и отдельный процесс проверяют сохранение состояния, а отказ старой команды не оставляет обхода истории. Возврат к нужному объяснению допустим; будущие тестовые формулировки и эталоны создаются на Stage 3. Для следующего эксперимента самостоятельно создать и проверить отдельно снимок после расширения. До работы вернуться к полному независимому примеру и собственной пробе Backup API из планируемых подготовки снимка и восстановления: SOURCE это существующий файл, DEST это новый свободный путь, занятый путь вызывает отказ без перезаписи. Повторить малую пробу на отдельной демонстрационной базе, убедиться в чтении восстановленной копии и отказе при занятом DEST. Из `project/` выбрать по описи заполненную синтетическую базу после расширения, например `data/lesson84_1/filled-upgraded.sqlite3`, и проверить два новых разных свободных пути. Вызвать `python -m app.DBase.backup_snapshot data/lesson84_1/filled-upgraded.sqlite3 data/lesson84_1/post-upgrade-snapshot.sqlite3`: SOURCE это проверенная заполненная база после расширения, DEST новый snapshot. Только после успешного вызова выполнить `python -m app.DBase.backup_snapshot data/lesson84_1/post-upgrade-snapshot.sqlite3 data/lesson84_1/post-upgrade-restored.sqlite3`: SOURCE полученный snapshot, DEST другой новый восстановленный путь. В восстановленной копии сверить revision, схему, старые поля, NULL и текст. Отсутствие обёртки, занятый путь или неуспешное восстановление останавливают передачу. Исходный резерв до расширения остаётся отдельно, его не перезаписывают.
