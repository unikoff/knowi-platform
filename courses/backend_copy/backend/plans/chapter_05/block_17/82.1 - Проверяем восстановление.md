## 00. Вступление

Подводка: снимок можно открыть, но пока неизвестно, вернутся ли нужные задачи и их ограничения. Планируется одна группа `LinkedNotes variant="connected"` без интерактива.

1. **Точка старта:** есть подтверждаемый снимок и опись учебной базы.
2. **Новый вопрос:** как убедиться, что из снимка получается отдельная пригодная база, а не просто существующий файл?
3. **Результат:** восстановить копию и собрать разные свидетельства её пригодности.

Снимок служит входом опыта, опись задаёт ожидаемый результат, а отдельный путь позволяет проверить восстановление, сохранив оба источника. После этого объясняем роли файлов и безопасную последовательность.

## 01. Три адреса и право на восстановление

- **Что объяснить:** исходная база содержит учебные данные; снимок зафиксировал их на момент резервирования; восстановление создаёт третью базу. Успех открытия снимка ещё не равен успешному восстановлению. При совпадении адресов, занятом назначении, непонятном источнике или ошибке прежней операции остановиться до записи.
- **Независимый пример для автора Stage 3:** в отдельном каталоге `demo_restore/` задать три пути `notes.sqlite3`, `notes-snapshot.sqlite3`, `notes-restored.sqlite3`. Показать абсолютные разрешённые пути через `Path(...).resolve()` и существование через `is_file()` / `exists()` с объяснением импорта `from pathlib import Path`, точек, скобок и возвращаемых логических значений. Первые два уже подготовлены полностью на синтетических заметках; третий отсутствует. Сравнить пути попарно и объяснить, что одинаковый адрес или уже занятый третий путь означает отказ. Путь к каталогу выделяется заранее, проверка сама не создаёт файл. Ограничение: при символьных ссылках и иных одновременных изменениях простая проверка не является универсальной защитой; здесь каталог изолирован, без сторонних изменений.
- **Первая проба:** на другом наборе трёх названий ученик определяет допустимость отдельного нового пути, затем выбирает вариант с совпадением и объясняет отказ. Наблюдение: только все три разные и новый конечный путь разрешают продолжение; при ошибке вернуться к ролям путей и повторить на новом наборе.
- **Визуал:** схема трёх подписанных файлов показывает направление передачи и остановку на занятых/совпадающих путях. Варианты состояния: три разных адреса, совпадение, занятое назначение; обратная связь называет причину отказа, а не просто цвет. Схема не должна раскрывать конкретные адреса практики.
- **Переход и опора:** различив роли, можно безопасно передать снимок как источник следующей операции; `resolve` помогает сравнению, а исключительное создание защищает саму запись.

## 02. Восстановление через согласованную операцию

- **Механизм:** восстановление здесь использует тот же приём SQLite Backup API в обратном направлении: источником становится снимок, целью новый файл. Показать, что `source_connection.backup(destination_connection)` вызывается у источника, принимает соединение назначения и не проверяет занятость пути. До подключения проверить существование источника и различие адресов; зарезервировать новое назначение `Path.open("xb")`, закрыть файловый объект, открыть два соединения и закрыть оба даже при исключении. `sqlite3.connect` на отсутствующем пути может создать пустую БД, поэтому существование источника проверяется заранее. Исключительное создание вызывает `FileExistsError` для занятого пути. При ошибке после резервирования считать новый файл частичным и не принимать его; не удалять и не изменять чужой ранее существовавший файл. В изолированном каталоге действие без исключения и открытие результата ещё требуют последующих проверок.
- **Полный независимый пример:** автор приводит законченную программу для `demo_restore/`: создаёт синтетическую таблицу `notes(id, body)` и две известные строки, фиксирует ожидаемые ID и текст; готовит снимок этой базы; после закрытия соединений восстанавливает его в `notes-restored.sqlite3` описанным способом. В отдельной ветви заранее создаёт `occupied.bin` с известными байтами, сохраняет `Path.read_bytes()` до попытки, показывает отказ `open("xb")` и равные байты после. В успешной ветви открывает восстановленную базу и получает обе строки. Разобрать импорты `sqlite3` и `Path`, аргументы `connect`, `backup`, режим `xb`, `with` для файла, `try/finally` и `close()` для соединений: контекст соединения сам по себе не закрывает его. Пояснить синтаксис и результат на экране, направление копирования и причину неизменности занятого файла. Код полностью представлен в будущей теории, но использует другие таблицу и имена, не решение Planner.
- **Первая проба:** ученик на другом синтетическом снимке сам выбирает источник и новую цель, выполняет восстановление, открывает результат и сравнивает известные строки; отдельно прогнозирует отказ при занятом пути. Ожидание: строки совпадают, занятый файл не меняется; при неверном направлении вернуться к вызывающему соединению и аргументу.
- **Перенос и отдельная проба интерфейса:** принятый план «Получаем согласованный снимок» предусматривает модуль `app/DBase/backup_snapshot.py` с командой из `project/`: `.\.venv\Scripts\python.exe -m app.DBase.backup_snapshot SOURCE DEST`. `-m` запускает модуль; `SOURCE` и `DEST` обозначают два позиционных файловых пути, не SQL URL и не буквальные имена файлов; флагов нет. Для восстановления первый путь указывает на успешно созданный снимок, второй на ещё не существующий файл. Пути с пробелами заключают в кавычки. До практики автор показывает полный независимый вызов с подготовленным `demo_restore/notes-snapshot.sqlite3` и новым `demo_restore/notes-command-copy.sqlite3`, открытие результата и сравнение обеих строк; занятую цель проверяет отдельно без изменения её байтов. Ученик затем на другом синтетическом снимке сам подставляет два пути, выполняет команду и открывает новую копию; при занятом назначении ожидает отказ, при успехе видит известные строки. Неверный порядок путей разбирается до повторной пробы на другом свободном имени. Перед выдачей проверить наличие реализации и соответствие этой команде и защите путей; на входном SHA её нет. При несовпадении устранить стык до выдачи, не объявлять плановый интерфейс существующим сейчас.
- **Переход:** открываемая отдельная база ещё может быть технически повреждена или содержать не те данные.

## 03. Техническая проверка и её предел

- **Что объяснить:** открываем восстановленный файл как отдельную базу для чтения, а не подключаемся к исходнику по привычному URL. `PRAGMA integrity_check;` возвращает одну строку `ok`, если проверка не обнаружила ошибок, либо сообщения об ошибках; исключение открытия/чтения тоже означает отказ от приёмки. Это проверка структуры SQLite, не проверка полноты задач. Она не проверяет нарушения внешних ключей; при наличии FK отдельно использовать `PRAGMA foreign_key_check;`, пустой результат означает отсутствие обнаруженных нарушений.
- **Полный независимый пример:** из учебного корня запустить `.\.venv\Scripts\python.exe` без `-m`, объяснив приглашение Python и завершение `exit()`; в интерактивном Python импортировать `sqlite3` и `Path`, назначить `path` существующему `demo_restore/notes-restored.sqlite3`, открыть его через URI только для чтения: `sqlite3.connect(path.resolve().as_uri() + "?mode=ro", uri=True)`. Автор показывает полный связный ввод и результат с безопасным закрытием в `finally`, а для последующих SQL-запросов явно показывает, что выражения вводятся в Python и соединение открывают заново либо сохраняют открытым до завершения проверок. Объяснить `as_uri`, добавление параметра, `uri=True`, `execute(...).fetchall()` и закрытие соединения. Показать ожидаемые строки `[('ok',)]` и пустой результат `foreign_key_check` на образце без нарушений; на заранее подготовленном текстовом файле вместо SQLite показать исключение при запросе и отказ, без создания новой базы. Пояснить, что нельзя принимать отсутствие исключения самого `connect` без чтения схемы или PRAGMA.
- **Первая проба:** ученик выполняет те же проверки на отдельной синтетической копии и решает, можно ли по одному `ok` утверждать наличие нужной заметки. Ответ: нет, нужны отдельные сравнения. При ошибке вернуться к назначению PRAGMA и повторить на изменённом наборе.
- **Опора:** читать все строки результата; принимать техническую проверку только при единственном `ok`, отсутствии ошибок открытия и отсутствии нарушений FK, если они есть. Следом проверяем сам договор схемы.

## 04. Сверка схемы и ограничений

- **Механизм:** реальная схема хранится в базе, а модель Python описывает ожидаемую структуру; наличие таблицы по имени не доказывает типы и ограничения. Опись из темы сверки схемы является ожидаемой стороной сравнения, восстановленная база фактической. Проверять столбцы, типы, PK, nullable, SQL-default, CHECK, индексы, FK, представления и триггеры при наличии. Python-default не превращать автоматически в SQL-default.
- **Полный независимый пример:** на восстановленном `notes` показать запрос `SELECT type, name, tbl_name, sql FROM sqlite_schema ORDER BY type, name;` и `PRAGMA table_info('notes');`, `PRAGMA index_list('notes');`, `PRAGMA foreign_key_list('notes');`; для каждого найденного индекса показать `PRAGMA index_info('имя_индекса');`. Объяснить строки и поля результата, SQL в `sqlite_schema` для CHECK и объектов, отсутствие SQL у автоматически созданного индекса, пустые списки как отсутствие соответствующих объектов, а не как ошибку. Сравнить с заранее показанной описью `notes`; в отдельном заранее подготовленном одноразовом образце отсутствует CHECK, что видно в DDL при одинаковом имени таблицы. Не утверждать, что текстовое равенство DDL доказывает семантическую эквивалентность любых схем.
- **Первая проба:** ученик получает опись другой маленькой таблицы и её наблюдаемые результаты; сам находит недостающее ограничение, затем на восстановленной синтетической копии выполняет чтение и фиксирует совпадение. Ошибка «таблица есть, значит всё совпало» выявляется отсутствующим CHECK; возврат к содержимому DDL и описи.
- **Визуал:** сравнение ожидаемой и фактической схемы по строкам с состояниями «совпадает», «отсутствует», «не проверено»; выбор несовпадения показывает конкретное поле и причину отказа. Это подготовка к сравнению структуры, а не готовая таблица Planner.
- **Переход:** правильная схема допускает отсутствие или изменение строк, поэтому далее сравниваем значения.

## 05. Число строк, ID и все значения

- **Механизм:** количество отлавливает потерю строк, но равное количество допускает замену ID или полей. Сравнивать упорядоченные по ID строки и каждое поле, включая внутренние; не полагаться на порядок без `ORDER BY`. На входном Planner поля именно `id`, `title`, `priority`, `is_done`, `tags`, `title_normalized`. Значения сравниваются с фактической описью, не с предположением об ID; JSON tags сравнивать по значениям, не делать вывод только по публичному API.
- **Полный независимый пример:** в восстановленных `notes` использовать `SELECT COUNT(*) FROM notes;` и `SELECT id, body FROM notes ORDER BY id;`; объяснить `COUNT(*)`, выбор столбцов, сортировку, `execute`/`fetchall`, полученные кортежи и сравнение со списком ожидаемых двух строк. Показать второй синтетический образец с тем же количеством, но изменённым текстом: счётчик совпадает, посрочное сравнение нет. Третий образец с одной строкой выявляется счётчиком. Эти данные не совпадают с будущими задачами Planner.
- **Первая проба:** ученик сам сравнивает две строки другого независимого набора, где число и ID одинаковы, а одно значение отличается; называет точное поле и отказ. При затруднении вернуться к сравнению кортежей, затем повторить на новой паре.
- **Визуал:** небольшая трассировка двух сравнений: сначала счётчик, затем строки по ID; при равном числе, но изменённом значении обратная связь отмечает несовпадающую ячейку и объясняет, почему первый тест пропустил ошибку.
- **Переход:** сверка SQL подтверждает данные и внутренние поля, а теперь проверим обычное чтение сборкой приложения.

## 06. Чтение через обычную сборку с явным URL

- **Механизм:** `load_settings` берёт `DATABASE_URL` из окружения; относительный путь SQLite разрешается от `project/`, а явная переменная имеет приоритет над `.env`. Новый процесс получает настройки при старте. Показать до запуска, что URL указывает на существующий восстановленный файл, а не на исходник или снимок. Читать через обычный CLI `app.main`, который использует `load_settings`, `make_engine`, фабрику Session и `PlannerService`; `list` и `find` не изменяют записи. Публичный вывод не показывает внутренние tags и `title_normalized`, поэтому не заменяет SQL-сравнение.
- **Полный независимый пример:** на малом учебном приложении, не Planner, показать PowerShell из его корня: назначение `$env:DATABASE_URL = 'sqlite:///./data/demo-restored.sqlite3'`, проверку значения и соответствующего существующего пути, запуск его показанного модульного entry point тем же `.venv\Scripts\python.exe`, чтение одной известной синтетической строки и выход процесса. Объяснить `sqlite:///` и относительный путь, `$env:`, модульный `-m`, выбор рабочего каталога и интерпретатора; затем на Planner отдельно показать реальный путь запуска `.\.venv\Scripts\python.exe -m app.main` и команды меню `list`, `find`, ID, `exit` на других учебных данных. До примера напомнить, как открыть PowerShell в `project/`, проверить `.\.venv\Scripts\python.exe --version` и наличие рабочей среды по `project/README.md`; при отсутствии среды остановиться и восстановить окружение по README, не устанавливать пакеты во время этого урока. В теории автор даёт полноценный пример этих проверок и малую пробу выбора правильного пути.
- **Первая проба:** на другом безопасном URL ученик определяет разрешённый путь и ожидаемый файл, затем читает известную запись синтетического приложения. При несовпадении пути или отсутствии файла не запускает процесс, возвращается к настройке URL. Возвращать или закрывать учебный терминал после проверки, чтобы переменная не повлияла на последующие команды.
- **Переход:** осталось соединить разные свидетельства и проверить отрицательный образец.

## 07. Решение о пригодности и отрицательный случай

- **Механизм:** принять восстановление можно только при одновременном выполнении входных условий, успешном открытии, технической проверке, совпадении схемы и всех данных и чтении приложением. Любое несовпадение, невозможность открыть файл или отсутствие свидетельства означает «не принято», а не предположение об успехе. `integrity_check = ok` на неполной базе возможно: технически корректная структура не гарантирует нужные записи.
- **Полный независимый пример:** автор готовит два файла заметок с одинаковой корректной схемой: один содержит две ожидаемые строки, второй только одну. Для обоих показывает `integrity_check`, схему, число и строки, затем решение: первый соответствует описи, второй отклоняется из-за отсутствующего ID при техническом `ok`. Дополнительно неоткрываемый текстовый файл получает отказ на чтении, без требования чинить его. Оба примера в отдельном каталоге, исходный снимок не меняется.
- **Первая проба:** ученик получает другую маленькую опись и результаты проверок, сам выбирает принятие или отказ и называет отсутствующее доказательство; при ошибке возвращается к различию технического и содержательного результата.
- **Визуал:** таблица доказательств со статусами «совпало», «ошибка», «не проверено»; выбор `ok` без строк даёт обратную связь «содержимое ещё не проверено». Никакое непроверенное поле не даёт принятия.

## 08. Что мы будем делать в практике

**Формат и вход:** проектная практика восстановления в изолированной копии `project/`. Ученик получает подтверждённый отдельный снимок из успешной ветви резервирования, исходный путь, полную опись схемы и данных и созданную ранее обёртку; это планируемая A, которую нужно проверить до выдачи. Назначение восстановления: новый `project/data/restored-check.sqlite3`; если занят, выбрать другой новый путь и отразить его в URL, не перезаписывать. Для отрицательного случая автор Stage 3 заранее предоставляет отдельный `project/data/incomplete-check.sqlite3` с той же исходной схемой и неполным набором относительно переданной синтетической описи: готовит его из отдельной копии, удалив в ней одну известную строку, и до выдачи проверяет `ok`, различие количества и ID. Ни исходник, ни снимок при подготовке не изменяются. Никаких скрытых данных для сравнения нет. При отсутствии любой передачи сначала восстановить её в соответствующей теме.

1. **Проверить вход и восстановить.** Контекст: нужно удостовериться, что снимок можно вернуть, не затрагивая рабочую базу. Условие: назови абсолютные пути исходника и снимка из фактической передачи и предложенный путь нового файла; проверь существование первых двух, отсутствие третьего и попарное различие. Останови учебные API/CLI и закрой соединения; проверь подтверждение успеха предыдущего backup и наличие описи. Сохрани прочитанные через `Path.read_bytes()` байты обоих небольших учебных файлов в отдельных переменных, как показано в независимом примере защиты занятого пути, и после восстановления сравни повторное чтение с сохранёнными значениями; для вызова модуля используй отдельный PowerShell, сохранив Python-сеанс с переменными. Самостоятельно вызови из `project/` `.\.venv\Scripts\python.exe -m app.DBase.backup_snapshot SOURCE DEST`, подставив на место `SOURCE` проверенный снимок, а на место `DEST` новый `data/restored-check.sqlite3` или другой выбранный свободный путь. Пути с пробелами заключи в кавычки; не используй непроверенный путь и не продолжай после ошибки. Опора: 01–02 и конкретная B резервирования. Локальный результат: новая отдельная база открывается, исходник и снимок побайтно не изменились; занятое назначение или неверный источник дают отказ без перезаписи. Помощь: вернуться к трём ролям и направлению соединений; будущий разбор объясняет, почему `backup` сам не защищает целевой путь и как распознаётся частичный результат.
2. **Проверить структуру.** Контекст: существование файла не показывает его пригодность. Открой только что восстановленный файл для чтения способом из 03; выполни `PRAGMA integrity_check;`, при наличии FK также `PRAGMA foreign_key_check;`. Затем самостоятельно прочитай `sqlite_schema`, `PRAGMA table_info('tasks');`, `PRAGMA index_list('tasks');`, информацию по найденным индексам и `PRAGMA foreign_key_list('tasks');`. Сравни фактические столбцы, типы, PK, nullable, SQL-default, CHECK, индексы и, если есть, FK, представления и триггеры с описью. Опора: 03–04 и запланированная опись. Локальный результат: единственная строка `ok`, нет нарушений FK и каждое поле договора схемы отмечено как совпавшее или конкретное расхождение; ошибка чтения или расхождение прекращает приёмку. Помощь: сначала найти DDL и строку нужного столбца; разбор показывает, почему `table_info` одного недостаточно для CHECK и почему Python-default и SQL-default различаются.
3. **Сверить содержимое и приложение.** Контекст: корректная структура может хранить не те задачи. На восстановленной базе самостоятельно выполни `SELECT COUNT(*) FROM tasks;` и `SELECT id, title, priority, is_done, tags, title_normalized FROM tasks ORDER BY id;`. Сверь число, все ID и шесть значений каждой строки с описью, включая tags и нормализованное название. Затем в PowerShell из `project/` проверь существующий путь и назначь `$env:DATABASE_URL = 'sqlite:///./data/restored-check.sqlite3'` либо соответствующий выбранному новому пути URL; проверь переменную и запусти `.\.venv\Scripts\python.exe -m app.main`. В меню выполни `list`, `find`, существующий ID из описи и `exit`; сопоставь доступные публичные поля. Опора: 05–06. Локальный результат: число и каждая строка совпали, новый CLI-процесс показывает ожидаемую задачу. Равное число с отличающимся значением или ID не проходит; `tags` и нормализованное поле проверяются SQL, не выводом CLI. Помощь: сопоставлять строки по ID, затем поля; разбор демонстрирует случай равного количества с различием. Не запускать `init_db`, изменение или импорт; при неверном URL остановиться до запуска.
4. **Отклонить неполный образец и зафиксировать вывод.** Контекст: исправная по структуре база может потерять данные. На предоставленном `incomplete-check.sqlite3` повтори открытие для чтения, `integrity_check`, счётчик и список ID с полями, сравни с той же описью. Самостоятельно назови обнаруженный отсутствующий ID и причину отказа, даже если результат целостности `ok`. Если образец не открывается, зафиксируй ошибку и также отклони его; отсутствие результата нельзя считать совпадением. Опора: 03, 05 и 07. Локальный результат: неполный файл не принят, а для восстановленного файла зафиксированы отдельные результаты проверки схемы, всех значений и чтения CLI. Помощь: различить вопрос «цел ли файл» и «все ли данные на месте»; разбор сопоставляет `ok` с отсутствующей строкой и показывает место отказа без исправления снимка.

Первый результат становится входом последующих проверок; техническая проверка, схема и полные данные дополняют друг друга, а CLI подтверждает обычное чтение на явном адресе. Итог принимается только при всех совпадениях и успешном отрицательном случае. Ученик может возвращаться к указанным разделам; фиксируются конкретные наблюдения, не личные данные. По окончании закрыть процесс и учебный терминал. Автопроверка или её тип паспортом не предписаны; ручные наблюдения не выдавать за выполненные здесь тесты.
