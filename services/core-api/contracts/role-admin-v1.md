# Role admin contract v1 — CORP-527

Status: **contract for implementation**, not a description of the deployed API. DTOs and their JSON Schema are in `role-admin-v1.py` and `role-admin-v1.schema.json`; machine-readable HTTP paths are in `role-admin-v1.openapi.json`. All JSON objects reject undeclared fields. All timestamps have an explicit UTC offset; stored instants are UTC. Calendar dates/month boundaries and the 36-hour rule use UTC+03:00. User and resource IDs are positive integers; the distinct stable account lifecycle identifier `account_ref` is a UUID, never the integer ID or email. Course IDs are enabled product catalog IDs, never lesson track IDs. `null` and omission are distinct: every field in each DTO is required, including nullable fields. New command bodies are JSON; all mutations require `Idempotency-Key` header: a client-generated UUID string. Its value is the `command_id` in audit. User-targeting quota/subscription/admin-role mutations additionally require `X-Account-Ref` UUID matching the current target lifecycle under lock; mismatch is 409. Assignment includes the same reference in `AssignmentCommand`. All endpoints require the existing `session` cookie; no role/scope headers are authoritative.

## HTTP operations

Paths include the `/api` prefix; a reverse-proxy prefix such as `/platform` may precede it. All successes return 200 JSON. Columns show request DTO and success DTO; `—` means no body. Path IDs and `course_id` are required. `year` (2000–2100), `month` (1–12), `owner_id` (positive integer) query parameters are mandatory where shown. Lists use `cursor` optional opaque string and `limit` optional integer 1–100, default 50, unless stated otherwise. Cursors bind the authorization scope and filters; an invalid/mismatched cursor is 400, not a fallback. Permission is checked before filtering/pagination/aggregation. Course scope never defaults to backend.

Course staff means platform admin for the explicit selected course, or the lifecycle-pinned configured leader for that course. Calendar lists expose the active configured leader only. Booking context preserves the student's own future history. Search accepts a complete exact email or a name of at least 3 non-wildcard characters, returning a minimal masked identity. The roster lists distinct accounts with a preserved personal booking for this course (including cancelled and future appointments) or a positive course quota for any month. For accounts without a preserved booking, `last_booking_status` is present and null. A search or platform subscription alone does not add an account. Progress contains only this course's completed lesson/task IDs and timestamps.

In the roster and grant search responses, `username` is a display label with embedded email-like text removed. Partial name lookup uses the same label, including ordinary leading `@handles`. Full email and whole email-like username lookups are exact and case-insensitive. Use `id` and `account_ref` for profile access.

The roster row's `display_booking` is the nearest future booked appointment for this student and course (`kind: upcoming`). If none exists, it is the booked or completed record with the latest start time (`kind: latest`). It is null if that course has no booked or completed record for the student, including when the history contains only cancellations. Start and end are timestamps with an explicit offset, and status is the stored booking status. The selected month changes the quota balance only. `last_booking_status` and the profile booking history retain their previous semantics, including cancellations.

When the roster request supplies both `year` and `month`, each row includes `remaining_lessons` for that Moscow calendar month. It counts course quota granted minus that student's booked or completed appointments in the month. Cancelled appointments and records from other courses do not consume the balance. If there is no quota or usage, the balance is zero. A discrepancy where usage exceeds the grant returns an explicit `null`. With neither month parameter, the field is omitted for backward compatibility. A single month parameter is rejected with 422, and roster cursors are bound to the requested period.

`StudentStatistics` shows the chosen account's chapters, blocks and lesson completions for the named course and is available from both roster and grant search. It returns the same completion decisions and Moscow dates as the learner catalog. Use distinct lesson IDs whose `counts_toward_statistics` is true and whose `completed_on` is within the inclusive range to count completed lessons in a period. The actor and selected target UUIDs must match their current account lifecycles. A stale actor reference returns 401 and a stale or missing target returns 404. For a course leader, selecting a person outside the roster requires the existing current-revision search permission for that course and target. The permission expires after 15 minutes, returning 403 until the person is selected from search again. Roster members and platform administrators do not require search permission. Responses use `Cache-Control: no-store`.

`StudentProfileDetails` uses the same authorization and response cache policy. Its subscription fields describe the account's current platform subscription, independent of the selected month, and are null when there is no subscription. `bookings` contains retained records for the selected student and course whose start falls in the requested UTC+03:00 calendar month, including cancelled appointments and appointments with past teachers or archived slots. Status comes from the booking record. An elapsed appointment remains booked unless the stored status changed. Each entry contains the booking ID, start, end, and status. The results are ordered by descending start and booking ID. `next_cursor` continues the history for the same actor authority, course, target lifecycle and period. The quota endpoint provides the balance separately.

For study-time details, `POST /api/analytics/grants/report` accepts an opt-in body with `student_statistics: true`, `course_id`, `user_id`, `expected_actor_ref` and `expected_target_ref`. Core checks the course authority and exact lifecycles and issues a short-lived `report:student` grant limited to that course and learner. A course leader needs a personal booking in that course or a current-revision search permission for the target; quota membership alone authorizes only Core course data and operations. The original Analytics report grant bodies and permissions remain available.

`CourseStudyTime` reports the last 30 Moscow dates, including today, as of the report snapshot. For each current subscription group, `active_ms` totals measured study time and `learners` counts distinct learners with measured positive study time that day. The mean for a day is the total `active_ms` divided by the total `learners` in the selected groups. Current course leaders and platform administrators are outside both groups. A null group means that no positive observation is available, and `quality: unknown` means coverage is unverified. An unavailable source returns `status: unavailable` and an empty `daily` array without affecting `/overview`. The actor lifecycle and authority revision must match the current session and course authorization. Responses use `Cache-Control: no-store`.

The quota read returns only `QuotaEnvelope` for the explicit course, user and month; it works for both roster entries and a person selected from grant search. The caller supplies that person's `account_ref` as required `X-Account-Ref` UUID. Server checks live course authority and that the integer ID still resolves to the same active lifecycle, returning 404 on a missing or mismatched target; it never returns a global profile or another course's balance. An existing person with no row for this course/month receives a zero-valued quota without creating a row. Apply per-actor rate limiting as for grant search.

`Me.user` retains existing user fields and envelope. `is_admin` is true only for platform admin. The server derives `role` from live admin truth then active leadership, else `user`; an admin cannot also hold active leadership. `course_id` is null for user/admin and the single assigned course for leader. A role revision changes whenever staff authority changes; it is an invalidation hint, not authorization. Capabilities are: user `[]`; leader `[course.read, course.roster, course.search_grant, course.quota.grant, course.subscription.extend, course.calendar.manage]`; admin those six plus `[platform.read, platform.manage]`. Each request still verifies resource authorization. Existing personal learning and booking remain available to all three roles. Admin-role grant to an active leader conflicts until leadership is explicitly revoked; removing the last admin conflicts. The student slot list omits occupied slots belonging to other students and never includes another student's identity.

Quota is keyed `(course_id,user_id,year,month)` and consumed in the slot's UTC+03 month. Subscription is one shared platform entitlement, never course-owned. `SubscriptionExtend` computes `max(now,current_until)+days`, without shortening paid time; it does not create quota. Course quota grant adds only to the selected course/month and neither grants subscription nor books. Admin reset sets until and plan to null only after explicit confirmation; leaders cannot reset, shorten, revoke, manage roles, delete accounts or read platform data. `CourseOverview.period` applies to event/quota counters; `roster_count` counts the distinct roster accounts across all months and `course_activity_days=null` means unavailable, not zero. Platform `active_subscribers` counts distinct accounts with unexpired shared subscription once even across courses. `completed_lessons` is course-attributed, not global activity.

The optional `CourseOverview.course_trends` extension covers the last 30 Moscow calendar dates including today, irrespective of `period`. Each available series contains 30 date-sorted rows with counts by current active platform subscription. A `null` daily count means no observation with unknown coverage. An unavailable series contains an empty `daily` array. The series contain aggregate counts for the selected course only and do not extend the leader's access to student-level reports. Completion cohorts use authoritative Core receipts independently of the legacy Analytics completion offload, which has a different roster scope. The existing visits total is not a source for cohort-split visits.

The visitor series requires an enabled Analytics grant signer and a private `PYMENTOR_ANALYTICS_QUERY_URL`. The internal query transport requires HTTPS except on loopback; the current Helm Query service does not itself provide TLS. Each request is bounded to 1,000 candidate subjects and 300,000 matching facts, and returns `unavailable` rather than a truncated result when a bound or a privacy check fails. Coverage remains `unknown`; counts represent received observations, not proof that all visits were collected.

Staff calendar context returns `course_id` and at most one active owner `[{id, username, active, pending_slots}]`; the compatibility field `pending_slots` is zero. An unconfigured course returns an empty list. Former-owner snapshots remain in booking history but are not offered as a public calendar or transfer workflow.

`Me.user.account_ref` is the server-owned opaque UUID of the actor account lifecycle, stable across requests and email changes. It is distinct from the integer ID and changes on a genuinely new lifecycle. Client pending-command fingerprints bind it along with authority revision, target reference and payload, preventing numeric-ID reuse from inheriting a previous account's unresolved command metadata. Logout clears sensitive UI data; opaque unresolved keys may remain isolated for at most24 hours without automatic replay. An expired key or changed authority requires reconciliation, never a silent fresh-key retry of an unknown outcome.

`SubscriptionQuotaGrant` combines the two writes in one transaction for the selected student. The request requires `X-Actor-Ref`, `X-Account-Ref` and one `Idempotency-Key`. It adds `add` lessons to the named course and Moscow calendar month and extends the platform subscription by `days`. Both audit records share the command ID and the same trimmed reason. `SubscriptionQuotaResult` returns the platform subscription fields and the updated monthly `quota`. Replays require current authorization for the course and target. Any failure before commit rolls back both changes and their audit records.

## Errors and consistency

For new paths use `Error` (`detail` human-readable, `code` stable): 400 `invalid_cursor`, 401 `unauthenticated`, 403 `forbidden` (including revoked leader), 404 `not_found` (missing/disabled course or inaccessible target/slot; do not leak existence), 409 `conflict` (including duplicate key with different operation/payload, slot taken, overlap, insufficient quota, last admin or assignment conflict), 422 `invalid_request`, 429 `rate_limited`, 503 `unavailable`. Return `Retry-After` on 429/503 when known. Validation errors use this same shape on new endpoints. Specific authorization/validity checks do not replace one another: a leader's own course path paired with a foreign slot is 404, not access to that slot. Errors are never cached as successful empty results.

Keys are scoped to `(actor lifecycle ID, operation, key)` with canonical request payload including method, path/resource, scope, body and relevant query. Same key/same payload returns the persisted original status and body, only after rechecking current authority and target lifecycle; revoked/deleted actors cannot retrieve sensitive cached results. Different payload within that scope is 409. Retain command/result and audit durably for at least 30 days; never auto-retry after retention expiry without reconciliation. Persist idempotency record, mutation, audit, and transactional outbox atomically; no external send before commit. A timeout means unknown outcome: retry the same key during retention, do not issue a new key without reconciliation. Concurrent different keys serialize on relevant resource locks and both valid increments survive. Search is rate-limited per actor and paginated; precise operational rate configuration is server-owned.

Use one order across all command types: lock lifecycle identities (actor, target, and affected owner/student IDs in ascending ID order); then platform-admin invariant and active assignment rows (course IDs ascending, then user IDs ascending); then subscription row; then quota keys `(course_id,user_id,year,month)` lexicographically; then owner/date calendar locks ordered `(owner_id, local_date)`; then student/date locks ordered `(student_id,local_date)`; then slots/booking rows ordered by ID; finally idempotency/audit/outbox writes. Acquire the needed subset in this order; cover every local date touched by an interval. Missing-key creation uses transaction-scoped keyed/advisory locks or equivalent uniqueness-safe upserts, with deterministic ordering. Revocation/demotion/deletion and staff commands share the same identity/assignment locks and recheck current authority and target lifecycle under lock before commit. If the command wins the lock it commits before revocation; if revocation wins the command fails. Last-admin guard is protected by the same global admin invariant lock. DB uniqueness/exclusion constraints and atomic updates remain final guards. Audit includes actor and actual role/authority, target lifecycle ID, action, scope/course, before/after/delta, reason, timestamp and command ID; do not put email in Analytics events.

Account deletion uses the existing guarded lifecycle deletion flow, coordinated with the above locks. Remove or irreversibly anonymize subject-linked booking history, audit actor/target identifiers and their account references, user-supplied reasons and before/after data, cached idempotent responses, search projections and notification subjects/payloads; retain only non-identifying operational facts where allowed by the existing deletion policy. Suppress or redact pending outbox delivery in that same guarded lifecycle and clean external session/notification sinks using the existing durable cleanup protocol. Deleted users must not reappear in roster, progress, search, platform profiles or replayed response bodies, even after integer ID reuse. An applied bootstrap marker whose subject is deleted becomes a subject-free retired marker; it must not reassign the role to a new account with the same email. R2/R8 must test deletion interleaved with staff mutation and delayed notification delivery. The contract does not authorize adding personal data to retained audit.

Booking atomically checks course/owner, slot availability, course quota and cross-course overlaps, then claims the slot and writes history and outbox. Cancellation is allowed at least 36 hours before start, transitions once and restores quota once. Archive only an unbooked slot; historical bookings remain durable. A non-cancelled booking becomes completed at end time without asserting attendance. Owner conflicts and future appointments require an operator migration; no public transfer endpoint exists.

Preserved legacy bookings may lack the actual booking creation timestamp: the old slot `created_at` records slot creation, not booking creation. `Booking.created_at` is nullable only when `legacy_coverage=true`; new bookings set `legacy_coverage=false` and require their actual timestamp. Do not substitute the slot's date/time or invent lost cancellation/attendance history. Clients must render an explicit unknown-history state for null timestamps. This metadata does not change the current/future slot time or erase a retained booking.

On account deletion, a surviving student's booking history may have `owner_at_booking_id=null` after owner anonymization. An instructor with active future booked slots cannot be deleted through administrative APIs until those paid appointments are safely resolved (409); free future slots may be archived. Historical slot deletion conflicts return 409. Existing privacy cleanup and account lifecycle guards remain mandatory.

An anonymized audit operation may have `reason=null` alongside redacted actor/target references and before/after payloads. A non-anonymized operation still requires its reason. Clients display the redacted state without reconstructing names, emails or free-form reasons from another source.

Audit `actor_role` additionally permits `system` for operator/bootstrap automation with no human actor ID; this is an audit actor category, not a fourth assignable user role. The three account roles remain user/leader/admin.

## Bootstrap and compatibility

`GET /api/user/booking-mode` exposes the current booking cutover state as `legacy` or `scoped` with `Cache-Control: no-store`. A missing cutover record returns 503. In legacy mode the primary `backend` workspace uses the legacy schedule, and platform administrators can use the legacy admin panel there. Clients keep course-scoped authorization in scoped mode. The mode signal does not grant authority or replace the transaction checks on booking writes.

Leader configuration defaults to the optional positive `leader_user_id` in each course manifest. A deployment can instead set `KNOWI_COURSE_LEADER_IDS_JSON` to a JSON object containing exactly every enabled course ID, each mapped to a unique positive integer or `null` (for example, `{"backend": 42, "backend_copy": null}`). Invalid JSON, duplicate keys or IDs, and missing or unknown courses fail closed. The setting supplies IDs only; it does not grant privileges. A guarded operator dry-run/apply pins the first valid assignment to its account lifecycle and synchronizes the SQL projection. Missing, unverified, admin, duplicate, conflicting, revoked, deleted or recycled identities fail closed with a reason; an existing matching assignment can be pinned. A changed owner or incompatible future slots requires an operator migration, never an implicit transfer. `kiryukhin_nik@bk.ru` may only be resolved once read-only when preparing a production configuration; email is not runtime authorization.

The runtime captures all enabled leader IDs once on initialization. Editing a manifest in place does not revoke a running process. A configuration change requires draining/stopping all writers, guarded reconciliation, then restarting with the validated configuration; mismatched projections fail closed. Database revocation and deletion retain their transactional lock ordering.

The platform overview's optional course filter scopes its dashboard to personal-booking roster and course records; subscription values describe those members' shared global subscriptions. Global `activity_today` counts distinct users in legacy `user_activity_days` for the Moscow date; dates historically may be supplied by clients and coverage is unknown. For a course, `activity_today.unique_users`, `coverage_since`, and dashboard activity fields are null: course activity requires the future Analytics service and is not inferred from bookings or progress.

Existing `/api/admin/*` remains platform-admin only and keeps its preexisting request/response/error shapes for legacy clients; it never authorizes a leader. Existing legacy booking endpoints must have an explicitly proven migration/compatibility policy before cutover; the new scoped routes do not imply that old writers can run against changed quota keys. `Me.user` additions are additive to JSON but may break strict consumers; coordinate all auth/profile clients, including register/login/profile response DTOs, before rollout. Old admin global subscription/quota writers must be migrated or safely gated, not allowed to violate new idempotency/scope invariants. No unverified paid balance or future booking may disappear due to a missing mapping; ambiguous active data blocks that cutover. No automatic downgrade after course-aware writes.

Client keys include `(user_id, auth_revision, role, scope, course_id, owner_id, filters)`; logout, revocation, identity/course change clear staff data and discard stale responses. Unknown/disabled resources and unavailable data never silently default to backend or zero. Fixture examples and the checks in `test_role_admin_contract.py` test design only; runtime, database, security enforcement and browser remain R2–R8 acceptance work.
